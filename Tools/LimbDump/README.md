# 팔다리 폴리라인 덤프 (Tools/LimbDump)

```bash
Tools/LimbDump/build.sh < cases.tsv     # 프로덕션 좌표를 탭 구분으로
python3 Tools/LimbDump/compare.py       # 병합 전/후 대조 → 종료코드 0 이어야 한다
```

## 왜 있는가

2026-09-03 **마디 병합**(리더 판정 CH-8)의 채택 근거는 *"조형이 바뀌지 않는다"* 하나였다.
그 문장은 **좌표가 같다**는 뜻이고, 좌표가 같은지는 말이 아니라 숫자로만 알 수 있다.

`Tools/ShapeDump`와 같은 원리다 — Unity를 띄우지 않고 Unity 동봉 Roslyn으로
**프로덕션 `States/LimbCurveRenderer.cs`를 한 줄도 고치지 않고** 컴파일해 실제로 실행한다.
흉내내는 것은 `UnityEngine`(`Shim.cs`)뿐이고 **기하 수식은 전부 프로덕션 그대로**다.

## `compare.py`가 대조하는 넷

| # | 대조 | 기대값의 출처 |
|---|---|---|
| (1) | 병합 렌더러 9점 ↔ 병합 이전 두 렌더러의 5+5점을 위 마디 좌표계로 옮긴 것 | 프로덕션 static 두 개(옛 `BuildCurve`가 문자 그대로 이 둘이었다) |
| (2) | 병합 렌더러 9점 ↔ 초상화 경로(`BuildLimbPolyline`) | 이미 출하 중인 병합 구현 |
| (3) | **새 프리팹의 9점 ↔ 옛 프리팹(HEAD)의 5+5점을 옮긴 것** | ★ **디스크 비트** — 프로덕션 코드를 한 줄도 안 쓴다 |
| (4) | 새 프리팹을 읽었을 때 ↔ **옛 프리팹**을 새 렌더러가 읽었을 때 | 세대 호환(다시 굽기 전에도 그림이 같아야 한다) |

★ (3)이 가장 값어치가 크다. TEAM.md의 *"기대값을 프로덕션 함수로 만들지 마라"* 규칙 그대로,
프로덕션이 틀어져도 이 대조는 **함께 틀어지지 않는다.**

## 2026-09-03 실측 결과

```
(1) 최대 편차 3.1e-08 유닛   (2) 7.2e-05(다리) / 3.7e-04(팔)   (4) 4.0e-08 유닛
(3) 프리팹 비트 최대 편차 1.4e-08 유닛 = 1.15e-06 물리픽셀
```

- (1)(4)는 float32 왕복 오차 수준이다 ⇒ **병합은 좌표를 움직이지 않는다.**
- (2)의 차이는 **의도된 것**이다. 초상화 경로는 관절을 `(0, −Lu)`로 **가정**하고,
  본체는 아래 마디의 **실제 `localPosition`**을 쓴다. 차이 = `Lu − Lu_read`
  (다리 0.375 − 0.37492803, 팔 0.285 − 0.28463042) — **본체 쪽이 더 정확하다.**

## ★ 부수 발견 — 프리팹이 코드 상수와 갈라져 있다 (이 라운드 이전부터)

```
프리팹에 구워진 필렛 비율 0.3500  vs  LimbCurveRenderer.FilletLengthRatio = 0.42
```

`FilletLengthRatio`가 2026-09-01에 0.35 → 0.42로 올라갔는데 **프리팹을 다시 굽지 않았다.**
런타임은 첫 `LateUpdate`에서 전부 다시 굽기 때문에 **화면은 영향이 없고**, 어긋나는 것은
프리팹의 에디터 프리뷰와 `ReadSegmentLength`가 읽는 `Lu`(0.375 → 0.37492803)뿐이다.
**이 라운드는 그 상태를 그대로 보존했다**(비트 동일이 목표였다). 다시 굽는 것은 조형 변경이라
별도 판정이 필요하다 — `compare.py`가 매번 이 줄을 인쇄해 조용히 묻히지 않게 한다.
