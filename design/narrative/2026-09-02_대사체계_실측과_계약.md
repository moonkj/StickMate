## 2. ★ 원칙 1이 깨지는 자리 — 종료 사유 계약

### 2-1. 두 사고는 같은 병이었다

| 사고 | 상태 | 그 안에서 갈린 사실 | 대사가 본 것 |
|---|---|---|---|
| 격파 50/50 전부 "필살기다!" | 판정 상태 | **성공/실패, 릴리즈 사유** | 상태 + `chargeRatio`뿐 |
| 미끄러져 떨어졌는데 완료 대사 | 타이머 상태 | **정상 완료 / 비정상 이탈** | 상태 + 경과 시간뿐 |

> **병명: 상태 ID는 "무엇을 하고 있었나"만 말하고 "어떻게 끝났나"는 말하지 않는다.**
> 원칙 1은 "확정된 상태로부터 파생"이라고 쓰여 있지만, 실제로 필요한 것은
> **"확정된 상태 + 그 상태가 확정한 결과"** 다. `design-motion`이 `ActivityExitReason` 4종을
> `DialogueParams`에 싣자고 한 것은 이 진단과 정확히 같다. **동의한다.** 다만 그것만으로는 안 된다.

### 2-2. 채택 — 종료 사유는 파라미터에 실린다

```
enum ActivityExitReason { Completed, TimedOut, PreconditionLost, ForcedInterrupt }

sealed class ActivityDialogueParams : /* 상태가 IHasDialogueParams로 노출 */
{
    public ActivityExitReason Reason;   // 마지막 박자 재생 여부로 확정된 값(모션 1-4절)
    public int OutcomeCode;             // 행동별 결과 축. 낚시 = Caught/Empty/Aborted
}
```

- **`Completed`의 유일한 판정식은 박자 인덱스다**(모션 1-4절). 경과 시간을 보지 않는다. 동의.
- `Reason`은 **매핑 함수가 읽는 값**이고, 아래 2-3의 **호출부 게이트**와는 역할이 다르다.
  둘 다 필요하다 — 하나는 *무엇을* 말할지, 하나는 *말할지 말지*를 정한다.

### 2-3. ★★ 빠진 절반 — 지금 계약에는 "말하지 않는다"를 표현할 반환값이 없다

`Func<StickmanStateId, object, DialogueLine>`의 반환형 `DialogueLine`은 **구조체**다. 널이 없다.
`AmbientChatter.Resolve`가 표가 비었을 때 `DialogueLine.Say(string.Empty)`를 돌려주는 선례까지 있다.

**그대로 두고 "PreconditionLost는 대사 0건"을 구현하면 이렇게 된다:**

```
return p.Reason == ActivityExitReason.PreconditionLost
    ? DialogueLine.Say("")            // ← 빈 문자열
    : DialogueLine.React("다 캤다!");
```

빈 문자열의 가독예산은 `clamp(0.28 + 0×0.075, 0.62, 2.20) = 0.62초`다. **0이 아니다.**
`TryCreate`는 이걸 정상 대사로 보고 게이트만 통과시키며, `DialogueRequested`가 그대로 나간다.
결과는 **0.62초짜리 빈 말풍선** — 화면에는 아무 글자도 없지만, 그동안 다른 대사가
`CanReplaceVisible`에 막힌다. 침묵이 아니라 **투명한 소음**이다.

> **처방 — 무대사는 매핑 함수가 아니라 호출부가 정한다.**
> ```
> // 상태의 마무리 경로
> if (reason == Completed || reason == TimedOut)          // ← 말할 자격을 여기서 판정
>     _ = new DialogueIntent(context, ActivityLines.Resolve);
> // PreconditionLost / ForcedInterrupt 는 아예 만들지 않는다 = 침묵
> ```
> **근거는 이 저장소에 이미 있다**: `AmbientChatter.TryRollChatter`가 정확히 이 모양이다 —
> *"판정 순서가 곧 계약이다. 한 번 true를 반환하면 그 전이의 대사는 반드시 만들어진다"*.
> 말할지 말지는 **상태**가 정하고, 무엇을 말할지만 **매핑 함수**가 정한다. 두 질문을 한 함수에
> 넣으면 "말하지 않음"을 표현할 타입이 없어 빈 문자열이라는 **거짓 대사**가 생긴다.
>
> ★ 대신 `Reason`은 여전히 파라미터에 실어야 한다 — `Completed`("월척!")와 `TimedOut`("오늘은
> 아닌가")은 **둘 다 말하지만 다른 말을 하기 때문**이다. 게이트가 결과 축을 대신할 수 없다.

**검증 가능한 단언(테스트 인계, 2건)**
1. 신규 9종의 매핑 함수에 `PreconditionLost` / `ForcedInterrupt`를 넣어도 **`DialogueIntent`가
   생성되지 않는다**(호출부 수준 단언).
2. **어떤 매핑 함수도 빈/공백 문자열을 돌려주지 않는다** — `AmbientChatter.Resolve`의 방어 분기까지
   포함해 전수. 지금 이 단언은 없다.

### 2-4. ★ 완료 대사는 `Enter()`에서만 만들 수 있다 — 자기 전이가 유일한 경로

`DialogueIntent`는 `StateTransitionContext`를 요구하고, 그 컨텍스트는 `ChangeState()`가
`Enter()`에 넘길 때만 발급된다(1회용 토큰). **즉 상태 중간에는 대사를 만들 수 없다.**

그런데 아래 대사들은 전부 **상태 중간 또는 끝**의 사실에서 파생된다:

| 대사 | 파생 시점 | `Enter()`인가 |
|---|---|---|
| 낚시 "던졌다" | 던지기 박자(#4) 종료 | ✗ (진입 후 0.83초) |
| 낚시 "안 물리네" | 대기 중, 잔여 ≥1.0초 | ✗ |
| 낚시 "월척!" / "오늘은 아닌가" | 결과 확정 | ✗ |
| 로프 "걸렸다" | 걸림 확인 박자(#3) | ✗ |
| 로프 "올라왔다" | 맨틀 완료 | ✗ |
| 낮잠 "잘 잤다" | 깨기 박자 | ✗ |

> **처방 — 자기 전이(self-transition)**. `ChangeState(같은 ID)`는 `Exit()` → 세대 증가 →
> 새 컨텍스트 → `Enter()`를 돌린다(`StickmanStateMachine.cs:150-174`).
> **선례가 이미 있다**: `RunawayState`의 `_pendingReconciled` / `_pendingSelfReturn` 보류 플래그가
> "어느 페이즈의 `Enter()`인가"를 구분해 각기 다른 대사를 만든다.
> 그리고 `MOTION_SPEC 31-2 #5`도 *"`Enter()` — self-transition으로 재실행되는 판정 프레임 포함"*
> 이라고 이미 적어 두었다. **새 배관이 필요 없다.**
>
> **대가 2가지를 명시한다**(구현이 이걸 모르면 사고가 난다):
> - 자기 전이는 **`TransitionGeneration`을 올린다** → 그 프레임에 떠 있던 이전 대사가 **즉시
>   만료**된다(`DialogueIntent.OnAnyStateTransitioned`). 낚시 "던졌다"(서술)는 "월척!"이 뜨는
>   순간 사라진다 — **이건 옳다.** 던지는 중이 아니게 됐으므로 문장이 거짓이 됐다.
> - `Exit()`가 매 페이즈 경계에서 돈다 → **`Exit()`에 상태 정리 로직을 두면 안 된다.**
>   `RunawayState`가 보류 플래그로 페이즈를 넘기는 이유가 이것이다.

### 2-5. 매핑 표 — first-match 순서가 곧 계약이다 (`UX_FLOW 31-2` 규칙 3)

낚시 예시(내가 아래 4절에서 유지 판정한 4줄):

```
Resolve(id, params):
    p = params as ActivityDialogueParams
    ── 여기 도달했다는 것 자체가 "말할 자격이 있다"는 뜻이다(2-3의 호출부 게이트) ──
    if p.Phase == Cast     : return Say("던졌다")          # 서술, 잔여 3.00초 ≥ 0.680 ✓
    if p.Phase == Waiting  : return Say("안 물리네")        # 서술, 잔여 1.00초 ≥ 0.715 ✓
    if p.Outcome == Caught : return React("월척!")
    if p.Outcome == Empty  : return React("오늘은 아닌가")
    ── 여기 도달하면 계약 위반이다. 침묵이 아니라 **예외**로 터뜨린다 ──
```

**마지막 줄이 핵심이다.** 빈 문자열로 폴백하면 2-3의 결함이 뒷문으로 돌아온다.
도달 불가 분기는 **`Assert.Fail`이 아니라 `Assert.Ignore`로 남기라**는 CLAUDE.md 관례의 대사판이다 —
조용히 통과시키지 않는다.

### 2-6. ★ 같은 라운드에 착지한 `SpectacleExitClassification`과의 관계 (중복 경보)

이 문서를 쓰는 도중 `coder`가 `Assets/_Project/Scripts/Core/SpectacleExitClassification.cs`를
착지시켰다(같은 사고 — *"낙서하다 굴러떨어져도 정상 완료로 기록"*). 기존 4개 디렉터
(`Graffiti` / `DesktopIconMirror` / `WindowTheft` / `Archery`)가 `IsAbnormalExit`를 쓴다.

**대사 쪽 영향은 지금 0건이다** — 그 4개 중 대사가 있는 것은 `WindowTheft` 하나뿐이고, 그 대사
(`"헥헥... 안 되겠다..."`)는 **`Enter()`에서** 나오지 종료 시점에 나오지 않는다.
`Archery`는 무대사다. 즉 **지금 잘못된 완료 대사가 나가는 경로는 없다.**

**그러나 축이 둘이 된다는 것을 리더에게 보고한다:**

| | `SpectacleExitClassification.IsAbnormalExit` | `ActivityExitReason` |
|---|---|---|
| 무엇을 보나 | **도착 상태**(Fall/Ragdoll/ThrowTumble/GroundLossHang) | **박자 인덱스**(마지막 박자를 재생했는가) |
| 답의 종류 | bool | 4값 열거형 |
| 대상 | 기존 연출 4종 | 신규 9종 |

두 축은 **모순되지 않는다**(도착 상태가 비정상이면 마지막 박자를 재생했을 리 없다).
하지만 신규 9종이 둘 다 갖게 되면 **한 사실에 두 판정기**가 생긴다.
**권고**: 신규 9종은 `ActivityExitReason` 하나만 쓰고, `IsAbnormalExit`는 **그 값을 만드는 입력의
하나**로만 쓴다(`IsAbnormalExit(to) == true` → `PreconditionLost`/`ForcedInterrupt`).
**판정은 `game-architect`/리더 소관이다** — 나는 대사가 어느 쪽을 읽어야 하는지만 못 박는다:
**대사는 `ActivityExitReason` 하나만 읽는다.** bool 두 개를 조합해 결과를 유추하는 순간
격파 사고의 형태로 돌아간다.

## 3. ★ 세트 완성 시 대사 풀 전환 (기획 5-3 / `ECONOMY_SPEC` 3-4)

> ★ **기획서의 예시("격파 성공 시 마법진")는 무효다.** 격파는 2026-09-02에 삭제됐고,
> `ECONOMY_SPEC` 3-4도 이미 그렇게 못 박았다. 아래는 **살아 있는 상태에서만** 파생한다.

### 3-1. 판정 — 전환은 **앰비언트 풀(Idle/Walk)에만** 건다

| 후보 | 판정 | 이유 |
|---|---|---|
| Idle / Walk 앰비언트 | **채택** | 저장소에서 **"풀"인 것은 이 둘뿐**이다(동등한 후보 n개 중 난수 1개). 나머지 대사는 전부 파라미터의 함수라 대체 후보가 없다 |
| `ParkourClimb` / `LedgeHang` / `Ragdoll` / `Attack` 등 | **기각** | 세트별로 다시 쓰면 `31-2` 매핑 표가 **6장**이 된다. 임계값·분기 순서가 6벌로 갈라지면 격파 사고(도달 불가 분기)가 6배로 재발할 자리가 생긴다 |
| `FocusStart` 등 고정 1줄 상태 | **기각(이번 라운드)** | 1줄짜리를 6벌로 늘리는 것은 어조 전환이 아니라 **문자열 6배**다. 세트 체감은 앰비언트가 만든다 |

**근거(체감 쪽)**: 사용자가 캐릭터를 보는 시간의 대부분이 Idle/Walk다 — 그래서 `AmbientChatter`가
애초에 만들어졌다(*"캐릭터가 실제로 대부분의 시간을 보내는 Idle/Walk에는 대사가 전혀 없었다"*).
**격차를 벌려야 하는 곳이 정확히 여기다.**

### 3-2. 세트 판정 — 새 데이터가 필요 없다

`ECONOMY_SPEC 3-2`의 `rank`는 **슬롯 내 요구 레벨 순위**이고, 그 값은 이미 `itemIndex`다
(에셋 42종 전수 확인: 슬롯 0~3 × index 0~5, 요구 레벨 오름차순).

```
세트 완성 ⟺ w = WornIndex(Head) == WornIndex(Eyes) == WornIndex(Neck) == WornIndex(Shoulders)  ∧  w ≥ 0
세트 ID  = 'A' + w        (w = 0..5 → A..F)
미완성/이종조합 → 세트 없음 → **중립 풀**(지금의 IdleLines/WalkLines 13줄)
```

에셋 대조(내가 42개 `.asset`을 전부 읽어 확인):

| 세트 | w | 구성(모자/안경/넥타이/망토) | 완성 Lv |
|---|---:|---|---:|
| A | 0 | 천모자 · 선글라스 · 나비넥타이 · 짧은망토 | **1** |
| B | 1 | 털모자 · 동그란안경 · 줄무늬타이 · 긴망토 | 13 |
| C | 2 | 중절모 · 고글 · 목도리 · 날개 | 17 |
| D | 3 | 왕관 · 외알안경 · 방울목걸이 · 배낭 | 22 |
| E | 4 | 베레모 · 뿔테 안경 · 펜던트 목걸이 · 판초 | 25 |
| F | 5 | 밀짚모자 · 안대 · 반다나 · 요정 날개 | 28 |

> 이름이 `ECONOMY_SPEC` 표와 **한 곳도 어긋나지 않는다**(공백 표기만 다르다: `뿔테안경`↔`뿔테 안경`).
> 세트 D의 `Shoulders = 배낭`은 `EquipmentSlot.Shoulders`가 역사적 이름이고 실제 슬롯 코드는
> `BACK`이라는 점만 주의(`EquipmentModel.cs:24-30`).

### 3-3. ★★ 원칙 1 — 세트가 바꾸는 것은 **어조**지 **사실**이 아니다

이 절이 이 설계의 방어선이다.

> **세트 대사도 여전히 Idle/Walk가 정의상 참으로 만드는 사실만 말한다.**
> 세트는 **어휘와 어미**만 정한다. 착용 사실 자체는 앱이 아는 사실이므로 언급해도 된다
> ("망토가 따라온다"는 망토를 걸쳤고 지금 걷는 중이면 참이다).
> **금지**: 세계에 대한 검증 불가 주장("바람이 좋군" — 바람이 없다),
> 소리 주장("발소리가 조용하네" — 사운드가 없다), 유저 행동 주장, **예고·청유형**("한 바퀴 돌자").

이 규율은 `35-3-3`(말투 반말/존댓말)의 판정과 **정확히 같은 모양**이다 —
*"톤은 의미를 바꾸지 않는 표면 선택"*. 그래서 두 축이 충돌 없이 합성된다(3-6절).

### 3-4. ★ 세트 대사의 **글자수 상한은 9자다**

- 노출 상한도 커져(9자에서 2.21초) **Walk 최장 4.00초** 안에서는 괜찮지만,

### 3-6. ★ 축이 세 개다 — 곱하지 말고 **역할을 나눈다**

`35-3-3`이 예정한 `SpeechLexicon`(반말/존댓말 2열)과 이 설계가 만나면 **표가 곱해질 위험**이 있다.

```
✗ 곱하는 설계:  SpeechKey × {반말,존댓말} × {중립,A..F} = 열 14개
✓ 나누는 설계:  세트 = "어느 SpeechKey 집합을 뽑을 수 있는가"(행 선택)
                톤   = "그 키의 어느 열을 읽는가"(열 선택)
                → 표는 여전히 `SpeechKey × {반말, 존댓말}` 하나뿐
```

즉 **세트 42줄 = 새 `SpeechKey` 42개**이고, 각 키는 톤 2열을 갖는다(→ 최종 문장 84개).
그것이 정직한 비용이고, **열이 늘어나지는 않는다.** 중립 13 + 세트 42 = **키 55개**.

### 3-7. ★ 파라미터 계약 — 세트 ID는 `Enter()` 스냅샷이어야 한다

```
sealed class ChatterParams {
    public int LineIndex;   // 지금 있는 필드
    public int PoolId;      // ★ 신설: 0 = 중립, 1..6 = 세트 A..F
}
```

**왜 스냅샷인가 — 스냅샷이 아니면 이렇게 깨진다:**
`Resolve`가 `EquipmentModel`을 직접 읽으면 그 함수는 **전역 가변 상태를 읽는 함수**가 된다.
그러면 대사가 뜬 뒤 유저가 모자 한 칸을 벗는 순간, **같은 `LineIndex`가 다른 표를 가리켜**
화면의 글자가 바뀌거나(렌더러가 다시 물으면) 인덱스가 범위를 벗어난다.
`AmbientChatter.Resolve`의 현재 계약(*"난수/시간/전역 상태를 읽지 않는다 — 그래야 이 텍스트가 어느
`Enter()`의 어느 파라미터 스냅샷에서 나왔는지 역추적할 수 있다"*)이 그대로 답이다.

**그리고 `TryRollChatter`의 표 선택도 함께 바뀌어야 한다.** 지금은
`stateId == Walk ? WalkLines : IdleLines`로 **두 곳**(`TryRollChatter`와 `Resolve`)이 각자 표를 고른다.
`PoolId`가 생기면 **같은 함수 하나가 표를 고르게** 하라 — 두 곳이 서로 다른 표를 고르면
게이트가 **잰 문장과 화면에 뜨는 문장이 달라진다**. 규칙 8이 통째로 무의미해지는 경로다.

**풀 크기가 세트마다 달라도 안전하다**: `LineIndex`는 `Random.Range(0, table.Length)`로 **그 표에
대해** 뽑히고, `Resolve`의 모듈로가 같은 표 길이를 쓴다. 단 위 "같은 함수 하나" 조건이 전제다.

### 3-8. 3종 착용(미완성 힌트) — 1줄, **1회성**, 풀에 넣지 않는다

`ECONOMY_SPEC 3-4`의 *"미완성 힌트 대사 1종('하나만 더…')"*.

| 빠진 슬롯 | 대사 | 글자 | 종류 |
|---|---|---:|---|
| Head | `모자만 더` | 5 | 반응 |
| Eyes | `안경만 더` | 5 | 반응 |
| Neck | `넥타이만 더` | 6 | 반응 |
| Shoulders(BACK) | `망토만 더` | 5 | 반응 |

- **`UX_SHOP §6`의 UI 문구 `"{슬롯}만 더"`와 같은 표현을 쓴다.** 한 사실에 두 표현을 만들지 않는다.
  슬롯 이름도 `EquipmentModel.SlotName()`이 이미 소유한다(모자/안경/넥타이/망토).
- **풀에 넣지 않는다.** 풀에 넣으면 3종 착용 상태에서 **영원히 조르는 캐릭터**가 된다(원칙 2 위반).
- **발화 조건**: 착용이 바뀌어 "3/4가 됐다"는 사실이 확정된 뒤 **다음 Idle 진입 1회**.
  `StickmanBlackboard.ForcedChatterSignaled`(1프레임 펄스, 소비 즉시 리셋)와 **같은 관례**를 쓴다 —
  새 배관이 아니라 이미 있는 것의 두 번째 사용자다.
- **종류 = 반응**: "방금 3/4가 됐다"는 점 사건이라 Idle이 끝나도 참이다. 그리고 이건
  **놓치면 안 되는 안내**라 게이트에 막히면 안 된다(5-2절과 같은 판단).

### 3-9. 2종 착용 — **이번 라운드에는 만들지 않는다**

`ECONOMY_SPEC`은 *"기존 대사 풀에 그 세트 어휘가 낮은 확률로 섞인다"*고 했다. 설계는 가능하지만
(세트 풀에서 1~2줄을 중립 풀에 섞고 확률을 낮춘다) **지금 만들면 검증이 불가능하다** —
"낮은 확률"의 값이 `design-systems` 소관이고, 그 값이 없는 채로 줄만 쓰면 실기에서 도달하는지
아무도 모르는 분기가 42줄 위에 또 생긴다(= 격파 사고의 형태).
**보류. `design-systems`가 확률을 주면 그때 쓴다.**

## 5. 내 소관의 나머지 — 요일 · 시간대 · 복귀 · 저전력 · 어질러짐

### 5-1. 구조 — 풀을 늘리지 말고 **자격 술어**로 거른다

요일 7 × 시간대 4 × 세트 7을 풀로 곱하면 196벌이다. 그럴 필요가 없다.

```
중립 풀 = 상시 13줄  +  조건부 n줄
조건부 줄은 각자 "언제 뽑힐 수 있는가"(요일/시간대)를 가진다.
TryRollChatter:  ① 지금 자격 있는 줄만 모은다  ② 그 안에서 난수  ③ **절대 인덱스**를 스냅샷
Resolve:         스냅샷된 절대 인덱스로 전체 표를 조회 — 순수 함수 유지
```

**★ 절대 인덱스여야 하는 이유**: 걸러진 목록의 상대 인덱스를 저장하면 `Resolve`가 그 필터를
재현하려고 **다시 시계를 읽어야** 한다 — 그 순간 순수 함수가 깨지고, 자정을 넘는 순간 같은
스냅샷이 다른 문장을 가리킨다. 필터는 시계를 읽어도 되는 `TryRollChatter`가 소유한다
(이미 `Time.unscaledTime`과 `Random`을 읽는 함수다).

    했으므로, **갈라 쓰지 않기로 한 것도 기록해 둔다.**

### 5-3. ★ 저전력 안내 — **반드시 말해야 하는 유일한 자리**

**이 줄이 필요한 이유는 배터리가 아니라 "고장처럼 보이는 화면"이다.**

`ViewerPresence.ShouldApplyLowPowerDownshift()`가 참이면 `BuildPlan`이 **`Active` 등급에서도**
나누기 2를 건다. 즉 **유저가 보고 있는데 30fps로 걷는다.** 그 함수의 문서가 직접 적어 둔 대가가
*"이 앱은 끊긴다는 인상"*이고, 이 저장소는 이미 *"부드럽지 않다"*는 신고를 한 번 받았다.

| 항목 | 값 |
|---|---|
| 대사 | **`배터리 아끼는 중`** (9자, 가독예산 0.955초, 노출 상한 2.21초) |
| 종류 | **반응** — ★ 게이트에 막혀 침묵하면 **이 줄의 존재 이유를 정면으로 배반한다** |
| 사실 출처 | `ShouldApplyLowPowerDownshift(presence, uiInteractionActive) == true` |
| 빈도 | **저전력 진입 1회.** 회복 전까지 재발화 금지 |
| 선례 | `HardwareReactionDirector.SignalState`의 `Notified` + `RecoveryCooldownRemaining` — **똑같은 문제를 이미 푼 구조다** |

- **`Away` / `DisplayOff` 등급에는 붙이지 않는다.** `Away`는 3분 무입력 **AND** 캐릭터 정지이고
  `DisplayOff`는 화면이 꺼진 상태다 — **볼 사람이 없다.** 아무도 못 보는 안내는 안내가 아니다.
- **하드웨어 반응 4종(`LowBattery` 이모트)과 다른 것이다.** 그쪽은 23절의 *"은유만 담당"*
  이모트이고 자율 발동이 기본 OFF다. 이쪽은 **우리 앱이 스스로 화질을 낮춘 사실에 대한 설명**이다.
  겹치지 않게 하려면 저전력 안내가 뜨는 동안 `LowBattery` 이모트를 띄우지 않는 것으로 충분하다
  (23절 *"동시에 두 가지를 겹쳐 보이면 안 됨"*의 기존 우선순위 리졸버가 이미 그 일을 한다).
- **기본 ON을 권고하되, 토글 위치는 `ux-designer`/리더 소관**이다. 근거: 이건 장난이 아니라
  **오해 방지**다. 다만 1회성이라 끄고 싶은 유저도 있을 수 있다.

### 5-4. 장기 미접속 후 복귀 — 3줄, 1회성

**★ 먼저 정직하게: "휴가 다녀옴"은 대사로 낼 수 없다.**
앱이 아는 사실은 **"마지막 실행 이후 N일이 지났다"** 하나뿐이다. 캐릭터가 어디 갔었는지는
아무도 모른다 — `"휴가 다녀왔어"`는 **거짓말**이고, `"한참 안 왔네"`는 **유저의 부재를 주장**한다
(다른 컴퓨터를 썼을 수도, 앱만 껐을 수도 있다).
말할 수 있는 것은 **재회라는 사실**과 **캐릭터 자신의 주관**뿐이다.
"휴가에서 돌아오는 그림"(가방을 내려놓는 자세 등)은 **모션 소관**이고, 그건 만들어도 된다 —
자세는 주장이 아니기 때문이다.

| 경과 | 대사 | 글자 | 종류 |
|---|---|---:|---|
| 3~6일 | `오랜만이야` | 5 | 반응 |
| 7~29일 | `많이 기다렸어` | 7 | 반응 |
| 30일+ | `정말 오랜만이야` | 8 | 반응 |

- **임계 3/7/30은 자리표시자다** — 확정은 `design-systems`.
- **반응인 이유는 5-3과 같다**: 복귀 직후 첫 Idle이 1프레임짜리일 수 있는데, 그때 침묵하면
  이 줄은 **영원히 못 나온다**(다음 기회가 없다 — 1회성이므로).
- **1회성 펄스** — 3-8절과 같은 `ForcedChatterSignaled` 관례.

> **★ 교차 레이어 — 저장 스키마(리더 보고)**: 이 기능은 `LastSeenUtc`를 저장 파일에 새로 넣어야
> 하고, 저장소 전체 grep 결과 **그 필드는 존재하지 않는다.** CLAUDE.md 협업 프로토콜에 따라
> `CharacterSaveStore.CurrentVersion`을 올리는 라운드는 **`vN-1` 파일을 읽었을 때 새 필드가 안전한
> 기본값으로 채워지는지 검증하는 하위 호환 테스트 1건을 반드시 동반**한다.
> 그리고 **기본값이 "방금"이어야 한다** — `default(DateTime)`(0001년)이면 **첫 실행에서
> 경과 730,000일**이 되어 신규 유저가 `"정말 오랜만이야"`를 듣는다. 원칙 1 위반이자 첫인상 사고다.

### 5-5. 데스크톱 어질러짐 코멘트 — **이번 라운드 0줄**

**말할 사실이 없다.** 4-3절과 같은 근거:
`IDesktopIconLayoutService`가 **양쪽 플랫폼 모두 미구현 스텁**이라 아이콘 개수도 영역도
런타임에 `false`/빈 목록이다. 지금 무엇을 쓰든 그것은 **화면을 안 보고 하는 말**이다.

**해금 조건(그날이 오면 이 규칙으로 쓴다)**:
1. `TryGetIconRegion` / `EnumerateIconRects`가 **두 플랫폼에서** 실제 값을 돌려줄 것.
2. "어질러졌다"의 **임계**를 `design-systems`가 줄 것(개수? 영역 대비 밀도? 열 정렬 이탈?).
   **임계 없이는 형용사를 쓸 수 없다** — 그게 "발판 참 좁네"가 죽은 이유다.
3. 대사는 **개수/영역에서 파생 가능한 것만** 말한다. 아이콘이 *무엇인지*는 영원히 모른다
   (썸네일 캡처는 원칙 3/27-7이 금지한다).
4. **`"정리해줄까?"`는 영구 금지.** 원칙 3상 우리는 정리할 수 없고, 물어보는 것 자체가
   **하지 못할 일의 예고**다(원칙 1의 예고 금지).

## 7. 플랫폼 영향

### macOS 영향
- **함께 설계함.** 이 문서의 모든 값은 **초·글자수**뿐이라 배율/DPI/OS와 무관하다
  (`DialogueBudget` 상수가 전부 무차원 축 ④).

  `MacViewerPresenceService.ProbeLowPowerMode()`가 `NSProcessInfo.isLowPowerModeEnabled`를 읽는다.
- 어질러짐 대사(5-5)를 보류한 사유 중 하나가 macOS의 `IDesktopIconLayoutService` 미구현이다
  (`MacWindowService.cs:59` — 의도적 미구현).

### Windows 영향
- **함께 설계함. 별도 배정 필요 0건.**
- 저전력 안내는 Windows에서도 **같은 날 같은 라운드에** 배선돼 있다 —
  `WindowsViewerPresenceService`가 `GetSystemPowerStatus().SystemStatusFlag == 1`(배터리 세이버)을
  읽어 `LowPowerMode`를 채운다. **양쪽 플랫폼 모두 사실 출처가 존재한다.**
- 어질러짐 대사 보류는 Windows에서도 같은 사유다 —
  `Win32WindowService.cs:1836-1855`가 `false` / 빈 목록을 돌려주는 정직한 스텁.
- **요일·시간대·복귀·세트**는 전부 `System.DateTime` / `EquipmentModel`(플랫폼 중립)에서 나온다.

## 8. 미확인 (거짓 통과 방지)

1. **모든 대사의 화면 판정은 실제 빌드 캡처로만 가능하다.** 이 문서의 숫자는 전부 계약 수준의
   계산이고, "실제로 읽히는가"는 재지 않았다. 특히 **1-3절의 여유 +0.030초는 실기에서 한 번도
   관측된 적이 없다** — 계산상 통과일 뿐이다.
2. **`Walk`/`Idle`의 "계획 잔여 하한"은 진입 시점의 값이다.** 페이즈 한복판으로 들어오는 경로
   (기상/착지/등반 복귀)에서는 잔여가 하한보다 훨씬 작을 수 있고, 그때 침묵 비율이 얼마인지는
   **로그로만 알 수 있다**(`[말풍선] 발화 보류` 줄 수). **아직 재지 않았다.**
3. **세트 대사 42줄의 어조가 실제로 구별되는지는 사람이 읽어야 안다.** 페르소나
   (특히 `persona-immersion`) 검증 대상으로 올린다.
4. **4-2절의 충돌은 전이 배선을 추정한 부분이 있다.** `FocusStart` 다음이 `Idle`인지
   `FocusWorkMining`인지는 아직 코드가 없다(신규 상태). 확실한 것은 **같은 유저 조작 하나에서
   두 문장이 몇 초 안에 나온다**는 것이고, 그 판정은 어느 배선이어도 바뀌지 않는다.
5. **2-4절(자기 전이) 대가 2건은 코드를 읽고 유도한 것이지 실행해 본 것이 아니다.**
   `Exit()`가 페이즈마다 도는 것은 `ChangeState` 본문에서 명백하지만, 신규 9종이 `Exit()`에
   무엇을 둘지는 아직 없다.
6. **`ActivityExitReason`이 실제로 오기록을 막는지는 구현 후에만 검증 가능하다**
   (모션 사양 17절과 같은 항목).
7. **2-6절의 `SpectacleExitClassification`은 이 라운드가 도는 도중에 들어온 파일이라, 최종 형태가
   아닐 수 있다.** 나는 그 파일을 읽고 판단했을 뿐 실행하지 않았고, 그 라운드의 테스트 결과도
   확인하지 않았다.
