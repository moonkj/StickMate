## 0. 리더가 먼저 읽을 9줄

1. **9종 중 수평 이동을 스스로 소유하는 것은 2종뿐이다** — 로프 등반(전 구간)과 아이콘 닦기(옆걸음
   구간). 나머지 7종은 제자리다. 단, **5종이 접근(Approach) 페이즈를 갖는다**(곡괭이질/낚시/닦기/
   쓰다듬기 + 기존 활쏘기) — 이건 상태 ID 하나 안에서 소유권이 바뀐다는 뜻이라,
   `IsHorizontalMotionSelfManaged(stateId)`를 **상태 ID 단위 목록으로만 두면 이 5종이 전부 회색지대**가
   된다. 처방은 1-2절.
2. **모든 제자리 연출 앞에 `정지(brake)` 박자 0.14초를 넣는다.** 표류를 막을 뿐 아니라, 속도를 그냥
   0으로 대입하면 생기는 **급정지 튐**도 같이 막는다. 정지 거리 4.30pt(배율 0.60), 감속률 438 pt/s²
   = 리더가 보고한 실측 표류 감속(−0.68 pt/s²)의 **645배**. (1-3절)
3. **"정상 완료"의 정의를 시간이 아니라 박자 인덱스로 바꾼다.** 지금 결함(미끄러져 떨어졌는데 완료
   기록)의 원인은 "시간이 다 되면 완료"이기 때문이다. **마지막 박자를 재생했는가**로 판정하면 떨어진
   순간 구조적으로 완료가 될 수 없다. 열거형 4종은 1-4절.
4. **집중모드 타이머 앵커 — 실측 근거를 제출한다(판정은 리더/ux-designer).** 곡괭이질 중 머리는
   1사이클(1.26초)마다 **19.13pt를 수평 왕복**한다(링 지름 26.51pt의 **72.2%**). 발은 **0.00pt**다.
   계기를 진짜 머리에 붙이면 읽을 수 없다. **"머리 위"를 지키면서 스윕을 0으로 만드는 방법이 있다** —
   앵커를 애니메이션되는 머리가 아니라 **루트 + 1.0 H 고정 오프셋**에 둔다(곡괭이질 중 정수리 최고가
   0.9854 H라 겹치지 않는다, 여유 0.82pt). 4-3절.
5. **낚시의 Windows 폴백은 "포기"가 아니라 "발판 교체"다.** `TryGetReservedBottomBarOsScreen`이
   false면(자동 숨김/좌·우·상단 배치) **현재 발판(창 상단)의 바깥 모서리에 걸터앉는다** — 걸터앉기
   그림이 그대로 성립하고, 오히려 줄이 늘어질 여유가 더 크다. 두 발판 다 없으면 **시작하지 않는다.** 6-6절.
6. **아이콘 닦기는 기하학적으로 반쯤 막혀 있다.** 이 리그의 팔은 0.3297 H이고 서 있을 때 어깨는
   0.7758 H다. **무릎을 138°까지 접고 상체를 리그 상한 30°까지 굽혀도 손끝이 발판 위 7.67pt에 머문다**
   — 서서 발판면을 닦는 것은 불가능하다. 걸터앉으면 닿지만 문지름 궤적이 **4.61pt**밖에 안 나온다.
   → **후순위 권고 + design-character 교차 레이어 보고**(팔 길이). 11절.
7. **로프 등반 속도는 21.1 pt/s**(보행의 34.4%, ParkourClimb의 37.9%)로 유도됐다 — 각도에서 나온
   값이지 고른 값이 아니다. 그래서 **상한 시간이 곧 오를 수 있는 높이의 상한**이다. 권장
   `ropeClimbMaxSeconds = 12.0초 → 253pt(4.54 H)`. 그보다 높은 창은 **시작하지 않는다**(도중 포기 금지). 5-6절.
8. **대사 16줄 전수 검산 통과.** 서술 9줄은 전부 발화 시점 잔여가 필요체류를 넘고, 반응 7줄은 전부
   "방금 일어난 점 사건"이라 상태 종료 후에도 참이다. **`Aborted` 경로는 9종 전부 대사 0건**이 계약이다. 1-5절.
9. **새 자세는 사실상 3개뿐이다** — 걸터앉기(`SitOnEdge`, 낚시·닦기·낮잠 진입이 공유) / 곡괭이 양손
   그립 / 로프 그립. 나머지는 기존 어휘(`LedgeHang` 늘어진 다리, `ParkourClimb` 4박자 IK,
   `LandingCrouch` 무릎, `IdleAmbient` 눈동자 스윕)의 재조합이다.

### 1-2. ★ 수평 이동 소유권 — 신규 9종 선언

리더 전달(디버거 실측): *능동 상태를 떠날 때 잔여 수평속도가 살아남고, 접지 중력 억제가
`gravityScale = 0`으로 만들어 수직항력 N = 0이라 쿨롱 마찰 상한 μN도 0이다.*
즉 **마찰로는 절대 멈추지 않는다. 속도를 누군가 명시적으로 0으로 만들어야 한다.**

> ### ★★ 목록을 상태 ID 단위로만 두면 5종이 회색지대가 된다
>
> 위 표에서 **"접근만 소유"가 4종 + 닦기의 교대 소유 1종 = 5종**이다(기존 `Archery`까지 6종).
> `IsHorizontalMotionSelfManaged(stateId)`가 상태 ID 하나에 true/false만 돌려주면:
> - **true로 넣으면** — 안전망이 이 상태를 통째로 건너뛰므로, 채굴/앉기/문지름 구간의 잔여 표류를
>   아무도 안 막는다. 오늘 결함이 그대로 남는다.
> - **false로 넣으면** — 안전망이 접근 페이즈의 정당한 보행 속도를 지운다. 캐릭터가 목표까지
>   영원히 못 간다(또는 매 프레임 0으로 눌려 제자리걸음한다).
>
> **처방(모션 쪽 계약)**: 목록은 **true**(자기가 소유한다)로 두고, 그 대신 이 5종은
> **"제자리 페이즈에 들어가는 프레임에 정지 박자를 시작하고, 정지 박자가 끝나면 그 페이즈가 끝날
> 때까지 매 프레임 `v.x = 0`을 재확인한다"** 를 상태 자신의 의무로 진다.
> 매 프레임 재확인이 필요한 이유는 이미 저장소가 답을 갖고 있다 —
> `ApplyGroundedGravitySuppression()`이 `v.y`에 대해 정확히 같은 일을 매 프레임 한다
> (*"중력이 0인데 속도가 남아 있으면 등속으로 미끄러져 오히려 밴드를 벗어난다"*).
> **x축은 그 대칭 처방이 빠져 있었을 뿐이다.**
>
> 검증(테스트 인계): 각 행동의 제자리 페이즈에서 **벽시계 2.0초** 동안 루트 x 변위 ≤ 정지 거리
> (아래 1-3) + 허용오차. 프레임 수 예산 금지(배치모드 8,000fps).

### 1-3. ★ 정지(brake) 박자 — 표류와 급정지 튐을 한 번에 막는다

**모든 제자리 페이즈의 첫 박자로 0.14초 `정지`를 넣는다.**

| 항목 | 값 |
|---|---|
| 길이 | **0.14초** (전이 박자 하한 0.10초 대비 +40%, 60fps에서 8.4프레임) |
| 속도 곡선 | `v.x = v0 × (1 − SmoothStep(0,1,t/0.14))` — 선형 대입 금지 |
| 정지 거리 | **0.07693 H = 4.30pt** (배율 0.60, 보행 최대속도에서) |
| 감속률 | 7.850 H/s² = **438.4 pt/s²** |
| 관성 표현 | 진입 순간 상체 **−7°**(진행 반대 = 브레이크), 0.14초에 걸쳐 0으로 복귀 |

**왜 −7°(뒤로)이고 +7°(앞으로)가 아닌가**: 앞으로 쏠리면 "발이 걸려 넘어질 뻔했다"로 읽히고,
뒤로 젖히면 "발을 앞에 심고 멈췄다"로 읽힌다. 이 9종은 전부 **의도한 정지**다.
상한 `MaxBodyLeanDegrees = 30`의 23%만 쓰므로 다른 lean 요청과 겹쳐도 클램프에 안 걸린다.

**왜 정지 거리가 이렇게 작아도 되는가**: 4.30pt는 캐릭터 키의 7.7%다. 이건 "미끄러짐"이 아니라
"발이 한 번 더 나간 것"으로 읽힌다. 반대로 **0초(즉시 대입)는 한 프레임에 61.37pt/s가 0이 되는
불연속**이라 팔다리 스무더(`poseSmoothingRate 35`)만 관성을 남기고 몸통은 얼어붙는다 —
그게 "인형" 느낌의 정확한 정의다.

### 1-4. ★ 완료 판정 — 시간이 아니라 **박자 인덱스**

> 지금 결함: *미끄러지다 발판 밖으로 떨어지면 "정상 완료"로 기록된다*(원칙 1 위반).
> **원인은 "경과 시간이 지속시간을 넘으면 완료"라는 판정식**이다. 떨어지는 동안에도 시간은 흐른다.

**신규 9종 공통 계약**:

```
enum ActivityExitReason {
    Completed,          // 마지막 박자를 끝까지 재생했다  ← 이것만 완료다
    TimedOut,           // 상한 만료. 행동별로 완료일 수도(낚시 '꽝') 아닐 수도(로프 등반)
    PreconditionLost,   // 발판/대상/커서 소실           ← 절대 완료 아님
    ForcedInterrupt,    // 드래그/전체화면/랙돌/유저 취소  ← 절대 완료 아님
}
```

- **`Completed`의 유일한 판정식은 `_beatIndex == LastBeatIndex && _beatTimer >= LastBeatDuration`이다.**
  경과 시간을 보지 않는다. 발판이 사라져 Fall로 나가면 마지막 박자를 **재생한 적이 없으므로**
  구조적으로 `Completed`가 될 수 없다.
- **`TimedOut`의 완료 여부는 행동마다 명시한다**(각 절의 "완료 계약" 표).
- **이 열거형을 `DialogueParams`에 반드시 싣는다.** 격파 사고(*"결과 축이 파라미터에 없다"*,
  MOTION_SPEC 2-2)와 같은 형태의 재발을 막는 유일한 방법이다. 대사 매핑 함수가
  `ActivityExitReason`을 못 보면 **"다 캤다!"가 떨어지는 도중에도 나온다.**
- **`PreconditionLost` / `ForcedInterrupt`는 9종 전부 대사 0건**이다(1-5절).

  행동을 끼워 맞추는" 쪽으로 한 걸음 가는 것이다.
- **종료 임박 체크 리액션** — `UX_FLOW 35-7 (g)` 확정("반드시 1회만, 대사 없이 동작으로만").
  ★ 나중에 "곧 끝나!"를 붙이자는 제안이 나오면 **기각**한다. 그건 **예고**이고, 원칙 1은 예고를
  허용하지 않는다(대사는 **확정된 사실**에서만 파생한다 — 잔여 60초는 사실이고, "곧 끝난다"는 예측이다).
- **로프 등반 중 사이클** — 박자가 0.99초로 촘촘해 글자가 붙었다 떨어지기를 반복한다(번쩍임 노이즈).
  발화 자격 게이트가 어차피 막지만, **애초에 만들지 않는다.**

**배경화면 감상 대사의 특별 제약**: 앱은 배경화면 **픽셀을 분석하지 않는다**(경로만 읽는다).
따라서 **내용을 특정하는 문장은 전부 금지**다("바다 사진이네" = 거짓말이 될 수 있다).
`잘 골랐네`처럼 **선택 행위**만 언급하는 문장만 허용한다. 이건 취향이 아니라 원칙 1의 요구다.

## 2. 집중모드 A — 곡괭이질 (`FocusWorkMining`)

### 2-1. 그림

### 2-2. 박자 — 1사이클 **1.26초** (0.794 Hz = 47.6회/분)

| 2 | 내려찍기 | 동작 | **0.22초** | 이징 `t^2.2`(가속). 등속이면 무겁게 안 보인다 |

  → **교차 레이어 보고**: 제자리 연출에서 이차 운동을 살리려면 그 렌더러가 속도 대신

## 3. 집중모드 B — 책상업무 (`FocusWorkDesk`)

### 3-1. 그림 — **성과물이 곧 책상이다**

세계에 책상이 없다. 그래서 **쌓이는 서류더미 자체를 작업면으로 쓴다.**
서류가 쌓일수록 작업면이 높아지고, **캐릭터의 상체 굽힘이 저절로 펴진다.**
성과물 누적이 소품이 아니라 **자세로 보인다** — 이 연동이 이 행동의 설계 핵심이다.

```
작업면 높이 D = 발판 + 서류 장수 × 장당 두께        (장당 두께는 design-systems)
쓰는 손끝 목표 = (앞으로 0.20 H, D + 0.02 H)
상체 굽힘 = 그 목표에 손이 닿는 데 필요한 최소 각도, 상한 30°(MaxBodyLeanDegrees)
```
D = 0(첫 장)일 때 굽힘이 최대(30°)이고, D가 커지면 0으로 수렴한다. **자유 상수가 없다.**

### 3-2. 박자

**1줄 쓰기 = 0.73초**

| # | 박자 | 종류 | 길이 | 하는 일 |
|---|---|---|---:|---|
| 1 | 쓰기 스트로크 | 동작 | **0.33초** | 앞손끝이 좌→우로 0.11 H 이동 |
| 2 | 되돌리기 | 동작 | **0.21초** | 왼쪽으로 복귀(다음 줄) |
| 3 | 줄 넘김 | 정지 | **0.19초** | — |

**4줄마다 종이 넘기기 = 0.61초** (넘기기 0.42 동작 + 정지 0.19 정지)
→ **1페이지 = 4 × 0.73 + 0.61 = 3.53초**, 이때 서류더미 +1.
`k_min = 0.905`.

> 세션당 몇 장이 쌓이는지는 **`design-systems` 소관**이다. 모션이 확정하는 것은
> **"1장 = 3.53초"** 하나뿐이고, 그 값이 그쪽 계산의 입력이 된다.

### 3-4. 무게감

곡괭이질과 정반대다. **충격이 없고, 침하가 없고, 관성이 없다.**
살아 있음은 (a) 손끝 궤적 0.11 H(6.1pt), (b) `idleBreathAmplitude`의 **0.6배**로 낮춘 호흡
(집중하면 숨이 얕아진다), (c) 종이 넘기기 박자의 팔 전체 이동이 만든다.

## 4. 집중모드 C — 타이머 계기와 종료 임박 체크 리액션

### 4-1. 모션 쪽 계약 (이것만은 내 소관이다)

1. **계기는 포즈 파이프라인을 통과하지 않는다.** `StickmanBlackboard.TickPose()` 경로에 들어오는
   순간 캐릭터 상태와 독립일 수 없다. 지금 `FocusWatchRenderer`가 `SetParent(null, false)`로
   씬 루트에 두고 **위치만 복사**하는 것이 정확히 옳은 형태다 — **그대로 유지한다.**
2. **작업 포즈는 계기가 그려지는 사각형을 침범하지 않는다.** 곡괭이질/책상업무 두 자세 모두
   정수리가 **1.0 H를 넘지 않고**(4-3 실측) 발이 루트 원점에 고정된다.
3. **손에 드는 것은 작업 소품뿐이다.** 타이머를 손에 드는 제안은 이 문서에서 미리 기각한다.

### 4-2. 종료 임박 체크 리액션 — **0.86초, 1회, 무대사**

| # | 박자 | 종류 | 길이 | 하는 일 |
|---|---|---|---:|---|
| 1 | 멈춤 | 정지 | **0.19초** | 곡괭이/펜이 멈춘다. 작업 박자의 관성을 끊는 순간 |
| 2 | 확인 | 동작 | **0.26초** | 상체 **±11°** + **눈동자 계기 방향 최대치** |
| 3 | 응시 | 정지 | **0.20초** | |
| 4 | 복귀 | 동작 | **0.21초** | 작업 사이클로 되돌아간다 |

**★ "고개 돌려 확인"을 목 관절 없이 만드는 법.**
이 리그에는 **목 관절이 없다**(`StickmanPoseAnimator`: *"목은 Torso LineRenderer의 윗부분이고 루트
로컬 x=0에 고정"*). 머리만 옆으로 밀면 **정의상 머리가 목에서 미끄러진다** — 사용자가 이미
신고했고 그래서 `idleAmbientLookHeadShiftRatio = 0`으로 꺼져 있다.
따라서 "확인"은 **상체 회전 + 눈동자**로만 만든다. 눈동자 경로는 이미 있다:
`StickmanBlackboard.TryGetIdleAmbientEyeSweep()`이 커서 추적을 가로채 `SetLookDirection()`을 쓰는
구조 그대로, **`TryGetFocusCheckEyeTarget()` 한 갈래를 같은 자리에 추가**하면 된다(새 배관 0).
상체 부호는 계기 위치가 정한다: **발밑 앵커면 +11°(굽힘), 머리 위 앵커면 −11°(젖힘).**

**삽입 규칙 — 박자 중간에 자르지 않는다.** 트리거는 `RemainingSeconds`가 60.0을 **아래로 교차한
프레임**이지만, 실제 삽입은 **진행 중인 박자를 끝낸 뒤**다. 최장 박자가 들기 0.34초이므로
실제 발동은 잔여 **59.66 ~ 60.00초** — "마지막 1분" 안에 100% 들어간다.

### 4-3. ★ 타이머 앵커 — 모션 실측 근거 제출 (판정은 리더/ux-designer)

> **충돌 상태**: 리더 전달은 *"머리 위 HUD 링/모래시계 — 사용자 확정"*이고,
> `docs/UX_FLOW.md 35-7 (f)`는 *"발밑 유지"*로 이미 판정을 내려 두었다.
> **UI 표면은 내 소관이 아니다.** 아래는 판정에 필요한 **모션 실측**이고, 결론은 리더가 낸다.

**실측 — 곡괭이질 1사이클(1.26초) 동안 각 앵커가 얼마나 움직이는가**

| 앵커 | 수평 스윕 | 수직 스윕 | 링 지름 대비 |
|---|---:|---:|---:|
| 애니메이션되는 **머리 중심** | **19.13pt** | 3.86pt | **72.2%** |
| **발**(루트 원점) | **0.00pt** | 0.00pt | 0% |

유도: 상체 lean이 −14°(들기) ↔ +27°(찍기)로 **41° 왕복**하고, 회전 중심이 엉덩이(0.410909 H)이며
머리 중심 반경이 `0.903281 − 0.410909 = 0.492373 H`다.
`Δx = 0.492373 × (sin27° − sin(−14°)) = 0.342648 H = 19.13pt @배율0.60`.
발은 수평 비소유 + 접지 고정이라 **정의상 0**이다.

**판정 재료**:
- 정량 계기(남은 시간)가 **자기 지름의 72%를 0.794Hz로 왕복**하면 읽을 수 없다. 이건 취향이 아니라
  가독성이다. 곡괭이질이 최악이고 책상업무는 굽힘이 준정적이라 훨씬 낫다.
- **그런데 "머리 위"와 "안 흔들림"은 양립 가능하다.** 앵커를 *애니메이션되는 머리*가 아니라
  **루트 + 1.0 H 고정 오프셋 + 여유 m**에 두면 된다:
  - 곡괭이질 중 **정수리 최고 = 0.985372 H**(찍기/들기 양 끝 중 최대) → 1.0 H 앵커와 **0.82pt 여유**로
    절대 겹치지 않는다.
  - 루트 x는 수평 비소유 구간에서 고정이므로 **스윕 0**.
  - 즉 **"머리 위 HUD"라는 사용자 문구와 "계기는 흔들리면 안 된다"는 물리 요구가 동시에 만족된다.**
- **남는 문제는 내 소관이 아니다**: 머리 위 구역은 이미 대사 레터링 / 하드웨어 이모트 /
  스트레스 퍼프 / 모자 슬롯이 쓴다(`UX_FLOW 35-7 (d)` 실측). **그 혼잡은 ux-designer가 판단한다.**

**리더에게 라우팅 요청**: 위 두 문단을 `ux-designer`에게 전달해 35-7 (f)를 재검토하게 할 것.
내가 직접 그 문서를 고치지 않았다(소유자가 다르다).

## 5. 유휴 1 — 로프 등반 (`RopeClimb`) · **수평 소유** · 던전 진입 겸용

### 5-1. 그림

작은 창 상단을 향해 로프를 던져 걸고, **발로 로프를 물고 다리로 서는 방식**으로 올라간다.
맨 위에서 `ParkourClimb`의 **맨틀 박자를 그대로 재사용**해 창 위에 올라선다.

### 5-2. 박자 A — 던지기 **0.89초**

| # | 박자 | 종류 | 길이 | 각도 |
|---|---|---|---:|---|
| 1 | 뒤로 넘기기 | 동작 | **0.22초** | 앞팔 어깨 −132°, 팔꿈치 78°. 상체 **−12°** |
| 2 | 던지기 | 동작 | **0.26초** | 어깨 −132 → **+74°**, 팔꿈치 78 → 14°. 상체 −12 → **+16°** |
| 3 | 걸림 확인 | 정지 | **0.19초** | 릴리즈 자세 유지. 로프 비행 **0.34초**가 이 박자와 겹쳐 끝난다 |
| 4 | 당겨 팽팽 | 동작 | **0.22초** | 양팔 어깨 **+142°**(위로), 팔꿈치 34°. 상체 **−16°**(체중을 뒤로) |

`k_min = 0.895`.
**로프 비행 0.34초**는 릴리즈 프레임 기준이며 `archeryArrowFlightSeconds(0.62)`보다 짧다 — 거리가 짧고
로프는 화살보다 무겁게(포물선 정점 낮게) 난다. 정점 비율 **0.22**(활 0.38 대비 낮음).

### 5-3. 박자 B — 등반 1사이클 **0.99초**, 상승 **0.374498 H**

| # | 박자 | 종류 | 길이 | 무릎 | 팔꿈치 | 상승 |
|---|---|---|---:|---:|---:|---:|
| 1 | 접기(Tuck) | 동작 | **0.26초** | 20 → **126°** | 118 → **22°** | 0 |
| 2 | 뻗기(Drive) | 동작 | **0.30초** | 126 → **20°** | 22 → **118°** | **+0.220698 H** |
| 3 | 당기기(Pull) | 동작 | **0.23초** | 20° 유지 | 118° 유지 | **+0.153800 H** |
| 4 | 그립 확정 | 정지 | **0.20초** | | | 0 |

`k_min = 0.850`.

**상승량은 고른 값이 아니라 유도값이다**:
- 다리 행정 = `|다리|(0.417637) − eff(0.219809, 0.197828, 126°)(0.190612) = 0.220698 H`
- 팔 행정 = `eff(0.167055, 0.162659, 22°)(0.323657) − eff(…, 118°)(0.169857) = 0.153800 H`
- `eff(u,l,b) = √(u² + l² + 2ul·cos b)`, `b` = 굽힘각(0 = 곧게 폄)

**등반 속도 = 0.374498 / 0.99 = 0.37828 H/s = 21.1 pt/s** (배율 0.60).
보행의 **34.4%**, `ParkourClimb`(55.8 pt/s)의 **37.9%**. 로프는 느린 것이 맞다 —
`ParkourClimb`가 "한 번에 뛰어오르는" 것이라면 이건 "힘들게 오르는" 것이다.

### 5-4. 박자 C — 맨틀

**`ParkourClimb`의 맨틀·정착 박자를 그대로 쓴다**(재구현 금지):
`parkourClimbMantleArmDegrees 62 / MantleElbow 18 / MantleHip 40 / MantleKnee 39`,
맨틀 **0.28초**(동작) + 정착 **0.14초**(블렌드아웃).
`MantleHip − MantleKnee ≈ 1°`(정강이 수직)라는 관계가 이미 검증돼 있으므로 **두 값을 따로 만지지 않는다.**

### 5-5. 대상 선정 — 유효 대역

```
ropeClimbMinRiseHeights = 1.20 H  (= 67pt @0.60)   로프가 캐릭터 키보다 길어야 로프로 읽힌다
ropeClimbMaxSeconds     = 12.0초                   -> 유도 상한 4.54 H (= 253pt @0.60)
유효 대역 = [1.20 H, 4.54 H]                       12 사이클
```

| 상한 후보 | 최대 높이 | 사이클 | 유휴 최장(낚시 11.85초) 대비 |
|---:|---:|---:|---:|
| 9.0초 | 190pt (3.40 H) | 9 | 75.9% |
| **12.0초 ★권장** | **253pt (4.54 H)** | **12** | **101.3%** |
| 14.0초 | 296pt (5.30 H) | 14 | 118.1% |
| 18.0초 | 380pt (6.81 H) | 18 | 151.9% |

**대상은 창만이다.** 하단 예약 막대(Dock/작업표시줄)는 제외한다 —
배율 0.35에서 Dock 단차가 **2.06 H**가 되어 대역에 들어오고, 그러면 로프를 Dock에 건다.
"작은 창" 판정은 `Interaction/WindowTheftTargetRules.IsEligibleTarget`을 **그대로 재사용**한다
(폭 기준이라 높이 조건은 위 대역이 따로 진다).

**상한을 넘는 창은 시작하지 않는다. 도중에 포기하지 않는다.**
도중 포기는 `ActivityExitReason`을 오염시킨다 — "12초가 지나서 그만뒀다"를 `Completed`로 기록하면
이 문서 1-4절이 고치려는 결함이 새 행동에서 재발한다.

### 5-6. 전이 / 완료 계약

```
Idle ──(IdleActivityDirector 선택 + 대상 창 유효 + 대역 통과)──> RopeClimb
  ├ 접근(수평 소유, 상한 8.0초) ─> 정지 0.14초
  ├ 던지기 0.89초
  │    └ 던지는 중 대상 창 소실 ─> 로프 회수 0.19초 ─> Idle   [PreconditionLost, 무대사]
  ├ 등반 사이클 × N (수평·수직 모두 소유)
  │    ├ 대상 창 소실/이동으로 로프 끝이 사라짐 ─> **로프를 놓는다** ─> Fall  [PreconditionLost, 무대사]
  │    │     ★ 이때 LedgeHang이 아니라 Fall이다 — 잡고 있던 것이 모서리가 아니라 로프이므로
  │    │       손이 갈 곳이 없다. Fall 진입 시 수직 속도는 그 시점 등반 속도(+0.378 H/s 상승)를
  │    │       그대로 넘긴다 — 위로 올라가다 멈추고 떨어지는 것이 물리적으로 옳다.
  │    └ 상한 12.0초 초과 ─> **발생하지 않는다**(대역이 미리 막는다). 안전망으로만 Fall.
  ├ 맨틀 + 정착 ─> Idle                                      [Completed, "올라왔다"]
  └ 외력/드래그/전체화면 ─> Ragdoll|Dragged|Idle              [ForcedInterrupt, 무대사]
```

**★ 던전 진입 겸용의 확장 훅**: 종료 시 `RopeClimbCompleted(handle, topWorldY, ActivityExitReason)`
이벤트 하나만 낸다. 던전 디렉터는 그것을 구독해 "문 열기"로 이어붙인다.
**등반 상태는 던전을 모른다** — 원칙 4(플러그인 구조)를 여기서 미리 지킨다.

### 5-7. 무게감

- **상승은 등속이 아니다.** 사이클 상승의 **59%가 뻗기 박자(0.30초)에**, 41%가 당기기(0.23초)에
  실리고 접기·그립 확정에는 **0이다.** `ParkourClimb`의 `ClimbRiseProfile`과 같은 사상이다.
- **로프의 이차 운동**: 캐릭터 아래쪽 로프가 사이클 위상에 맞춰 흔들린다. 진폭은 캐릭터 아래 로프
  길이에 비례(길수록 크게) — LineRenderer 소관이라 값은 렌더러가 정한다.
- **접기 박자의 몸 침하**: 다리를 당기는 동안 몸이 **−0.014 H** 내려간다(팔이 늘어난다). 작지만
  이게 있어야 "매달려 있다"가 된다.

### 6-6. ★ Windows 폴백 — 발판이 아예 없는 경우

`IReservedBottomBarService.TryGetReservedBottomBarOsScreen()`이 **false**를 돌려주는 것은
*"추정해 보라"가 아니라 "하단 예약 막대가 지금 존재하지 않는다"는 확정 신호*다
(그 인터페이스 문서 원문). Windows에서 **자동 숨김이거나 좌/우/상단 도킹**이면 상시 false다.

> ### ★ 2026-09-02 병행 라운드 반영 — false가 나는 경우가 **줄었지 사라지지 않았다**
>
> 같은 날 다른 라운드가 `IReservedBarAutoHideControl` /
> `ReservedBarRevealPolicy` / `WindowsReservedBarAutoHideControl`을 착륙시켰다(작업 트리에서 확인).
> 앱 실행 중 **Windows 작업표시줄의 자동 숨김 비트를 해제**하므로, 자동 숨김 케이스는 대개
> true로 바뀐다. **그래도 폴백을 지우면 안 되는 이유 4가지**:
> 1. **좌/우/상단 도킹은 그대로 false다.** 그 컨트롤이 여는 것은 자동 숨김 비트 하나뿐이고,
>    막대를 옮기는 능력(`ABM_SETPOS`)은 계약에서 명시적으로 배제돼 있다.
> 2. **macOS는 이번 라운드에 구현되지 않았다**(그 인터페이스 문서 39~41행: *"구현하지 않는
>    플랫폼(현재 macOS/모바일)"*). macOS Dock 자동 숨김은 여전히 폴백 대상이다.
> 3. 해제 실패/`Unavailable`(조회 실패) 경로가 정책에 정식으로 존재한다 —
>    *"모르면 건드리지 않는다"*.
> 4. 낚시는 **폴백이 있으면 더 좋아지는** 행동이다(창 상단이 Dock보다 줄 여유가 크다).
>    폴백을 지우는 것은 기능을 줄이는 쪽이다.
>
> **즉 아래 3단계는 그대로 유효하다.** 바뀌는 것은 ①의 적중률뿐이다.

```
발판 선택 순서:
 ① 하단 예약 막대의 바깥 모서리    (macOS 상시 / Windows 하단 도킹 + 비자동숨김)
 ② 현재 발판(창 상단)의 바깥 모서리 ← Windows 폴백
      전제: 발판 폭 ≥ 1.2 H (앉을 자리) AND 모서리에서 화면 하단까지 낙차 ≥ 0.9 H (줄 여유)
 ③ 둘 다 불가 ─> **낚시를 시작하지 않는다**(활동 가중치에서 이번 라운드 제외)
```

**왜 ②가 그림으로 성립하는가**: 걸터앉기는 "모서리 + 아래쪽 빈 공간"만 있으면 된다.
창 상단도 모서리이고, 창 높이가 Dock 두께(75pt)보다 크므로 **줄이 늘어질 여유가 오히려 더 크다.**
새 자세가 하나도 필요 없다.

**왜 ③(시작 안 함)이 옳은가**: 화면 최하단 안전망 위에서 낚시하면 **"바닥에 앉아 바닥을 낚는"**
그림이 된다. 그리고 전제조건을 강하게 잡는 것이 곧 `Aborted` 발생률을 줄이는 길이다 —
**시작하지 않은 활동은 오기록될 수 없다.**

### 6-7. 비정상 이탈 — 앉은 자세에서 발판을 잃으면

**`GroundLossHang`(제자리 종종걸음 + 팔 허우적)으로 보내면 안 된다.** 그 상태는
"서 있다가 발밑이 사라졌다"의 그림이고, 앉은 자세에서 그리로 가면 몸 오프셋 −0.410909 H가
한 프레임에 0으로 튄다(**22.95pt 순간 점프**).

```
낚시 전용 이탈:  대 놓기 0.10초(전이 하한) ─> Fall
  · 그 0.10초 동안 몸 오프셋을 −0.410909 → 0으로 SmoothStep 복귀시킨다 (튐 제거)
  · 낚싯대/줄 렌더러는 같은 프레임에 제거
  · [PreconditionLost] — **대사 없음**
```

## 7. 유휴 3 — 배경화면 감상 (`WallpaperGazing`) · 비소유

### 7-1. 그림 — 2D 측면도에서 "뒤를 본다"는 표현 불가

배경화면은 화면 **뒤**에 있는데 이 캐릭터는 측면도라 뒤를 볼 수 없다.
그래서 **액자를 소환해 앞에 놓고 본다** — 그라피티/블랙홀과 같은
"실제 OS 상태와 완전히 분리된 렌더 레이어" 패턴의 재사용이다.

### 7-2. 박자 — 총 **3.86초**

| # | 박자 | 종류 | 길이 | 하는 일 |
|---|---|---|---:|---|
| 1 | 정지 | 전이 | **0.14초** | |
| 2 | 액자 소환 | 동작 | **0.30초** | 앞팔 어깨 **+64°**, 팔꿈치 18°. 액자가 손 앞에 팝인 |

### 7-3. ★ 뒷짐 — 팔짱을 쓰지 않는 이유

팔짱은 **집중모드 시작 포즈**의 시각 어휘다(`UX_FLOW` 18절 *"안경을 쓰고 팔짱 끼는 확정 전이"*).
감상에 팔짱을 쓰면 화면만 보고는 **"지금 집중모드인가?"**가 구분되지 않는다.
그래서 이 저장소에 아직 없는 어휘인 **뒷짐**을 쓴다:

| 부위 | 값 |
|---|---:|
| 양팔 어깨 | **−28°** (뒤로) |
| 양팔 팔꿈치 | **52°** |
| 앞팔/뒷팔 어깨 차 | **6°** (실루엣 분리) |
| 상체 lean | **−6°** (약간 젖혀 올려다본다) |
| 다리 엉덩이 / 무릎 | **±11 / 8** |

### 7-4. 전제 / 완료 계약 / 원칙 1 제약

- 전제: `IDesktopWallpaperService`(읽기 전용 경로 조회)가 유효한 경로를 돌려주고, 로컬 다운샘플이
  끝나 있을 것. **화면 캡처 금지 / 서버 전송 금지**(원칙 3, 기획서 명시).
- `Completed` = 정착 박자 재생 완료. 그 외는 전부 `ForcedInterrupt`(무대사).
- **대사는 배경화면 내용을 절대 언급하지 않는다**(1-5절 마지막 문단). 앱은 픽셀을 안 읽는다.

## 10. 유휴 6 — 창 그림자 밑 낮잠 (`WindowShadeNap`) · **후순위**

기획서 스스로 "검증 후, 후순위"라고 적었고, 아래는 **개략 사양**이다.

### 10-1. 박자 (수면 루프 제외 **2.20초**)

### 10-2. 무게감 — **눕기는 떨어지는 것이 아니라 내려놓는 것이다**

- 눕기 0.52초 전체를 SmoothStep(감속)으로. 마지막 **0.12초**에 어깨가 면에 닿으며

  **랙돌이 아니다** — 아키텍처 0절대로 팔다리는 Kinematic + 절차적 각도다.

### 10-3. ★ 원칙 2 위험 — 실루엣이 낮아지면 "죽은 앱"으로 읽힌다

누우면 실루엣 높이가 **머리 지름(0.193 H = 10.8pt)** 수준이 된다. 이 저장소는 이미
"캐릭터 사라짐"(커밋 `802143f`)으로 한 번 데였고, 숨바꼭질에도 같은 경고가 붙어 있다.
→ **수면 중에도 호흡(3.2배 진폭)이 계속 보이게 하고**, 수면 루프 상한(40.0초)을 반드시 둔다.

### 10-4. 스탯 훅

**집중력 → 명상·졸음 해금**의 착지점이 여기다. 해금 임계와 수면 루프 길이가 그 값에 걸린다.
수치는 `design-systems`.

## 11. 유휴 7 — 단축아이콘 닦기 (`TaskbarPolish`) · **기하 한계 보고 있음**

### 11-1. ★★ 서서 닦는 것은 기하학적으로 불가능하다 (반증 실측)

발판 상면(y = 0)에 손끝을 대려면 **어깨가 팔 길이(0.329714 H) 안**에 들어와야 한다.
무릎과 상체를 최대로 접어도 그렇게 되지 않는다:

| 무릎 굽힘 | 엉덩이 높이 | 어깨 높이(상체 30° 굽힘 포함) | **손끝 최저** |
|---:|---:|---:|---:|
| 0° | 0.4176 H | 0.7336 H | **+0.4039 H** (+22.56pt) |
| 60° | 0.3619 H | 0.6778 H | +0.3481 H (+19.44pt) |
| 96° | 0.2799 H | 0.5959 H | +0.2662 H (+14.87pt) |
| 126° | 0.1906 H | 0.5066 H | +0.1769 H (+9.88pt) |
| **138°**(사실상 완전 쪼그림) | 0.1511 H | 0.4671 H | **+0.1374 H (+7.67pt)** |

**리그 상한을 전부 써도 손끝이 발판 위 7.67pt에 남는다.** 원인은 팔 길이다 —
이 리그의 팔은 **0.3297 H**인데 사람 팔은 대략 **0.44 H**다(어깨 0.82 H에서 손끝이 발에 닿는다).

### 11-2. 유일한 해 — 걸터앉아서 닦는다, 대신 궤적이 작다

걸터앉으면(12절, 몸 오프셋 −0.410909 H) 어깨가 **0.364883 H**로 내려와 팔 길이와의 차이가
**0.035169 H**밖에 안 남는다. 상체를 굽히면 닿는다:

| 상체 굽힘 | y=0 도달 x 구간 | 폭 |
|---:|---|---:|
| +0° / +12° / +18° | **도달 불가** (어깨 y > 팔 길이) | — |
| **+26°** | [+0.1259, +0.1940] H | 3.80pt |
| **+30°**(리그 상한) | [+0.0883, +0.2765] H | 10.51pt |

**문지름 궤적(상체 +26° ↔ +30°, 팔 최대 신장) = 0.082584 H = 4.61pt @배율0.60.**

> ### ★ 교차 레이어 보고 (리더 → design-character)
> 이 행동의 가독성은 **팔 길이 0.3297 H**에 직접 걸려 있다. 팔을 늘리면 닦기·쓰다듬기·책상업무가
> 동시에 좋아지지만 **비율은 내 소관이 아니다.** 리더 판단 요청.
> 팔을 안 늘리는 경우의 처방은 아래 11-4.

### 11-3. 박자 — 1구간 **1.30초**, 진행 **0.26 H**

| # | 박자 | 종류 | 길이 | 수평 소유 |
|---|---|---|---:|---|
| 1 | 밀기 | 동작 | **0.21초** | 비소유 |
| 2 | 당기기 | 동작 | **0.21초** | 비소유 |
| 3 | 밀기 | 동작 | **0.21초** | 비소유 |
| 4 | 당기기 | 동작 | **0.21초** | 비소유 |
| 5 | **엉덩이 옆걸음** | 동작 | **0.46초** | **소유** — 앉은 채 0.26 H 이동(31.6 pt/s) |

`k_min = 0.905`. **한 상태 안에서 소유권이 1.30초마다 교대한다** — 1-2절 처방이 필요한 대표 사례다.

앞뒤 고정분: 접근(가변, 상한 8.0초, 소유) + 정지 0.14 + 앉기 0.42 + … + 일어서기 0.42 + 정착 0.14.
루프 상한 `taskbarPolishMaxSeconds = 12.0초` → 약 **8구간 = 2.08 H = 116pt**.
**바 전체를 훑지 않는다.** Dock 폭 1123pt 실측을 전부 훑으면 59구간 = 77초로,
유휴 연출로 성립하지 않는다.

### 11-4. ★ 팔이 아니라 몸이 문지른다 — 4.61pt를 읽히게 만드는 법

**실제로 힘줘 문지를 때 사람은 팔보다 몸통을 쓴다.** 그 원리를 그대로 쓴다:

- 손끝 궤적 **4.61pt** (위 유도) — 이것만으로는 안 읽힌다.
- **상체 +26° ↔ +30° 왕복이 어깨를 3.9pt 움직인다** — 몸 전체가 리듬을 탄다.
- 박자 0.21초 왕복(2.38Hz)이 **속도로 읽히게 한다.**
- 반짝임 FX는 손끝 위치에 붙는다(렌더러 소관).

즉 이 행동의 시각 신호는 **궤적이 아니라 리듬**이다. 그래도 부족하면 **후순위로 미룬다** —
낮잠과 함께 이 둘이 9종 중 가장 약한 두 개다.

### 11-5. 발판 / 폴백 / 완료 계약

```
① 하단 예약 막대                                   (macOS 상시 / Windows 하단 도킹)
② 바탕화면 아이콘 열(IDesktopIconLayoutService, 읽기 전용)이 있는 발판
③ 둘 다 없으면 시작하지 않는다
```
`Completed` = 상한 도달 또는 구간 소진 후 **일어서기 + 정착까지 재생**.
발판 소실은 낚시와 **같은 이탈**(대 놓기 대신 손 떼기 0.10초 + 몸 오프셋 복귀 → Fall), `PreconditionLost`.

**아이콘 좌표는 조회 수단이 없다**(ARCHITECTURE 5-2-4). 개별 아이콘을 조준하지 않는다.

## 12. 공용 자세 — `SitOnEdge`(걸터앉기)

**낚시 · 닦기 · 낮잠 진입**이 공유한다. 새 자세 1개로 3종을 덮는 절약이다.

| 항목 | 값 | 근거 |
|---|---:|---|
| 몸 전체 오프셋 | **−0.410909 H** | 엉덩이 피벗을 발판 상단에 놓는다 |
| 앉기/일어서기 박자 | **0.42초** | 54.6 pt/s @0.60. SmoothStep |
| 앞다리 엉덩이 / 무릎 | **+18 / 22** | 정강이가 거의 수직으로 늘어진다 |
| 뒷다리 엉덩이 / 무릎 | **+12 / 16** | 좌우를 갈라 실루엣 확보 |
| 늘어진 다리 흔들기 | 무릎 **±9° @ 0.9Hz** | `ledgeHangSwayAmplitudeDegrees(5)`보다 크다 — 매달림은 참는 자세, 앉기는 편한 자세 |
| 상체 lean | 행동별 | 낚시 0° / 닦기 +26~+30° / 낮잠 진입 0° |

### 12-1. ★ 이 자세가 접지 규약을 깬다 — 이미 있는 처방을 쓴다

이 프로젝트의 접지 규약은 **"루트 원점 = 발바닥"**인데, 그건 **서 있을 때만 참**이다.
`GetupState`가 정확히 같은 문제를 겪었고 처방이 이미 있다:
**"지금 이 포즈의 최저 잉크가 루트 원점 높이에 닿는 데 필요한 만큼만" 들어 올리는 유도값**
(`StickmanBlackboard`의 잉크 바닥 클리어런스, `DockGeometry.ResolveEdgeStopDistance`와 같은 관례).

걸터앉기는 그 **반대 방향**이다 — 몸을 **내려야** 엉덩이가 발판에 놓인다. 그래서:
- **접지 스냅은 계속 루트 Y를 발판 상단에 못박고**, 앉기는 `SetBodyOffset(−0.410909 H)`으로만 표현한다.
  루트를 직접 내리면 접지 판정과 싸운다.
- **늘어진 다리가 발판 아래로 내려가는 것은 정상이다.** 잉크 클리어런스 안전망이 이걸
  "발판 관통"으로 오인해 몸을 들어 올리면 앉기가 무너진다.
  → **`SitOnEdge` 계열 상태에서는 잉크 클리어런스 리프트를 끈다**(또는 앉기 오프셋만큼 상쇄).
  **이걸 안 하면 앉는 순간 몸이 22.95pt 튀어 오른다.** 구현 시 첫 번째로 확인할 것.

신규 9종은 **그 목록에 들어가지 않는다** — 각자 자기 이탈 박자를 갖는 것이 옳다
(앉은 자세/매달린 자세에서 제자리 종종걸음으로 튀는 것을 막는다).

**★ FramePacing 등급 게이트**(ARCHITECTURE 5-2-4): 등급이 `Away` 이상(≈10fps/4fps)이면
**새 유휴 활동을 시작하지 않고, 진행 중인 것은 이탈 박자로 중단**한다.
`4fps 낚시 애니메이션은 고장으로 보인다.` 집중모드 2종은 **유저가 명시적으로 시작한 것**이므로
이 게이트에서 제외한다(보는 사람이 없다는 전제가 성립하지 않는다).

## 14. 스탯 연동 지점 (수치는 `design-systems`)

| 스탯 | 착지점 | 모션 쪽 제약 |
|---|---|---|
| **민첩 → 이동속도** | 접근 페이즈 보행 배율 · `TaskbarPolish` 옆걸음 속도 · `RopeClimb` 접근 | **각도에는 절대 곱하지 않는다.** 거리/시간에만 |
| **민첩 → 회전** | 방향 전환 시간(현재 즉시) | 전이 박자 하한 0.10초를 지킬 것 |
| **민첩 → 박자**(대안) | 전 박자 길이 × k | **k ∈ [0.905, 1.00]** — 하한은 협상 대상이 아니다(1-6절) |
| **근력 → 산출** | 곡괭이질 사이클당 광물 / 책상업무 페이지당 서류 | 박자를 건드리지 않는다 |
| **집중력 → 명상·졸음 해금** | `WindowShadeNap` 해금 임계 · 수면 루프 길이(8.0~40.0초) | 상한 40.0초는 원칙 2(실루엣 소실) 때문에 고정 |
| **집중력 → 세션** | 집중모드 세션 길이 | 체크 리액션 트리거(잔여 60초)는 고정 |

### ★ 권장 — 박자에는 배율을 곱하지 않는다

`k ∈ [0.905, 1.00]`은 **최대 9.5%**밖에 못 준다. 그 정도는 화면에서 안 보이는데
**박자 하한을 뚫을 위험만 새로 만든다.** 민첩은 **접근 보행 속도와 옆걸음 속도**에만 태우고,
연출 박자는 스탯과 무관하게 고정하는 쪽을 권장한다. 그게 "컨트롤 하나 = 효과 하나"이기도 하다.

## 16. 플랫폼 영향

### macOS 영향
- **낚시 / 닦기**: `IDockMetricsService`가 이미 Dock 사각형을 타일 실측으로 만들어 준다
  (실측 로그: `tilesize=49pt, 타일 20개, 폭 1123.0pt, 두께 75.0pt`).
  걸터앉기 다리 길이가 Dock 두께의 **30.6%**라 화면 밖으로 나가지 않는다 ✓.
  **폴백 경로가 발동할 일이 사실상 없다**(Dock 자동 숨김 시에는 발동한다 — 미확인, 실기 검증 필요).
- **로프 등반 / 집중모드 2종 / 감상 / 인형극 / 쓰다듬기 / 낮잠**: 플랫폼 무관.
- 신규 정책 판정(발판 선택 순서 ①②③)은 **`Platform/` 중립 위치**에 둘 것.
  `Platform/MacOS/` 안에 넣으면 Windows가 물리적으로 호출할 수 없다(`FullscreenSuspendPolicy` 실제 사고).

### Windows 영향 — **함께 설계함(낚시·닦기 2종), 별도 배정 필요 0건**
- **낚시가 갈리는 유일한 행동이다.** `Win32WindowService.TryGetReservedBottomBarOsScreen()`이
  **자동 숨김 / 좌·우·상단 도킹**에서 false를 돌려준다 = "하단 예약 막대가 없다"는 확정 신호.
  ★ 같은 날 병행 라운드의 `WindowsReservedBarAutoHideControl`이 **자동 숨김 쪽만** 해소한다
  (6-6절 박스). **좌·우·상단 도킹은 여전히 false**이므로 폴백은 반드시 남긴다.
  → **6-6절에 폴백 2단계 + 시작 안 함 조건을 설계에 포함했다.** 새 자세 0개, 새 각도 0개
  (창 상단 모서리에서 같은 `SitOnEdge`를 쓴다).
- **닦기도 같은 서비스에 의존**한다 → **11-5절에 같은 3단계 폴백**을 붙였다.
- **`PlatformParityAuditTests`에 추가할 항목(구현 라운드 인계)**:
  `Fishing` / `TaskbarPolish`의 **발판 선택 순서가 두 플랫폼에서 같은 코드를 타는가**.
  아직 구현이 없으므로 지금은 `Assert.Ignore("낚시/닦기 미구현 — 2026-09-02 모션 설계만 완료")`로

- 나머지 7종은 **Windows 영향 없음**(플랫폼 API를 전혀 안 탄다).

## 17. 미확인 (거짓 통과 방지)

1. **실기 빌드 캡처를 하지 않았다.** 리더에게 알리지 않고 앱을 띄우거나 빌드하지 않는다는 지시를
   지켰다. 이 문서의 모든 판정은 **저장소 실측 상수 + 기하 계산 + 기존 로그**로만 성립한다.
   **연속 프레임 캡처로만 잡히는 "튐"은 아직 하나도 검증되지 않았다** — 특히
   (a) 걸터앉기 진입/이탈의 22.95pt 오프셋 튐, (b) 정지 박자 0.14초가 실제로 부드러운지,
   (c) 곡괭이질 41° lean 왕복에서 `LimbCurveRenderer` 곡선이 무너지지 않는지.
2. **참고 영상/이미지를 이번 라운드에 새로 확보하지 못했다.** `~/.claude/uploads/`의 34개 파일을
   전수 확인했으나 Alan Becker 계열 스틱맨 레퍼런스는 **0장**이었다(성능 관련 텍스트 스크린샷,
   앱 자체 스크린샷, 작업관리자 캡처 등). 그래서 각도는 **기존에 이미 실측으로 확정된 값**
   (`parkourClimbMantle*` 37~44° / `landingCrouch*` / `ledgeHang*`)의 어휘를 승계하고,
   신규 각도는 **기하 유도 또는 그 어휘와의 정합**으로만 정했다. **새로 "레퍼런스에서 쟀다"고
   적은 값은 이 문서에 하나도 없다.**
3. **곡괭이질 상체 lean 41° 왕복이 액세서리(모자/망토)와 충돌하는지 미확인.**
   `design-equipment` 소관이며 리더 라우팅 필요.
4. **Dock 자동 숨김 상태에서 macOS가 `TryGetDockRectOsScreen`을 어떻게 돌려주는지 미확인.**
   낚시 폴백 ①→② 전이가 macOS에서도 발동하는지는 실기 확인이 필요하다.
   ★ 이 항목의 중요도가 병행 라운드로 **올라갔다** — `IReservedBarAutoHideControl`이
   Windows에만 구현되어(`docs/TASKBAR_REVEAL.md` 3절이 근거라고 적혀 있으나 **그 문서를
   읽지 않았다**), macOS는 자동 숨김 Dock에서 폴백에 의존하는 유일한 플랫폼이 된다.
5. **병행 라운드의 `ReservedBarRevealDirector`가 실제로 언제 도는지 미확인.**
   부팅 1회인지 주기적인지에 따라 "낚시 도중 막대가 사라지는" 경로의 빈도가 달라진다.
   그 경로 자체는 이미 `PreconditionLost`로 설계에 들어가 있다(6-7절).
6. **`FocusWatchDirector`의 실제 세션 길이 분포 미확인.** 체크 리액션 검산은
   `MinimumSessionSeconds = 60f`(코드 실측)만 근거로 했다. 데모 길이 `DemoSessionSeconds = 90f`에서도
   잔여 60초 트리거는 성립한다(90 > 60) ✓.
