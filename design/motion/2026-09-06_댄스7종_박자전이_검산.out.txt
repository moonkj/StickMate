2. ★ 정정 — §26의 두 속도 계산이 배율을 한쪽에만 곱했다
==============================================================================
ResolveWalkSpeed() = walkSpeed x 배율 (StickConfig.cs:2104). 즉 보행 속도는 배율에 비례한다.
§26은 **거리는 배율을 곱하고 속도는 안 곱한** 채로 두 값을 나눴다.

(가) D2 도움닫기 — §26-3-2는 '0.602초'라고 적었다.
     거리 = 1.6 H x 2.2747 x s = 3.63951s 유닛
     속도 = 1.45 x 2.5 x s = 3.6250s 유닛/초
     시간 = 3.63951 / 3.6250 = 1.00400초  (배율이 약분된다 = 배율 무관)
     ★ 0.602초가 아니라 **1.004초**다. §26의 값은 67% 짧다.
     => danceStarJumpRunSeconds = 1.00 (파생값. 필드로 두지 말고 거리/속도에서 계산할 것)

(나) D3 활강 속도 — §26-3-3은 '보행의 22.7%'라고 적었다.
     활강 = 0.3 H / 0.72초 = 0.68241s / 0.72 = 0.94779s 유닛/초
     보행 = 2.5 x s
     비   = 37.9%   (배율 무관)
     ★ 22.7%가 아니라 **37.9%**다. 22.7%는 '배율 곱한 활강'을 '배율 안 곱한 보행 2.5'로 나눈 값이다.
     결론은 살아남는다 — 보행보다 2.64배 느려서 보행과 혼동되지 않는다. 숫자만 틀렸다.

(다) D2 체공시간 — §26은 s=0.60 한 점에서만 중력과 맞췄다(0.66 vs 0.684, 오차 3.5%).
     중력과 맞는 체공 = 2*sqrt(2*g*h)/g,  h = 0.42 H x 2.2747 x s   =>  sqrt(s)에 비례한다
       s=0.35: 중력값 0.5222초   고정 0.66초 대비  +26.4%
       s=0.60: 중력값 0.6837초   고정 0.66초 대비   -3.5%
       s=0.75: 중력값 0.7644초   고정 0.66초 대비  -13.7%
       s=1.00: 중력값 0.8827초   고정 0.66초 대비  -25.2%
     ★ 고정 0.66초로 두면 s=1.00에서 25% 빨라(가벼워) 보이고 s=0.35에서 26% 느려(붕 떠) 보인다.
     => 상수 대신 **식**으로 둔다: t_air(s) = 0.7644 x sqrt(s/0.75)
        (배포 기본 배율 0.75에서 0.7644초. 내역은 상승:정점:하강 = 0.41:0.18:0.41 비율 유지)
        상승 0.313 / 정점 0.139 / 하강 0.313  (합 0.764)

3. 박자 흔들림(humanization) — '봇처럼 반복되면 안 된다'의 수치화
==============================================================================
§26의 루프는 전부 **정확한 주기**다. 그대로 두면 8~16초 동안 같은 간격이 20~30번 반복된다.
처방: 루프 경계에서만 재추첨하는 두 종류의 흔들림. (루프 중간에 바꾸면 위상이 튄다)

  danceLoopJitterFraction      = 0.06  : 다음 루프 길이 x U(1-0.06, 1+0.06)
  danceAmplitudeJitterFraction = 0.05  : 다음 루프의 봉우리 진폭 x U(0.95, 1.05)

유도(임의값이 아니다):
  상한 — 흔들림은 주파수를 1/(1-j)배까지 올린다. 그 최대 주파수에서도 진폭 이득 0.95를
         지켜야 하므로 1절의 dancePoseSmoothingRate가 j와 **함께** 결정된다.
         j=0.00 -> 필요 baseRate   72.4
         j=0.04 -> 필요 baseRate   75.4
         j=0.06 -> 필요 baseRate   77.0
         j=0.08 -> 필요 baseRate   78.7
         j=0.12 -> 필요 baseRate   82.3
         j=0.06이 baseRate 78과 짝이다. 더 키우면 계수가 함께 올라가고,
         계수를 계속 올리면 '지수 감쇠 = 즉시 대입'에 수렴해 이 앱의 부드러운 관절 연쇄가 죽는다.
  하한 — 가장 짧은 루프(D7 0.48초)에서 흔들림이 최소 한 프레임(60fps=0.0167초)보다 커야
         존재한다. 0.48x0.06 = 0.0288초 = 60fps에서 1.73프레임. 통과.

★ 예외 2건 (지어낸 예외가 아니라 그 동작의 정체성이다):
   · D5 로봇 — 흔들림 0. 메트로놈처럼 정확한 것이 이 동작의 농담 그 자체다(dime stop).
   · D1/D2 — 세트 내부 박자(회전/도약)에는 걸지 않고 **끝의 '호흡/복귀' 박자에만** 건다.
     회전 시간이 흔들리면 SetFacing 반전 간격이 흔들려 '회전'이 '떨림'이 된다.

4. 진입(Intro) / 퇴장(Outro) 박자 — §26이 비워 둔 자리
==============================================================================
§26은 D1/D2의 세트 내부 박자만 정했다. D3~D7은 '루프'만 있고 중립에서 들어가고 나오는
박자가 없다. 그대로 구현하면 Idle -> 루프 첫 프레임으로 **툭** 갈아탄다.

전이 속도의 앵커 2개 — 둘 다 이 저장소의 확정값이다(충격 구간은 앵커로 쓰지 않는다):
  집중 팔짱     94° / 0.72초 =  130.6 °/초   (숙고형 자세 변화의 느린 끝)
  활쏘기 당기기 109° / 0.42초 =  259.5 °/초   (숙고형 자세 변화의 빠른 끝)
  기하평균 w_intro = 184.1 °/초   <- 진입/퇴장 각속도 기준
  (참고 — 무릎앉아 압축은 126°/0.1116초 = 1129 °/초다. 그건 **충격 흡수**라
   운동량이 만든 속도이고 자발적 자세 변화의 앵커가 될 수 없다. 그래서 뺐다.)

규칙: t = ceil( (dMax / 184.1) / (loop/2) ) x (loop/2),  하한 0.20초
  · 반(half) 루프 격자로 올림 붙임 = 첫 루프가 박에 맞게 시작한다.
  · 하한 0.20초의 근거는 danceRobotStepSeconds(§26-3-5). 한 dime stop보다 짧은 구간은
    별개의 박으로 지각될 수 없다 — 그것이 이 저장소가 이미 확정한 '최소 박' 값이다.

  D1 피루엣         1.82초   <- 회전 (3) 시작 직후에 중단 요청
  D2 스타점프        1.50초   <- (2) 시작 직후 (도움닫기 중이면 0.28초 브레이크로 즉시 취소)
  D3 문워크         1.06초   <- 반루프 + 방향전환이 함께 걸린 경우
  D4 러닝맨         0.84초   <- 반루프 직후
  D5 로봇          0.40초   <- 키 경계 직후
  D6 프리샤트카       1.26초   <- 반루프(차기 1회) 직후
  D7 말춤          0.72초   <- 반루프 직후
  최악 = 1.82초 (D1)  =>  danceGracefulExitBudgetSeconds = 1.90 (감시견)
  ★ §26-6-4는 이 값을 '로봇 루프 1.60 + 정리 0.42 = 2.02초'로 적었다. 실제 구속은 로봇이 아니라
    피루엣 회전이다 — 로봇은 **어느 키 경계에서든** 나갈 수 있어 0.40초로 가장 빠르다.

사용자가 체감하는 '음악이 끝났는데 아직 춘다' 총 지연:
  폴링 0.5 + T2 3.0 + 퇴장 1.82 = 5.32초
  단, 듀티 사이클상 중단 요청의 73%는 **휴지 중**에 도착한다 — 그때는 화면에 아무 변화가 없다.

9. 듀티 사이클 + 피로 램프 — 원칙 2(비침해)의 수치
==============================================================================
§26-4-4: 에피소드 8~16 / 휴지 20~45 => 듀티 27.0%
그대로 두면 3시간짜리 플레이리스트에서 3시간 내내 27%로 춘다. 사람도 안 그러고, 상주 앱에서는
그게 곧 시선 강탈이다(원칙 2). 그리고 락 점유도 27%로 계속 남는다.

처방: 피로 램프 F(n) = min(1 + 0.25(n-1), 3.0)  — n = **이번 창 안에서의** 에피소드 번호
      휴지 = U(20,45) x F(n).  창이 닫히면(음악이 T2만큼 끊기면) n은 1로 되돌아간다.
      => 새 감상 세션은 늘 활기차게 시작하고, 한 세션이 길어질수록 조용해진다.

  n   F(n)      휴지 평균(초)      누적 시각(분)     누적 듀티
  1   1.00          32.5          0.74     27.0%
  2   1.25          40.6          1.62     24.7%
  3   1.50          48.8          2.63     22.8%
  4   1.75          56.9          3.78     21.2%
  5   2.00          65.0          5.06     19.8%
  6   2.25          73.1          6.48     18.5%
  7   2.50          81.2          8.04     17.4%
  8   2.75          89.4          9.72     16.5%
  9   3.00          97.5         11.55     15.6%
 10   3.00          97.5         13.38     15.0%
 15   3.00          97.5         22.50     13.3%
 20   3.00          97.5         31.62     12.6%
  정상상태 듀티 = 12.0/(12.0+32.5x3.0) = 11.0%
  램프 없는 §26 값 = 27.0%
  ★ 짧은 감상(1~2곡)에서는 §26과 거의 같고, 긴 감상에서만 갈라진다 — 그게 의도다.

10. T1~T4 맞물림 — 창(window)과 에피소드는 서로 다른 층이다
==============================================================================
AudioReactiveDancePolicy는 Start/Continue/Stop만 낸다. 그 출력을 **상태 전이에 직결하면**
음악이 나오는 내내 Dance 상태가 슬롯을 잡는다 = 7절의 함정 그 자체다.

  1층  창(Window)     : 정책의 Start로 열리고 Stop으로 닫힌다. 상태가 아니라 **플래그**다.
  2층  에피소드       : 창이 열려 있는 동안 디렉터가 에피소드/휴지를 반복한다. 상태는 여기서만 잡는다.

검산 — T3(최소 유지 8초)가 첫 에피소드를 자르지 않는가:
  정책이 Stop을 낼 수 있는 가장 이른 시각 = max(T2 3, T3 8) = 8초 (창 기준)
  가장 짧은 에피소드 = 8.16초 (+ 진입 브레이크 0.28)
  8.16 + 0.28 = 8.44 >= 8  =>  통과
  ★ 이건 우연이 아니다. T3 = MotionEpisodeMinSeconds이고 그 상수의 문서가 그렇게 적고 있다.
    에피소드 하한을 8초 아래로 내리는 순간 정책의 Stop이 에피소드 한가운데를 자른다.

검산 — T1(3초)과 첫 춤까지의 지연:
  음악 시작 + 폴링 0.5 + T1 3 + 진입 브레이크 0.28 + 진입 박자(최대 0.84)
  = 4.62초 뒤에 첫 루프가 돈다. (D2는 도움닫기 1.00초가 그 자리를 대신한다)

검산 — T4(1200초 = 20분) Lockout에서 몇 번 추고 잠기는가:
  고착 신호(공백 0)로 20분을 채우는 동안 에피소드 약 14회, 총 춤 시간 약 2.8분
  = 20분 중 14.0%. Lockout이 걸리면 그 뒤 8초 연속 무음까지 완전 정지.
  ★ Stop(고착 상한)은 **강제 중단이 아니라 정상 퇴장**으로 처리한다 — 급한 일이 아니다.
    강제 0.18초 크로스페이드는 억제(집중/숨김/드래그)에만 쓴다. 그 셋은 사용자 의도가 급하다.

11. 5% 진폭 손실이 §26의 기하 검산을 깨뜨리는가 — 실제로 재본다
==============================================================================
D3 뒤꿈치 들림 — §26은 0.08126 H(획의 1.47배)라고 했다.
  재현 0.08122 H  (일치)
  진폭 95%에서 0.07453 H = 획의 1.35배  ->  여전히 획 두께 위. 통과

D1 retire 발끝 높이 — 목표 하강 0.21981 H (지지 다리 무릎)

    정상상태 오차 0이다. 이 검산은 감쇠와 무관하게 그대로 성립한다.

결론: 진동 신호에만 손실이 걸리고, 0.95 기준에서 §26의 검산 4건은 전부 여유가 남는다.

12. 발판 여유 요구 — §26-7-2 재검증 (도움닫기 시간이 바뀌었으니 다시 잰다)
==============================================================================
D2 수평 예산 (danceStarJumpHorizontalBrakeScale=0.25, 착지 감쇠 14/초):
  도움닫기 1.60 H
  공중 잔여 = 0.25 x 1.45 x walkSpeed x t_air / H = 0.3045 H   (§26 추정 0.43)
  착지 감속 = v/k = 0.0285 H                                     (§26 추정 0.25 — 훨씬 보수적이었다)
  합 1.9330 H + 여유  =>  §26의 2.70 H는 여유 0.767 H로 **여전히 유효**하다.
  (배율 무관 — 세 항 전부 H로 정규화하면 배율이 약분된다. 단 t_air가 sqrt(s)라 공중 잔여만
   배율에 따라 0.3517(s=1.0) ~ 0.5944(s=0.35) H로 움직인다.
   최악 0.5944 H를 넣어도 합은 2.223 H로 2.70 안이다.)

나머지 6종은 이동이 없거나(§26-7-2) 후진 왕복이라 §26 값을 그대로 승계한다:
  제자리 5종 0.45 H / D3 문워크 1.60 H / D2 스타점프 2.70 H
