§0 교정(CALIBRATION) — 알려진 값으로 먼저 맞춘다
==============================================================================
  [OK ] pcm_bytes(1000ms) == 96000 B                   = 96000.0
  [OK ] pcm_bytes(250ms)  == 24000 B                   = 24000.0
  [OK ] pcm_bytes(0ms)    == 0 B                       = 0.0
  [OK ] kb(1024)          == 1.0 KB                    = 1.0
  [OK ] mb(1048576)       == 1.0 MB                    = 1.0
  [OK ] interval(1/day)   == 86400 s                   = 86400.0
  [OK ] interval(354/day) == 244.07 s  (narrative 실측 재현) = 244.0677966101695
  [OK ] interval(24/day)  == 3600 s                    = 3600.0
  [OK ] occupancy(86400s) == 100 %                     = 100.0
  [OK ] occupancy(864s)   == 1 %                       = 1.0
  [OK ] occupancy(0s)     == 0 %                       = 0.0

  ★ 교차 교정 — 다른 팀의 출하된 숫자를 우리 함수로 재현할 수 있는가
     design-narrative R2: 말풍선 하루 354회 / 간격 244초 / 화면 점유율 0.690%
  [OK ] narrative 간격 244초 재현                           = 244.0
     -> 역산: 말풍선이 하루에 화면에 떠 있는 총 시간 = 596 초 (= 9.9 분)
        354회로 나누면 1회당 1.68 초
     -> 개선 전(3,654회 / 7.23%)으로 같은 역산: 1회당 1.71 초
        두 역산이 1.68 vs 1.71 로 일치한다 = narrative의 두 숫자쌍이 서로 정합적이고,
        내 함수가 그것을 재현한다. **교차 교정 통과.**

  음성 대조 — 일부러 틀린 기대값(pcm_bytes(250ms)를 30000 B로)이 통과하는가?
    통과했는가: False   (False여야 정상 — True면 검사기가 고장난 것)

  교정 12/12 통과 + 음성 대조 통과. 아래 표는 전부 이 함수들로 계산됐다.

§1 자격 시험 — 허가(Permission) 2문 AND / 필요(Necessity) 1문
==============================================================================

  허가 P1 [원인]  : 인과 사슬의 시작이 사용자의 명시적 조작인가?
  허가 P2 [예상]  : 사용자가 그 소리가 날 것을 이미 알고 있었는가?
                    (= 소리가 '새 정보를 놀라움으로' 전달하지 않는가)
  필요 N  [정보]  : 소리가 없으면 사용자가 놓치는 것이 있는가?

  판정 = P1 AND P2 -> 소리를 만들 수 있다.  P1 또는 P2가 아니오 -> 만들지 않는다.
  N은 티어를 가르지 않는다(마스터 하나에 전부 딸린다). N=예 인 항목은
  '시각 신호 필수' 등급이 올라간다 — 소리가 유일한 전달자가 되면 안 되므로.

  후보                                         P1   P2   N    판정
  --------------------------------------------------------------------------
  사용자가 누른 것 — 단축키/버튼                         O    O    -    자격 있음
  집중 세션 시작                                   O    O    -    자격 있음
  ★ 집중 세션 완료(재화 지급)                          O    O    O    자격 있음
  집중 세션 중도 취소                                O    O    -    자격 있음
  구매                                         O    O    O    자격 있음
  착용 / 해제                                    O    O    -    자격 있음
  던진 뒤 착지 / 구르기 (사용자가 던짐)                    O    O    -    자격 있음
  로데오 커서 잡기                                  O    O    -    자격 있음
  자율 착지 (배회하다 떨어짐)                           X    X    -    ★ 자격 없음
  자율 파쿠르 등반                                  X    X    -    ★ 자격 없음
  자율 모서리 매달리기                                X    X    -    ★ 자격 없음
  레벨업                                        X    X    O    ★ 자격 없음
  말풍선 발화                                     X    X    -    ★ 자격 없음
  오류 / 예외 상태                                 X    X    O    ★ 자격 없음
  발판 소실 매달리기(사용자가 창을 닫음)                     O    X    -    ★ 자격 없음
  설정창 [미리듣기] 버튼                              O    O    O    자격 있음
  --------------------------------------------------------------------------
  자격 있음 9 / 16  (56.2%)   자격 없음 7 (43.8%)

  ★ 판별 기준 반박 — 리더 제안 '사용자가 방금 한 행동의 결과인가'를 그대로 쓰면
     '집중 세션 완료'가 탈락한다(25분 = 방금이 아니다). 그런데 그것은 이 앱에서
     소리가 가장 필요한 단 하나의 순간이다(재화 지급 = 회수 불가).
     -> 하중을 받는 것은 '방금'(최근성)이 아니라 '예상됨'이다. P2로 교체한다.
     교체해도 자율/말풍선/오류/레벨업은 전부 그대로 탈락한다(P1에서 이미 걸린다).
     즉 P2로 바꾸는 것은 기준을 느슨하게 하는 것이 아니라 정확하게 하는 것이다.

§3 파일 크기 — 디스크 / 빌드 / 스팀
==============================================================================
  실측 현재 빌드: macOS .app 98.8 MB(146파일) / Windows 84.3 MB(141파일)
  실측: UnityEngine.AudioModule.dll 이 두 빌드에 **이미 들어 있다**
        (macOS 93,184 B / Windows 104,360 B). FMOD는 UnityPlayer 안에 있다.
  -> ★ 오디오를 켜는 것의 바이너리 비용 = 0 바이트. 늘어나는 건 클립뿐이다.

  기본 세트 13파일 / 4.65 s / PCM 원본 435.9 KB = 빌드의 0.431 % (macOS 기준)

  포맷 후보 비교 (총 4.65 s, 모노 48 kHz)
    포맷                                디스크        메모리 비고
    PCM (무압축)                     435.9 KB    435.9 KB  디코드 0, 헤더 오버헤드 0
    ADPCM (Unity 4bit)            109.0 KB    435.9 KB  3.5~4:1, 디코드 매우 쌈
    Vorbis q0.7                    97.4 KB    435.9 KB  ★ 0.3초 클립에 코드북 헤더 ~4 KB/파일이 붙는다

  판정: **PCM**. 최대 절감액(Vorbis 채택 시)은 338.5 KB = 빌드의 0.335 % 다.
        ★ 정직 정정: Vorbis(97.4 KB)가 ADPCM(109.0 KB)보다 작다 — 헤더 오버헤드를
        넣어도 그렇다. 그러나 세 후보의 차이가 전부 빌드의 0.4% 미만이므로
        **크기는 이 선택의 결정 변수가 아니다.** 결정 변수는 24시간 상주 앱에서
        디코드 스레드/CPU를 새로 들이느냐이고, 그 답이 PCM이다.
        (Vorbis 헤더 4 KB/파일 x 13파일 = 52 KB 는 추정치 — 실측 아님)

§4 팩 스키마 산술 — 덮어쓰기 vs 더하기
==============================================================================
  팩당 상한 6키(정확한 키 지정, 와일드카드 금지). 팩은 키를 추가할 수 없다.

  팩                   키수      길이 ms     PCM KB
  pack.office          6       2450     229.7
  pack.cyber           6       1900     178.1
  pack.graffiti        6       1800     168.8
  pack.sports          6       2300     215.6
  pack.ink             6       1950     182.8
  pack.military        6       2300     215.6
  ---------------------------------------------
  6팩 합계               36               1190.6  (= 1.16 MB)

  기본 435.9 KB + 6팩 1190.6 KB = 전량 소유 최악 1.59 MB
  macOS 빌드 99 MB 대비 1.61 % (기본만 배포하면 0.431 %)
  팩 1개당 평균 198.4 KB — 스팀 DLC depot 1개가 오디오 때문에 커지는 양.

  ─ 만약 '더하기(additive)'로 설계했다면 ─
  6팩 전량 소유 시 한 키에 몰리는 클립 수:
    sfx.land.throw           6개 팩이 같은 키를 교체하려 한다
    sfx.equip.wear           5개 팩이 같은 키를 교체하려 한다
    sfx.focus.start          3개 팩이 같은 키를 교체하려 한다
    sfx.focus.complete       3개 팩이 같은 키를 교체하려 한다
    sfx.equip.remove         3개 팩이 같은 키를 교체하려 한다
    sfx.archery.release      3개 팩이 같은 키를 교체하려 한다
    sfx.shop.purchase        2개 팩이 같은 키를 교체하려 한다
    sfx.archery.draw         2개 팩이 같은 키를 교체하려 한다
    sfx.archery.bullseye     2개 팩이 같은 키를 교체하려 한다
    sfx.ragdoll.impact       2개 팩이 같은 키를 교체하려 한다
    sfx.archery.hit          2개 팩이 같은 키를 교체하려 한다
    sfx.rodeo.grab           2개 팩이 같은 키를 교체하려 한다
  최악 키 = sfx.land.throw (6개 팩)
  더하기로 동시 재생하면 이론 합성 이득 = +15.56 dB (동일 신호 가정)
    -> 마스터 기본 -13.26 dB 위에 얹으면 출력 피크 1.30 dBFS
    -> R1 §1이 확보한 OS 알림음 대비 여유 8.26 dB 가 -7.30 dB 로 무너진다.
  동시 발성 상한 3(R1 §4-4)도 6 > 3 으로 즉시 초과한다.
  ★ 결론: **덮어쓰기. 1 트리거 키 = 최대 1 클립.** 더하기는 두 가지를 동시에 깬다 —
     (a) 볼륨 예산, (b) '돈을 낼수록 시끄러워진다'는 구조. 협상 불가.

  ─ 그러면 6팩 전량 소유 시 sfx.land.throw 는 누가 이기는가 ─
  채택: **사용자가 [이벤트] 탭에서 사운드 테마를 정확히 하나 고른다.**
        기본값 = '기본(팩 없음)'. 팩을 사도 소리는 자동으로 바뀌지 않는다.
  기각 A: 팩 로드 순서 / packVersion 최신 우선 -> 비결정적. 팩 업데이트가 소리를 바꾼다.
  기각 B: 착용 중인 4슬롯의 다수결 -> 2:2 동률이 흔하고(4슬롯), 모자 하나 바꾸면
          소리 6개가 조용히 전부 바뀐다. 사용자가 고른 적 없는 변경이다.
  기각 C: 매니페스트에 우선순위 int -> 팩끼리 숫자 경쟁. 볼륨 필드와 같은 종류의 누수.

  ★ 이펙트와 반드시 다르게 구현해야 한다:
     ARCHITECTURE 5-3-2 (D)는 (stateId, trigger) -> **이펙트 목록**(리스트)이다 = 더하기.
     사운드는 (triggerKey) -> **클립 하나**다 = 덮어쓰기.
     같은 레지스트리 헬퍼를 재사용하면 사운드가 조용히 더하기가 된다. 분리 필수.

§5 재발행 비용 — 지금 굳는 것과 나중에 바꿔도 되는 것
==============================================================================
  game-architect: '팩은 6개라 재발행 비용이 세이브의 6배다.'
  -> 팩 6개 × 채널 1(스팀) = 재발행 단위 6개. 세이브는 1개.

  스키마 요소                                 재발행?       이유
  --------------------------------------------------------------------------
  트리거 키 문자열 집합                           예          팩이 문자열로 참조한다. 이름 변경·삭제 = 6팩 전부 깨짐
  assetKey(주소) vs AudioClip 직접참조         예          직접참조면 미소유 팩도 매니페스트와 함께 로드된다
  클립 원본 포맷(모노/48k/16bit/WAV)             예          재수록은 원본 재작업 = 6팩 전부
  팩당 키 상한 6                              아니오        늘리는 건 하위호환. 줄이면 재발행
  soundSchemaVersion 필드 존재               예          없으면 키 집합을 영원히 버전할 수 없다
  키 '추가'                                 아니오        구팩은 그 키를 안 덮을 뿐 — 기본 클립이 난다
  음색·믹싱(클립 내용)                           아니오        같은 키에 새 파일 = 팩 업데이트 1건
  티어/예산/볼륨/묵음 조건                         아니오        ★ 애초에 팩 스키마에 넣지 않는다(앱 소유)

  즉 '지금 안 정하면 6팩 재발행'인 것은 4건뿐이다.
  나머지는 나중에 정해도 된다 — 그게 이 스키마의 설계 목표다.

§6 원칙 2(비침해) 잔여 위험 — '회의 중이면?'
==============================================================================
  §1-B에서 티어 C/M이 전부 사라졌으므로, 남은 14키는 전부 사용자 조작이 원인이다.
  -> 회의 중에 소리가 나려면 **사용자가 회의 중에 그 조작을 해야 한다.**

  잔여 벡터는 정확히 하나다: **sfx.focus.complete**
    사용자가 25분 집중을 걸어 놓고 그 사이에 회의에 들어갈 수 있다.
    이것이 이 설계 전체에서 유일하게 '사용자가 지금 안 하고 있는데 나는 소리'다.

  1차 방어선(추가 구현 0): FramePacingPolicy.RecentInputSeconds = 2f [실측]
    티어 Active = 최근 2초 내 입력. 회의 중 사용자는 듣고 있지 타이핑하지 않는다.
    -> 완료 순간 입력이 2초 내에 없으면 무음, 시각 신호만 남는다.
  2차 방어선(P2): M9 마이크 사용 중 — 회의를 직접 관측한다.
  3차: M6 야간 / M5 집중모드 / M1 전체화면 — R1 §3 그대로.

  ★ 구현 함정 (이걸 안 적으면 '완료음이 영원히 안 난다'가 된다):
    M5(집중 모드 중 묵음)를 **전이 전 상태**로 평가하면 focus.complete가 자기 자신에게
    막힌다. 묵음 조건은 반드시 **전이가 확정된 뒤의 상태**로 평가한다.
    (절대 불변 원칙 1 '상태 전이가 확정된 뒤 그 상태로부터만 파생'의 사운드판)

  ★ 즉시 숨김 ⌃⌥⌘K — 소리도 멎는가: **구조적으로 멎는다.**
    StickmanAgent.SetUserHidden -> ApplySuspendDecision -> Suspend()
    Tick()이 `if (_isSuspended) return;`(StickmanAgent.cs:623)로 조기 반환한다 [실측].
    상태 전이가 아예 일어나지 않으므로 상태 파생 소리는 발생할 수 없다.
    다만 상태 밖 경로(설정창 버튼/구매)는 별도 게이트가 필요하다:
      묵음 조건에 **M8 = StickmanAgent.IsSuspended** 를 명시적으로 넣는다.
      IsSuspended 는 전체화면 자동 숨김과 사용자 숨김을 **이미 합성한 값**이다
      (StickmanAgent.cs:1152 `_fullscreenAutoHide || _userHidden`) [실측] —
      두 축을 사운드가 따로 볼 이유가 없다.

§7 백신·배포 위험 — 오디오가 실제로 늘리는 표면
==============================================================================
  시장 조사 결론(MARKET_LANDSCAPE 3-3): Shimeji를 죽인 건 기능이 아니라 배포와 백신 경고.
  SECURITY_MODEL 선 3: 난독화·패킹·무결성 자가검사는 전부 백신이 싫어하는 형태.

  오디오 도입안                                    백신 표면 증가
  --------------------------------------------------------------------------
  Unity 내장 오디오(m_DisableAudio=0)             0 — AudioModule.dll이 이미 서명된 빌드에 있다 [실측]
  OS 원샷 P/Invoke(winmm / AudioToolbox)       0 — OS 라이브러리. 새 바이너리 없음
  ★ 네이티브 오디오 플러그인 번들(.dll/.bundle)           ★ 큼 — 서명 안 된 새 바이너리. 금지
  ★ 런타임 오디오 다운로드(CDN/원격 팩)                   ★ 큼 — 실행 중 파일 기록 + 네트워크. 금지
  클립 13개 436 KB 를 depot에 동봉                  0 — 데이터 파일은 휴리스틱 대상이 아니다

  판정: 오디오는 백신 위험을 **늘리지 않는다** — 위의 두 금지선만 지키면.
  실제 위험은 크기가 아니라 '실행 중에 새 실행가능 바이트가 생기는가'다.
  빌드 증가분 436 KB(0.431%)는 SmartScreen 평판에도 무의미하다.

  ★ 다만 하나 진짜 비용이 있다 — macOS 마이크 방어선(M9, P2)을 넣으면
    Info.plist에 NSMicrophoneUsageDescription이 필요해질 수 있다.
    권한 프롬프트는 이 카테고리에서 **최대 이탈 요인**이다(Shimeji의 교훈).
    -> M9는 kAudioDevicePropertyDeviceIsRunningSomewhere(장치 속성 조회, 캡처 아님)로만
       구현하고, 권한 프롬프트가 뜨면 **그 자리에서 기능을 버린다**. 실기 확인 대상.
