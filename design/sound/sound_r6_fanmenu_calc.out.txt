§1. 이 표면의 «사건»을 전부 센다 — 자격 시험 P1(원인) AND P2(예상)
======================================================================================

  기준 원문 (SOUND_QUALIFICATION.md §1-2, 오늘도 그대로 쓴다):
    P1 원인 : 인과 사슬의 «시작»이 사용자의 명시적 조작인가
    P2 예상 : 사용자가 그 소리가 날 것을 «이미 알고 있었는가»
    허가 = P1 AND P2. 하나라도 아니오면 그 소리는 만들지 않는다.

  사건                               P1   P2   판정        프로덕션 근거
  ------------------------------------------------------------------------------------------------
  펼침 (우클릭/톱니 클릭)                    O    O   자격 있음     Expand / ExpandTotalSeconds 0.30
  칸 호버 (이름표 노출)                     O    X   자격 없음     HoverSeconds 0.09 / HoverLabel*
  칸 선택 (클릭)                         O    O   자격 있음     PressFlashSeconds 0.09
  접힘 User (선택/재클릭/밖클릭)              O    O   자격 있음     CollapseUserSeconds 0.13
  접힘 Drag (드래그 시작)                  O    X   자격 없음     CollapseDragSeconds 0.08
  접힘 Auto (6초 유휴)                   X    X   자격 없음     CollapseAutoSeconds 0.26 / 6.0s
  종료 1차 (무장)                        O    O   자격 있음     QuitConfirmSeconds 3.0
  종료 2차 (실행)                        O    O   자격 있음     Quit
  종료 해제 — 3초 경과                     X    X   자격 없음     DisarmQuit("3초 경과")
  종료 해제 — 커서 이동                     O    X   자격 없음     DisarmQuit("커서가 [..]로 옮겨감")
  ------------------------------------------------------------------------------------------------
  통과 5 / 10  = 50.0 %

  사유 (탈락분만):
    - 칸 호버 (이름표 노출)                커서 이동은 «명령»이 아니고, 훑기는 의도하지 않은 칸도 지난다
    - 접힘 Drag (드래그 시작)             의도는 «옮기기»였다. 닫힘은 부작용이라 예상 밖이다
    - 접힘 Auto (6초 유휴)              원인이 사용자의 «부작위»다 — 자율 발동이다
    - 종료 해제 — 3초 경과                타이머가 원인이다 — 자율
    - 종료 해제 — 커서 이동                의도는 이동이었다. 해제는 부작용

  ★ 구조적 사실 하나: 「접힘」은 한 사건이 아니라 세 사건이다.
    프로덕션이 이미 세 갈래로 갈라 놓았다 — GearMenuCollapseMode {User 0.13s / Drag 0.08s / Auto 0.26s}.
    «접힘음 하나»를 설계하면 그중 자율 1건(Auto)이 자격 없이 함께 울린다.
    ⇒ 소리를 붙인다면 트리거 키를 «접힘»이 아니라 «접힘.User»로 쪼개야 한다.
    같은 함정이 「종료 확인 해제」에도 있다(3초 경과 = 자율).

§3. 호버 소리의 구조적 결함 — 최소 간격 150 ms가 물리는 커서 속도
======================================================================================

  SILENCE_POLICY §2-2: 티어 A는 «예산»을 두지 않는 대신 최소 간격 150 ms로 연타만 자른다.
  부채꼴 이웃 버튼 사이 현 길이 = 2 x 111 x sin(15도) = 57.46 pt

    이웃 두 칸의 호버가 «둘 다» 울리려면 커서 속도가  383.1 pt/s  이하여야 한다.
    호 전체(90도, 현 156.98 pt)를 훑으며 4칸을 다 울리려면
    그 훑기가 최소 450 ms = 평균 348.8 pt/s 이하로 «느려야» 한다.

  ⇒ 그보다 빠른 보통의 훑기에서는 틱이 «어떤 것은 울리고 어떤 것은 안 울린다».
     사용자는 그것을 리듬으로 읽지 않는다 — 고장으로 읽는다.
     ★ 이건 튜닝으로 못 고친다. 최소 간격을 없애면 이론 최대 연타가 되살아나고,
       최소 간격을 두면 비결정적으로 빠진다. 두 출구가 다 막혀 있다.
       (호버는 §1에서 이미 P2 탈락이다. 이 절은 «그래도 붙이면»에 대한 두 번째 독립 근거다.)

§4. ★ 프로브 되먹임 — 부채꼴 소리가 AudioReactiveDance를 켜는가
======================================================================================

  전제(가정법): 사운드가 언젠가 돌아왔고 R4의 온디맨드 링거 3.0초가 그대로라고 하자.
  macOS 프로브는 «레벨»이 아니라 «스트림 개방»을 본다(kAudioDevicePropertyDeviceIsRunningSomewhere,
  M-B 실측: 무음 스트림도 1). 즉 문제는 크기가 아니라 «장치를 여는 시간» L이다.

    L = (마지막 클립이 끝나는 시각) + 링거 3.0s
    춤 개시 조건 : L >= T1(3.0s)
    춤 정지 시각 : max(L + T2, T1 + T3)      => 춤 길이 D = max(L, T3) = max(L, 8.0s)

  시나리오                                         마지막클립끝      개방창 L      춤개시       춤 길이
  ------------------------------------------------------------------------------------
  A 최소 — 펼침음만(0.30s)                            0.30s      3.30s        예      8.00s
  B 개폐 — 펼침 + 0.5s 뒤 접힘                         0.63s      3.63s        예      8.00s
  C 조작 — 펼침 + 2.0s 뒤 선택 + 접힘                    2.22s      5.22s        예      8.00s
  D 읽기 — 5칸 호버(4.0s) + 선택 + 접힘                  4.22s      7.22s        예      8.00s
  E 자동접힘 — 6초 유휴 뒤 접힘음                          6.26s      9.26s        예      9.26s
  ------------------------------------------------------------------------------------

  ★ 다섯 시나리오 전부에서 춤이 개시된다. 가장 짧은 A조차 L = 3.30s >= T1 3.0s
    (여유 +0.30s)이고, 그 결과 춤은 T3에 눌려 최소 8.0초 돈다.

  ⇒ **부채꼴을 한 번 여는 것만으로 캐릭터가 8.0초간 춤춘다.** 음악은 한 소절도 없었다.

  링거를 줄여 피할 수 있는가 — 없다. A안 기준 안전 링거는 < 2.70초여야 하는데,
  R4가 링거 3.0초를 고른 이유가 «연속 조작을 한 번의 개방으로 병합»이었다.
  부채꼴은 그 병합의 극단이다 — 한 번의 열기 안에 펼침·호버·선택·접힘이 전부 들어온다.
  ★ 링거의 존재 이유(병합)가 곧 T1을 넘기는 기전이다. 노브로 뺄 수 없다(R5 §2-V3와 같은 형태).

  하루 총량 (§2의 개폐 15.5회/일 x 최소 8.0초):
    하한 76 초/일 (9.5회 — 집중 세션 중 확인 6.00회는 게이트가 억제)
    상한 124 초/일 (15.5회 전부)
    = 하루의 0.088 ~ 0.144 %

  ★ 그리고 그 시간 동안 MOTION_SPEC §26-0 #8에 따라 춤이 SpectacleEventLock을 잡는다
    => 활쏘기 · 그라피티 · 투두 · 포모도로 포즈가 그동안 발동 불가.
    소리 하나가 다른 기능 4종을 조용히 죽인다(R5가 발견한 것과 같은 2차 피해).

  ── 독립 검산: 틱 시뮬레이션 (해석식과 코드를 공유하지 않는다) ──
  시나리오                                            해석식 D    sim dt=0.01 sim dt=0.50(실폴링)

§5. Windows 임계 대비 — «UI 틱» 계열도 볼륨으로 못 도망간다
======================================================================================

  Windows 프로브는 «엔드포인트(장치) 미터»를 본다 — 세션 미터가 아니므로 우리 출력이 그 합에 들어간다.
  임계 PeakThreshold = 0.0005 = -66.02 dBFS

  R6은 부채꼴용으로 기존 하한(-16 dB)보다 더 조용한 «UI 틱» 계열(-22 dB)을 가정한다.
  그래도 도망갈 수 없다:

      슬라이더      UI 틱 출력(dBFS)          임계 대비       프로브 ON
  ------------------------------------------------------------
        10            -56.33        9.69 dB            예
        20            -46.30       19.72 dB            예
        40            -36.26       29.76 dB            예
        70            -28.16       37.86 dB            예
       100            -23.00       43.02 dB            예
  ------------------------------------------------------------

  임계 아래로 내려가려면 슬라이더가 5.12 이하여야 한다. 정의역 하한은 10이다
  (R4가 «0»을 빼서 만든 값이라 더 내릴 수도 없다). ⇒ 볼륨으로 도망갈 수 없다.
  ★ 그리고 macOS는 애초에 «레벨»을 안 본다 — 볼륨 0이어도 스트림이 열리면 1이다.

§6. 「촤르륵」을 소리 없이 지탱하는 값 — 스태거 27.5 ms가 순차로 읽히는가
======================================================================================
  스태거 이력 (버튼이 3 -> 4 -> 5개로 늘 때마다 «0.30초 예산»을 지키려고 깎였다)
      스태거(s)         = ms        총 스팬(s)               출처
  ------------------------------------------------------------
      0.0700        70.0        0.1400   UX_FLOW 32-2 초안
      0.0550        55.0        0.1100   UX_FLOW 32-2 확정(3버튼)
      0.0370        37.0        0.1110   UX_FLOW 4118(4버튼)
      0.0275        27.5        0.1100   코드 36-3-3(5버튼)
  ------------------------------------------------------------
  [OK] 3버튼 시절 순차 스팬                                         =       0.1100 s  (기대 0.11 s)
  [OK] 5버튼 현행 순차 스팬                                         =       0.1100 s  (기대 0.11 s)

  ★ 총 스팬은 보존됐다(110 ms -> 110 ms, 0 % 변화).
    보존되지 않은 것은 «칸과 칸 사이의 간격»이다: 55.0 -> 37.0 -> 27.5 ms (-50.0 %).

  그리고 «촤르륵»이라고 읽히는지를 결정하는 것은 스팬이 아니라 그 간격이다.
  시각 순차 판단 역치는 문헌상 대략 20~40 ms 구간에 있고, 27.5 ms는 그 하한에 걸린다.
  ★ 이 저장소는 그것을 «실측한 적이 없다»(U-R6-2). 그리고 지금 있는 테스트는 이 위험을 구조적으로 못 본다:
    InfoGearRadialMenuTests:175는 «진행도가 서로 다른가»(수치)만 단언한다.
    수치가 다른 것과 사람 눈에 순차로 보이는 것은 다른 명제다.
    27.5 ms 차이는 «항상 수치가 다르다» — 그 테스트는 스태거가 1 ms여도 초록이다.

  겹침 비율(한 버튼의 자기 애니메이션 0.19s 대비 시작 간격):
    0.0275 / 0.19 = 14.5 %  -> 임의 시점에 동시에 움직이는 버튼 수 = 5 개
