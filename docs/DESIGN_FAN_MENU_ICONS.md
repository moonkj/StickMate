## R26-0. 결론 일곱 줄

1. **이 다섯 글리프는 이 앱에서 유일하게 「막대기 조립」으로 그려진 그림이다.**
   조각 26개 중 **꺾은선(곡선)이 0개**다. 장비 카드 42종은 전부 `UiChrome.AddPolyline`로
   베지에를 평탄화해 그린다. 같은 앱 안에서 문법이 둘로 갈려 있다.
2. **획 폭이 사다리 밖이다** — `4.0 / 2.0 / 1.8 / 1.6 / 1.4 / 1.0` **6종**이고 그중 5종이
   어떤 규칙에서도 유도되지 않는다. 장비 쪽은 `strokeMult` 연속 배수 하나로 통일돼 있다.
3. **간극 규칙을 5/5 전부 어긴다.** `design-art` R14가 「4/5 미달, ⑤만 통과」라고 적었는데
   **⑤도 미달(2.38pt = 1.19W)**이고, R14 표의 숫자는 **캡 규약을 잘못 잡아 3행이 틀렸다**(§1-2).
   진짜 최악은 R14가 재지 않은 **확성기 나팔↔목 0.43pt = 0.22W**다.
4. **조각 하나는 100% 가려져 있다** — 체크리스트의 `Strike`(취소선)가 `Line2` **위에 정확히 겹쳐**
   같은 색으로 그려진다. 화면에 존재하지 않는 `Image` 1개.
5. **②의 머리는 링인데 우리 캐릭터의 머리는 채운 원반이다.** 「캐릭터로 가는 문」의 표지가
   가리키는 그 캐릭터와 다르게 생겼다.
6. **장비 카드 문법(잉크 윤곽 + 재질 채움 + 흰 광택)은 이 크기로 이식되지 않는다.** 산술 반증은 §3.
   이식되는 것은 셋이다: **획 위계 · 꺾은선 곡선 · 덩어리(채움)**.
7. 새 사양은 게이트 **30/30 통과**(현행 18/30), 조각 26→20, 획 6종→3종, 꺾은선 0→16,

### 1-2. ★ `ART_FAN_MENU_LANGUAGE` §5 표 정정 — 캡 규약

`UiChrome.AddStroke(길이 L, 두께 t)`는 **보이는 총 길이가 L**인 캡슐이다
(`UiChrome.cs:971-995` — `sizeDelta = length + feather×2`, 스프라이트가 캡슐).
즉 둥근 캡의 **중심**이 축 위 `±(L/2 − t/2)`이고 코어의 끝점이 `±L/2`다.
R14는 캡 중심을 `±L/2`로 잡은 뒤 반지름 `t/2`를 **한 번 더** 뺐다 —
마주 보는 캡슐 쌍마다 여유를 `(t_a + t_b)/2`만큼 **작게** 본다.

정정표(`r26_correct.py`):

### 1-3. ★ 이 앱의 「골(valley)」은 관례가 아니라 유도된다 — `EdgeFeather`

> ★ **2026-09-06 정정(R27 · `design/art/r27_shrink_fg3.out.txt` §0 교정6).**
> 이 절은 원래 램프가 **코어 바깥에 통째로 얹힌다**고 적었다. 프로덕션은 그렇게 굽지 않는다.
> 아래 본문은 **정정본**이고, 옛 서술로 나온 파생값(`g − 1.0pt` · `g ≥ 2.0pt` · `−0.57px`)은 **폐기**다.

`UiChrome.EdgeFeather = 0.5pt`(`UiChrome.cs:847`)가 모든 획에 **폭 0.5pt의 알파 램프**를 붙인다.
실제 텍셀 굽기는 **`alpha = clamp01((core − d) / feather + 0.5)`**
(캡슐 `UiChrome.cs:948` · 원/링 `:892`)이고, 이 식은 **알파 0.5 등고선이 정확히 코어 가장자리**라는 뜻이다.
즉 램프는 코어 바깥에 **얹히는** 것이 아니라, 가장자리를 **가운데 두고 ±`EdgeFeather`/2 = ±0.25pt**로 걸친다.
(`core = t/2`, `feather = EdgeFeather`는 `box = t + 2·EdgeFeather` · `coreFraction = t/box`에서 유도된다 —
`:980-982` 캡슐 상자 · `:1053-1061` `AddCircle`. 두께 `t ≥ 0.43pt`에서만 성립하고, 그 아래는
`coreFraction`이 0.30에 **클램프되어** 램프가 0.5pt보다 좁아진다.)

| | 알파 1이 끝나는 곳 | 알파 0이 시작하는 곳 | 골(간극 g일 때) |
|---|---|---|---|
| 옛 서술(코어 밖 램프) | `d = t/2` | `d = t/2 + 0.5` | `g − 1.0pt` ← **폐기** |
| **실제(가장자리에 ±F/2 걸침)** | **`d = t/2 − 0.25`** | **`d = t/2 + 0.25`** | **`g − 0.5pt`** |

따라서 두 획의 **코어 간극 g** 일 때 화면에 남는 **알파 0인 골 = g − 0.5pt**다(양쪽이 0.25pt씩 먹는다).

| 획 t | 그려지는 폭 `t+0.5` | 심(알파 1) `t−0.5` | 심 비율 | 램프 비율 |
|---:|---:|---:|---:|---:|
| 4.0 | 4.5 | 3.5 | 77.8 % | 22.2 % |
| 3.0 (=g2) | 3.5 | 2.5 | 71.4 % | 28.6 % |
| 2.0 (=W=g0) | 2.5 | 1.5 | 60.0 % | **40.0 %** |
| 1.6 | 2.1 | 1.1 | 52.4 % | 47.6 % |
| **1.5 (=g1)** | 2.0 | 1.0 | **50.0 %** | **50.0 %** |
| 1.4 | 1.9 | 0.9 | 47.4 % | 52.6 % |
| 0.825 (장비 슬롯행 24pt) | 1.325 | 0.325 | 24.5 % | **75.5 %** |

⇒ **1× (Windows 100%)에서 골이 1px이라도 남으려면 `g ≥ 1.5pt`.**
`1.5W = 3.0pt` 규칙은 골 **2.5pt = 1×에서 2.5px**라 이 하한을 여유 있게 넘는다 — 그래서 3.0pt를 쓴다.
배율까지 넣은 일반형은 **`(g − 0.5pt) · k · S ≥ 1.0px`**(`k` = 배치 배율, `S` = DPI 배율)이고,
Ø36 축소 폴백(`k = 36/44 = 0.8182`)에서 3.0pt는 **2.05px**다(R27 §3, 전 쌍 통과).
현행 최악 0.43pt는 골이 **−0.07px**다. **두 획이 화면에서 한 줄로 합쳐진다** —
장비 라운드가 찾은 「뚜껑」 현상과 **같은 병, 다른 원인**(그쪽은 획 미달, 이쪽은 램프 겹침).
> 이 판정은 −0.07이라는 **얇은 부호**에 기대지 않는다. R27이 정정된 램프 모형으로 옛 확성기를
> 화소 연결성으로 다시 돌려 **병목 임계 θ\* = 1.000 ≥ θ_ink 0.348**을 냈다(양성 대조, `교정9b`) —
> 「한 줄로 합쳐진다」가 **재현**됐고, 같은 자로 새 확성기는 θ\* = 0.000이다(음성 대조).

**정정의 방향은 항목마다 다르다 — 한쪽으로 안전하지 않다.**
- **골**: 옛 서술이 0.5pt **비관적**이었다. 옛 기준으로 통과한 것은 지금도 전부 통과다(안전).
- **획**: 옛 서술이 **낙관적**이었다. 알파 1인 심은 `t`가 아니라 **`t − 0.5`**다 — 표의 마지막 줄이
  뒤집힌다. 관측: 0.825pt 획은 1×·최악 위상(획 축이 두 화소 중간)에서 최고 알파 **0.325**,
  면색 대비 **2.79:1**로 **잉크 문턱(θ_ink 0.3476 · 3.0:1) 아래**다(2×에서는 0.825 / 10.55:1 ✓).
  이 획은 부채꼴이 아니라 **장비 슬롯행 아이콘**(`AccessoryCardIcon` → `UiChrome.AddPolyline`,
  `AccessoryCardIcon.cs:385`)이라 이 문서의 범위 밖이다 — **리더 배정 대기 항목으로만 남긴다.**

### 2-1. ★ 실루엣 — 한 쌍이 사실상 같은 그림이다

|  | ① | ② | ③ | ④ | ⑤ |
|---|---:|---:|---:|---:|---:|
| ① | 1.00 | 0.18 | 0.14 | 0.10 | **0.74** |
| ⑤ | **0.74** | 0.12 | 0.14 | 0.11 | 1.00 |

`GearRadialMenuWidget.cs:2471-2473`은 *"원은 스톱워치와 공유하지만 **트인 틈 + 관통하는 세로획**이 구분한다"*고

## R26-4. ★ 카드 문법을 통째로 이식하지 않는 이유 — 산술 반증

「인계본처럼」을 **잉크 윤곽 + 재질 채움 + 흰 광택**의 **문자 그대로의 이식**으로 읽으면 이 크기에서 깨진다.

### 4-1. 하이라이트는 이 필드에 못 들어온다

윤곽이 있는 채움 한 덩어리의 최소 폭:
```
윤곽 W + 내부 ≥1.5W + 윤곽 W = 3.5W = 7.0pt
```
그 위에 **흰 광택 한 획**이 윤곽에서 1.5W 떨어져 앉으려면:
```
W + 1.5W + 0.75W + 1.5W + W = 5.75W = 11.5pt
```
필드가 Ø28이므로 **그런 물건이 2.43개 폭**밖에 안 들어간다(장비 카드 58pt는 **5.04개 폭**).
즉 **광택을 가진 조각을 하나 넣으면 글리프 전체가 그 하나로 끝난다.**

### 4-2. 그리고 광택은 애초에 「큰 면」 위에서만 성립한다

| 대비 | 값 |
|---|---:|
| 장비 카드 하이라이트(흰 42 %) ↔ 그 재질색 | **1.88 : 1** |
| 장비 카드 재질색 `#96814F` ↔ 카드 바탕 | 4.70 : 1 |
| 장비 카드 잉크 `CardIconInk` ↔ 카드 바탕 | 13.79 : 1 |
| **부채꼴 심볼 `TextPrimary` ↔ 원판 면 `CardSurface`** | **14.99 : 1** |

- 광택 1.88:1은 **넓은 면 위의 결**이라 성립한다. 1.5pt 획으로는 **보이지 않는다.**
- 카드가 **잉크 윤곽**을 쓰는 이유는 채움이 **중간 명도 재질색(4.70:1)** 이라 어두운 바탕에서 형태가 안 서기 때문이다.
  부채꼴 심볼의 잉크는 `TextPrimary`(**14.99:1**)라 **그 이유가 존재하지 않는다.** 윤곽을 이식하면 조각만 2배가 된다.

### 4-3. ⇒ 이식되는 것 셋 · 이식되지 않는 것 셋

| 인계본/카드 문법 | 이식 | 근거 |
|---|---|---|
| **획 위계(연속 배수 → 등급)** | ✅ **이식** | 지금 6종이 무근거. §5 FG-2 |
| **꺾은선 곡선(베지에 평탄화)** | ✅ **이식** | 지금 0/26. §5 FG-5 |
| **채움 = 덩어리를 만든다** | ✅ **이식**(②의 머리, ④의 닫힌 나팔) | `EQUIPMENT_SHAPE_SPEC` — 「채움은 가림용만」은 반증됐다 |
| 잉크 윤곽 | ❌ | §4-2 — 대비 이유가 없다 |
| 흰 광택(톤 3) | ❌ | §4-1 — 11.5pt 필요, 필드 Ø28 |
| 재질색·보조색 | ❌ | `ART_FAN_MENU_LANGUAGE` F-3 — 부채꼴 기호는 `TextPrimary`, 색이 바뀌는 것은 `Accent`뿐 |

  얼룩이 되지 않는 방법은 「가늘게」가 아니라 **「용접된 g0 한 획」**이다.

  안쪽 호는 나팔 입(코어 오른쪽 x = 6.0)에서 3.0pt를 띄우느라 **반경 6.6 아래로 못 내려가므로**
  (`6.6·cos38° − 2.0 = 3.20`) 바깥 호는 반경 11.6, 그 먼 점이 `5.0 + 11.6 + 1.0 = **17.6pt**`로
  필드 상한 15pt를 **2.6pt 넘는다**. 현행이 소리선 2개를 억지로 넣느라 입과 1.50pt(0.75W)로 붙어 있다.
- 검산: r_max **12.58** · 잉크 **20.5 %** · 금지대 **0** · 최소 골 3.22pt

> ### ★★ `design-art` F-L2 「확성기 → 지휘봉」에 대한 답 — **이 크기에서 반증됐다**
> 후보 **8안**을 좌표로 만들어 실크기까지 렌더했다(`r26_slot4.png` · `r26_slot4b.png`).
> - **R14가 제안한 「봉 19pt + 방사 3획」은 기하학적으로 불가능하다.** 수렴점에서 방사 3획이
>   서로 3.0pt를 지키려면 안쪽 끝이 수렴점에서 **r₀ ≥ 8.2pt**여야 하고(간격 35°),
>   그러면 바깥 끝이 봉 끝에서 **r ≈ 21pt** — 필드(15pt)를 6pt 넘는다. 2획으로 줄여도 넘는다.
> - **십자 반짝임은 금지 글리프다**(§5 ★): 대각 십자 = `✕`, 수직 십자 = `+`.
> - 남는 형태 5안(구슬 손잡이·3단 테이퍼·끝 구슬·궤적 호·과녁)을 렌더한 결과
>   **각각 핀 / 펜 / 마이크 / 스와시 / 열쇠고리로 읽혔다.** 24pt에서 「지휘봉」을 지시하는 특징
>   (코르크 그립의 테이퍼, 가늘음, 쥔 손)이 전부 3pt 미만이라 **표현 수단이 없다.**
> ⇒ **권고: F-L2를 「형태 교체」가 아니라 「조형 재작성」으로 이행한다**(위 3조각).
>   의미 축(「알린다」 vs 「시킨다」)은 **손잡이를 되살리는 것으로 완화된다** —
>   손잡이가 있는 확성기는 스피커(수동적 알림)가 아니라 **들고 외치는 도구**다.
>   그래도 교체를 원하면 **필드를 키워야 하고**(Ø44 버튼 자체를 손대야 한다) 그건 이 라운드 범위 밖이다.

### 8-1. ★ API 제약 하나 — `AddPolyline`이 `Image[]`를 안 준다

```
UiChrome.AddPolyline(Transform, string, Vector2[], int, float, Color)   →  반환형 void
```
부채꼴은 만든 `Image`들을 `ButtonView.SymbolParts`에 담아 **호버/무장 색 보간**을 걸어야 한다
(`:1717-1731`). 그래서 둘 중 하나가 필요하다:

- **(A) 권고** — `UiChrome`에 싱크 오버로드 하나:
  `AddPolyline(…, List<Image> sink)`. 기존 `void` 오버로드는 그것을 `sink: null`로 부르게 한다.
  장비 카드 경로(`AccessoryCardIcon.AddStrokes`)는 **한 줄도 안 바뀐다**.
- **(B) 새 API 0** — 부채꼴 빌더가 선분마다 `AddStroke`를 직접 부른다.
  **반드시 `AddPolyline`과 같은 식을 써라**: 길이 `|b−a| + thickness`, 중심 `(a+b)/2`, 각 `atan2`.
  (이 보정을 빼면 이음매에 `thickness/2` 틈이 생긴다 — `UiChrome.cs:1016-1019`가 그 이유를 적어 두었다.)
