### 0-3. ★ 리더 브리핑 정정 ② — "상시 시계 위젯"은 **일부 이미 출하돼 있다**

`Interaction/FocusWatchRenderer.cs`가 **세션이 도는 동안 캐릭터 발밑에 원형 타이머 링을 그린다.**

이 라운드의 질문은 *"무엇을 남길까"*가 아니라 **"이미 남아 있는 것으로 충분한가, 아니라면 무엇을 더하나"**다.

## 1. 이 라운드의 축 — 상시 표면이 어려운 진짜 이유는 이미 **측정**돼 있다

`ux-designer` §50-1-1이 나와 무관하게 같은 문제를 재서 다음 규칙을 냈다. **이 문서는 그 규칙을 따른다.**

```
임의의 바탕화면 위 글자 : 잉크+헤일로 회색 전 구간 최악 4.37 : 1  <  MinTextContrast 4.50   → 못 쓴다
임의의 바탕화면 위 도형 : 같은 4.37 : 1                     >  MinNonTextContrast 3.00  → 46% 여유로 쓴다
```

> **그래서 바탕화면 층(캐릭터 레이어)에는 도형만 산다. 숫자는 창 안에서만 산다.**

이 한 줄이 "시계 위젯" 질문의 절반을 이미 닫는다.
**상시 `mm:ss`를 바탕화면에 띄우는 안은 취향이 아니라 대비 측정으로 기각된다.**
남은 절반은 **"그러면 도형은 얼마나 비싼가"**이고, 그것을 아래에서 pt²로 잰다.

### 1-1. 비침해 비용의 기준선 — 이미 출하된 것이 얼마나 비싼가

### 2-1. 【답 ①】 시간 설정 — **프리셋 3 + `직접` 1 = 칩 4개. 세로 증가 0pt.**

#### 왜 `AddSegment`가 아닌가 (`ux-designer` §49-1이 이미 실측했다)

`SettingsControls.AddSegment`는 칩 개수가 **조립 시점에 굳는다.** 가변 개수를 감당하지 못한다.
그리고 애초에 이 팝오버는 `SettingsControls`를 쓸 수 없다 — 그쪽은 설정창 호스트(`_host?.Register`)에
클릭을 등록하는데, 팝오버의 클릭 경로는 `PopoverPanel.Wire` + `OnGlobalClick` 두 벌이다.
**컨트롤을 빌려오는 것이 아니라 기하만 빌려온다.**

#### 확정안 — 칩 4개 (세로 증가 없음)

```
시간
┌─────────┬─────────┬─────────┬─────────┐
│  15분   │  25분   │  50분   │  직접   │      4칩 × 48.5 + 3갭 × 6 = 212 = ContentWidth ✔
└─────────┴─────────┴─────────┴─────────┘
```

| 항목 | 값 | 검산 |
|---|---:|---|
| 칩 폭 | **48.5pt** | (212 − 3×6) / 4 = 194/4 = 48.5 ✔ |
| 칩 높이 | 32pt (현행 유지) | 세로 증가 **0pt** |
| 라벨 `15분` | 25.2pt | 숫자 2 × 6.6 + 한글 1 × 12 = 25.2 < 48.5 − 12(패딩) = 36.5 ✔ |
| 라벨 `직접` | 24.0pt | 한글 2 × 12 = 24.0 < 36.5 ✔ |

#### ★ 영어 예산 — **여기서 넘친다. 미리 보고한다.**

영어 1.0 포함이 확정이므로 같은 칩을 영어로 재면:

| 후보 | 글자 수 | 실측 추정 폭 | 36.5pt 안? |
|---|---:|---:|:--|
| `15 min` | 6 | ≈ 39.6pt | ✘ **넘침** |
| `15m` | 3 | ≈ 19.8pt | ✔ |
| `Custom` | 6 | ≈ 42pt | ✘ **넘침** |
| `Set` | 3 | ≈ 21pt | ✔ |

**→ 영어 라벨은 `15m / 25m / 50m / Set`으로 제한한다.**
문구 확정은 `design-narrative` · `localization` 소관 — **내가 정한 것은 "3글자 이내"라는 상한**이다.
(이 상한을 안 지키면 칩이 2행이 되고, 그러면 세로 증가 0pt가 깨진다.)

#### `직접`을 골랐을 때 — 스테퍼 1행이 나타난다 (세로 +28pt)

```
시간
┌────────┬────────┬────────┬────────┐
│  15분  │  25분  │  50분  │ ▣직접  │
└────────┴────────┴────────┴────────┘
        ┌────┬──────────┬────┐
        │ −  │   35분   │ +  │            −/+ 24×24 · 값 56×24 · 갭 8
        └────┴──────────┴────┘            총 폭 24+8+56+8+24 = 120pt (212 안, 좌우 46pt 여백)
```

| 항목 | 값 | 근거 |
|---|---:|---|
| −/+ 버튼 | **24 × 24pt** | ★ `SettingsControls.StepButton`은 20pt인데 **쓰지 않는다** — 같은 창의 닫기 칩이 WCAG 2.2 SC 2.5.8(24×24 하한) 때문에 22→24로 올라갔다(`PopoverPanel.CloseChipHeight`). 한 창 안에서 20pt 타깃을 새로 만들면 그 라운드를 되돌리는 셈이다 |
| 값 라벨 | **56 × 24pt** | `ValueLabelWidth` 44는 `120분`(31.8pt)은 담지만 `120 min`(≈46pt)을 못 담는다. 영어 예산으로 56으로 올린다 |
| 갭 | 8pt | `SettingsControls.ControlGap` 그대로 |
| 행 높이 | 24 + 여백 4 = **28pt** | Divider가 −84 → −112로 밀린다 |

**세로 검산**: 스테퍼가 뜬 상태 콘텐츠 높이 = 194 + 28 = 222 → **패널 280pt.**
`PanelSizePoints`는 이미 `_running` 여부로 갈리는 **동적 프로퍼티**라 세 번째 값을 추가하는 데 구조 변경이 없다.
280pt는 화면 안전영역(982 − 상단 인셋 33 − 여백 24 = 925)에 여유롭게 들어간다 ✔

> `PanelSizePoints`(=IdleHeight 252)로 한 번만** 놓는다. 지금도 진행 페이지(224)에서 Content가 28pt
> 넘치고 있지만 그 아래에 그리는 것이 없어 눈에 안 보일 뿐이다. **세 번째 크기를 도입하면 Content도
> 함께 다시 놓아야 한다** — 안 그러면 스테퍼가 잘리는 것이 아니라 조용히 패널 밖에 그려진다.

```

17.85  <  19.82      →  링은 **기존 히트 사각형 안에 완전히 들어간다**
```

`InfoGearIconWidget._clickTarget`(BoxCollider2D)의 반변은 `(VisualRadiusPoints + HitPaddingPoints)`로
계산된다(`:595`, `:666`). **그 식에 링이 등장하지 않으므로 콜라이더는 정의상 변하지 않는다.**

|---|---|---:|

| 시각 바운딩 증가 | (2×17.85)² − (2×14.82)² = 1274.5 − 878.6 | **395.9 pt²** = 0.0267% |
| 클릭관통 해제 증가 | — | **0 pt²** |
| 포스트잇(2.430%) 대비 | 395.9 / 36,080 | **1/91.1** |

#### 시간 적분으로도 재 둔다 (상주 앱이므로 면적만으로는 부족하다)

```

포스트잇       2.430%  × 50%(하루 12h) = 1.215   %·day     →  1,300배 차이
```

**이 위젯은 이 앱이 이미 치르고 있는 침해의 1/1300이다.** 그것이 "픽셀 하나마다 근거"에 대한 내 답이다.

#### ★ `ux-designer` §50-1-2와의 정면 대조 — 반박이 아니라 **경계 긋기**

그쪽은 *"미확인 획득 뱃지를 톱니에 붙이자"*를 **스스로 기각**했다. 근거:

> 활쏘기 쿨다운 600초 → 상한 6회/시 = 144회/일 → 뱃지는 평균 10분마다 다시 켜진다 = **하루 대부분 켜져 있다.**
> **항상 켜져 있는 뱃지는 뱃지가 아니라 HUD다.**

**그 기각에 동의한다. 그리고 이 안은 그 기각을 통과한다.** 셋이 다르다:

| | 기각된 뱃지 | 이 진행 링 |
|---|---|---|
| 켜져 있는 시간 | 하루 **대부분** | 하루 **3.47%**(세션 중에만) |
| 히트 사각형 | 39.6 → **94.1pt (+138%)** ← 그쪽 실측 | 39.64 → **39.64 (+0%)** |
| 나르는 것 | 미확인 획득(사용자가 **처리해야 할 일**) | 지금 도는 세션의 **남은 비율**(처리할 것 없음) |

**같은 자리라고 같은 물건이 아니다. 그러나 이 판단은 `ux-designer` 영역과 접한다 — 리더 조정 필요.**

#### ★ `FramePacing` 계산 — 리더가 요구한 항목

**Still 등급 = `divisor 4` → 60/4 = 15fps → 프레임 주기 66.7ms** (`FramePacingPolicy.DefaultStillDivisor = 4`).

**(1) 진행 링은 홀드가 필요 없다. 필요량의 1/562이다.**

```
25분 세션 각속도  = 360° / 1500s = 0.240 °/s
호 끝 선속도      = r × ω = 17.0 pt × (2π/1500) = 0.0712 pt/s
15fps 프레임당    = 0.0712 / 15 = 0.00475 pt/frame     ← 서브픽셀의 1/200

기준선(이 저장소가 이미 확립한 "60fps가 필요한 속도"):
  CharacterPetRenderer.CursorHoldSpeedPoints = 40 pt/s
  0.0712 / 40 = 1/562
```

**→ `HoldActiveForInteraction()`을 부르지 않는다.** 커서 친구가 홀드를 거는 이유(캐릭터가 서 있어도
화면을 가로지른다)가 여기에는 **562배 차이로 성립하지 않는다.** 홀드를 걸면 세션 25분 내내 60fps를
붙잡게 되고, 그건 24시간 상주 앱에서 가장 비싼 실수다(`FramePacing` 파일 머리가 직접 경고한 형태).

**(2) 팝오버의 `mm:ss` — 프레임레이트는 문제가 아니다. `TickSlow`가 문제다(★ 기존 결함).**

```
프레임만 보면 : 초 경계 지연 상한 = 66.7 / 1000 = 6.67%  → 인지 임계 100ms 아래. 문제없다.

진짜 양자화기는 프레임이 아니라 TickSlow(0.25초)이고, _slowTimer는 나머지를 이월하지 않고
0으로 리셋하므로 실제 주기 = ceil(0.25 / dt) × dt 다:

  Active 60fps (dt 16.667ms) : ceil(15.00) × 16.667 = 250.0ms
      1000 / 250.0   = 4.00 (정수)  →  갱신 1000 / 2000 / 3000 / 4000ms
      보이는 간격 = 정확히 1000ms 균일                                   ✔

  Still  15fps (dt 66.667ms) : ceil(3.75)  × 66.667 = 266.7ms
      1000 / 266.7 = 3.75 (비정수)  →  갱신 1066.7 / 2133.3 / 3200.0 / 4000.0ms
      보이는 간격 = 1066.7 / 1066.7 / 800.0 ms   (4초마다 반복)
      → **+6.7% / −20.0%**
```

**★ 자기 정정**: 이 문단의 초고에 *"±6.7%"*라 적고 갱신 시각을 `3066.7`로 계산했다.
**3066.7은 266.67의 배수가 아니다** — 올바른 값은 `3200.0`이고, 그러면 직전 간격이 **800ms(−20%)**가 된다.
스크립트로 다시 세어 정정한다. **결론이 바뀌므로 그대로 남긴다.**

**판정: 이건 내 설계가 만든 것이 아니라 지금 출하돼 있는 거동이다.** 진행 페이지는 이미 `TickSlow`로
`mm:ss`를 그리고 있고, 캐릭터가 오래 서 있는 세션 중반이 정확히 Still 등급이다.
4초마다 한 번 초 눈금이 0.8초 만에 넘어가는 것은 **디지털 시계에서 인지 가능한 불균일이다.**

**처방(선택 2개 — 리더 판정 대상)**:

| 안 | 내용 | 대가 |
|---|---|---|
| (가) 그대로 둔다 | 세션 중 팝오버를 열어 두는 시간이 짧다면 실害가 작다 | 눈금이 4초마다 한 번 튄다 |
| **(나) 전용 타이머** | 진행 페이지가 열려 있는 동안만 `_lastShownSeconds` 갱신을 `TickSlow`가 아니라 **매 프레임 판정**으로 옮긴다(값이 바뀐 프레임에만 문자열을 만드는 현행 가드는 그대로) | 프레임당 `int` 비교 1회. 사실상 0 |

**(나)를 권고한다.** `RefreshRunning()`은 이미 `if (seconds != _lastShownSeconds)`로 문자열 생성을
막고 있으므로, 판정만 앞으로 당기면 15fps에서도 지연 상한이 66.7ms(6.67%)로 떨어진다.
★ **`HoldActiveForInteraction()`으로 푸는 것은 반대한다** — 그건 세션 내내 60fps를 붙잡는 대가로
6.7%를 사는 일이고, 위 (1)에서 홀드를 거절한 근거와 정면으로 모순된다.

**(3) 발밑 링 — 여기에 실제 결함이 하나 있다(내 설계가 만든 것 아님, 리더 보고).**

`FocusWatchRenderer.UpdateArc()`가 **매 `LateUpdate`마다 `new Vector3[segments + 1]`을 새로 할당한다.**

```
segments = ceil(40 × ratio) → 세션 초반 41개
60fps × 41 × 12바이트 = 29.5 KB/s → 25분 세션 = 44.3 MB의 GC 쓰레기
```

24시간 상주 앱에서 이건 그냥 새는 것이다. 버퍼 재사용은 이 저장소가 이미 `PopoverPanel.CornerBuffer`와
`Core/DockGeometry`에서 명문화한 관례다. **`perf-doc` 또는 `coder` 배정 대상 — 내 영역 밖이다.**

### 2-3. 【답 ③】 캐릭터가 시계가 될 수 있는가 — **아니다. "어디쯤"만 말할 수 있다.**

리더가 이 질문을 정면으로 물었으므로 정면으로 답한다.

#### 왜 불가능한가 — 산술

시계는 **양(quantity)**을 나른다. 자세는 **순서(ordinal)**를 나른다. 자세로 25분을 1분 해상도로 읽으려면
**서로 구별되는 자세 25개**가 필요하다. 이 앱의 `StickmanStateId` 전체가 그 규모이고, 그 전부는 이미
다른 뜻을 지고 있다(걷기 / 착지 / 파쿠르 / 랙돌 / 가출 …). **자세 예산이 구조적으로 없다.**

그리고 대사로 시간을 말하는 것은 **원칙 1이 아니라 §50-1의 대비 규칙이 먼저 막는다** —
말풍선 글자는 바탕화면 위에 앉고, 그 층에서 글자는 4.37 < 4.50으로 이미 기각됐다.

#### 그러면 무엇이 가능한가 — **3구간 위상(phase)** 은 가능하고, 원칙 1을 지킨다

| 구간 | 파생 근거(전부 이미 있는 값) | 원칙 1 판정 |
|---|---|---|
| 시작 | `IsSessionActive`가 참이 된 프레임 | ✔ 이미 `FocusStart`로 출하됨 |
| 절반 | `RemainingSeconds / SessionDurationSeconds` 가 0.5를 아래로 지난 프레임 | ✔ **확정된 사실**에서 파생 |
| 막바지 | 같은 비율이 임계(예: 0.1)를 아래로 지난 프레임 | ✔ 같음 |
| 완주 / 취소 | `CompleteSession()` / `StopFocusSession()` | ✔ 이미 출하됨(`FocusComplete` / `FocusCancelled`) |

**즉 지금 2개(시작·끝)만 있는 것을 4개로 늘리는 일이지, 새 개념을 만드는 일이 아니다.**

**★ `design-motion`에 넘길 요구사항** (수치는 그쪽이 정한다 — 내가 정하는 것은 계약뿐):

1. **자세는 시간을 주장하지 않는다.** "절반 지났다"를 그리는 것이 아니라 **"자세가 바뀌었다"**만 그린다.
   숫자를 읽는 곳은 링과 팝오버다.
2. **전이는 `SpectacleEventLock`을 지나야 한다.** 다른 스펙터클이 돌고 있으면 **조용히 건너뛴다** —
   `FocusWatchDirector.TryTriggerPoseState`가 이미 그 관례다(`Idle`/`Walk`가 아니면 스킵).
   **위상 전이를 놓쳐도 타이머는 아무 영향을 받지 않아야 한다.**
3. **빈도 예산**: 세션당 최대 2회 추가(절반·막바지). 원형 B(2세션/일)에서 **하루 4회.**
   그 이상은 "먼저 나서지 않는다"를 깨는 쪽으로 기운다.
4. **`IsSuspended` 중에는 위상 전이가 없다.** 그동안 `RemainingSeconds`가 실제로 줄지 않기 때문이다
   (`FocusWatchDirector.Update`가 조기 반환한다). 여기서 자세를 바꾸면 화면이 거짓말을 한다.

**요약 판정: 캐릭터는 시계가 될 수 없다. 캐릭터는 "구간 표시기"가 될 수 있고, 그건 값어치가 있다.**

### 2-5. ★ 경제와의 맞물림 — **획득원을 하나도 늘리지 않는다**

`design/systems/ECONOMY_SPEC.md`를 읽었다(수정하지 않았다). 관련 사실:

```
집중모드: 완주 분당 1.2동전 / 중도취소 분당 1.0동전
  15분 = 18동전 / 25분 = 30동전 / 50분 = 60동전  →  세 길이 전부 정확히 72동전/시
기각안(분당 1 + 완주 보너스 5)의 기각 사유: "15분 스팸이 최적이 된다"
```

#### 발견 ① — **가변 길이는 경제를 흔들지 않는다. 이미 그렇게 설계돼 있다.**

지급이 분당 **선형**이므로 `동전/시 = 72`가 **길이와 무관하게 상수**다.
`design-systems`가 15분 스팸을 막으려고 정액 보너스를 기각한 그 결정이, **의도치 않게 임의 길이까지
안전하게 만들어 놓았다.** 리더가 걱정한 *"지급량이 흔들린다"*는 **선형성 덕분에 성립하지 않는다.**

#### 발견 ② — ★ **단 하나의 조건: 격자가 5분의 배수여야 반올림 exploit이 없다**

```
지급 = 1.2 × 분  →  정수가 되려면 분이 5의 배수여야 한다
   1분  →  1.2   → 올림 2 이면 120동전/시 (기준 72의 1.67배)  ✘ exploit
   3분  →  3.6   → 올림 4 이면  80동전/시                      ✘
   5분  →  6.0   → 정확히 정수                                 ✔
  10분  → 12.0  ✔    25분 → 30.0 ✔    50분 → 60.0 ✔    120분 → 144.0 ✔
중도취소 1.0 × 분 은 어떤 정수 분에서도 정수다 ✔
```

**→ 스테퍼의 간격을 5분으로 하면 반올림 규칙이 무엇이든 exploit이 없다.**
**이건 UI 격자 결정이 아니라 경제 결정이다. `design-systems`가 확정한다.**
내가 넘기는 것은 **"UI가 만들 수 있는 값의 집합"**뿐이고, 그 집합을 5분 배수로 한정할 수 있다는 사실이다.

#### 발견 ③ — ★ **`ECONOMY_SPEC`에 정의되지 않은 것이 하나 있다(리더 보고)**

> *"중도취소 **분당 1.0동전**"* — **어느 분인가?** 문서에 없다.

| 해석 | 120분을 골라 0초에 취소하면 | 판정 |
|---|---|---|
| (가) **경과한** 분 | 0동전 | ✔ 안전 |
| (나) **선택한** 분 | **120동전 즉시** | ✘ 무한 파밍 |

지금은 15/25/50 고정이라 (나)여도 상한이 50동전이라 눈에 안 띈다.
**가변 길이를 도입하는 순간 이 모호성이 exploit이 된다.** 명시가 필요하다 — `design-systems` 소관.

#### 발견 ④ — 소프트캡: **내 설계는 §4-3 재검토를 요구하지 않는다**

`ECONOMY_SPEC` §4-3은 일일 하드캡을 **기각**하고, 대신 획득원마다 **구조적 레이트 리미터**를 뒀다:

```
집중모드 : 실제 벽시계 시간을 소비한다 → 원리적으로 파밍 불가
활쏘기   : archeryCooldownSeconds 600초 → 6동전/시
```

그 결정은 **"획득원이 둘뿐이고 둘 다 구조적 리미터를 가진다"**는 전제 위에 서 있다.
**이 문서의 어떤 설계도 획득원을 늘리지 않는다**(§3-5 · §4-5에서 각각 왜 늘리면 안 되는지 산술로 보인다).
→ **§4-3은 그대로 유효하고, 인플레이션 재검산이 필요 없다.** 그것이 이 설계의 경제적 안전성이다.

> ★ **반대로 말하면**: 만약 리더가 [오늘 할일]이나 [행동]에 지급을 붙이기로 한다면,
> **그 순간 §4-3의 "캡 없음" 결정이 재검토 대상이 된다.** 새 획득원은 자기 몫의 **구조적 리미터**를
> 가져와야 하고, 그게 불가능하면 §4-3이 기각한 바로 그 일일 캡이 되돌아온다.

## 3. 【오늘 할일】 고도화

### 3-0. 지금 있는 것 — 실측

| | 값 | 출처 |
|---|---|---|
| 팝오버 | **300 × 336**, 6행 × 33pt, 탭 2개(할일/완료함) | `TodoBoardPopover` |
| 포스트잇 | **220 × (12 + 28n + 40)**, 기본 최대 4행 | `TodoPostItWidget` / `todoPostItMaxVisibleRows = 4` |
| 소프트캡 | 15건 | `todoActiveCountSoftCap` |
| 항목 | `{ Id, Text, Completed, CompletedAtUnscaledTime }` | `Core/TodoListModel.TodoItem` |
| 저장 | 스키마 **v10**, `TodoRecord[] todos` / `todoArchive` | `CharacterSaveStore` |

### 3-1. ★★ 가장 큰 발견 — **이 기능의 이름이 사실이 아니다**

`TodoItem`에는 **날짜가 없다.**
유일한 시간 필드 `CompletedAtUnscaledTime`은 `Time.unscaledTime`(**이번 실행의 초 카운터**)이고,
`TodoListModel.AppendRestored()`가 불러올 때 **0으로 밀어 버린다**(주석이 그 이유를 직접 적어 뒀다).

```
→ 이 앱은 "어제 적은 할일"과 "방금 적은 할일"을 구조적으로 구별할 수 없다.
→ [오늘 할일]은 실제로는 [언젠가 할일]이다.
```

리더의 질문 *"어제 못 한 것은 어떻게 되는가?"*의 답은 지금 **"아무 일도 안 일어난다.
일어날 수가 없다"**이다. 이것이 이 표면 고도화의 **선행 조건**이다.

**확정안**: `TodoItem`에 **`CreatedUnixSeconds`(long) 1개**를 추가한다.

- `CharacterStatsModel.FirstRunUnixSeconds`가 이미 **같은 형식의 절대 시각**을 저장한다 —
  새 개념 0개, 검증된 형식 그대로.
- **저장 스키마 v10 → v11.** CLAUDE.md 규약: *"`CurrentVersion`을 올리는 라운드는 `vN-1` 구버전
  파일을 읽었을 때 신규 필드가 안전한 기본값으로 채워지는지 검증하는 하위 호환 테스트 1건을 반드시
  동반한다."* → **v10 파일의 `CreatedUnixSeconds = 0`을 "날짜 미상"으로 읽고, 경과일 표시를 하지
  않는다**(0을 1970년으로 읽어 "20,000일 지났어요"가 되면 그게 최악의 결함이다).

### 3-2. ★ 비침해 결함 2건 — **고도화보다 먼저다** (P0)

#### (a) 포스트잇 펼침에 자동 접힘이 없다 → **화면의 7%가 무기한 클릭 차단**

```
_expanded = true  →  RefreshView()가 items.Count 전부를 그린다 (상한 없음)
소프트캡 15건에서 : panelHeight = 12 + 15×28 + 12 + 28 = 472
                    220 × 472 = 103,840 pt² = 화면의 6.994%
SyncClickThroughBlocker()가 _panelRoot 전체를 덮는다 → 그 6.994% 전부 클릭관통 해제
```

`_expanded`를 되돌리는 것은 **사용자가 `[+N개 더보기]`를 다시 누르는 것뿐이다.**
타이머도, 무입력 자동 접힘도, `IsSuspended` 복귀 시 리셋도 없다
(`ExitFullscreenHiding()`은 `RefreshView()`만 부르고 `_expanded`는 살아남는다).

**처방**: `PopoverPanel.DefaultIdleAutoCloseSeconds`(180초 무입력)와 **같은 관례**로 펼침을 접는다.
새 개념을 만들지 않는다. 값도 그 상수를 **참조**한다(CLAUDE.md: 프로덕션 상수 하드코딩 금지).

#### (b) 펼침에 행 수 상한이 없다

**처방**: 펼침 상한 = **10행**. 근거 산술 —

```
10행 : 220 × (12 + 280 + 40) = 220 × 332 = 73,040 pt² = 4.919%
      팝오버 300×336(4.141%)를 이미 넘는다. 상시 카드가 "사용자가 연 창"보다 커서는 안 된다.
 8행 : 220 × 276 = 60,720 pt² = 4.089%  < 4.141%  ✔
```

**→ 상한 8행.** 그 이상은 `[전체 보기]`가 팝오버를 연다(그쪽은 6행 × 페이지 넘김 레일이 이미 있다).
**포스트잇은 훑는 곳이고 팝오버는 관리하는 곳이다.** 지금은 그 경계가 없다.

### 3-3. 어제 못 한 것 — **글자로 추궁하지 않는다. 띠 색으로만 말한다.**

17절이 못박은 톤: *"할일을 강제하거나 미완료를 추궁하는 분위기(죄책감 유발)는 피한다."*

`3일 지났어요` 같은 문장은 **정확히 그 추궁이다.** 그리고 §50-1의 대비 규칙과 같은 축에서:
**도형은 추궁하지 않는다.**

포스트잇에는 이미 **왼쪽 4pt 노란 띠**(`AccentStripeWidth = 4`, `PostItStripe #f5d76e`)라는
**색 어휘가 출하돼 있다.** 새 어휘를 만들지 않고 그것을 행 단위로 내린다.

| 경과 | 띠 | 왜 |
|---|---|---|
| 오늘 | 현행 노랑 `#f5d76e` | 변화 없음 |
| 1일 이상 | 채도만 낮춘 같은 색 | **다른 색으로 바꾸지 않는다** — 다른 색은 새 뜻으로 읽히고, 그러면 "빨간 = 혼남"이 된다 |
| N일 | 더 낮은 채도 (계단 3단 상한) | 계단이 4단 이상이면 사용자가 단계를 세게 된다 = 그게 추궁이다 |

**정확한 색 값은 `design-art` 소관**(팔레트는 그쪽 정본이다). 내가 정하는 것은 **"같은 색상, 채도만,
3단 이하"**라는 계약이다. 폭은 4pt 그대로 — **면적을 늘리지 않는다.**

★ **글자 0자. 숫자 0자.** 이것이 이 앱이 [오늘 할일]을 "챙겨주는 동료"로 유지하는 방법이다.

### 3-4. 쌓이는 것 — **집중 세션과 묶는다** (두 표면이 처음 연결된다)

리더의 기준: *"한 번 쓰고 끝나는가, 쌓이는가"* / *"캐릭터와 연결돼 있는가."*
지금 [오늘 할일]은 **체크하면 사라지고 아무 데도 남지 않는다.** 완료함에 쌓이지만 거기서 끝이다.

**확정안 — 세션에 할일 하나를 묶는다:**

```
[집중 모드] 대기 페이지에서 [시작]을 누르는 순간
  · 미완료 할일이 0건  → 지금과 완전히 동일하게 시작한다 (아무것도 묻지 않는다)
  · 미완료 할일이 1건 이상 → 시작은 그대로 하고, 진행 페이지의 신설 1줄(§2-4)에
                              **가장 오래된 미완료 1건**이 뜬다
[집중 모드] 진행 페이지의 그 줄을 누르면 → 다음 미완료 할일로 넘어간다 (묶음 교체)
세션 완주 → 그 할일에 **체크를 제안**한다. 자동으로 체크하지 않는다.
```

★ **왜 자동 체크가 아닌가 (원칙 1)**: 앱은 사용자가 25분 동안 그 일을 실제로 했는지 **알 수 없다**
(원칙 3 — 남의 창 내용을 못 읽는다). 자동 체크는 앱이 모르는 것을 사실로 기록하는 일이다.
**제안은 참이고 자동 체크는 거짓일 수 있다.**

제안이 뜨는 자리 = **대기 페이지로 돌아온 `Subtitle` 아래가 아니라, 그 세션 직후 1회의 인라인 확인**.
`TodoBoardPopover`의 삭제 확인(3초) · `ActionCommandPopover`의 종료 확인(3초)과 **같은 패턴, 같은 3초**를
쓴다 — 이 앱에서 "확인"의 모양이 세 벌이 되지 않게.

**쌓이는 것 = `CharacterStatsModel`에 카운터 1개** (`TodoCompleted`). 이 모델은 이미 저장되고 있고
(`archeryShots` / `battleWins` / `companionSeconds` / `ragdollFalls`), **재화가 아니므로 인플레이션이 없다.**
표시 위치는 팝오버 푸터 1줄(현행 `완료함 {N}건 · 앱을 껐다 켜도 남아요`가 이미 그 자리다).

### 3-5. ★ 경제 — **할일 완료는 지급원이 될 수 없다. 산술로 진다.**

리더의 질문에 정면으로 답한다.

```
할일 1건의 실제 비용 = 입력칸에 1글자 + Enter + 행 클릭 ≈ 2초
                     → 1,800건/시간

지급이 1건당 1동전이라면  : 1,800 동전/시
지급이 1건당 0.1동전이라면:   180 동전/시

비교(ECONOMY_SPEC):
  집중모드 기준          72 동전/시
  ECONOMY_SPEC D상한(가장 헤비한 정당 유저) 300 동전/일
     → 1동전/건이면 그 하루치를 10분에 넘긴다.
```

**§4-3의 파밍 방어 전체가 "획득에 벽시계 시간이 든다"는 사실 위에 서 있다.**
할일 완료는 **벽시계 시간을 0초 소비한다.** 그러므로:

> **[오늘 할일] 자체는 지급원이 될 수 없다.** 지급을 붙이려면 §4-3이 기각한 일일 캡을 되살려야 하고,
> 그건 이 표면 하나를 위해 경제 전체의 설계 결정을 뒤집는 일이다.

**대신 §3-4의 묶음이 답이다.**

```
지급은 여전히 집중 세션의 벽시계 시간에서만 나온다  →  동전/시 = 72, 변화 없음
할일은 그 세션에 "이름"을 준다                       →  인플레이션 정확히 0
두 표면이 연결되고, 획득원 개수는 그대로 2개다        →  §4-3 재검토 불필요
```

**`design-systems`에 넘기는 것**: *"이 자리에서 지급이 일어날 수 있는가"* → **아니다(위 산술).**
*"묶음이 지급량에 영향을 주는가"* → **주지 않는다.** 다만 **묶인 세션에 배율을 주고 싶다면**
(예: 할일이 묶인 완주만 ×1.1) 그건 순수한 수치 결정이고 **그쪽 소관**이다. 나는 값을 제안하지 않는다.

## 4. 【행동】 고도화 — **칭찬받은 것을 지키면서 깊게**

### 4-0. 지키는 것 — 먼저 못박는다

민지(사전지식 0) 평가에서 살아남은 두 가지는 **건드리지 않는다**:

1. **불가 타일에 이유가 문장으로 붙는다**(`낙서할 빈 자리가 없어요`).
   구조적 근거: `GetAvailability()` **하나가** 회색·이유·실행을 전부 결정한다(36-7 "진실은 한 벌").
2. **푸터 `내가 누를 때만 실행돼요. 창을 닫아도 하던 건 계속해요.`**

이 문서의 어떤 제안도 위 두 구조를 경유하지 않고 화면에 문장을 만들지 않는다.

### 4-1. 알려진 결함 ① — 헤더 캡션이 목록과 어긋난다

```
현행: readyCount > 0  →  "지금 시킬 수 있어요"
      5개 중 2개가 "…없어요"인데도 같은 문장이 뜬다.
```

**확정안 — 이미 계산하고 있는 값을 그대로 쓴다.** `RefreshContent()`가 `readyCount`를 **이미 세고 있다.**

| 상태 | 캡션 | 파생 근거 |
|---|---|---|
| 가출 중 | `지금 가출 중이에요` | 현행 유지 |
| `readyCount == 0` | `지금은 다른 일 하는 중이에요` | 현행 유지 |
| `readyCount == CommandCount` | `다 시킬 수 있어요` | 실제 값 |
| 그 밖 | **`{CommandCount}개 중 {readyCount}개 지금 가능`** | 실제 값 |

**폭 검산**: 캡션 상자 = `ContentWidth − RecallChipWidth − Space2` = 448 − 88 − 8 = **352pt**.
`5개 중 3개 지금 가능` = 한글 7 × 10 + 숫자 2 × 5.5 + 공백 4 × 3 = **93pt** (FontCaption 10). 여유 **259pt** ✔
영어 `3 of 5 available` ≈ 17자 × 5.5 = **93.5pt** ✔

★ **원칙 1**: 이 문장은 방금 센 개수 그 자체다. **목록과 어긋나는 것이 구조적으로 불가능하다** —
같은 루프의 같은 변수이기 때문이다. 이것이 "행동-텍스트 싱크"의 가장 강한 형태다.

### 4-2. 알려진 결함 ② — 한 창에 `[✕]` 두 개

**`ux-designer` §48-4-2 / §48-4-3이 이미 처방을 냈다. 중복하지 않는다:**
`✕ 앱 종료` → `앱 종료` (글리프 제거) / 테두리를 `NonTextMuted`(#6C7480, 3.81:1)로.
**두 처방 다 지지한다.**

내가 답할 것은 리더가 준 질문 하나 — **"종료가 이 창에 있는 게 맞는가?"**

> **정본으로서는 맞지 않다. 그러나 물리적 위치는 유지해야 한다.**

| | |
|---|---|
| **왜 맞지 않나** | 이 창은 부채꼴 ④ **[행동]** = *놀이*에서 열린다. 종료는 *설정*의 일이다. 그리고 §48-4-4가 실측했듯 **설정창에 이미 같은 2단 확인 종료가 구현돼 있다**(`SettingsWindow.cs:1180`) |
| **왜 옮기면 안 되나** | 옮기면 마우스 종료가 3클릭 → **4클릭**이 되고, 그 4번째가 **`[✕]`로만 닫히는 창 두 겹 뒤**에 놓인다(2026-09-02부터 바깥 클릭이 창을 닫지 않는다). 탈출구는 짧아야 탈출구다 |

**→ §48-4-4의 (나)안을 지지한다**: **정본은 설정창.** 행동창 푸터는 **유지**하되 문서·로그가 설정창을
먼저 안내한다. **배치 변경 0, 탈출구 손실 0, 정보 구조는 정정된다.**

#### ★ 부수 발견 — 코드 주석의 이격 주장이 **2pt 틀렸다**

```
ActionCommandPopover.BuildFooter() 주석:
  "그리드에서 44pt 이상 떨어진 푸터 오른쪽 끝에 둔다(오조준 방지)."

실측:
  그룹2 카드 y      = Group1Y(−34) − Group1Height(198) − 12 = −244
  Group2Height      = 10×2 + 18 + 4 + 52×2 + 4 + 16       =  166
  마지막 타일(창 부수기) 바닥 = −244 − (10+18+4+52) − 52   = −380
  FooterY(종료 칩 상단)                                    = −422

  가장 가까운 **클릭 가능한** 것과의 이격 = 422 − 380 = 42pt   ← 44가 아니다
```

**42 < 44.** 결론(오조준이 실제로 잘 나지 않는다)은 바뀌지 않지만,
**"44pt 이상"이라는 문장은 거짓이다.** 값이 아니라 **문장을 고쳐야 한다** —
§48-4-2가 경고한 것과 같은 함정이다(*"값만 바꾸고 문장을 두면 다음 사람이 그 문장으로 판단한다"*).

### 4-3. 고도화 — **"열 번째 볼 때도 볼 만한가"에 대한 답은 재화가 아니라 기록이다**

`CharacterStatsModel`을 실측했다. 지금 세는 것:

```
BattleWins / ArcheryShots / ArcheryBullseyes / TotalCompanionSeconds / RagdollFalls / FirstRunUnixSeconds
```

**세지 않는 것**: 말 걸기 · 그라피티 · 창 도둑 · 창 부수기 · **집중 세션** · **할일 완료**.
즉 **[행동] 5개 중 4개, 그리고 이 문서가 다루는 나머지 두 표면 전부가 아무것도 남기지 않는다.**

#### 확정안 — 타일 오른쪽에 **개인 기록 칩** 1개

**빈 자리가 실제로 있는지 먼저 쟀다:**

```
타일 폭 RowWidth        = 428
설명 상자               = x 48 … 420  (폭 372, FontCaption 10)
가장 긴 설명 "빈 자리에 낙서했다 지웁니다" = 13글자 ≈ 130pt
가장 긴 불가 사유 "낙서할 빈 자리가 없어요"  = 12글자 ≈ 120pt

→ 설명 상자의 **242pt가 늘 비어 있다.**
```

**기록 칩 = 폭 80pt, 오른쪽 정렬(x 340…420).** 설명과의 간극 = 340 − 130 − 48 = **162pt** ✔

| 타일 | 기록 칩 | 왜 이 지표인가 |
|---|---|---|
| 말 걸기 | `{N}번` | 유일하게 상태를 바꾸지 않는 명령이라 화면 변화가 없다(코드 주석이 직접 지적). **숫자가 유일한 흔적이다** |
| 활쏘기 | **`최장 {N}H`** | ★ `design-systems` 7-2 C안 그대로. 명중률은 처방 전이면 33.3%, 처방 후에도 66.7%로 **포화**한다. 최장 사거리는 **포화하지 않는 기록**이다 |
| 그라피티 | `{N}번` | |
| 창 도둑 | `{N}번` | |
| 창 부수기 | `{N}번` | |

★ **왜 활쏘기만 다른가 — `design-systems`의 실측을 그대로 받는다:**

> `ArcheryBullseyes / ArcheryShots`는 **분자 = 사이클 수, 분모 = 사이클 수 × 3.**
> `51/153`은 통계가 아니라 **사이클 카운터의 다른 표기**이고 값이 **영원히 33.33%다.**

그쪽 처방 A(정의 교정) + B(앞 2발 독립 베르누이 `p_miss = 0.50`)가 그 숫자를 살린다.
**나는 그 처방을 반복하지 않는다** — 다만 그 결과가 **행동창에서 보이게** 자리를 만든다.
그리고 명중률은 처방 후에도 **66.7%로 수렴**하므로, *"열 번째에도 볼 만한"* 지표는
그쪽이 C안으로 권고한 **최장 사거리**다(현행 밴드는 6.60H에서 포화하지만 처방 후 13.40H까지 열린다).

#### 세로 예산 — **증가 0pt**

기록 칩은 **기존 설명 상자 안의 빈 공간**에 오른쪽 정렬로 들어간다.
`RowHeight` 52 · `Group1Height` 198 · `Group2Height` 166 · `Height` 508 **전부 그대로.** ✔

#### 빈 상태 — 0회일 때

**칩을 통째로 숨긴다.** `0번`은 정보를 0 추가하면서 *"이 앱은 미완성이구나"*를 말한다
(17절 "빈 상태를 굳이 보여주지 않는다" · 포스트잇 0건 숨김 · `[돌아와!]` 칩과 같은 판단).

### 4-4. 고도화 — **명령 5개를 늘리지 않는다**

★ 리더 지시대로 **격파 놀이(2026-09-02 삭제) · 미니 보스 레이드(2026-08-31 제외)는 되살리지 않는다.**
그리고 **새 명령도 만들지 않는다.** 근거는 세로 예산이다:

```
현행 Height 508 = 콘텐츠 450 = 푸터 바닥 −450  (정확히 맞아 있다)
타일 1개 추가   = RowHeight 52 → Height 560
행동창 면적     = 480 × 560 = 268,800 pt² = 화면의 18.10%
```

**팝오버 하나가 화면의 18%를 덮는 것은 "2초 심부름"의 정의를 넘는다**
(`PopoverPanel` 클래스 문서: *"2초 심부름에 화면 1/6을 덮는 것이 곧 이 앱이 스스로 금지한 업무 방해"*).
**깊이는 개수가 아니라 각 타일이 남기는 것으로 만든다.**

### 4-5. ★ 경제 — **[행동]도 지급원으로 확장하지 않는다**

```
연출 1회 소요(ECONOMY_SPEC 실측) = 활쏘기 의식 구간 6.14~8.03초
→ 쿨다운이 없으면 상한 586회/시  (그래서 §4-2가 600초 쿨다운을 필수로 못박았다)

나머지 4개도 같은 구조다: ForceTriggerNow는 확률/쿨다운을 건너뛰고,
유일한 구조적 제약은 SpectacleEventLock + 연출 지속시간뿐이다.
```

**지급을 붙이려면 4개 각각에 쿨다운이 필요하고, 그러면 대부분의 클릭이
"보고 싶어서 눌렀는데 아무것도 안 준다"가 된다.** 그건 지금보다 나쁘다 —
지금은 **아무것도 약속하지 않으므로 실망시킬 것도 없다.**

**→ [행동]의 "쌓이는 것"은 재화가 아니라 §4-3의 기록이다.**
활쏘기 지급(1동전 / 600초 쿨다운)은 **이미 `ECONOMY_SPEC`에 있는 유일한 지급이고, 그대로 둔다.**

## 5. 세 표면에 공통으로 걸리는 것

### 5-1. 시끄러워지지 않기 — 리더가 지목한 이 라운드의 난이도

> *"사용자가 프로젝트 내내 원한 것은 깔끔한 졸라맨이 돌아다니는 것이다.
> 깊이를 늘리되 시끄러워지지 마라."*

**이 문서가 화면에 더한 총량:**

| 무엇 | 새 면적 | 새 클릭 차단 | 새 글자 |
|---|---:|---:|---:|
| 톱니 진행 링 | **395.9 pt²** (세션 중에만) | **0** | **0자** |
| 집중 팝오버 4번째 칩 | 0 (세로 증가 0) | 0 | 2자 |
| 집중 스테퍼 행 | +28pt 세로 (**`직접` 선택 시에만**) | 0 | — |
| 집중 진행 페이지 1줄 | +24pt 세로 (**묶인 할일이 있을 때만**) | 0 | ≤17자 |
| 할일 띠 색 계단 | **0** (기존 4pt 띠의 색만) | 0 | **0자** |
| 행동 기록 칩 5개 | **0** (기존 빈 공간) | 0 | ≤4자 × 5 |

**상시 화면 증가의 총합 = 0 pt².**
세션이 도는 동안에만 **395.9 pt² = 0.0267%**가 는다. 그리고 **클릭관통 해제는 한 픽셀도 늘지 않는다.**

**대신 이 문서는 이미 있는 침해 2건을 줄인다**(§3-2):
펼친 포스트잇 **6.994% → 4.089%**(상한 8행) + 무기한 → 180초 무입력 자동 접힘.

```
순 비침해 수지 = −2.905%(상시, 펼침 상태) + 0.0267%(세션 중에만)  →  크게 음수
```

### 5-2. 자율 발동 — **새로 만든 것 0건**

| 새 요소 | 발동 조건 |
|---|---|
| 톱니 진행 링 | 사용자가 시작한 세션이 도는 동안에만 |
| 스테퍼 행 | 사용자가 `직접`을 누른 뒤에만 |
| 진행 페이지 할일 줄 | 사용자가 적어 둔 할일이 있을 때만 |
| 체크 제안 | 사용자가 시작한 세션이 완주됐을 때만 |
| 위상 자세 2개 | 사용자가 시작한 세션 안에서만 |
| 기록 칩 | 사용자가 그 명령을 1번 이상 눌렀을 때만 |

**전부 사용자가 시작한 것의 결과다. 확률이 붙은 것은 하나도 없다.**

### 5-3. 원칙 1 자체 감사 — 이 문서가 화면에 놓는 문장 전수

| 문장 | 파생 근거 | 거짓이 될 수 있는가 |
|---|---|---|
| `{5}개 중 {3}개 지금 가능` | 같은 루프의 `readyCount` | **불가능**(같은 변수) |
| `▸ {할일 텍스트}` | `TodoItem.Text` 원문 그대로 | 불가능(옮겨 적기만) |
| `{N}번` / `최장 {N}H` | `CharacterStatsModel` 누적값 | 불가능(사실 보고) |
| `{35}분` (스테퍼 값) | `_selectedMinutes` | 불가능(입력값 그대로) |

★ **일부러 쓰지 않은 문장 3개** — 각각 거짓이 될 수 있어서다:

- ~~`이 할일을 하는 중이에요`~~ — 앱은 사용자가 그걸 하는지 **모른다**(원칙 3).
- ~~`3일 지났어요`~~ — 참이지만 **추궁이다**(17절 톤). 띠 색이 같은 사실을 추궁 없이 나른다.
- ~~`17분 남았어요`(바탕화면 층)~~ — 참이지만 **글자가 그 층에서 4.37 < 4.50으로 못 읽힌다**(§50-1).

## 6. 우선순위 — 리더가 준 순서대로, 어디까지 했는지 명시

| # | 항목 | 상태 |
|---|---|---|
| **1** | 집중 모드 — 시간 설정 / 시계 위젯 / 비침해 / FramePacing / 캐릭터 시계 판정 / 경제 | **완료**(§2) |
| **2** | 오늘 할일 — 날짜 부재 발견 / 비침해 결함 2건 / 어제 처리 / 세션 묶음 / 경제 | **완료**(§3) |
| **3** | 행동 — 캡션 정정 / ✕ 두 개 판정 / 기록 칩 / 경제 | **완료**(§4) |

**다 했다. 다만 아래는 하지 않았고, 하지 않았다고 적는다.**

- **실기 빌드 캡처 없음.** 리더 승인 없이 앱을 띄우지 않았다(정의서 규칙). 위 pt는 전부 **소스 실측 + 산술**이다.
  **최종 판정은 빌드 캡처로만** — 특히 톱니 진행 링이 톱니 자체와 시각적으로 붙어 보이는지는
  **화면에서만 알 수 있다**(r 17.0 vs 톱니 팁 13.8 → 간극 3.2pt).
- **글자 폭은 추정이다.** 이 저장소에 폰트 메트릭 조회 경로가 없어 한글 1.0em / 숫자 0.55em으로 잡았다.
  §48-8 #5가 같은 가정을 명시적으로 미확인 처리했다. **여유가 260pt 이상인 항목은 가정이 2배 틀려도
  안전하고, 칩 라벨(여유 12pt)만 실측이 필요하다.**
- **색 값은 정하지 않았다** — `design-art` 소관(띠 채도 3단).
- **수치는 정하지 않았다** — `design-systems` 소관(세션 범위·간격·묶음 배율·취소 지급 정의).

## 9. 미확인 — 추측으로 메우지 않은 것

1. **글자 실측 폭.** 폰트 메트릭 조회 경로가 저장소에 없다. 한글 1.0em / 숫자 0.55em 가정.
   **칩 라벨(여유 12pt)만 실기 확인이 필요하다.** 나머지는 여유가 160pt 이상이다.
2. **톱니 진행 링이 톱니 이빨과 시각적으로 분리돼 보이는가.** r 17.0 vs 팁 13.8 = 간극 3.2pt.
   **산술로는 겹치지 않지만 "붙어 보이는가"는 빌드 캡처로만 판정 가능하다.**
3. **`직접` 스테퍼의 실제 사용률.** 텔레메트리가 없다. 프리셋 3개를 유지한 것은
   *"대부분은 25분을 쓸 것"*이라는 가정이고, **이 문서에서 가장 크게 틀릴 수 있는 단일 가정이다.**

## R2-4. ★ `FramePacing` 재검산 — R1의 처방은 옳았고, **더 좋아 보이는 대안을 반증했다**

Still 등급 = `divisor 4` → 15fps → dt 66.667ms (`FramePacingPolicy.DefaultStillDivisor`).

### R2-4-1. 세 갈래를 시뮬레이션으로 재고, **지터를 넣어 다시 쟀다**

`_slowTimer`는 나머지를 이월하지 않고 0으로 리셋한다 → 실제 주기 = `ceil(period/dt) × dt`.

| 안 | dt 지터 0% | 지터 ±15% | 지터 ±35% |
|---|---|---|---|
| **reset(현행 0.25s)** | 지연 ≤266.7ms · 간격 **800~1066.7** | ≤320.9 · 770~1190 | ≤321.6 · 772~1228 |
| carry(나머지 이월) | 지연 ≤266.7 · 간격 **733~1266.7** | ≤74.9 · 761~1066 | ≤86.6 · 709~1083 |
| **frame(매 프레임 판정)** | 지연 **≤66.7** · 간격 **933~1067** | ≤74.7 · 935~1066 | ≤85.8 · 924~1075 |

★ **자기 반증 1건 — 정직하게 적는다.** 나는 처음에 `carry`가 더 낫다고 판단했다.
등간격 모델에서 `carry`가 **정확히 1000.0ms**를 내는 출력을 봤기 때문이다.
**그런데 같은 `carry`를 두 번째 시뮬레이터로 재니 최대 간격이 1266.7ms로 나왔다.**
차이는 코드 한 곳뿐이었다 — 비교식이 `acc >= period - 1e-12`인가 `acc >= period`인가.

> **`carry`의 「완벽함」은 부동소수 1e-12에 얹혀 있었다.**
> 이건 `TEAM.md`가 열 번째 형태로 못박은 그 병이다 — *생성기와 검사기가 같은 함정에 같이 빠진다.*
> 두 시뮬레이터가 **갈라졌기 때문에** 잡았다. 하나만 돌렸으면 `carry`를 권고했을 것이다.

### R2-4-2. 확정 처방 — **(나) 매 프레임 판정**. R1과 같고, 근거가 더 세다

`frame`만이 **보장이 dt에 의존하지 않는다**: 지연 상한이 정확히 1프레임이고, 지터 ±35%에서도
간격이 924~1075ms(±7.5%) 안에 머문다. `reset`(현행)은 지터 0%에서도 **간격이 800ms(−20%)까지 내려간다**
— 이건 지터가 아니라 **구조적 톱니**다.

```
RefreshRunning():389  이미  if (seconds != _lastShownSeconds) 로 문자열 생성을 막고 있다
→ 판정만 TickSlow 밖으로 당기면 된다. 프레임당 int 비교 1회. 할당 0.
```

★ **`HoldActiveForInteraction()`으로 푸는 것은 여전히 반대한다.** 세션 25분 내내 60fps를 붙잡는 대가다.

### R2-4-3. ★ 대조군이 저장소 안에 있다 — 부채꼴은 **두 등급 모두에서 정확하다**

```
GearRadialMenuWidget:1168   _clockTimer >= 1f
  60fps: ceil(1.0/0.016667) × 16.667 = 1000.00ms      간격 = 1000.0 균일
  15fps: ceil(1.0/0.066667) × 66.667 = 1000.00ms      간격 = 1000.0 균일
```

**1000ms가 16.667과 66.667의 공배수라 두 등급 다 정확히 떨어진다.**
같은 앱 안에서 **1초 주기는 안전하고 0.25초 주기는 안전하지 않다.**
→ 이 대비가 처방의 양성 대조다. *"프레임레이트 탓"이 아니라 "주기 선택 탓"이다.*

## R2-5. 【답】 중도 취소 — **지금 UI로는 예측 불가능하다. [그만두기]가 말하게 한다**

### R2-5-1. 문제를 산술로 세운다

`design-systems` DS-5/DS-6 확정식:

```
취소 지급 = floor( (SessionDurationSeconds − RemainingSeconds) / 60 ) × 1.0
```

**사용자가 화면에서 보는 것은 `RemainingSeconds`뿐이다**(`mm:ss` 남음).
지급을 알려면 **`선택 − 남음`을 암산하고 다시 floor**해야 한다.

| 화면에 보이는 것 | 사용자가 해야 하는 계산 | 지급 |
|---|---|---:|
| 25분 세션 · `07:20` 남음 | 25:00 − 07:20 = 17:40 → floor(17.67) | **17동전** |
| 50분 세션 · `31:05` 남음 | 50:00 − 31:05 = 18:55 → floor(18.92) | **18동전** |

**아무도 이 계산을 하지 않는다.** 그리고 계산하지 않으면 [그만두기]는 **결과를 모르는 버튼**이다.

### R2-5-2. 확정안 — 버튼 라벨이 지급식과 **같은 함수**를 부른다

| 조건 | 라벨 | 왜 |
|---|---|---|
| `floor(경과분) == 0` | `그만두기` | `· 0동전`은 정보를 0 추가하고 **벌처럼 읽힌다**(18절 "패널티 없는 톤") |
| `floor(경과분) ≥ 1` | `그만두기 · 지금까지 {N}동전` | 누르기 전에 결과를 안다 |

**폭 검산** (FontBody 12 / 버튼 폭 212):
`그만두기 · 지금까지 17동전` = 한글 10×12 + 공백 3×3 + `·` 6 + 숫자 2×6.6 = **148.2** < 212 ✔ 여유 63.8
영어 `Stop · 17 coins so far` ≈ 21자 × 6.0 = **126** ✔

**갱신 비용**: 이 문자열은 **분이 바뀔 때만** 바뀐다 = 세션당 최대 60회.
`_lastShownSeconds` 가드 옆에 `seconds/60` 비교 1회를 더하면 끝이다. **할당 0.**

### R2-5-3. ★ 원칙 1 계약 두 줄 — 이게 이 절의 핵심이다

> **(1) 라벨의 `{N}`과 실제 지급은 「같은 함수 하나」에서 나와야 한다.**
> 식을 두 번 쓰면 라벨이 약속한 것과 지갑에 들어온 것이 갈리고, **그 갈라짐을 아무도 못 본다**
> (`TEAM.md` 거짓통과 공통형: 실패한 측정과 성공한 측정이 똑같이 생겼다).

> **(2) 경과는 벽시계가 아니라 「감시된 시간」이다. 그리고 그 성질을 UI가 깨면 안 된다.**
> `Update()`가 `if (_player.IsSuspended) return;`이라 전체화면 게임 중에는 타이머가 **아예 안 돈다.**
> → 게임을 10분 켰다 오면 `{N}`이 **그대로 멈춰 있다.** 이건 버그가 아니라 **파밍 차단의 본체**다.
> 그래서 라벨은 `지금까지`라고 쓰고 **`{경과}분 지났어요`라고 쓰지 않는다** —
> 후자는 벽시계에 대한 주장이 되어 **거짓이 될 수 있다.**

★ 같은 이유로 **진행 페이지의 `mm:ss`를 "언제 끝나는지"로 읽히게 하는 문구를 만들지 않는다.**
현행 `남음`은 안전하다(감시된 시간의 잔량이라는 뜻으로 읽어도 참이다).
`{시각}에 끝나요` 같은 절대 시각 표시는 **금지**한다 — 서스펜드 한 번에 거짓이 된다.

## R2-7. 【오늘 할일】 — `registeredAtUnix` 판정과 **지급이 보이지 않는 문제**

### R2-7-1. ★ 판정: **내 설계는 그 필드를 요구한다. 그리고 게이트 ②보다 강하게 요구한다**

리더 질문: *"네 설계가 그 필드를 요구하는지 판정하고, 요구하면 그렇게 적어라."* → **요구한다.**

소비자가 둘인데 **필드에 요구하는 것이 다르다**:

| 소비자 | 묻는 것 | `registeredAtUnix == 0`(v9 파일)이면 |
|---|---|---|
| 게이트 ②(`design-systems`) | **"10분이 지났는가"** (불리언) | `예` — 그리고 **사실이다**. 문제 없음 |
| **R1 §3-3 띠 채도 3단**(내 설계) | **"며칠 지났는가"** (수량) | **20,000일** — 모든 옛 할일이 최저 채도로 흐려진다 |

> ★ **그래서 `design-systems` DS-7(*"등록 시각 필드는 그 자체로 CurrentVersion을 요구하지 않는다"*)는
> 게이트 ②에 대해서는 참이고, 내 띠 설계에 대해서는 참이 아니다.**
> 같은 필드 · 다른 소비자 · 다른 판정이다. 이건 **인계 계약이 잡아낸 종류의 갈라짐**이다.

**해결은 버전이 아니라 필드 계약이다 — v10 창의 「테스트 추가 0건」을 지킨다:**

> **UW-1 (필드 계약)**: `registeredAtUnix == 0` 은 **"등록 시각 미상"**이고,
> **띠 채도 계단을 적용하지 않는다**(오늘 색 그대로). 게이트 ②는 `0`을 **통과**로 읽는다(현행 DS-7 그대로).

**비용 재산정**: `design-systems`는 *"v10이 의무로 지는 v9 테스트에 **단언 1줄**"*이라 적었다.
내 소비자가 붙으면 **단언 2줄**이다 — (a) v9 파일 → `0`, (b) `0` → **채도 미적용**.
★ (b)가 빠지면 **v9 사용자의 모든 할일이 업데이트 직후 흐려지고, 테스트는 초록이다.**
그 실패는 조용하다 — `TEAM.md`가 경고한 **부재 단언이 썩는 형태**와 같은 자리다.

### R2-7-2. ★★ 새 충돌 — **지급이 일어나는 순간에 그 표면이 화면에서 사라진다**

`design-systems` 0-2-6 확정: **그날 등록한 할일을 전부 완료 → 하루 1회 정액 15동전.**
"전부 완료" = **미완료 0건**. 그런데:


| 안 | 내용 | 판정 |

**(나) 확정 — 기존 푸터 1줄을 바꿔 쓴다. 새 픽셀 0.**

### R2-7-3. ★ 세 번째 줄이 이 라운드에서 가장 중요하다 — **게이트 ②는 조용한 미지급을 만든다**

한쪽만 풀어도 계속 조용하면 그게 다음 신고가 된다.

### R2-9-5. ★ 세 번째 답 — **볼륨 0은 두 번째 off 스위치다. 그래서 사유가 없다**

`design-sound` §2-2는 **볼륨 0~100**을 확정했다. **0이 도달 가능하다.**

```
마스터 = 켜짐,  볼륨 = 0   →   사유 함수는 "지금 소리: 켜짐"을 반환한다
                            →   그런데 아무 소리도 안 난다
```

**UW-4를 그대로 위반하는 상태가 수치 설계에서 들어온다.** 두 갈래:

| 안 | 내용 | 대가 |
|---|---|---|
| **(가) 슬라이더 하한을 0이 아니게** | 무음을 **마스터 스위치 하나만** 소유한다 | `design-sound`의 `0~100`을 바꿔야 한다(그쪽 수치) |
| (나) 사유에 `볼륨이 0이에요`를 추가 | 스키마 무변경 | 같은 뜻의 off 컨트롤이 **둘**로 남는다 |

**(가)를 권고한다.** 근거는 취향이 아니라 **UI 원칙 하나**다 — *같은 뜻의 컨트롤이 둘이면
사용자는 둘 중 어느 것이 진짜인지 매번 확인해야 한다.* 마스터 스위치가 이미 「끔」을 소유한다.
**단, 값은 `design-sound` 소관이다. 나는 (가)를 요구하지 않고 충돌을 보고한다.**

### R2-9-6. ★★ 네 번째 답 — 세로 예산. **넘친다. 억지로 넣지 않고 보고한다**

```
페이지 시작 y = −ContentPadTop(16),  AddEyebrow가 20 소비  →  y = −36
카드 높이 = CardTitleHeight(26) + Σ행높이 + CardBottomPad(4)
다음 카드 topY = topY − 높이 − CardGap(14)
뷰포트 = ContentHeight = 426
```

| 카드 | 행 | Σ행 | 카드 높이 | topY | bottom |
|---|---|---:|---:|---:|---:|
| [접근성 · 성능] | 윤곽선 강조 / 애니메이션 줄이기 / 저전력 렌더링 (60×3) | 180 | **210** | −36 | −246 |
| **[소리]** | 60 + 44 + 60 + 60 + 60 | 284 | **314** | −260 | −574 |

```
_pageHeights[i] = −y + ContentPadTop  이고, y 는 마지막 Finish() 의 반환값이다
Finish(topY) = topY − height − CardGap   ← ★ 마지막 카드 뒤의 갭 14pt 도 포함된다
  y = −36 − 210 − 14 = −260  →  −260 − 314 − 14 = −588
페이지 높이 = 588 + 16 = 604
뷰포트      = 426
넘침        = 604 − 426 = 178 pt        ← 뷰포트의 41.8%
```

> ★ **자기 정정**: 이 표의 초고에 페이지 높이를 **590**(카드 bottom −574 기준)이라 적고 넘침을 164로
> 계산했다. **틀렸다.** `_pageHeights`는 카드 bottom이 아니라 **마지막 `Finish()`의 반환값**에서 오고,
> 그 값은 **마지막 카드 뒤의 `CardGap` 14pt를 이미 뺀 자리**다. 스크립트로 다시 세어 **604 / 178**로
> 정정한다. **아래 절감표의 숫자도 전부 다시 계산했다.** 결론(넘친다 · 사유 행은 접힘선 위)은 안 바뀐다.

**넘치는 것 자체는 이 창의 기존 거동이다**(`SettingsWindow.cs:62` 주석 실측: *"[일반] 탭은 앞으로도
항상 넘친다"* — 112pt 초과). `_pageScroll` / `PageStep`(=426−44=382)이 스크롤을 이미 지원한다.

★ **그러나 넘침을 그냥 넘기면 안 되는 이유가 이 탭에만 하나 있다:**

> **사유 한 줄은 「소리가 안 나요」 신고를 막으려고 존재한다.
> 스크롤해야 보이는 사유는 그 신고를 못 막는다.**

**그래서 내가 지켜야 하는 것은 「탭 전체가 들어가는가」가 아니라 「사유 행이 접힘선 위인가」다.**

```
[소리] 카드 topY  = −260
카드 제목 26pt    → 첫 행(=소리 · 사유 캡션) = −286 … −346
뷰포트 하단       = −426
−346 > −426  →  ★ 사유 행 전체가 접힘선 위에 있다. 여유 80pt   ✔
2행 볼륨 −346…−390 ✔  |  3행 야간 −390…−450  ✘ 잘린다(스크롤 필요)
```

**판정: 카드 순서를 바꾸지 않아도 요구는 충족된다.** 3~5행은 스크롤 아래여도 되고
(설정을 바꾸러 온 사람은 스크롤한다), **사유는 스크롤 없이 보인다.**

★ **그래도 164pt 초과는 보고 대상이다.** 줄일 수 있는 곳 3군데를 **값과 함께** 적어 둔다 —
**어느 것도 내가 결정하지 않는다**(행 구성은 `design-sound`, 큰 창은 `ux-designer`):

| 줄이는 법 | 절감 | 누적 페이지 | 누적 넘침 | 대가 |
|---|---:|---:|---:|---|
| (기준) 5행 그대로 | — | 604 | **178** | — |
| [미리듣기]를 **볼륨 행 오른쪽 칩**으로 흡수 | −60 | 544 | 118 | 볼륨 행 우측 점유 = 44+8+20+8+96+8+20 = **204pt**, 카드 안쪽 628 → 칩 64pt를 넣어도 **여유 360pt** ✔ |
| ＋ 사운드 테마 행을 **팩 보유 시에만** 표시 | −60 | 484 | 58 | 대부분의 사용자에게 기본으로 안 보인다(빈 상태 예외 선례와 일치) |
| ＋ 야간 캡션을 **1행 사유 줄에 흡수** | −16 | **468** | **42** | 야간이 켜져 있을 때만 사유에 등장 |

★ **셋을 다 해도 42pt가 남는다.** 즉 **이 탭은 어떤 조합으로도 한 화면에 안 들어간다.**
그래서 내가 지킨 것은 「한 화면」이 아니라 **「사유 행이 접힘선 위」**다(위 계산, 여유 80pt).

### R3-6-2. 처방 — 톱니가 받은 것과 **같은 처방**(`coder-ui` 선례)

`InfoGearIconWidget.DefaultCenterPoints()`가 이미 `ReservedTopBarProbe` → `SurfaceSafeAreaPolicy`로
세로를 **파생**시킨다. 포스트잇만 상수로 남아 있다. 같은 함수로 보낸다.

```
세로 인셋 = SurfaceSafeAreaPolicy.ClampTopDownCenterY(
                desiredCenterY = panelHeight/2,   // "제일 위로 가고 싶다"
                sizeY          = panelHeight,
                screenHeight,
                topInset       = ReservedTopBarProbe.TopInsetPoints(...),
                margin         = PanelInsetPoints /* 16 */)  −  panelHeight/2
          ≡  topInset + 16                       (산술 등가 — 검산용이지 이 식을 코드에 쓰지 말 것)
```

| 환경 | 지금 | 처방 후 | 메뉴바 침범 |
|---|---:|---:|---|
| macOS 메뉴바 33pt | 16 | **49** | 17pt → **0** |
| Windows 상단 도킹 작업표시줄 40pt | 16 | **56** | 24pt → **0** |
| 예약 띠 없음(자동 숨김/하단 도킹) | 16 | **16** | **한 픽셀도 안 바뀐다** |

★ 마지막 줄이 이 처방의 안전성이다 — `ReservedTopBarProbe`는 **못 물으면 0**을 돌려주므로
(그 클래스 문서 *"실패는 0이다"*), **관측 실패가 카드를 이상한 자리로 보내지 않는다.**

세로 예산: 8행 카드 높이 = `12 + 8×28 + 12 + 28` = **276pt**. 위 49 + 276 = 325 ≤ 982. ✔ 넘치지 않는다.

### R3-6-3. ★★ 짝 변경 — 이걸 빠뜨리면 **51-9-3이 좁은 구간에서 되살아난다**

`ResolveRightInsetPoints()`(가로 톱니 회피)가 겹침을 판정할 때 **카드 위 모서리를
`PanelInsetPoints`(16)로 하드코딩**한다:

```
TodoPostItWidget.cs:506
  bool overlapY = gearTop < PanelInsetPoints + panelHeight && gearBottom > PanelInsetPoints;
```

세로 배치만 49로 옮기고 이 줄을 그대로 두면 **판정식이 더 이상 존재하지 않는 카드를 잰다.**

```
발산 구간 :  gearTop ∈ [16 + H, 49 + H)          (판정은 "안 겹친다", 실제는 "겹친다")
  H = 80  (1행 카드) → gearTop 96.0 ~ 129.0 → 톱니 중심 y 115.8 ~ 148.8 pt
  H = 276 (8행 카드) → gearTop 292.0 ~ 325.0 → 톱니 중심 y 311.8 ~ 344.8 pt
```
그 구간에 톱니를 끌어다 놓은 사용자는 **카드가 톱니를 다시 덮는 것**을 본다 —
51-9-3이 없앤 "이중 발동 구역 47.0pt²"까지 함께 돌아온다.

> **처방: 세로 배치와 `overlapY`의 카드 상단을 같은 한 곳에서 뽑는다.**
> `float panelTop = ResolveTopInsetPoints();` 하나를 만들어 **두 곳이 모두 그것을 읽는다.**
> 두 벌이 되면 반드시 한쪽만 고쳐진다(이 저장소가 이미 여러 번 겪은 실패).

### R3-6-4. 회피가 계속 도는지 확인 (처방 후 재검산)
