## 2. ★ 1순위 — 발화 게이트 단위 오류

### 2-1. 무엇이 틀렸는가 (독립 재계산으로 확인)

`docs/localization/verify/gate.py` 교정 먼저 — **깨지면 그 아래 숫자를 전부 폐기한다**:

`PerGlyphSeconds = 0.075f`는 실제로 **초/음절**인데 `int glyphs = text.Length`가 **초/글자**로 읽는다.
한글에서만 글자 = 음절이라 지금까지 안 들켰다.

### 2-2. ★★ 언어를 어떻게 아는가 — **알 필요가 없다**

리더가 "이게 핵심"이라고 짚은 지점이다. **답은 로케일이 아니다.**

> **가독예산은 "이 사용자의 언어"가 아니라 **"내가 지금 받은 이 문자열의 문자체계"**의 함수다.**

근거 셋:

1. **`ReadingSeconds`는 순수 함수라고 스스로 문서에 적어 두었다** — *"순수 함수다(시간/난수/전역 상태를 읽지 않는다)"*.
   여기에 로케일(전역 상태)을 주입하면 그 계약을 우리가 먼저 깬다. 그리고 이 저장소는
   **"받을 자리를 만들어 두면 언젠가 누가 채운다"**를 이미 한 번 명시적으로 거부했다
   (`RequiredDwellSeconds`가 노출 배율을 **인자로도 받지 않는** 이유). 같은 판단을 여기 적용한다.
2. **혼합 문자열이 실재한다** — `"Wi-Fi 끊겼네"`. 로케일 기준으로 갈랐다면 이 줄은 라틴 계수를 맞아
   **과소 청구**된다(= 조기 소멸). 문자열 기준으로 갈랐으면 **비싼 쪽**으로 간다(= 침묵. 침묵은 거짓말이 아니다).
3. **사용자 입력 대사가 실재한다** — 할일 리마인더는 `TodoListModel.ConsumePendingReminderText`가
   **사용자가 타이핑한 원문**을 그대로 말풍선에 싣는다(`TodoReminderDirector.cs:62/126`).
   한국어 UI를 쓰는 사용자가 영어로 적은 할일이 **로케일=Korean이라는 이유로 0.075/글자를 청구받으면 침묵한다.**
   문자열 기준이면 정확히 옳게 동작한다.

**결과: 게이트 수정은 로케일·설정·저장 스키마 어느 것도 기다리지 않는다. 오늘 착수 가능하다.**

> 로케일(§3-6)은 **문자열 테이블이 어느 배열을 고르는가**에만 쓰인다. 두 축을 절대 섞지 마라.

### 2-3. `coder`가 바로 착수할 수 있는 형태

**파일: `Assets/_Project/Scripts/Dialogue/DialogueKind.cs` — `DialogueBudget` 한 클래스, 함수 하나.**

```csharp
/// <summary>한 글자당 추가 가독 시간(초) — <b>글자 하나가 곧 음절 하나</b>인 문자체계용
/// (한글 음절 / CJK 통합한자 / 가나). 이 값은 원래부터 "초/음절"이었다.</summary>
private const float PerGlyphSeconds = 0.075f;

/// <summary>라틴 글자 한 자당 추가 가독 시간(초) = <b>0.0472</b>.
/// 고른 값이 아니라 <c>0.28 + w·G_en = 0.28 + 0.075·G_kr</c>를 실재 대사 17줄 + 그 영어
/// 재창작으로 푼 결과다(한글 112자 / 영어 178자 = 0.629 × 0.075).
/// 근거: design/narrative/2026-09-02_R2_발화빈도_풀24_영어게이트.md §5-3,
///       design/narrative/verify/en_budget.out.txt, docs/localization/verify/gate.out.txt.
/// ★ "안전하게" 더 낮추지 마라 — 침묵은 줄지만 <b>글자가 읽기 전에 사라진다</b>. 규칙 8이
///   없애려던 결함 그 자체다. 이 저장소에서 안전한 실패는 침묵이지 조기 소멸이 아니다.</summary>
internal const float PerLatinGlyphSeconds = 0.0472f;

/// <summary>이 문자열에 <b>글자=음절</b>인 문자체계가 하나라도 섞였는가(순수 함수).
/// 섞였으면 비싼 쪽으로 청구한다 — 과다 청구의 결과는 침묵이고, 침묵은 거짓말이 아니다.
/// <para>★ 로케일을 보지 않는다. 이 판정의 대상은 <b>사용자의 언어</b>가 아니라
/// <b>이 문자열</b>이다(사용자가 직접 입력한 할일 대사가 이 파이프라인에 실린다).</para></summary>
internal static bool IsSyllabicScript(string text)
{
    if (string.IsNullOrEmpty(text)) return true;   // 빈 문자열은 어차피 MinSeconds로 잘린다
    for (int i = 0; i < text.Length; i++)
    {
        char c = text[i];
        if (c >= '가' && c <= '힣') return true;                 // 한글 음절
        if (c >= 'ᄀ' && c <= 'ᇿ') return true;                 // 한글 자모
        if (c >= '㄰' && c <= '㆏') return true;                 // 호환 자모
        if (c >= '぀' && c <= 'ヿ') return true;                 // 히라가나/가타카나
        if (c >= '一' && c <= '鿿') return true;                 // CJK 통합한자
        if (c >= '㐀' && c <= '䶿') return true;                 // CJK 확장 A
    }
    return false;
}

public static float ReadingSeconds(string text)
{
    int glyphs = string.IsNullOrEmpty(text) ? 0 : text.Length;
    float perGlyph = IsSyllabicScript(text) ? PerGlyphSeconds : PerLatinGlyphSeconds;
    return Mathf.Clamp(BaseSeconds + glyphs * perGlyph, MinSeconds, MaxSeconds);
}
```

**바뀌지 않는 것(하나도 건드리지 마라)**: `BaseSeconds` 0.28 / `MinSeconds` 0.62 / `MaxSeconds` 2.20 /
`ReadsBeforeStale` 2 / `MinVisibleScale` / `MaxVisibleScale` / `RequiredDwellSeconds`의 형태 /
`IsEligible`의 형태 / `CanReplaceVisible` / `VisibleIsDoomedByIncoming` / `DialogueTiming` 3상수.

**`internal`인 이유**: 회귀 테스트가 `PerLatinGlyphSeconds`를 **숫자로 베끼지 않고 참조**해야 한다
(CLAUDE.md). `InternalsVisibleTo`는 `Scripts/AssemblyInfo.cs`에 이미 있다.

### 2-4. 파급 — `ReadingSeconds`를 쓰는 세 곳이 전부 함께 언어 인식형이 된다

| 소비자 | 영어에서 어떻게 되는가 | 판정 |
|---|---|---|
| `RequiredDwellSeconds` / `IsEligible` | 필요 체류가 짧아진다 → **영어가 말할 수 있게 된다** | ★ 이번 수정의 목적 |

### 3-2. UI 테이블 — `StickMateDisplayNames`의 어법을 확장한다

**새 런타임 로더(JSON/CSV/Addressables)를 도입하지 않는다.** 이유 넷:

1. `Core/StickMateDisplayNames.cs`가 이미 정확히 이 물건이다 — **enum → 완성 문장 정적 배열, 무할당**.
   그 파일의 문서가 이유까지 적어 뒀다(*"행동 명령창은 0.25초마다 6개 타일의 가용성을 다시 묻는다 …

2. **키를 컴파일러가 검사한다.** 런타임 키 조회는 "키 없음"이라는 새 실패 모드를 만들고, 그 증상은
   화면의 `##MISSING##`이다. enum 인덱싱은 **키 오타가 빌드 에러**다.
3. **`Resources.LoadAll`은 이미 위험 지점이다** — `ItemCatalog.EnsureLoaded`가 도메인 리로드 문제 때문에
   지연 로드로 우회하고 있다. 문자열까지 그 경로에 태우면 실패 지점이 하나 는다.
4. 감사(§4)와 골든 테스트가 **소스를 읽는다** — 활성 빌드 타깃과 무관하게 동작해야 하므로(CLAUDE.md)
   테이블이 소스에 있는 편이 검사가 쉽다.

**신규 파일 4개 (`Core/Loc/`)**:

```
Core/Loc/StringId.cs        enum StringId { … }              — 키. 유일한 진실
Core/Loc/StringTableKo.cs   static readonly string[] Table   — (int)StringId 인덱싱
Core/Loc/StringTableEn.cs   static readonly string[] Table
Core/Loc/L.cs               static string T(StringId id)     — 활성 테이블에서 하나 꺼낸다
                            static string T(StringId, arg0…) — string.Format 1회
```

`L.T(id)`는 **인덱싱 한 번**이라 할당이 0이다(`StickMateDisplayNames.Of()`와 동일한 비용).
서식 인자가 있는 35건만 `string.Format`을 탄다 — 지금도 보간으로 매번 새 문자열을 만들고 있으므로 비용은 동일하다.

### 3-3. ★★ 문자열 연결(concat) 조립을 폐기한다 — 이게 어법 확장의 핵심 변경점

`StickMateDisplayNames`의 어법 중 **하나는 그대로 못 쓴다**:

```csharp
// 현행 — 앞/뒤 조각을 붙여 문장을 만든다
BuildBusyTexts(SpectacleNames, "지금 ", " 중이에요")   // → "지금 활쏘기 중이에요"
```

영어는 **어순이 다르다**. `"Busy: " + name + ""`처럼 억지로 맞출 수는 있지만, 그건 어순이 같은 언어에서만
버티는 구조이고 다음 언어에서 반드시 깨진다. **조각이 아니라 템플릿을 테이블에 둔다**:

```csharp
BuildBusyTexts(SpectacleNames, StringId.BusySpectacleFormat)   // ko: "지금 {0} 중이에요"
                                                              // en: "Busy with {0} right now"
```

같은 처방이 필요한 실측 대상:

| 형태 | 건수 | 예 |
|---|--:|---|
| 중괄호 보간을 포함한 문자열 | **35** | `ItemCatalog.cs:248` `"Lv.{ResolveUnlockLevel(config)}에 열림"` → en `"Unlocks at Lv.{0}"` (**어순 반전**) |
| 4자 이하 조각(연결 조립 의심) | **113** | `StickMateDisplayNames` `"지금 "` + `" 중이에요"` |

**규칙 3개 (`coder`/`coder-ui`에게 그대로 넘겨라)**
1. **테이블 항목은 언제나 완성된 문장이다.** 조각을 넣지 않는다.
2. **가변부는 `{0}`,`{1}`.** 번호를 쓴다(순서를 바꿀 수 있어야 한다).
3. **테이블 항목끼리 `+`로 붙이지 않는다.** 붙이고 싶으면 그건 한 항목이어야 한다.
   → §4의 감사가 `L.T(…) +` 패턴을 금지 항목으로 잡는다.

### 3-4. 대사 저장소 — 별도

**버전 분기가 필요 없다** — 옛 파일에는 키가 없어 `false`/`null`로 채워지고, 그 `false`는
*"아직 고른 적 없다 = 자동 판정"*이라는 **정확한 사실**이다.
값은 숫자가 아니라 **이름 문자열**로 적는다(`DialogueVisibleLengthSaveName`이 쓰는 그 관례 —
열거형 순서가 바뀌어도 파일이 안 밀린다).

> ★ 트리 실측: `CharacterSaveStore.CurrentVersion`은 **지금 10**이다(`preferredMonitorSaved`/`preferredMonitorKey`, `dev-platform`).
> 리더 브리핑의 "9로 되돌렸다"와 다르다 — **확인 필요**. 어느 쪽이든 언어 2필드는 **다음 묶음에 얹으면 되고 단독 인상은 필요 없다.**

**언어 전환 UI**: 설정창 [일반]에 3단 세그먼트(`자동 / 한국어 / English`). `ux-designer` 소관.
전환 시 이미 그려진 라벨을 다시 칠해야 하므로 `L.LanguageChanged` 이벤트가 필요하다 —
**또는 1.0은 "다시 시작하면 적용됩니다" 한 줄로 끝낸다**(권고: 후자. 표면 35개를 다시 칠하는 경로가 새 버그 표면이다).

### 3-7. `KoreanParticle` — 손대지 않는다

## 7. 플랫폼 영향

**Windows 영향: 없음(이번 라운드) / L0에서도 없음.**
`DialogueKind.cs`는 `#if` 하나 없는 **완전한 플랫폼 중립**(`Mathf` + `string`)이다.
문자열 테이블도 `Core/Loc/`에 두므로 마찬가지다. 다만 **감사 테스트는 소스 파일을 읽도록** 짠다 —
그래야 macOS 타깃에서 돌려도 `Platform/Windows/*.cs`의 리터럴을 함께 센다(CLAUDE.md 활성 빌드 타깃 사각지대).

**macOS 영향: 없음(이번 라운드).**
★ 단, **폰트에 실측 위험이 하나 있다** — `DialogueBubbleRenderer.ResolveFont()`는 후보 폰트를
`CanRenderKorean(f)`(`'한'` 글리프 실측)으로 **거른다**. 한국어 폰트가 없는 영어권 머신에서는 후보가 전부

## 10-1. ★★ `layout.py` — 판정: **역할 전환(3안) + 예측 기능 폐기(2안)**

### 무엇이 잘못돼 있었나 — 「자기 상수로 자기를 교정」

R2의 `layout.py`는 상자 폭을 **글자 수 × 상수**로 계산했고, 그 상수 4종(11 / 9 / 14 / 11)은
프로덕션에서 베껴 온 것이었다. `coder-ui`가 2026-09-03에 그 모형 7곳을 전부
`Text.preferredWidth` 실측으로 바꾸면서 **네 상수가 프로덕션에서 사라졌다.**

**그런데 CALIBRATION은 그 뒤에도 3/3 통과했다.** 교정 앵커를 다시 보면 이유가 즉시 보인다:

| 교정 항목 | 실제로 검사한 것 | 판정 |
|---|---|---|
| `[장비]` 상자 = 32pt | `len("장비") × 14 + 4 == 32` | **산술 항등식.** 프로덕션이 어떤 상태든 참 |
| 마지막 탭 끝 = 230pt | 같은 식의 합 | 항등식 |
| 밑줄 한계 = 776pt | `22 + 754` | 항등식 |
| 설명 칸 = 39자 | `floor(434 / 11)` | 항등식 |

넷 다 **자기가 만든 숫자를 자기 주석과 대조**하고 있었다.
그리고 그 주석들도 **같은 모형이 써 넣은 것**이다.
> **측정 도구가 자기 자신을 검증하는 구조.** 이 저장소가 아홉 번 당한 형태 그 자체다.

### 왜 「재전사(1안)」가 아닌가 — 계수를 새로 넣어도 병은 남는다

**직접 해 봤다.** `coder-ui` 실측 계수(한글 12.0 / 라틴 6.8 / 공백 3.0 pt·자, 12pt 기준)로
설정창 탭바를 다시 계산하고 러너 실측과 견줬다:

| 문안 | 새 계수 모형 | **러너 실측** | 오차 |
|---|--:|--:|--:|
| **한국어** (현행) | 464pt | **461pt** | **+3pt (0.7%)** |
| **라틴 풀네임** | 696pt | **655pt** | **+41pt (6.3%)** |

★★ **이 두 줄이 결론 전체다. 모형은 «양쪽에서 대충 맞는» 물건이 아니다 —
한국어에서는 거의 정확하고, 라틴에서만 계통적으로 과대하다.**
한글은 음절마다 자폭이 12.0으로 사실상 고정이라 평균이 곧 참값이지만,
라틴은 가변폭이라 평균이 글자마다 어긋나고 **문자열이 길수록 누적**된다
(`Accessibility & Performance` 한 탭에서만 모형 177pt vs 실측이 함축하는 값).

- **41pt는 남은 여유 65pt의 63%다.** 재전사한 모형은 «여유 24pt»라고 보고할 것이고,
  그건 여전히 `ux-designer`에게 **문안을 줄이라고 요구하게 만드는 숫자**다. 방향이 같은 병이다.
- 원인이 계수가 아니라 **평균이라는 방법**에 있다. 계수를 아무리 잘 뽑아도
  **정밀도가 필요한 바로 그 자리(긴 라틴 문자열)에서 가장 크게 틀린다.**
- 그리고 계수를 러너에서 가져오면 **또 자기교정이 된다**(러너 숫자로 만든 모형을 러너 숫자로 검증).

### 왜 「완전 폐기(2안)」도 아닌가 — 러너가 **구조적으로** 못 보는 축이 하나 남는다

이 개발 머신에 **Windows 폰트 스택이 없다.** 러너의 655pt는 macOS 폰트가 잰 값이다.
상자는 이제 «그 폰트가 잰 값»으로 만들어지므로 **상자와 글리프는 어느 폰트에서도 맞다**.
**남는 위험은 창 폭이 고정(720pt)이라는 것 하나**다 — 자간이 넓은 폴백에서 누적 끝이 밀린다.

그 위험은 **나눗셈 한 번**으로 정직하게 말할 수 있다:
```
720 / 655 − 1 = 9.9%      ← 라틴 탭바가 견디는 자간 확대 한도
720 / 461 − 1 = 56.2%     ← 한국어 탭바 (폴백 글꼴 자체가 다르다: 맑은 고딕/굴림 계열)
```
**내가 만든 계수가 하나도 안 들어간다.** 실측 두 개의 나눗셈이다.

### ★ 옛 결론이 어떻게 됐는가 — **방향은 옳았고 크기가 틀렸다**

| | 값 | 출처 |
|---|--:|---|
| R2 `layout.py` 예측(라틴 배지 `Coming soon` 포함) | **1073pt** (초과 353pt) | 폐기된 글자수 모형 |
| 러너 EditMode `[갭G]`의 «라틴 옛근사»(**한국어** 배지 유지) | **863pt** | 같은 모형, 배지만 다름 |
| **러너 실측** | **655pt** | `Text.preferredWidth` |
| 창 폭 | 720pt | `SettingsWindow.PanelWidth` |

- **1073과 863의 차이는 배지 문자열 하나다**: 내 계산은 배지도 영어(`Coming soon` 11자 × 10pt = 110pt)로
  바꿨고, 러너의 음성 대조는 배지를 한국어(`준비 중` 4자 × 10 = 40pt)로 뒀다. 미배지 탭이 3개이므로
  `3 × (110 − 40) = 210pt`, `1073 − 210 = 863`. **두 숫자는 같은 모형이고 모순이 아니다.**
  ⇒ **같은 문안·같은 배지로 견주면 옛 모형 1073pt vs 실측 655pt — 모형이 418pt(64%)를 지어냈다.**
- **판정 방향은 옳았다**: "여기가 영어에서 가장 위험한 줄이다"는 맞았고, 실제로 여유가 65pt(9%)뿐이다.
- **크기가 틀렸다**: 353pt 초과가 아니라 **65pt 여유**였다. 문안을 줄이라고 요구할 근거가 아니었다.

### ★★ 성공 사례는 지운다 — 푸터 [지금 종료] 칩은 **실제 출하 결함**이었다

R2 `layout.py`가 유일하게 **정탐**한 자리다. 그 출력은 이랬다:
```
버튼 폭 132pt.  영어/Windows  a=5.5 → 138pt(초과)  a=6.0 → 150pt(초과)
                              a=6.5 → 162pt(초과)  a=7.0 → 175pt(초과)
※ a(라틴 평균 자폭)는 이 머신에서 측정 불가 — 러너의 Text.preferredWidth로만 확정된다.
```
러너 PlayMode 실측(2026-09-03 06:33):
```
[글자폭모형-TEST] 종료 칩 — 호스트 «지금 종료 (⌃⌥⌘Q)» 잉크 99.0pt / 칩 132.0pt.
   Windows 표기 «지금 종료 (Ctrl+Alt+Win+Q)» 잉크 150.0pt → 필요 폭 176.0pt.
```
⇒ **150pt 글리프가 132pt 상자에 들어 있었다. 18pt 유출.**
그리고 그 라벨은 `HorizontalWrapMode.Overflow`라 **잘리지도 않는다** — 테두리를 뚫고 나온 글자다.
프로덕션 주석이 *"Windows에서 `Ctrl+Alt+Win+Q`로 늘어나도 담기는 값"*이라고 적어 두고 있었는데
**한 번도 검증된 적이 없는 거짓**이었다.

★ **정직하게 적는다**: 내 모형이 «150pt»를 맞힌 것이 **아니다**. 그 150은 *다른 문자열*(영어 라벨 25자)에
`a=6.0`을 곱한 값이고, 실측 150은 *한국어 라벨 + Windows 표기*의 잉크다. **숫자 일치는 우연이다.**
값을 한 것은 **점 추정이 아니라 구간**이었다 — `a`를 5.5~7.0로 훑어 **어떤 가정에서도 132pt를 넘는다**를
보였고, 그 구간이 진실(150)을 담고 있었다.

### ★★★ 그래서 남는 일반 규칙 — 부호가 반대인 세 가지 형태

「글자 수 × 상수」 모형은 한 종류의 오차가 아니다. **상자와 문자열의 관계에 따라 부호가 뒤집힌다.**
R2가 맞은 곳과 틀린 곳이 정확히 이 축으로 갈렸다.

| 형태 | 식 | 라틴에서 | R2 결과 | 실측 |
|---|---|---|---|---|
| **곱셈형** | 상자 = 글자수 × k | 상자가 **부푼다** → **가짜 넘침** | **오탐** (탭바 2곳, 세그먼트, 버튼, 배지) | 863→655 |
| ↑ 왜 한국어에서 안 들켰나 | 같은 식 | 한글은 자폭이 **사실상 고정**(12.0) | 오차 0.7% | 464 vs 461 |
| **나눗셈형** | 상한 = floor(폭 / k) | 상한이 **과소** → 자리가 남는데 **미리 자른다** | 실제 결함이지만 「넘침」이 아니다 | 434pt 칸, 옛 상한 39자 |
| **고정형** | 상자 = 상수, 문자열은 따로 자란다 | **모형이 유일한 탐지 수단** | **정탐** (종료 칩) | 150pt vs 132pt |

> **오프라인 모형은 「상자가 문자열에 의존하지 않는 자리」에서만 값을 한다.**
> 프로덕션이 문자열을 재서 상자를 만들기 시작하면 모형은 남아도는 정도가 아니라 **해로워진다** —
> 방금 제거한 그 부풀림을 다시 더하기 때문이다.

그래서 새 `layout.py`의 **원장에는 고정형 표면만 실려 있다.** 곱셈형 표면은 뺐다 —
그쪽은 러너의 «상자 폭 == 실측 잉크» 단언이 구조적으로 더 강하다.

## 10-2. 규모 재확정 — **고유 440 / 총 505**

`ship.py`를 다시 돌렸다(2026-09-03). `product-strategy` 3회차 숫자를 **내 도구가 그대로 재현**한다.

| | R2 (09-02 15:30) | R3 (09-03) | 증가 |
|---|--:|--:|--:|
| `.cs` SHIP (총) | 401 | **421** | +20 |
| `.asset` (디코드 후) | 84 | **84** | 0 |
| **총건수** | 485 | **505** | **+20** |
| **고유** | 424 | **440** | **+16** |

`product-strategy`의 증가율(작업 14.4시간, 시간당 고유 +1.11 / 총 +1.39)로 계산하면
`485 + 14.4×1.39 = 505.0`, `424 + 14.4×1.11 = 440.0`. **정확히 맞는다** — 두 측정이 독립적으로 일치한다.
(리더 브리핑의 "네가 냈던 425"는 **424**의 반올림으로 보인다. `.cs` 고유 340 + `.asset` 84.)

### ★ 「고유」와 「총건수」를 왜 섞으면 안 되는가 — 실측 65건

```
.cs SHIP  총 421  /  고유 356      (중복 65건, 서로 다른 문자열 36종이 만든다)
.asset    총  84  /  고유  84
합계      총 505  /  고유 440
```
가장 많이 겹치는 것: `"집중 모드"` **9곳** · `"앱제어 {source}"` **9곳** · `"[✕] 클릭"` **5곳** ·
`"활쏘기"`/`"그라피티"`/`"창 도둑"`/`"창 부수기"` 각 4곳.

- **번역 비용 = 고유 440.** 테이블 항목 수이고 `design-narrative`/번역가가 실제로 쓰는 문장 수다.
- **코드 수정 비용 = 총 505.** 손대야 하는 호출 지점 수다.
- ★ **그리고 이 65건은 테이블 도입으로 공짜로 사라진다** — `StringId.FocusModeName` 하나에 9개
  호출부가 모인다. 즉 **이관은 중복 제거를 겸한다.**

### ★ `diagarg.py`가 더 좁힌 숫자 — 437 (혼동 주의)

## 10-3. Unity Localization 기각 — **사유 순서를 다시 세운다** (결론 유지)

`product-strategy`가 대표 사유를 뒤집었다. 옳은 지적이다:

> *"Android `INTERNET` 권한"은 **오늘 우리에게 해당 없다** — Android는 어느 문서에도 타깃이 아니다*
> *(CLAUDE.md 모바일 타깃은 iPad/iPhone).*
> ***"약한 근거로 옳은 결론을 지키면, 근거가 무너질 때 결론이 함께 무너진다."***

**결론(자체 테이블 채택 / Unity Localization 기각)은 유지된다.** 사유 순서만 다시 세운다.

| 순위 | 사유 | 왜 이 자리인가 | 무너지면? |
|--:|---|---|---|
| **1** | **감사가 소스 텍스트를 읽는다** | CLAUDE.md 활성 빌드 타깃 규칙: *"플랫폼 감사는 타입이 아니라 **소스 파일**을 읽도록 짠다"*. 문자열이 `Addressables`/`AssetBundle`로 나가면 **부채 상한 감사가 구조적으로 불가능**해진다 — `.cs`에 문자열이 없으니 셀 것이 없고, 애셋 안은 빌드 타깃에 묶인다. **그 감사가 부채를 막는 유일한 장치다**(§10-2가 실측으로 보여 준다: 14.4시간에 +20건) | 결론이 무너진다. **이 사유가 무너지면 자체 테이블을 고집할 이유가 없다** |
| **2** | **키 오타가 빌드 에러다** | `enum StringId` 인덱싱은 컴파일러가 검사한다. 런타임 키 조회는 «키 없음»이라는 **새 실패 모드**를 만들고 증상은 화면의 `##MISSING##`이다 | 결론이 약해지지만 살아 있다(1이 남는다) |
| **3** | **상주 앱의 할당 예산** | `StickMateDisplayNames`가 이미 그 이유를 적어 뒀다 — *"행동 명령창은 0.25초마다 6개 타일의 가용성을 다시 묻는다 … 초당 24개의 쓰레기 문자열"*. 24시간 상주라 이 제약은 그대로다. 정적 배열 인덱싱은 할당 0 | 성능 팀이 반증할 수 있는 축이다 |
| **4** | **`Resources.LoadAll`이 이미 위험 지점이다** | `ItemCatalog.EnsureLoaded`가 도메인 리로드 문제로 지연 로드로 우회 중이다. 문자열까지 그 경로에 태우면 실패 지점이 하나 는다 | 로더를 고치면 사라지는 사유 |
| **5** | **이미 그 물건이 있다** | `Core/StickMateDisplayNames.cs` = enum → 완성 문장 정적 배열. 새 어법을 배우지 않는다 | 취향에 가깝다. 단독으로는 근거가 못 된다 |
| ~~폐기~~ | ~~Android `INTERNET` 권한~~ | **해당 없음.** Android는 타깃이 아니다(macOS/Windows/iPad/iPhone) | — |

★ **1번이 다른 넷과 성질이 다르다**: 2~5는 «비용이 더 든다»이고, **1은 «검증 능력을 잃는다»**이다.
이 저장소의 사고 목록이 전부 «못 재서» 난 것이므로 그 상실이 가장 비싸다.

★ **1번이 언제 무너지는가 — 미리 적어 둔다**: (가) 부채 상한 감사가 끝내 안 세워지거나,
(나) 문자열이 `.cs`를 떠나도 감사가 계속 가능한 형태(예: 빌드에 포함되는 **평문 TSV**를 감사가
직접 읽는 구조)가 마련되면. **그때는 이 판정을 다시 열어라.** 결론을 지키려고 사유를 늘리지 마라.

## 10-4. ★★ 팩 부채 구조화 — 사용자 확정이 만든 영구 증가

**그리고 `grep '[가-힣]' *.asset`은 그 위반을 영원히 0건으로 답한다.**

### 10-4-1. 감사 설계 — `docs/localization/verify/packguard.py` (신규, 프로토타입 동작 중)

**함정의 실증 (이 라운드에서 다시 확인)**

0                        ← rc=1. 파일에는 「베레모」와 설명이 들어 있다.

```

**규칙 3개**

1. **디코드한 뒤에 센다.** 그리고 **raw 스캔도 함께** 돌려 «raw 0 / 디코드 N»이라는
   **함정의 실재를 매번 증명한다.** ★ **둘 다 0이면 «깨끗»이 아니라 「디코더가 죽었다」**이고,
   그 실행의 모든 판정을 폐기한다. (거짓 통과 #4의 정확한 형태)

   숫자는 **내려갈 때만** 손으로 고친다(이관이 진행된 만큼). 올리려면 리더 승인.
3. **`*Key`로 끝나는 필드에 한글이 있으면 그건 부채가 아니라 즉시 결함이다.**
   `Core/PackManifestKeys.IsWellFormed`가 `false`를 내고 팩 로드가 거부된다. 별도 등급으로 신고한다.

**양성/음성 대조 — 짝으로 21건** (`packguard.py --selftest`, 현재 **21/21 PASS**)

## 10-5. ★ 자기 산출물의 거짓 신호 — `dryrun.py`가 대사 9줄에 눈이 멀어 있었다

이 라운드 시작 때 `dryrun.py`(오프라인 예행)를 돌리자 **실패 1건**이 나왔다:
```
FAIL  골든 -> 소스 (삭제 감지)
  ['거긴 다리야','거긴 머리야','놔줘 놔줘','다리 놔','머리 놔','안 놔?','야!','어딜 잡아','잡혔다']
```
**「대사 9줄이 삭제됐다」로 읽으면 틀린다. 9줄은 전부 살아 있다.**
`Dialogue/GrabReactionLines.cs`가 대사를 **배열 초기화자**
(`static readonly string[] HeadLines = { "머리 놔", ... }`)에 담는데,
`dryrun.py`의 수집기는 `DialogueLine.Say|React` / `TriggerSelfReturn` / `cfg =>` **세 형태만** 알았다.

**왜 갈렸나**: `golden_gen.py`(생성기)는 2026-09-03 00:12에 이 형태를 흡수했고
`dryrun.py`(검사기)는 09-02 16:07에서 멈춰 있었다.
> TEAM.md의 열 번째 형태는 **«생성기와 검사기가 코드를 공유해 같이 틀린다»**였다.
> 이번은 **그 반대** — 둘이 **갈라져서** 틀렸다. 그리고 **갈라진 쪽은 시끄러웠다(FAIL)**.
> 공유해서 틀리면 조용히 초록이 된다. **갈라지는 쪽이 안전한 방향이다.**

**고친 방식** (`golden_gen.py`를 `import`하지 **않았다** — 그러면 다시 공유가 된다):
1. `dryrun.py`에 **형태가 다른 독립 구현**을 넣었다. `golden_gen`은 배열 **이름 4개를 열거**하고,
   이쪽은 `Dialogue/**` **디렉터리를 전수 스캔**해 모든 `static readonly string[]`을 훑는다.
   ⇒ **새 풀 파일이 생기면 자동으로 따라간다.**
   ★ 그리고 이 형태는 곧 **주류가 된다** — §3-4가 영어 대사 풀을 정확히 이 모양으로 만들라고 정해 뒀다.
   **안 고쳤으면 대사가 테이블로 옮겨가는 순간 골든이 조용히 텅 빈다.**
2. **제3의 심판**을 붙였다 — `census.py`의 **C# 어휘 분석기**(정규식이 아니라 전체 토크나이저,
   자체 대조 10/10)로 같은 파일의 한글 리터럴을 세어 **9건**을 확인한다.
   두 정규식 수집기가 다투면 이쪽이 가른다.
3. 합성 소스 대조 3건 추가: 배열 형태를 찾는가 / **배열 안 주석 줄의 인용부호를 대사로 세지 않는가** /
   `Combine(...)` 합본 배열이 **중복을 만들지 않는가**.

**결과**: `dryrun.py` 말뭉치 **33줄 → 42줄**, 골든 42줄과 **양방향 일치**, 전체 **rc=0 · FAIL 0**.

                                               ⇒ 그 함수 안에서 text.text = content 를 한다 (SettingsControls.cs:119)
```

화면에 뜨는 글자는 **하나도 안 바뀌었다.** 그런데 `ship.py`의 싱크 정규식은 `\.text\s*=`만 알았고,
파일에 그것이 **0건**이 되자 **파일 전체를 `LOGF`(미출하)로 떨어뜨렸다.** 그래서
`장비` · `외형` · `보관함` · `상점` · `상점은 다음 업데이트에 들어옵니다.` **5건이 원장에서 증발했다.**

★ **이 저장소가 아홉 번 당한 그 형태다** — *"실패한 측정과 성공한 측정이 똑같이 생겼다."*

그리고 하필 **탭 라벨 4개**(앱에서 가장 많이 읽히는 글자)와 **`상점`**(E-B의 입구)이었다.
