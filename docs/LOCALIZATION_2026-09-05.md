### 처방 (착지함) 과 그 대조

`SINK_RE`(uGUI)와 **일부러 분리해** `OS_SHELL_SINK_RE`를 신설하고, **근거 확인에만** 썼다.

> **왜 `SINK_RE`에 합치지 않았나** — 합치면 `WindowsSystemTrayIcon.cs`가 「싱크 있는 파일」이 되어
> 그 안의 **로그 문자열 8건**(`[트레이]`, `Shell_NotifyIcon 호출 중 예외…`)까지 SHIP으로 딸려 온다.
> **사각지대를 고치면서 반대쪽으로 과대를 만드는 것은 고친 것이 아니다.**

`ship.py --selftest` **15 → 20건, 전부 PASS**. 신설 4건은 **전부 실파일 앵커**다:

| 대조 | 무엇 |
|---|---|
| ★ 양성(실파일) | 트레이 4라벨 + 툴팁이 **SHIP으로 잡히는가** |
| ★ 짝(음성, 실파일) | `WindowsSystemTrayIcon.cs`의 로그 8건은 **여전히 SHIP이 아닌가**(과잉 확대 방지) |
| ★ 죽은 니들 방지 | 새 화이트리스트의 **근거가 비어 있지 않은가** |
| ★ 근거 실재 | 그 근거가 **실제로 Win32 트레이 파일을 가리키는가** |
| ★ 선언된 과대 고정 | 이 파일 SHIP 9건 중 **개발자 산문(`MacOsGapReason`)이 정확히 4건**인가 |

**★ 감지 경로 생존 증명** — 화이트리스트 항목을 빼고 다시 돌렸다:

```
수정 있음 :  20 PASS / 0 FAIL
수정 제거 :  16 PASS / 4 FAIL   ← 심은 그 4건만 빨개졌다. 나머지 16건은 그대로 초록
```

*"에러가 났다"*가 아니라 *"심은 그것만 빨개졌다"*를 확인했다. 그리고 **과잉 확대 음성 대조는 두 상태 모두 초록**이었다
— 즉 「전부 SHIP으로 쓸어담아 통과시킨 것」이 아니다.

★ **선언된 과대 4건**: `MacOsGapReason`(macOS 트레이 갭 사유 산문)이 리터럴 4조각으로 SHIP에 남는다.
소비처는 **테스트 하나뿐**이라 유저 노출이 아니다. §1-4 관례대로 **안전측으로 남기고 selftest가 그 4를 못박는다**

**처방(착지함)**: 표류를 **개별로 보고**하고, **「자동 검출기가 같은 파일을 보고 있는가」**로
*표류/자동흡수*와 *진짜 죽은 니들*을 가른다.

```
~~ 줄 표류/자동흡수 의심 14건 (같은 파일을 자동 검출기가 이미 보고 있다)
!! ★ 죽은 니들 0건
```

**★ 감지 경로 생존 증명** — 자동 검출기가 **안 보는 파일**로 고의 니들 1개를 주입:

```
!! ★ 죽은 니들 1건 — Core/EquipmentModel.cs:99999  고의 주입
```

⇒ 죽은 니들 분기가 **실제로 살아 있다.** (주입은 즉시 원복했고 `diff -q`로 동일 확인.)

**방향은 안전측이다** — 니들이 죽으면 **비번역이 번역 대상으로 남는다**(과대). 그러나 형태가 그 형태이므로 신고한다.

**(2) ★★ 레이아웃이 글자 수에 하드코딩돼 있지 않다 — 이것이 이 앱의 가장 큰 이득이다.**
2026-09-02~03에 곱셈형 상수 3종(`TabLabelCharWidth` · `TabBadgeWidth` · `CaptionKoreanAdvance`)을
**폐기하고 실측으로 갈아탔다.** 그 결과:

> **길어진 영어가 상자를 넘치게 하는 경로가 원리적으로 막혀 있다.** 상자가 글자를 따라간다.

★ 그 폐기가 지금도 유효한지 **이번 라운드에 다시 확인했다**(`layout.py` 폐기 감시, 아래 §3-6).
남는 위험은 **상자가 먼저 정해진 자리** 하나뿐이다 — `SettingsWindow.PanelWidth = 720`(고정)에 5탭이 들어가는 곳.
**그 숫자는 지금 폐기 상태다**(러너 xml 신선도 실패). 재측정이 필요하다.

**(3) ★★ 조형이 바뀌는 곳은 딱 하나 — 말풍선이다.**
`ResolveKoreanFont`는 **모든 후보를 `CanRenderKorean('한')`으로 거른다 — 언어와 무관하게.** 그래서:

| 환경 | 뽑히는 폰트 | 결과 |
|---|---|---|
| 한국어 폰트 있는 머신 + 영어 모드 | `AppleSDGothicNeo-Heavy` / `Malgun Gothic Bold` 등 **한국어 폰트** | ★ **영어 글자를 한국어 폰트의 라틴 글리프로 그린다.** 창 UI(Arial 계열)와 **서로 다른 서체가 한 화면에 뜬다** — 한국어 모드에서는 둘 다 다른 서체라 안 보이던 것이, 영어에서는 **같은 문자를 나란히 비교**하게 되어 드러난다 |
| 한국어 폰트 **없는** 머신(영어권 Windows 다수) | 후보 전멸 → `LegacyRuntime.ttf` | ★ **`_cachedFontIsRealBold` 경로를 잃어 합성 볼드가 된다** — `design-art`/`design-motion`이 맞춰 둔 만화 레터링 굵기가 **그 환경에서만** 달라진다. 그리고 찍히는 경고가 *"말풍선의 **한글**이 네모로 보일 수 있습니다"* — **영어 모드에서 거짓말** |

**권고 — 게이트가 이미 쓰는 술어를 그대로 재사용한다:**

```
지금 : 후보 전부를 CanRenderKorean('한')으로 거른다  (문자체계 무관)
제안 : 캐시를 둘로 — [라틴 우선 캐시] + [한국어 가능 캐시]
       줄마다 DialogueKind.IsSyllabicScript(text) 로 고른다   ← L0이 이미 착지시킨 그 함수
```

★ **한국어는 비트 단위로 불변이다** — 한글이 한 자라도 있으면 `IsSyllabicScript`가 true라 **지금과 완전히 같은
후보 목록**을 탄다. **양성 대조는 「한국어 대사 42줄 전수에서 뽑히는 폰트 이름이 같은가」로 잡으면 된다.**
★ **캐시를 둘로 두어야 하는 이유**: 할일 리마인더 대사는 **사용자가 직접 입력한 문자열**이라
영어 로케일에서도 한글이 들어올 수 있다. **로케일 단위로 폰트를 하나만 고르면 그 사용자의 말풍선이 두부가 된다.**

## 3-5. ★ 연결(concat) 조립을 폐기한다 — 어법 확장의 핵심 변경점

```csharp
// Core/StickMateDisplayNames.cs:42, :87
BuildBusyTexts(SpectacleNames, "지금 ", " 중이에요")       → "지금 활쏘기 중이에요"
BuildBusyTexts(StateNames,     "지금 ", " 중이라 못 해요")  → "지금 걷는 중이라 못 해요"
```

**접두사 + 이름 + 접미사**는 어순이 언어마다 다르다. **포맷 문자열 1개**로 바꾼다:

```
ko : "지금 {0} 중이에요"        en : "Busy: {0} right now"
ko : "지금 {0} 중이라 못 해요"   en : "Can't — {0} right now"
```

★ **미리 굽는 최적화는 그대로 살아남는다** — `BuildBusyTexts`가 `string.Format`을 **정적 생성 시 1회**
돌리면 된다. 그 파일이 걱정한 *"초당 24개의 쓰레기 문자열"*은 그대로 0이다.

**규모**: 보간(`{}`) 포함 **37건 / 고유 28** · 4자 이하(조립 의심) **129건 / 고유 102**.
후자 전부가 조각인 것은 아니다(`모자`·`전설`처럼 온전한 낱말이 다수). **확정 목록은 문자열 테이블을 만드는
라운드가 한 건씩 판정한다** — 여기서는 규모만 준다.

★ **이미 잡힌 조각의 실물**: `StickMateDisplayNames`의 `"지금 "` / `" 중이에요"`가 4자 이하 목록에 **각각 따로** 잡혀 있다.
그것이 이 절이 존재하는 이유다.

# 4. 언어별 발화 게이트

## 4-1. 이미 언어 인식형이다 (L0 착지 완료 — 이번 라운드 재확인)

```csharp
// Dialogue/DialogueKind.cs:102,126,209
internal const float PerGlyphSeconds      = 0.075f;    // 음절 문자체계
internal const float PerLatinGlyphSeconds = 0.0472f;   // 라틴 = 0.075 × (112/178)
public static float ReadingSeconds(string text)
    => Mathf.Clamp(BaseSeconds + glyphs * (IsSyllabicScript(text) ? PerGlyphSeconds
                                                                 : PerLatinGlyphSeconds),
                   MinSeconds, MaxSeconds);
```

`dryrun.py` **전부 통과**(계수 비율 0.6293 vs 유도값 0.6292 · 혼합은 비싼 쪽 · 사용자 입력 할일도 문자체계로 청구).
★ **게이트는 「언어」를 모른다 — 「그 문자열의 문자체계」만 안다.** 그래서 로케일 인프라에 의존하지 않는다.

## 4-2. ★ 영어 대사가 말풍선 폭을 넘기는가 — **넘길 수 없다**

**(a) 구조적으로 잘리지 않는다.**
```csharp
_label.horizontalOverflow = HorizontalWrapMode.Wrap;     // 가로는 줄바꿈
_label.verticalOverflow   = VerticalWrapMode.Overflow;   // 세로는 자라난다
```
⇒ 넘치는 대신 **줄이 늘어난다.** 진짜 질문은 **「줄 수가 늘어 블록 높이 상한(캐릭터 키의 130%)을 깨는가」**다.

**(b) 그 상한을 깨려면 「라틴 한 자가 한글 한 자의 0.611배보다 넓어야」 한다.**

랩 폭은 `ComicWrapWidthPoints = 170 × 배율 × 폰트/13`으로 **문자체계와 무관**하다.
게이트가 허용하는 **최장 줄**을 상태별로 놓고 두 언어의 **차지 폭(em)**을 견준다:

| 상태 | 분모 | 한글 상한 | 영어 상한 | 손익분기 비 = 한글/영어 |
|---|--:|--:|--:|--:|
| Idle | 1.65s | 17자 | 27자 | 0.630 |
| Walk | 1.24s | 12자 | 19자 | 0.632 |
| **ParkourClimb** | 1.20s | 11자 | 18자 | ★ **0.611** ← 가장 빡빡 |
| LedgeHang | 1.12s | 10자 | 16자 | 0.625 |

**한글 음절 ≈ 1.000 em**이므로, **라틴 평균 자폭 ≤ 0.611 em이면 영어 줄이 한글 최악보다 넓어질 수 없다**
⇒ **줄 수가 늘 수 없다** ⇒ **130% 보장이 영어에서 약해지지 않는다.** (배율에 무관한 부등식이다.)

**실측 대조** — `layout.py`가 보존한 **러너 실측**(12pt 기준):
```
한글 12.0 pt·자   라틴 6.8 pt·자   공백 3.0 pt·자      →  라틴/한글 = 0.567
```
공백을 섞은 실제 영어 문장은 더 낮다(6자당 공백 1 가정 시 **≈ 0.52**).

> **판정: 0.567 < 0.611 — 통과. 다만 여유가 7.2%p뿐이고 이것은 「평균」이지 「상한」이 아니다.**
> ★ 그리고 **이 실측은 UI 폰트(`LegacyRuntime.ttf`)의 값이지 말풍선 폰트의 값이 아니다.**
> §3-3 (3)대로 말풍선은 **한국어 폰트의 라틴 글리프**를 쓸 수 있고, 그 자폭은 안 재 봤다.
> ⇒ **실기 확인 1건 필요**: 영어 빌드에서 `ParkourClimb` 최장 후보(18자)를 띄우고 **줄 수**를 센다.
> **2줄이면 통과, 3줄이면 이 절의 결론을 폐기한다.** (`design-art`가 맞춰 둔 만화 레터링이 걸린 자리다.)

## 4-3. 노출 시간이 상태 지속보다 길어지는가 — **아니다. 오히려 짧아진다**

`MaxVisibleSecondsFor`도 `ReadingSeconds`를 쓰므로 **영어 대사는 같은 글자 수의 한국어보다 짧게 떠 있는다.**
`DialogueKind.cs`가 그것을 **결함이 아니라고 미리 못박아 두었다** — *"라틴 17자는 한글 10자보다 빨리 읽힌다.
**「영어가 너무 빨리 사라진다」고 되돌리지 마라.**"* **동의한다.**

**알약(부채꼴 힌트/안내)은 게이트에 매이지 않는다** — `OnboardingHintSeconds = 4.5초`를 스스로 산다.
`design-narrative` §2-5 추천 A의 영어 대응(`Right-click your buddy to open the menu`, 38자)의 가독예산은
`0.28 + 38 × 0.0472 = 2.074초` ⇒ **4.5초에 2.43초가 남는다.** 한국어 21자(1.855초)와 거의 같다.
★ **알약 문안은 영어에서 제약이 아니다.**

## 4-4. ★ 남아 있는 게이트 부채 — 영어 문안 예산은 **한 번 더 줄어들 수 있다**

`design-narrative`가 영어 풀을 재창작할 때 **오른쪽 열(마진 0.18)을 기준으로 쓰는 편이 안전하다.**
§7-3(팝인 마진)이 도입되면 예산이 한 번 더 조이고, 그때 **`Whoa, that's high`(17자, ParkourClimb)가 탈락**한다.
**한국어는 세 조건 전부에서 탈락 0줄이다** — 이 비대칭 자체가 L0의 논거였다.

## 4-5. 부채꼴 이름표 — **영어 길이에 구조적으로 안전하다**(검산 붙임)

두 배치 모드 각각을 확인했다.

**(가) 부채꼴(정상)**: `HoverLabelCenterPoints`가 **지지 함수 논증**으로 보장한다 —
*"알약의 모든 점이 `ring` 밖에 있다 … **알약이 아무리 넓어져도 형제를 물 수 없다**."* **폭 무관.**

**(나) 세로 일렬 폴백**: 알약을 **화면 안쪽으로** 민다(`dir = 원점이 왼쪽 반이면 +1`).
클램프가 무는 조건을 풀면
```
labelW > 화면폭/2 − 38pt      (d/2=22, 간격 8, 화면 여백 8)
```
화면 640pt(가장 좁은 상정)에서도 **282pt**가 필요하다. 영어 최장 후보(`Today's Tasks` ≈ **79pt**: 10pt 캡션
자폭 ≈ 5pt × 13자 + 패딩 14pt)의 **3.5배**다. ⇒ **안전.**

★ **단 하나 걸리는 것은 §3-2의 「굽는 순간 1회」다.** `_nameWidths`가 한국어 폭인 채로 글자만 영어가 되면
알약이 **글자보다 좁아진다.** ⇒ **재시작 후 적용**이면 이 문제 자체가 없다.
