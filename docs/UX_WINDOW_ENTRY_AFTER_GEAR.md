## 1-2. ★★★ 톱니를 지우면 무엇이 끊기는가 — 상태 전수표

톱니의 진짜 역할은 「창 여는 버튼」이 아니다. `Platform/UserSurfaceSummonPolicy.cs`가 클래스 문서 첫 줄에
그것을 적어 두었다:

> **"등급 1을 끄는 유일한 스위치 = `AppSettingsModel.AutoHideOnFullscreen` → 유일한 조작 지점 = 설정창 [일반]
> → 그 설정창은 `ArePanelsSuppressed`이면 그 프레임에 스스로 닫힌다"**
> **"즉 등급 1이 켜져 있는 동안 등급 1을 끄는 방법이 앱 안에 하나도 없었다."**

그 루프를 여는 열쇠가 **톱니 1클릭**이고, 그래서 톱니만 `ArePanelsSuppressed`가 아니라 **`HidesScreenSurfaces`**를
읽도록 **일부러** 남겨졌다(`InfoGearIconWidget.cs:802-809`):

> *"(1) 등급 1의 안전판이 「복구는 톱니 1클릭」인데, 톱니를 등급 1에 넣으면 그 안전판이 **자기 자신을 지운다**.
> … **이 줄을 `ArePanelsSuppressed`로 「정리」하지 마라 — 그건 결정을 되돌리는 것이다.**"*

### 1-2-a. 축 2 단독 — 왜 ⚠️인가
X라

- **1홉.** 그리고 되돌아온 캐릭터에 우클릭하면 평소 경로가 그대로 열린다 — **잃는 기능이 0이다.**
- ①의 「열린 창을 닫는다」 분기가 이 상태에서 **구조적으로 사라진다**(→ §6 L-3 강화).
- ★ **다만 아이콘이 톱니(⚙)인 것이 이 동작과 어긋난다.** 톱니는 「설정/기계」 은유이고 지금 필요한 것은
  「되돌리기/보이기」다. **글리프·형태 판정은 `design-art`/`ux-widgets` 소관**이므로 §6 **L-11**로 올린다.
  내가 정하는 것은 **동작과 홉 수**까지다.

### (2) ⚠️ 비상 톱니가 **중앙 고정 창 뒤에 숨는 화면 폭**이 있다
축2 단독은 패널을 회수하지 않으므로 **정보창이 열린 채 비상 톱니가 뜰 수 있다.**
```
톱니 x = [W − 30 − 19.82, W − 30 + 19.82]      창 x = [(W−w)/2, (W+w)/2],  w = min(1042, max(320, W−32))
겹치지 않을 조건:  W − 49.82 ≥ (W+w)/2   ⟺   W ≥ w + 99.64

  W=1512 → 여유 185.2pt   W=1280 → 69.2pt   W=1180 → 19.2pt   W=1152 → 5.2pt   W=1142 → 0.2pt
  W=1120 → ★겹침 10.8pt   W=1074 → ★겹침 33.8pt   W=1024 → ★겹침 33.8pt
  ⇒ 손익분기 W = 1042 + 99.64 = 1141.64 pt
  ⇒ W < 1074 에서는 w = W−32 라 조건이 0 ≥ 67.64 → 폭에 무관하게 항상 겹친다
```
세로도 함께 겹쳐야 실제로 가려진다(창 상단 = `(H−h)/2`, 톱니 y = `topInset+12 .. +51.64`):
```
  H=982  메뉴바 33 → 창상단 90.0, 톱니 45.0..84.6 → 겹침 0%
  H=900  메뉴바 33 → 창상단 49.0, 톱니 45.0..84.6 → 겹침 35.64pt = 톱니의 90%
```
⇒ **가로·세로가 동시에 걸리는 화면(예: 1120×832)에서 비상 톱니가 창 뒤에 뜬다.**
창이 열려 있으면 탈출구는 이미 있으므로 **잠금은 아니다.** 다만 **§1-3-(다)의 가림 미판정**이
톱니에도 그대로 적용되어(`IconScreenRect.Contains(cursor)`만 본다, `:1443`·`:1670`)
**보이지 않는 톱니가 클릭을 먹는다.** ⇒ **W-3의 범위에 톱니를 포함시킨다.**

### (3) ⚠️ 비상 톱니는 **항상 흐리게** 그려진다
`IsDimmedForUserHide => _agent.IsUserHiddenOnly && !_highlighted && !_dragging` (`:510`)이고
알파는 `userHidden ? UserHiddenAlpha(0.78) : IdleAlpha` (`:1348`)다.
(B′)에서 톱니가 존재하는 조건이 **정확히 `IsUserHiddenOnly`**이므로 ⇒ **비상 톱니의 평상 알파는 항상 0.78이다.**
0.80(평상) → 0.78은 미미하지만, **「흐림」이 원래 뜻하던 것은 「지금은 부차적 상태」**였다.
(B′)에서 이 아이콘은 **화면에 남은 유일한 것**이다. ⇒ **「흐림」의 뜻이 정반대가 된다.**
`InfoGearHaloContrastTests`가 이 상수를 읽어 대비를 검사하므로 **값을 바꾸면 그 테스트가 함께 따라온다**
(하드코딩이 아니다 — 안전하다). ⇒ **`design-art` 판정 항목**(§6 L-11에 합침).

## 1-8-3. ★ 내 소관에서 나온 **신규 이음매 1건** — 창이 열릴 때 반응 대사가 창 뒤에 남는다


그리고 §2-2에서 계산했듯 **화면 세로 922.3pt 미만에서는 바닥에 선 캐릭터조차 창에 걸린다.**

  (`CharacterInfoWindow.cs:834` *"정리 책임을 여는 쪽 한 곳에만 둔다"* — **이미 이 파일의 관례다**).
⇒ §6 **L-12**.

# 2. 창 헤더 · 배치 규칙

## 2-1. ★ 「창이 톱니 위치를 기준으로 뜬다」는 전제는 **큰 창에 대해 거짓이다**

브리프가 *"창이 톱니 위치를 기준으로 뜨던 규칙이 있으면 캐릭터 기준으로 바뀐다"*고 가정했는데,
**소스에는 그런 규칙이 없다.** 근거를 들어 반박한다.

| 표면 | 배치 규칙 | 소스 |
|---|---|---|
| **정보창** 1042×802 | **화면 중앙 고정.** 열 때마다 중앙으로 리셋 | `CharacterInfoWindow.cs:1233-1234` `anchorMin=anchorMax=pivot=(0.5,0.5); anchoredPosition = Vector2.zero;` + `:800` `ResetPanelToCenter()` |
| **설정창** 720×560 | **화면 중앙 고정** | `SettingsWindow.cs:962-963` (동일 형태) |
| **상점** | 정보창 4번째 탭 — 자기 배치가 없다 | `CharacterInfoWindow.Tabs.cs:98` |
| 팝오버 3종 | **앵커(부채꼴 버튼) 상대** | `PopoverPanel.cs:425-465` |
| 부채꼴 | 톱니 상대 (→ 캐릭터 상대) | `ux-widgets` 소관 |

⇒ **큰 창 세 개는 톱니가 사라져도 좌표가 한 픽셀도 안 바뀐다.**
바뀌는 것은 팝오버 3종뿐이고, 그쪽은 `Open()`이 받은 사각형에서 **화면 안쪽으로 눕히고 마지막에 여백
12pt로 클램프**하므로(`PopoverPanel.cs:421-465`, 상·하 인셋은 `ReservedTopBarProbe`/`ReservedEdgeProbe`)
**앵커가 어디로 옮겨가든 화면 밖으로 나가지 않는다.** 새 규칙이 필요 없다.

## 2-2. ★ 진짜 배치 문제는 반대 방향이다 — **중앙 고정 창이 캐릭터를 덮는다**

톱니는 이 문제를 **구조적으로** 피하고 있었다. 톱니 기본 중심 x = `화면폭 − 30`, 히트 반지름 19.82pt이고
정보창은 폭 1042 중앙 고정이므로:
```
화면폭 1512 : 창 x 235..1277 · 톱니 x 1462..1502  →  185pt 여유, 겹치지 않는다
화면폭 1280 : 창 x 119..1161 · 톱니 x 1230..1270  →   69pt 여유, 겹치지 않는다
```
**캐릭터에는 그런 보장이 없다.** 캐릭터는 바닥과 남의 창 턱 위를 걸어 다닌다.

**바닥에 선 캐릭터 vs 중앙 고정 정보창** (`h = min(802, max(320, H−32))`, 창 하단 `y = (H−h)/2`)
```
화면세로H  창높이h  창하단y   캐릭터머리y(배율0.75=60.1pt)  겹침(pt)  머리 가려짐
  1080      802    139.0              60.1                 0.0        0.0%
   982      802     90.0              60.1                 0.0        0.0%    ← 저장소 실측 화면
   962      802     80.0              60.1                 0.0        0.0%
   922      802     60.0              60.1                 0.1        0.2%    ← 손익분기
   900      802     49.0              60.1                11.1       18.5%    ← MacBook Air 13" 기본
   864      802     31.0              60.1                29.1       48.5%
   800      768     16.0              60.1                44.1       73.4%
   768      736     16.0              60.1                44.1       73.4%

⇒ 배율 0.75(기본, 신장 60.1pt) → 완전히 안 겹치려면 화면 세로 ≥ 922.3 pt
⇒ 배율 1.00(최대, 신장 80.2pt) → 완전히 안 겹치려면 화면 세로 ≥ 962.4 pt
```
```
     화면 세로 900 (MacBook Air 13" 기본 배율)
   ┌───────────────────────────────────────────────┐ y=900
   │                                               │
   │        ┌───────────────────────────┐          │ y=851  창 상단
   │        │   정보창 1042 × 802        │          │
   │        │   (화면 중앙 고정)          │          │
   │        │                           │          │
   │        └───────────────────────────┘          │ y= 49  창 하단
   │            ╷  ← 캐릭터 머리 y=60.1 (11.1pt 가려짐 = 18.5%)
   │           ／＼                                 │
   └──────────────────────────────────────────────┘ y=  0  바닥
        우클릭 가능한 부분: 다리 49pt (표적 세로 68.07 중 72%)
```

**판정**: 화면 세로 922pt 이상이면 무시해도 되고, 900에서는 **다리로 우클릭이 가능하므로 치명적이지 않다.**
768에서는 세로 16pt만 남아 **사실상 불가능**하다 — 그 화면에서는 창을 [✕]로 먼저 닫아야 한다.

**⇒ 새 규칙은 필요 없다. 필요한 것은 「창이 열려 있으면 창이 이긴다」는 명시적 소유권**(§1-6 W-3)**과,
창을 닫지 않고도 창을 옮길 수 있다는 사실의 발견 가능성**이다(창은 이미 드래그 가능하다 — `_draggingPanel`).

## 3-3. 창이 열린 상태에서 우클릭을 또 하면?

현행 톱니 규칙(`InfoGearIconWidget.ActivateClick`)은 **3단 우선순위**다:
```
① 정보창이 열려 있다      → 그 창을 닫는다        (":1581  톱니 재클릭(창 닫기)")
② 부채꼴이 펼쳐져 있다     → 접는다                (":1587  토글 닫기")
③ 그 외                  → 허가 + 회전 + 펼침      (":1601-1603")
```
그리고 `:1578` 주변 주석이 ①의 이유를 적어 두었다 — *"창이 없어야 다음 클릭이 평소처럼 부채꼴을 편다."*

**우클릭으로 옮길 때의 문제**: ①이 성립하려면 그 우클릭이 **캐릭터에 도달해야 하는데,
정보창이 캐릭터를 덮고 있으면 도달하지 않는다**(§2-2 · §1-3-다). 즉 **같은 규칙을 그대로 옮기면
「가려지지 않은 경우에만 작동하는 토글」**이 된다 — 이 저장소가 싫어하는 형태(*"실패한 측정과 성공한 측정이
똑같이 생겼다"*의 UI 판)다.

**권고 — 3단을 2단으로 줄인다.**
```
① 부채꼴이 펼쳐져 있다  → 접는다
② 그 외                → (배타 규칙이 열린 창을 알아서 닫는다) 허가 + 펼침
```
근거: `ExclusiveSurfaces.CloseAllExcept`가 **이미** 「부채꼴을 펼치면 정보창·설정창·팝오버가 닫힌다」를
보장한다. 그러면 ①(창 닫기)은 **중복**이고, 중복인 채로 두면 위의 「가려짐」 조건부 동작이 남는다.
**닫기 전용 경로는 [✕]와 ESC가 이미 갖고 있다**(창의 유일한 탈출구로 이미 못박힌 것).
⇒ **신규 코드 0 · 규칙 1개 삭제.** 리더 판정 항목 §6 L-3.

# 4. 3열 브라스 아카이브 레이아웃 × 새 장비 재질색 — **배치와 위계만**

> 대비 판정은 `design-art`(`docs/EQUIPMENT_PALETTE.md`)가 했다. 그쪽 §8이 나에게 명시적으로 넘긴 것은
> *"아이콘 채움이 불투명 재질색이 되므로 카드 4상태 테두리와의 관계 재확인은 그쪽 판단"*이다.
> 그래서 이 절은 **좌표**와 **읽는 순서**만 본다. 색을 재판정하지 않는다.

## 4-1. 등급 크롬과 재질 채움은 **좌표상 맞닿지 않는다** — 검산

`design-art` §6-(3)이 *"충돌이 화면에 안 나오는 이유는 **자리**다 … 리본·낱말·프레임은 카드 바탕 위에만
있어 재질 채움과 **맞닿지 않는다**"*라고 주장했다. **3열 이식 좌표로 그것을 검산했고, 참이다.**

```
카드 186 × 208 (UX_EQUIPMENT_WINDOW_3COL_PORT §4-3-3)
┌──────────────────────────────────────────┐ y = 0
│▓▓▓▓▓▓▓▓ 등급 리본 h=4 (RarityColor) ▓▓▓▓▓▓│ y = −4     ← 등급 크롬

   테두리 ↔ 아이콘 영역 사이 = 카드 패딩 13pt

  리본 바닥 y=−4  ↔  아이콘 영역 상단 y=−13     간격  9 pt   ✔ 맞닿지 않는다

  아이콘 58×58 은 78pt 영역 안에 상하 10pt 여백  ⇒ 채움이 영역 경계에도 안 닿는다
```

## 4-2. 그런데 **위계**는 다르다 — 한 카드 안에 브라스 계열이 몇 개인가

`design-art` §6-(3)(b): **재질 24색 중 13색이 브라스 가족**(색상각 18.6°~47.0°, 최소 ΔE 19.4).
그리고 카드 크롬도 브라스다 — 등급 램프 4색 · `Accent #C8A15A` · `CardActionSurfaceWorn`(= `Accent` 틴트).

**착용 중인 Gold 재질 아이템(예: 왕관 `#9B7922`) 카드 한 장의 브라스 계열 요소**
```
① 등급 리본 4칸           RarityColor(전설 #FFD375)        면적 158 × 4 =    632 pt²
② 아이콘 채움             Gold #9B7922                     ≤ 58 × 58 =     3,364 pt²
③ 등급 낱말 "전설"         RarityColor                       글자
④ 주스탯 값               Accent #C8A15A                    글자
⑤ 액션 버튼 면            CardActionSurfaceWorn (Accent 틴트) 160 × 29 =    4,640 pt²
                                                     ─────────────────────────────
                                                     면 합계 ≤ 8,636 pt² = 카드의 22.3 %
```
**브라스 계열 「면」이 카드의 22.3%, 그중 셋이 서로 다른 뜻이다**(등급 / 재질 / 상태).
`design-art`가 휘도로 갈랐다 — **등급 크롬 L ≥ 0.31 · 재질 아트 L ≤ 0.2382.** 그 분리는 유효하다.

**내 판정: 배치는 통과, 위계는 통과, 다만 「읽는 순서」에 조건이 붙는다.**
```
읽는 순서(설계 의도)   ① 무슨 아이템인가(아이콘)  ② 얼마나 좋은가(리본/낱말)  ③ 지금 뭘 할 수 있나(버튼)
공간 순서(실제 좌표)   리본(맨 위) → 아이콘 → 이름/낱말 → 스탯 → 버튼(맨 아래)
```
①과 ②의 **공간 순서가 뒤집혀 있다**(리본이 아이콘보다 위다). 그런데 리본은 h=4pt이고 아이콘은 58×58이라

## 4-4. ★★ P1 — 무대 오버레이 2종이 **불투명 RT 뒤에** 그려진다

`CharacterInfoWindow.cs:1471-1502`의 `_portraitFrame` 자식 **생성 순서**(uGUI는 뒤 형제가 위에 그려진다):
```
1. Border            (AddOutline)
2. StageSheen        Stretch(전면)          sprite=VerticalGradientFill  color=PanelSheen
3. StageFloorGlow    PlaceTopLeft(0,−164, 265, 74)  sprite=RadialGlow   color=AccentSurface
4. PortraitImage     Stretch(여백 StagePadding=8)   RawImage ← RT
5. PREVIEW 라벨 / PresenceText / PortraitFallback
```
그리고 `CharacterPortraitStage.cs:528-529`:
```csharp
_camera.clearFlags = CameraClearFlags.SolidColor;
_camera.backgroundColor = ResolveBackdropColor(_config);
```
**⇒ RT는 불투명하다.** 4번이 2·3번을 덮는다.

```
   무대 265 × 238 = 63,070 pt²
   RT  249 × 222 = 55,278 pt²  (여백 8pt)

   ┌═════════════════════════════════════════┐  ← StageSheen: 여기 8pt 띠만 보인다
   ║ ┌─────────────────────────────────────┐ ║     (그리고 하필 그래디언트가 가장 밝은 곳)
   ║ │                                     │ ║
   ║ │        불투명 RenderTexture          │ ║
   ║ │        (SolidColor clear)           │ ║
   ║ │           ／＼                       │ ║
   ║ │          ／  ＼                      │ ║
   ║ ├─────────────────────────────────────┤ ║ ← y=−164 바닥 광원 상단
   ║ │  ← 바닥 광원이 여기 있지만 RT에 가림 → │ ║
   ║ └─────────────────────────────────────┘ ║
   └═════════════════════════════════════════┘

   StageSheen      전면 63,070 pt² → 보이는 것  7,792 pt² = 12.35 %
   StageFloorGlow  19,610 pt²     → 보이는 것  3,176 pt² = 16.20 %
   남는 것은 폭 8pt 테두리 띠뿐이다.
```
**그리고 두 스프라이트의 알파 분포가 이 결함을 각각 다르게 악화시킨다:**
- `RadialGlow`는 **가운데가 진하고 가장자리가 옅다** ⇒ 살아남은 16.20%는 **광원의 가장 옅은 부분**이다.
  실제로 보이는 브라스는 16.20%보다 **더 적다.**
- `VerticalGradientFill`은 **위쪽이 가장 밝다** ⇒ 살아남은 12.35% 중 상단 8pt 띠가 **가장 밝은 부분**이다.
  화면에서는 「위에서 비추는 빛」이 아니라 **액자 안쪽에 그어진 밝은 선**으로 읽힌다.

**⇒ 3COL_PORT §6-2가 이식의 목적으로 못박은 문장 —**
> *"인계본이 실제로 개선한 것은 … **무대를 크게·어둡게·바닥광원으로 받쳐** 인형을 전시물처럼 보이게 한 것"*

**— 그 「받침」이 화면에 12~16%만 도달한다.** 액자(265×238)와 RT 종횡비(1.122)는 제대로 이식됐지만,
**조명 2겹은 실질적으로 이식되지 않았다.**

### 이것이 §4-3 표의 의미를 뒤집는다
- **오늘 출하 상태에서는** 오버레이가 캐릭터에 닿지 않으므로 §4-3의 미달 24건은 **일어나지 않는다.**
- **§4-4를 「고치는」 순간**(오버레이를 RT 위로 올리면) **§4-3이 즉시 참이 된다.**
  특히 **흰 잉크 사용자 + 위 광원에서 재질 24색 전부 미달(2.20~2.96)** 이다.
  **머리 장비(모자·안경)가 무대 상단 10.9%~25% 구간에 있어 위 광원이 가장 진한 자리와 정확히 겹친다.**
- 바닥 광원 구간(무대 하단 31.1% = y −164..−238)에는 **발밑 그림자(83.3%)와 펫**이 있다.
  펫은 초상화에 실제로 그려진다(`AccessoryShapeBuilder.DrawPetPreview`, `PetPreviewXRatio = 0.38`)
  ⇒ **`look.pet.snail`(Wool 2.77) · `look.pet.plane`(Paper 2.77)이 종이+바닥광원에서 미달 5건에 든다.**
  장비 4슬롯(head/eyes/neck/shoulders)에는 발 슬롯이 없어 **장비는 이 구간에 없다** — 걸리는 것은 펫과 긴망토뿐.

### 내가 내는 것은 「선택지와 숫자」이고, 판정은 리더 + `design-art`다 (§6 L-5)
| 안 | 무엇 | 대가 |
|---|---|---|
| **A. 그대로 둔다** | 조명 2겹이 8pt 띠로만 산다 | 이식 목적 미달성 + **상단 8pt 밝은 선이 결함처럼 보인다.** 최소한 `StageSheen`은 **지워야** 한다(안 보이는 것을 남기면 다음 사람이 「왜 여기 있나」를 다시 조사한다) |
| **B. 오버레이를 RT 위로 올린다**(형제 순서만 바꿈) | 조명이 의도대로 산다 | **§4-3의 미달이 즉시 발생한다** — 목탄+위광원 24/24, 종이+바닥광원 5/24. **그리고 조명이 캐릭터 위에도 얹힌다** |
| **C. 조명을 RT 안(촬영장 월드)으로 옮긴다** | 조명이 **캐릭터 뒤에** 놓인다 — 물리적으로 옳다 | 새 월드 스프라이트 + 카메라 레이어 작업. 대비는 B와 **같은 값**(장비는 여전히 조명 앞에 있다) |
| **D. 알파를 낮춘다** | 미달을 피한다 | 종이+바닥광원이 3.0을 넘으려면 브라스 α ≤ 약 **0.055**(0.14의 39%). 그 정도면 **눈에 안 보인다** = A와 같아진다 |
| **E. 조명은 목탄(흰 잉크)에서만, 종이에서는 끈다** | 종이에서 0건, 목탄은 위 광원만 제거 | 두 잉크에서 무대가 **다르게 생긴다.** 다만 우리는 이미 무대 **바탕**을 잉크로 뒤집고 있으므로 규칙이 새로 생기는 것은 아니다 |

**내 권고: 지금은 A(단, `StageSheen`은 삭제)**, 그리고 B/C는 `design-art`가 §4-3 표를 보고 판정한 뒤에.
근거: **보이지 않는 것을 고치는 것보다, 보이지 않는다는 사실을 먼저 확정하는 것이 싸다.**
그리고 이 판정은 **실기 캡처 없이는 끝나지 않는다**(내 판정은 전부 좌표 계산이다 — §0-1).
