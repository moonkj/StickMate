## 0-A. 측정 방법 — 먼저 교정한다

이 문서의 모든 대비 수치는 스크래치패드의 계산기가 낸 것이고, 그 계산기는
`Tools/ContrastProbe/measure_chip.py`와 **완전히 같은** `lin/L/CR` 함수를 쓴다(방법이 갈리면
before/after 비교가 성립하지 않는다). 실행할 때마다 아래 5건으로 **먼저** 교정하고, 하나라도
어긋나면 숫자를 내지 않고 죽는다.

| 교정 항목 | 정답 | 실측 | 판정 |
|---|---|---|---|
| 흰 / 검 | 21.0000 | 21.0000 | PASS |
| 동일색(흰) | 1.0000 | 1.0000 | PASS |
| 동일색(패널 #14171C) | 1.0000 | 1.0000 | PASS |
| `#767676` / 흰 (WCAG 예제) | 4.5422 | 4.5422 | PASS |
| `#000000` / `#808080` (WCAG 예제) | 5.3172 | 5.3172 | PASS |

**교정만으로는 부족하다** — 교정이 통과해도 *저장소의 색을 잘못 집어넣으면* 숫자가 거짓이 된다.
그래서 **저장소가 이미 문서에 적어 둔 값을 재현하는지**를 2차 대조로 확인했다.

| 저장소가 주석에 적어 둔 값 | 이 계산기 | 판정 |
|---|---|---|
| `ChromeButtonSurface` 대 창바탕 = 5.26 : 1 | **5.27 : 1** | 일치(양자화 1자리) |
| 그 면 위 글리프 = 5.59 : 1 | **5.60 : 1** | 일치 |
| 톱니 헤일로 회색 전 구간 최악 = 4.37 : 1 | **4.37 : 1** | 완전 일치 |
| `[착용]` 라벨 대 면 = 11.10 : 1 | **11.14 : 1** | 일치 |
| `[해제]` 라벨 대 면 = 7.14 : 1 | **7.16 : 1** | 일치 |

> ★ **이 문서에서 한 번 거짓 결과를 냈고, 그 자리를 남긴다.**
> 1차 계산에서 카드 메타 잉크를 `NonTextMuted`(#6C7480)로 넣고 **"메타 텍스트가 3.50:1로 하한
> 미달"**이라는 결론을 냈다. 틀렸다. 실제로 카드 메타는 `UiChrome.InkMeta`이고
> `Ink(InkRole.Meta, *)`는 **`TextTertiary`(#8B939F)**를 돌려준다(`UiChrome.cs` Ink 스위치의
> `default:` 가지). 정정하면 **5.33:1 / 5.73:1로 통과**다. 교정을 통과한 계산기도 **입력을 틀리면
> 거짓 실패를 낸다** — 그래서 위 2차 대조가 필요하다.

**미확인으로 남기는 것**
- 글자 폭은 전부 §42-7 모델(한글 = 폰트크기 / 공백 = 0.3× / ASCII·기호 = 0.55×)의 **추정**이다.
  macOS 내장 폰트 메트릭 기준이고, **Windows 렌더링에서 다를 수 있다.** 최종 판정은 빌드 캡처다.
- 이 문서의 색은 전부 **상수에서 계산한 값**이다. `[✕]` 수정본조차 아직 실기 캡처 검증이 안 됐다
  (리더 지시 명시). 내 신규 표면도 **실기 캡처 전까지는 예측**이다.
- 등급 4단계가 42종 중 **어느 아이템에 붙는가**는 `design-systems`의 산출물이다. 여기서는
  **표면의 계약**만 정한다.
- 가격표 · 획득량 · 임계 경계값의 **숫자**도 `design-systems`다. 예시로 쓴 `1,200` 같은 값은
  **자리 크기 검산용 더미**이고 기획 수치가 아니다.

# 1. 【실측】 탭이 4개가 되면 탭 바는 어떻게 되는가

## 1-1. 식은 코드에 있다 — 숫자를 베끼지 않는다

```
TabLabelWidth(label) = label.Length * UiChrome.FontTitle + 4      // CharacterInfoWindow.cs:2880
x_0 = RightPadX                                                    // 22
x_{i+1} = x_i + TabLabelWidth(name_i) + TabGap                     // TabGap = 22
밑줄(TabBottomLine) 오른쪽 끝 = RightPadX + RightContentWidth      // 22 + 592 = 614
```

## 1-2. 결과

| 구성 | `[장비]` | `[외형]` | `[보관함]` | `[상점]` | 마지막 끝 | **남는 폭** |
|---|---|---|---|---|---|---|
| 현재 3탭 | 22..54 | 76..108 | 130..176 | — | 176 | **438pt** |
| **4탭(신설 후)** | 22..54 | 76..108 | 130..176 | **198..230** | **230** | **384pt** |
| 참고 5탭 | 〃 | 〃 | 〃 | 〃 + `[도감]` 252..284 | 284 | 330pt |

**판정: 탭 바는 빡빡하지 않다.** 4번째 탭은 밑줄 길이의 **35%** 지점에서 끝난다.
"창이 이미 빡빡하다"는 리더의 경계는 옳지만, **그 빡빡함은 세로에 있다**(§7). 가로 탭 스트립은
지금 **65%가 비어 있다.**

## 1-3. ★ `TodoBoardPopover` 함정을 피하는 법 — 여기에는 **다른 모양**으로 있다

`TodoBoardPopover.BuildTabs()`가 걸렸던 함정은 *"닫기 칩 폭 22를 식 안에 숫자로 베낀 것"*이었다
(칩이 44가 되자 탭과 **18pt 겹침**). 탭 스트립에는 그 형태의 함정이 없다 — 폭은 전부
`TabLabelWidth()`에서 파생된다.

**여기 있는 함정은 다른 모양이다: 같은 사실이 세 곳에 적혀 있다.**

| 곳 | 지금 값 | 4탭이 되면 |
|---|---|---|
| `private enum Tab { Equipment=0, Appearance=1, Inventory=2 }` | 값 3개 | `Shop=3` 추가 |
| `private const int TabCount = 3;` | **3(직접 적은 숫자)** | 4로 **손으로** 고쳐야 함 |
| `private static readonly string[] TabNames = { "장비","외형","보관함" };` | 길이 3 | 항목 추가 |

셋 중 **둘만 고치면** 조용히 깨진다: `TabCount`만 4로 올리면 `TabNames[3]`에서
`IndexOutOfRange`, `TabNames`만 늘리면 4번째 탭이 **그려지지 않는다**(그리는 루프가 `TabCount`를
돈다). 어느 쪽도 컴파일 에러가 아니다.

**처방 (코드 구조 영향 — §9-1로 리더에게 올린다)**
```csharp
// TabNames 를 먼저 선언하고, 개수는 거기서만 나온다.
private static readonly string[] TabNames = { "장비", "외형", "보관함", "상점" };
private static readonly int TabCount = TabNames.Length;     // const -> static readonly
```
`TabCount`가 `const`가 아니게 되어도 `new Image[TabCount]` 같은 **필드 초기화자 배열 크기**는
문제없다(런타임 값이면 된다). 단 **선언 순서가 계약이 된다**(정적 필드 초기화는 텍스트 순서) —
그래서 EditMode 테스트 1건을 함께 못 박는다:

```
Assert: TabNames.Length == Enum.GetValues(typeof(Tab)).Length
Assert: 모든 Tab 값 t 에 대해 TabScreenRect((int)t).width > 0
Assert: 인접 탭 사각형이 겹치지 않는다  (i+1의 왼쪽 끝 ≥ i의 오른쪽 끝)
Assert: 마지막 탭의 오른쪽 끝 ≤ RightPadX + RightContentWidth
```
마지막 두 줄이 정확히 `TodoBoardPopover`가 못 잡았던 것이다 — **겹침을 값으로 검사한다.**
숫자(230/614)를 테스트에 베끼지 않고 **상수에서 다시 계산**한다.

# 2. 【판정】 5-6 재화 HUD — 어디에 두는가

## 2-1. 결론

> **[정보창 안 · 우측 컬럼 탭 스트립 오른쪽 끝]에 둔다. 데스크톱 상시 노출은 0이다.**
> 리더가 준 세 후보 중 **"정보창 헤더"의 부류를 채택**하되, **정확한 자리는 타이틀바가 아니라
> 탭 스트립**으로 정정한다. "톱니 근처"는 반려하고, "노출 안 함"도 반려한다.

## 2-2. ★ "톱니 근처" 반려 — 근거 4건, 전부 측정값

### (1) 이 앱이 가진 임의-배경 가독 기법은 **글자 하한에 못 미친다**

톱니 아이콘은 `유저의 임의의 데스크톱` 위에 맨몸으로 놓인 유일한 표면이고, 그래서
`ResolveHaloColor`가 **잉크의 역상 헤일로**를 깐다. 그 보장치를 회색 0~255 전 구간에서 다시 쟀다:

| 잉크 | 헤일로 | 회색 전 구간 **최악** `max(CR(잉크,bg), CR(헤일로,bg))` | 최악 배경 | 비텍스트 3.00 | **텍스트 4.50** |
|---|---|---|---|---|---|
| 검정 | `#F2F4F7` | **4.37 : 1** | 회색 114 | 통과 | **미달** |
| 캐릭터 잉크 `#0B1016` | `#F2F4F7` | **4.18 : 1** | 회색 117 | 통과 | **미달** |

이 4.37이라는 값은 저장소가 주석에 스스로 적어 둔 값과 **소수 둘째 자리까지 같다**(§0-A 2차 대조).
톱니는 **아이콘**이라 `MinNonTextContrast` 3.00을 적용받아 46% 여유로 통과한다. **숫자는 글자다.**
`UiChrome.MinTextContrast` = 4.50을 적용받고, **3.1% 모자란다**(4.37 / 4.50 = 0.971).

그리고 **회색 축은 쉬운 축이다.** 실제 바탕화면은 사진이라 "배경 휘도" 자체가 한 값이 아니다.
숫자 글리프 하나가 밝은 하늘과 어두운 산 위에 동시에 걸릴 수 있다.

### (2) 헤일로를 숫자에 적용하는 것은 **형태상 불가능에 가깝다** (저장소가 이미 한 번 증명했다)

```
HaloWidth = StrokeWidthPoints(1.7) × HaloWidthFactor(2.2) = 3.74pt
```
2026-09-01에 **작은 기어를 통째로 버린** 이유가 정확히 이것이다 — 그 기어의 이 골이 1.68pt라
`1.68 < 3.74`로 헤일로 한 겹도 못 넣었다(가능한 최대 배율 0.99배). 숫자 글리프의 속공간
(`0`·`6`·`8`·`9`의 구멍)은 `FontCaption 10`에서 그와 같은 자릿수의 폭이다.
**정확한 속공간 폭은 미확인**(Unity 내장 폰트 메트릭을 이 머신에서 잴 수 없다) — 그러나
**같은 산술이 이 저장소에서 이미 한 형태를 죽였다**는 사실은 측정값이다.

### (3) 클릭을 받는 사각형이 넓어진다 = **비침해 원칙 2를 직접 깎는다**

지금 화면 전체에서 클릭을 흡수하는 것은 톱니의 히트 사각형 하나뿐이다
(`VisualRadius = 13.8 + 1.02 = 14.82` → 지름 **29.64pt**, `HitPadding 5pt`를 더해 약 **39.6pt** 정사각).
숫자를 붙이면 그 사각형이 함께 커진다. `999,999`는 `FontCaption 10`에서 **38.5pt** 폭
(+ 글리프 12 + 간격 4 = **54.5pt**)이므로 폭이 **39.6 → 94.1pt, +138%**가 된다.
톱니는 **드래그로 옮겨지고 위치가 저장된다**(`UiLayoutModel.GearCenterPoints`) — 그 사각형이
따라 움직이고 화면 클램프도 함께 커진다. **100% 관통이던 화면에 뚫는 구멍을 2.4배로 넓히는 설계다.**

### (4) 상시 잔액은 **결제 압박 HUD의 형태 그 자체**다

`design-systems`가 이미 확정한 것: *"결제는 **시간 단축** 역할이다. 재화만으로 전 등급 도달이
가능해야 한다(페이투윈 차단)."* 바탕화면 구석에 24시간 떠 있는 잔액은 **아무 문을 열지 않는다**
— 톱니는 유일한 진입점이라 상주가 정당하지만, 잔액은 **문이 아니라 상태**다.
얻는 것 없이 "너는 N밖에 없고 저건 M이다"를 하루 종일 말한다.

> **톱니는 문이라서 상주한다. 잔액은 문이 아니다.** 이 한 줄이 반려 사유의 요약이다.

## 2-3. "노출 안 함"도 반려 — 이 저장소의 §43 규칙에 걸린다

상점에 가격표가 있는데 잔액이 어디에도 없으면, `[구매]` 버튼의 활성/비활성이 **이유 없는 상태**가
된다. 이 저장소는 그것을 이미 결함으로 규정했다(§43 *"비활성 사유의 두 종류 분리"*,
`InkMeta`가 비활성일 때도 안 흐려지는 이유: *"비활성 행에서 가장 중요한 글자는 '왜 못 쓰는가'를
말하는 그 한 줄이다"*). 잔액을 감추면 **그 한 줄을 쓸 수가 없다.**

## 2-4. 왜 타이틀바가 아니라 탭 스트립인가 (같은 "창 안"인데 자리를 정정한다)

| 후보 | 이웃 | 무엇으로 읽히는가 | 판정 |
|---|---|---|---|

**"5번째 탭으로 오해되지 않는가" — 숫자로 답한다.**

## 2-6. ★ "동전"이 잠정 명칭인 것에 대한 설계상의 답

**표면에서 그 낱말을 쓰지 않는다.** 잔액도 가격 버튼도 **[글리프 + 숫자]**이고, `동전`이라는
낱말은 **문장 안에서만** 나온다(상세 패널 안내문). 그래서 이름이 바뀌면 고칠 곳이
`CurrencyName` 상수 **한 곳**이다.
반대 설계(버튼 라벨 `1,200 동전`)를 골랐다면 이름 변경이 **카드 24장 × 4상태**에 걸렸을 것이다.

> 실루엣으로 감추는 것과 **의도적으로 반대**다. 상점의 일은 상품을 보여 주는 것이고,
> 그 차이가 두 탭이 같은 24장을 놓고도 서로 다른 화면인 이유다.
> **`[장비]` 탭의 `???` 규칙은 한 글자도 건드리지 않는다.**

> 된다. 값이 없으면 숫자가 아니라 `가격 미정`이다.

> ★ **S5는 이 저장소의 사실에서 나온다.** `ItemCatalog.cs`가 스스로 적어 둔 문장:
> *"결제 백엔드가 없다(스토어/영수증 검증/복원 어느 것도 이 프로젝트에 없다)."*
> 그래서 `스토어` 버튼은 **지금 켜면 안 된다** — 누르면 아무 일도 안 나는 버튼은 이 앱이
> "최악의 형태"라고 부르는 패턴이다. S5 ↔ S6 전환은 **불리언 하나**(`StoreLinkAvailable`)로 하고,
> S5의 안내문은 §43-1-④가 확정한 가족 어법을 그대로 쓴다.

## 3-4. 카드 하단 버튼 — 면을 **규칙으로** 띄운다 (오늘 밤 `[✕]` 함정 회피)

`UiChrome.ControlFaceOnSurface(backdrop)`를 그대로 호출해 얻는 값이다(손으로 고른 색 아님):

| 바탕 | `ControlFaceOnSurface` 결과 | 면 대 바탕 | 잉크 | 잉크 대 면 |
|---|---|---|---|---|
| `CardSurface #1B1F26` (S1/S2/S3) | **`#838689`** | **4.51 : 1** | `#0B1016` | **5.22 : 1** |
| `CardSurfaceMuted #15181E` (S4~S7) | **`#848589`** | **4.82 : 1** | `#0B1016` | **5.18 : 1** |

두 값 모두 `ControlFaceContrastTarget 3.60` / `ControlInkContrastTarget 5.175`를 **동시에** 넘는다.
`Flatten` 결과라 **α = 1** → 바탕화면이 비치지 않는다.

**비활성 버튼(S2~S7)의 면은 어떻게 하는가** — **면을 지우지 않는다.**
`UiChrome.ControlFaceLift 0.50` 대신 한 단 낮은 리프트로 같은 함수를 태워 얻은 면을 쓰고,
잉크는 `InkOnSurface`가 고른다. **비활성이라고 면을 없애면 오늘 밤 `[✕]`(1.00:1)와 같은 상태가
된다** — 비활성 버튼도 "여기 버튼이 있다"는 사실은 보여야 하고, **못 쓰는 이유는 메타 한 낱말과
상세 패널 한 줄이 말한다**(§43의 규칙 그대로).

## 3-5. 구매 — 되돌릴 수 없는 행동의 탈출구

```
[ ◉ 1,200 ]  ──첫 클릭──▶  [ 정말 살까요? ]  ──둘째 클릭──▶  구매 확정
                                   │
                                   ├── 3초 경과 ────────────▶ 원래 라벨로 복귀
                                   ├── 다른 카드 클릭 ──────▶ 즉시 복귀
                                   ├── 탭 전환 ────────────▶ 즉시 복귀
                                   └── 캐러셀 드래그 ───────▶ 즉시 복귀
```

| | |
|---|---|
| **목표** | 재화 소모는 되돌릴 수 없다. 1클릭으로 확정되면 안 된다 |
| **왜 팝업이 아닌가** | 이 창은 **바깥 클릭으로 안 닫힌다**(사용자 지시). 그 위에 확인 팝업을 얹으면 **탈출구를 하나 더 설계·검증해야 하고**, 오늘 밤 정확히 그 자리(`[✕]` 면 1.00:1)가 무너졌다. 2단 버튼은 **새 표면이 0개**이고 탈출이 "아무것도 안 하기"다 |
| **탈출구 소요 시간** | 0초(가만히 두면 3초 뒤 자동 복귀) / 즉시(다른 곳 클릭) — 리더 기준 "1초 내 해제" 충족 |
| **문구 폭** | `정말 살까요?` = 58.5pt / 139pt ✔ |
| **접근성** | 라벨이 바뀌므로 **글자를 읽는 사람에게도** 상태 변화가 전달된다(색만 바뀌는 안 반려) |

**구매 확정 순간에 일어나는 일 (같은 프레임)**

1. 잔액 표시가 **즉시** 감소한다 — 애니메이션으로 늦추지 않는다. *숫자가 줄지 않으면 안 산 것이다.*
2. 카드가 S1 → S3(`보유 중`)로 바뀐다. 자물쇠 없음, 이름 그대로.
3. 상세 패널 한 줄: `{이름}{을/를} 얻었어요. [장비] 탭에서 입힐 수 있어요.`
   조사는 `KoreanParticle.Objective(name)`가 만든다 — **손으로 적지 않는다.**
4. 섹션 헤더 카운터가 `보유 2 / 6` → `보유 3 / 6`으로 바뀐다.
5. `[장비]` 탭의 **같은 자리 카드**가 `???` → 실명 + `[착용]` 활성이 된다.

> ★ 이 5개가 **한 프레임에 함께** 일어나야 한다. 하나라도 늦으면 화면이 서로 다른 이야기를 한다
> (원칙 1의 UI판). `RefreshAll()`이 이미 필요한 모든 순간에 불리므로 **새 갱신 경로를 만들지 않는다.**

## 3-6. `[장비]` 탭 쪽 변화 — 최소 1건

상점에서 살 수 있는 아이템이 `[장비]` 탭에서는 지금 `???` + `LV.n`으로만 보인다. 살 수 있다는
사실을 어디서도 알 수 없다. **메타 한 낱말만 바꾼다.**

| 조건 | `[장비]` 메타(41pt) | 하단 버튼 | 상세 패널 |
|---|---|---|---|
| 레벨 잠금 | `LV.20` (변경 없음) | `잠김` (변경 없음) | 변경 없음 |
| **상점에서 살 수 있음** | **`상점`** | `잠김` (변경 없음) | `[상점] 탭에서 얻을 수 있어요.` |

**새 컨트롤을 만들지 않는다** — 탭 이동은 이미 탭 스트립이 한다. 상세 패널의 한 줄이 길을 알려 줄 뿐이다.

# 4. 【확정】 등급 4단계 — 카드에서 어떻게 구분하는가

## 4-1. 먼저 실측: **카드에 남은 채널이 없다**

```
카드 161 × 108  (CardWidth × CardHeight)
 y   0 ─┬─ 상단 여백 8
    -8  ├─ 썸네일 139 × 54   (x 11..150)      ← 안쪽에 아이콘 44×44가 정중앙(x 47.5..91.5)
   -62  ├─ 간격 2
   -64  ├─ 이름 90pt + 간격 8 + 메타 41pt      (x 11..101 / 109..150)
   -78  ├─ 간격 2
   -80  ├─ [착용]/[해제] 버튼 139 × 22
  -102  ├─ 하단 여백 6
  -108  ┴
```
**세로는 108pt가 정확히 꽉 차 있다.** 새 줄을 넣을 자리가 0pt다.
그리고 기존 채널은 전부 다른 뜻이 붙어 있다:

| 채널 | 이미 말하는 것 |
|---|---|
| 카드 면 | 보유 / 미보유 |
| 썸네일 면 | 착용 중 / 보통 / 잠김 |
| 테두리 | **선택 > 호버 > 착용 중 > 기본** (4파전) |
| 메타 41pt | `착용 중` / `보유` / `LV.20` |
| 아이콘 색 | 잠김(회색) / 소재색 |
| 자물쇠 배지(우하단) | 미보유 |
| 하단 버튼 | 보유 · 착용 여부 |

**남은 것은 썸네일의 빈 면뿐이다** — 139 × 54 = 7,506pt² 중 아이콘이 1,936pt²(**25.8%**)만 쓴다.
자물쇠는 우하단이고, **좌상단은 완전히 비어 있다.**

## 4-2. 확정 — 썸네일 좌상단 **등급 배지**

```
썸네일 (139 × 54) 로컬 좌표
┌───────────────────────────────────────────────────────┐  y 0
│ ┌──────┐                                              │
│ │ 전설 │  ← 32 × 16, RadiusBadge 5, 불투명 등급색 면   │  배지 y -4 .. -20
│ └──────┘             ┌────────────┐                   │  x 6 .. 38
│                      │  아이콘 44 │                   │  아이콘 x 47.5 .. 91.5
│                      │            │                   │      → 배지와 9.5pt 간격 ✔
│                      └────────────┘             ┌───┐ │
└──────────────────────────────────────────────── │🔒 │─┘  자물쇠 18×17 (우하단, 기존)
                                                  └───┘
```

| 항목 | 상수(제안) | 값 | 배율 검산 ×1.25/1.5/1.75/2.0 |
|---|---|---|---|
| 배지 폭 | `RarityBadgeWidth` | **32** | 40 / 48 / 56 / 64 ✔ |
| 배지 높이 | `RarityBadgeHeight` | **16** | 20 / 24 / 28 / 32 ✔ |
| 배지 x, y | (썸네일 로컬) | 6, −4 | 7.5/9/10.5/12 · 5/6/7/8 ✔ |
| 반지름 | `UiChrome.RadiusBadge` | 5 (기존) | — |
| 글자 | `UiChrome.FontCaption` 10, bold, 중앙 | 낱말 20pt / 상자 32pt ✔ | — |

## 4-3. ★ 왜 "색만"이 아니라 **불투명 면 + 낱말**인가 — 반려된 안이 숫자로 진다

썸네일 바탕은 **3종**이다(`CardSurfaceMuted #15181E` / 착용중 `#243143` / 잠김 `#101318`).
등급색 **글자만** 얹는 안을 그 3종 전부에서 재면:

| 등급 | 색 | 기본 | **착용중** | 잠김 | 최악 | 텍스트 하한 4.50 |
|---|---|---|---|---|---|---|
| 일반 | `#8B939F` | 5.73 | **4.24** | 6.00 | **4.24** | **FAIL** |
| 희귀 | `#3EB3A9` | 6.96 | 5.16 | 7.29 | 5.16 | PASS |
| 영웅 | `#C39BF5` | 7.90 | 5.85 | 8.27 | 5.85 | PASS |
| 전설 | `#F0B84A` | 9.87 | 7.31 | 10.33 | 7.31 | PASS |

**`일반`이 착용 중인 카드 위에서 4.24로 떨어져 하한 미달이다.** 4개 중 1개만 무너지는,
이 저장소가 여러 번 당한 바로 그 모양이다(옛 `TabInactive`: 패널 4.52 ✔ / 카드 4.15 ✘).

**불투명 면 + 어두운 잉크로 바꾸면 두 지표가 동시에 여유로 통과한다**:

| 등급 | 면 | 면 대 썸네일 3종 (최악) | 하한 3.00 | 잉크 | 잉크 대 면 | 하한 4.50 |
|---|---|---|---|---|---|---|
| 일반 | **`#8B939F`** | **4.24** (5.73 / 4.24 / 6.00) | PASS | `#0B1016` | **6.16** | PASS |
| 희귀 | **`#3EB3A9`** | **5.16** (6.96 / 5.16 / 7.29) | PASS | `#0B1016` | **7.48** | PASS |
| 영웅 | **`#C39BF5`** | **5.85** (7.90 / 5.85 / 8.27) | PASS | `#0B1016` | **8.48** | PASS |
| 전설 | **`#F0B84A`** | **7.31** (9.87 / 7.31 / 10.33) | PASS | `#0B1016` | **10.60** | PASS |

같은 `#8B939F`인데 왜 한쪽은 FAIL이고 한쪽은 PASS인가 — **적용되는 하한이 다르기 때문이다.**
글자로 쓰면 `MinTextContrast 4.50`을 받고, **면(그래픽)으로 쓰면 `MinNonTextContrast 3.00`**을
받는다. 그리고 그 면 위의 글자는 이제 **바탕이 딱 하나**(등급색)라 6.16~10.60으로 크게 뜬다.
**변덕스러운 바탕 3종을 면 하나로 덮어 버리는 것**이 이 설계의 요점이다.

## 4-4. 램프의 세 가지 계약

**(a) 낱말이 1차 채널이다.** 배지 안에는 항상 `일반/희귀/영웅/전설`이 적힌다.
색을 전혀 못 보는 사람도 **읽는다.** 색은 스캔 속도를 위한 2차 채널이다.

**(b) 휘도가 등급 순서와 같은 방향이다.** 어두운 UI에서 밝을수록 눈에 띈다 — 등급이 오르는데
덜 띄면 **그림이 낱말과 다른 말을 한다**(원칙 1의 그래픽판).

| 등급 | 색 | 상대휘도 L | 창바탕 대비 | 흑백 근사 |
|---|---|---|---|---|
| 일반 | `#8B939F` | 0.2886 | 5.79 : 1 | 145 |
| 희귀 | `#3EB3A9` | 0.3613 ↑ | 7.04 : 1 | 161 |
| 영웅 | `#C39BF5` | 0.4164 ↑ | 7.98 : 1 | 171 |
| 전설 | `#F0B84A` | 0.5330 ↑ | 9.97 : 1 | 192 |

**흑백으로 눌러도 순서가 유지된다**(145 < 161 < 171 < 192) — 전색맹에서도 서열이 남는다.

**(c) `Accent`(#5DA1F5)와 충돌하지 않는다.** 이 앱에서 강조 파랑은 이미 **"지금 걸치고 있다"**를
뜻한다(`CardBorderWorn` / 착용 썸네일 wash / 메타 `착용 중` / EXP 게이지 / 섹션 도트).
장르 관례대로 `희귀 = 파랑`을 쓰면 **착용 중인 희귀 아이템 카드가 온통 같은 파랑**이 된다.
그래서 희귀를 **청록 `#3EB3A9`**으로 옮겼다.

| 등급 | Accent와의 최대 채널차 | 판정 |
|---|---|---|
| 일반 | 86 | 구분됨 |
| 희귀 | **76** | 구분됨 |
| 영웅 | 102 | 구분됨 |
| 전설 | 171 | 구분됨 |

> **신규 `UiChrome` 상수 4개**: `RarityCommon #8B939F` / `RarityRare #3EB3A9` /
> `RarityEpic #C39BF5` / `RarityLegend #F0B84A`.
> **`TextTertiary`를 면으로 재사용하지 않는다** — 값이 같아도(#8B939F) 역할이 다르면 이름이
> 달라야 한다. 잉크 상수를 면으로 쓰기 시작하면 잉크 서열을 조정할 때 면이 조용히 따라 움직인다.
> (`UiInkHierarchyTests`가 소스를 훑는 규율과 같은 취지다.)

## 4-5. `[장비]` 탭에도 같은 배지가 붙는가 — **붙는다**

같은 카드 오브젝트이므로 배지는 **탭과 무관하게** 그려진다. 내 옷의 등급을 `[장비]`에서 못 보고
`[상점]`에서만 보는 것은 말이 안 된다. 잠긴 카드(`[장비]`의 `???`)에도 **배지는 붙는다** —
*"무엇을 향해 모으고 있는가"*가 잠금 게이트의 동기 그 자체다. 이름만 감추고 등급은 감추지 않는다.

# 5. 【확정】 스탯 4종 + 임계 3단계

## 5-1. 어디에 — 좌측 컬럼 (판정 근거)

스탯은 **장비를 고르는 동안** 보여야 한다. 결정의 순간이 *"이 모자로 바꾸면 집중력이 어떻게
되지?"*이기 때문이다. 그래서:

- **우측(탭 안)은 안 된다** — 카드와 같은 열에 넣으면 카드가 밀리고, 탭을 바꾸면 사라진다.
- **좌측 컬럼은 `body` 직하라 탭의 것이 아니다**(`ApplyTabVisibility`가 건드리지 않는다).
  네 탭 전부에서 그대로 보인다. 그리고 바로 위에 **초상화(지금 입은 모습)**와 **EXP 게이지**가 있다
  — 스탯은 그 가족이다.

## 5-3. 세그먼트 3칸 = 임계 3단계 — **상태는 2개가 아니라 3개다**

> ★ `design-systems`에게서 직접 넘어온 요구(§14-2):
> *"세트 완성 효과는 영구 해금이 아니다 … **임계 영구 해금과 반대 규칙이므로 UI가 둘을
> 시각적으로 구분해야 한다(→ ux-designer)**"*.
> 그리고 그 규칙에는 내가 처음에 못 본 결과가 하나 더 있다 — **임계가 영구라면, 지금 값이
> 임계 아래로 내려간 뒤에도 그 단계는 열려 있다.** 즉 *"지금 도달했는가"*와 *"한 번이라도
> 열었는가"*가 **갈라진다**. 상태를 2개(채움/빔)로 그리면 그 순간 그림이 거짓말을 한다.

**두 개의 독립된 비트를 두 개의 독립된 채널에 싣는다.**

| 상태 | 뜻 | 색 | 높이 | 창바탕 대비 | 하한 3.00 |
|---|---|---|---|---|---|
| **지금 도달** | 현재 값 ≥ 임계 | `UiChrome.Accent #5DA1F5` | **8** | **6.74 : 1** | PASS |
| **영구 보유 · 현재 미달** | 한 번 열었으나 지금은 아래 | `UiChrome.Accent #5DA1F5` | **4** | **6.74 : 1** | PASS |
| **미도달** | 한 번도 못 열었다 | `UiChrome.NonTextMuted #6C7480` | **4** | **3.80 : 1** | PASS |

```
          한 번도 못 열었다      영구 보유 · 지금은 미달        지금 도달
높이 8    ─                      ─                             ▮▮▮▮▮▮
높이 4    ▂▂▂▂▂▂(회색)          ▂▂▂▂▂▂(파랑)                 ─

예)  집중력 14 → 9로 떨어짐 (중급을 한 번 열었음)
     ▮▮▮ ▂▂▂ ▂▂▂        읽기: "지금은 초급, 중급·고급 자리는 회색이 아니라 파랑"
      초급  중급  고급          → 색이 살아 있다 = 열린 것은 안 닫혔다
```

- **색 = 한 번이라도 열었는가(영구)** / **높이 = 지금 그런가(현재)**. 두 축이 직교한다.
- 임계는 순서가 있으므로 파랑은 **항상 왼쪽부터 연속**이고 높이 8도 그 안에서 연속이다 —
  읽을 수 없는 조합(예: 회색 다음에 높이 8)이 **원리적으로 나올 수 없다.**
- **얇은 선(윤곽선)을 쓰지 않는다.** 세 상태 전부 **채운 면**이다. 1px 테두리는 배율 1에서
  물리 1픽셀이고 이 저장소가 이미 한 번 잃어 본 적이 있다(커밋 39ab690).
- 채움/빔 사이 대비는 1.77:1뿐이지만 **둘은 4pt 간격의 창바탕으로 떨어져 있어** 실제 인접 경계는
  각각 *칸 ↔ 창바탕*이고 셋 다 통과한다. 구별은 **높이 2.0배 + 색 + 오른쪽 값 숫자**의 3중 중복이다.

> ★ **왜 게이지 트랙(`TrackBackground` α0.09)을 안 쓰는가**: 그 색은 창바탕 대비 **1.28:1**이라
> 눈에 안 보이고, 무엇보다 **생 알파를 쓰면 그 화소에서 창 알파가 0.91로 내려가** 바탕화면이
> 9% 비친다. 세 상태 전부 **α=1**로 그린다.
> ★ **왜 연속 막대가 아니라 3칸인가**: 이 창에는 이미 연속 막대가 둘(STRESS/EXP) 있다.
> 임계는 **이산값**이다. 연속 막대로 그리면 "42%"로 읽힌다.

## 5-4. 델타 미리보기 (P2 — 분리 배정 가능)

**트리거는 이미 있는 상태다**: 카드를 선택하면 `_selectedSlot`/`_selectedItem`이 정해지고
상세 패널이 그 아이템을 그린다. 그 아이템이 **아직 안 입은 것**이면:

```
집중력  ▰▰▱▸▰   42▸51        ← 값 칸에 "현재▸예상", 새로 채워질 칸은 테두리만
```
- 값 칸 48pt 안에서 처리된다(`42▸51` = 38.4pt) → **레이아웃 변화 0**
- 입고 있는 것을 고르면 델타가 0이므로 **표기가 사라진다**(상태에서 파생 — 원칙 1)
- 필요 함수: `design-systems`가 `StatsIfEquipped(slot, itemIndex)` 순수 함수를 제공해야 한다.
  **없으면 이 절만 빼고 나머지는 그대로 간다.**

## 5-5. 예외 상태 — 스탯

| 상태 | 보이는 것 |
|---|---|
| 4슬롯 전부 비었음 | 값 `0`, 세그먼트 `▱▱▱` (**`—`가 아니다** — 0은 실제 값이다) |
| 스탯 데이터 미로딩 | 값 `—`, 세그먼트 전부 빈 칸. 0과 구별된다 |
| 임계 경계값 미정(`design-systems` 미확정) | 값은 그리고 **세그먼트는 전부 빈 칸**. 거짓 단계를 그리지 않는다 |
| **한 번 연 단계 아래로 값이 내려감** | 그 칸은 **파랑 · 높이 4**(영구 보유 · 현재 미달). 회색으로 되돌리면 *"닫혔다"*는 거짓말이 된다 |
| 저장 파일에 최고 도달 기록이 없음(구버전) | 최고 도달 = 현재 값으로 간주(파랑 · 높이 4가 안 생긴다). **거짓 영구 표시를 만들지 않는 쪽으로 기운다** |
| 값이 3자리 초과 | `Ellipsize` 대상 아님 — 소프트캡이 `design-systems` 책임이다. 4자리(`9999` = 26.4pt)까지 48pt 칸에 들어간다 ✔ |

# 6. 【확정】 세트 완성 여부

## 6-1. 행 스펙 — 좌측 컬럼 1행

```
┌──────┬──┬──────────────┬──┬──────────────────────────┐
│ 세트  │  │ ●●●○         │  │            넥타이만 더   │   행 높이 20
└──────┴──┴──────────────┴──┴──────────────────────────┘
  32     8   8+4+8+4+8+4+8    8         112              합계 204 / 204
             = 44
```

| 요소 | 값 | 배율 검산 |
|---|---|---|
| 라벨 `세트` | 32 (`FontBody 12`, 24pt 글자) | 40/48/56/64 ✔ |
| 도트 | 지름 **8**, 간격 4, 4개 = 44 | 10/12/14/16 ✔ |
| 상태 칸 | 112 (`FontCaption 10`, 오른쪽 정렬) | 140/168/196/224 ✔ |

**도트 순서는 슬롯 순서로 못 박는다**: `모자 → 안경 → 넥타이 → 망토`
(`EquipmentSlot.Head/Eyes/Neck/Shoulders` 값 순). **왼쪽 스탯 4행의 순서와 같다** —
`집중력(모자) / 관찰력(안경) / 매력(넥타이) / 민첩(망토)`. 두 줄이 세로로 맞춰 읽힌다.

| 도트 | 색 | 지름 | 창바탕 대비 | 판정 |
|---|---|---|---|---|
| 채움(그 슬롯이 후보 세트의 것) | `Accent #5DA1F5` | 8 | 6.74 : 1 | PASS(3.00) |
| 빔 | `NonTextMuted #6C7480` | **4** (같은 8pt 자리 중앙) | 3.80 : 1 | PASS(3.00) |

### 6-1-b. ★ 세트와 임계는 **반대 규칙**이다 — 그래서 **모양**으로 갈라 놓는다

`design-systems`가 직접 넘긴 요구다: *"세트 완성 효과는 영구 해금이 아니다 … 임계 영구 해금과
반대 규칙이므로 **UI가 둘을 시각적으로 구분해야 한다**"*. 두 줄이 좌측 컬럼에 **세로로 붙어 있으므로**
같은 모양을 쓰면 같은 규칙으로 읽힌다.

| | 스탯 세그먼트 (임계) | 세트 도트 |
|---|---|---|
| **모양** | **가로 막대** 20 × 8 (`RadiusDot 2`) | **원** 지름 8 (`UiChrome.AddCircle`) |
| **상태 수** | **3** (지금 도달 / 영구 보유·현재 미달 / 미도달) | **2** (지금 이 세트다 / 아니다) |
| **규칙** | **영구** — 한 번 열면 안 닫힌다 | **조건부** — 한 칸만 벗어도 즉시 꺼진다 |
| **"영구" 표현** | 파랑 · 높이 4 | **없다 — 원리적으로 존재할 수 없다** |
| **칸 수** | 3 (임계 3단계) | 4 (슬롯 4종) |

> **구분은 색이 아니라 모양과 개수다.** 둘 다 `Accent`를 쓰지만 하나는 **막대 3개**,
> 하나는 **원 4개**다. 그리고 세트 줄에는 **파랑 · 높이 4(= 영구)가 절대 나타나지 않는다** —
> 그 조합이 화면에 없다는 사실 자체가 "세트는 영구가 아니다"를 말한다.
> ★ 색으로 가르지 않은 이유: 세트에 다른 색을 주면 이 창의 강조색이 둘이 된다(§4-4-(c)와 같은 근거).

## 6-2. ★ 상태 문구는 **행동 상태에서만 파생된다** (원칙 1)

**문구를 먼저 쓰고 상태를 맞추지 않는다.** 아래가 확정 파생 규칙이다.

```
입력 : worn[4]  =  각 스탯 슬롯에 지금 착용된 아이템 (없으면 null)
                  setOf(item) = 그 아이템이 속한 세트 id (없으면 null)

1. 후보 세트 C = worn 4칸에서 가장 많이 등장하는 setId
   · 동수면 슬롯 순서(모자→안경→넥타이→망토)에서 먼저 나온 쪽    ← 결정론적
   · setId를 가진 착용 아이템이 하나도 없으면 C = 없음
2. n = C에 속하는 착용 슬롯 수 (0~4)
3. missing = C에 속하지 않는(또는 빈) 슬롯 목록,  m = 4 − n

문구:
   C 없음        →  "아직 세트 아님"
   m == 0        →  C에 표시 이름이 있으면  "세트 완성 · {이름}"
                    없으면(현재 상태)        "세트 완성"          ← §14-3
   m == 1        →  "{missing[0]의 슬롯 이름}만 더"        예) "넥타이만 더"
   m >= 2        →  "{m}칸 더"                             예) "2칸 더"
```

> ★ **`design-systems`의 6개 세트에는 지금 표시 이름이 없다**(A~F는 내부 식별자다).
> 그래서 **완성 문구는 `세트 완성`(43.0pt) 하나**로 확정한다. 이름이 생기면 `· {이름}`을
> 덧붙이는 형태로 확장되고, 그때 **한글 4자 이하** 제약이 걸린다(§9-7).
> 내부 식별자 `A`~`F`를 화면에 그대로 내보내지 않는다 — 유저에게 아무 뜻이 없다.

**폭 검산 (상태 칸 112pt @ `FontCaption 10`)**

| 문구 | 폭 | 판정 |
|---|---|---|
| `아직 세트 아님` | 66.0 | ✔ |
| `세트 완성` (현재 확정형) | **43.0** | ✔ |
| `세트 완성 · 도서관장` (이름이 생겼을 때의 최장 후보) | 94.5 | ✔ |
| `넥타이만 더` | 53.0 | ✔ |
| `2칸 더` / `3칸 더` | 28.5 | ✔ |

> ★ **세트 이름 길이 상한을 `design-systems`에 요구한다**: 상태 칸 112pt에서
> `세트 완성 · ` 접두(= 6한글 + 공백2 + 가운뎃점 ≈ 66.5pt)를 빼면 **세트 이름에 남는 폭은 45.5pt
> = 한글 4자**다. 5자 이상이면 말줄임이 걸린다(`UiChrome.Ellipsize`).
> **세트 이름은 4자 이하로 확정해 달라.**

> ★ **`m == 1`에서 빠진 슬롯을 이름으로 부르는 것이 이 행의 전부다.** 3/4에서 *"왜 효과가 안 켜지지"*가
> 이 기능의 최대 이탈 지점이고, `3/4`라는 분수는 그 질문에 답하지 않는다.
> (`보관함` 페이지 지시자가 `1 / 3`으로 분수처럼 읽혀 문제가 됐던 §45-9와 같은 교훈이다.)

## 6-3. 세트 완성/해제의 **연출**은 여기 없다

임계 도달·세트 완성 시 **어떤 모션/이펙트**가 나오는가는 `design-motion`이다.
표면 쪽 계약만 남긴다: **문구가 바뀌는 프레임과 연출이 시작되는 프레임이 같아야 한다.**
문구가 먼저 바뀌고 연출이 늦으면 그 사이가 원칙 1 위반 구간이다.

## 6-4. 예외 상태 — 세트

| 상태 | 보이는 것 |
|---|---|
| 4슬롯 전부 비었음 | 도트 `○○○○`, `아직 세트 아님` |
| 세트 데이터 미정의 | 도트 `○○○○`, `아직 세트 아님` (**거짓 완성 금지**) |
| 2:2 동률 | 규칙 1의 슬롯 순서로 결정 → `2칸 더` |
| 세트 완성 직후 한 칸 벗음 | 즉시 `{슬롯}만 더`로 되돌아간다. **효과도 같은 프레임에 꺼진다**(영구 해금 아님 — `design-systems` 확정) |

# 7. 【실측 + 경고】 좌측 컬럼 세로 예산 — **여기가 진짜 빡빡한 곳이다**

## 7-1. 지금 상태

| 탭 | 섹션 칸 | 창 높이 | 본문 높이 |
|---|---|---|---|
| `[장비]` | 4 | 861 | 821 |
| **`[외형]`** | **3** | **705** | **665** ← 가장 짧다 |
| `[보관함]` | 4(목록) | 861 | 821 |
| `[상점]`(신설) | 4 | 861 | 821 |

좌측 컬럼은 `body` 직하이고 `RectMask2D`가 **현재 창 높이에서** 자른다.
따라서 **모든 탭에서 보이는 좌측 깊이 = 665pt**다.

```
좌측 컬럼 현재 맨 아래  = StatsFirstRowY(-408) − 3×StatRowStep(32) − StatRowHeight(31) = -535
남는 깊이 (모든 탭 기준) = 665 − 535 = 130pt         ← 여기에 스탯 4행 + 세트 줄을 넣어야 한다
```

## 7-2. ★ 경고: 지금 이 665pt 천장을 **막는 것이 아무것도 없다**

`PanelHeightForTab()`은 **우측 컬럼의 필요만** 보고 창 높이를 정한다. 좌측 컬럼이 그보다 길어지면
**예외도 경고도 없이 화면에서 사라진다.** 이건 P0-1이 고친 결함과 **같은 종류**다
(그때는 상한 상수를 고정 예산으로 써서 176pt를 낭비했고, 지금은 좌측을 예산에서 아예 빼먹었다).
**테스트도 없다(확인함).**

## 7-3. 배치안 A — 게임 스탯을 전적 **위**로 올린다

**순서를 바꾸는 근거**: 이 창에서 **바뀌는 것**이 위로 가야 한다.
게임 스탯과 세트는 카드를 누를 때마다 바뀐다. 전적(근속/함께한 시간/…)은 안 바뀐다.

## 7-4. 남은 여유 — 전적 행 수에 따라 갈린다

| 전적 행 수 | 좌측 맨 아래 | **`[외형]` 탭 여유** | 좌측이 요구하는 창 높이 |
|---|---|---|---|
| **4행 유지** | −663 | **2pt** | 725 |
| **3행(`보유 장비` 삭제)** | −631 | **34pt** | 693 |

**2pt는 여유가 아니라 우연이다.** 한 행만 늘거나 폰트가 한 단 커지면 그 자리에서 잘린다.

## 7-5. ★ 확정 권고 — `보유 장비` 행 삭제 + `max()` 가드

**(a) `보유 장비` 행을 뺀다.** 이번 라운드에 **그 정보가 두 곳에서 더 잘 말해진다**:
- `[상점]` 각 섹션 헤더의 `보유 4 / 6` (슬롯별로 나눠서)
- `[보관함]` 탭이 이미 보유 목록 전체를 나열한다

**표시만 뺀다** — 계수 로직도 저장 필드도 건드리지 않는다(2026-09-01 `넘어진 횟수`,
2026-09-02 `격파 성공`과 완전히 같은 방침).
※ `StatCount = 4`와 `StatLabels` 길이 4가 **또 두 곳에 적힌 같은 사실**이다(§1-3과 동종).
   `StatCount`도 `StatLabels.Length`에서 파생시킨다.

**(b) `PanelHeightForTab`을 `max(우측 필요, 좌측 필요)`로 바꾼다.**

| 전적 행 | 탭 | 우측 필요 | 좌측 필요 | `max` | 오늘 값이 바뀌는가 |
|---|---|---|---|---|---|
| **3행** | 장비 | 861 | 693 | **861** | 변화 없음 |
| **3행** | **외형** | **705** | **693** | **705** | **변화 없음** |
| **3행** | 보관함 | 861 | 693 | **861** | 변화 없음 |
| **3행** | 상점 | 861 | 693 | **861** | 변화 없음 |
| (참고) 4행 | 외형 | 705 | **725** | **725** | ★ 창이 20pt 커진다 |

> ★ **이것이 (a)를 함께 권고하는 이유다.** 전적을 3행으로 줄이면 `max()` 가드가
> **오늘 단 1픽셀도 바꾸지 않는다.** P0-1이 얻은 `[외형]` 705를 그대로 지키면서,
> "좌측이 조용히 잘리는" 구멍만 영구히 막는다. **비용 0의 가드다.**
> 4행을 유지하면 같은 가드가 창을 20pt 키워 P0-1의 성과를 일부 되돌린다.

**(c) 작은 화면 검산.** `ClampPanelToScreen`은 창 높이를 `Screen.height/scale − 32`로 자른다.
1280×800(논리) 환경에서 상한은 **768** → 본문 728. 좌측 맨 아래 −631은 **그 안에 들어온다** ✔
(우측 상세 패널은 이미 그 환경에서 잘린다 — 기존 조건이고 이번 건과 무관하다).

# 10. ★ 부수 발견 — 오늘 밤의 `[✕]` 함정이 **카드에도 살아 있다**

> **이번 설계가 만든 것이 아니다. 기존 상태다.** 리더가 *"네 새 UI에 같은 함정을 만들지 마라"*고
> 지시했고, 그 함정을 피하려고 기존 면들을 재다가 발견했다. **조용히 넘기지 않고 보고한다.**

`StyleActionButton()`이 카드 하단 버튼에 칠하는 면을 `ControlFaceContrastTarget(3.60)`으로 재면:

| 상태 | 면 | 대 카드 바탕 `#1B1F26` | 하한 3.60 | 참고: 오늘 고친 `[✕]` |
|---|---|---|---|---|
| 미착용 `[착용]` | `#32353C` (`Flatten(CardBorder α0.10, CardSurface)`) | **1.35 : 1** | **미달** | 1.00 : 1 (수정 전) |
| 착용 중 `[해제]` | `#243143` (`Flatten(AccentSurface α0.14, CardSurface)`) | **1.26 : 1** | **미달** | — |
| 잠김 `[잠김]` | `#15181E` (`CardSurfaceMuted`) | **1.08 : 1** | **미달** | — |

**글리프는 잘 읽힌다**(11.14 / 7.16 / 5.73:1 — 전부 통과). 오늘 밤 `[✕]`와 **완전히 같은 모양의
결함**이다: *"고칠 것은 잉크가 아니라 면이다."* 그리고 이건 칩 2개가 아니라 **카드 24장 × 4탭**이다.

**덤 — 알파 채널**: 그 버튼의 테두리는 **생 `CardBorder`(α0.10)**를 쓴다
(`AddOutline(..., UiChrome.CardBorder, ...)`). `UiChrome`이 스스로 적어 둔 계산
`dstA' = srcA² + dstA(1−srcA) = 0.01 + 0.90 = 0.91`이 그대로 적용된다 —
**그 테두리 화소에서 유저의 바탕화면이 9% 비친다.** 카드 24장의 버튼 테두리 전부가 그렇다.

**내 신규 표면은 이 두 함정을 피한다**: 면은 전부 `ControlFaceOnSurface()`/미리 합성한 `α=1` 색이고,
생 알파를 얹는 곳이 **0곳**이다(§2-5 `#8D7035`, §4-3 등급 면, §5-3 빈 칸 `NonTextMuted` 전부 α=1).

**이건 내 배정 범위가 아니다 — 리더 판단 사항으로 올린다.**
(고치면 `Tests/PlayMode/InfoWindowSurfaceRegressionTests` 계열에 면 대비 검사 추가가 함께 필요하다.)

# 14. ★ `design-systems` 산출물과의 대조 — 정정 4건 + 반박 1건

> 대조 대상: `design/systems/ECONOMY_SPEC.md`(2026-09-02, 같은 라운드 병렬 산출).
> **위 §3 / §5 / §6 / §8 / §13은 이미 이 대조를 반영해 고쳤다.** 이 절은 **무엇이 왜 바뀌었는지**만 남긴다.
> 협업 규칙대로 **다른 담당자에게 직접 지시하지 않고 리더를 거친다.**

## 14-1. 【정정 1 · 가장 큼】 동전은 "해금"이 아니라 **"앞당기기"**다

`ECONOMY_SPEC` 4-1 채택 모델:
> 1. 요구 레벨 도달 → 상점 진열, 동전으로 **즉시** 구매 가능
> 2. 요구 레벨 도달 + **등급별 유예 시간** 경과 → **동전 없이 자동 해금**
>
> | 등급 | 가격 | 유예 |
> |---|---|---|
> | 일반 | 30동전 | 5시간 |
> | 희귀 | 70동전 | 15시간 |
> | 영웅 | 150동전 | 35시간 |
> | 전설 | 330동전 | 80시간 |

**내 초안은 이 사실을 화면 어디에도 안 그렸다.** 가격만 있는 카드는 *"동전이 유일한 길"*을 뜻하고,
그건 **경제와 다른 말을 하는 화면**이다 — 원칙 1의 정확한 위반이다.

**고친 것 (§3-3 / §3-3-b)**
- 상태를 7 → **8**로(`S3b 유예로 무료 해금`). 단 **S3와 화면에서 구별하지 않는다** —
  획득 경로를 남기면 *"기다려서 얻은 열등한 소유"*라는 없는 서열이 생긴다.
- 카드 **메타 41pt = 남은 유예**(`80시간` / `3시간` / `29분` / `곧`). 폭 검산 전부 통과.
  `3시간 뒤`(38.5)는 들어가지만 `12시간 뒤`(44.0)가 41을 넘어 **조사를 뺀 맨 기간**으로 확정.
  메타 칸을 넓히는 안은 반려 — 이름 칸(90)이 줄면 P0-5의 `리틀스틱메이트` 겹침이 재발한다.
- **상세 패널 기본 문구**로 모델을 한 번 가르친다:
  `동전으로 지금 열거나, 함께한 시간이 쌓이면 그냥 열려요.` (314.4 / 560pt)
- **부족 상태 문구가 두 문장이 됐다**: `동전이 12개 모자라요. 3시간 뒤에는 그냥 열립니다.`
  ★ `design-systems`가 스스로 적은 *"상점이 '안 됩니다'라고 말하지 않는다. **'또는 기다리세요'**라고
  말한다"*는 **UX에 온 지시**다. 둘째 문장을 빼면 상점이 벽이 되고 그 경제 설계의 요점이 사라진다.

**세이브 영향(§9-3에 추가)**: 유예를 재려면 **"요구 레벨을 넘긴 시각"**이 아이템마다 저장돼야 한다.
`함께한 시간` 기준이므로 벽시계가 아니라 누적 사용 시간 축이다.

## 14-2. 【정정 2】 임계는 **영구**다 → 세그먼트 상태가 2개가 아니라 **3개**다

`ECONOMY_SPEC`이 나에게 직접 넘긴 문장:
> *"세트 완성 효과는 영구 해금이 아니다 … 임계 영구 해금과 반대 규칙이므로
> **UI가 둘을 시각적으로 구분해야 한다(→ ux-designer, 리더 경유)**"*

넘겨받은 요구는 "세트 ↔ 임계를 구분하라"였는데, **그 안에 한 겹이 더 있었다**:
임계가 영구라면 **값이 임계 아래로 내려간 뒤에도 그 단계는 열려 있다.**
그러면 *"지금 도달했는가"*와 *"한 번이라도 열었는가"*가 갈라지고, 채움/빔 2상태로는
**둘 중 하나를 반드시 거짓으로 그린다.**

→ §5-3을 **색(영구) × 높이(현재) 두 직교 채널**로 다시 썼다. 셋 다 채운 면이고
얇은 선이 없으며(커밋 39ab690 교훈), 셋 다 비텍스트 하한 3.00을 넘는다(6.74 / 6.74 / 3.80).

→ §6-1-b에 **세트 ↔ 임계 대조표**를 넣었다. 구분은 색이 아니라 **모양(원 4개 vs 막대 3개)**이고,
**세트 줄에는 "파랑 · 높이 4"가 절대 나타나지 않는다** — 그 조합이 화면에 없다는 사실 자체가
"세트는 영구가 아니다"를 말한다. (색으로 가르지 않은 이유는 §4-4-(c)와 같다 — 강조색이 둘이 된다.)

**요구 사항(§9-7에 추가)**: `PeakTierOf(stat) → 0..3`. 없으면 3상태를 그릴 수 없다.
저장 필드도 새로 필요하다(§9-3).

## 14-3. 【정정 3】 세트 A~F에는 **표시 이름이 없다**

`ECONOMY_SPEC` 3-3의 6개 세트는 `A`~`F`가 **내부 식별자**이고 표시 이름이 없다.
내 초안의 `세트 완성 · {이름}`은 쓸 이름이 없다.
→ 완성 문구를 **`세트 완성`**(43.0 / 112pt)으로 확정했다. 내부 식별자를 화면에 내보내지 않는다.
이름이 생기면 `· {이름}`으로 확장되고 그때 **한글 4자** 제약이 걸린다(리더 결정 요망).

**호환 확인**: `ECONOMY_SPEC` 3-4의 부분 착용 규칙(2종 = 플레이버만 / 3종 = 힌트 대사 /
4종 = +2 & 매니페스트 전환)과 §6-2의 파생 규칙은 **충돌하지 않는다** —
내 문구는 `m`(빠진 칸 수)만 쓰고 **보너스가 있다고 말하지 않는다.** 특히 3종에서
`넥타이만 더`는 3-4의 *"하나만 더…"* 힌트 대사와 **같은 사실을 말한다**(대사는 캐릭터가,
문구는 창이 — 둘이 어긋날 수 없다).

## 14-4. 【반박 1】 레벨 미달 아이템도 **상점에 진열한다**

`ECONOMY_SPEC` 4-1은 *"요구 레벨 도달 → 상점 **진열**"*이라고 썼다. 문자 그대로 읽으면
레벨 미달 아이템은 상점에 **안 보인다**. **그 읽기에 반대한다 — 근거 3건.**

1. **선반이 고장난 것처럼 보인다.** 1일차 유저의 모자 칸은 6종 중 Lv.1~2짜리 2종만 남는다.
   이 저장소는 같은 결론을 이미 냈다 — §45-9 *"칩을 숨기지 않는다 … **죽이되 지우지 않는다**"*.
2. **위치 기억이 깨진다**(§3-1-(b)). 같은 아이템이 `[장비]`와 `[상점]`에서 같은 자리에 있어야
   두 탭이 "같은 선반의 앞뒤"로 읽힌다. 레벨이 오를 때마다 카드가 **끼어들면서 자리가 밀린다.**
3. **`보유 n / 6` 카운터의 분모가 흔들린다.** 분모가 진열 수를 따라 변하면 진행도가 아니라 잡음이다.

**해소**: `진열(가시성)`과 `구매 가능(purchasability)`은 다른 축이다.
`ECONOMY_SPEC` 4-1은 **경제 규칙**(= 언제부터 살 수 있는가)이고, 레벨 미달 아이템은
**S4로 진열하되 살 수 없다.** 경제 수치는 한 자리도 안 바뀐다.
그리고 이 편이 4-1의 다른 요구를 더 잘 지킨다 — *"레벨업 메시지가 거짓말이 되지 않는다"*.
`Lv.9에 열립니다`라고 적힌 카드가 **상점에 보여야** 그 약속이 눈에 보이는 대상을 갖는다.
(상세 패널: `Lv.9에 열립니다. 그 뒤에 동전으로 앞당기거나 기다릴 수 있어요.` — 356.4 / 560pt ✔)
