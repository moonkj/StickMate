# 0. 결론 — 리더가 먼저 읽을 것 (7줄)

1. **【판】U-1의 방향 서술은 반증된다. 100h는 그대로 간다 — 임계도 재화곡선도 옮기지 않는다.**
   실측 순서는 **동전완주 35.1일 < 레벨천장 90일 < 100h 마스터 120일**(원형 B)이다.
   진화는 이미 **가장 마지막 목표**이고, 덤으로 §21-9가 적어 둔 **U-23(「90일차에 완전히 멈춘다」)의
   첫 처방**이 된다 — 곡선이 90 → 120일로 **+33%** 늘어난다.
2. **【판】사용자가 쓴 네 숫자(0·10h·50h·100h)를 하나도 안 버리는 읽기가 있다** — 상태 4개 /
   **진화 사건 3회**(10h·50h·100h). "3단계 진화"를 «3번 진화한다»로 읽으면 문장이 정확히 닫힌다.
   대가는 **조형 상태 +8개**(8팩 × 1상태)이고, 그건 내 소관이 아니라 리더 판단이다(§3-2).
3. **【판】일일 누적 소프트캡 240분/일을 신설한다.** 방치 체인(60분 세션 무한 반복)이 100h를
   **4.17일**로 줄이는 경로가 열려 있다. 240분은 가장 적극적인 정상 사용자(원형 D = 200분/일)의
   **1.20배**이고, 그 1.20배는 내가 만든 게 아니라 `ArcheryDailyAwardLimit`이 이미 쓴 여유율이다.
4. **【판】「1분 세션 반복」에는 방어를 넣지 않는다.** 시간 누적은 격자 이득이 **구조적으로 0**이다
   (1분×480 = 60분×8 = 480분). §22-14가 동전에 대해 내린 판정과 같은 이유·같은 결론이다.
5. **【판】진행률은 「다음 경계까지 %, 소수 1자리, 내림」이다.** 통짜 100h 대비로 그리면
   **25분 완주 1회가 막대에서 0.97pt** — 1pt를 못 넘어 아무 일도 안 일어난 것처럼 보인다
   (UX_WIDGETS R3-2-3이 링에서 이미 당한 그 형태). 구간별로 그리면 최악 구간에서도 **1.95pt**다.
   ★ **2026-09-07 정정**: 초판은 이 기준을 문장으로 못박아 놓고 **§7-3 표를 통짜로 계산**했다.
   구현 라운드가 잡았고 **리더 판정 = 구현(구간 기준)이 맞다.** 재계산 결과는 §7-3, 정정 이력은 §0-3.
6. **`game-architect`의 `[DS-구멍 1·2]`에 값을 채웠다**(§3-3 · §7-5). 그쪽 §8-2 모형은 **채택**했고
   상수 하나(`MaxEdgeFraction` 0.40 → **1/3**)만 근거를 대어 내렸다 — 그래야 그쪽이 독립적으로
   유도한 **180초**와 `D*`가 **같은 숫자**가 된다. 그리고 U-1 원문의 전제 오류 1건을 정정했다(§2-4).
7. **저장 빈도 추가 = +0.00회/일.** 누적은 코인·XP가 **이미** `IsDirty`를 세우는 같은 자리에서
   같은 프레임에 일어난다. 스키마는 **v11 → v12**(신설 필드 3개).

## 0-3. ★ 정정 이력 (2026-09-07, 구현 라운드가 잡아 리더가 반려)

> **하나의 뿌리에서 4건이 나왔다: 「퍼센트의 분모」를 §7-2는 구간으로 못박고 §7-3 이하는 통짜로 계산했다.**
> `floor` 채택이라는 **결론은 두 기준 모두에서 유효**했지만 **근거 숫자가 전부 통짜**였다.

| # | 초판(틀림) | 정정 | 자리 |
|---:|---|---|---|
| 1 | §7-3 표 전체가 `누적 ÷ 6,000` | **`(누적 − 구간시작) ÷ 구간span`**. 5,990분 = 99.8% → **99.6%** | §7-3 |
| 2 | `round`의 거짓 창 **「3분」**(5,997~5,999) | **「1분」**(5,999 한 칸) | §7-3 |
| 3 | 퍼센트 범위 `0.0 ~ 100.0` · *"100h 초과 → 100.0%에서 멈춘다"* | **`0.0 ~ 99.9`. `100.0%` 화면은 존재하지 않는다**(마스터면 칸이 사라진다). 초판의 두 줄은 같은 절의 *"마스터: 퍼센트를 그리지 않는다"*와 **스스로 모순**이었다 | §7-2 |
| 4 | 소수 1자리 논거 *"2.4회마다 1%p · 하루에 안 움직이는 날"* | **1.2회**. 하루 단위로는 0자리도 **안 멈춘다**(60일 중 0일). ⇒ 논거를 **세션 단위**로 교체: 구간2 완주 120회 중 **20회(16.7%)가 0자리에서 정지**, 1자리는 **0회** | §7-2 |

★ **결론은 4건 모두 그대로다** — 「구간 기준 · 소수 1자리 · 내림」. **바뀐 것은 근거 숫자뿐이다.**

### ★ 왜 초판이 통과했나 — 이 저장소가 반복해 당한 형태 그대로다

> **두 기준이 둘 다 「그럴듯한 99.x%」를 낸다.** 99.8333%도 99.6667%도 눈으로는 똑같이 옳아 보이고,
> `floor` vs `round` 결론도 **어느 기준으로 계산하든 같은 답**이 나왔다.
> ⇒ **틀린 계산과 맞는 계산이 똑같이 생겼고, 결론까지 같아서 아무도 안 봤다.**
> 이걸 잡은 것은 **구현이 문서와 다른 방법으로 같은 값을 다시 잰 것**이다(인계 계약의 목적 그 자체).
> **그래서 I-C8′을 신설해 「분모는 구간 span이지 6,000이 아니다」를 테스트로 못박는다**(§9).

### ★ 내 오류가 프로덕션 주석까지 갔다
`CostumeEvolutionRules.cs`의 XML 문서가 초판 §7-3을 인용해 **「5,997~5,999분 / 3분」**을 적고 있다.
**코드 동작은 옳고 주석만 낡았다.** 내가 못 고치므로 §12에서 `coder-systems`에 회부한다.

## 1-1. ★ 원형표를 **역산으로** 되살렸다 — 이게 이 문서의 계기다

§18-3의 원형표는 「능동 수입」만 적고 **「집중 몇 분」인지는 안 적혀 있다.** 진화 임계는 분으로
매겨지므로 그 값이 없으면 아무것도 못 잰다. 그래서 구조를 가정하고 **4개 원형 전부로 대조**했다:

```
능동 수입 = 집중분 × 24 + 활쏘기횟수 × 20
   A :   0분×24 + 3.4회×20 =    68  ✔ (문서 68)
   B :  50분×24 +   4회×20 = 1,280  ✔ (문서 1,280)
   C : 100분×24 +   8회×20 = 2,560  ✔ (문서 2,560)
   D : 200분×24 +  60회×20 = 6,000  ✔ (문서 6,000)
```

**4/4가 정확히 맞는다.** ⇒ 원형별 집중 사용량은 **A·A2 = 0분 / B = 50분 / C = 100분 / D = 200분**이고,
이건 내가 고른 가정이 아니라 **문서가 이미 쥐고 있던 값을 되찾은 것**이다.

|---|---:|---:|---:|---:|

> 세트별 회계의 필연이고, 화면이 **어느 세트가 가장 앞섰는지**를 보여 주면 사용자가 스스로

### ★ 원문을 확보했다 — 그리고 **전제에 사실 오류가 1건 있다**

라운드 도중 `docs/DESIGN_COSTUME_FOCUS_ARCHITECTURE.md` **§7-2**가 도착해 U-1 **원문**을 봤다:

> *"100 h 누적이면 **유휴 수급만으로** 144,000 동전이 쌓인다 = 전설 아이템 가격의 15배."*

| 주장 | 판정 | 근거 |
|---|---|---|
| 144,000 = 전설 15배 | ✅ **참·재현 성공** | 6,000분 × 24 ÷ 9,600 = 15.0 |
| **그것이 「유휴 수급」이다** | ❌ **거짓** | 144,000은 **집중 완주 요율 24**의 결과다. 유휴는 **12**이고 같은 6,000분이면 72,000(절반)이다 |
| 〃 | ❌ **더 강하게 거짓** | 【실】**집중 세션 중 유휴 수급은 정확히 0**이다 — `CharacterProgressionDirector.cs:374` `isIdleEarning = _focusWatch == null \|\| !_focusWatch.IsSessionActive`. **그 6,000분 동안 유휴로 버는 돈은 0원이다** |
| 〃 | ❌ | 유휴에는 **일일 상한**(1,500 ~ 2,500)이 있어 요율 × 시간으로 곱해지지도 않는다 |

> **⇒ 숫자는 옳고 채널 귀속이 틀렸다.** 그리고 채널을 바로잡으면 U-1의 걱정이 더 줄어든다 —
> 144,000은 «가만히 있어도 쌓이는 돈»이 아니라 **«그 100시간을 실제로 집중해야 나오는 돈»**이다.

★ **`game-architect`의 구조적 처방(§7-2, 「임계를 재화와 절대 연결하지 않는다 ·
`CostumeEvolutionRules`가 `CurrencyModel`을 참조하지 않는다」)은 그대로 옳고, 나는 그 축 분리를
전제로 §3의 값을 잡았다.** 코스튬 단계는 동전으로 살 수 없다 — 이 문서 어디에도 그런 경로가 없다.

## 3-1. 문장이 스스로 충돌한다 — 먼저 그것부터 적는다

> 사용자 원문(Tasklist 25519행): *"세트별 「입은채 누적집중시간」에 따른 **3단계** 시각적진화

| **정상 사용자에게 닿는가** | **닿지 않는다.** 원형 D(200분)조차 40분 여유 |
| **세트별인가** | **아니다 — 전 세트 공유 1개.** 한 번에 한 세트만 입을 수 있으므로 나눌 이유가 없다. 필드 `int` 1개 |
| **리셋** | 일자 롤오버(`CurrencyModel.TickDayRollover`)에 함께. 새 타이머 0개 |
| **넘으면** | 그날 **누적만** 멈춘다. **동전·XP는 건드리지 않는다** — 다른 축이다 |
| **화면** | 그날 남은 분을 **표시하지 않는다.** 정상 사용자가 평생 못 보는 값을 HUD에 두면 §2-4(결제 압박 HUD)와 같은 형태가 된다 |

★ **왜 동전에는 이런 캡이 없는데 여기엔 두는가**(코인과 갈라지는 유일한 지점):
동전은 **소진되는 자원**이라 많이 벌어도 살 것이 없어지면 끝이다. **진화는 되돌릴 수 없는 시각적
보상**이라, 4일 만에 마스터하면 *"마지막 목표"* 그 자체가 사라진다. §15-4의 XP 상한이 코인과
갈라진 것과 **완전히 같은 논증**이다.

# 7. 【판】진행률 표시 수치 — `ux-designer` 인계 계약

> 인계 계약: *"수치가 화면에 뜬다. 표시 불가능한 값을 정하면 그때 알아야 한다."*
> 그래서 **여기서 그릴 수 있음을 먼저 증명하고 값을 넘긴다.**

## 7-1. ★★ 막대는 「다음 경계까지」로 그려야 한다 — 통짜로 그리면 **안 움직인다**

【실】그릴 수 있는 폭 = `Col2ContentWidth(256) − StatCardPadX(11)×2` = **234pt**.

| 표시 기준 | 구간 | **25분 완주 1회의 이동** | 판정 |
|---|---:|---:|---|
| 통짜 0→100h | 6,000분 | **0.97pt** | ★ **1pt 미만 — 안 보인다** |
| S4 구간 0→10h | 600분 | 9.75pt | ✅ |
| S4 구간 10h→50h | 2,400분 | 2.44pt | ✅ |
| **S4 최악 구간 50h→100h** | 3,000분 | **1.95pt** | ✅ |
| S3′ 두 구간 | 3,000분 | 1.95pt | ✅ |

> **이건 UX_WIDGETS R3-2-3이 링에서 이미 당한 것과 같은 형태다** — *"60fps에서도 링은 3.7~12.4초에
> 1pt 움직인다 ⇒ 진행의 시각 증거는 100% 숫자가 지고 있다."* 통짜 100h 막대는 **한 세션을 완주해도
> 1픽셀이 안 움직여서**, 사용자에게 *"아무 일도 안 일어났다"*로 읽힌다.
> ⇒ **막대를 쓸 거면 반드시 구간별. 통짜는 숫자로만.**

## 7-2. 【판】확정 표시 명세

```
형식   : [누적 시간]  +  [다음 경계까지 %]
누적   : "12시간 30분"   — CharacterStatsModel.FormatCompanionTime()과 같은 규칙
                          (1시간 미만이면 "30분"). ★ 새 형식 0개, 재사용
퍼센트 : "37.4%"        — 소수 1자리, 내림(floor). ★ 실제 범위는 **0.0 ~ 99.9**
기준   : 현재 단계의 다음 경계까지 (통짜 100h 대비가 아니다 — §7-1)
마스터 : 퍼센트를 그리지 않는다. 누적 시간만 남는다  ⇒ 그래서 100.0은 **표시될 일이 없다**
```

> ### ★ 범위가 `0.0 ~ 100.0`이 아니라 **`0.0 ~ 99.9`인 이유**
> 마스터가 아닌 동안은 **정의상 구간 안**이라 100.0에 닿을 수 없고, 마스터가 되는 순간
> **퍼센트를 아예 안 그린다.** ⇒ **`100.0%`라는 화면은 이 설계에 존재하지 않는다.**
> 이 문서 초판이 적었던 *"0.0 ~ 100.0"*과 *"100h 초과 → 100.0%에서 멈춘다"*는
> **위 두 줄과 스스로 모순**이었다(§7-3-a에서 함께 정정한다).

| 값 | 표기 | 근거 |
|---|---|---|
| **소수 자리** | **1자리 필수** | 최악 구간(`[50h,100h)`)에서 25분 완주 1회 = **0.833%p → 8틱**. ★ **0자리면 그 구간 완주 120회 중 20회(16.7%)가 숫자를 한 칸도 안 바꾼다**(전수). 1자리는 **0회(0.0%)** |
| **반올림 방향** | **내림(`floor`)** | §7-3 |
| **누적 0분** | **`0.0%`를 그대로 그린다** | §2-5 선례 승계: *"잔액 0 → '0'. 흐리지 않고 다른 값과 같은 잉크로"* |
| **미로딩(세이브 미로드)** | **`—`** | §2-5 선례 승계. `0.0%`와 구별된다 |
| **팩 미소유 / 세트 미완성** | **퍼센트도 시간도 그리지 않는다**(행 자체가 없다) | §4-6 — 쌓이지 않는 값을 0으로 그리면 «쌓이는데 0»으로 읽힌다 |
| **마스터(100h 이상)** | **퍼센트 칸이 사라진다**(누적 시간만) | 【실】`PercentTenthsToNextBoundary`가 `NoNextBoundary(-1)`를 돌려준다 — 「그릴 값이 없다」가 반환값으로 표현된다 |
| **마스터 직전 최댓값** | **99.9%** | 【실】전수 0~5,999분에서 내림 천분율 최댓값 = **999** (§7-3) |

> ### ★ 자기정정 2건 — 이 칸의 초판 논거도 **통짜 잔재**였다
> 초판은 *"0자리면 **2.4회** 세션마다 1%p라 **하루에 안 움직이는 날이 생긴다**"*라고 적었다.
> **둘 다 틀렸다** — 2.4회는 통짜(6,000분) 값이고 구간 기준의 정답은 **1.2회**다.
> 그리고 원형 B의 하루 진행은 구간 기준으로 **1.667%p**라 **0자리로도 하루 단위로는 안 멈춘다**
> (60일 전수 확인, 멈추는 날 **0일**).
> ⇒ **논거를 「하루 단위」에서 「세션 단위」로 바꿨다.** 위 칸이 그 재계산 결과이고,
> **1자리를 고르는 결론은 그대로 유지된다**(16.7% vs 0.0%).

## 7-3. ★ `floor`를 고르는 근거 — **구간 기준으로 재계산했다** (2026-09-07 정정)

> ### ★★ 자기정정 — **이 표는 초판에서 「통짜」로 계산돼 §7-2 문장과 어긋나 있었다**
> §7-2가 *"기준 = 현재 단계의 다음 경계까지(통짜 100h 대비가 아니다)"*라고 못박아 놓고,
> **바로 아래 표를 `누적 ÷ 6,000`으로 계산했다.** 구현 라운드가 대조로 잡아 리더가 돌려줬다.
> **리더 판정: 구현이 맞다(구간 기준). 문서를 고친다.**
> ★ **결론(`floor` 채택)은 두 기준 모두에서 유효했지만 근거 숫자가 틀렸다** — 그리고
> **그 틀린 숫자가 프로덕션 주석까지 갔다**(§7-3-a).

**기준: 현재 구간 `[50h, 100h)` = 3,000분. 진행 = `누적 − 3,000`.**

| 누적 | 구간 진행 | `floor` 1자리 | `round` 1자리 | 실제로 마스터인가 |
|---:|---:|---:|---:|---|
| 5,990분 | 2,990 / 3,000 | 99.6% | 99.7% | 아니오 |
| 5,997분 | 2,997 / 3,000 | 99.9% | 99.9% | 아니오 |
| 5,998분 | 2,998 / 3,000 | 99.9% | 99.9% | 아니오 |
| **5,999분** | 2,999 / 3,000 | **99.9%** | **100.0%** ← | **아니오** |
| **6,000분** | — (마스터) | **그리지 않음** | 그리지 않음 | **예** |

> `round`가 만드는 「100.0%인데 마스터가 아닌」 창 = **1분**(5,999분 한 칸뿐).
> ★ **초판의 「3분」은 통짜 기준 값이었다. 구간 기준의 정답은 1분이다.**
> `floor`는 그 창이 **0분**이고, 코인·XP가 전부 `floor`다(§22-9~12) —
> **같은 앱에서 반올림 방향이 갈리지 않는다.**

### 7-3-a. 【실】구현이 이 성질을 **`floor`보다 한 겹 더 강하게** 잠갔다 — 클램프

【실】`Core/CostumeEvolutionRules.PercentTenthsToNextBoundary`:
```
long tenths = (long)done * 1000L / span;    // 음이 아닌 값이라 정수 나눗셈 = 내림
if (tenths > 999L) tenths = 999L;           // 마스터가 아닌데 100.0%가 뜨는 창을 만들지 않는다
```
⇒ **마스터가 아닌 동안 반환 범위가 구조적으로 `[0, 999]`**이고, 마스터에 닿는 순간
`NoNextBoundary(-1)`로 바뀐다.

**전수 확인 (0 ~ 5,999분 전부)**

| 구간 | 범위 | 내림 천분율 최댓값 |
|---:|---|---:|
| 0 | `[0, 600)` | 998 (99.8%) |
| 1 | `[600, 3000)` | 999 (99.9%) |
| 2 | `[3000, 6000)` | 999 (99.9%) |
| **전체** | — | **999. 1000 도달 0건** |

> ### ★ 그래서 이 클램프는 **오늘 도달 불가(unreachable)다. 그런데 그것이 값이다.**
> **내림만으로도 1000에 못 닿으므로** 클램프는 지금 한 번도 실행되지 않는다.
> **그 줄이 지키는 것은 오늘이 아니라 「다음 사람」이다** — 같은 자리에 `round`를 넣으면
> **1건(5,999분)이 1000을 내는데, 클램프가 그것을 999로 잡는다.**
> ⇒ **「100.0% 표시 ≡ 마스터 도달」이 반올림 방향의 선택에 의존하지 않게 된다.**
> `floor` 하나로 이 성질이 선다고 읽으면 **틀린다** — 그건 오늘의 우연이고, 클램프가 구조다.
> ★ **지우지 마라.** 커버리지 도구가 «한 번도 안 타는 줄»로 지목해도 그것은 결함이 아니다.

### 7-3-b. ★ 내 오류가 **프로덕션 주석까지 갔다** — 리더 회부 (내가 못 고친다)

【실】`Core/CostumeEvolutionRules.cs`의 `PercentTenthsToNextBoundary` XML 문서가
내 초판 §7-3을 인용하며 이렇게 적고 있다:

> *"`round`는 5,997~5,999분 구간에서 「100.0%인데 마스터가 아닌」 화면을 **3분 동안** 만든다"*

**그 「5,997~5,999 / 3분」이 바로 통짜 기준 값이다.** 구간 기준의 정답은 **「5,999분 / 1분」**이다.
- **동작은 옳다** — 코드는 구간 기준으로 정확히 계산한다. **틀린 것은 주석 하나뿐이다.**
- 그러나 이 주석은 *"왜 내림인가"*의 **근거 문장**이라, 낡은 채로 두면 다음 사람이
  **틀린 근거 위에서 반올림 방향을 재검토**하게 된다.
- **나는 프로덕션 `.cs`를 못 고친다**(설계 담당 + 그 파일은 다른 라운드 소유).
  ⇒ **리더 → `coder-systems`에 주석 1건 정정 요청**(§12 인계표에 등재).

【실】정보창 좌측(Col2)에 **「테마 세트」 블록**이 이미 있다(`Col2BlockSet`, `SetPanelHeight = 56pt`,

> 그쪽 §8-2가 이미 **세 상수를 겹쳐 무는 모형**을 세워 두고 값 확정을 나에게 넘겼다(`[DS-구멍 2]`).
> **나는 경쟁안을 내지 않는다 — 그 모형을 채택하고 상수만 확정한다.** 내가 처음 적었던
> 「순수 비율 0.20/0.80」은 **그쪽 반증이 옳다**: 60분 세션에서 적응기가 **12분**이 되어 거짓이 된다.

**모형(그쪽 §8-2, 내가 재현했다)**
```
EdgeSeconds(D) = min( MaxEdgeFraction × D ,  clamp(0.2 × D, MinEdgeSeconds, MaxEdgeSeconds) )
적응기 = [0, Edge)        몰입기 = [Edge, D − Edge)        한계 = [D − Edge, D]
```
★ **교정**: 그쪽 §8-2 표 **9행 전부**를 이 식이 재현했다(f = 0.40). 재현이 깨졌으면 아래 비교는 무효다.

| 상수 | 【판】확정값 | 유도 근거 |
|---|---:|---|
| `MaxEdgeSeconds` | **300초(5분)** | ★ **사용자 제시값 승계.** 25분 예시의 적응기가 정확히 5분이다 |
| `MinEdgeSeconds` | **60초** | 지급 격자의 최소 단위다 — §22-12가 *"1분 미만은 0동전"*으로 못박은 그 1분. **그보다 짧은 구간은 이 앱의 경제가 관측조차 못 하는 길이**다 |
| `MaxEdgeFraction` | ★ **1/3** (그쪽 잠정값 **0.40**에서 내림) | 아래 |

### ★ `MaxEdgeFraction` = 1/3 을 권고하는 이유 — **두 상수가 서로를 유도한다**

`MinEdgeSeconds`가 물기 시작하는 세션 길이는 `D* = MinEdgeSeconds / f`다.

| f | D* | 코스튬 최소 세션 길이(몰입기 ≥ 60초) | 일치? |
|---:|---:|---:|:--:|
| 0.40 | **150초** | 180초 | ✘ 두 숫자가 남는다 |
| **1/3** | **180초** | **180초** | ✅ **같은 숫자** |

> **f = 1/3에서만 「두 갈래가 만나는 지점」과 「코스튬 최소 세션 길이」가 같은 180초가 된다.**
> 그러면 모형이 **한 문장으로 닫힌다**: *"180초 이하는 정확히 3등분이고, 그 위는 적응·한계가
> 60초에서 시작해 20%까지 자라 300초에서 멈춘다."* f = 0.40이면 150과 180 두 숫자가 따로 남고,
> **150에 붙일 근거가 없다.**

| 세션 D | f = 0.40 (적응/몰입/한계) | **f = 1/3** | 몰입기 변화 |
|---:|---|---|---:|
| 60초(하한) | 24.0 / **12.0** / 24.0 | 20.0 / **20.0** / 20.0 | **+67%** |
| 120초 | 48.0 / 24.0 / 48.0 | 40.0 / 40.0 / 40.0 | +67% |
| **180초** | 60.0 / 60.0 / 60.0 | 60.0 / 60.0 / 60.0 | **동일** |
| 300초 이상 전부 | — | — | **완전히 동일** |

- **f는 D < 180초에서만 값이 갈린다.** 프리셋(15/25/50분)과 사용자 예시는 **두 값에서 완전히 동일**하다.
- 내리는 방향의 이득: 짧은 세션에서 **코스튬이 보이는 시간(몰입기)이 67% 길어진다.**
- **사용자 제시 25분은 두 값 모두에서 정확히 `0~5 / 5~20 / 20~25분`이다** — 어느 쪽을 골라도
  사용자가 준 숫자는 안 흔들린다.

### 【판】코스튬 최소 세션 길이 = **180초(3분)** — 확인 요청 승인

`game-architect`가 *"몰입기가 60초 이상이려면 세션 ≥ 180초"*로 유도한 값이다. **확인했다:**
- f = 0.40에서도 f = 1/3에서도 `D = 180`에서 몰입기가 **정확히 60초**다(위 표) — **f 선택과 독립이다.**
- 프리셋 3종(15/25/50분)은 전부 **8.3배 이상** 여유로 통과한다. 잘리는 것은 **직접 입력 1~2분**뿐이고,
  그 구간은 §5-1이 이미 *"1분 세션에는 방어를 넣지 않는다"*로 판정한 그 구간이다 —
  **연출이 안 나오는 것이 벌칙이 아니라 「장면이 성립하지 않는 길이」라는 사실**이다.
- 【미】 실제로 3분 미만 세션을 고르는 비율은 **텔레메트리가 없어 모른다**(U-C9).

### 부수 규칙 3개

- **경계는 반열린 구간**, 판정은 `RemainingSeconds / SessionDurationSeconds`에서 **매번 파생**한다.
  **저장 필드 0개.** 일시정지 중에는 진행도 멈춘다(§4-2와 같은 코드).
- 세 구간의 **연출 내용**은 `design-motion` 소관이다. 나는 **경계값만** 낸다.
- `game-architect` §7-3 **규칙 C-6**(*"단계는 세션 시작에 래치되고, 승급은 세션 종료에 판정된다"*)과
  내 §4-4(*"시작 ∧ 종료 둘 다 같은 세트"*)는 **충돌하지 않는다** — 둘 다 «시작에 읽고 종료에 판정»이고,
  내 쪽은 거기에 **테마 일치 조건**을 하나 더 얹는다(어뷰징 경로 하나를 닫는다).


### ★ 두 문서 사이에 **남은 발산은 하나뿐**이다 — `MaxEdgeFraction`

【실】라운드 종료 시점 `DESIGN_COSTUME_FOCUS_ARCHITECTURE.md` §8-2의 코드 스케치는
`MaxEdgeFraction = 0.40f`다. 나머지 셋(`NominalFraction 0.20` · `MinEdgeSeconds 60` ·
`MaxEdgeSeconds 300`)은 **두 문서가 완전히 일치**한다.

| | game-architect §8-2 | 이 문서 §7-5 |
|---|---:|---:|
| `NominalFraction` | 0.20 | 0.20 ✅ |
| `MinEdgeSeconds` | 60 | 60 ✅ |
| `MaxEdgeSeconds` | 300 | 300 ✅ |
| **`MaxEdgeFraction`** | **0.40** | **1/3** ← **여기만 갈린다** |

**차이가 실제로 나타나는 곳은 `D < 180초`뿐이고**(위 표), 프리셋·사용자 예시는 **전부 동일**하다.
⇒ **구현을 막지 않는다.** 리더가 어느 쪽으로 확정하든 상수 한 줄이고, 그 상수를
`FocusSessionPhases`가 **단일 출처로 들고 있으므로**(그쪽이 이미 그렇게 짰다) 나중에 바꿔도
베껴 둔 숫자를 쫓아다닐 필요가 없다.
