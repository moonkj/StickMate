## 2. 동작 — "우리가 안 바꿨으면 안 건드린다"

### 2-1. 기동 (`BeforeSceneLoad`, 씬의 어떤 `Awake`보다 먼저)

```
0. 디스크 흔적 읽기
1. OS 상태 읽기(ABM_GETSTATE)
2. [지난 실행의 빚] 열린 흔적이 있고 OS가 기록과 다르면 → 사용자의 원래 값으로 먼저 되돌린다
                     → 되돌린 뒤 상태를 **다시 읽는다**
3. [이번 실행]     자동 숨김이 켜져 있으면 → ★흔적 먼저 쓰고★ → 해제
                    자동 숨김이 꺼져 있으면 → 아무 것도 안 한다(디스크에도 흔적 없음)
```

**자동 숨김을 원래 안 쓰는 사용자에게는 이 기능이 존재하지 않는 것과 같다.** 시스템 쓰기 0회,
디스크 파일 0개. (`ReservedBarRevealPolicyTests.자동숨김이_꺼져_있으면_시스템도_디스크도_건드리지_않는다`,
`네거티브컨트롤_흔적이_없으면_복구는_일어나지_않는다`)

### 2-2. 종료 — 입구 둘, 순서 하나 (`Application.quitting` / Windows `WM_ENDSESSION`)

우리가 바꿨으면 원래 값으로 되돌리고 흔적을 닫는다. 이미 원래 값이면(사용자가 그 사이 직접 바꿨다면)
**시스템에 쓰지 않고** 흔적만 닫는다.

★ 2026-09-14 — 이 원복은 **두 입구**에서 온다. 둘 다 `Platform/AppShutdownSequence.cs`의 같은 순서
(`Order`: **⓪ 종료 시작 표지 → ① 작업표시줄 원복 → ② 동결 워치독 정지 → ③ 진행 저장 → ④ 정상 종료 표지**)를 돈다.
③ 진행 저장은 5차에 들어온 **합류 자리**다 — 저장 계층이 `AppShutdownSequence.RegisterSaveHandler`(단일 슬롯 `AppShutdownSaveHandler`)로
처리기를 등록했을 때만 돌고, 등록이 없으면 아무것도 하지 않는다. 등록은 coder 라운드 몫이다(5차 커밋 시점 미등록).

**⓪이 원복보다 앞이어도 되는가 — 판단(2026-09-14 4차).** R-1이 원복 앞에서 막은 것은 **기다리는 단계**(워치독 합류 최대 1초)다. ⓪은 우리 폴더(`FreezeForensics/session-exit-marker.txt`)의 한 줄을 OS에 넘기고 끝나며 디스크 동기화(`Flush(true)`)를 하지 않는다 — 프로세스가 끊겨도 OS가 받은 쓰기는 남고, 잃는 것은 전원 차단뿐이다. 사용자 설정·시스템을 바꾸지 않으므로 **"시스템을 바꾸는 단계 중 원복이 맨 앞"**은 그대로다(`SessionEndShutdownTests.종료_순서는_…`가 `Order[1]`로 잠근다). ⓪이 필요한 이유: 셸이 먼저 내려가 ①의 동기 셸 호출이 돌아오지 않은 채 강제 종료되면(추정 경로, 실기 미확인) ④가 영영 남지 않아 그 실행이 크래시와 구별되지 않는다. 대가는 원복 전 파일 쓰기 한 번(Windows 실측 없음). 디스크 쓰기 자체가 멈추는 환경이면 원복도 늦어지고, 그때는 2-3의 흔적이 다음 실행에서 갚는다.

| 입구 | 언제 | 누가 부르나 | 워치독 합류 대기 |
|---|---|---|---|
| `Application.quitting` | 앱이 스스로 끝날 때(트레이 「종료」·단축키·설정창) | `AppShutdownSequence.EnsureQuitHookInstalled()`가 **한 번만** 건 구독 | 최대 1초 |
| `WM_ENDSESSION`(wParam=TRUE) | Windows 로그오프·시스템 종료·재시작, Restart Manager(`ENDSESSION_CLOSEAPP`) | 우리 **숨은 호스트 창**의 프로시저가 **맨 앞에서 동기로** `AppShutdownSequence.TryHandleSessionEndMessage(message, wParam, lParam)` 한 줄만 부른다 — 판정이 참이면(lParam 값과 무관) `HandleSessionEnding(lParam)`이 같은 순서를 돈 뒤 **앱 종료를 요청**(5차: 분기 규칙을 중립 함수로 옮겨 lParam 조합을 실행으로 잠금) | 0(신호만) |

**왜 두 번째 입구가 필요한가.** Windows는 `WM_ENDSESSION` 처리가 끝나면 언제든 프로세스를 끊는다
(MS 문서: *"the session can end any time after all applications have returned from processing this message"*).
Unity가 그 전에 `Application.quitting`을 부르는지는 **실기 미확인**이다. 부르지 않으면 매일 밤 PC를 끄는 사용자의
작업표시줄이 자동 숨김이 풀린 채로 남고, **StickMate를 다시 켜야** 2-3 (b)의 복구로 돌아온다 — "실행 중에만"이라는
승인 조건이 평범한 종료 경로에서 깨진다.

- `wParam=FALSE`(다른 앱이 종료를 막아 **취소**됨)에서는 아무것도 하지 않는다 — 세션이 계속되는데 원복하면 실행 중에
  자동 숨김이 돌아온다.
- `WM_QUERYENDSESSION`은 건드리지 않는다(DefWindowProc = 종료 허용). 우리는 종료를 막지 않는다.
- ★ **처리한 뒤 앱이 스스로 끝난다(2026-09-14 4차, X1).** MS 문서상 wParam=TRUE면 *"the session can end any time after all applications have returned"*, `ENDSESSION_CLOSEAPP`(Restart Manager)는 *"If wParam is TRUE, the application must shut down"*, `ENDSESSION_CRITICAL`은 *"forced to shut down"* — 플래그와 무관하게 끝나야 한다. 그런데 Restart Manager 경로나 사용자가 종료를 취소한 경로에서는 프로세스가 **살아남을 수 있고**(실기 미확인), 그러면 실행 중인데 자동 숨김이 원복된 상태("실행 중에만 해제" 조건이 뒤집힘)와 "정상 종료" 표지가 남는다. 살아남은 뒤 해제를 **다시 거는** 복귀 경로는 두지 않았다 — 복귀 직후 실제로 끊기면 작업표시줄이 앱 없이 드러난 채 남기 때문이다. 대신 원복·표지 뒤 `Application.Quit()`을 요청해 **살아남은 상태 자체를 없앤다**(승인된 `ABM_SETSTATE` 형태는 늘지 않는다). lParam 플래그는 진단 로그(`[종료순서]`)에만 남긴다.
- 두 입구가 **차례로** 와도(세션 종료 뒤 quitting) **시스템에 두 번 쓰지 않는다** — 원복은 "이번 실행이 바꿨는가" 상태로 멱등이다(첫 원복이 실패했으면 두 번째 순서가 다시 시도한다).
  ★ **예외(5-b) — 중첩 시에만 같은 값 2회가 가능하다.** 한 순서의 원복 쓰기(`SHAppBarMessage`)가 돌아오기를 기다리는 사이 다른 입구의 순서가 **같은 스레드에서 끼어들면**
  (Windows는 동기 호출이 대기하는 동안 보낸 메시지를 처리할 수 있다 — `SHAppBarMessage` 내부 대기 방식은 1차 문서에 없어 이 경로에서의 실재는 **미확인**, 실재한다고 가정하고 막는다),
  끼어든 순서도 원복을 **건너뛰지 않고 같은 값을 한 번 더 쓴다.** 이유: `WM_ENDSESSION` 처리가 반환되면 언제든 프로세스가 끝날 수 있는데(MS 문서 — 위 인용), 그 순간 바깥 쓰기가
  반영됐는지 알 방법이 없다. 건너뛰면 원복 없이 끊길 수 있다(리더 우선순위: 반환 전 원복 완료 > 같은 값 중복 쓰기 회피). 값이 같아 결과가 같고, 승인된 `ABM_SETSTATE`
  **형태**(파일 1개·형태 2개)는 늘지 않는다 — 늘어나는 것은 중첩 시 호출 **횟수** 1회뿐이다. 바깥 쓰기가 돌아왔을 때 끼어든 순서가 이미 원복·흔적 닫기를 마쳤으면 바깥은 흔적을
  다시 쓰지 않고 로그도 남기지 않는다(`ReservedBarRevealDirector.RunShutdown`). 원복 **조회** 안에서 끼어들면 바깥은 조회가 돌아온 뒤 "이미 원복됨"을 보고 쓰지 않는다(1회).
  잠금: `SessionEndShutdownTests.재진입_…`(끼어드는 자리 8곳 × 바깥 입구 2).
- ★ **표지는 한 실행에 한 번 끝낸다(5차 → 5-c).** 두 번째 순서는 이번 실행이 ④ 정상 종료 표지를 **이미 썼으면 ⓪·③·④를 건너뛴다**
  (`AppShutdownSequence.ShouldRunStep` ← `SessionExitMarker.CleanExitWrittenThisRun`). 4차까지는 두 번째 순서의 ⓪이 첫 순서가 남긴 `clean-exit`을
  `exit-started trigger=ApplicationQuitting`으로 덮어써, 그 틈에 끊기면 판정이 "원복 도중 끊김"과 구별되지 않았다(verify-change 4차 실측).
  ①·②는 두 번째 순서에서도 돈다(원복 재시도). ★ **5-c(리더 판정): ③ 진행 저장은 ④가 이미 쓰였으면 건너뛴다** — 5-b까지는 두 번째 순서의 ③이 `clean-exit` **뒤에** 돌아,
  그 저장 도중 프로세스가 끝나면 "표지는 깨끗한데 저장 도중 죽음"이 됐다. 첫 순서의 ④는 그 순서의 ③ 뒤에만 쓰이므로 잃는 것은 사이 몇 프레임분 증분뿐이다.
  첫 순서가 ④를 **못 썼으면**(쓰기 실패·끊김) 표지가 거짓말하지 않았으므로 두 번째 순서가 ③과 ④를 **다시** 돈다
  (쓰기 실패는 `SessionEndShutdownTests.S1_…`가 표지 자리에 같은 이름 폴더를 세워 실제로 실패시켜 잠근다).
- ★ **중첩(5-b·5-c) — 한 순서가 기다리는 사이 다른 입구의 순서가 끼어들 때.** 우선순위 (1) `WM_ENDSESSION` 반환 전 원복 완료 > (2) ③ 처리기 재진입 금지·저장 중 ④ 금지·
  ④ 뒤 ③ 금지 > (3) `trigger=`는 그 줄을 실제로 쓴 순서의 것 > (4) 같은 값 중복 쓰기 회피. 코드로는: 끼어든 순서도 ①을 돈다(위 예외) / ③은 **걸쇠**로 한 번에 하나만 돌고,
  걸쇠에 걸린 순서는 ③과 ④를 **건너뛴다**(⓪은 쓴다) — 저장을 시작한 바깥 순서가 저장을 마친 뒤 ④를 쓴다 / "④를 이미 썼는가"와 "③이 도는 중인가"는 순서 시작이 아니라
  **⓪·③·④ 직전에** 읽는다(`AppShutdownSequence.ShouldRunStep(step, 이미 썼는가, 저장 중인가)`) — 5차는 순서 시작 때 한 번 읽어, 재개된 바깥 순서가 안쪽이 쓴
  `clean-exit` 줄을 자기 `trigger`로 덮었다(verify-change 5차 탐침 A·B). ③ 처리기 계약은 `AppShutdownSaveHandler` 문서(재진입 없음·순차·**④ 뒤에는 불리지 않음**·보통 한 번 —
  횟수는 코드가 세지 않는다).
- 셸(탐색기)이 먼저 끝나 원복이 반영되지 않으면 **흔적을 닫지 않는다** — 다음 실행이 먼저 갚는다(2-3 (b)).

**수신 창 — 누가 `WM_ENDSESSION`을 받나.** Unity 창은 서브클래싱하지 않는다. 받는 것은
`Platform/Windows/WindowsSystemTrayIcon.cs`의 **숨은 호스트 창**(부모 없는 최상위 `WS_POPUP`, `WS_VISIBLE` 없음)이다.

| 트레이 | 수신 창 |
|---|---|
| 켜짐(기본) | 트레이 아이콘의 호스트 창이 그대로 받는다 |
| 끔(`STICKMATE_NO_TRAY_ICON`) | **아이콘 없는 숨은 창만** 세운다 — 이번 실행이 자동 숨김을 실제로 바꿨거나, 정상 종료 표지가 켜져 있을 때. 둘 다 아니면 창도 만들지 않는다. 결정 경로 전체(프로세스당 한 번 판정 · 조건 · 창 생성 호출)는 중립 `SessionEndReceiverGate.EnsureReceiverWithoutTray`에 있고, 트레이 파일은 옵트아웃 여부와 창을 만드는 손만 넘긴 뒤 결과로 로그만 고른다(5차 — 트레이 줄 앞에 조건 한 줄로 이 사용자의 수신 창이 사라지던 구멍) |

숨은 창을 세워도 원칙 3의 쓰기 형태(`ABM_SETSTATE`)는 한 줄도 늘지 않고, 트레이 예외 API
(`SetForegroundWindow`/`PostMessage`/`DestroyWindow`)도 새로 부르지 않는다. 창 생성이 실패하면 수신자가 없고, 그때도
흔적이 남아 다음 실행이 먼저 갚는다.

**④ 정상 종료 표지는 무엇인가.** `persistentDataPath/FreezeForensics/session-exit-marker.txt` 한 줄(우리 파일)이다.
다음 실행이 "실행 중"으로 남은 표지를 보면 직전 실행이 비정상으로 끝났다고 보고 `Player-prev.log`를 같은 폴더로
**복사**해 둔다(원본은 읽기만, 상한 4MB 끝부분, 슬롯 3개 링, 알림 UI 없음 — `Platform/SessionExitMarker.cs`).
표지를 이 순서 안에 두는 이유는 위와 같다 — Unity가 로그오프·시스템 종료에서 quitting을 부르지 않는다면(실기 미확인) quitting에만 찍은 표지로는 Windows 밤 종료가 매일 비정상으로 오판된다. ⓪ "종료 시작"이 남은 채 끊긴 실행(⓪과 ④ 사이에서 끊김 — ①원복·②워치독 정지·③진행 저장 중 **어디서인지는 표지로 가를 수 없다**, 추정 경로는 셸 선종료로 원복 도중 강제 종료)은 비정상으로 보지 않고 복사하지 않는다. 판독 규칙은 6절 8번.

**이 순서에 들어오지 않는 종료 정리.** 트레이 아이콘 제거, 작업표시줄 버튼 제거기·오디오·가상 데스크톱 탐침의 COM 해제,
스팀 종료는 각자 `Application.quitting`에만 붙어 있고 세션 종료에서는 돌지 않는다 — 세션이 끝나면 그 상대(탐색기·스팀
클라이언트)도 함께 끝나 남는 흔적이 없다. 진행 저장(`Interaction/CharacterProgressionDirector.OnApplicationQuit`)은
세션 종료에서 돌아야 할 수 있어, 5차에 순서 안의 **③ 합류 자리**(`AppShutdownSaveHandler` 단일 슬롯 — `RegisterSaveHandler`는 슬롯이 비었을 때만,
`UnregisterSaveHandler`는 등록한 대리자 참조일 때만 성공)를 넣었다. **처리기 등록과 `OnApplicationQuit` 제거는 coder 라운드**이고, 그 전까지 대장은
**결정 미정**으로 러너에 건너뜀으로 띄워 둔다. 계약: 처리기가 실패를 알리거나 던져도 순서는 ④까지 간다(표지는 "순서를 끝까지 돌았다"만 말한다),
★ 5-b: 처리기는 **재진입되지 않고 순차로만** 불린다(걸쇠). ★ 5-c(리더 판정 — 5-b의 「두 번째 호출은 ④ 뒤일 수 있다」를 기각): 같은 프로세스에서 ④가 **실제로 쓰였으면

### 2-3. ★ 크래시 — 이 기능의 핵심

`OnApplicationQuit` / `Application.quitting`은 **강제 종료·크래시·SIGTERM에서 돌지 않는다.**
이 저장소가 이미 겪었다 — `driver.sh stop`의 SIGTERM에서 저장이 한 줄도 돌지 않았다.
그 경로만 믿으면 크래시 한 번에 사용자의 작업표시줄이 **영구히** 바뀐 채 남는다.

그래서 두 가지를 강제한다.

**(a) write-ahead — 흔적이 시스템보다 먼저다.**
`Application.persistentDataPath/stickmate_reserved_bar_restore.json`에 원래 값을 적고
`FileStream.Flush(true)`로 OS 캐시까지 밀어낸 **뒤에** 시스템을 바꾼다.

| 순서 | 그 사이에 크래시하면 |
|---|---|
| 흔적 → 시스템 (**채택**) | 다음 실행이 "원래 자동 숨김이었다"를 복원. 실제로는 안 바꿨더라도 같은 값이라 무해 |
| 시스템 → 흔적 (기각) | 사용자가 **영구히** 바뀐 상태에 남는다 |

대칭이 아니다. 한쪽만 안전하다. 흔적을 못 쓰면(권한 실패 등) **시스템을 아예 바꾸지 않는다** —
되돌릴 수 없는 변경은 승인 범위 밖이다.
(`흔적을_못_쓰면_시스템을_바꾸지_않는다`, `흔적은_시스템_변경보다_먼저_디스크에_쓰인다`)

**(b) 다음 실행이 남의 빚부터 갚는다.**
열린 흔적을 발견하면 이번 실행의 판정보다 **먼저** 물리적으로 되돌리고, 되돌린 뒤 상태를 **다시
읽어서** 이번 실행을 판정한다.

> **왜 흔적의 값을 그냥 이어받지 않는가**(그러면 깜빡임이 없다): 흔적은 우리가 쓴 것이고, 그 사이에
> 사용자가 직접 설정을 바꿨을 수 있다. 값을 계승하면 **흔적이 틀렸을 때 영원히 틀린다.** 실제로
> 되돌려 놓고 다시 읽으면 그 시점의 진실에서 새로 출발한다. 이 앱은 "캐시가 참일 것"이라고 믿었다가
> 이미 한 번 크게 당했다(`Platform/TopmostRestorePolicy.cs`의 `IsTopmost` 캐시 절).
> 대가는 크래시 직후 **1회의 짧은 깜빡임**뿐이다.

**파일을 지우지 않는다.** "갚았다"는 삭제가 아니라 `active=false` 쓰기다. 이 저장소의 프로덕션
코드에는 `File.Delete(`가 **0건**이고 감사가 그 0건을 지킨다 — 흔적 하나 닫자고 삭제 능력을 여는
것은 대가가 너무 크다.

### 2-4. 안 건드리는 경우들

| 상황 | 동작 |
|---|---|
| 자동 숨김이 원래 꺼져 있음 | 시스템·디스크 둘 다 0회 |
| 제어 능력이 없는 플랫폼(macOS/모바일/에디터) | 아무 것도 안 함 |
| OS 상태 조회 실패 | 아무 것도 안 함 (모르면 추측하지 않는다) |
| 흔적이 **다른 OS**가 남긴 것 | 손대지 않고 보존 |
| 흔적이 **이 빌드보다 새로운 스키마** | 손대지 않고 보존 + 이번 실행도 쉰다(신버전이 갚는다) |
| `ABM_SETSTATE` 후 되읽기가 요청값과 다름 | 실패로 처리하고 남긴 흔적을 즉시 닫는다 |

## 3. macOS Dock — 이번 라운드에서 **하지 않는다** (판단과 근거)

같은 문제가 macOS에도 있다(`com.apple.dock autohide`). 그런데 **성질이 같지 않다.**

**근거 1 — 되돌릴 수 있는 성질이 다르다.**
Windows는 셸이 제공하는 공개 메시지 하나로 **런타임 상태 비트**를 바꾸고, 같은 호출로 되돌린다.
권한 요구 없음, 사용자 파일 안 건드림. macOS에는 대응 API가 없다 —
`NSApplication.presentationOptions`는 **우리 앱이 활성일 때 우리 자신의 표현**만 바꿀 뿐 Dock 설정을
만지지 못한다.

**근거 2 — 알려진 macOS 경로는 전부 더 침해적이다.**
- `defaults write com.apple.dock autohide -bool false` + Dock 재시작
  → **다른 프로세스를 죽였다 살리는 행위**이고(감사가 프로세스 종료를 이미 금지한다),
    사용자의 **환경설정 파일**을 실제로 고친다. 원칙 3의 훨씬 깊은 위반이다.
- System Events 애플스크립트
  → **TCC 자동화 권한 동의 창**이 첫 실행에 뜬다. 처음 쓰는 사용자에게
    "이 앱이 시스템을 제어하려 합니다"를 띄우는 대가가 "Dock이 안 숨는다"보다 크다.

**근거 3 — 크래시 복구의 난도가 다르다.**
Windows는 비트 하나를 되돌리면 끝이다. macOS는 **파일을 고쳐 놨을 수 있는 상태**를 복구해야 한다.
예외를 승인받은 조건이 "실행 중에만"인데, 그 조건을 구조적으로 지킬 수 있는 길이 macOS에는 아직 없다.

**결론: 별도 배정 필요(사유 = 위 3건).** 사용자에게 물어야 할 것:
> "macOS에서는 Dock 자동 숨김을 그대로 두어도 괜찮은가? 원하면 첫 실행에 권한 동의 창이 한 번 뜨는
> 방식으로 구현할 수 있다."

판정이 끝나면 새로 쓸 것은 **사실 조회 한 벌**뿐이다 — 규칙(`ReservedBarRevealPolicy`)과 원복
장치(`ReservedBarRestoreLedger`)는 이미 플랫폼 중립으로 서 있다.
러너에 계속 보이게 `PlatformParityAuditTests.미해결_macOS_Dock_자동숨김을_같이_해제할지_판단되지_않았다`로
남겼다(Assert.Ignore).

## 4. 타이밍 — 왜 `BeforeSceneLoad`인가

작업표시줄 **실측**(`Win32WindowService.TryGetReservedBottomBarOsScreen`)은 `_overlayHwnd`가 잡히기
전에는 조기 반환한다. 사용자 실기 로그가 그 순서를 그대로 보여 준다:

```
[Dock실측] 하단 예약 막대 없음(OS 확정) — …          ← 오버레이 창이 아직 없다
   (한참 뒤)
[Dock실측] 하단 예약 막대 실측(OS 확정) — rect=(0, 1552, 2560, 48)
```

여기서 쓰는 두 호출(`ABM_GETSTATE`/`ABM_SETSTATE`)은 **창 핸들을 요구하지 않는다.** 그래서 오버레이가
생기기 전에 끝낼 수 있고, **끝내야 한다.**

**늦으면 무슨 일이 생기는가(가설, 실기 미확인).** 해제가 첫 실측보다 늦으면 "막대 없음 → 막대 있음"
전이가 **세션 중간**에 일어난다. Windows 작업표시줄은 화면 가로 **전체**를 점유하므로
`BottomSafetyNetPolicy`가 뚫는 구멍이 안전망 전체를 덮고, 좌/우 두 조각이 **동시에 폭 0**으로 사라진다
(`MinPieceWidthOsPoints=1pt` 미달). 그 순간 안전망 위에 서 있던 캐릭터는 자기보다 **위**(막대 두께만큼)에
생긴 작업표시줄 발판을 낙하로 잡을 수 없어 화면 밖으로 떨어지고, `LostCharacterRescueSeconds`
안전망까지 가야 회수된다.

`BeforeSceneLoad`는 씬의 어떤 `Awake`보다 앞이라 그 전이를 **세션 시작 전으로** 밀어낸다.

**남는 위험(정직하게)**: 셸이 상태 변경을 반영해 작업 영역(`rcWork`)을 다시 계산하는 데 걸리는 시간을
**측정하지 못했다**(이 개발 머신에 Windows가 없다). 그 반영이 오버레이 확보보다 늦으면 위 전이가
여전히 한 번 일어난다. 사용자 실기 로그의 두 줄 시간 간격으로 바로 읽힌다(6절 ①).

> 참고: 이 전이는 **이 라운드가 새로 만든 것이 아니다.** 작업표시줄을 쓰는(자동 숨김 안 쓰는) 사용자는
> 지금도 기동마다 같은 전이를 겪는다(위 로그가 그 증거다). 이번 변경은 자동 숨김 사용자의 정상 상태를
> "막대 없음"에서 "막대 있음"으로 바꿀 뿐, 전이 **빈도**를 늘리지 않는다.

```
[작업표시줄] 시작 — 지금 상태를 읽었습니다: 자동 숨김 켜짐(막대가 숨어 있음). 디스크 흔적=없음(정상). 흔적 파일=…
[작업표시줄] ★ 자동 숨김이 켜져 있어 이번 실행 동안만 해제했습니다. 종료할 때 원래대로 되돌립니다.
             원래 값=자동 숨김 켜짐(막대가 숨어 있음) → 지금=자동 숨김 꺼짐(막대가 항상 보임).
             원복 흔적을 먼저 남겼습니다(…) — 강제 종료나 크래시로 이 프로그램이 원복하지 못하더라도 다음 실행이 되돌립니다.
…
[작업표시줄] ★ 종료합니다 — 이번 실행에서 해제했던 자동 숨김을 원래대로 되돌렸습니다. 복원값=자동 숨김 켜짐(막대가 숨어 있음).
```

크래시 뒤 다음 실행:
```
[작업표시줄] 시작 — … 디스크 흔적=★ 열림 — 지난 실행이 원복하지 못했습니다(지난 실행이 기록한 원래 값: 자동 숨김 켜짐…)
[작업표시줄] ★ 복구 — 지난 실행이 원복하지 못하고 종료된 흔적을 발견했습니다 — 사용자의 원래 설정으로 먼저 되돌렸습니다. 되돌린 값=…
```

자동 숨김을 안 쓰는 사용자:
```
[작업표시줄] 시작 — 지금 상태를 읽었습니다: 자동 숨김 꺼짐(막대가 항상 보임). 디스크 흔적=없음(정상). …
[작업표시줄] 자동 숨김이 원래 꺼져 있습니다 — 아무 것도 바꾸지 않았고 흔적 파일도 남기지 않았습니다.
```
(그 뒤로는 이 태그가 종료까지 한 줄도 안 나온다 — 24시간 상주 앱이라 "변화 없음"은 찍지 않는다.)

## 6. ★ 실기 확인 필요 목록 (사용자 Windows 머신)

**이 개발 머신에는 Windows가 없다. 아래는 전부 미확인이다.**
검증된 것은 *규칙과 순서*이고(EditMode 19건 통과), `SHAppBarMessage`가 실제 Windows 셸에서
무엇을 하는지는 **검증되지 않았다**.

1. **해제가 실제로 되는가.** 작업표시줄 자동 숨김을 켠 뒤 앱을 실행한다.
   → 막대가 나타나는가? 로그에 `★ … 해제했습니다` 줄이 있는가?
   → 같이 봐야 할 것: 그 줄과 `[Dock실측] … 실측(OS 확정)` 줄의 **시간 간격**(4절의 미측정 항목).
      실측 줄이 먼저 `막대 없음`을 찍고 나중에 `실측`으로 바뀌면 세션 중 전이가 일어난 것이다.
2. **종료 원복.** 앱을 정상 종료(트레이/설정창의 종료)한다.
   → 작업표시줄이 다시 자동 숨김으로 돌아가는가? `★ 종료합니다 — … 되돌렸습니다` 줄이 있는가?
3. **★ 크래시 원복(가장 중요).** 앱 실행 중 **작업 관리자에서 강제 종료**한다.
   → 작업표시줄은 보이는 채로 남아 있을 것이다(정상 — 종료 훅이 안 돌았다).
   → **앱을 다시 실행한다.** `★ 복구 —` 줄이 뜨고 자동 숨김이 한 번 돌아왔다가 다시 해제되는가?
   → 그 다음 정상 종료했을 때 자동 숨김이 되돌아오는가?
4. **안 쓰는 사용자.** 자동 숨김을 **끈 상태**로 실행한다.
   → `아무 것도 바꾸지 않았고 흔적 파일도 남기지 않았습니다` 줄이 뜨는가?
   → `%USERPROFILE%\AppData\LocalLow\<회사>\<제품>\stickmate_reserved_bar_restore.json`이
      **생기지 않는가?**
5. **캐릭터가 사라지지 않는가.** 자동 숨김을 켠 상태로 앱을 여러 번 재시작한다.
   → 기동 직후 캐릭터가 화면 밖으로 떨어지거나 몇 초 사라졌다 나타나는 일이 있는가?
      (4절의 안전망 두 조각 동시 소멸 가설. 있으면 그 시각의 `[Dock실측]` 줄을 함께 보고할 것.)
6. **작업표시줄이 좌/우/상단에 있을 때.** 자동 숨김 + 왼쪽 도킹으로 두고 실행한다.
   → 해제는 되지만 하단 발판은 생기지 않아야 정상이다(캐릭터는 화면 바닥 안전망에서 논다).
7. **Windows 11에서 설정 앱의 체크박스.** 해제 후 [설정 > 개인 설정 > 작업 표시줄]을 연다.
   → 체크박스 표시가 실제 상태와 어긋나는지(알려진 회색 지대). 어긋나도 우리 원복에는 영향이 없지만,
      사용자가 혼란스러워할 수 있으므로 사실을 기록해 둘 필요가 있다.
8. **★ 로그오프·다시 시작(세션 종료, `WM_ENDSESSION`) 원복.** 체크표 `docs/verify/WINDOWS_CHECK_SESSION.md` **§R**(CW-2 재부팅 판독 — 다시 시작·로그아웃 2회)을 그대로 따른다(체크표는 qa-regression 소유 — 판독 문자열·순서는 그쪽이 정본이다).
   → 로그인 뒤 작업표시줄이 원래 자동 숨김인가, 흔적 파일이 `active = false`인가.
   → 다음 실행 로그에 `★ 복구 —` 줄이 **없는가**(있으면 세션 종료 원복이 돌지 않은 것이다).
   → (4차 이후 빌드) 직전 실행 로그에 `[종료순서] Windows 세션 종료 통보(lParam=…)` 줄이 있는가, 다음 실행의 `[동결기록] 직전 실행 판정=` 값이 `CleanExit`인가.
      ★ 판독 규칙(5차 정정 → **5-b 정밀화** — 판정 6종 전부 · 흔적 `active` · `trigger=`):
      - `NoMarker` — 표지 파일이 없다: 이 기능이 처음 도는 실행(표지가 없는 2차 이하 빌드에서 올라온 첫 실행 포함)이거나 우리 폴더(`FreezeForensics`)가 비었다(기동부가 폴더 경로를
        받지 못한 경우도 같은 값). 직전 실행을 판단할 근거가 없다 — 복사하지 않는다. 기동 로그 `note`에 `표지 처리 실패`가 붙었으면 **이번 실행의 "실행 중" 표지도 못 쓴 것**이다.
      - `CleanExit` — 마지막으로 ④를 쓴 종료 순서가 ⓪→④를 끝까지 돌았다. **작업표시줄이 실제로 돌아왔는지는 이 값이 말하지 않는다**(실제 자동 숨김 상태와 흔적 `active`로 따로 본다).
      - `AbnormalExit` — 표지가 "실행 중"으로 남았다 = 종료 순서가 ⓪을 한 번도 남기지 못했다: 세션 종료 통보를 못 받았거나 받기 전에 끊김, 또는 ⓪ 쓰기 실패(④까지 실패했으면 순서를
        끝까지 돌았어도 이 값이다 — 표지 두 쓰기는 실패를 로그 없이 삼키므로 이 경우들은 가를 수 없다).
      - `ExitStartedNotFinished` — **⓪은 썼고 ④가 남지 않았다**(④에 닿기 전에 끊겼거나, ④ 쓰기만 실패했다). ①원복·②워치독 정지·③진행 저장 중 **어디서인지는 이 값으로 가를 수 없다.**
        원복까지 끝났는지는 흔적 파일이 말한다:
        - `active = false` — 원복과 흔적 닫기는 끝났고 그 뒤(②·③·④ 직전)에서 끊겼다.
        - `active = true` — 아래 셋 중 하나이고 **흔적만으로는 가를 수 없다**: (가) 원복 쓰기가 반영되지 않은 채 끊김(추정 경로 셸 선종료) (나) **원복 쓰기는 반영됐지만 흔적을 닫기 전에
          끊김**(`Platform/ReservedBarRevealDirector.cs:280` 시스템 쓰기와 `:287` 흔적 닫기 사이) (다) 원복 쓰기가 실패로 돌아와 흔적을 열어 둔 채 뒤 단계로 갔다가 끊김.
          **로그인 뒤 실제 자동 숨김 상태를 함께 본다** — 원래 값(자동 숨김 켜짐)이면 (나), 막대가 보인 채면 (가)·(다)이고 다음 실행이 `★ 복구 —`로 갚는다((나)에서는 다음 실행이
          "이미 원래 값"으로 읽어 시스템에 쓰지 않고 흔적만 닫는다).
          ★ 5-d(verify-change 2단계) — 단, **재시작·로그오프가 설정 자체를 되돌렸을 가능성**도 같은 「원래 값」 관측을 만든다: `ABM_SETSTATE`로 바꾼 자동 숨김이
          그 세션에만 유지되고 다음 로그인 때 사용자 프로필 값으로 돌아오는지는 1차 문서가 없고 실기 미확인이다. 그렇다면 로그인 뒤 원래 값은 (나)의 증거가 아니고,
          (나)와 「(가)·(다) + 재시작이 되돌림」을 이 관측으로 가를 수 없다(다음 실행 로그도 둘 다 `★ 복구 —` 없이 흔적만 닫는다).
        - ★ 5-b 이후 빌드 + 진행 저장 처리기 등록 뒤: 저장이 도는 중에 끼어든 순서는 ④를 쓰지 않으므로 **저장이 끝나기 전에 끊긴 실행**도 이 값이다.
      - `OtherInstanceAlive` — 표지가 "실행 중"이고 그 pid가 **지금 살아 있는 같은 이름의 프로세스**다: 두 번째 인스턴스를 켰다. 직전 실행이 어떻게 끝났는지는 **판정하지 않은 것**이다
        (복사 안 함). 두 인스턴스는 같은 표지 파일을 번갈아 쓰므로 **그 뒤의 판정도 믿지 않는다** — 판독 전에 인스턴스를 하나로 정리하고 한 주기를 다시 잰다. pid 재사용으로 이름만
        같은 다른 프로세스일 수도 있다(비교는 프로세스 이름뿐).
      - `Unreadable` — 표지 파일은 있는데 `state=`·`pid=`를 읽지 못했거나 모르는 상태 값이거나, 표지 폴더 만들기·읽기가 예외로 끝났다(잠김·권한): 반쯤 쓰인 파일(⓪은 디스크 동기화를
        하지 않는다 — 전원 차단)·손상·다른 빌드 형식. 추측하지 않는다(복사 안 함).
      어느 입구의 순서였는지는 **앱을 켜기 전에** 표지 파일 줄의 `trigger=`를 읽는다(앱을 켜면 기동이 표지를 "실행 중"으로 덮어쓴다).
      - ★ **`trigger=`의 뜻 — 5-b 이후 빌드**: 그 줄을 **실제로 쓴 순서의 입구**다. "④를 이미 썼는가"를 ⓪·③·④ **직전에** 읽으므로(`AppShutdownSequence.ShouldRunStep`) 먼저 ④를 쓴
        순서의 줄이 남고 뒤 순서가 덮지 않는다. 상태별로 풀면(★ 5-c 리더 판정으로 명시):
        - `clean-exit trigger=X` = **④를 쓴 순서의 입구**. ④는 한 실행에 성공적으로 한 번만 쓰인다(쓰인 뒤에는 ⓪·③·④를 전부 건너뛴다).
        - `exit-started trigger=X` = **⓪을 마지막으로 쓴 입구**. ⓪은 완료를 주장하지 않으므로, ④가 아직 안 쓰였으면 뒤에 끼어든 순서(저장 도중 끼어든 순서 포함)가 다시 써서
          입구가 바뀔 수 있다. ④가 쓰인 뒤에는 ⓪도 건너뛰므로 `clean-exit`이 `exit-started`로 **강등되지 않는다.**
        - ★ 5-c 이후 빌드: ④가 쓰인 뒤에는 ③ 진행 저장도 건너뛴다 — 따라서 `clean-exit`이 남았으면 **그 뒤에 이 순서로 도는 저장은 없었다**(표지 뒤 끊김이 저장 도중 끊김일 수 없다).
          5-b 빌드(처리기 등록 시)는 뒤따르는 순서의 저장이 `clean-exit` 뒤에 돌 수 있었다.
        - 차례로 올 때(세션 종료 → 종료 요청 → quitting): 세션 종료 순서가 ④(`clean-exit trigger=SessionEnding`)를 썼으면 quitting 순서는 표지 두 단계를 건너뛰어,
          **그 두 번째 순서가 끊겨도 판정은 `CleanExit` 그대로다.**
        - 중첩 시(한 순서가 원복·워치독·저장을 기다리는 사이 다른 입구의 순서가 끼어듦 — 실재 미확인): 안쪽 순서가 ④를 먼저 쓸 수 있다. `clean-exit trigger=SessionEnding`은 "quitting
          순서 **도중에** 끼어든 세션 종료가 썼다"일 수도, `clean-exit trigger=ApplicationQuitting`은 "세션 종료 처리 **도중에** 끼어든 quitting이 썼다"일 수도 있다(판정 `CleanExit`은 같다).
          저장 도중 끼어든 순서는 ⓪만 다시 쓰고 ④를 쓰지 않는다.
        - 그래서 `exit-started trigger=ApplicationQuitting`은 "이번 실행에서 ④를 먼저 쓴 순서가 없었다 — 세션 종료 통보가 오지 않았거나, 세션 종료 순서가 ④를 못 쓴 채 quitting 순서가
          이어 돌았거나, (처리기 등록 뒤) 세션 종료의 저장 도중 끼어든 quitting이 ⓪만 남기고 끊겼다"로 읽는다. `exit-started trigger=SessionEnding`도 대칭이다.
        - 저장 도중 끼어들었는지는 직전 실행 로그로 가른다: `[종료순서] 진행 저장이 이미 진행 중입니다` 줄이 있으면 끼어든 순서가 있었다(처리기가 등록된 빌드에서만 나온다).
      - ★ **5차 빌드(5-b 전)**: "④를 이미 썼는가"를 순서 **시작 때** 한 번 읽어, 중첩 시 재개된 바깥 순서가 안쪽이 쓴 `clean-exit` 줄을 **자기 `trigger`로 덮어쓸 수 있었다**
        (verify-change 5차 탐침 A·B) — 5차 빌드의 `clean-exit trigger=`는 "마지막으로 ④를 쓴 순서"로 읽는다. 차례로 올 때의 판독은 위와 같다. 저장 걸쇠는 없지만 5차 빌드는 처리기가
        미등록이라 ③이 아무것도 하지 않는다.
      - ★ **4차 빌드(5차 가드 전)**: 두 번째 quitting 순서가 `clean-exit`을 `exit-started trigger=ApplicationQuitting`으로 덮어쓸 수 있어, 이 값만으로는
        "원복을 마친 뒤 재실행 중 끊김"과 구별되지 않는다(verify-change 4차 실측) — 체크표 `docs/verify/WINDOWS_CHECK_SESSION.md` §R의 4차 판독 표를 따른다.
   → 트레이를 끈(`STICKMATE_NO_TRAY_ICON=1`) 상태로 한 번 더.
