## 1. 좌표 규약 (변환식)

| 이 문서 | 프로덕션 |
|---|---|
| 원점 | 머리 중심 | 발바닥 |
| 단위 | 머리 반경 R = 1 | 월드 유닛 |
| +x | 진행 방향 | 진행 방향(`rig.F`가 부호를 곱한다) |

```
프로덕션_점 = rig.F( x * rig.HeadRadius,  rig.HeadCenterY + y * rig.HeadRadius )
```

NECK/BACK은 머리가 아니라 **어깨**에 매달리므로, 이 문서의 y를 그대로 쓰지 말고 아래 유도값을 써라
(그래야 신장 비율이 바뀌어도 따라온다 — 규칙 4-a).

```
어깨   SH  = (ShoulderY − HeadCenterY)/R = −1.31818 R      ← 이 문서의 y 좌표는 이 값에서 유도했다
엉덩이 HIP = −5.09091 R
몸통   TL  = (ShoulderY − HipY)/R = 3.77273 R
목 부착선   NeckLocalY  = ShoulderY + R·0.04     (현행 유지)
망토 옷깃선 CapeCollarY = ShoulderY + R·0.10     (현행 유지)
```

**절대 좌표를 쓰지 마라.** 배율 불변은 이 규약이 보장한다.

## 2. 검산 결과 — 이 스펙이 보장하는 것

검산 배율은 출하 기본값 **0.75**다. 그 배율에서 실제로 그려지는 획

```
W = max(0.048 × 0.75, 2pt / 35.25) / (0.22 × 0.75) = 0.343864 R
```

**머리 지름 = 2R = 5.82 W.** 즉 얼굴 위에 놓을 수 있는 "서로 구분되는 독립 요소"는 최대 3개다.
이 한 줄이 EYES 설계 전체를 결정한다(5절).

| 검사 | 기준 | 결과 |
|---|---|---|
| 규칙 1 — 모든 변 | ≥ 1.0 W (양끝이 모두 꺾임인 변) | **30종 위반 0** |
| 규칙 1 — 잉크 사각형 | ≥ 1.5 W | **30종 위반 0** |
| 규칙 2 — 채움 | 가리는 물건은 `filled: true` | HEAD/EYES/HAIR 전종 충족 |
| 규칙 3-2 — 보조색 | 아이템당 **정확히 1개** | 30종 전부 1개 |
| 규칙 4 — 부착 | HAIR 최내곽 ≤ 1 − W = 0.656 R | 6종 전부 0.46~0.58 R |
| 규칙 5 — 정원 | 2~4개 | 30종 전부 2~4 |
| 자기교차 | 없음(귀 자르기가 깨진다) | **30종 0건** |

| **위반 0 최소 배율** | — | ★ **0.7120**. 출하 기본 0.75까지 여유가 **0.0380**뿐이다 → **12절**. 12-3 수정 뒤 LOD를 넣으면 **0.5861** |
| 쌍별 실루엣 차 | > 1.0 W | HEAD 1.84 / EYES 1.67 / NECK 1.98 / BACK 2.21 / **HAIR 4.60** |

검산 스크립트는 `AccessoryStrokeBudgetTests.DescribeRuleOneViolation` 과 `AccessorySilhouetteMetrics.ProfileOf`
를 **같은 식으로** 옮겨 썼다(72구간 × 5도, 변 조밀 표본 64분할, 꺾임 문턱 45도).

> ★ 브리핑 정정 1 — 배정문의 "규칙 5 정원 2~3개"는 오독이다. `docs/UX_FLOW.md` 37-6 규칙 5 원문은
> **"합계 2~4개"** 이고, `EyesVisorOpacityTests.구성_정원과_보조색_개수를_지킨다` /
> `AccessoryStrokeBudgetTests.머리카락이_두피에_붙어있고_채워져_있다` 둘 다 `Is.InRange(2, 4)` 로 잠근다.
> **정원은 4개다.** 리더 시안의 배낭 5개만 초과였고, 이 스펙은 4개로 줄였다(8-4절).
>
> ★ 브리핑 정정 2 — 배정문의 "착용 시 머리 지름 32pt"는 이 앱에 존재하지 않는 크기다.
> `ReferencePointsPerWorldUnitApprox = 846/24 = 35.25 pt/unit` 이므로 머리 지름은
> **배율 0.75에서 11.6pt, 다이얼 최대(1.5)에서도 23.3pt** 다. 그래서 검산은 0.75(최악) / 1.0 / 1.5로 했다.

## 4. HAIR (머리 6종) — ★ 사용자가 지목한 부분

### 4-1. 현행 진단 (숫자)

| 아이템 | 정수리에서 머리카락이 두피 링 위로 나온 두께 | 판정 |
|---|---|---|
| 삐친머리 | 0.22 R = **0.64 획** | 위반 |
| 단정한머리 | 0.14 R = **0.41 획** | 위반 |
| 곱슬머리 | 0.28 R = **0.81 획** | 위반 |
| 바가지머리 | 0.52 R = 1.51 획 | 통과 |
| 포니테일 | 0.16 R = **0.47 획** | 위반 |

머리카락 윤곽선과 두피 링 획은 각각 1 W다. 둘 사이가 1.5 W 미만이면 **화면에서 한 줄로 뭉친다.**
그래서 5종이 "머리에 씌운 뚜껑"이 된 것이고, 유일하게 통과한 바가지머리만 페르소나가 읽어냈다.
그리고 **6종 중 어느 것도 턱(−1.0R) 아래로 내려가지 않았다**(최저 −0.68R).

### 4-2. 바꿀 상수 — 배정문이 물은 두 값에 대한 답

```
HairSpanEndDegrees   = 196f   →  폐기한다
HairlineEdgeRatio    = -0.06f →  폐기한다
```

**두 상수를 조정하는 것으로는 고칠 수 없다.** 이유는 기하다.
`HairSilhouette`의 바깥 윤곽은 **반경이 일정한 극좌표 호**다. 스팬을 −16°/196°에서 −75°/255°로 늘리면
옆머리는 내려오지만 `radius`가 그대로여서 **머리에 딱 붙은 껍질**이 된다. 참고 이미지의 머리카락은
"머리를 감싼 껍질"이 아니라 **머리보다 넓은 덩어리**다. 반경을 키우면 이번엔 정수리가 초상화 액자
(1.75 R, `AccessoryStrokeBudgetTests`가 잠근다)를 넘는다.

그래서 **구성을 바꾼다**: 하나의 원호가 아니라 **돔 + 커튼 2개 + 두피 안쪽 경계**다.

```
새 상수
  HairInnerRadiusRatio = 0.58f   // 두피 안쪽 경계. 규칙 4 판정선 1−W = 0.656R보다 작다
  HairCapMinRatio      = 1.52f   // 돔 반경 하한 = 1.0R + 1.5W. 이 값이 '뚜껑'을 없앤다
  HairCapMaxRatio      = 1.75f   // 초상화 액자 상한(그대로)
```

경계를 도는 순서는 **6종 전부 같다**. 이 순서가 어긋나면 폴리곤이 자기교차하고 귀 자르기가 깨진다.

```
   돔(앞→뒤, 반경 cap)  →  뒤 커튼(내려갔다 안쪽으로)  →  두피 안쪽 호(뒤→앞, 반경 0.58)  →  앞 커튼(이마선→앞 끝)
   ↑ 마지막 점이 돔의 첫 점으로 닫힌다
```

```
        ┌───────  돔  cap ≥ 1.52R  ───────┐          정수리에서 두피 링 위로 1.6획 이상
        │        ╭──────────────╮         │
   뒤 ←─┤   ╭────╯   두피 안쪽   ╰────╮    ├─→ 앞
        │   │      호 r = 0.58R       │   │
   뒤 커튼   ╰──────────────────────╯   앞 커튼
     │                                     │
     ▼ 끝은 점으로 수렴                     ▼ 끝은 점으로 수렴
   (긴 머리는 −2.1R까지)                (얼굴 앞으로 흘러내린다)

   얼굴(파인 공간) = 두피 안쪽 호가 끝나는 **앞·아래** 사분면
```

### 4-4. 모자와 함께 썼을 때

모자 커버선이 내려가므로(5절) 잘리는 양이 늘어난다. **6종 × 5개 모자 = 30조합 전부에서
1~2개 조각이 남는 것**을 검산했다(`CharacterAppearanceLayerTests.모자를_쓰면_머리카락이_커버선_아래로_잘리고...`
가 요구하는 "옆머리는 남는다"를 유지한다).

## 5. HEAD (모자 6종)

### 5-1. 현행 진단

커버선(`HatCoverLocalY`)이 전부 머리 중심 **위**에 있다 — 캡 +0.62 / 털모자 +0.42 / 중절모 +0.58 /
베레모 +0.46 / 밀짚 +0.56 R. 즉 **모자가 머리 위쪽 1/3에만 얹혀 있다.** 참고 이미지의 모자·가시는
전부 머리를 **옆으로 감싸고 뒤로 뻗는다.**

### 5-2. 새 커버선 + 감쌈

| # | 이름 | 새 커버선 | 감쌈 확인(|x| ≥ 0.85R 이면서 y ≤ 0.05R 인 잉크) | 앞/뒤 뻗음 |
|---|---|---|---|---|
| 0 | 야구모자 | **+0.06 R** | 관 옆벽 (±0.94, −0.22) | 앞 1.92 / 뒤 1.02 |
| 1 | 털모자 | **−0.06 R** | 접힌 단 (±1.00, −0.42) | 대칭 |
| 2 | 중절모 | **+0.08 R** | 챙 뿌리 (−1.00, −0.34) | 앞 2.06 / 뒤 1.68 |
| 3 | 왕관 | **+∞ (유지)** | 면제 — 스스로 "얹는 물건"이라 선언 | 대칭 |
| 4 | 베레모 | **+0.02 R** | 뒤로 처진 끝 (−1.46, −0.10) | 뒤 1.46 / 앞 0.98 |
| 5 | 밀짚모자 | **+0.08 R** | 챙 (−1.20, −0.22) | 앞 2.18 / 뒤 2.06 |

전 종이 `hmin.y > −1.0 R`(턱 위)과 `1.0 < hmax.y < 2.551 R`을 지킨다
(`CharacterAppearanceLayerTests`의 두 단언).

### 5-3. 부피 — 챙은 닫힌 띠다

```
            ╭─────────────╮
            │   관(채움)   │        관 옆벽이 −0.22R까지 내려와 머리를 **감싼다**
   ─────────┴──┬──────────┴────────╮
   뒤 챙        │ 뿌리 두께 0.50 R  │  ← 1.45 획 (현행 0.38R = 1.10획)
   ────────────┴───────────────────╯──▶ 끝은 점으로 수렴
```

- 야구모자 챙 뿌리 두께 **0.50 R = 1.45 획**(현행 `HatBrimRootDropRatio` 0.38 R = 1.10 획).
- 중절모 챙 뿌리 두께 **0.52 R = 1.51 획**.
- 밀짚 챙 뿌리 두께 **0.46 R = 1.34 획**, 대신 폭이 4.24 R로 카테고리 최대.
- **띠(band)는 좌표를 새로 적지 않는다** — 관 밑변의 두 끝점을 그대로 받는다(현행 규약 유지, 규칙 4-a).

### 5-4. 왕관 — 채움으로 바꾼다

현행은 채움 없는 지그재그 폴리라인이라 봉우리 끝이 **둥근 캡**으로 뭉갠다(참고 이미지의 소닉 가시가
"끝이 완전히 뾰족하다"고 한 것과 정반대). 새 왕관은 **닫힌 채움**이고, 봉우리 3개가 꼭짓점으로 수렴한다.
밑이 뚫린 성질은 채움이 아니라 `HatCoverLocalY = +∞`가 계속 보장한다(현행 그대로 — if 분기가 아니다).

## 6. EYES (안경 6종) — ★ 눈 노출 결정

### 6-1. 결정

> **한쪽만 가리는 물건은 가려지지 않은 눈을 보여 준다. 두 눈을 다 가리는 물건은 아무것도 보여 주지 않는다.**

| # | 아이템 | 눈 노출 | 근거 |
|---|---|---|---|
| 0 | 선글라스 | ✗ | 이름이 "가린다"고 말한다(37-6 규칙 2) |
| 1 | 동그란안경 | ✗ | 아래 6-2 산술 |
| 2 | 고글 | ✗ | 〃 |
| 3 | **외알안경** | **✓ 뒤쪽 눈** | 사용자 명시 요구 |
| 4 | 뿔테안경 | ✗ | 아래 6-2 산술 |
| 5 | **안대** | **✓ 뒤쪽 눈** | 사용자 명시 요구 |

### 6-2. "렌즈 안으로 눈이 비친다"는 이 배율에서 **기하학적으로 불가능하다**

리더가 푼 제약("6종 전부여도 된다")에 대한 답이다. 취향이 아니라 산술이다.

```
눈이 보이려면          잉크 사각형 ≥ 1.5 W        →  눈 반폭 a ≥ 0.75 W
테와 눈이 안 붙으려면   간격 ≥ 1.5 W               →  렌즈 반경 ρ ≥ a + 1.5W ≥ 2.25 W = 0.774 R
두 렌즈가 안 붙으려면   중심 간격 2d ≥ 2ρ + 1.5W   →  d ≥ 3.00 W = 1.032 R
                       바깥 끝 = d + ρ ≥ 5.25 W = 1.805 R   >  1.0 R  ← 머리 밖
```

머리 지름이 **5.82 W**뿐이라 "테 + 간격 + 눈 + 간격 + 테"를 한쪽 눈에조차 넣을 수 없다.
**같은 산술이 외알안경 자신의 알에도 적용된다** — 그래서 외알안경도 *자기가 가린 눈*은 보여 주지 않고,
**가리지 않은 반대쪽 눈**만 드러난다. 사용자의 요구("외눈안경 같이 한쪽만 가릴 때만 눈 노출")와
정확히 일치하고, 그 요구가 **왜 옳은지**까지 설명한다.

부수 효과: 2026-08-30 "눈 삭제"가 사후적으로 정당화된다. 눈동자 반경 0.136 R은 **0.79 획** —
획 하나보다 작았다. 그래서 안 보였던 것이고, 되살리려면 눈이 지금의 **2.5배**가 되어야 한다.

### 6-3. 드러난 눈의 좌표 — 새 상수

`EyeOffsetXInHeadRadii`(0.3409)는 **"눈이 있던 자리"의 정의처로 그대로 남긴다**(가림 판정이 이 값을 쓴다).
하지만 **그려지는** 눈은 규칙 1이 위치를 결정하므로 별도 상수가 필요하다.

```
DrawnEyeOffsetRatio     = 0.62f    // 유도: 2·d ≥ 1.5W + ρ_visor(0.36) + a(0.34) = 1.216 → d ≥ 0.608
DrawnEyeHalfWidthRatio  = 0.34f    // 폭 0.68R = 1.98 획
DrawnEyeHalfHeightRatio = 0.24f    // 높이 0.48R = 1.40 획
```

도형은 **채운 아몬드 4점**(양 끝이 점으로 수렴):

```
(sx·(0.62−0.34), 0.00)  (sx·(0.62−0.06), +0.24)  (sx·(0.62+0.34), +0.02)  (sx·(0.62+0.02), −0.24)
sx = −1 (진행 반대쪽 = 가려지지 않은 눈)
```

검산: 최단 변 1.07 획 · 가리개와의 간격 **1.57 획**(외알) / **1.63 획**(안대) · 최대 반경 0.960 R(머리 안).
**동공은 넣지 않는다** — 내부를 보이려면 3.0 W = 1.03 R, 즉 머리 반지름만 한 눈이 필요하다(규칙 1).

### 6-4. 기존 테스트와의 관계 — ★ 중요

`EyesVisorOpacityTests.채움이_눈_자리를_덮는다`는 외알/안대에 대해
**"뒤쪽 눈 자리(−0.3409, +0.0909)가 채움에 덮이면 안 된다"**를 단언한다.
드러난 눈은 (−0.62, 0)에 있고 반폭이 0.34라서 그 점을 **포함하지 않는다**(실측: 정규화 거리 1.26 > 1).

> **결론: 기존 단언은 수정 없이 그대로 통과한다.**
> 다만 그것은 좌표가 맞아떨어진 결과이지 의도한 계약이 아니다. **coder는 이 단언의 뜻을 명시로 바꿔라**:
> 프로브 대상을 "모든 채움"이 아니라 **"가리개 도형(이름이 `*Eye`가 아닌 채움)"** 으로 좁히고,
> 그 대신 **"`*Eye` 채움이 정확히 1개 있고 진행 반대쪽에 있다"**를 새로 단언해라.
> 그러지 않으면 다음 사람이 눈 좌표를 조금만 옮겨도 "가리개가 뒤 눈을 덮었다"는 **엉뚱한 실패 메시지**를 본다.

`규칙 2`(EYES 실루엣은 반드시 채움)는 **그대로 유효하다.** 6-2가 증명하듯 투명 렌즈는 그릴 수 없으므로
"채움은 옵션이 아니다"라는 규칙의 근거가 오히려 강해졌다. 규칙 2에 한 줄만 덧붙일 것을 권고한다 —
**"규칙 2-a: 눈은 가리개 **안**이 아니라 가리개 **옆**에만 그린다."**

## 8. BACK (망토·등 6종)

### 8-1. 망토 3종 — 서명 디테일 하나

현행 망토는 보조색 도형이 **0개**다(주름 2개는 `Shade` 톤). 규칙 3-2 위반이면서, 참고 이미지 3이 가진
**"서명 디테일 하나"**(금색 장식)가 없다. 그래서 **목을 감는 옷깃 띠**를 넣는다 — 감쌈 원칙과 서명
디테일을 한 번에 만족한다.

```
CapeCollar (닫힘·채움·보조색)
  (+0.40, CapeCollarY+0.10)  (+0.40, CapeCollarY−0.34)  (−0.66, CapeCollarY−0.38)  (−0.66, CapeCollarY+0.06)
  폭 1.06 R (3.08 획) · 높이 0.44 R (1.28 획)
```

> 처음에는 작은 **잠금쇠**(0.62 × 0.36 R)로 설계했는데, 긴 망토 카드에서 전체 span이 7.13 R이라
> 정규화 뒤 **1.02 획**까지 쪼그라들었다(하한 1.00). 규칙 5의 "예산 못 지키는 [선택] 디테일은 넣지 않는다"에
> 걸리므로 **목을 감는 띠로 키웠다**(카드 1.24 획). 이것이 이 스펙에서 가장 빠듯한 자리다.

밑단·주름·제비꼬리는 **현행 값을 그대로 쓴다**(이미 검산을 통과했고, 사용자 신고 대상이 아니었다).

### 8-2. 날개 2종

현행 유지. 쌍 구성·등뼈 유도 모두 이미 옳다. 검산 통과(최단 1.45 획).

### 8-3. 판초

현행 유지 + 옷깃 띠.

### 8-4. 배낭 — "대괄호 `(`"의 정체와 수정

현행 배낭은 **몸 1개(윤곽) + 덮개 선 1개 + 끈 1개**다. 몸의 채움이 몸통 선 뒤(sort −1)에 깔리는데,
가로 폭이 1.10 R뿐이라 화면에서는 **세로로 긴 얇은 조각**만 남는다 — 그게 대괄호다.

새 구성(정원 **4개**, 보조색 1개):

```
  PackBody   (닫힘·채움, 주색)   폭 1.56 R × 높이 2.53 R   ← 가로를 1.10 → 1.56 R로 넓혔다
  PackLid    (닫힘·채움, 주색)   몸 위에 겹치는 뚜껑        ← 같은 색이라 겹쳐도 순서 무관
  PackBuckle (닫힘·채움, 보조색) 0.60 × 0.54 R (1.74 × 1.57 획)
  PackStrap  (열린 선, 주색)     어깨 → 몸의 실재 꼭짓점    ← 좌표를 새로 적지 않는다(현행 규약 유지)
```

리더 시안의 5개(몸+덮개+버클+끈2)는 정원 4를 넘는다. 어깨끈을 **1개**로 줄였다 — 측면도에서 두 번째
끈은 몸통 선에 가려 보이지 않으므로 예산만 먹는다.

## 9. 함께 바뀌어야 하는 것 (coder 필독)

### 9-1. 커버선 표 (`HatCoverLocalY`)

5-2의 새 값으로 갱신. `AccessoryRuleOneCoverageTests`의 털모자 띠 면제 사유가
"커버선 0.42 R"을 인용하므로 **그 주석도 함께 고쳐라**(면제 자체는 새 설계에서 사라진다 — 아래).

### 9-2. 선 위계 — ★ 리더 보고 대상

37-6 규칙 6("실루엣 1.0 W / 내부 디테일 0.7 W")을 **이번 라운드에서는 구현하지 않는다.**
렌더러가 `RenderStrokeWidth` 한 값을 모든 `LineRenderer`에 쓰기 때문에 `Shape`에 두께 역할 필드를
추가하고 렌더러·초상화·카드 세 소비처를 바꿔야 한다. **도형 스펙과 분리해서 별도 라운드로 배정하기를 권고한다.**
이번 스펙은 **채움 vs 선**으로 위계를 만들어 두께 변경 없이 같은 목적을 달성한다.

### 9-3. 같은 레이어 채움의 그리기 순서 — ★ 리더 보고 대상

한 아이템 안에서 채움 2개가 겹치면 둘 다 `SortingOrder − 1`이라 **그리기 순서가 미정**이다
(이 저장소가 33-2-0에서 이미 한 번 정리한 함정). 현행 코드도 HAIR(덩어리 vs 삐침/묶음)에서 이미
이 상태이고, 새 스펙에서는 HEAD(관 vs 챙)·NECK(고리 vs 자락)·BACK(천 vs 옷깃)로 늘어난다.

**권고(1줄 수정, 테스트 가능)**: 채움 메시 오브젝트의 로컬 z에 **도형 인덱스 × −0.0001**을 준다.
`sortingOrder`를 건드리지 않으므로 `EyesVisorOpacityTests.판이_머리카락과_모자_사이의_제자리에_깔린다`
(모든 도형이 `SortEyes`여야 한다)가 그대로 통과한다. 그리고
**"sink에 나중에 넣은 채움이 위로 온다"**를 PlayMode에서 단언할 수 있게 된다.

### 9-4. 면제 대장(`AccessoryRuleOneCoverageTests.Waivers`)

새 스펙은 **면제 6건을 전부 닫는다**(털모자 띠 1 + 나비넥타이 1 + 줄무늬타이 4).
**고쳤으면 대장에서 지워야 한다** — 그러지 않으면 `면제된_도형은_아직_실제로_위반한다`가 빨간불이 된다
(그 검사의 설계 의도가 바로 이것이다). 동시에 `AccessoryStrokeBudgetTests.BudgetedItems`에
NECK 나비넥타이·줄무늬타이, HEAD 털모자를 **추가**해라.

### 9-5. 배율 0.35 (다이얼 최소)

새 스펙은 배율 0.35에서 규칙 1을 49건 어긴다. 이것은 **현행도 마찬가지**이고, 37-6 규칙 1이
그 구간을 "어떤 규칙도 만족시킬 수 없는 **실루엣 전용 구간**"으로 이미 선언했다(W = 0.737 R,
머리 지름이 **2.7 획**뿐이다). 규칙 5가 지시한 LOD("배율 0.5 미만에서 [선택] 디테일을 끈다")는
아직 구현돼 있지 않다 — **별도 라운드 배정 권고**(37-7 #3의 공개 시그니처 변경과 같은 건이다).

## 부록 A. 평가된 점 전체 (오타 대조용)

좌표는 **머리 중심 원점 · R 배수 · 진행 방향 +x**. 1절의 변환식을 적용해서 옮겨라.
"최단 변"은 양끝이 모두 꺾임(≥45°)인 변 중 가장 짧은 것이고, 하한은 1.00 획이다(— 는 그런 변이 없다 = 매끈한 곡선).

```
### Hair
```

## 10-0. ★ 먼저 — 30종의 폴백은 **화면에 한 픽셀도 안 나온다**

배정문의 전제("네 새 도형이 착용 화면에만 들어갔고 카드 아이콘은 옛 모양 그대로다")는
**30종에 대해서는 성립하지 않는다.** 코드와 실제 빌드 캡처 양쪽으로 확인했다.

```
CharacterInfoWindow.BuildCardArt(...)
    if (AccessoryCardIcon.TryBuild(root, slot, itemIndex, IconSize, IconStroke, ...)) return;   ← 여기서 끝난다
    BuildIcon(root, entry.Icon);                                                                 ← 폴백. 30종은 여기 못 온다
```

`TryBuild`가 false를 돌려주는 경우는 `_shapes.Count == 0`뿐이고, `AccessoryShapeBuilder.Append`의
switch는 **Head / Eyes / Neck / Shoulders / Hair 다섯 자리 × 인덱스 0~5를 전부** 갖고 있다
(`AppendHead`/`AppendEyes`/`AppendNeck`/`AppendBack`/`AppendHair` 각 6 케이스 — 실측).
**따라서 30종은 언제나 몸 도형으로 그려진다.**

**실제 빌드 캡처 증거**(`/tmp/stickmate-run/screenshots/minji-18.png`, 2026-09-01 22:51, PID 37699):
천모자 카드가 **채운 관 + 채운 주황 챙**, 털모자가 **채운 관 + 단 + 폼폼**, 선글라스가 **채운 렌즈 2장**,
줄무늬타이가 **채운 매듭 + 날 + 띠**로 그려져 있다.

> **결정적 사실**: 폴백 형식에는 **채운 다각형이 없다.**
> `ItemIconPartKind = Polyline / Ring / DashedRing / Dot` 이고 `CharacterInfoWindow.BuildIcon`은
> Polyline을 **획**으로, Ring/DashedRing을 **테두리 원**으로, Dot만 **채운 원**으로 그린다.
> 채운 다각형 프리미티브가 아예 없다. 그러므로 캡처에 보이는 **채운 관·채운 챙은 폴백이
> 만들 수 없는 그림**이다 = 카드는 몸 도형 경로다. 반대로, **폴백은 v2 스펙의 근본 원칙
> (원칙 2 "채움이 덩어리를 만든다")을 원리적으로 표현할 수 없다.**

**그래서 30종의 폴백 결함은 "형태 결함"이 아니라 "표현 매체가 다른 데서 오는 데이터 표류"다.**
사용자 화면 영향 **0**. 다만 세 곳이 이 데이터를 계속 읽는다 —
`ItemCatalogDigest`(설정 표류 대장) · `ItemCatalogAssetParityTests` · 그리고 **DLC로 슬롯이
늘었을 때의 진짜 폴백 경로**. 그래서 **지워도 되고 고쳐도 되지만, 손으로 고치면 안 된다**(10-3).

## 10-3. 30종 처방 — ★ **좌표를 손으로 적지 않는다. 유도한다.**

30종의 새 폴백 좌표를 손으로 세 번째로 적으면 **다음 라운드에 또 갈라진다**(그게 지금 상태다).

```

   viewX  = 20 + (x − cx)·k          viewY = 20 − (y − cy)·k        (cx,cy = 잉크 사각형 중심)
   Tone == Shade(2) 조각은 넣지 않는다                     ← 폴백에 음영이라는 개념이 없다(리더 판정: 정당)
   닫힌 도형은 마지막에 첫 점을 한 번 더 적는다              ← ItemIconPart 규약
```

# 11. 머리 액세서리(sortingOrder 6·10)가 "주위 살피기" 손을 가린다 — 실측

> 하니스: `design/equipment/verify/handocclusion.py`
> 입력은 전부 `docs/MOTION_SPEC.md` 13절의 실측을 인용했다(내가 지어낸 값 없음).
> 손끝 = 머리 중심에서 **1.179 R**, 방향 **β = 52.8°**(0° = 정수리, +x = 진행) → **(+0.939, +0.713) R**.
> 손끝 캡 반지름 = 팔 획 반폭 0.03919 로컬 = **0.2375 R**.

## 11-1. 왜 액세서리가 팔보다 위인가 (리더가 먼저 찾으라고 한 이유)

```
프리팹   뒤 팔다리 0 · 몸통 1 · 앞 팔다리 2 · 머리채움 3 · 머리링 4 · 눈동자 5
액세서리 BACK −1 · HAIR 6 · NECK 7 · EYES 8 · HEAD 10 (채움 9)
```

**액세서리가 6 이상인 이유는 머리 자신 때문이다** — 머리카락·모자는 **머리 링(4)**을 덮어야 하고,
안경은 **눈동자(5)**를 덮어야 한다(`SortEyes` 주석이 그렇게 적어 놨다: "선글라스를 쓰면 눈동자가
렌즈 뒤로 간다"). 그러므로 **머리 액세서리를 팔(2) 아래로 내리는 안은 불가능하다** —
내리면 모자가 머리 채움(3)에 삼켜진다.

## 12-4. 배율 축을 상시 검산에 넣었다

`design/equipment/verify/verify.py`가 이제 매번 **0.35 / 0.50 / 0.60 / 0.75 / 1.00 / 1.50**을 훑고
**"규칙 1 위반 0이 되는 최소 배율"을 이분법으로 찍어 출력한다.** 그 숫자가 있으면 다음 사람이
여유를 안다 — 지금은 **0.7120이고 출하 기본 0.75까지 여유가 0.0380뿐**이다.

> **관행 정정**: 배율을 넷만 재던 것이 이 구멍을 만들었다. 새 도형을 낼 때는
> **0.50과 0.60을 반드시 포함**해라. 0.60은 실측된 사용자 저장 배율이다.
>
> **자기교차는 배율을 훑을 필요가 없다** — 액세서리 좌표는 전부 R 배수라 배율 변환이
> **닮음(similarity)**이고 교차 여부는 닮음에 불변이다. 한 배율에서 0이면 전 배율에서 0이다.
> **팔다리(규칙 B)는 다르다** — 그쪽은 배율에 따라 **각도가 바뀌는** 관절이라 전 구간을 봐야 한다.
