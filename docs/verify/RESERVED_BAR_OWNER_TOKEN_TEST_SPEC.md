**폴더**(흔적 폴더 안 파일 구성)
- `∅` 비어 있음

- `Ren(T←U)o` — **이름은 T의 것, 본문은 U의 열린 흔적**

- `Fx3o` — 고정 이름, `version = CurrentVersion + 1`, 열림
- `OwnN` — T의 파생 이름, `version = CurrentVersion + 1`, 열림
- `Gar` — 고정 이름, 파싱 불가 바이트

**자동 숨김(AH)**: 기동 시점에 가짜 제어기가 보고하는 값. `ON`(켜짐) / `OFF`(꺼짐 = 막대가 보임)

**행위**
- `기동` — `RunStartup(제어기, 저장소)` 1회
- `크래시` — `기동` 뒤 종료를 부르지 않고 `ReservedBarRevealDirector.ResetForTesting()`(프로세스 재시작 흉내)
- `정상종료` — `RunShutdown()`

**계수**
- `R` — 복구 방향 시스템 쓰기(쓴 값 = 흔적의 원래 값) 횟수
- `V` — 해제 방향 쓰기(쓴 값 = 꺼짐) 횟수
- `생성` — 가짜 저장소가 **새 토큰을 만든** 횟수
- `확보` — 확보 호출 횟수

### 0-4. ★ 준비물은 프로덕션 파생 함수로 만들지 않는다

`For(U)o`·`Ren(T←U)o`·`Own(T)o`를 `ReservedBarOwnership`의 파생 함수로 파일명을 계산해 심으면 **파생이 망가졌을 때 준비물도 같이 망가진다.** 예를 들어 꼬리가 상수로 돌아가면 U와 T 흔적이 한 경로에 겹쳐 심기고, 테스트는 그 겹친 세상을 잰다(TEAM.md 「생성기와 검사기가 같이 틀린다」).

그래서 준비물은 **실제 경로를 실제로 돌려** 만든다:
- **`For(U)o`** — 같은 폴더에서 저장소 U·AH=ON으로 `크래시`. 디스크에 생긴 파일 이름을 **폴더 열거로** 얻는다.
- **`Own(T)o`** — 저장소 T로 같은 방식.
- **`Ren(T←U)o`** — (1) 저장소 T·AH=ON으로 `기동`+`정상종료`해서 T 이름의 닫힌 파일을 얻는다. (2) U로 `크래시`해서 U 파일의 바이트를 얻는다. (3) T 이름 파일을 **U 파일 바이트로 덮어쓴다**. (4) U 이름 파일은 이 준비물에서 **다른 폴더로 옮겨** 치운다(삭제가 아니라 옮기기다. 테스트 코드라 원칙 3 감사 대상 밖이지만 관례를 따른다).
- **`OwnN`** — `Own(T)o`를 만든 뒤 JSON의 `version`만 `CurrentVersion + 1`로 바꿔 쓴다.

- `ReservedBarRevealDirector.cs:102`의 쉬기 조건은 `NewerSchema`·`ForeignPlatform` **둘뿐**이다. `Unreadable`은 통과해 `:189` 판정으로 간다. 자동 숨김이 켜져 있으면 `:204` `Open` → `ReservedBarRestoreLedger.cs:231` `FileMode.Create`가 그 파일을 **0바이트로 자르고 덮는다.**
- 그런데 두 문장이 그 거동과 **어긋난다**:
  - `ReservedBarRestoreLedger.cs:184-185` 경고 — *"없는 것으로 취급합니다 — 이번 실행은 시스템 설정을 바꾸지 않습니다."*
  - `:228-230` 주석 — *"다음 실행이 Unreadable로 읽고 '시스템을 바꾸지 않는다'로 가므로"*
  - `:164`(빈 파일)과 `:167`(`version < 1`)의 `Unreadable`은 경고조차 없다.
- 흔적 쓰기는 `FileMode.Create` → `Write` → `Flush(true)`다. **원자적이지 않다.** 자르기와 쓰기 사이에 끊기면 새 내용의 앞부분만 남는다.
- ★ **`ReservedBarLedgerState.Unreadable`을 참조하는 테스트는 0건이다.** 측정 `grep -rn "ReservedBarLedgerState.Unreadable" Tests` → 0. 같은 명령의 `ReservedBarLedgerState\.` 양성 대조와 없는 상태 이름 음성 대조 결과는 6절에 적는다. **이 분기는 한 번도 잠긴 적이 없다.**

**물리 분석 — 추론이다, 실측이 아니다.** write-ahead 순서에서 흔적 쓰기 5곳이 끊기는 순간의 시스템 값은 이렇다.

| 쓰기 | 자리 | 끊기는 순간 시스템 | 반쯤 쓰인 파일을 다음 실행이 만나면(현재 코드) |
|---|---|---|---|
| w1 기동 열기 | `Director:204` | 아직 안 바꿨다 = 원래 값(켜짐) | 켜짐 관측 → 해제 진행·덮어씀. **값은 옳다**, 증거만 사라진다 |
| w2 해제 실패 뒤 닫기 | `Director:226` | 안 바뀌었다(켜짐) | 같음 |
| w3 복구 뒤 닫기 | `Director:149` | 이미 복구했다(켜짐) | 같음 |
| w4 종료 원복 뒤 닫기 | `Director:276` | 이미 원복했다(켜짐) | 같음 |
| w5 레거시 v1 닫기(신규) | 구현 예정 | 이미 복구했다(켜짐) | 고정 이름이라 토큰 빌드는 덮지 않는다(TK-06) |

- **프로세스 강제 종료 모델**에서는 「반쯤 쓰인 흔적 ⇒ 시스템이 원래 값」이 성립한다. 그래서 현재의 통과 거동이 **사용자 설정을 틀리게 만드는 경로는 찾지 못했다.** 거짓인 것은 로그·주석 문장이고, 잃는 것은 증거다.
- ★ **전원 차단 모델에서는 그 등식이 깨질 수 있다(가설, 미확인).**
  - 셸이 `ABM_SETSTATE`로 바뀐 값을 **재부팅 뒤에도 남도록** 언제 디스크에 반영하는지 모른다.
  - w3·w4에서 「런타임은 켜짐으로 복구, 지속 값은 아직 꺼짐」인 채 전원이 나가고 흔적도 반쯤 쓰였다면, 재부팅 뒤 상태는 **흔적은 읽을 수 없음 + 시스템은 꺼짐**이다.
  - 현재 코드는 이것을 `AlreadyVisible`로 지나쳐 **고아**를 만든다.
  - (가)는 보존·쉬기로 바꿀 뿐 **갚지 못한다** — 원래 값을 읽을 수 없기 때문이다.
  - **옛 온전한 열림 흔적이 남아 있어야 갚는다. 즉 이 경로는 (나)만 구한다.**
  - 체크표 §R의 ◐ 「세션 한정」 칸(`WINDOWS_CHECK_SESSION.md:304`)이 같은 미지(셸 반영 시점)를 다룬다.
- 이 분석은 설계 선택의 판단 자료다. **아래 사례는 재기만 하고 고르지 않는다.**

**준비물 — 모든 접두부 길이 전수**(세이브 H2′ T7과 같은 방식. `Tasklist.md:27219`에 계획으로만 있고 테스트는 미착지다. 현존 세이브 사망 주입은 `SavePreviousGenerationTests.cs:212,247`의 **고정 40바이트** 한 점뿐이다)
- **원본 바이트는 네 벌이다.** 전부 디스크에서 읽고, 손으로 조립하지 않는다.
  - (a) 자기 v2 열림 — T로 `크래시`해 생긴 파일
  - (b) 자기 v2 닫힘 — T로 `기동`+`정상종료`
  - (c) 레거시 v1 열림 — 골든(G-6)
  - (d) 레거시 v1 닫힘 — 골든 닫힘, 그리고 새 빌드가 TK-01에서 실제로 쓴 바이트(구현 산출물)
- **길이** L = 0, 1, …, N(N = 원본 길이).
  - ★ **L = N은 양성 대조**다. 온전한 흔적이 정상 판정을 내지 않으면 준비물이 틀린 것이고, 그 행 전체를 무효로 처리한다.
  - L = 0(과 공백만 남은 경우)은 Q-10에서 따로 판정한다.
- **각 L마다**:
  1. 흔적 경로에 앞 L바이트를 쓴다. 자기 흔적은 열거로 얻은 T 이름, 레거시는 `〈레거시 파일명 상수〉`다.
  2. Director를 리셋한다.
  3. 자동 숨김 켜짐 / 꺼짐을 **각각 새 폴더 복제에서** 돌린다.
  4. 계수한다.
- **변형(선택) — 영채움**: 앞 L바이트 뒤를 `0x00`으로 채워 원래 길이를 맞춘다. 크기 메타데이터만 반영되고 데이터는 안 내려간 전원 차단 모양이다(가설). `0x00`은 `string.IsNullOrWhiteSpace`의 공백이 아니므로 `Ledger:164` 가드를 타지 않는다.
- **기록 칸**: L · 분류(`ReservedBarRevealDirector.LastLedgerState`/O-4) · R · V · 흔적 바이트 불변 · 폴더 파일 수 · **다음 실행 판정**.
  - 다음 실행 판정 = 이번 실행을 `크래시`로 끝내고 리셋한 뒤, 이번 실행이 남긴 자동 숨김 값으로 한 번 더 기동했을 때의 분류와 R/V.
  - 전 행을 `[흔적절단] 원본=… L=… AH=… 분류=… R=… V=… 불변=…` 한 줄씩 로그로 남긴다(거짓 통과 판독용 표).
- ★ **관대한 파서 함정.** `JsonUtility`가 잘린 JSON을 **거절하는지, 빈 필드를 기본값으로 채워 받아들이는지** 이 명세는 모른다(미확인).
  - 그래서 불변식을 「L < N이면 전부 `Unreadable`」로 **가정하지 않는다.**
  - 불변식은 이것이다: **L < N인 어떤 접두부도 원본과 다른 `active`·`originalAutoHide`·소유 표식을 가진 흔적으로 분류되지 않는다.**
  - 이유: `"active": true` 직후에서 잘린 조각이 `active` 누락 → 기본값 `false` → `Closed`로 읽히면 **빚이 조용히 사라진다.** 레거시 v1 필드 순서(`version, active, originalAutoHide, …` — `Ledger:36-52` 선언 순서 = `JsonUtility` 출력 순서, 구현 시 골든으로 확인)상 이런 자리가 실제로 있다.

### G-2. 임시 폴더 · 폴더 전수 단언
- 테스트마다 새 폴더를 쓴다: `ReservedBarRestoreLedger.RedirectToTemporaryDirectoryForTesting(<라벨>-<GUID 8자>)`(기존 관례 `ReservedBarRevealPolicyTests.cs:71-72`).
- ★ **흔적 부재는 파일명이 아니라 폴더 전수로 단언한다.**
  - 기존 `Assert.IsFalse(File.Exists(ReservedBarRestoreLedger.FilePath))`(`:231`, `:340`)은 새 구조에서 **조용한 초록**이 된다. `FilePath`가 고정 이름을 가리키는 한 새 빌드는 거기에 아무것도 안 만들기 때문이다(CLAUDE.md 「부재 단언은 썩으면 조용히 초록」).
  - 스냅샷 헬퍼는 `Directory.GetFiles(<O-3 폴더>)` 전수를 대상으로 (이름, 길이, SHA-256, `LastWriteTimeUtc`)를 기록한다.
  - 헬퍼 자체의 **존재 대조**: 알려진 파일 1개를 넣었을 때 1을 센다.
- 바이트 불변 판정의 1순위는 **길이 + SHA-256**이다. `LastWriteTimeUtc`는 보조다(verify-change 4차: 이 러너는 파일 속성 일부만 반영한다).

### G-4. 가짜 토큰 저장소
- 메모리 문자열 하나를 들고 호출 수를 센다: 읽기, 확보, **생성**(없어서 새로 만든 횟수).

## 5. Windows 실기 1건 — 절차 초안 (체크표 반영은 qa-regression 몫, 리더 경유)

> ### ⛔ 전제 — 토큰이 이미 있는 기계에서 하면 이 시험은 **무효**다
> 토큰이 이미 있으면 재실행은 **앞선 정상 종료로 이미 디스크에 내려간 토큰**을 읽는다. 강제 종료 직전의 `PlayerPrefs.Save()`가 레지스트리에 실제로 닿았는지는 **한 번도 재지 않은 초록**이 나온다(architect 3절 ④).
> 「토큰 없음」은 아래 0-c에서 **값 이름 목록으로 확인한 뒤에만** 시작한다.

**무엇을 재나**: 첫 토큰 생성 → `Save()` → 흔적 열기 → 해제 직후 프로세스가 끊겨도 토큰이 레지스트리에 남아 다음 실행이 **자기 흔적으로 알아보고 갚는가.**
**무엇을 못 재나**: ① 전원 차단(레지스트리 지연 반영 — S-7-7 표 「수 초 안 전원 차단」, 시간 미확인) ② 두 인스턴스 경합 ③ `GetString` 캐시 여부 자체 ④ **반쯤 쓰인 흔적**(1-J) — 사람 손으로 쓰기 도중 사망을 바이트 단위로 맞출 수 없다. EditMode TK-80~86이 유일한 계기다. 셸이 자동 숨김 값을 재부팅 뒤에도 남도록 반영하는 시점(1-J 전원 차단 가설)도 이 절차로는 못 잰다 — 체크표 §R R-1(「다시 시작」 판독)의 ◐ 칸이 가장 가까운 관측이다.

### 0. 준비 (앱을 켜기 전)
- **0-a 빌드 확인** — `StickMate_Data\Managed\StickMate.Runtime.dll`의 `LastWriteTime`이 리더가 준 시각과 같다(TEAM.md 거짓 통과 #7). 인스턴스 0: `Get-Process StickMate -ErrorAction SilentlyContinue` → 0줄.
- **0-b 레거시 흔적 먼저 치운다** — 고정 이름 `…\LocalLow\Vibelab\StickMate\stickmate_reserved_bar_restore.json`이 있고 `active = True`면, 이 시험의 `★ 복구` 줄이 **레거시 갚기와 섞여** 판독이 무효가 된다.
  - 순서: 앱 1회 실행 → 트레이 종료 → `False` 확인.
  - ★ **이 1회 실행이 토큰을 만든다. 그래서 0-b는 반드시 0-c보다 먼저다.**
- **0-c 토큰 없는 상태 만들기** — 둘 중 하나. **어느 쪽이든 사용자 동의 + 리더 승인 뒤.**
  - **(A) 새 Windows 로컬 계정**(권장) — 사용자 레지스트리를 한 줄도 안 건드린다. 비용은 계정 생성과 그 계정의 자동 숨김 설정.
  - **(B) 토큰 값 하나만 제거**
    - ★ **촬영 절차와의 관계부터 적는다.** 촬영 절차 R12(`CAPTURE_PROTOCOL.md:266-285`)는 이 키에서 **토큰일 수 있는 값을 지우지 않는다**고 적는다. (B)는 그 금지의 **명시적 예외**이고, 조건은 셋이다. ① 이 검증 세션 한정 — 사용자 동의 + 리더 승인 뒤, **촬영 세션과 같은 날·같은 계정에서 섞지 않는다** ② 아래 「(B) 전 추가 확인」(토큰 파생 흔적이 전부 닫힘)을 통과해야 한다 — 촬영 절차가 그 값을 지우지 못하게 한 이유가 「열린 흔적의 고아화」인데, 그 이유를 이 조건이 먼저 없앤다 ③ 지우는 것은 토큰 값 **하나**다. R12의 나머지 금지는 그대로 따른다: **키 통째 삭제 금지 · 다른 기계·다른 계정 `.reg` 가져오기 금지 · 온보딩 값(`StickMate.GearMenu.OnboardingSeen.v1_h*`)은 건드리지 않는다**(R12가 비우는 대상이고, 이 시험의 판독과 무관하다).
    - 먼저 백업한다(**비상용 — 평상시 되돌리기에 쓰지 않는다**, 아래 「끝낸 뒤」). 자리는 R12 백업과 같은 부모 폴더다. **바탕화면에 두지 않는다** — 촬영 절차가 바탕화면 아이콘 0개를 요구하고, 촬영 화면에 사용자 자산이 찍힌다(`CAPTURE_PROTOCOL.md` 2-3 ③). 이름은 촬영 백업과 헷갈리지 않게 따로 붙인다:
      `$B = "$env:USERPROFILE\AppData\LocalLow\Vibelab"; $T = Get-Date -Format yyyyMMdd-HHmmss; reg export "HKCU\Software\Vibelab\StickMate" "$B\prefs.tokentest-backup-$T.reg"`
    - ★ **이 파일에는 토큰 값이 들어간다 — 이 PC 밖으로 옮기지 않는다. 내용을 메모·채팅·버그 신고에 붙이지 않는다**(R12 `:279`와 같은 문구). 값 **이름만** 기록한다: `(Get-Item -LiteralPath 'HKCU:\Software\Vibelab\StickMate').Property | Sort-Object`
    - 그다음 토큰 값 **하나만** 지운다. ★ **키 전체를 지우지 마라** — 온보딩 「봤음」과 Unity 창 설정도 같은 키에 있다.
    - ★ Unity는 Windows에서 값 이름에 `_h<해시>` 꼬리를 붙인다(Unity 6 문서: *"DeckBase_h3232628825"*). 그래서 **정확한 이름으로는 못 찾는다.** `<토큰 키 이름>_h*` 패턴으로 찾는다. 키 이름은 구현 코드의 `〈토큰 키 상수〉`에서 옮긴다 — **추측 금지**.
    - ★ (B) 전 추가 확인: 폴더의 토큰 파생 흔적이 **전부 `active = False`**여야 한다. 열린 것이 있으면 토큰을 지우는 순간 **이 절차가 고아를 만든다.**
  - **판독**(값 이름만 찍는다. **값은 절대 출력하지 않는다** — 로그·스크린샷 금지 규칙과 같다):
    - 토큰 패턴 일치 수 **= 0**.
    - **양성 대조**: 같은 명령으로 `Screenmanager*_h*` 일치 수 **≥ 1**(Unity 플레이어가 쓰는 값. 이 머신의 macOS plist에 `Screenmanager …` 키가 실재한다 — Windows 실측은 아직 없다).
    - 대조가 0이면 **판독 무효로 리더에게** 넘긴다. 경로를 잘못 봤을 수도 있고, Windows 플레이어가 `Screenmanager` 계열을 아예 안 쓸 수도 있어 둘을 가를 수 없다(R12 `:283`과 같은 처리). 경로 쪽은 회사명 칸부터 본다 — 2-3 확인 줄의 폴더가 `Vibelab`인가(R12 `:277`).
- **0-d 흔적 폴더 목록** — 토큰 파생 이름 파일 **개수**만 적는다(이름은 적지 않는다).
  - ★ `Get-ChildItem -Filter`에 와일드카드 두 개짜리 패턴을 쓰지 마라. Win32 8.3 짧은 이름 매칭이 끼어든다.
  - `Where-Object { $_.Name -match '<구현이 정한 파생 이름 정규식>' }`으로 거르고, 고정 이름이 **안 걸리는지**(음성 대조)와 파생 이름이 **걸리는지**(양성 대조)를 먼저 보인다.
- **0-e** 작업표시줄 자동 숨김 **ON** 확인.

### 1. 첫 해제 직후 강제 종료
1. PowerShell 창 하나에서 `Get-Content "$env:USERPROFILE\AppData\LocalLow\Vibelab\StickMate\Player.log" -Wait -Tail 0`으로 대기한다.
2. 앱을 실행한다.
3. `[작업표시줄] ★ … 이번 실행 동안만 해제했습니다` 줄이 뜨면 **즉시**(목표 5초 이내) 작업 관리자 → StickMate → **작업 끝내기**.
   - 대안 `Stop-Process -Name StickMate -Force`는 같은 강제 종료 경로로 판단한다(미확인).
   - 끊은 시각을 적는다.

### 2. 앱을 켜기 전 판독
- ① 막대가 **보이는 채**다(정상 — 종료 훅이 안 돌았다).
- ② **토큰 패턴 일치 수** — 0-c 명령으로 = 1. ★ **이 시험의 본체다.**
- ③ 토큰 파생 흔적 개수 = 0-d + 1, 그 파일의 `active = True`.
- ④ 고정 이름 레거시 파일 0-b 상태 그대로.
- ⑤ `Player.log`를 바탕화면 `StickMate확인\T-1-Player.log`로 복사한다(켜는 순간 `Player-prev.log`로 밀린다).

### 3. 재실행 → 판독
재실행 뒤 `Player.log`에서 센다(문장은 구현의 O-4 정의처에서 옮긴다 — 아래 괄호는 자리 표시일 뿐 판독 문자열이 아니다):

| 줄 | 기대 |
|---|---|
| 소유 일치 문장(`소유=일치` 자리) | **≥ 1** |
| `[작업표시줄] ★ 복구 —` | **≥ 1** |
| 레거시 갚기 경고 | **0** (0-b가 살아 있다는 확인) |
| 소유 불일치 문장 | **0** |
| (양성 대조) `이번 실행 동안만 해제했습니다` | **≥ 1** — 0이면 판독 무효 |
| (가림 확인) `stickmate_reserved_bar_restore.` 뒤에 꼬리가 붙은 문자열 · `LocalLow` 경로 | **0** — 양성 대조: `[작업표시줄]` 태그 ≥ 1 |

작업표시줄은 복구로 **한 번 숨었다가** 이번 실행 해제로 다시 보여야 한다(깜빡임 1회).

### 4. 트레이 종료 → 판독
자동 숨김 **ON**으로 복귀 · 토큰 파생 흔적 개수 **변화 없음**(재사용) · 그 파일 `active = False`.

### 판독 2×2 — ② 토큰(끊은 뒤) × 3 `★ 복구` 줄

| | **복구 줄 있음** | **복구 줄 없음** |
|---|---|---|
| **토큰 있음** | ✅ 설계 가정 성립 | ❌ 토큰은 남았는데 자기 흔적으로 못 알아봄 → **소유 판정 결함**(리더 → debugger) |
| **토큰 없음** | ⚠ 있어서는 안 되는 조합 → 레거시 줄 오인이나 로그 혼입. 판독 무효 | ◐ `Save()`가 끊기기 전 레지스트리에 안 닿았다 → **고아**. 실패 방향은 안전(남의 설정 불변)이지만 **S-7-7 조건 2의 전제가 무너진 것** → 즉시 리더 |

### (선택 · 리더 승인) 음성 대조 T-2 — 판독이 「불일치」를 실제로 가르는가
1. 4 뒤에 1을 한 번 더 한다(열린 흔적 1개).
2. 앱이 꺼진 상태에서 토큰 값 **이름**을 `…_bak`으로 바꾼다.
3. 재실행 → 소유 불일치 ≥ 1 · `★ 복구` **0** · 막대가 보이는 채(고아 흉내).
4. 트레이 종료 → 값 이름 원복 → 재실행 → `★ 복구` ≥ 1.

대가: 사용자 작업표시줄이 3~4 사이 보이는 채로 있고, 레지스트리 이름 바꾸기가 2회.

### 끝낸 뒤 — ★ (B)를 썼다면 백업을 **되돌리지 마라**
`reg import`는 **옛 토큰**을 되살려 새 토큰을 덮는다. 새 토큰으로 열린 흔적이 하나라도 남아 있으면 **그 순간 고아가 된다.** 새 토큰을 그대로 두고 백업 파일(`prefs.tokentest-backup-<시각>.reg`)은 **이 PC 안에** 보관만 한다. R12와 같은 규칙이다 — 백업은 비상용이고 평상시 되돌리기에 쓰지 않으며, 비상 복구도 리더 승인 뒤에만 한다. 같은 기계의 자기 백업이라도 가져오기 전에 리더에게 묻는다(다른 기계·계정의 `.reg`는 R12대로 **금지**).

Unity 6 문서상 에디터 PlayerPrefs 자리는 플레이어와 다르다.

## 플랫폼 영향

- **Windows 영향: 별도 배정 필요(구현 라운드).** 명세 대상 코드는 전부 `Platform/` 중립 위치이고 `Platform/Windows/` 수정 요구는 0이다(A-4가 diff 0을 관문으로 건다). 실기 1건(5절)과 판독 문서 7곳 갱신이 따라온다. ★ 1-J에서 (나)·(다)를 택하면 **Windows에서만 드러나는 실패**가 하나 더 붙는다: `File.Replace`가 대상에 삭제 공유 없는 핸들이 열려 있으면 1175로 거절한다(세이브가 실기에서 이미 밟았다, `CharacterSaveStore.cs:1142-1164`). 이 머신에서는 재현이 안 되므로 O-8 강제 주입(TK-84)과 `FileShare.Delete` 읽기 확인(A-7 비고)으로만 잰다. 이 라운드의 코드 변경은 0줄이다.
- **macOS 영향: 없음(동작) / 테스트로 잠금 필요.** 제어기가 null이라 토큰도 흔적도 없어야 하고, 신규 중립 파일이 macOS에도 컴파일되므로 TK-50·A-3으로 **저장소 호출 0**을 잠근다. 에디터 PlayMode의 `BeforeSceneLoad`가 매 러너 실행에서 이 경로를 태우므로, 뚫리면 개발자 plist에 토큰이 쓰인다.
