### 2-4. ★ 조각이 늘 때 **어디가 먼저 아픈가** — 순서를 확정한다

브리프의 질문(드로콜? 정점? 재질 전환?)에 대한 답: **셋 다 아니다. 1순위는 CPU 쪽 매 프레임 순회다.**

#### (a) 재질 전환 — **아프지 않다** (M)
액세서리 선·채움은 **전부 캐릭터 `LineRenderer`의 `sharedMaterial` 한 장을 빌려 쓴다**
(`CharacterAccessoryRenderer.ResolveLineMaterial()` → `AddLine`의 `lr.material = _lineMaterial` / `AddFill`의 `mr.sharedMaterial = _lineMaterial`).
**몸 표면에서 재질은 1장이다. 조각을 아무리 늘려도 재질 전환은 0회.**

> ⚠ **잠재 위험 1건(지금은 비용 0)**: 두 자리의 문법이 다르다 — 선은 `lr.material`, 채움은 `mr.sharedMaterial`.
> `Renderer.material`은 **게터가 호출되는 순간 머티리얼을 복제한다.** 지금은 세터만 쓰므로 안전하지만,
> 앞으로 누가 진단 목적으로 `lr.material`을 **읽으면** 그 순간 렌더러 20여 개가 각자 인스턴스를 갖고
> **드로콜이 조각 수만큼 늘어난다.** ⇒ `AddLine`도 `sharedMaterial`로 통일 권고(거동 변화 0).

#### (b) 드로콜 — **조각 수의 함수가 아니다** (M + E)
액세서리는 **정렬 순서로 묶인다**. 사용 중인 값은 `SortBack(-1)` / `SortCapeFront(3)` / `SortHair(6)` / `SortNeck(7)` / `SortEyes(8)` / `SortHead(10)`이고, **채움은 그 −1**(`Shape.FillSortingOrder => SortingOrder - 1`, `AccessoryShapeBuilder.cs:1202`)이다.
⇒ **서로 다른 정렬 순서는 최대 12개.** 같은 순서·같은 재질끼리는 배칭 후보다.
⇒ 드로콜 **하한 12 / 상한 43**(배칭이 하나도 안 붙는 경우). **조각 43개가 43 드로콜이 되지는 않는다.**
★ 실제 배치 수는 **U**(§6-1).

#### (c) 정점 — **아프다. 그런데 원인이 좌표 수가 아니라 설정 하나다** (M + E)

**(c-1) `numCornerVertices = 4`가 코너마다 둥근 조인을 굽는다** (`CharacterAccessoryRenderer.cs`의 `AddLine`).
인계본 폴리라인은 **이미 잘게 쪼개진 호**다. 실제 꺾임각을 전수로 쟀다(몸 표면 선 조각 56개, 표본 1,529개):

| 통계 | 값 |
|---|---|
| 중앙값 | **4.25°** |
| p75 / p90 / p95 | 7.25° / 15.00° / 15.01° |
| **15° 이하** | **89.5%** |
| 45° 초과 | 3.5% |

출하 배율 0.75에서 액세서리 선은 **1pt 하한**에 걸린다(`StickConfig.MinAccessoryStrokeScreenPoints = 1f`, `:1982`).
15° 코너에서 조인이 만드는 어긋남은 `(폭/2)·tan(θ/2) = 0.5 × tan 7.5° =` **0.066pt** — **1픽셀의 1/15이다.**
⇒ **89.5%의 코너에서 `numCornerVertices=4`는 화면에 아무것도 만들지 않는다.**

정점 추정(**E** — Unity `LineRenderer` 확장식 `2N + c·코너 + 2k·캡`을 가정):

| 아이템 | `c=4`(지금) | 코너 20° 이하 조각만 `c=0` | 절감 |
|---|---:|---:|---:|
| `wings` | 1,446 | 1,154 | 20% |
| `goggles` | 924 | 340 | **63%** |
| `sunglasses` | 1,146 | 414 | **64%** |
| `crown` | 600 | 312 | **48%** |
| 12종 합계 | **9,630** | **5,910** | **−39%** |

**(c-2) ★ 그리고 그 정점을 매 프레임 다시 굽는다 — `alignment`가 설정돼 있지 않다** (M: 미설정 / E: 비용)

```
grep -rn "alignment|LineAlignment" CharacterAccessoryRenderer.cs SceneBootstrapper.cs CharacterPortraitStage.cs
→ 0건.  useWorldSpace만 설정한다.
```
`LineRenderer.alignment` 기본값은 **`LineAlignment.View`** = *"선 메시를 카메라를 향하도록 굽는다"*.
직교 2D 오버레이에서 이것은 **결과가 같은데 매 카메라·매 프레임 지오메트리를 다시 만드는 것**이다.
그리고 **정보창이 열리면 카메라가 2대**다(메인 + 초상화 촬영장, §2-7).
⇒ `alignment = LineAlignment.TransformZ`가 안전한 후보다. 컨테이너 회전은 **Z축 회전뿐**(상체 기울임)이라 평면이 안 바뀐다.
⚠ **실기 캡처 대조 없이 바꾸지 마라** — 「같은 그림인가」는 계산이 아니라 눈으로 닫아야 한다(§6-2).

#### (d) ★ **1순위 — 매 프레임 렌더러 순회 + 힙 할당** (M)

`CharacterAccessoryRenderer.LateUpdate()`는 알파 > 0.001인 **모든 프레임에** 아래를 돈다:

| 함수 | 하는 일 | 조각 수와의 관계 |
|---|---|---|
| `SetLinesEnabled(true)` | `_lines` + `_fills` 전수 순회, `enabled` 비교 | **선형** (43회 네이티브 프로퍼티 읽기) |
| `TickHemMotion()` | 흔들 구간이 있는 선만 (지금 **2개**: 망토 2종) | 상수 |
| **`ApplyAlpha()`** | `_lines` 전수 + **`_fillMeshes` 전수** | **선형 + 힙 할당** |

★★ **`ApplyAlpha()`의 실제 결함** (`CharacterAccessoryRenderer.cs:1374`, 게터는 `:1393`):

```csharp
for (int i = 0; i < _fillMeshes.Count; i++)
{
    Mesh mesh = _fillMeshes[i];
    if (mesh == null) continue;
    Color[] colors = mesh.colors;          // ← ★ 게터가 매번 새 배열을 딴다
    if (colors == null || colors.Length == 0) continue;
    if (Mathf.Approximately(colors[0].a, _alpha)) continue;   // ← 조기 반환이 할당 '뒤'에 있다
```

`Mesh.colors`는 **게터가 복사본을 돌려주는 Unity API**다. 조기 반환 가드가 **할당 다음 줄**에 있어
**값이 하나도 안 바뀌는 프레임에도 정점 수만큼 `Color[]`를 새로 딴다.**

| | 이식 전 | **지금** | 등급 |
|---|---:|---:|---|
| 채움 메시 | 7 | **21** | **M** (양쪽 다 셌다) |
| 채움 정점 합 | ≈70 | **639** | 전=**E**(v1 도형이 절차적) / 후=**M** |
| **프레임당 할당** | ≈1,120 B | **10,224 B** | 전=E / 후=**M** |
| 초당(60fps) | ≈0.067 MB/s | **0.613 MB/s** | |
| 하루(24시간 상주) | ≈5.8 GB | **53.0 GB** (= 49.4 GiB) | |

```
DisplayOff  →  Suspended  →  Away(180초 무입력 ∧ 캐릭터 Idle)  →  ★ uiInteractionActive → Active  →  Still  →  Calm
```
`if (uiInteractionActive) return FramePacingTier.Active;`가 **`characterStill`보다 위**에 있다. ⇒ **홀드가 Still을 이긴다. 확정.**

⚠ **295 프레임은 「최대 절감」이지 「평균」이 아니다** (정직한 한정):
- Still에 들어가려면 `characterStill`, 즉 캐릭터가 **`FramePacing.StillDwellSeconds = 1.6초`** 이상 서 있어야 한다.
  부채꼴을 여는 순간 캐릭터가 걷고 있었다면 그 1.6초는 홀드가 없어도 Active다.

★ **이것은 결함이 아니다.** 홀드의 근거가 클래스 주석에 명시돼 있다 —
*"부채꼴이 떠 있다 = 사용자가 지금 이것을 겨누고 있다는 **관측된 사실**"*. **반응성을 위해 의도적으로 산 비용이다.**

**다만 6.0초는 「반응성을 위한 시간」이 아니라 「사용자가 아무것도 안 하는 시간」이다.**
전체 사이클 6.56초 중 **91.5%가 무반응 구간**이고, 그 동안 프레임을 붙잡을 근거는 «곧 누를지도 모른다» 하나다.

⇒ **제안(리더·`ux-widgets` 판정 사항, 성능 단독 결정 아님)**:
무반응 타이머가 **일정 시간(예: 2초)을 넘긴 뒤에는 홀드를 놓는다.** 커서가 움직이거나 호버가 생기면
`KeepAlive`가 이미 타이머를 되돌리므로 **즉시 Active로 복귀한다**(0.5초 홀드 재취득).
효과: 홀드 구간 6.56s → **2.56s(−61%)**. 접힘 연출(0.26s)은 이미 알파만 바꾸는 «제자리에서 스르르»라 등급이 내려가도 끊기지 않는다.
⚠ **반증 가능성**: Still 등급에서 15fps로 그려지는 0.26초 페이드가 **계단으로 보일 수 있다.** 이건 계산이 아니라 눈으로 닫아야 한다(§6-6).

### 4-3. ★ 예산을 넘는지 **못 재는 항목이 두 개** — 그것이 이 라운드의 정직한 결론

*"5.8ms × N = …"* 이라고 쓰고 싶은 유혹이 있지만 **그 N을 이 문서는 갖고 있지 않다.**
두 겹으로 모른다:
1. **분자를 모른다** — 이식 전 카드 16장의 오브젝트 합계를 못 셌다(v1 도형이 절차적). 정확한 대조는 `HeadCap` **한 종(×3.7)**뿐이다.
2. **곱셈이 성립하는지도 모른다** — uGUI 캔버스 재빌드는 정점 정렬(O(n log n))과 배치 병합이 섞여 선형이 아니고,
   `RectMask2D` 컬링이 어느 단계에서 끊는지에 따라 결과가 갈린다.

⇒ **§6-1을 돌리기 전까지 「정보창이 예산을 넘는다」고 쓰지 않는다.**

다만 **방향은 확정적이다**: 조각 수가 늘고 조각당 점 수가 늘었는데(`HeadCap` 카드 20선분 → 82선분)
재빌드 시간이 **줄어들 경로가 없다.** 실측이 필요한 것은 **부호가 아니라 크기**다.

## 7. 플랫폼 영향

- **macOS 영향: 없음(코드 변경 0건).** 이 문서는 분석이고 §5는 전부 제안이다.
- **Windows 영향: 없음(코드 변경 0건).** 다만 **§5의 처방을 착수할 때는 Windows도 같은 라운드에서 봐야 한다**:
  - **P0-1 / P1-1 / P1-2 / P2-2**는 `Interaction/` — **플랫폼 중립**이다. 분기 없음. `xcheck.sh win`/`osx` 양쪽 0에러만 확인하면 된다.
  - ★ **P1-3(`alignment`)은 `Assets/Editor/SceneBootstrapper.cs`를 건드린다.** 이 파일은 프리팹을 굽는 자리라 **양쪽 타깃에서 같은 프리팹이 나와야 한다.** 타깃 전환은 리더 승인 사항(`CLAUDE.md` 활성 빌드 타깃 규칙).
  - ★ **P2-1(프레임 홀드)은 플랫폼 거동이 갈릴 뻔한 자리인데, 실측 결과 지금은 갈리지 않는다.**
    `FramePacingPolicy.BuildPlan`이 **보는 사람이 있는 등급에서는 플랫폼 분기 없이 `renderFrameInterval`만 나눈다**
    (`Platform/ViewerPresence.cs:533-540`, 주석 원문 *"**플랫폼 분기가 없다** — Windows도 이 경로를 쓰도록 바뀌었다"*).
    ⇒ 홀드 해제 효과는 **두 플랫폼에서 같다.** 다만 **Windows BitBlt는 present마다 표면 전체를 복사**하므로
    (`ARCHITECTURE.md` 측정 한계 절) **절감의 절대값은 Windows 쪽이 더 클 가능성이 높다 — 미확인.**
  - ★ **문서 정정 1건(플랫폼 서술)**: `PERFORMANCE_NOTES.md:385`의 *"Windows에서 Calm은 `targetFrameRate`를 60→30으로 나눈다"*는 **현행 코드와 다르다.** 그 문장을 근거로 Windows 절감을 계산하면 안 된다.
- **모바일(iPad/iPhone)**: 스크린샷 백드롭 모드에도 **장비 렌더러와 카드 UI는 그대로 간다.**
  §5의 처방은 전부 모바일에 유효하고, **P0-1(GC)·P1-1(0.35 컬링)·P0-2(RT)는 모바일에서 더 크게 이긴다**
  (모바일 GPU 대역폭·GC 예산이 데스크톱보다 좁다). **미측정.**
