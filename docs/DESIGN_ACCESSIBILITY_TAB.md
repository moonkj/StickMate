## 0. 착수 전 영향도 — 먼저 낸다 (내 정의서의 선행 조건)

닿는 표면·테스트·문서를 앵커로 열거한다. 없으면 없다고 적는다.

| 닿는 것 | 앵커 | 무엇이 바뀌는가 |
|---|---|---|
| 설정창 탭 개방 판정 | `Interaction/SettingsWindow.cs` `IsTabReady` | `Tab.General`·`Tab.Character` 두 값만 참인 함수. 접근성 탭 개방 = 이 함수에 값 하나 추가 |
| 플레이스홀더 본문 | 같은 파일 `BuildPlaceholderTab` · `PlaceholderLabel` | `Tab.Accessibility` 분기가 죽고 실제 본문 빌더로 갈린다 |
| 탭바 배지 | 같은 파일 `TabBadgeText` · `TabBadgeGap` | 배지 1개가 사라진다. 탭바가 **좁아진다**(§7) |
| 세이브 스키마 | `Core/CharacterSaveStore.cs` `CurrentVersion` (현재 13) | 신규 필드가 들어간다 → v14. 하위 호환 테스트 1건 동반 필수 |
| 앱 설정 모델 | `Core/AppSettingsModel.cs` | 값이 사는 자리. `StickConfig`에는 절대 안 쓴다 |
| 프레임 페이싱 | `Platform/ViewerPresence.cs` `ShouldApplyLowPowerDownshift` | 저전력의 **기존 주인**이다. 새 축을 만들지 않고 이 술어에 사용자 의사를 합류시킨다 |
| 사운드 행 예정지 | `design/sound/SILENCE_POLICY.md` §6-2 | 같은 탭을 이미 예약해 두었다. **공동 소유** — §7-3 |
| 탭바 조형 규약 | `docs/UI_SURFACE_SPEC.md` §12 | 배지 치수·좌표·대비 표. 접근성 탭 행이 거기 있다 |

(`CharacterSaveStore.cs`가 그 규칙을 못박아 뒀다 — 「문을 닫는 것은 커밋이 아니라 빌드다」).
그래서 §2-4에 **필드를 한 라운드에 전부 넣는 안**을 낸다.

## 1. ★ 리더 전달값 반박 3건 — 착수 전에 먼저 읽어야 한다

### 1-1. 「지금 저장소에 접근성 축을 다루는 표면이 없다」는 거짓이다

`Interaction/SettingsWindow.cs`가 이미 들고 있다:

```
public enum Tab { General = 0, Character = 1, Event = 2, Accessibility = 3, Data = 4 }
TabNames  = { "일반", "캐릭터", "이벤트", "접근성 · 성능", "데이터" }
TabEyebrows[3] = "내 눈과 내 컴퓨터에 맞추기"
```

**표면은 있다. 본문이 비어 있다.** 판정은 한 함수에만 있다:

```
private static bool IsTabReady(Tab tab) => tab == Tab.General || tab == Tab.Character;
```

그래서 이 라운드의 일은 **「새 탭 신설」이 아니라 「플레이스홀더 해제」다**.
이 구별이 중요한 이유: 신설은 상시 표면을 늘려 절대 불변 원칙 2와 부딪히지만,
**해제는 이미 세어진 탭 하나의 본문을 채우는 것이라 상시 표면 수가 0 증가**다.
`game-architect` 판정 부담이 크게 다르다.

### 1-2. 세 항목의 이름과 순서는 이미 코드에 적혀 있고, 리더가 준 순서와 역순이다

```
private static string PlaceholderLabel(Tab tab) => tab switch
{
    Tab.Accessibility => "윤곽선 강조 · 애니메이션 줄이기 · 저전력 렌더링",
    ...
};
```

리더 지시는 「저전력 → 애니메이션 → 윤곽선」이고 **화면에 이미 나가 있는 순서는 그 역순**이다.
이 문장은 지금 사용자에게 보이는 약속이다. 순서를 바꾸면 **약속을 바꾸는 것**이므로
`design-microcopy`와 교차가 필요하다. 내 판정은 **화면 순서를 유지**하는 쪽이고
착수 순서는 그와 별개로 잡는다 — 근거 §2-2.

### 1-3. 「정보창 탭이 4개가 될 수 있다」는 잘못된 창을 겨눈다

정보창은 `장비 / 외형 / 보관함 / 상점 / DLC` 5탭이고 뒤 둘이 폐지되면 3탭이 된다. 맞다.
그러나 **접근성은 정보창의 주제가 아니다.** 정보창은 「내 캐릭터가 무엇을 가졌나」이고
접근성은 「이 앱이 내 눈과 내 컴퓨터에 어떻게 맞추나」다. 후자의 주인은 이미 설정창이다
(§1-1). 정보창에 넣으면 같은 축이 두 창에 살면서 **어느 쪽이 정본인지 사용자가 알 수 없다.**

⇒ **정보창은 3탭으로 남긴다. 접근성은 설정창 3번 자리에서 연다.** 상세 §7.

### 1-4. 내 역할 카드 숫자 2건 — 하나는 기준 복원, 하나는 정정

| 카드에 적힌 값 | 재측정 | 판정 |
|---|---|---|
| 호의 「프레임당 0.0025pt」 | 0.0025133 | **유효.** 기준은 **25분 프리셋 · 획 중심선 지름 18pt · 15fps**였다. 바깥 지름 20pt로 재면 같은 프리셋이 0.0027925다 — 기준을 안 적으면 두 값이 모순으로 보인다 |
| 「실주기 1066.7ms」 | **1000.00ms** | **정정.** `_clockTimer`를 float32로 실제 누적해 보면 15fps에서 **15프레임에 정확히 1.0에 닿는다**. 16프레임(1066.7ms)은 실 dt가 1/15보다 작을 때만 나오는 경계이고, 프레임 페이싱은 목표 주기까지 기다리므로 실 dt는 1/15 이상이다. **판정은 안 바뀐다** — 어느 쪽이든 호는 1초에 한 번만 다시 그려진다 |

## 2. 설계안 — 탭이 여는 순서

### 2-0. 왜 셋을 한꺼번에 열지 않는가

세 항목의 **위험 등급이 다르다.** 하나는 기존 술어에 합류만 하면 되고, 하나는 앱 전역 연출을
건드리며, 하나는 아직 기준이 없는 새 색 축을 만든다. 한 라운드에 셋을 열면
「어느 것이 무엇을 깼는가」를 가를 수 없다.

### 2-1. 확정 순서 — 저전력 → 애니메이션 감소 → 윤곽선 강조

리더가 준 순서와 **같다.** 다만 근거가 「중요도」가 아니라 **「기존 주인이 있는가」다**.

| 단계 | 항목 | 기존 주인 | 새로 만드는 것 | 위험 |
|---|---|---|---|---|
| 1 | 저전력 렌더링 | **있다** — `ViewerPresence.ShouldApplyLowPowerDownshift`가 OS 저전력을 이미 읽어 등급을 한 칸 내린다 | 사용자 의사표시 1비트. 그 술어에 OR로 합류 | **낮다.** 판정 로직이 이미 플랫폼 중립 위치(`Platform/`)에 있다 |
| 2 | 애니메이션 감소 | 부분적 — `general.musicDance` 토글이 자동 춤 하나를 이미 끈다 | 「무엇을 끌 것인가」 목록(§5) + 그 목록을 읽는 술어 1개 | **중간.** 앱 전역 연출에 걸린다. 끄는 목록이 곧 계약이다 |
| 3 | 윤곽선 강조 | **없다** | 새 색 축. 대비 상한을 새로 유도해야 한다 | **높다.** `design-art` 판정 선행 |

### 2-2. 화면 순서와 착수 순서는 다르다 — 둘 다 유지한다

화면(카드 안 행 순서)은 코드에 이미 나간 **윤곽선 · 애니메이션 · 저전력** 순서를 지킨다(§1-2).
착수는 **저전력 · 애니메이션 · 윤곽선** 순서다.
⇒ **1단계에서 탭이 열릴 때 3행이 아니라 1행 + 준비 중 2행으로 뜬다.**
이 저장소에는 그 형태의 선례와 규칙이 이미 있다:

- 행 단위 「준비 중」 캡션: `SettingsControls.NotBuiltPrefix`
- 비활성 행 위계 규칙(`docs/UI_SURFACE_SPEC.md` §2.4): **비활성은 한 단만 내리고 행 안의 상대
  순서를 절대 뒤집지 않는다. 이유 문장은 비활성 행에서 가장 중요한 글자다.**
- 대비 실측: 비활성 라벨 8.53:1 / 이유 한 줄 5.73:1 — 둘 다 AA 통과, 역전 없음(§3-1)

**탭바 배지는 1단계에서 떼지 않는다.** 3행 중 2행이 준비 중인 탭은 아직 준비 중이다.
배지가 빠지는 시점은 **3단계 완료**다. 그래야 탭바의 「준비 중」이 거짓말을 하지 않는다.

### 2-3. 각 단계의 관문 — 무엇이 참이어야 다음으로 가는가

| 단계 | 관문 |
|---|---|
| 1 → 2 | 저전력 비트가 저장·복원된다 · v13 파일이 그 비트 없이 안전 기본값으로 읽힌다 · `ShouldApplyLowPowerDownshift`의 OS 경로가 **여전히 단독으로도 동작**한다(음성 대조: 사용자 비트를 꺼도 OS 저전력만으로 내려가는가) |
| 2 → 3 | §5 목록의 각 항목이 **꺼졌는지 실기 캡처로 확인**된다 · 끈 뒤에도 그 연출이 전달했던 정보가 **다른 채널로 남아 있다**(§6-3의 규칙) |
| 3 → 완료 | `design-art`가 윤곽선 색의 대비 상한을 유도했다 · 탭바 배지를 뗀다 · `IsTabReady` 잠금 테스트 |

### 2-4. ★ 세이브는 단계마다 올리지 않는다 — v14 한 번에 3벌을 넣는다

`CharacterSaveStore.cs`가 v10·v12에서 같은 판단을 이미 두 번 했다:
**필드를 나눌 때마다 다운그레이드 창이 한 번씩 열린다. 그리고 문을 닫는 것은 커밋이 아니라 빌드다.**

세 항목을 세 라운드에 나눠 저장하면 v14·v15·v16이 되고 하위 호환 테스트가 3배가 된다.
⇒ **스키마는 1단계에서 v14로 한 번 올리고 3벌을 전부 넣는다.** 2·3단계는 이미 있는 필드를
읽기 시작할 뿐이라 스키마를 **한 비트도 움직이지 않는다.**

## 3. Saved 비트 쌍 — 실제 형태 (유도, 지어내지 않았다)

### 3-0. 「Saved 비트 쌍」이라는 이름의 필드는 없다. 관례의 이름이다

`Core/CharacterSaveStore.cs`를 훑으면 그 관례가 실재한다 — 값 하나에 불리언 하나를 짝지운다:

| 실재하는 쌍 | 도입 버전 |
|---|---|
| `gearPositionSaved` | v3 |
| `characterScaleSaved` | v6 |
| `inkColorSaved` | v7 |
| `dialogueVisibleLengthSaved` · `dialogueFontSizeSaved` | v8 / v9 |
| `preferredMonitorSaved` | v9 |
| `dayBoundaryOffsetSaved` | v10 |
| `infoWindowPositionSaved` · `settingsWindowPositionSaved` · `focusPopoverPositionSaved` · `todoPopoverPositionSaved` · `actionPopoverPositionSaved` | 창 위치 5종 |

**접근성 3항목에 해당하는 필드는 0건이다.** 검색 결과 `lowPower`·`reduceMotion`·`highContrast`·
`윤곽선 강조` 계열의 세이브 필드가 없고, 유일한 `LowPowerMode`는 **세이브가 아니라
`Platform/ViewerPresence.cs`의 OS 조회 결과**다(읽기 전용 스냅숏).
⇒ **리더 메모의 「Saved 비트 쌍을 착수 조건으로」는 「그 이름의 필드를 찾아라」가 아니라
「이 관례로 새로 만들어라」로 읽어야 맞다.**

### 3-1. 그 관례가 요구하는 것 — 코드가 직접 적어 둔 판정 규칙

`CharacterSaveStore.cs`의 리더 판정이 규칙을 못박아 두었다:

> **필드의 「없음」이 그 필드의 0값과 다른 뜻일 때만 버전을 강제한다.**

그리고 v6이 겪은 함정을 같은 파일이 적어 둔다 — **기본이 `true`인 값은 「없음」이 `false`로
채워져 뜻이 뒤집힌다**(`cornerPanelEnabled`·`autoHideOnFullscreen`이 그래서 버전 분기를 받았다).

### 3-2. 그래서 3항목의 필드 형태는 이렇게 유도된다

세 항목의 **배포 기본값은 전부 「꺼짐」이다**(근거 §3-3). 즉 「없음」 = `false` = 「아직 안 켰다」가
**정확한 사실**이므로 뜻이 뒤집히지 않는다. ⇒ `FirstVersionWith…` 분기가 **0개** 필요하다.

그런데 **「아직 고른 적 없다」와 「직접 껐다」를 갈라야 하는가**가 항목마다 다르다.
이것이 Saved 비트가 필요한지를 가르는 유일한 질문이다:

| 항목 | 값 | Saved 비트가 필요한가 | 왜 |
|---|---|---|---|
| 저전력 렌더링 | `lowPowerRenderEnabled` (bool, 기본 false) | **필요하다** | OS 저전력이 이미 같은 일을 한다. 「안 골랐다」와 「직접 껐다」가 **다른 뜻**이다 — 직접 끈 사용자에게는 OS 저전력 하강까지 존중할 것인가를 다시 물어야 한다. 이게 갈리지 않으면 **사용자가 끈 것을 OS가 되켠다** |
| 애니메이션 감소 | `reduceMotionEnabled` (bool, 기본 false) | **필요하다** | OS 접근성 설정(macOS 「동작 줄이기」 / Windows 「애니메이션 표시」)을 **미래에 읽게 되면** 같은 충돌이 생긴다. 지금 비트를 안 만들면 그때 스키마를 또 올린다 |
| 윤곽선 강조 | `outlineEmphasisEnabled` (bool, 기본 false) | **필요 없다** | OS에도, 앱 안에도 같은 일을 하는 다른 주인이 없다. `false`가 「기본 조형을 쓴다」와 정확히 같은 뜻이다 |

**⇒ 최소 형태 (v14에 한 번에 들어간다)**

```
lowPowerRenderSaved      (bool)   +  lowPowerRenderEnabled      (bool, 기본 false)
reduceMotionSaved        (bool)   +  reduceMotionEnabled        (bool, 기본 false)
                                     outlineEmphasisEnabled     (bool, 기본 false)
```

**5필드.** 값이 사는 곳은 `Core/AppSettingsModel.cs`이고 `StickConfig`에는 쓰지 않는다 —
배포 에셋에 플레이 중 쓰기를 하면 그 값이 출하 기본값이 되어 전 사용자에게 나간다
(이 저장소가 `characterScale`과 `inkColor`로 **두 번** 겪은 사고다).

### 3-3. 왜 셋 다 기본 꺼짐인가

- **저전력**: 이미 OS 저전력이 자동으로 한 칸 내린다. 앱이 기본으로 또 내리면
  `ShouldApplyLowPowerDownshift`가 적어 둔 판단(「사용자가 OS에서 켠 것은 존중해야 할
  의사표시」)이 **사용자가 켜지도 않은 것을 존중하는 것**으로 변질된다.
- **애니메이션 감소**: 캐릭터의 자율 움직임이 이 앱의 정체성이다. 기본으로 끄면 다른 앱이 된다.
- **윤곽선 강조**: 조형 변경이라 기본으로 켜면 `design-character`·`design-equipment`의
  출하 조형이 기본값 자리에서 밀려난다.

`design/sound/SILENCE_POLICY.md` §1의 논거와 같은 형태다 — **기본 ON은 전원에게 청구서를 보낸다.**

### 3-4. 하위 호환 테스트 — 반드시 동반하는 1건

`Tests/EditMode/EquipmentMigrationTests`에 v13 파일을 읽는 테스트를 더한다.
기대값은 **숫자 14를 베끼지 않고** `CharacterSaveStore.CurrentVersion`을 참조한다

## 6. 소리 없이 정보 전달 — 축이 뒤집혀 있다

### 6-1. 소리로만 전달되는 정보는 0건이다. 소리 자체가 0이기 때문이다

프로덕션 `.cs` 전체에서 `AudioSource` · `PlayOneShot` · `AudioClip` **실코드 0건**.
유일한 적중 1건은 `Core/StickPackManifestSO.cs`의 `[Header("소리 — 키만. AudioClip 참조는 여기 두지 않는다")]`
= **그 사실을 말하는 문자열 자신**이고, 묶음 ⑪ 규칙 16(「주석이 그 사실을 말하는 줄은 계수 대상이
아니다」)에 정확히 해당한다.
양성 대조: 같은 도구로 `Core/StickmanAgent.cs`의 `Debug.Log` = 19건 ⇒ **검색은 살아 있다.**

`design/sound/SILENCE_POLICY.md` §4-1이 규칙을 이미 들고 있다 —
**「소리는 어떤 정보의 유일한 전달자가 될 수 없다.」**
지금 이 규칙은 **위반할 대상 자체가 없어서** 자동으로 지켜진다.

### 6-2. ★★ 대신 더 나쁜 것이 실재한다 — 「모션이 유일한 전달자」와 「0채널」

| 사건 | 시각 채널 | 판정 |
|---|---|---|
| **레벨업** | **없다.** `Interaction/CharacterProgressionDirector.cs`의 신호는 `Debug.Log` 한 줄뿐이다 | ★★ **0채널.** `SILENCE_POLICY` §4-3이 이 결함을 기록한 뒤 **오늘도 그대로다** |
| **집중 세션 완주** | **캐릭터 포즈 하나**(`FocusComplete`) | ★★ **모션 전용.** 캐릭터가 숨겨져 있거나 다른 연출 중이면 관문에 막히고, `FocusWatchDirector`가 그 실패를 `완주 포즈를 잡지 못했습니다`로 로그만 남긴다 — 코드 자신이 「50분을 채운 축하가 조용히」 사라졌다고 적어 두었다 |
| **집중 세션 잔여 시간** | 호(1Hz, 숫자 0) + 창(180초에 닫힘) | ★★ **지속 채널 0개**(§5-3) |

⇒ **접근성 탭이 애니메이션 감소를 켜는 순간 ②가 더 나빠진다.** 모션을 줄이라고 시킨 사용자에게
모션이 유일한 전달자인 축하를 보낼 수는 없다.

### 6-3. 그래서 제안하는 규칙 — 대칭을 세운다

`SILENCE_POLICY` §4-1의 문장에는 **짝이 없다.** 짝을 세운다:

> **소리도, 모션도, 색도 어떤 정보의 유일한 전달자가 될 수 없다.**
> 셋 중 하나를 줄일 수 있는 설정이 존재하는 한, 그 채널 하나에만 실린 정보는 줄이는 순간 사라진다.

그리고 `SILENCE_POLICY` §4-2가 쓴 강제 방법을 그대로 빌린다 — **데이터로 잠근다.**
그쪽은 사운드 카탈로그 항목마다 `visualCounterpart`를 필수로 요구하고 비어 있으면 출하 금지다.
같은 형태로 **모션 감소 목록(§5-1)의 각 항목에 「이 연출이 전달하던 정보」 칸을 필수로 두고,
그 칸이 비어 있지 않으면 대체 채널을 함께 적게 한다.** A등급은 전부 빈 칸이어야 하고
(빈 칸이 아니면 A등급이 아니다), C등급은 전부 채워져 있어야 한다.
빈 목록을 기대값으로 명시해 `foreach`가 아무것도 안 재고 초록이 되는 형태를 막는다.

### 6-4. 시각적 대체 수단 — 셋 다 「이미 있는 부품」으로 낸다

★ 새 상시 표면을 만들지 않는 것이 이 절의 제약이다(절대 불변 원칙 2).

**⑴ 잔여 시간 숫자 — 이미 출하된 부품이 있다**

`GearRadialMenuWidget`이 [오늘 할일] 버튼에 **숫자 배지**를 이미 그린다:
16×16 원(`BadgeSurface`, `Accent`) + 10pt 굵은 글자(`BadgeText`, `OnAccentSolid`), 앵커 (15, 15),
최대 문자열 `9+`. 주석이 그 정체를 적어 둔다 — **「유일하게 남은 글자 — 이름이 아니라 상태 수량이다.」**

⇒ **같은 부품을 [집중 모드] 버튼에 붙인다.** 남은 분을 두 자리로(`50`→`49`→…→`1`) 쓴다.
- 대비: `OnAccentSolid` on `Accent` = **7.91:1** (AA 4.5 통과, §4-1에 이미 측정돼 있다)
- 신규 색 0개 · 신규 폰트 pt 0개 · 신규 컴포넌트 종류 0개
- 배지는 세션 중에만 켜진다 — 투두 배지가 `uncompleted > 0`일 때만 켜지는 것과 **같은 관례**
- 갱신 주기도 그 자리에 이미 있다(`_clockTimer >= 1f`, 값이 바뀐 틱에만 쓴다)
- ★ **한계**: 부채꼴은 상시 표면이 아니다. 열어야 보이고 180초에 닫힌다.
  ⇒ 이것은 **「열면 숫자가 있다」를 보장할 뿐 「지속적으로 읽힌다」를 해결하지 못한다.**
  후자는 §6-5의 선택지 문제다.

**⑵ 완주 축하 — 포즈 말고 한 채널 더**

포즈를 **끄지 않는다**(C3). 채널을 **더한다**. 가장 싼 자리는 **말풍선**이다 —
`design-narrative`가 이미 소유한 표면이고 새 상시 표면이 아니다.
★ 단 원칙 1(행동-텍스트 싱크)이 걸린다: **대사는 상태 전이가 확정된 뒤 그 상태로부터만 파생한다.**
`FocusWatchDirector`에는 그 확정 지점이 이미 있다 — 완주 포즈가 **상태머신에 실제로 들어갔는가**를
보는 플래그(`IsStartPoseConfirmed`의 완주판). ⇒ **그 플래그가 참이 된 시점에서만 파생**시키면
원칙 1을 지키면서 채널이 둘이 된다. 문안은 `design-narrative` 소관이다.
★★ 그리고 **포즈가 관문에 막혀 끝까지 못 나온 경우**(코드가 `완주 포즈를 잡지 못했습니다`로 남기는
그 경로)에는 **말풍선이 유일한 채널이 된다** — 이 경로에서 말풍선을 함께 막으면 다시 0채널이다.

**⑶ 레벨업 — 0채널을 1채널로**

내 범위가 아니다(`ux-designer`). 다만 **접근성 관문으로서 요구는 적어 둔다**:
모션 감소가 켜진 상태에서도 살아남는 채널이어야 하므로 **포즈 단독은 안 된다.**

### 6-5. ★ 「지속적인 숫자」는 선택지 문제다 — 고르지 않는다

내 정의서가 금지한다 — **상시 표면을 늘리는 제안은 절대 불변 원칙 2와 정면 충돌하므로
선택지와 각각이 깨뜨리는 원칙을 함께 올리고 고르지 마라.** 그대로 한다.

지금 **항상 화면에 있는 것**은 톱니 아이콘 하나다(`InfoGearIconWidget`, 팁 반지름 13.8pt →
지름 27.6pt). 나머지는 전부 닫힌다. 그래서 「지속적인 숫자」를 얻는 길은 넷뿐이고 **전부 대가가 있다**:

| 안 | 무엇 | 깨뜨리는 것 | 비용 |
|---|---|---|---|
| **가** | 톱니 아이콘에 숫자 배지를 붙인다 | **원칙 2(비침해).** 상시 표면의 잉크 면적이 는다. 그리고 톱니는 27.6pt 안에 이미 톱니 조형이 산다 — `design-iconography`가 「톱니 링」 오명으로 한 번 다친 자리다 | 상시 표면 면적 증가. 전체화면 앱에서는 함께 물러나므로 도현(persona-gamer)의 지갑 문장은 안 깨진다 |
| **나** | 부채꼴 [집중 모드] 버튼에 배지(§6-4 ⑴) | **아무것도.** 상시 표면 0 증가 | 열어야 보인다. 「지속」을 만족하지 않는다 |
| **다** | 집중 팝오버의 180초 자동 닫힘을 **세션 중에만** 면제한다 | **원칙 2.** 창이 계속 떠 있다. 자동 닫힘은 2026-09-01 페르소나 J5 지적으로 **생긴** 장치라 되돌리는 것이다 | 창 면적이 세션 내내 점유된다 |
| **라** | 아무것도 안 한다 | **아무것도.** 대신 「지속적인 숫자 판독 수단 0개」가 그대로 남는다 | 접근성 결함 유지 |

**판정하지 않는다. `game-architect` 선행이다.**
내 의견은 참고로만 적는다 — **나와 다는 함께 갈 수 있고**(나는 비용 0이라 어느 경우든 넣을 값이 있다),
가와 다는 원칙 2를 각각 다른 방식으로 건드리므로 **둘 중 하나만** 고려 대상이다.

## 7. 탭 배치 제안

### 7-1. 정보창은 3탭으로 남긴다 — 접근성을 넣지 않는다

| 창 | 지금 | DLC 폐지 후 | 내 제안 |
|---|---|---|---|
| 정보창 | 장비 / 외형 / 보관함 / 상점 / DLC = 5 | 장비 / 외형 / 보관함 = **3** | **3 유지** |
| 설정창 | 일반 / 캐릭터 / 이벤트 / 접근성 · 성능 / 데이터 = 5 | (이벤트 폐지 판정 미착수) | **접근성 탭을 연다.** 탭 수 변화 0 |

근거 셋:

1. **주제가 다르다.** 정보창은 「내 캐릭터가 무엇을 가졌나」, 설정창은 「이 앱이 어떻게 행동하나」다.
   `TabEyebrows[3]`가 그 경계를 이미 문장으로 적어 두었다 — 「내 눈과 내 컴퓨터에 맞추기」.
2. **주인이 이미 있다.** 설정창에 `Tab.Accessibility`가 실재한다(§1-1). 정보창에 또 만들면
   같은 축이 두 창에 살고, `docs/TEAM.md`가 금지하는 「겹치면 리더를 거쳐 조정한다」 이전의
   **구조적 중복**이 된다.
3. **정보창 탭 표의 계약이 막는다.** `CharacterInfoWindow.Tabs.cs`의 `TabDef`는 탭마다
   `TabPage`(본문 종류)를 요구하고 종류는 `Cards` / `Inventory` / `Shop` / `Dlc` 넷뿐이다.
   접근성 탭은 **설정 행 본문**이라 넷 중 어느 것도 아니다 ⇒ `TabPage`를 새로 하나 만들고
   그 창에 설정 행 빌더를 두 번째로 구현해야 한다. **`SettingsControls`가 이미 있는데 두 벌이 된다.**

### 7-2. 설정창 탭바 — 접근성 탭 개방은 탭바를 **좁힌다**

`docs/UI_SURFACE_SPEC.md` §12.3이 배지 달린 탭 3개를 적어 두었다(이벤트 · 접근성 · 성능 · 데이터).
배지 1개가 빠지면 그 탭의 폭이 정확히 **`TabBadgeGap` 8pt + 배지 글자폭** 만큼 줄어든다.

★ **배지 글자폭은 오프라인에서 못 잰다.** 코드는 `SettingsControls.MeasuredWidth`
(= `Text.preferredWidth`)를 쓰고, 「글자 수 × 상수」 모형은 이 저장소가 **폐기한 가족**이다
(`Tests/PlayMode/UiTextWidthModelTests`). §12.3 표의 `40pt`는 그 폐기된 모형의 값이고
그 문서 자신이 2026-09-28에 「모형 추정, 측정 아님」으로 표시해 두었다.
⇒ **내가 낼 수 있는 것은 모형 없는 하한뿐이다: 최소 8pt 줄어든다.**

**그래도 방향은 확정이다 — 넓어지지 않는다. 좁아진다.**
그러므로 이 라운드는 §12.3이 걱정한 넘침(탭 우측단 vs `[▲][▼]` 칩)을 **악화시킬 수 없다.**
확정 판정은 실기 캡처이고 소관은 `design-capture-review`다.
★ 그리고 한글 글리프가 번들 폰트에 없어 OS 폴백에서 오므로 **macOS 한 장으로 판정하지 않는다.
Windows 한 장을 반드시 함께 받는다.**

### 7-3. ★ 이 탭은 이미 공동 소유다 — 사운드가 먼저 예약했다

`design/sound/SILENCE_POLICY.md` §6-2가 **같은 탭을 이미 찍어 두었다**:
마스터 on/off · 볼륨 · 야간 시간대 · 미리듣기 · 「지금 왜 조용한지」 사유 한 줄 — **전부 접근성 탭**.
근거도 내 것과 같다(그 탭의 아이브로우가 「내 눈과 내 컴퓨터에 맞추기」이고 소리의 진짜 비용은
컴퓨터에 대한 것이다).

⇒ **카드 순서를 미리 갈라 둔다.** 그러지 않으면 두 라운드가 같은 `y`에 카드를 쌓는다.

```
[접근성 · 성능]  아이브로우: 내 눈과 내 컴퓨터에 맞추기
 ┌ 카드 1 «보기»        윤곽선 강조            (3단계)
 │                      애니메이션 줄이기       (2단계)
 ├ 카드 2 «컴퓨터»      저전력 렌더링          (1단계)
 └ 카드 3 «소리»        design-sound 소관 — 이 라운드는 자리만 비워 둔다
```

카드 1이 «보기»이고 카드 2가 «컴퓨터»인 이유: 화면 순서를 지키면(§1-2)
윤곽선·애니메이션이 앞이고 저전력이 뒤인데, 그 셋을 한 카드에 담으면
**「눈에 대한 것」과 「기계에 대한 것」이 섞인다.** 아이브로우가 그 둘을 이미 나눠 말하고 있다.
★ 이 배치는 `SILENCE_POLICY` §6-2가 기각한 것(「없어진 설정을 없어질 탭에 넣는 행」)과 무관하고,
그 문서가 인용한 「`[일반]` 탭은 앞으로도 항상 넘친다」와도 충돌하지 않는다 — 여기는 `[일반]`이 아니다.

### 7-4. 탭을 숫자로 잡지 마라 — 이미 경고가 붙어 있다

`SILENCE_POLICY` §6-2가 적어 둔 경고를 그대로 승계한다:
리더 판정(「이벤트」 폐지 → 4탭)이 들어오면 **`Tab.Accessibility`의 enum 값이 3에서 2로 내려간다.**
⇒ **접근성 행을 배치하는 코드는 `Tab.Accessibility`로 잡는다. 3으로 굳히면 4탭 라운드가 행을
엉뚱한 탭으로 옮긴다.** 그리고 `SettingsWindow.cs`는 그 라운드와 **같은 파일**이라
리더가 순서를 갈라야 한다(동시 진행 규칙).

★ **as-of 정정 1건**: `SILENCE_POLICY` §6-2는 `CharacterSaveStore.CurrentVersion`을 **9**라고 적고
사운드 필드가 v10이 된다고 쓴다. **지금은 13이다.** 그 문단은 작성 시점에 참이었고 지금은 낡았다 —
사운드 라운드가 그 문장을 믿고 v10을 쓰면 **다운그레이드 방어가 뚫린다.**

위쪽 앵커를 밀지 않도록 꼬리에 모았다(묶음 ⑩ 규칙 11의 처방).

**기준 판**: HEAD `56ea93898d170889` + 작업 트리(병렬 라운드 진행 중).
이 문서의 모든 코드 인용은 **그 시점의 작업 트리**에서 읽었다.

★ **이 문서가 겨누는 파일이 지금 다른 라운드에 물려 있다.**
`Assets/_Project/Scripts/Interaction/SettingsWindow.cs`가 작업 트리에서 **수정 중**이다.
그래서 행 번호를 쓰지 않고 **고정 문자열 앵커**로만 인용했고, 편집 후에 앵커 네 개를 다시 세어
전부 살아 있는 것을 확인했다(행 번호는 실제로 약 6줄 밀려 있었다 — 행 번호로 인계하면
같은 라운드 안에서도 썩는다는 규칙의 실물이다):

| 앵커(고정 문자열) | 확인 |
|---|---|
| `IsTabReady(Tab tab) =>` | 1건 |
| `Tab.Accessibility =>` | 1건 |
| `접근성 · 성능` | 2건(`TabNames` 1 + 폭 모형 주석 1) |
| `내 눈과 내 컴퓨터에 맞추기` | 1건 |
