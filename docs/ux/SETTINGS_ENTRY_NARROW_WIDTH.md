## 0. 판정 일곱 줄

1. **테스트 환경만의 문제가 아니다.** 다만 **가로로 놓인 표준 데스크톱 구성에서는 도달하지 않는다.** 가장 좁은 현실 사례인 Windows 1366×768 @150%에서도 여유가 **264.7pt 이상**이다.
2. **실제로 닿는 경로**는 네 가지다.
   - 세로 방향 화면 @175% (2-in-1 태블릿 모드, 세로 모니터)
   - 8인치급 세로 태블릿 @125% 이상
   - 사용자 지정 극단 배율
   - 폰 폭
   빈도는 드물다(추정). **macOS에서 도달하면 설정창으로 가는 마우스 경로가 0**이 된다.
3. ★ **test-engineer §5-2의 「긴 이름이면 약 750pt 화면에서도 접힌다」는 프로덕션에서 지금은 거짓이다.**
   - 헤더는 `Awake`에서 이름을 재는데, 세이브는 그 뒤 `Start`에서 읽힌다.
   - 그래서 헤더는 **항상 기본 이름 「스틱메이트」 폭으로 배치된다**(§3).
   - 이 때문에 현행 문턱은 이름과 무관하게 **패널 586~614pt**다.
4. ★ **같은 사실에서 별건 결함 F-1이 나온다.** 이름을 기본값보다 길게 바꾼 사용자는 **매 실행마다** 헤더에서 이름이 `Lv.N`에 겹친다(코드 판독 기반 추정, 실기 캡처 필요). §4 참조.
5. ★ **F-1만 따로 고치면 이 문제가 악화된다.** 저장된 이름으로 재배치하면 문턱이 최대 712pt로 올라가고, 세로 @150%(패널 688)에서도 [설정]이 접힌다. **두 수정은 같은 라운드에 착지해야 한다.**
6. **추천: (나)의 변형 — 「[설정]은 접지 않는다 · 헤더 왼쪽이 정해진 순서로 양보한다」 강등 사다리.**
   - [설정]이 접히는 문턱이 586~614(이름에 따라 최대 712)에서 **492~512로 내려가고, 이름 길이와 무관해진다.**
   - 현행 문턱 이상 폭에서 기본 이름을 쓰는 사용자에게는 **비트 단위로 같다.**
7. (가) 허용, (다) 부채꼴·넘침 메뉴·메뉴바는 **기각**한다(§6). 모바일(폰 폭)은 이 사다리로도 못 풀고 **헤더 2단 재설계가 필요하다** — 모바일 이식 선결 과제로 넘긴다.
8. ★ **제2부(§15-16) — 게임이 아닌 전체화면 앱(등급 1)에서도 입구가 사라진다. 이쪽은 일상 상태이고 P1이다.**
   - 원인 ①: 우클릭 게이트가 허가를 발급하기 **전에** `ArePanelsSuppressed`로 막는다(`AppControlDirector.cs:854-857` vs `:886`).
   - 원인 ②: 톱니는 평상시 숨김이다(`InfoGearIconWidget.cs:933-934`).
   - 결과: macOS는 마우스 경로 0이다.
   - **의도가 아니다.** `UX_FLOW.md` §52-2 R-1과 부채꼴 설계 §5-6·§R5-9·§10-4에 반한다.
   - 뿌리는 **ux-designer 설계서 §10-1 #3의 자기모순**이고, EditMode F18이 그 모순을 정답으로 잠갔다. 등급 1 도달성 PlayMode 2건은 전역 톱니 우회 때문에 **거짓 통과**다.
9. **두 상태를 한 불변식으로 묶는다** — 「캐릭터가 보이면 우클릭 → 부채꼴 → 정보창 → [설정] 네 홉이 열린다. 캐릭터가 안 보이면 톱니. 둘 다 없는 것은 등급 2뿐.」
   - 수정 E-1: 게이트 항을 「허가를 받아도 억제되는가」로 교정
   - 수정 E-2: 정보창 열기도 허가를 낸다
   - 수정 E-3: 헤더 강등 사다리 + F-1


### 1-2. 논리 폭 L이 정해지는 경로
`ScreenCoordinateConverter.ResolveCanvasScaleFactor` (`Platform/ScreenCoordinateConverter.cs:527-532`)의 판정 순서:

| 순서 | 조건 | 캔버스 배율 | 쓰는 곳 |

| 1 | `config.desktopDpiScale > 0` | `1 / 그 값` | 수동 오버라이드. 배포 에셋은 0이다(§5-4 인용) |

  - 양성 대조: 같은 grep이 `Dialogue/DialogueBubbleRenderer.cs:256`의 「텍스트 크기」는 잡았다.
- `STICKMATE_FORCE_UI_DENSITY`(`Platform/UiDensityOverride.cs:61`)는 계측 전용 환경변수라 제품 경로가 아니다.

## 2. 글자 폭 — 실측 범위 (FontTitle 14, `UiChrome.cs:650`)

- Unity 레거시 `Text.preferredWidth`는 `SettingsControls.MeasuredWidth`에서 **올림**된다(`SettingsControls.cs:130-135`).
- 이 머신의 **실제 폰트 파일**로 PIL 전진 폭을 쟀다.
- **교정**: Arial 14px에서 `W` 13.00(이론 13.21), `i` 3.00(이론 3.11). 정수 픽셀 반올림 수준이라 **글자당 ±1pt 오차**로 본다.
- Unity 레거시 폰트(`LegacyRuntime`)의 한글 폴백이 어떤 글꼴로 가는지는 **미확인**이다. 그래서 범위로 적는다.
  - 하한: Apple SD Gothic Neo — 한글 12pt/자, 굵게도 12
  - 상한: AppleGothic / Arial Unicode — 1em = 14pt/자
  - [DLC]는 라틴 문자이므로 Arial 기준 28pt
  - Windows 맑은 고딕은 이 머신에 없어 **미측정**이다. 같은 12~14 범위 안이라고 **추정**한다.

| 항목 | 하한 (SD Gothic Neo) | 상한 (1em) |
|---|---:|---:|
| 탭 라벨 `장비/외형/보관함/상점` | 24/24/36/24 | 28/28/42/28 |
| `DLC` | 28 | 28 |
| **Σ5** | **136** | **154** |
| Σ4 | 108 | 126 |
| 기본 이름 「스틱메이트」(굵게) | **60** | **70** |
| 최대 이름 12자 (`MaxNameLength`, `Core/CharacterProgressionModel.cs:67`) — 한글·전각 | 144 | 168 |
| 최대 이름 12자 — 라틴 `W` 굵게 | 156 | 156 |

**배치 모드 증거로 좁히기 (간접, 추정)**
- 640×480, 배율 1 ⇒ L 640, 패널 608.
- 4탭은 통과했고(09-07) 5탭은 실패했다(09-14).
- 기본 이름 기준으로 `T5 = 390 + 5a + 9a + 28 > 608`이면 `a > 13.57`이다(a = 한글 글자당 폭).
- ⇒ **이 환경의 한글 폴백은 1em 쪽이다.** 아래 표에서는 **상한(1em)을 보수적 주 추정**으로 쓴다. 정확한 값은 R1 실측이 확정한다.

## 3. ★ 프로덕션에서 헤더가 재는 이름은 **항상 기본 이름**이다

| 사실 | 출처 |
|---|---|
| 정보창과 진행 디렉터는 **같은 GameObject**에 붙는다 | `Editor/SceneBootstrapper.cs:1245`(`CharacterProgressionDirector`), `:1261`(`CharacterInfoWindow`) |
| 그 GameObject는 **씬에 배치된 프리팹 인스턴스**다(런타임 생성이 아니다) | `SceneBootstrapper.cs:1592`(`InstantiatePrefab`), `:1627`(`SaveScene`). GUID 탐침으로 두 스크립트 GUID가 `Prefabs/Stickman.prefab`에서 확인됐다. 양성 대조: `StickmanAgent` GUID는 `Main.unity`에도 있다. 음성 대조: 가짜 GUID는 0건 |
| 헤더 배치(이름 측정 → 탭 줄 x)는 `Awake`에서 **딱 한 번** 한다 | `CharacterInfoWindow.cs:864` → `BuildHeader`(유일한 호출 `:1375`) → `:1452` |
| 세이브 로드는 `Start`에서 한다 | `Interaction/CharacterProgressionDirector.cs:210`. 테스트 밖 유일한 호출이다 |
| 로드 전 이름은 기본값이다 | `CharacterProgressionModel.cs:82` `= DefaultCharacterName`(`:64` 「스틱메이트」) |
| 이름이 바뀌어도 헤더는 **글자만** 바꾼다 | `:1094`(4Hz `RefreshNumbers`), `:1289`. 변경 경로 두 곳: `:1277`(정보창), `SettingsWindow.cs:1697`(설정창) |

- Unity는 씬 로드 시 모든 `Awake`를 모든 `Start`보다 먼저 부른다. ⇒ **현행 헤더는 사용자가 저장한 이름을 한 번도 재지 않는다.**
- 따라서 **현행 [설정] 문턱은 이름과 무관하다.** `T_설정 = 390 + 60~70 + 136~154 = 586 ~ 614pt`(주 추정 614).
- ※ PlayMode 테스트에서 `SetCharacterName`을 **창이 만들어지기 전에** 부르면 이름이 문턱에 반영된다. **그 테스트는 프로덕션을 재현하지 않는다.** R1 이름 길이 대조(§5-7-3)는 호출 시점을 함께 기록해야 한다.

## 4. 별건 F-1 — 이름을 바꾼 사용자는 헤더에서 이름이 `Lv.N`에 겹친다 (P1 후보 · 실기 캡처 필요)

- 부팅 때 배치는 기본 이름 폭(60~70) 기준이다: `Lv` x = **96~106**, 탭 줄 x0 = **164~174**.
- 저장된 이름이 그보다 길면, 이름 글자는 **상자 폭 200 안에서 그대로 그려지고** 옆 요소는 움직이지 않는다.

| 저장된 이름 | 이름 잉크 오른끝 (28 + w) | 결과 |
|---|---:|---|
| 한글 5자(기본과 같음) | 88~98 | 정상 |
| **한글 6자** | 100~112 | **`Lv.N` 첫 글자를 덮는다**(Lv 왼끝 96~106) |
| 한글 9자 | 136~154 | `Lv.N`과 EXP 진행선을 전부 덮는다 |
| 한글 12자 | 172~196 | 탭 줄 테두리를 8~22pt 침범한다. 1em이면 [장비] 라벨 잉크(x 191~)와 **글자끼리 겹친다** |
| 한글 2자 | 52~56 | 겹치지는 않지만 이름과 `Lv.1` 사이에 **40~50pt 틈**이 생긴다(「레벨이 이름 옆에 붙는다」는 설계 의도가 깨진다) |

- 클릭 오배선은 없다. 이름 라벨은 `raycastTarget = false`다(`:1450`). **화면 결함뿐이다.**
- **플랫폼 무관**(macOS·Windows 공통 코드). 창 폭과도 무관하다(1042에서도 난다).
- 판정 등급: **코드 판독 기반 추정. 실기 미확인.** 디자인팀 최종 판정 규칙상 **실제 빌드 캡처가 필요하다**(이름 6자·12자 두 장).

### 6-2. 비용
- **원칙 2(비침해) — 간접 비용.**
  - [설정]이 사라져도 화면을 더 가리지는 않는다. 직접 위반은 아니다.
  - 그러나 설정창은 **비침해를 사용자가 조절하는 스위치들이 모인 곳**이다(숨기기, 클릭 관통, 소리, Windows 작업표시줄 원복 카드 `UX_FLOW.md` §56-4).
  - 입구가 없어지면 **「이 앱이 거슬릴 때 줄이는 법」에 마우스로 닿지 못한다.**
- **원칙 4(탈출구) — 위반 없음.** [✕]는 절대 접히지 않는다(`Layout.cs:191`). 방해 이벤트의 탈출구(~~ESC~~·드래그 셰이크·트레이)는 설정창을 거치지 않는다.
  - ★ **2026-09-26 정정(`ux-designer`) — 결론은 서고, 근거 목록이 줄었다.** 상세는 **21절**.
    **ESC는 2026-09-05부터 개발 게이트 뒤**라 릴리스에 없다(`Core/StickmanAgent.cs` 앵커
    `if (StickMateDevTools.Enabled && Input.GetKeyDown(EmergencyDisableKey))`, 적중 1).
    **트레이는 Windows 전용**이다 — 이 문서 자신이 그 사실을 이미 두 곳에 적어 두었는데(트레이 행의 macOS `✘ 미구현`,
    허가 발급자 표의 `✘ 트레이 없음`) 이 줄만 플랫폼 한정 없이 셋을 나열하고 있었다.
  - ★ **플랫폼별 재계수**(사용자가 진행 중인 방해 이벤트를 **스스로** 끊는 수단):
    **Windows 2개**(드래그 셰이크 · 트레이 긴급정지) · **macOS 1개**(드래그 셰이크뿐).
    전역 단축키는 **탈출구가 아니다** — `Interaction/RodeoCursorWatcher.cs` 앵커 `if (!_config.rodeoCursorEnabled)`(적중 1)가
    **발동을 막는 게이트**이고 진행 중인 것을 끊지 않는다.
  - **그래서 결론은 그대로 선다**: 이 절의 주장은 「좁은 폭에서 [설정] 입구가 접혀도 **방해 이벤트 탈출구가 함께 사라지지는 않는다**」이고,
    남은 드래그 셰이크는 설정창과 무관하다(`States/RodeoCursorState.cs`, 플랫폼 가드 **0** — 양성 대조로
    `Platform/Windows/Win32WindowService.cs`의 `#if UNITY_STANDALONE_WIN` 1을 같은 검색이 잡는다).
    `Interaction/CharacterInfoWindow.Layout.cs`의 [✕] 근거도 **살아 있다**(앵커 `이 창의 유일한 탈출구라 접지 않는다`, 적중 1).
  - ★ **다만 「1초 내 해제」는 판정하지 않았다** — 셰이크는 커서 속도 임계
    (`Core/StickConfig.cs` 앵커 `public float rodeoShakeSpeedThresholdWorldPerSec`, 적중 1)를 넘겨야 성립하고,
    **몇 초가 걸리는지는 실기 측정이 있어야** 말할 수 있다. **판정 불가**로 남긴다(무엇이 있어야 판단되는가: 실기 1회).
- **발견 가능성 — 실제 비용.**
  - macOS에서 도달하면 **마우스 경로가 0이다.** 코드 스스로 [설정]을 「설정창의 유일한 GUI 경로」라 부른다(`CharacterInfoWindow.cs:148`).

- **원인이 사용자에게 안 보인다.**
  - 원인은 「화면을 세로로 돌렸다 / 배율을 올렸다」이고, F-1을 고친 뒤에는 「이름을 바꿨다」까지 더해진다.

### 8-2. 사다리 — 단계와 진입 폭

기호:
- w = 헤더에 표시할 이름의 실측 폭
- Σ = 탭 라벨 실측 합
- 1em 주 추정: Σ = 154, 기본 이름 w = 70, 12자 w = 168

| 단계 | 들어가는 조건 (패널 폭) | 하는 일 | 기본 이름 (w 70) | 12자 (w 168) |
|---|---|---|---:|---:|
| 0 | — | 현행 배치: 이름 전폭, 탭 여백 14 | — | — |
| 1 (현행) | < R_full + 368 | [보유] 접힘 | < 850 | < 948 |
| 2 (현행) | < R_full + 256 | [동전] 접힘 | < 738 | < 836 |
| **3 (신규)** | < R_full + 132 (**= 현행 [설정] 접힘 문턱**) | 탭 좌우 여백 `HeaderTabPadX` 14 → **8**. 탭 줄 폭 −60 | < 614 | < 712 |
| **4 (신규)** | < R_compact + 132 | 이름을 `slot = 패널 − 330 − Σ`로 말줄임(`UiChrome.Ellipsize`, `UiChrome.cs:1914`) | < 554 | < 652 |
| 5 (현행 가드) | slot < 실측(「첫 글자 + …」) | [설정] 접힘 + 경고 1회 | **< 512** | **< 512** |

식:
```
R_full    = 258 + w + Σ
R_compact = 198 + w + Σ
5단계 문턱 = 330 + Σ + w(첫 글자 + …) = 492 (하한 폰트) ~ 512 (1em)   ← 이름 길이와 무관
```

**순서 근거**
- **1·2단계는 손대지 않는다.** 현행 [설정] 문턱 이상에서는 기본 이름 사용자에게 비트 동일해야 회귀 표면이 최소다.
- **3이 4보다 먼저다.** 여백은 모양이고 이름은 정보다. 여백 14 → 8에도 모든 라벨이 온전히 읽힌다.
- **`Lv.N`/EXP 숨기기 단계는 두지 않는다.** 얻는 폭(68pt)에 비해 성장 피드백을 잃고, 사다리가 길어질수록 검증 표면이 커진다.

**사다리 후 도달 가능성**(§5 대조)
- 세로 1080p @175%(585) ✔
- 8" 세로 @125%(608) ✔
- 배치 640(608) ✔
- 세로 @150% + 12자 이름(688) ✔
- 여전히 접힘: 8" 세로 @150%(501), 사용자 지정 극단, 폰 폭 — **폰 폭은 모바일 헤더 재설계 과제(§11-4).**

## 10. `coder-ui` 인계 사양 (코드 수정은 이 문서 소관 밖)

**H-1 측정 캐시**

**H-2 새 배치 함수 한 곳** (이름 예: `LayoutHeaderLeft(float panelWidth)`)

**H-3 호출 시점은 세 곳뿐**
- ① `SyncColumnLayout` 안(`Layout.cs:174` 직전) — 크기 변경 시에만
- ② `RefreshNumbers`(`CharacterInfoWindow.cs:1094` 부근)에서 `CharacterName`이 캐시와 **다를 때만**
  - 문자열 비교만 하고 할당하지 않는다. `UiChrome.Ellipsize` 호출부 규약(`UiChrome.cs:1910-1912`)

- ③ `BuildHeader` 끝 1회

- `HeaderTabPadXCompact = 8`
- 근거: 탭 5개 × 12 = 60pt 절감, 최소 탭 폭 = 24 + 16 = 40 ≥ `UiChrome.MinTargetSizePoints`.

**H-5 로그**
- 단계가 **바뀔 때만** 1줄:

## 12. 무엇을 안 봤는가 / 미확인

- Unity 레거시 `Text`의 **한글 폴백 글꼴**(macOS·Windows) — 12~14pt/자 범위로 처리했다. 배치 실패가 1em 쪽을 가리키는 것은 간접 증거다.
- Windows **맑은 고딕** 폭 — 이 머신에 없다.
- MacBook Air 13.6"·MacBook Pro 14" 배율 목록, 외장 4K 세로 「looks like」 목록 — Apple 사양표에 없거나 기억 기반이다. 1366×768에서 150%가 Windows 기본 목록에 뜨는지도 미확인이다.
- **모바일이 이 정보창을 그대로 쓰는지** — `Platform/Mobile/`에 정보창 참조 0건이지만, 쓰지 않는다는 증거도 아니다.
- **F-1 실기 캡처 없음** — 코드 판독만 했다.
- 세로 방향 화면에서 앱 전체 동작(발판·오버레이) — 이 문서의 계산은 헤더에 한정된다.
- Windows 11 새 트레이 아이콘의 기본 숨김 — 일반 관찰, 실기 미확인.
- 굵게(활성 탭) 라벨이 여백 8에서 상자를 넘는지 — 측정은 Normal 스타일 기준. Apple SD Gothic Neo는 굵게도 12pt/자로 같았다. 1em 폴백 글꼴의 굵게 폭은 미측정이다.
- PIL 측정의 정수 반올림 — 교정 편차는 글자당 최대 0.21pt였다.

### 16-2. 이 불변식이 요구하는 수정 — 전부 「이미 결정된 계약의 복원」이다

**E-1 우클릭 게이트 넷째 항 교정 (등급 1)**
- 넷째 항을 「지금 억제 중인가」가 아니라 **「허가를 받아도 억제되는가」**로 바꾼다.
- 새 판정은 `UserSurfaceSummonPolicy`(`Platform/`, 중립)에 **기존 두 함수로 파생**해 둔다. 재구현하지 않는다:
  ```
  BlocksUserSummon(s, r, g) = SuppressesPanels(s, r, g ∨ CanGrant(s, r))
  ```
- 진리표로 풀면 이 값은 `s`(= `HidesScreenSurfaces`, `StickmanAgent.cs:341`)와 같다 — 등급 2와 정지 상태에서만 막는다.
  - 그래도 파생식으로 두는 이유: 두 정책 중 하나가 바뀌면 게이트가 **자동으로 따라 움직여야** 한다. `s`를 직접 넘기면 기준과 대상이 갈라진다.
- **배선 — 한 가지로만 한다**
  1. `Platform/UserSurfaceSummonPolicy.cs`에 추가:
     `public static bool BlocksUserSummon(bool characterSuspended, bool panelRetreatActive, bool userSummonGranted) => SuppressesPanels(characterSuspended, panelRetreatActive, userSummonGranted || CanGrant(characterSuspended, panelRetreatActive));`
  2. `Core/StickmanAgent.cs`의 `ArePanelsSuppressed`(`:241-242`) **바로 옆**에 추가:
     `public bool IsUserSummonBlocked => Platform.UserSurfaceSummonPolicy.BlocksUserSummon(HidesScreenSurfaces, _fullscreenPanelRetreat, IsUserSummonGrantActive);`
     — 인자 셋은 `ArePanelsSuppressed`와 **같은 순서·같은 필드**다. `_fullscreenPanelRetreat`가 private이라 판정을 에이전트 쪽에 둔다.
  3. `RightClickFanGatePolicy.ShouldOpenFan`(`AppControlDirector.cs:801-807`)의 넷째 매개변수 이름을 `panelsSuppressed` → **`userSummonBlocked`**로 바꾼다(식 `&& !userSummonBlocked`의 형태는 그대로). 호출부 `:857`은 **`_agent.IsUserSummonBlocked`**를 넘긴다.
  4. 허가 `:886`은 이미 펼침 앞이다 — **옮기지 않는다.**
- ★ **바꾸지 않는 것**: `ArePanelsSuppressed` 자체와 **그것을 읽는 닫기 소비자 전부**(부채꼴 자동 접힘, 정보창·설정창·팝오버 닫기, 포스트잇, 설정창 자동 복귀 가드 `SettingsWindow.cs:705` 등). 이 수정은 **「열기 판정」 한 곳**만 바꾼다. 소비자를 `IsUserSummonBlocked`로 바꾸면 등급 1 **진입 순간의 회수**가 사라진다 = 원칙 2 회귀(§16-2b B2).
  - ★ **2026-09-15 정정 주** — 위 「전부」는 **E-1 라운드에 대해서만** 참이다.
    - 그 뒤 자동 표면 4곳(포스트잇 · 리마인더 · 크랙 · 설정창 자동 재오픈)은 `docs/systems/AUTO_SURFACE_LEASE_AXIS.md`가 억제를 **넓히는** 방향(`SuppressesUnsummonedSurfaces` = s ∨ r ∨ g)으로 옮긴다. 위 괄호의 「포스트잇」이 그중 하나다.

## 18. 등급 1 재진입 에지마다 사용자 창이 무연출로 회수된다 — 신호를 설계할지의 **판정 조건만** (소은 ②)

**지금은 신호를 설계하지 않는다**(리더 지시). 이 절은 **무엇을 세어, 어느 선에서 설계에 들어가는가**만 적는다.

### 18-1. 사실

- **회수 자체는 의도다** — §16-2b B2 「등급 1 진입 엣지: 기존 임대 즉시 만료 · 전부 회수」, 원칙 2.
  - 이 절은 회수를 늦추거나 없애는 안을 다루지 않는다.
- **기전**:
  1. 등급 1에서 사용자가 부른 표면(부채꼴·정보창·설정창)이 떠 있다.
  2. 그 채로 등급 1 → 0 → 1이 된다.
  3. `TickPanelRetreatEntry`(`StickmanAgent.cs:442-448`)가 허가를 만료시킨다.
  4. 각 표면이 다음 프레임에 스스로 걷는다. 경고·연출은 없다.
- ★ **폴링 주기 정정: 1.5초다**(브리프·페르소나의 「1초」가 아니다).
  - 코드 기본값 1초(`StickmanAgent.cs:1548`)를 배포 애셋 `DefaultStickConfig.asset` `fullscreenPollInterval: 1.5`가 덮는다.
  - 양성 대조: 같은 애셋에서 `throwTumbleEnabled: 1`·`longCapeTripMeanSeconds: 0`을 확인했다.
- **등급 확정 지연은 (P, 2P] ≈ 1.5~3.0초다**(`dev-platform` A-4, 디바운서 1.0초 + 폴링 1.5초).
  - 등급 0 체류가 약 1.5초 미만이면 흡수될 수 있고, 3.0초 이상이면 반드시 에지가 된다.
  - **흡수된 체류는 회수도 만들지 않는다** — 지표와 거동이 같은 디바운서를 거친다.
- ★ **Windows에는 자기 유발 재진입 경로가 코드상 있다** — H1(`dev-platform` A-2: 활성화 경로 있음, 발현은 실기로만 판정).
  1. 사용자가 우리 창(설정창 등)을 클릭하면 우리 창이 전경이 된다.
  2. 등급 0이 확정된다.
  3. 브라우저를 다시 누르면 등급 1로 재진입한다.
  4. 사용자 창이 회수된다.
  - **이 경우 필요한 것은 신호가 아니라 H1 수정**(A-6 (a) 「전경이 우리 창일 때 직전 등급 유지」)이다. 그래서 18-3은 에지를 **사유로 가른다.**
  - macOS에는 코드상 이 형태가 없다(A-3).

### 18-2. 셀 줄 — 무엇을 세고 무엇을 세지 않는가

**검색 규칙** (Windows, `dev-platform` A-5 판독 규칙 그대로)
1. `Get-Content -Encoding UTF8 <Player.log>`로 읽는다 — 인코딩을 빼면 한글이 깨져 **0건 = 죽은 프로브**다.

### 18-3. 임계값 제안 (로그 1개 = 실행 1회)

**먼저 H1을 가른다**
- N_self⁺ ≥ 1 → **신호가 아니라 H1 수정 경로**로 리더에게 올린다(`dev-platform` A-6 (a)). 이 에지는 아래 셈에서 뺀다.
- H1 수정 뒤 같은 절차로 **다시 센다** — N_self가 사라진 세계에서 판정한다.

| 판정 | 조건 (착수가 아닐 때 — 위에서부터) |
|---|---|
| **신호 설계 착수** | 아래 T1 · T2 · T3 중 하나라도 참 |
| **현행 유지** | N_ext⁺ ≤ 1 (H 무관) |
| 한 세션 더 수집 | H < 1.5시간 · N_ext⁺ = 2 |
| ★ 한 세션 더 수집 | **H ≥ 1.5시간 · 2 ≤ N_ext⁺ < 2H · N_ext⁺ ÷ H ≥ 4/3회/시간** — 정수 비교 `45 × N_ext⁺ ≥ H분` |
| ★ **현행 유지** | **H ≥ 1.5시간 · 2 ≤ N_ext⁺ < 2H · N_ext⁺ ÷ H < 4/3회/시간** — 정수 비교 `45 × N_ext⁺ < H분` |

**★ 2026-09-15 보완 — 빈칸 채움 (`qa-regression` 적발, ux-designer)**
- **빈칸**: 옛 표는 H ≥ 1.5 · 2 ≤ N_ext⁺ < 2H · T1 거짓 칸에 판정이 없었다. 예: 2시간 로그에 3회는 T3(1.5회/시간 < 2)도, T2(H ≥ 1.5)도, 수집(N ≠ 2)도, 유지(N > 1)도 아니었다.
  - 옛 행 원문: 수집 = 「N_ext⁺ = 2이고 T1 미충족(H < 1.5시간)」, 유지 = 「N_ext⁺ ≤ 1이고 T1 미충족」. H 조건이 괄호에 묻혀 H ≥ 1.5 쪽 공백이 안 보였다. 뜻은 바꾸지 않고 H로 가르는 행으로 풀어 적었다(T1은 에지 2회 이상을 요구하므로 N_ext⁺ ≤ 1이면 구조상 거짓이다).
- **근거 한 줄**: 짧은 로그의 수집 선(N = 2)을 H = 1.5 경계에 그대로 이어 붙인 비율이다 — 2 ÷ 1.5 = **4/3회/시간**. T2와 T3을 H = 1.5에서 같은 선으로 맞춘 방법(3 ÷ 1.5 = 2)과 같다.
- **예시**: 2시간 3회 = 1.5회/시간 → 수집. 8시간 3회 = 0.375 → 유지. 3시간이면 2·3회 유지, 4·5회 수집, 6회 이상 착수(T3).
- **T3 정수 비교**(같은 이유로 병기): `30 × N_ext⁺ ≥ H분`. H는 T 줄의 분 단위라 부동소수 비교를 피한다.
- **검산** (`scratchpad` 스크립트, H 1~1,440분 × N 0~198(199값) × T1): 교정 12/12(위 예시와 경계값 포함). 음성 대조로 새 두 행을 빼면 2시간 3회가 **빈칸으로 잡힌다**(검사기가 빈칸을 볼 수 있다). 전수 573,120칸에서 **빈칸 0 · 중복 0**. H = 89분/90분 연속성: N = 2는 양쪽 수집, N = 3은 양쪽 착수.
- ★ **수집 종결 조건 — 채택(리더 2026-09-15)**: **직전 로그와 이번 로그가 연속으로 「한 세션 더 수집」이면 「신호 설계 착수」로 올린다.** 직전 로그도 같은 절차(18-2 판독 유효 조건 · H1 분리 · 검증 절차 에지 제외)로 센 것이어야 한다.
  - 재검산(`scratchpad` 스크립트 2판, 직전 판정 {없음·착수·수집·유지} × 위 전수 범위): 교정 8/8. 음성 대조로 종결 행을 빼면 「직전 수집 + 2시간 3회」가 수집으로 남는다(검사기가 조건을 본다). 전수 2,292,480칸에서 **빈칸 0 · 중복 0**.
  - 채택 전 문안(제안): 「한 세션 더 수집」의 **종결 조건**이 표에 없다. 제안: **연속 두 로그가 수집이면 착수로 올린다.** 근거는 T1과 같다 — 한 번은 우연이고 두 번은 반복이다. 두 로그를 합산해 다시 판정하는 안은 기각했다. 합산해도 다시 수집 구간에 떨어질 수 있어 끝나지 않는다(예: 3시간 로그 두 개가 각각 4회로 수집이면 합산은 6시간 8회 = 4/3회/시간, 곧 `45 × 8 = 360분`으로 다시 수집이다).

| 조건 | 정의 | 근거 |
|---|---|---|
| T1 버스트 | N_ext⁺ 에지 뒤 **다음 T 줄이 나오기 전(≤60초)**에 R이 오는 묶음이 **2회 이상** | 한 번은 우연이고, 두 번은 「뺏기고 다시 부르고」의 **반복**이다 — 소은 가설(발표자 보기 전환)의 형태 그대로 |
| T2 짧은 로그 | H < 1.5시간이면 N_ext⁺ ≥ **3** | 저장소 선례: 설정창이 예고 없이 닫힌 사건이 검증 중 **3번** 나오자 「설정창이 자꾸 혼자 꺼진다 = 고장」으로 판정했다(`SettingsWindow.cs:100-103`) |
| T3 긴 로그 | H ≥ 1.5시간이면 N_ext⁺ ÷ H ≥ **2회/시간** | T2를 긴 로그에 그대로 쓰면 8시간에 3회(0.375회/시간)도 착수가 된다. **T2와 T3은 H = 1.5에서 같은 선이다**(3 ÷ 1.5 = 2) |

- 참고 지표(판정에 쓰지 않는다): **N_ext**(피해 없는 재진입 포함)는 **기회**의 크기다. N_ext가 크고 N_ext⁺가 작으면 사용자가 등급 1에서 창을 거의 안 연다는 뜻이다 — 신호 수요가 없다.
- **세는 사람이 빼야 할 것**: 검증 세션 절차 중 **의도적으로 전체화면을 오간 단계**(예: `docs/verify/WINDOWS_CHECK_SESSION.md` F-4)의 에지.
  - 뺄 수 없으면 T2·T3을 쓰지 말고 **T1만** 쓴다. T1은 재소환 R을 요구하므로 절차 단계에 덜 오염된다(완전하지는 않다).

### 18-4. 신호를 설계하게 되면 지킬 것 (지금 정하는 것은 이것뿐)

- **회수를 늦추지 않는다.** B2 회수는 그 프레임에 그대로 일어난다.
  - 「회수 **직전** N초 경고」는 그 N초 동안 남의 전체화면 위에 우리 표면을 남긴다 → 원칙 2와 부딪친다.
  - 설계 라운드는 **먼저 이 충돌을 풀어야 한다**(지연 0인 형태만 후보).
- 닻은 캐릭터(§16-2 E-4와 같은 자리), 문구는 `design-narrative`.

### 18-5. 인계

### ㉠ 원칙 4 「위반 없음」 — 결론 유지, 근거 셋 중 **하나가 죽고 하나가 플랫폼 한정**이다

- **옛 문장**(§7, 글자 그대로 남겼다): 「방해 이벤트의 탈출구(ESC·드래그 셰이크·트레이)는 설정창을 거치지 않는다.」
- **① 무엇이 사라졌는가**: **ESC**. 2026-09-05에 원칙 2 위반 봉인으로 **개발 게이트 뒤로** 갔고,
  게이트가 닫힌 릴리스에서는 **조회조차 하지 않는다**(앵커 `if (StickMateDevTools.Enabled && Input.GetKeyDown(EmergencyDisableKey))`, 적중 1).
  **② 날짜**: 2026-09-05. **③ 지금 실재하는 것**: 릴리스 기준 **0**.
- **트레이는 죽지 않았지만 플랫폼 한정**이다 — Windows에만 있다. ★ 이 문서는 **자기 안에서 이미 모순**이었다:
  트레이 행이 macOS를 `✘ 미구현`으로, 허가 발급자 표가 `✘ 트레이 없음`으로 적어 두고도 원칙 4 줄만 한정 없이 셋을 나열했다.
- **④ 그래서 판단이 어떻게 바뀌는가**

| 탈출구 | Windows | macOS | 근거 |
|---|---|---|---|
| ESC | **0** | **0** | 개발 게이트 뒤(위 앵커) |
| 트레이 긴급정지 | 1 | **0** | 트레이가 Windows 전용. `States/RodeoCursorState.cs`가 종료 경로로 「트레이 긴급정지」를 열거한다(그 파일 1회 · 저장소 전체로는 7파일이라 파일 범위를 적는다) |
| 드래그 셰이크(커서로 털어내기) | 1 | 1 | 플랫폼 가드 0(양성 대조: 같은 검색이 `Win32WindowService.cs`의 `#if UNITY_STANDALONE_WIN` 1을 잡는다) |
| 전역 단축키 | — | — | **탈출구가 아니다.** `Interaction/RodeoCursorWatcher.cs` 앵커 `if (!_config.rodeoCursorEnabled)`(적중 1)는 **발동 게이트**이고 진행 중인 것을 끊지 않는다 |

⇒ **Windows 2개 · macOS 1개.** **결론(「위반 없음」)은 그대로 선다** — 이 절의 주장은 「[설정] 입구가 접혀도
방해 이벤트 탈출구가 함께 사라지지는 않는다」이고, 남은 드래그 셰이크는 설정창을 거치지 않는다.
`Interaction/CharacterInfoWindow.Layout.cs`의 [✕] 근거도 살아 있다(앵커 `이 창의 유일한 탈출구라 접지 않는다`, 적중 1).

★ **그러나 macOS는 여유가 1개다.** 그 하나가 막히는 조건(커서를 못 쓰는 상황)에서는 남는 것이 전역 단축키뿐이고,
그것은 **이벤트를 끊지 못한다.** macOS는 accessory 정책으로 **Dock 아이콘과 Cmd-Tab에서도 빠져 있다**
(`Platform/MacOS/MacSpaceBehaviorNative.cs` 앵커 `Dock 아이콘과 Cmd-Tab 목록에서 사라진다`, 적중 1) —
즉 OS 쪽 우회 경로도 얇다. **「위반 없음」을 취소선으로 내리지는 않되, macOS 단일 탈출구를 리더 판정 대기 항목으로 올린다.**

★ **판정하지 않은 것**: 원칙 4가 요구하는 **「1초 내 해제」**. 셰이크는 커서 속도 임계

억지로 결론을 만들지 않았다.
