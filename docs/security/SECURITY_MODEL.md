## 1-3. ★ 정정 2 — 그리지는 않는다. 그러나 **로그에는 남는다** (출구가 두 개다)

리더가 확인된 사실로 적은 *"남의 창 제목·파일명을 한 글자도 그리지 않는다"* 는 **렌더에 대해서는 참**이다.
그러나 **렌더가 유일한 출구가 아니다.**

**(a) 세이브 경로가 Player.log에 그대로 찍힌다** — 리더의 브리핑대로였다. 실측 확인:
```
Player.log: [성장] 준비 완료 — 스틱메이트 Lv.4 (145/429 XP). 저장 파일=불러옴
            (/Users/<이름>/Library/Application Support/DefaultCompany/StickMate/stickmate_character.json).
출처: Interaction/CharacterProgressionDirector.cs:82
```
(양성 대조: 같은 grep이 그 로그에서 `/Users/` 4건, `StickMate` 5건을 찾는다 — 탐지력 있음.)

**(b) ★ 더 중요한 것 — 남의 앱 신원이 로그에 들어간다. 양 플랫폼 모두.**

| 플랫폼 | 파일 | 로그에 들어가는 것 |
|---|---|---|
| Windows | `Platform/Windows/WindowsGameProcessProbe.cs:159` → `Win32WindowService.cs:1870` | **`전경 실행 파일={전체 경로}`** — 남의 exe **풀 패스**. `C:\Users\<실명>\...` 가 통째로 |
| macOS | ~~`Platform/MacOS/MacWindowService.cs:1516,1534` → `:1403`~~ → `Platform/MacOS/MacWindowService.cs`의 `판정 근거 창 = '{owner}' bounds=`(HEAD `fa25570` 기준 :1518) · `판정 근거 창 = '{owner}'(pid {ownerPid})`(:1536) → 로그 줄 `Debug.Log($"[전체화면판정] …")`(:1405 — `[전체화면판정]`은 이 파일에 3회라 줄 번호에 판을 붙였다) | `판정 근거 창 = '{owner}'` — 남의 앱 **이름** |

둘 다 `Debug.Log($"[전체화면판정] ... — {reason}")`로 나간다. Windows 쪽이 더 나쁘다 —
경로에 **Windows 사용자 계정명**이 포함된다.

- **이건 원칙 3 위반이 아니다.** 읽기 전용이고, 최소 권한(`PROCESS_QUERY_LIMITED_INFORMATION`)이며,
  레지스트리는 `KEY_READ`만 쓴다. 그 파일은 **원칙 3을 매우 잘 지키고 있다**(쓰기 API를 선언조차 안 하고,
  그 사실을 테스트가 잠근다). 문제는 침해가 아니라 **로그 위생**이다.
- **왜 지금 말하는가**: 이 팀의 표준 절차가 *"릴리스 빌드를 켜고 Player.log로 확인한다"* 이고,
  버그 신고 때 사용자가 그 로그를 **개발자에게 보낸다**. 그리고 `TEAM.md`가 마케팅 캡처를
  *"깨끗한 테스트 환경에서 — 남의 창 제목·파일명이 찍힌다"* 며 이미 경계하고 있다. **그 경계가
  화면에 대해서만 걸려 있고 로그에는 안 걸려 있다.**

# 2. 유료 경계 감사 — 이번 라운드의 본체

## 2-1. ★ `STICKMATE_UNLOCK_ALL` — 오늘은 안전하다. 그리고 그게 문제의 전부가 아니다

> ★ **as-of 2026-09-02 ~ 2026-09-28.** 이 절의 사실 관찰(코드 형태 · 소비자 목록 · 우회 지점)은 그대로
> 유효하지만 **결론의 시제가 바뀌었다.** 2026-09-28 사용자 결정(DLC 폐지)으로 **「예약된 사고」가
> 취소됐다** — 이 절이 *"나중에 비싸지는 것의 교과서적 사례"*라고 부른 그 「나중」은
> **유료 경계가 `IsOwned`에 합류하는 날**이었고, 합류할 유료 경계가 없어졌다.
> ~~DLC 도입 후: 개발자~~ → **도입이 없다.**
> **그래서 §2-1의 우선순위는 내려간다.** `||` 하나를 나누는 일(3-1의 문법적 격리)은 여전히
> 「하면 좋은 위생」이지만 **매출 방어가 아니다** — 지금 `UNLOCK_ALL`이 여는 것은 **레벨 게이트뿐**이고
> 레벨 게이트는 **끝까지 무료 성장 요소**다. 판정: **오늘도 고칠 버그 없음, 그리고 기한도 없다.**
> ★ **한 가지는 살아남는다**: 이 절이 지적한 *"보유라는 단어 하나에 성장·구매·결제를 전부 담는"* 형태는
> **B층(동전 구매)에 대해서는 여전히 실재한다**(`Core/CurrencyModel.cs` 실측). B층 위조의 판정은
> §4 · E-8 그대로 「**그냥 둔다**」이고, 유료물이 0이 되어 그 근거가 **더 강해졌다**.

**릴리스 빌드에서 이 환경변수가 유료 경계를 넘는가? — 오늘은 "넘을 유료 경계가 없다".**

판정 규칙은 실제로 잘 짜여 있다(`Core/EquipmentDebugUnlock.cs`):

```csharp
public static bool ResolveUnlockAll(bool developmentConfiguration, string environmentRaw)
    => developmentConfiguration || StickMateDevTools.ResolveFromEnvironmentValue(environmentRaw);
```

- 릴리스 빌드(`UNITY_EDITOR`·`DEVELOPMENT_BUILD` 둘 다 없음) + 환경변수 미설정 → **닫힘**.
- 그 사실을 `EquipmentDebugUnlockReleaseGateTests`가 순수 함수로 잠근다(에디터에서도 릴리스 값을 재현).
- 사람이 출시 전에 상수를 되돌리는 구조가 아니다 — **컴파일 심볼이 보장한다.** 이건 잘한 설계다.
- 그래도 **릴리스 빌드 + `STICKMATE_UNLOCK_ALL=1`이면 열린다**(의도된 QA 탈출구).
  오늘 그것이 여는 것은 **레벨 게이트뿐**이고, 레벨 게이트는 무료 성장 요소다. **매출 피해 0.**

### 그런데 우회 지점이 하필 여기다

```csharp
// Core/ItemCatalog.cs:233
public bool IsOwned(StickConfig config)
    => !RequiredLevel.HasValue
       || EquipmentDebugUnlock.UnlockAll          // ← 무조건 단락시키는 OR
       || CharacterProgressionModel.Level >= RequiredLevel.Value;

// Core/EquipmentModel.cs:179
public static bool IsItemOwned(EquipmentSlot slot, int itemIndex)
    => EquipmentDebugUnlock.UnlockAll
       || CharacterProgressionModel.Level >= RequiredLevel(slot, itemIndex);
```

**이 두 함수는 "보유"라는 단어 하나에 성장·구매·결제를 전부 담게 되어 있다.** 그리고 그것이
추측이 아니라는 증거가 **코드 주석과 설계 문서 양쪽에 이미 적혀 있다**:

| 출처 | 적혀 있는 것 |
|---|---|
| `ItemCatalog.cs:244` (주석) | 상태 슬롯은 *"훗날 여기에 **가격표**가 들어와도 레이아웃을 두 번 고치지 않게"* |
| `ItemCatalog.cs` 클래스 주석 | *"훗날 판매를 얹을 때 데이터 모양이 이미 맞아 있게"* |
| `docs/UX_SHOP_AND_CURRENCY.md` §3-3 | 카드 상태표에 **S5 `DLC(백엔드 없음)` / S6 `DLC(스토어 배선 후)`** 가 이미 있다 |

**→ 유료 경계는 바로 이 `IsOwned`에 합류하도록 설계돼 있다.** 합류하는 순간
`EquipmentDebugUnlock.UnlockAll ||` 가 **그 위에 그대로 얹힌다.** 그러면
**환경변수 한 줄이 출하 빌드에서 유료 팩을 여는 크랙**이 된다 — 게다가 그 변수 이름은
**저장소 문서 9곳에 적혀 있고**, 형제 변수인 `STICKMATE_DEVTOOLS`는 **부팅 배너가 사용자에게 직접
알려준다**(`AppControlDirector.cs:187`).

> **판정: 오늘 고칠 버그는 없다. 그러나 이건 "나중에 비싸지는 것"의 교과서적 사례다.
> 지금은 `||` 하나를 나누는 일이고, DLC가 올라탄 뒤에는 매출 누수 + 스키마 마이그레이션이다.**

## 2-2. ★ 더 급한 것 — 설계 문서가 **소유 플래그를 평문 세이브에 넣기로** 이미 적어 두었다

> ★ **as-of 2026-09-02 ~ 2026-09-28.** 이 절이 경고한 수렴(*"둘 다 맞다. 합치면 틀린다"*)은
> **한쪽 팔이 사라져 성립하지 않는다.** 2026-09-28 사용자 결정(DLC 폐지)으로
> *"구매 소유 플래그"*가 **DLC 소유를 포함할 일이 없어졌다** — 남는 것은 B층(동전으로 산 것)뿐이고,
> B층은 이 문서가 처음부터 「**세이브(평문)에 둔다 · 위조되면 자기 손해뿐**」으로 판정한 층이다(§3-1 표).
> ⇒ **이 절의 P0 성격은 해제된다.**
> ★ **그러나 금지 토큰은 하나도 풀지 않는다.** `EntitlementNotInSaveAuditTests`의
> `dlc`·`pack`·`entitle`·`own`·`license`·`sku` **6종 전부 유지**하고, 성격만
> ~~「C층을 세이브에서 지킨다」~~ → 「**미래에 그릇을 먼저 만들지 않는다**」로 재정의한다.
> 이유는 이 절 자신이 적어 두었다 — 세이브에 소유 필드가 **한 번 생기면** 그것이 다음 라운드의
> 기본 설계가 되고, 그때는 「빈 그릇 지우기」가 아니라 **스키마 마이그레이션**이 된다.
> **0건을 0건으로 유지하는 비용이 가장 싸다.**
> ★ 아래 실측 세이브 예시(`"version": 9`)도 **2026-09-02 기록**이다 — 현행 버전은 이 문서가 보증하지 않는다
> (스키마 버전의 정본은 `CharacterSaveStore.CurrentVersion`이고, 테스트가 그 상수를 참조해 검증한다).

`docs/UX_SHOP_AND_CURRENCY.md` **§9-3 (P0, 리더에게 이미 올라간 항목)**:

> *"세이브 — 재화 잔액 + **구매 소유 플래그** + 스탯별 최고 도달 단계 + 유예 기산점이 새 필드다
> → `CharacterSaveStore.CurrentVersion` 올림"*

그리고 §3-7 예외 상태표에 **`DLC 미구매 | DLC 플래그`** 가 있다.

**이 "구매 소유 플래그"가 DLC 소유까지 포함하면, DLC 소유가 평문 JSON 한 줄이 된다.** 실측한 현재 세이브:

```json
{ "version": 9, "level": 6, "currentXp": 433.89, ... "wornHead": "equip.head.fur" }
```
경로: `~/Library/Application Support/Vibelab/StickMate/stickmate_character.json`
(Windows: `AppData/LocalLow/Vibelab/StickMate/`) — **평문, 메모장으로 편집 가능, 경로는 로그에 인쇄됨.**

**두 문서가 각자 옳은 판단을 하면서 같은 지점으로 수렴하고 있다.** `ux-designer`는 "구매했으니 저장해야
한다"는 당연한 결론을 냈고, `EquipmentDebugUnlock`은 "보유 판정은 한 곳이어야 한다"는 옳은 결론을 냈다.
**둘 다 맞다. 합치면 틀린다.** — 이게 `game-architect`가 말한 *"개별이 다 옳아도 합이 어긋난다"* 의 실례다.

## 2-3. `STICKMATE_DEVTOOLS` — 유료 경계를 넘지 않는다 (반증 완료)

주석이 *"일부러 다른 변수로 뒀다"* 고 주장한다. **그 주장은 참이다 — 소비자 목록으로 확인했다.**

`StickMateDevTools.Enabled`를 읽는 프로덕션 코드는 4개뿐이다:
`RunawayDirector`(가출 강제) · `ActionCommandPopover` · `ShapeCoverageGuard`(폴백 표시) ·
`AppControlDirector`(단축키 폴링 게이트). **보유·레벨·아이템 판정 경로에 하나도 없다.**
`EquipmentDebugUnlock`이 `StickMateDevTools`에서 재사용하는 것은
`ResolveFromEnvironmentValue(string)` — **문자열 파서 순수 함수 하나**이고 게이트가 아니다.

DEVTOOLS가 여는 것: 진단 로그(D) / 하드웨어 반응 미리보기(H) / 스트레스 게이지 순환(S) /
할일 알림 데모(J) / 집중 90초 데모(F) / 가출 강제(N).
**XP·레벨을 주는 경로는 없다** — `AddXp` 호출자는 `CharacterProgressionDirector` 하나뿐이고
개발 단축키에서 도달하지 않는다. 즉 "DEVTOOLS로 레벨을 올려 아이템을 연다"는 **간접 경로도 없다.**

- **판정: 현행 유지.** 원칙 1(행동-텍스트 싱크)을 지키려고 만든 게이트지 유료 게이트가 아니다.
  배너가 사용자에게 변수명을 알려주는 것도 **오늘은 무해**하다(여는 것이 전부 연출 미리보기라서).
- **단, §3의 규칙이 적용된다**: 앞으로도 이 게이트에 **보유·결제 판정을 얹지 않는다.**

> - **§3-2의 감사 2건은 둘 다 유지한다.** `EntitlementNotInSaveAuditTests`는 「**미래 그릇 금지**」로

# 4. 세이브 무결성 — 판정: **그냥 둔다** (감지도 하지 않는다)

**셋 중 "그냥 둔다"를 고른다.** 단, 그 판정은 §3의 C층 분리를 **전제로만** 성립한다.

1. **피해자가 가해자와 같은 사람이다.** 리더보드·거래·멀티·공유가 전부 **실측 0건**이다.

   **보안이 유통을 죽이면 순손실이다.**
4. **★ 오탐 비용이 비대칭이다.** *정당한 유저를 한 명 잠그는 것이 무단 사용 열 건보다 비싸다.*

   ```
   **손상된 세이브를 "변조"로 판정하는 코드는, 이 저장소에서 치터보다 우리 버그를 먼저 만난다.**
   그때 사용자에게 *"당신은 치터입니다"* 라고 말하는 것은 우리가 낼 수 있는 최악의 오답이다.

- **그런데 이 미확인은 우리에게 치명적이지 않다.** §3의 C층을 쓰면 판정 실패 시 답이 정해져 있다 —
  **§5-4의 "실패는 관대하게" 규칙.**

## 5-2. ★ MS 스토어 — `docs/strategy/`의 **미확인 1건을 해소했다**

선행 조사에 *"MS 스토어에서 DLC를 팔 수 있는지 자체가 미확인"*으로 남아 있던 항목이다.
**규범 문서(learn.microsoft.com)의 공식 비교표로 확인했다:**

| 기능 | **Packaged (MSIX)** | **Unpackaged (Win32 EXE/MSI 링크 등록)** |
|---|---|---|
| Commerce Platform (payment, **in-apps**, subscriptions, licensing) | **MS 스토어 커머스 사용 가능** | **"Use your own or 3P commerce platform"** |
| Code signing | **MS가 무상 제공** | **개발자가 CA 인증서 구매·부담** |

**→ 답: 팔 수 있다. 단 MSIX로 낼 때만.** "기존 EXE를 링크로 등록"하는 경로는 **애드온을 팔 수 없다.**

### ★ 이게 `ROADMAP.md` 3절의 비용 계산을 뒤집는다

`MARKET_LANDSCAPE.md` 220행이 *"MS 스토어 MSI/EXE 경로의 코드서명 인증서 비용"*을 새로 발견한 비용으로
적어 두었다. **그 비용을 무는 바로 그 경로가, 동시에 DLC를 팔 수 없는 경로다.**
즉 언패키지 경로는 **두 번 손해**이고, MSIX 경로는 **서명 무료 + 애드온 판매 가능**이다.
→ `product-strategy`에 인계할 항목(리더 경유).

### 형태까지 정해 둔다 — **"durable add-on"이지 "DLC"가 아니다**

MS 문서 주의사항 인용: *"Other types of add-ons, such as **durable add-ons with packages (also known as
downloadable content or DLC)** are **only available to a restricted set of developers**."*

**→ 패키지가 딸린 진짜 "DLC"는 우리가 못 쓴다.** 우리에게 맞는 것은 **durable add-on(기본 수명 Forever)**
= **라이선스만 사고 콘텐츠는 본편에 들어 있는 형태**다. 6팩 콘텐츠가 어차피 앱 안에 있으므로 **이게 정확히
우리 모양이다.** 우연이 아니라 §3의 C층 설계와 같은 구조다.

### 확인된 제약 2건

- **"In-app purchase functionality is not currently supported in elevated applications."**
  → StickMate는 승격 실행이 아니다(권한 0). **문제 없음.** 다만 **작업표시줄 원복 예외**(`ABM_SETSTATE`)가
  혹시라도 승격을 요구하게 바뀌면 **결제가 함께 죽는다** — `dev-platform`에 전달할 제약(리더 경유).
- **`Windows.Services.Store`에는 시뮬레이터가 없다.** 문서 명시: 테스트하려면 **먼저 스토어에 게시하고
  기기에 설치해 라이선스를 받아야** 한다. → 결제 배선 라운드의 일정에 이 왕복이 들어간다.

### 남은 미확인 (정직하게 남긴다)

MS 직원 Q&A 답변은 *"MSIX packaged **from an exe file**이면 스토어 기능을 못 쓸 수 있다"* 고 말한다.
규범 표는 "MSIX면 된다"고 하고, Desktop Bridge 앱이 `StoreContext`를 쓰는 방법도 문서화돼 있다.
**Unity가 만드는 exe → MSIX Packaging Tool 경로가 애드온을 지원하는지는 두 출처가 어긋난다 — 미확인.**
결제 채널을 확정하기 전에 **실물로 확인해야 한다.** 나는 Windows 실기가 없어 재지 못했다.

## 5-3. 맥 앱스토어 — 조사 안 함

1차 출시 대상 제외(우선순위 최하, 리더 지시). 참고로 `ProjectSettings.asset:
useMacAppStoreValidation: 0`. 착수 시 영수증 검증이 별도 주제가 된다.

## 5-4. ★ 핵심 질문에 대한 답

> **오프라인 상주 앱에서 "이 사람이 이 팩을 샀는가"를 어디까지 믿을 수 있는가?**

**답: 끝까지는 못 믿는다. 그리고 믿으려고 애쓰면 안 된다.**

- Valve가 자기 API에 *"아이템 지급용이 아니다"* 라고 적어 두었다. 그 이상의 보증은 **서버로만** 살 수 있고,
  서버는 이 앱이 팔지 않기로 한 것이다.
- 따라서 **정직한 목표는 "무단 사용 불가능"이 아니라 "정직한 사용자가 정직하게 살 이유가 있고,
  실수로 잠기지 않는 것"**이다.

### 실패는 **관대하게** — 이 규칙이 §4-1의 오탐 비대칭을 상속한다

| 스토어 조회 결과 | 우리 동작 |
|---|---|
| "샀다" | 연다 |
| "안 샀다" | 잠근다 + 구매 안내(S6) |
| **조회 실패 / 오프라인 / 스토어 미실행** | **★ 직전에 성공했던 판정을 그대로 유지한다. 절대 회수하지 않는다** |

**돈을 낸 사용자에게서 비행기 안에서 팩을 빼앗는 것**은, 안 낸 사용자 열 명이 쓰는 것보다 비싸다.
이건 §4-1의 4번과 **같은 원칙의 다른 적용**이다. 그리고 이 규칙 덕분에 §5-1의 "Steam 오프라인 동작 미확인"이
**설계상 무해**해진다 — 어느 쪽이든 우리 동작이 정해져 있다.

(마지막 성공 판정을 **어디에** 기억할 것인가는 §3의 C층과 충돌한다 — 파일에 쓰면 위조 대상이 생긴다.
**권고: 프로세스 메모리 + "이번 실행에서 한 번이라도 성공했으면 유지". 실행 간 캐시는 만들지 않는다.**
사용자가 오프라인으로 앱을 재시작하면 잠기지만, 스토어 클라이언트가 로컬 라이선스를 들고 있는 것이
정상 경로라 실무상 거의 발생하지 않는다. **이건 판정이 아니라 권고다 — 실기 확인 후 확정할 것.**)

# 8. 원칙 4 플러그인 통로 — **사용자 결정 대기. 답을 가정하지 않고 두 갈래로 쓴다**

★ 어느 갈래든 공통: **`game-architect` §1-D에 따라 레지스트리 자체가 아직 없다. 지금이 가장 싸다.**

## (가) 봉인 — 매니페스트는 우리만 만든다

- **서명 검증 불필요.** 매니페스트가 **서명된 우리 앱 번들 안에서만** 로드되면 OS 코드서명이 이미 무결성을 보장한다.
- **필요한 것 1가지**: 레지스트리를 **`Resources`/번들 내부에서만** 로드하도록 짓는다. 임의 경로 인자를
  받지 않는다. **비용 0(지금) / 파괴적 변경(나중).**
- **매출 영향 없음.** DLC 팩도 우리 것이므로 §3의 C층으로 충분하다.

## (나) 제작 개방 · 판매 봉인 — 남이 만들되 아무도 팔지 않는다

- **매출 위협 없음** → **서명 검증(코드 신뢰) 여전히 불필요.** 여기가 흔한 오해다: 서명은 **돈이 걸릴 때**
  필요하지, 제작 개방 자체가 서명을 요구하지 않는다.
- **대신 다른 3가지가 필요해진다** (위협의 성격이 매출 → 안전·평판으로 바뀐다):
  1. **매니페스트를 끝까지 선언적으로 유지한다.** 코드·스크립트 참조·파일 경로·URL을 **필드로 두지 않는다.**
     두는 순간 데이터가 아니라 **실행 가능 표면**이 되고, 그때부터 백신이 우리를 본다(선 3).
  2. **로드 시 엄격 검증 + 실패는 조용히 건너뛴다.** 남의 팩 하나가 앱 전체를 죽이면 그 신고는 우리에게 온다.
     (`game-architect`가 지적한 `Append*`에 `default:`가 없어 **조용히 안 그려지는** 문제와 같은 계열 —
     그쪽 착수 2번과 함께 보면 좋다.)
  3. **출처를 화면에 표시한다.** 제3자 콘텐츠가 1st-party로 읽히면 **남이 쓴 대사·조형이 우리 평판이 된다.**
     원칙 1(행동-텍스트 싱크)의 책임 주체가 흐려지는 문제이기도 하다 — `design-narrative` 소관과 겹친다.
- **판정 필요 항목**: 팩이 **대사**를 넣을 수 있는가. 넣을 수 있으면 검열·신고 경로가 필요해지고,
  그건 상주 동료 앱에서 무거운 주제다. **나는 이 질문을 열어 둔다 — `design-narrative`·`product-strategy` 사안.**

## (다) 완전 개방 (판매까지) — ★ 이 갈래만 선 1을 건드린다

**사용자가 이걸 고르면, 그건 보안 결정이 아니라 사업 모델 결정이고 리더가 그렇게 보고해야 한다.**

`MARKET_LANDSCAPE.md`가 최대 차별점으로 세운 자산을 태우는 선택이다.

- **덜 파괴적인 대안**: 제3자 팩을 **각 스토어의 애드온으로만** 팔게 하고(우리는 중개하지 않는다),

## T-3. 방어 1 — **앱이 도는 동안 벽시계를 수급 입력으로 쓰지 않는다** (완전 방어, 비용 0)

> **T-3-a (필수·금지):** 수급·정산 판정 경로에서 `DateTime.Now` / `DateTime.UtcNow` /
> `DateTimeOffset.Now` / `DateTimeOffset.UtcNow` / `System.Environment.TickCount`를 **읽지 않는다.**
> 예외는 **T-6의 재기동 정산 1지점**뿐이고, 그 지점은 **단일 함수**여야 한다(감사가 셀 수 있게).
>
> **T-3-b (필수):** 세션 내 시간 경과는 **`Time.realtimeSinceStartupAsDouble` 델타**로 잰다.
> 이 저장소는 이미 이 값을 **「단조 증가 시각」**이라 부르고 `Platform/`에서 10곳 넘게 쓴다
> (`FullscreenSuspendPolicy.cs:438`(`1f7e139` 기준, HEAD `:468`) · `RepeatedLogFolder.cs:68`(HEAD 그대로) 주석이 그 관례를 명시). **새 관례가 아니다.**
>
> **T-3-c (필수·회피):** `Time.deltaTime`을 쓰지 않는다. 두 가지 이유가 겹친다 —
> (i) `Time.timeScale`에 곱해진다(오늘 프로덕션 쓰기 0건이지만 **계약이 아니라 우연**이다),
> (ii) ★ **`Time.maximumDeltaTime`이 `deltaTime`을 자른다**(MS가 아니라 Unity 공식 문서:
> *"Sets a limit on the value of Time.deltaTime"*). 절전 티어·스톨·시스템 절전에서
> **실제 시간보다 적게 쌓인다.** `unscaledDeltaTime`이 같이 잘리는지는 **Unity 문서에 서술이 없다 — 미확인**
> (양쪽 문서 페이지를 직접 열어 확인했다). 그래서 **논쟁 자체를 없애는** `realtimeSinceStartupAsDouble`을 쓴다.
>
> ★ 오차 방향 주의: 잘림은 **적게 주는** 방향이라 보안 사고는 아니지만 **공정성 사고**다.
> "밤새 켜뒀는데 8시간이 안 찼다"는 신고가 이 경로로 온다.

### 이 하나로 무엇이 끝나는가

- **(다) 무효화** — 시계만 흘러도 아무것도 안 쌓인다.
- **(가)(나)를 「세션 안에서」 완전 차단** — 앱을 켜 둔 채 시계를 아무리 만져도 수급량이 안 바뀐다.
- **(자) 차단** — timeScale 무관.
- **오탐 0** — 검증도 거부도 없다. 다른 숫자를 쓸 뿐이다.

### 미확인 1건 (정직하게 남긴다)

`Time.realtimeSinceStartup(AsDouble)`이 **시스템 시계 변경에 면역인지 Unity 문서가 명시하지 않는다.**
근거는 정황이다 — 양 플랫폼 구현이 단조 카운터(Windows QPC / macOS `mach_absolute_time`)이고,
이 저장소가 이미 그렇게 부르고 있다. **확정 절차**(실기 필요, 우리 머신에서 하면 안 된다 —
사용자 시계를 건드리는 일이다): 별도 머신에서 앱을 켠 채 시계를 +1일 이동 → `[수급]` 로그의
누적 초가 **점프하지 않는지** 확인. 점프하면 T-9-2의 P/Invoke 앵커가 **필수로 승격**된다.

### T-4-a. 경과는 **음수가 될 수 없다** (시나리오 바)

```
- **시계를 되돌리면 지급이 0**이고, 그 뒤 `lastSettledWallUnix = min(lastSettledWallUnix, nowWallUnix)`로
  **아래로 재기준한다.** ★ 얼리지 않는다 — 이게 오탐 방어의 핵심이다.
  CMOS 방전·NTP 오작동으로 시계가 과거로 튄 **정상 사용자**가 영구 동결되면 안 된다.
- 선례가 이미 있다: ~~`CharacterStatsModel.cs:79`~~ → `CharacterStatsModel.cs`의 `if (elapsed < 0L) return 1;` 줄(HEAD `fa25570` 기준 :77 — 옛 인용이 가리키던 :79는 지금 닫는 중괄호다) — `if (elapsed < 0L) return 1;` (근속이 음수가 안 되게).
  **같은 관례를 수급에 확장하는 것이지 새 규칙이 아니다.**

### T-4-b. "우리 날짜"는 **전진만 한다** (시나리오 나 — 완전 차단)

```
dayIndex   = floor((nowWallUnix + fixedUtcOffsetMinutes*60) / 86400)
budgetRefill = (dayIndex > maxDayIndexSeen)
```
- 시계를 과거로 돌려도 `dayIndex ≤ maxDayIndexSeen`이라 **예산이 다시 차지 않는다.**
- **(나)는 여기서 100% 죽는다** — 되돌리기로는 어떤 이익도 만들 수 없다.

### T-4-c. ★ **한 번의 정산이 만들 수 있는 미래는 하루를 넘지 않는다** (오탐 상한을 1일로 고정)

```
if (budgetRefill) { maxDayIndexSeen = min(dayIndex, maxDayIndexSeen + 1); ... }
```

**이 한 줄이 T절 전체에서 가장 값싸고 가장 중요한 오탐 방어다.**

| 상황 | 래칫 없이 | 이 규칙으로 |
|---|---|---|
| CMOS 방전 → 시계가 2099년 → 한 번 실행 → 사용자가 시계 수정 | `maxDayIndexSeen`이 **26,000일** 앞서 박힘 → **평생 일일 보상 0** (조용한 실패, 사용자가 영원히 원인을 모른다) | **+1일**만 앞선다 → 최대 **하루** 멈추고 정상 복귀 |
| 공격자가 2099로 두고 100번 재실행 | — | 100번 실행 = 100사이클 공격. **T-6/T-7과 같은 얘기이지 새 구멍이 아니다** |

**검산**: 어떤 벽시계 입력이 들어와도 1회 정산에서 `maxDayIndexSeen` 전진 ≤ 1,
지급 ≤ `min(C, 남은 하루 예산)`. **입력이 무한대여도 출력이 유한하다** — 이게 검증 없이 얻는 안전이다.

## T-5. 방어 3 — **하나의 일일 예산**을 유휴·오프라인·정액 채널이 **공유**한다 (시나리오 차)

> **T-5-a (필수):** 시간 기반 채널(유휴 · 오프라인 · 무료 회복제 · [오늘 할일])은
> **단일 `dailyBudgetSpentCoins`**에서 인출한다. 채널별 별도 예산·별도 카운터를 만들지 않는다.
>
> **T-5-b (필수):** 예산 refill은 **T-4-b의 래칫 전진 시에만**. 「마지막 refill 이후 24시간」 같은
> 상대 시간 방식은 금지 — 그건 벽시계 델타를 다시 신뢰 입력으로 끌어들인다.

**왜 이게 보안 항목인가**: 채널이 3개고 예산이 3개면 (가) 1사이클의 상금이 **3배**가 된다.
그리고 채널은 앞으로 늘어난다(ECONOMY_SPEC 0-2-6이 *"앞으로 이런 채널을 하나 더 붙일 수 있다"*고 적어 뒀다).
**예산을 나누는 결정은 조용히 공격 상금을 곱한다.**

## T-6. 방어 4 — 오프라인 정산: **검증하지 않는다. 자른다.** (시나리오 마)

```
// 재기동 직후 1회. 이 함수가 앱 전체에서 벽시계를 읽는 유일한 수급 지점이다(T-3-a).
int SettleOffline(long nowWallUnix, Ledger led, EconomyRates r)
{
    long elapsed = Max(0, nowWallUnix - led.lastSettledWallUnix);   // T-4-a

    int dayIndex = DayIndex(nowWallUnix, led.fixedUtcOffsetMinutes);
    if (dayIndex > led.maxDayIndexSeen) {                            // T-4-b
        led.dailyBudgetSpentCoins = 0;
        led.maxDayIndexSeen = Min(dayIndex, led.maxDayIndexSeen + 1);// T-4-c ★
    }

    long raw      = (long)(elapsed * r.OfflineCoinsPerSecond);
    int  budgetLeft = Max(0, r.DailyBudgetCoins - led.dailyBudgetSpentCoins);
    int  grant    = (int)Min(Min(raw, r.OfflineCapCoins), budgetLeft);   // ★ 3중 clamp

    led.dailyBudgetSpentCoins += grant;
    led.lastSettledWallUnix    = Min(nowWallUnix,                        // 되돌림이면 아래로 재기준
                                     Max(nowWallUnix, led.lastSettledWallUnix));
    return grant;   // 0이어도 정상이다. 경고하지 않는다.
}
```

### 이 함수의 성질 (전부 검산 가능)

| 성질 | 근거 |
|---|---|
| **출력이 항상 유한** | `grant ≤ min(OfflineCapCoins, DailyBudgetCoins)` — 입력 `nowWallUnix`가 무한대여도 |
| **거부·경고·잠금이 없다** | 반환값만 있고 판정 플래그가 없다. **오탐이라는 개념이 존재하지 않는다** |
| **시간대·서머타임 무영향** | UTC 유닉스 초 + 고정 오프셋(T-D-4) |
| **NTP 보정 무영향** | 몇 초의 보정은 `grant`를 몇 동전 움직일 뿐, 어떤 분기도 안 바꾼다 |
| **세이브 필드 부재 시** | `lastSettledWallUnix == 0` → `elapsed`가 거대 → **상한 지급**. 구버전 파일·손상 파일이 **잠기지 않고 관대하게** 끝난다(§5-4 "실패는 관대하게"의 재사용) |

> **T-6-a (필수):** `SettleOffline`은 **순수 함수**여야 한다(시각·요율·원장을 전부 인자로 받는다).
> 이 저장소의 `EquipmentDebugUnlock.ResolveUnlockAll`·`FullscreenSuspendPolicy`가 쓰는 관례이고,
> **시계를 조작하지 않고도 테스트할 수 있는 유일한 형태**다. 정적 시각 읽기가 함수 안에 있으면
> 이 절의 어떤 규칙도 회귀 테스트로 잠글 수 없다.
>
> **T-6-b (필수):** 판정은 **`Platform/` 중립 위치**(또는 `Core/`)에. 플랫폼 전용 코드는
> 사실 조회만(T-9-2를 채택할 경우). — CLAUDE.md의 `FullscreenSuspendPolicy.cs` 사고 재발 자리.

## T-7. ★ **막을 수 없는 것** — 정직하게 (시나리오 사)

> **재부팅을 사이에 끼우고 시계를 앞으로 옮기는 반복 공격은 서버 없이 막을 수 없다. 끝.**

로컬에서 **위조 불가능한 양**은 세 개뿐이다:
① 프로세스 단조 시계(`realtimeSinceStartupAsDouble`) — 재기동에서 리셋
② 부팅 단조 시계(`mach_continuous_time` / `QueryInterruptTime`) — **재부팅에서 리셋**
③ 검증 가동시간(프레임 델타 누적 = `TotalCompanionSeconds`의 형제) — 위조 불가하지만 **평문 세이브에 있다**

즉 **재부팅이 우리의 마지막 앵커를 지운다.** 그리고 재부팅은 40초짜리 조작이다.

### 비용·상금 검산 (숫자는 리더 브리핑 유력값 + ECONOMY_SPEC 실측)

- 1사이클 = 재부팅 ~40초 + 시계 변경 ~15초 + 실행·정산 ~10초 ≈ **65초** → **55.4사이클/시**
- 유휴 12동전/분, 오프라인이 그 절반(6/분), 상한 8시간 → **C = 2,880동전/사이클**
- → **159,552동전/시** (55.4 × 2,880)
- **동전 소모처 총액 = 4,550동전**(`ECONOMY_SPEC.md` 0-2-1, 7슬롯 42종 전부 = 650×7)
- → **159,552 / 4,550 = 35.1배.** ★ **상한 C를 아무리 낮춰도 1시간이면 경제가 끝난다.**

> ### 그래서 결론이 뒤집힌다 — **「상한을 낮춰서」 막는 게 아니다. 「살 것이 유한해서」 막힌다.**
> `design-systems`가 C를 2,880으로 하든 288로 하든 공격자는 10배 더 오래 돌릴 뿐이다.
> **진짜 방어선은 「동전으로 살 수 있는 것의 총량이 4,550으로 유한하다」와
> 「그것을 다 사도 다른 사람에게 아무 영향이 없다」이다.** 그건 §4-1-1과 **정확히 같은 논거**다 —
> 피해자와 가해자가 같은 사람이다.
>
> 그리고 그 논거를 **한 가지가 무너뜨린다** → T-D-6.

### 참고 — 레벨 천장은 동전으로 뚫리지 않는다 (그래서 파밍의 상금이 더 작다)

`ECONOMY_SPEC.md` 0-2-7 검산표: **동전이 무한이어도 완주가 최대 2일 앞당겨질 뿐**이고
Lv.30 도달일(천장)은 안 움직인다. **단 이건 「유휴·오프라인이 XP를 주지 않을 때만」 참이다** → T-D-1.

## T-8. 세이브 직접 편집(시나리오 라) — **§4의 「그냥 둔다」를 유지한다. 단 근거가 한 겹 얇아졌다**

T-4~T-6의 원장 4필드는 **평문 세이브**에 들어간다. `lastSettledWallUnix`를 0으로 고치면
매 실행 상한 지급이다. **T절의 방어는 시계 조작을 막지, 메모장을 막지 않는다.**

**그래도 §4·E-8을 유지한다** — 이유는 E-8의 3개 그대로다(위조자는 구매자가 아니다 / 검증이
우리 쓰기 버그를 치터보다 먼저 만난다 / 위조가 갉는 것은 자기 경제다).

> ★ **다만 정직한 정정 1건**: E-8-1은 *"평문 JSON을 고칠 줄 아는 사람에게 대안은 결제가 아니라 dnSpy다"*
> 라고 적었다. **시계 조작에는 그 논거가 약해진다** — 시계 바꾸기는 **기술 장벽이 0이고
> 설정 앱에 버튼으로 있다.** 즉 **세이브 편집자 집단보다 시계 조작자 집단이 훨씬 넓고,
> 구매 고객과 겹친다.** 그래서 T절은 §4보다 **한 단계 강하게** 대응한다(T-3~T-6).
> 그것이 이 절이 존재하는 이유이고, **그럼에도 「탐지·처벌」로는 가지 않는 이유**는 §4-1-4와 같다.

## T-9. 구현 단계 — 2단계로 나눈다

### T-9-1. **1단계(필수, 1.0)** — P/Invoke 0개, 새 OS 권한 0개, 백신 표면 증가 0

T-3(단조 세션 시계) + T-4(래칫) + T-5(단일 예산) + T-6(3중 clamp 순수 함수).
**새 플랫폼 호출이 하나도 없다.** 선 1(네트워크 0)·선 2(권한 0)·선 3(백신)·원칙 3 전부 무접촉.
추정 규모: 순수 함수 1개 + 세이브 필드 4개 + 호출부 1곳.

### T-9-2. **2단계(권고, 1.0 이후 또는 T-3 미확인이 깨지면 즉시)** — 부팅 단조 앵커

**용도는 「지급을 깎는 것」이 아니라 「관측」과 「T-3의 보험」이다.** 1차 출처로 양 플랫폼 확인 완료:

| 플랫폼 | API | 1차 출처 원문 | 절전 포함 | 시계 변경 면역 |
|---|---|---|---|---|
| **macOS/iOS** | `mach_continuous_time()` | SDK 헤더 `mach/mach_time.h:59` — *"like mach_absolute_time, **but advances during sleep**"* (10.12+/iOS 10+) | **포함** | 예 |
| **Windows** | `QueryInterruptTime()` (kernel32) | MS Learn — *"the interrupt-time count is **not subject to adjustments by users or the Windows time service**"*. 형제 API `QueryUnbiasedInterruptTime`이 *"**does not include** time the system spends in sleep or hibernation"*이므로 **바이어스 포함형인 이쪽은 절전을 센다** | **포함** | 예 |

★ **절전 포함이 결정적이다.** 절전을 안 세는 시계(`mach_absolute_time` / `QueryUnbiasedInterruptTime` /
`Environment.TickCount`)를 쓰면 **노트북을 덮어 둔 밤 8시간이 「0초」로 읽혀서, 가장 흔한 정상 사용자에게
오프라인 보상을 거부하게 된다.** 이건 방어가 아니라 사고다 — **잘못된 API를 고르면 오탐이 기본값이 된다.**

> **★ 실측으로 배제된 후보 1건**: `Environment.TickCount64`는 **이 프로젝트에서 쓸 수 없다.**
> `apiCompatibilityLevel: 6`(= .NET Standard 2.1)이고, Unity 동봉 참조 어셈블리
> `.../NetStandard/ref/2.1.0/netstandard.dll`에 심볼이 **없다**.
> **양성 대조**: 같은 스캔이 `get_TickCount` 1건 · `GetTimestamp` 1건을 찾는다(스캐너 정상).
> `get_TickCount64` · `TickCount64` **0건**. → 남은 선택지는 `Environment.TickCount`(int32,
> **~24.9일에 감김** — 상주 데스크톱에서 흔한 가동시간이라 **부적격**) 또는 위 P/Invoke 2종.

**백신 관점(선 3) 판정: 안전.** 두 API는 커널 시각 조회이고, `S-3`의 문제 조합
(창 열거 + 키 상태 + 레지스트리 + 상주)에 **아무것도 더하지 않는다.** 권한 증가 0.

> **T-9-2-a (필수·설계):** 앵커는 **지급을 줄이는 데 쓰지 않는다.** 앵커가 없거나 이상하면
> **1단계 경로로 그대로 떨어진다**(= 상한 지급). **실패 방향이 항상 관대한 쪽**이어야 한다 — E-1/§5-4와 같은 원칙.
> **T-9-2-b (금지):** *"같은 부팅인데 벽시계가 뛰었다"*를 **거부·경고·되돌림의 근거로 쓰지 않는다.**
> 로그(개인정보 없는 숫자 1개)까지다. ★ **근거**: 「같은 부팅 + 시계 전진」과
> 「짧은 가동 뒤 재부팅 + 진짜 장기 부재」는 우리가 가진 숫자만으로 **구별할 수 없다.**
> 구별할 수 없는 것으로 처벌하면 **정상 사용자를 잠근다.**

## T-10. 탐지 시 사용자 경험 — **"탐지"라는 상태를 만들지 않는다**

> ### T-10-a (필수·금지): 이 앱에는 **조작 의심 상태가 존재하지 않는다.**
> 조작 여부를 저장하는 필드, 그것을 화면·로그에 나타내는 문구, 그것에 따라 달라지는 분기를
> **만들지 않는다.** T-4~T-6은 **같은 산술을 모두에게 적용**하고, 조작자는 그 산술에서
> **자연히 적게 받는다.** 이건 관대함이 아니라 **오탐을 만들 수 있는 코드 경로를 아예 안 만드는 것**이다.

| 상황 | 우리 동작 | 사용자에게 보이는 것 |
|---|---|---|
| 시계가 뒤로 갔다 | 지급 0, 아래로 재기준 | **아무 말도 안 한다.** 평소 인사 |
| 경과가 상한을 넘었다(며칠 만·또는 조작) | 상한만큼 지급 | *"그동안 {N}동전 모아 뒀어"* — **넘친 분량을 언급하지 않는다** |
| 예산이 이미 찼다 | 지급 0 | *"오늘 몫은 다 챙겼어"* — 정상 문구. 「캡」·「제한」 단어 회피 |
| 원장 필드가 없다/손상 | 상한 지급 | 평소와 동일 |

### 금지 목록 (하나라도 하면 이 앱의 성격을 배신한다)

**계정 정지**(계정이 없다) · **세이브 무효화·초기화**(원칙 3) · **잔액 회수** ·
**"시간을 조작하셨습니다" 류 문구** · **기능 잠금** · **재실행 강요** · **숨은 페널티 누적**.

★ 근거: §4-1-4에서 실제로 있었던 일 — `.writing` 고아 파일이 디스크에 남아 있었다.

### ★ T-D-6 상세 — 이 절 전체에서 가장 중요한 항목

**세 가지가 동시에 걸린다.**

**(1) 경제 — 회복제 유료 판매 = 「현금 → 동전」이고, 그건 `ECONOMY_SPEC`이 이미 금지를 권고한 것이다.**
`ECONOMY_SPEC.md` 0-2-7 원문: *"이 설계에는 **현금 → 동전 교환이 없다**. 현금은 DLC 팩만 산다.
… 그럼에도 **도입 금지를 권고한다**."* 회복제(동전 수급 캡 해제)는 **포장만 다른 동전 IAP**다.

**(2) 보안 — 그 순간 「피해자 = 본인」이 깨진다.**
§4·E-8·T-7의 **모든** 판정이 *"세이브를 고쳐도 시계를 돌려도 잃는 것은 자기 경험뿐"*에 기대고 있다.
회복제가 현금 SKU가 되면 **시계 조작은 그 SKU를 무료로 얻는 방법**이 되고, 손해는 개발자에게 간다.
**그리고 우리는 그걸 막을 수 없다**(T-7 — 서버가 없다, 그리고 서버는 선 1이다).
**막을 수 없는 것을 팔지 않는 것이 유일한 방어다.**

**(3) 구조 — 소모품은 C층 계약(§3-1 · E-4)과 원리적으로 충돌한다.**

| | 영구 해금(durable add-on) | 소모품(consumable) |
|---|---|---|
| 잔량 저장 | **불필요** — 매 실행 스토어에 묻는다 | **필요** — 어딘가에 남은 개수를 써야 한다 |
| 우리 세이브 | 안 넣는다(§3-1 C층 = 표적 제거) | **평문 세이브에 잔량이 앉는다 → 표적 부활** |
| 오프라인 | E-1~E-3으로 무해화됨(검증 완료) | 스토어 재고 조회 필요. **Steam Inventory Service의 오프라인 동작 미확인** |
| MS 스토어 | §5-2에서 **durable add-on이 정확히 우리 모양**이라고 확인함 | 재검토 필요 |

> **권고(판정은 리더·`product-strategy`)**: 회복제를 개당 파는 대신
> **「매일 회복제 +1개」 같은 영구 해금**으로 판다. 그러면 **팔리는 것은 소모품이 아니라 요율**이고,
> §3-1 C층 · E-1~E-5 · §5-2가 **한 줄도 안 바뀌고 그대로 적용된다.**
> ★ **다만 이렇게 해도 T-D-6(2)는 완전히 사라지지 않는다** — 유료로 산 요율 상승분을
> 시계 조작으로 흉내 낼 수 있기 때문이다. **다만 그 흉내의 상한이 T-4~T-6으로 유한해진다**는 점이
> 소모품과의 결정적 차이다(소모품은 잔량이 평문이라 **무한하다**).

## T-14-2. ★ 새 최악 시나리오 **(카)** — 세션 내 날짜 롤오버 반복

오프라인 획득이 사라져도 **"하루"라는 개념은 안 사라진다.** 오히려 이제 **하루가 유일한 경계**다:
① 일일 상한 1,500 리셋 ② **무료 회복제 1개 재지급**.

```
09:00  앱 실행. 오늘 상한 1,500 소진, 무료 회복제 1개 사용(→ 2,000)
09:01  ★ 앱을 켜 둔 채 OS 설정에서 날짜를 +1일  → dayIndex 전진 → 상한 리셋 + 무료 회복제 1개
09:02  또 +1일 …  (재실행 불필요 · 재부팅 불필요 · 관리자 권한 불필요)
```

- **1사이클 ≈ 20초.** T-7의 재부팅 공격(65초)보다 **3.3배 싸다.**
- **T-4-c(1회 정산 최대 1일 전진)는 반복을 막지 못한다** — 매 사이클이 각각 "1일 전진"이다.
- ★ **`design-systems`가 지금 만드는 수치 설계에 이 시나리오가 반드시 들어가야 한다.**

### T-14-3. 방어 — **refill 사이에 「단조 시계로 잰 최소 간격」을 요구한다**

> **T-14-3-a (필수):** `maxDayIndexSeen` 전진(= 일일 예산 refill + 무료 회복제 재지급)은
> **직전 refill 이후 단조 시계로 `MinRefillGapSeconds`가 지났을 때만** 허용한다.
> 권고값 **20시간(72,000초)**.
>
> ```
> // 세이브가 아니라 프로세스 메모리에 둔다(위조 대상 만들지 않기 — §3-1의 표적 제거와 같은 논리)
> static double _lastRefillMonotonic = double.NegativeInfinity;
>
> bool MayRefill(int dayIndexNow, int maxDaySeen, double nowMonotonic)
>     => dayIndexNow > maxDaySeen
>        && (nowMonotonic - _lastRefillMonotonic) >= MinRefillGapSeconds;
> ```

| 사용자 | 이 규칙에 걸리는가 | 왜 |
|---|---|---|
| 종일 상주(설계 목표 사용형) | **안 걸린다** | 자정 refill 간 단조 간격 = 24h ≥ 20h |
| 하루 몇 시간만 켜는 사용자 | **안 걸린다** | 앱을 껐다 켜면 `_lastRefillMonotonic`이 `-∞`로 초기화 → 첫 refill은 **항상 통과** |
| **(카) 공격자** | ★ **완전히 걸린다** | 같은 프로세스 안에서 20초 간격 재시도 → 20h 미달 → **차단** |

★ **오탐 0인 이유가 구조적이다**: 이 규칙은 **"한 프로세스 수명 안에서 두 번째 이후의 refill"에만** 적용된다.
프로세스를 새로 켜면 무조건 1회는 통과한다. **정상 사용자를 잠글 수 있는 경로가 문법적으로 없다.**

### T-14-3-b. 우회와 그 비용 — 정직하게

| 우회 | 공격자 비용 | 우리 대응 |
|---|---|---|
| 매 사이클 **앱 재시작** | ~30초 | **부팅 단조 앵커(T-9-2)를 채택하면 막힌다** — 앵커는 프로세스를 건너 살아남는다 |
| 매 사이클 **재부팅** | ~65초 | ★ **막을 수 없다.** T-7 그대로 |

> **T-14-3-c (권고, 필수 아님):** 앱 재시작 우회까지 막으려면 T-9-2의 부팅 앵커가 필요하다.
> **비용은 P/Invoke 2개**(`mach_continuous_time` / `QueryInterruptTime`, 둘 다 절전 포함형·권한 0·백신 무관).
> **다만 T-14-7의 피해 상한 검산을 보면 이 투자는 정당화되지 않는다** — 채택 판정은 리더에게 넘긴다.
> **1.0에는 T-14-3-a(무료·순수 로직)만 넣는 것을 권고한다.**

## T-14-5. 재고 위조 방어 — **설계의 핵심은 「재고를 저장하지 않는 것」이다**

### T-14-5-a. ★★ 사용자 결정 *"하루 넘어가면 없어짐"*이 **그 자체로 최고의 재고 방어다**

이 결정이 없었다면 세이브에 `potionStock: N`이 생기고 **`9999`로 고치면 무한**이었다.
이월이 없으므로 **누적 재고라는 개념이 존재하지 않고**, 저장할 것은 **오늘의 소비 상태뿐**이다.

> **T-14-5-a (필수):** **유료로 산 회복제도 당일 소멸이어야 한다.**
> 유료분만 이월되면 `paidPotionStock` 필드가 부활하고 **T-14절 전체가 무의미해진다.**
> ★ 이건 수치가 아니라 **구조 제약**이다 — `design-systems`·`product-strategy` 양쪽에 걸린다.

### T-14-5-b. 세이브 필드 — **4개. 그리고 전부 「지급 시점 재계산 + clamp」로만 쓴다**

```
int  dayIndex;                 // 래칫(T-4-b·T-4-c)
int  todayGrantedCoins;        // 오늘 지급된 동전
byte potionsUsedToday;         // 0~2
bool freePotionClaimedToday;   // 무료분 수령 여부
// ★ 재고(개수) 필드는 없다. 유료 회복제 재고는 스토어가 보관한다(아래 T-14-5-d).
```

> **T-14-5-b (필수·구현 규범):** **저장된 값을 그대로 믿지 않는다. 읽는 즉시 clamp하고,
> 상한은 저장하지 않고 매번 재계산한다.**
>
> ```
> // 로드 직후 무조건. "복구"가 아니라 "정규화"다 — 실패도 경고도 없다.
> potionsUsedToday  = Clamp(potionsUsedToday, 0, MaxPotionsPerDay);      // 2
> todayGrantedCoins = Clamp(todayGrantedCoins, 0, HardCeilingCoins);     // 2,500
>
> // 상한은 필드가 아니라 함수다. 파일에 "오늘 상한" 같은 필드를 만들지 않는다.
> int DailyCap() => BaseDailyCap + PotionBonus * potionsUsedToday;        // 1500 + 500*n ≤ 2500
> int Grant(int want) { int room = Max(0, DailyCap() - todayGrantedCoins); ... }
> ```
>
> **효과(검산)**: `potionsUsedToday = 9999`를 써 넣어도 `DailyCap()`은 **2,500에서 멈춘다.**
> 위조로 넘길 수 있는 최대는 **하루 1,000동전**(회복제 2개분)이고, 그중 500은 무료분이라
> **순이득은 하루 500동전 = 유료 회복제 정확히 1개**다.
>
> ★ 그리고 **이 clamp는 방어가 아니라 위생이다** — 손상된 세이브·구버전 파일·`.writing` 잔해에도
> 같은 코드가 답을 낸다. §4-1-4가 경고한 「우리 버그를 치터보다 먼저 만나는」 코드가 **아니다**
> (거부하지 않고 값만 다듬기 때문).

### T-14-5-c. ★ 그런데 정직하게 — **회복제 필드는 이 파일에서 가장 약한 공격 벡터다**

> ⛔ **대상 소멸 as-of 2026-09-28**(사용자 결정: DLC 폐지 — T절 머리 배너 참조).
> **결론은 바뀌지 않고 근거가 두꺼워졌다**: 「회복제 필드에 추가 방어를 붙이는 것은 순손실」이
> 그때는 *"자물쇠 옆의 열린 창문"* 때문이었고, 지금은 거기에 「**금고 안에 돈이 없다**」가 더해졌다 —
> 유료물이 0이므로 이 표의 어느 벡터도 **개발자에게 손해를 입히지 못한다**(잃는 사람은 자기 자신뿐).
> ⇒ **T-14-5-b의 clamp 한 줄만 유지**한다(위생). 서명·암호화·해시는 그때도 지금도 기각이다.

같은 평문 파일 안에 **더 넓은 옆문이 세 개** 있고, 전부 회복제 위조보다 **쉽고 강력하다.**

| 벡터 | 편집 횟수 | 얻는 것 | 우리 clamp로 막히나 |
|---|---:|---|---|
| `potionsUsedToday`를 고친다 | 1 | **하루 +500동전**(순이득) | **막힌다**(상한 2,500) |
| `todayGrantedCoins = 0` | 1 | 하루 상한 **전액 재수령**(2,500) | ❌ 못 막는다 |
| **`coinBalance = 999999`** | **1** | ★ **경제 전체(4,550) 즉시** | ❌ 못 막는다 |

> **판정: 회복제 필드에 「추가 방어」를 붙이는 것은 순손실이다.**
> 잔액 직접 편집이 100% 우월한 상황에서 재고 필드만 서명·암호화하는 것은
> **자물쇠 옆의 열린 창문**이다. §4·E-8의 판정을 **회복제 필드에도 그대로 적용한다.**
> 우리가 하는 것은 **T-14-5-b의 clamp 한 줄**뿐이고, 그건 방어비용이 사실상 0이다.

★ **리더 질문에 대한 답 —** *"재고 위조는 시계와 무관하게 세이브 편집만으로 되므로 오히려 더 쉬운 공격일 수 있다"*:
**기술적으로는 맞고, 위협 크기로는 틀리다.**

| 축 | 시계 조작 (카) | 세이브 편집(재고 위조) |
|---|---|---|
| 기술 장벽 | **0** — OS 설정의 버튼 | `%APPDATA%`/`Application Support`를 찾아 JSON 편집 |
| 인구 | **전 사용자** | **좁다.** 구매 고객과의 겹침이 작다(E-8-1) |
| 반복 비용 | 20초 | 편집 1회 후 무한 |
| 최대 이득 | 하루 경계 무한 반복 | **잔액 직접 편집이 이미 상한**(회복제 위조는 그 부분집합) |
| 우리 대응 | **T-14-3-a로 세션 내 완전 차단** | **T-14-5-b clamp까지. 그 이상은 안 한다** |

→ **회복제 재고 위조는 새 취약점이 아니라 「이미 열려 있는 문」의 좁은 부분집합이다.**
**T-8의 정정(*시계는 장벽 0이라 §4보다 강하게 대응한다*)은 시계에만 적용되고 세이브 편집에는 적용되지 않는다.**

### T-14-5-d. 유료 회복제의 소유 판정 — E-13을 재고형에 맞게 재적용

사용자가 재고형을 골랐으므로 E-13-a(요율 판매)는 폐기된다. **그러나 E-13-1의 표는 유효하고,
거기서 나오는 결론이 하나 있다:**

> **T-14-5-d (권고):** 유료 회복제의 **미소비 재고를 우리 세이브에 쓰지 않는다.**
> 스토어 소모품(Steam Inventory Service / MS consumable add-on)이 재고를 보관하고,
> 우리는 **소비 시점에 스토어에 소비를 알린다.** → **우리 파일에 위조 대상이 존재하지 않는다**
> (§3-1 C층의 「표적 제거」를 소모품에 그대로 적용). **★ 오프라인 동작은 여전히 미확인**(E-13-3).
>
> **T-14-5-e (필수·순서):** 소비 순서는 **① 우리 상한 +500 → ② 스토어 소비 통지**다. 반대로 하지 않는다.
> 근거는 §4-1-4의 **오탐 비대칭**이다 —
> - 순서 ①②: 중간에 죽으면 **개발자가 500동전 손해**. 그리고 `potionsUsedToday ≤ 2` clamp 때문에 **하루 2,500에서 멈춘다(유한).**
> - 순서 ②①: 중간에 죽으면 **유저가 돈 낸 회복제를 잃는다.** ← 이 앱에서 낼 수 있는 최악의 오답.
>
> **T-14-5-f (필수):** 오프라인/스토어 미실행이면 **유료 구매만 막히고 무료 1개는 정상 동작한다.**
> 문구는 E-2-a를 따른다 — *"안 샀습니다"*가 아니라 *"지금 확인할 수 없습니다"*.

## T-14-6. 「하루 2개」 제약의 방어 가치 — **정상 경로엔 절대 천장, 위조 경로엔 clamp 자리**

리더 질문 3에 대한 답. **두 가지를 나눠야 한다.**

1. **정상 경로**: `1,500 + 500×2 = 2,500`이 **절대 천장**이다. 무제한 회복제였다면 상한이라는 개념이
   없어지고 (카) 공격의 1사이클 상금이 무한이 된다. **하루 2개 고정은 큰 방어 이득이다.**
2. **위조 경로**: 직접적으로는 도움이 **안 된다**(필드를 고치면 그만). **그러나 「코드에 하드 상한을
   박을 자리」를 준다** — 그게 T-14-5-b의 clamp이고, 그 clamp가 **위조 순이득을 하루 500동전으로
   묶는다.** ★ **상한이 명시되지 않았다면 clamp를 쓸 근거 자체가 없었다.**

> **T-14-6-a (필수):** `MaxPotionsPerDay = 2` · `HardCeilingCoins = 2500`을 **상수 1곳**에 두고,
> 감사·테스트가 **그 상수를 참조해서** 검증한다(숫자를 베끼지 않는다 — CLAUDE.md 확정 규칙,
> 2026-09-01에 `MaxCharacterScale`·스키마 버전으로 4건 깨진 사고).

## T-14-7. ★★ 피해 상한 검산 — **유한하다. 그리고 그 이유는 방어가 아니라 소모처다**

전제 수치: 소모처 총액 **4,550동전**(7슬롯 42종 = 650×7, `ECONOMY_SPEC` 0-2-1) ·
일일 상한 1,500 / 회복제 최대 2,500 · **팩은 동전 경제에 접촉하지 않는다**(`ECONOMY_SPEC` 확정 DS-3:
*"팩 구매 시 6종 전부 0동전 즉시 해금"*) → **소모처는 팩이 몇 개 붙어도 4,550으로 유한하다.**

| # | 검산 | 값 |
|---:|---|---|
| 1 | 완주 소요(회복제 없이) | 4,550 / 1,500 = **3.03일** |
| 2 | 완주 소요(회복제 2개 매일) | 4,550 / 2,500 = **1.82일** |
| 3 | 회복제 1개의 상대 가치 | 500 / 4,550 = **카탈로그의 11.0%** |
| 4 | **유료 회복제의 총 시장(사용자 1인당)** | 완주까지 최대 3일 × 유료 1개/일 = **최대 3개** |
| 5 | 필드 위조의 순이득(clamp 적용 시) | **하루 500동전 = 유료 회복제 1개** |
| 6 | **(카) 시계 조작의 포화점** | 4,550 / 500(=하루 무료 회복제 1개분) = **9.1회** |

> ### → **시계를 9번 돌리면 살 것이 없어진다.** 그 이상 돌릴 이유가 존재하지 않는다.
> **(카)로 잃는 최대 매출 = 사용자 1인당 유료 회복제 약 3개 값**(검산 4·6이 독립적으로 같은 자리에 떨어진다).
> 그건 **정상 사용자 1명이 평생 낼 수 있는 회복제 대금의 전부**이기도 하다.

**판정: 이 구조에서 「탐지·처벌·서버 검증」은 정당화되지 않는다.**
`T-14-3-a`(무료·순수 로직·오탐 0) + `T-14-5-b`(clamp 한 줄)까지가 비용 대비 정당한 전부다.
T-9-2 부팅 앵커는 **P/Invoke 2개를 들여 3개어치 매출을 지키는 일**이라 **1.0에서는 권고하지 않는다.**

### ★ 그러나 이 결론을 무너뜨리는 조건이 **정확히 하나** 있다 — 리더가 지켜야 할 선

> **T-14-7-a (★ 되돌릴 수 없는 결정 후보):** **동전 소모처를 무한하게 만들지 마라.**
> 소모성 반복 구매(예: 동전으로 사는 소모품·뽑기·재도전권)를 넣는 순간 **4,550이라는 천장이 사라지고,
> 위 검산 6개가 전부 무효가 된다.** 그때는 (카)의 상금이 무한이 되고,
> **우리는 그것을 로컬로 막을 수 없다**(T-7).
>
> **오늘 이 천장은 우연이 아니라 확정 판정이다** — `ECONOMY_SPEC` DS-3이 팩을 동전 경제에서
> 명시적으로 떼어 놨다. **그 판정이 곧 이 절의 보안 근거다.** 되돌리려면 T-14절 전체를 다시 써야 한다.

## T-14-8. `design-systems`에 거는 추가 제약 (T-D-8 ~ T-D-12) — T-D-1~7은 그대로 유효

| # | 제약 | 왜 | 어기면 |
|---:|---|---|---|
| **T-D-8** | **유료 회복제도 당일 소멸.** 미사용분 이월·비축 금지 | T-14-5-a. 이월이 있으면 `paidPotionStock` 필드가 생기고 **평문 무한 재고**가 된다 | T-14절 전체가 무의미 |
| **T-D-9** | **일일 상한은 필드가 아니라 함수**: `1500 + 500×clamp(used,0,2)`. "오늘의 상한"을 세이브에 저장하지 않는다 | T-14-5-b. 저장된 상한은 위조 대상, 재계산된 상한은 아니다 | 위조 순이득이 무한 |
| **T-D-10** | **refill(일일 상한 리셋 + 무료 회복제 재지급)은 「하나의 사건」**이다. 두 개를 다른 조건으로 나누지 마라 | 나누면 (카) 공격이 두 경계를 각각 넘어 **상금이 2배**가 되고, T-14-3-a를 두 곳에 걸어야 한다 | 방어가 한쪽에만 걸린다 |
| **T-D-11** | **`MinRefillGapSeconds`(권고 20h)를 수치 설계에 포함**하라. 이건 밸런스 수치가 아니라 **방어 파라미터**지만 정상 사용자 곡선에 닿는다 | T-14-3-a. 20h는 "자정 기준 하루 1회"와 충돌하지 않는다(간격 24h) | 값이 너무 크면 정상 사용자를 잠근다 |
| **T-D-12** | ★ **소모처 총액 4,550의 유한성을 깨지 마라** — 동전으로 사는 반복 구매품을 만들지 않는다 | **T-14-7-a. 이 절 결론 전체의 전제다** | 피해 상한이 유한 → 무한 |

# T-15절 — 「8시간 창」 래칫 사양 (2026-09-03, `design-systems` R10-c U-37 인계)

**T-14절은 한 줄도 고치지 않았다. 이 절은 그 위에 3번째 축을 얹는다.**

> `design-systems` R10-c 확정 반영: 무료 1개는 **"하루 2개" 한도에 포함**(유료 채널 일일 가치 상한
> 500동전) · 세이브 필드 `tonicOwned` · `tonicUsedToday` · `tonicFreeGrantedToday`(재고 없음, clamp).
> `design-systems` 표현: *"8시간 창 = 시계 조작 방어선."*

---

## T-15-0. 결론 3줄 — **채택한다. 단 두 군데를 정정한다**

1. **창을 채택한다.** 비용이 사실상 0(필드 1개 + clamp)이고 **오탐이 구조적으로 0**이다
   (정상 최대 사용이 창의 **43.4%**밖에 안 쓴다 — T-15-5 검산).
2. ★ **리더 지시 1건을 근거를 대고 반박한다 — 창 소비량은 「세이브에 남겨야」 한다.**
   프로세스 메모리에만 두면 **앱 재시작 한 번으로 창이 사라지고, 창이 없는 것과 수학적으로 같아진다**(T-15-2).
3. ★ **창의 방어 가치를 과대평가하지 마라.** 6.912배 → 2.304배는 **맞는 계산**이지만,
   **두 값 모두 「소모처 4,550을 하루 안에 소진」한다**(0.263일 vs 0.790일). 창이 사는 것은
   **약 12.6시간**이다. 진짜 방어선은 여전히 **일일 상한 2,500**과 **소모처의 유한성**이다(T-15-5).

---

## T-15-1. 창의 구현 사양

### T-15-1-a. 창이 세는 것 — **「지급된 초」이지 「앱이 켜져 있던 초」가 아니다**

> **T-15-1-a (필수):** 창은 **실제로 동전이 지급된 초**만 갉는다.
> 비유휴 상태 · 상한 도달로 지급이 0인 초 · 일시정지 · 전체화면 자동숨김 중은 **창을 갉지 않는다.**
>
> **왜**: "앱이 켜져 있던 초"로 세면 **상한에 걸려 한 푼도 못 버는 동안 창만 닳는다.**
> 그러면 정상 사용자가 **아무 이득 없이 창을 잃고**, 그건 방어가 아니라 버그다.
> (같은 계열의 실제 사고: `Time.deltaTime` 잘림이 "적게 쌓이는" 방향으로 공정성 문제를 만든다 — T-3-c.)

### T-15-1-b. 시간 원천 — **T-3을 그대로 상속한다. 새 관례 없음**

```
// 수급 틱. 벽시계를 읽지 않는다(T-3-a).
double now   = Time.realtimeSinceStartupAsDouble;      // T-3-b 단조 시계
double dt    = now - _lastTickMonotonic; _lastTickMonotonic = now;

if (!IsIdleEarning) return;                             // 창을 갉지 않는다(T-15-1-a)

int    room     = Max(0, DailyCap() - todayGrantedCoins);            // T-14-5-b, 상한은 함수
double winRoom  = Max(0.0, WindowCapSeconds - windowSecondsUsedToday); // ★ 3번째 축
if (room <= 0 || winRoom <= 0.0) return;                // 지급 0 → 창도 안 갉는다

double paySec   = Min(dt, winRoom);
int    pay      = (int)Min(room, paySec * CoinsPerSecond);

todayGrantedCoins      += pay;
windowSecondsUsedToday += paySec;      // ★ 지급된 초만
```

### T-15-1-c. 세이브 필드 — **1개 추가. clamp 규범은 T-14-5-b를 그대로 상속**

```
float windowSecondsUsedToday;   // 0 ~ WindowCapSeconds(28,800)

// 로드 직후 무조건 정규화(거부·경고 없음 — T-14-5-b와 같은 코드 형태)
windowSecondsUsedToday = Clamp(windowSecondsUsedToday, 0f, WindowCapSeconds);
if (float.IsNaN(windowSecondsUsedToday)) windowSecondsUsedToday = WindowCapSeconds;  // ★ 실패는 보수적으로
```

★ **NaN을 0이 아니라 상한으로 보내는 이유**: 0으로 보내면 **손상된 파일이 창을 리셋하는 무료 우회**가 된다.
다른 clamp들과 방향이 **반대**이므로 코드에 그 이유를 반드시 주석으로 남긴다.
(피해: 손상 파일을 만난 정상 사용자가 그날 유휴 수급을 못 한다 — **상한 2,500은 그대로 살아 있으므로
활쏘기·집중모드로 벌 수 있다.** 잠기지 않는다.)

### T-15-1-d. ★ 창의 리셋은 **refill 사건에 합류한다** — 별도 조건을 만들지 않는다

> **T-15-1-d (필수):** `windowSecondsUsedToday = 0`은 **T-14-3-a의 `MayRefill`이 참일 때만** 일어난다.
> 일일 상한 리셋 · 무료 회복제 재지급 · **창 리셋**이 **하나의 사건**이다(T-D-10을 3항목으로 확장).

**이 한 줄이 창에 별도 방어 장치를 필요 없게 만든다** — T-14-3-a(단조 20시간 간격)를 **그대로 상속**한다.
창 리셋 조건을 따로 만들면 **방어를 두 곳에 걸어야 하고, 한쪽을 빠뜨리면 조용히 새는 문**이 된다.

## T-15-2. ★ 리더 지시 반박 — **"세이브에 안 남김(위조 대상 없음)"은 여기서 성립하지 않는다**

> ⛔ **대상 소멸 as-of 2026-09-28**(사용자 결정: DLC 폐지 — T절 머리 배너 참조).
> **이 절의 산술 반박은 여전히 옳다**(메모리만 두면 재시작 반복으로 창이 무력화된다 — 1,440×12 = 17,280).
> 바뀐 것은 **그 방어가 누구를 위한 것인가**다: 유료물이 0이므로 창 필드 위조의 피해자는
> **자기 자신뿐**이고, 표의 세 벡터 중 창 필드가 여전히 **가장 약하다**.
> ⇒ **T-15-2-a(평문으로 둔다)와 T-15-2-b(`PlayerPrefs` 금지 · 별도 파일 금지)는 그대로 유지**한다.
> 전자는 「방어를 안 한다」는 판정이라 유료 여부와 무관하고, 후자는 **원장이 하나 더 늘어나는 것**을
> 막는 조항이라 **애초에 유료와 무관한 위생**이다(S-7-2의 「고아 원장」).

리더 지시: *"`realtimeSinceStartupAsDouble` 누적, 세이브에 안 남김(위조 대상 없음)."*
**앞부분은 채택하고 뒷부분은 반박한다.** 근거는 산술이다.

| 창의 저장 위치 | 앱 재시작 시 | 하루 실효 상한 | 결과 |
|---|---|---:|---|
| **프로세스 메모리만**(리더 지시) | **0으로 리셋** | 재시작을 반복하면 **1,440분 × 12 = 17,280** | ★ **창이 없는 것과 수학적으로 동일** |
| **세이브 + T-15-1-d** | 유지 | 480분 × 12 = **5,760** | 의도대로 작동 |

**즉 "위조 대상을 안 만든다"를 지키면 「방어 자체가 없어진다」.** 둘 다 가질 수 없다.

### 그리고 세이브에 남겨도 **새 취약점이 아니다** — T-14-5-c의 표에 한 줄이 붙을 뿐이다

| 벡터 | 편집 | 얻는 것 |
|---|---:|---|
| **`windowSecondsUsedToday = 0`** | 1 | **하루 창 1회분**(= 상한 2,500에 걸려 실제로는 더 적다) |
| `todayGrantedCoins = 0` | 1 | 하루 상한 전액 2,500 |
| **`coinBalance = 999999`** | **1** | ★ **경제 전체 4,550 즉시** |

★ **창 필드 위조는 세 벡터 중 가장 약하다.** `todayGrantedCoins`를 고치는 쪽이 항상 우월하고,
`coinBalance`는 압도적이다. **자물쇠 옆에 열린 창문이 이미 두 개 있는데 세 번째 자물쇠를 안 다는 이유가 없다.**
§4 · E-8 · T-14-5-c의 판정을 **창 필드에도 그대로 적용한다: clamp까지만, 그 이상은 안 한다.**

> **T-15-2-a (필수):** 창 소비량은 **세이브에 평문으로 둔다.** 서명·암호화·해시 **전부 기각**(§4-2 표 그대로).
> **T-15-2-b (금지):** `PlayerPrefs`에 두지 않는다 — Windows에서 레지스트리에 쓰고
> **신원 문자열이 바뀌면 함께 이사한다**(S-7-4 실측). 별도 파일도 만들지 않는다(원장이 하나 더 늘고,
> S-7-2가 기록한 「고아 원장」 위험이 재발한다).

## T-15-5. ★ 정직한 평가 — **창을 방어로서 과대평가하지 마라**

`design-systems`의 *"8시간 창 = 시계 조작 방어선"*은 **비율로는 맞고 절대량으로는 약하다.**

> **검산 9가 말하는 것**: 창이 없으면 **조작을 하나도 안 하고 앱을 6.32시간 켜 두는 것만으로
> 소모처 전체(4,550)가 소진된다.** 그리고 **창이 있어도 0.79일 = 약 19시간이면 소진된다.**
> **6.912배와 2.304배는 둘 다 「하루 안에 게임이 끝난다」의 다른 표현이다.**

- 창이 실제로 사는 것은 **약 12.6시간**(검산 10)이다. 그게 이 방어의 정직한 값어치다.
- **진짜 방어선은 세 개 중 ①(일일 상한 2,500 → 1.82일)이고, 그보다 더 근본적인 것은
  T-14-7-a의 「소모처 4,550의 유한성」이다.** 창은 그 둘의 **보조선**이다.
- 그럼에도 **채택한다**: 비용이 필드 1개 + clamp이고, 오탐이 0이며(검산 5·6),
  ②가 못 덮는 (카') 구멍을 정확히 덮는다. **싸고 오탐 없고 구멍 하나를 정확히 메우면 그건 좋은 방어다.**

> ★ **`design-systems`에 돌려보내는 관측 1건(수치 판정은 그쪽 몫)**: 검산 9가 보여주는
> *"조작 없이 6.32시간이면 완주"*는 **보안 결함이 아니라 경제 스케일 문제**다.
> 요율 12동전/분은 기존 원형 B(64동전/일)의 **23.4배**이고, 창·상한 중 **어느 것도 그 스케일을
> 되돌리지 못한다.** 나는 요율을 판정할 수 없다 — 다만 **T-14-7의 검산 6개가 이 요율에 매달려 있으므로
> 요율이 바뀌면 그 6개를 다시 돌려야 한다**는 것만 못 박는다.

## T-15-6. 오탐 방지 — 창이 정상 사용자를 잠글 수 있는 경로가 있는가

| 정상 사용자 | 창에 걸리나 | 근거 |
|---|---|---|
| 회복제 2개 다 쓰는 헤비 유저 | **안 걸린다** | 상한 2,500이 **208.3분**에 먼저 걸린다 = 창의 43.4%(검산 5) |
| 회복제 0개 유저 | **안 걸린다** | 125분 = 창의 26.0%(검산 6) |
| 24시간 상주(설계 목표 사용형) | **안 걸린다** | 지급이 멈추면 창도 안 갉는다(T-15-1-a) |
| 앱을 여러 번 껐다 켜는 사용자 | **안 걸린다** | 창은 누적이고 하루 총량이 같다. 재시작이 창을 **늘리지도 줄이지도** 않는다 |

| 시간대 이동 · 서머타임 | **무관** | 창은 단조 초 누적이라 벽시계를 안 본다 |

> 화면에는 아무것도 뜨지 않는다(정상 사용자는 도달하지 않으므로 문구를 만들 필요 자체가 없다).
> **창 소진을 기록하는 플래그를 세이브에 만들지 않는다** — 그건 T-10-a가 금지한 「조작 의심 상태」다.

## T-15-9. 플랫폼 영향 · 보장하지 않는 것

- **Windows 영향: 함께 검토함.** 창은 `Time.realtimeSinceStartupAsDouble` + float 누적 + clamp뿐 —
  **플랫폼 분기 0**, P/Invoke 0, 새 OS 권한 0, 백신 표면 증가 0(선 3 무접촉).
  `PlatformParityAuditTests` 추가 항목 **0**. T-9-2(부팅 앵커)는 **여전히 격하 상태**이므로
  Windows 전용 파일은 이번에도 **생기지 않는다.**
  ★ 세이브 필드가 1개 늘어나므로 `CharacterSaveStore.CurrentVersion` 상승 라운드에 포함되고,
  그 라운드는 **`vN-1` 하위 호환 테스트 1건을 반드시 동반한다**(CLAUDE.md 명시 규칙).
  구버전 파일에는 필드가 없으므로 **기본값 0 = "오늘 창을 아직 안 썼다"**가 되고, 그건
  **사용자에게 관대한 방향**이다 ✔.
- **macOS 영향: 함께 검토함.** 동상 — 플랫폼 분기 0. 하드닝 런타임 엔타이틀먼트 목록 **무변**(S-1).
  ★ macOS 절전(뚜껑 닫기)에서 `realtimeSinceStartupAsDouble`이 멈추는지는 **미확인**이지만,
  **멈추는 쪽이 우리에게 옳다** — 절전 중에는 지급도 0이어야 하므로 창도 안 갉는 것이 맞다.
  즉 **어느 쪽이든 설계가 성립한다**(T-3의 미확인과 같은 성질: 무해화됐지 확인된 게 아니다).
- **모바일**: 창 자체는 중립. 단 iOS는 백그라운드 정지라 **"유휴"의 정의가 달라져** 창의 소비 속도가
  달라진다 — 모바일 라운드에서 T-D-15 비율을 **다시 계산해야 한다.**
- **프로덕션 `.cs` 수정 0건 · 신규 플랫폼 분기 0건 · 앱 실행/빌드 0회.**

### 보장하지 않는 것 (T-14-10의 8~11에 이어서)

12. **창은 (사) 재부팅 반복을 막지 못한다.** 재부팅은 ②(메모리)를 리셋하고, 그러면 창 리셋이 자유로워진다.
    **다만 창을 리셋해도 실시간 480분을 새로 기다려야 하므로 하루 상한은 17,280을 넘지 못한다** —
    그건 「종일 켜 둔 사람의 값」이지 조작으로 만든 값이 아니다.
13. **검산 1~10은 요율 12동전/분 · 창 480분 · 상한 1,500/2,500 · 소모처 4,550에 전부 의존한다.**
    `design-systems`가 **어느 하나라도** 바꾸면 10개를 다시 돌리고 **T-D-15 비율을 재검산해야 한다.**
14. **테스트를 돌리지 않았다.** T-15-7의 5,760·17,280은 **파이썬 독립 계산**이고 러너 결과가 아니다
    (E-12-6이 기록한 함정: 재구현과 본 구현이 같은 머릿속에서 나온다). **(B)를 반드시 러너로 돌려라.**
15. **`MinRefillGapSeconds = 20h`는 여전히 설계값**(T-14-10의 11). 창은 그 값에 의존하지 않는다 —
    ②가 완전히 없어도 창은 5,760에서 자른다.

## V-2. ★ 이 절이 잡아낸 함정 하나 — **MS Learn의 메서드 표는 vtable 순서가 아니다**

Learn의 `IVirtualDesktopManager` 페이지는 메서드를 **알파벳순**으로 싣는다:
`GetWindowDesktopId` → `IsWindowOnCurrentVirtualDesktop` → `MoveWindowToDesktop`.
**실제 vtable 순서는 다르다**: `IsWindowOnCurrentVirtualDesktop`(슬롯 0) →
`GetWindowDesktopId`(슬롯 1) → `MoveWindowToDesktop`(슬롯 2).

코드와 `VirtualDesktopProbeAuditTests`는 **vtable 순서가 맞다.** 그러나 다음 사람이
*"1차 출처와 대조했다"*며 **Learn 페이지의 표 순서로 재정렬하면 슬롯 0이 `GetWindowDesktopId`가
되고, 슬롯 2가 불리는 순간 「조회」가 아니라 「창 이동」이 실행된다**(원칙 3 위반이 컴파일 에러 없이
발생한다. 이 머신에는 Windows가 없어 실행으로도 못 잡는다).
⇒ **이 저장소의 「죽은 프로브가 성공한 프로브와 똑같이 생겼다」 계열의 새 변종이다.**
`VirtualDesktopProbeAuditTests.vtable_슬롯_순서가_1차_출처와_같다`의 주석에 **"Learn 표는
알파벳순이다"**를 명시해 둘 것을 권고한다(구현은 `coder`/`test-engineer` 배정).

## V-3. 조용한 실패 — **영구 포기는 항상 로그를 남긴다. 확인됐다.**

`MaxConsecutiveFailures = 5`(1.5초 폴링 × 5 = 7.5초)는 실재한다.

**세션당 경고는 정확히 1회**다. **조용한 영구 실패 경로 0건.**

- **1~4회차 실패는 로그가 없다.** 다만 소비 측(`Win32WindowService.GetVirtualDesktopMembership`)이

  보인다. ⇒ **실패가 삼켜지지 않는다.**
- ★ **남은 구멍 1건(경미, 신뢰성)**: 「4회 실패 → 1회 성공」이 반복되면 `_consecutiveFailures`가
  매번 0으로 리셋되어 **상한에 영원히 닿지 않는다.** 그러면 (가) 1.5초마다 `CoCreateInstance`가
  영구히 돌고, (나) 소속이 `Unknown ↔ CurrentDesktop`으로 왕복해 **전이 로그가 최악 하루
  ~57,600줄**까지 불어난다. 24시간 상주 앱에서 로그 폭주는 실측된 형태의 비용이다.
  **처방(저비용)**: 세션 누적 실패 카운터를 하나 더 두고 그쪽에도 상한을 건다. **보안 등급 아님 —

**X-2-A. 관리자 권한(UAC) 판정** (2026-09-15 측정 · 커밋판 `a8c3723`에 삽입만 했다. 위 표 「OS 권한 요청 0」 행의 권한 가운데 **관리자 권한 하나**만 판정한다. 방화벽 프롬프트 미확인과 짧은 형 「OS 권한 요청 0」 보류는 그대로다)

- **측정 — 실행 파일 매니페스트**: 아래 다섯 파일 모두 `RT_MANIFEST` 1개, `requestedExecutionLevel level="asInvoker"`, `uiAccess="false"`다. 두 방법(PE 리소스 디렉터리 파싱 / 파일 전체 원시 바이트 검색)이 일치했고, 원시 바이트의 `requireAdministrator`·`highestAvailable`은 0이다.
  - `Builds/Windows/StickMate.exe` · `Builds/Windows/UnityCrashHandler64.exe`
  - `Builds/StickMate-Windows-20260914-eb4670d.zip` 안의 같은 두 파일
  - Unity 6000.0.82f1 설치 폴더의 win64 비개발 Mono 스텁 `PlaybackEngines/WindowsStandaloneSupport/Variations/win64_player_nondevelopment_mono/WindowsPlayer.exe` — 매니페스트가 우리 `StickMate.exe`와 같은 1314바이트 · `asInvoker`라서, 우리 빌드 설정이 바꾼 값이 아니라 Unity 기본값으로 판단한다.
  - 음성 대조: 매니페스트가 없는 `Builds/Windows/StickMate_Data/Managed/StickMate.Runtime.dll` · `Builds/Windows/UnityPlayer.dll`에서 같은 파서가 `RT_MANIFEST` 0 · 원시 바이트 `asInvoker` 0이었다.
  - 엔진 dll: `Builds/Windows/UnityPlayer.dll`과 0914 zip의 `UnityPlayer.dll` sha256 앞 16자는 Unity 비개발 변형과 같은 `6052d8f8650c3acc`이고, 개발 변형(`90e1bbd568bb4b92`)과 다르다.
- **측정 — 소스**(고정 문자열, 대소문자 구분): `requireAdministrator`·`highestAvailable`·`runas`·`Process.Start`·`ShellExecute`가 런타임 스크립트 `Assets/_Project/Scripts`(`Tests/` 제외) · `ProjectSettings` · `Tools`에서 0줄이다. `Assets/Editor`에는 1줄이 있다 — 에디터 전용 macOS 빌드 후처리기의 `UseShellExecute = false`로, 플레이어에 들어가지 않는다(`PERSISTENT_WRITE_INVENTORY.md` 1-5). 같은 명령 형태의 양성: 합성 파일에서 2줄씩.
- **미측정**: 스팀 빌드(정의 ON — X-1대로 존재한 적이 없다) · 다른 스텁 변형(개발 · arm64 · x86) · 스팀 depot 설치 스크립트(저장소에 없다).
- **1차 문서** — Microsoft Learn 「Windows Firewall Rules」 (https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/rules · 페이지 `ms.date` 2025-06-06). 원문 HTML을 curl로 받아 옮겼다(요약 도구를 거치지 않았다):
  - 「If the user has admin permissions, they're prompted. If they respond No or cancel the prompt, block rules are created.」 (원문은 `No`에 기울임 태그가 있다)
  - 「If the user isn't a local admin and they are prompted, block rules are created. It doesn't matter what option is selected.」
  - 「However, the behaviors involved in the automatic creation of application rules at runtime require user interaction and administrative privilege.」
  - 계수(받은 HTML, 고정 문자열): 태그를 걷은 본문에서 세 문장 각 1회. 원시 HTML에서는 둘째·셋째가 각 1회이고, 첫째는 `<em>No</em>` 형태로 1회(태그 없는 형태 0회). 음성 대조: 첫째 문장의 한 낱말을 바꾼 형태 0회.
  - 알림이 뜨는 조건(같은 페이지): 「a dialog box prompts the user to either allow or block an application's packets the first time the app is launched or tries to communicate in the network」.
- **결론**:
  - 좁은 문장 「실행할 때 관리자 권한(UAC)을 요청하지 않습니다」: **측정한 바이너리 기준 게시 가능.** 조건은 출시 게이트에서 1.0 출시 바이너리의 매니페스트를 위 방법으로 다시 확인하는 것이다.
  - 열거형 「관리자 권한을 요구하지 않습니다」: **조건부.** 조건은 (a) 출시 바이너리가 `asInvoker`일 것, (b) 정의 ON 출시 바이너리로 깨끗한 Windows에서 스팀 켬·끔 각각 방화벽 알림이 0일 것이다. 알림이 뜨면 위 1차 문서대로 「허용」에 관리자 권한이 필요하므로, 사용자 눈에 이 문장이 거짓이 된다 — 그때는 좁은 문장으로 내린다.
  - 범위 밖: 스팀 클라이언트 자체의 설치 · 업데이트 권한.
