## ★★ 2차 갱신 공지 — 1차안(캡40)은 폐기, 캡50으로 재설계

1차 제출본은 design-systems의 **권고**로 레벨 캡 40(스탯 캡과 수치 정합)을 제안했다. **사용자가
직접 캡 50을 지정**했고, 지시문이 "네 권고를 대체하는 결정이니 그대로 반영해라"라고 명시했으므로
**40 관련 권고는 철회**하고 이하 전부 캡 50 기준으로 다시 계산했다. 40이 갖고 있던 근거
("스탯 캡과 숫자가 같아 커뮤니케이션이 쉽다")는 캡을 50으로 바꾸면 더 이상 성립하지 않는다 —
**레벨 캡(50)과 스탯 캡(`EquipmentStatRules.Cap`=40)은 이제 서로 다른 숫자인 두 개의 독립된
캡**이라는 점을 이하 전체 설계의 전제로 명시해 둔다. 이 둘을 같은 숫자로 맞춰야 한다는 요구는
없었으므로, 대신 §3에서 "레벨 캡이 커진 만큼 레벨이 스탯 캡 예산을 더 많이 가져가도 되는가"를
직접 계산으로 검증한다(결론: **아니오** — 두 캡은 독립적이고, 레벨 캡을 올렸다고 스탯 캡 밑
여유분이 같이 늘어나지 않는다. §3-4).

**이전 문서에 있던 "리더 승인 전 열린 질문 5개"와 "game-architect 회부 항목"은 사용자 지시대로
그대로 유지한다**(§8·§9, 번호와 문항 보존, 캡 변경으로 숫자가 바뀐 곳만 갱신).

## 1. 레벨 캡 = 50 (사용자 확정)

사용자가 직접 지정했으므로 이 숫자 자체를 재검토하지 않는다. 다만 설계자로서 확인해야 할
**하한 제약은 여전히 유효**하고 통과하는지만 짚는다: 콘텐츠 최고 요구 레벨 30(REF §1) < 50 —
통과. 이 캡이 시간상 무엇을 의미하는지는 §3에서 XP 경제 전체와 함께 계산한다.

`CharacterProgressionModel.RestoreFromSave`의 `Mathf.Clamp(level, 1, 9999)`(REF §1)는 여전히
"손상 방어용 기술 상한"일 뿐이고 이 설계 캡(50)과 다른 개념이다 — 혼동하지 않는다.

## 2. XP 곡선(1→50) — 그대로 쓴다, 재설계 불필요

### 2-1. 판단: 곡선을 바꾸지 않는다

`CharacterProgressionModel.XpToNextLevel`(REF §2-1, `100 × level^1.05`)을 1→50 전 구간에
그대로 연장해 재계산했다(계산 스크립트는 부록 A):

| 구간 | 필요 XP(그 구간 총합) | 직전 10레벨 대비 배율 |
|---|---:|---:|
| Lv1→10 | 4,915 | — |
| Lv10→20 | 16,592 | ×3.38 |
| Lv20→30 | 28,760 | ×1.73 |
| Lv30→40 | 41,190 | ×1.43 |
| Lv40→50 | 53,805 | ×1.31 |

**핵심 관찰: 구간별 비용은 계속 늘지만, 그 증가율 자체는 3.38배→1.73배→1.43배→1.31배로
계속 줄어든다.** 즉 곡선이 "뒤로 갈수록 급격히 가팔라지는" 형태가 아니라 **증가율이 스스로
누그러지는 형태**다 — 지수 1.05가 1(선형)에 아주 가깝기 때문에 나오는 자연스러운 결과다.
단일 레벨 기준으로도 확인된다: `Lv1→2 = 100XP`, `Lv49→50 = 5,952.6XP` — 마지막 레벨이 첫
레벨의 **59.5배**다. 며칠 안에 진행이 완전히 멎는 "벽"(코드 주석이 경고한 지수 2.0급 문제,
`StickConfig.cs` 툴팁)과는 질적으로 다르다.

### 2-2. 시간으로 재확인

| 레벨 | 누적 XP | 누적 시간 | 8h/일 | 24h 상주 |
|---:|---:|---:|---:|---:|
| 30(기존 콘텐츠 최고) | 50,266 | 558.5h | 69.8일 | 23.3일 |
| 40 | 91,455 | 1,016.2h | 127.0일 | 42.3일 |
| **50(신규 캡)** | **145,261** | **1,614.0h** | **201.8일** | **67.3일** |

8h/일 기준 201.8일(약 6.7개월), 24시간 상주 기준 67.3일(약 2.2개월) — **상주형 데스크톱
동료 앱**이라는 이 게임의 성격(몇 달 단위 리텐션을 전제)에 비춰 과도하지 않다. **결론: 곡선
상수(`progressionXpCurveBase=100`, `progressionXpCurveExponent=1.05`)는 무변경으로 간다.**
새 지수를 도입하거나 구간별로 곡선을 꺾을 근거를 찾지 못했다 — 오히려 곡선을 손대면 REF §2-3이
이미 교차검증해 둔 Lv1~30 구간(초반 리듬, "1~3시간 안에 레벨업")까지 재검증 대상이 되어 손실이
더 크다.

### 3-1. 패시브만(방치) — 하루 XP

| 앱 켜진 시간 | 하루 XP |
|---:|---:|
| 8시간 | 720 |
| 12시간 | 1,080 |
| 16시간 | 1,440 |
| **24시간 상주** | **2,160** |

### 3-2. 현실적인 하루 최대 — 패시브 + 상식적인 능동 활쏘기

활쏘기는 **자율 발동이 기본 OFF**다(`archeryChance=0f`, `StickConfig.cs:2819` — "사용자가 부르지
않으면 절대 발동하지 않는다"). 발동 경로는 전역 단축키(Ctrl+Opt+Cmd+A)와 우클릭 메뉴 둘뿐이라
**전부 수동**이다. 명중 확률은 `archeryHitChance(0.667) × archeryBullseyeChance(0.5) =
0.3335`(정중앙 확률, `StickConfig.cs:2972,2989`). 한 발의 전체 주기(과녁 등장~결과~아웃트로)를
관련 필드(`archeryTargetIntroSeconds 0.55` + `archeryDrawSeconds 0.42` + `archeryAimHoldSeconds
0.30` + `archeryArrowFlightSeconds 0.62` + `archeryRecoverSeconds 0.34` + `archeryOutroSeconds
0.55`)로 어림하면 **약 2.78초/발**이다(연출 단계가 일부 겹칠 수 있어 어림값이라고 표시한다 —
정확한 값은 실측이 필요하고 이 문서의 결론을 바꾸지 않는다).

| 연속 활쏘기 시간 | 발 수(어림) | 정중앙 수 | XP |
|---:|---:|---:|---:|
| 1분 | 21.6 | 7.2 | 108 |
| 5분 | 107.9 | 36.0 | 540 |
| 10분 | 215.8 | 72.0 | 1,080 |

**"현실적인 하루 최대"를 "앱이 하루 16시간 켜져 있고, 그중 활쏘기를 10분 정도 몰아서 하는
적극적이지만 상식적인 사용자"로 정의**하면:

```
패시브(16h) 1,440  +  능동(10분 활쏘기) 1,080  =  2,520 XP/일
```

이 가정(16h·10분)은 **design-systems가 임의로 고른 기준선**이다 — 리더가 다른 활동 시간을
원하면 위 표의 분당 108XP를 그대로 곱해 재계산하면 된다. 참고로 이 값(2,520)은 순수 방치
24시간(2,160)보다 **17% 높을 뿐**이다 — `CharacterProgressionDirector.cs:27`이 이미 적어 둔
"패시브가 주 경로라는 설계 덕에 [능동 보너스가] 성장 속도에 미치는 영향은 사실상 없다"는 서술과
정확히 일치한다(교차검증 통과).

### 3-3. ★★ 발견 — 활쏘기 XP 채널에는 코인과 달리 쿨다운도 일일 상한도 없다

`OnArcheryShotChanged`(`CharacterProgressionDirector.cs:496-509`)를 직접 읽으면, **같은 훅에서
동전과 XP가 함께 나가는데 동전 쪽만 방어돼 있다**:

- 동전: `CurrencyModel.TryAwardArcheryCoins`가 쿨다운(단조 시계 600초)과 일일 총량(72회/1,440코인,
  `CurrencyRules.ArcheryDailyAwardLimit`)을 **둘 다** 검사한다.
- **XP: `Grant(_config.progressionBullseyeXp, ...)`는 무조건 실행된다.** 같은 발 재발행 방어
  (`shot.ShotIndex == _lastRewardedShotIndex`)만 있고, **분당/일당 상한이 없다.**

이게 왜 문제가 되는지 계산했다: 연속 도배(매크로/자동클릭 등 비정상 사용, §3-2의 상식적 사용과는
다른 시나리오) 시 시간당 XP는

```
시간당 발 수(3600÷2.78) × 정중앙 확률(0.3335) × 15XP  ≈  6,478 XP/시간
```

패시브(90XP/시간)의 **72배**다. 이 속도를 24시간 유지하면(현실적이지 않지만 산술적으로는)
하루 155,472XP — **Lv50 전체 요구량(145,261XP)을 22.4시간 만에 넘는다.** 즉 지금 코드 그대로는
**정상 경로로 67.3일~201.8일 걸리는 캡 도달을, 방어되지 않은 반복 입력만으로 하루 안에 끝낼 수
있는 이론적 구멍이 있다.**

**이건 이 라운드가 만든 문제가 아니라 §3에서 시킨 "XP 수급원 전수 검색"으로 처음 드러난 기존
결함이다.** design-systems는 프로덕션 코드를 고치지 않으므로 직접 수정하지 않지만, 이 사실을
숨기지 않고 §8에 열린 질문으로 올린다 — **coder-systems/security가 확인해야 할 항목**이다
(제안 방향: 동전과 똑같이 `Grant`도 쿨다운/일일 상한을 걸거나, 아예 같은 관문 함수를 공유하게
만든다 — 코인 쪽이 "쿨다운 600초·일일 72회"로 이미 값을 정해 둔 것을 재사용하면 새 숫자를
지어낼 필요도 없다).

## 4. 레벨업 능력치 상승 설계(캡 50 기준 재설계) — `LevelBonus`

### 4-1. 구조 원칙은 1차안과 동일

BASE(8/6/5/7)는 손대지 않고 새 독립 항 `LevelBonus(level)`을 더한다(1차안 §2-1과 동일 논리,
U-4를 재론하지 않음). `총합(s) = BASE[s] + LevelBonus(level) + 주스탯 + 부스탯 + 세트보너스`,
`[0,40]` 클램프. 저장 안 함(파생값, `CurrencyRules.DailyCapCoins`와 같은 패턴).

### 4-2. ★ 예산이 줄었다 — 왜 1차안의 "Lv30 소프트캡, +6"을 버리는가

1차안(레벨캡 40)에서는 캡40 밑에 남는 여유가 "실제 도달 가능한 스탯 단일 최댓값"(REF §7-3,
집중력 35가 최댓값) 기준으로 **5**였다(40−35). **이 문서는 1차안에서 여유분 계산에 "완성
세트(28~31)" 기준을 썼는데, 다시 보니 그보다 더 높은 "실제 도달 가능한 단일 스탯 최댓값"
(세트 불일치, 부스탯을 그 스탯 하나에 몰아준 조합, 35/33/32/34)이 이미 REF §7-3에 있었다 —
**이 갱신판은 그 더 높은(더 엄격한) 기준으로 여유분을 다시 잡는다.** 캡을 50으로 올렸다고 이
여유분(5)이 커지지 않는다 — **스탯 캡(40)과 레벨 캡(50)은 독립된 숫자**이기 때문이다(§0 갱신
공지). 즉 **LevelBonus에 쓸 수 있는 예산은 1차안보다 오히려 작아진다(6→5, §5에서 정확히 검산)**.

레벨 범위는 40→50으로 25% 늘었는데 예산은 6→5로 줄었으므로, 1차안처럼 "초반에 몰아주고 뒤는
명예 구간으로 비운다"(Lv30에서 소프트캡, Lv31~40 10레벨 = 25% 무보상)를 그대로 유지하면
**Lv26~50(무려 25레벨, 전체의 50%)이 스탯 무보상 구간**이 된다 — 예산은 줄고 범위는 늘었으니
당연한 결과지만, 그 비율이 너무 커져 "레벨업이 능력치를 올린다"는 이번 요청의 체감이 후반부
절반에서 완전히 사라진다. **그래서 이번 갱신은 소프트캡을 하드캡과 일치시켜(50에서 정확히
끝남) 얇아진 예산을 전 구간에 고르게 편다.**

### 4-3. 채택 스케줄 — 10레벨마다 +1, Lv50에서 정확히 완료

| 레벨 구간 | 4스탯 전부에 지급되는 누적 보너스 |
|---|---:|
| Lv 1~9 | +0 |
| Lv 10~19 | +1 |
| Lv 20~29 | +2 |
| Lv 30~39 | +3 |
| Lv 40~49 | +4 |
| **Lv 50** | **+5(최종)** |

닫힌 형태(구현 참고): `LevelBonus(level) = min(5, floor(level / 10))`.

**초반 피드백이 늦어진 것은 인지된 트레이드오프다.** 1차안(Lv5부터 첫 지급, 11.7시간)보다
느리다 — 이 스케줄의 첫 지급은 **Lv10(누적 4,915XP ≈ 54.6시간 ≈ 8h/일 6.8일, 24h상주 2.3일)**이다.
대안으로 **Lv5,15,25,35,45**(첫 지급을 Lv5로 앞당기고 Lv46~50 5레벨만 명예 구간으로 남김,
"둥근 10 단위"보다 기억하기는 살짝 불리하지만 초반 피드백은 1차안 수준으로 복원)를 각주로
제시한다 — **어느 쪽을 채택할지는 리더 판단**(초반 체감 vs 숫자의 단순함).

### 4-4. 4스탯 균등 — 1차안과 동일한 근거로 유지

임계 경계(10/20/32)가 "4스탯 공통"이고(`EquipmentStatRules.cs:218-220`), 등급별 상승폭도
스탯이 아니라 등급에만 의존한다(1차안 §2-2 근거 그대로 유효). 차등을 둘 근거가 새로 생기지
않았으므로 균등을 유지한다.

## 5. ★★★ 최종 최대 도달 가능 스탯 — 정확한 계산 (다음 라운드의 "스탯→명중률" 기준 상한)

### 5-1. 결론 먼저: 다음 라운드가 써야 할 입력 상한은 **정확히 40**

`EquipmentStatRules.Evaluate`의 마지막 단계는 항상 `ClampStat`(REF §4-2·`EquipmentStatRules.cs:424`)
이고, 이건 **LevelBonus를 더해도 바뀌지 않는다** — `Total.Of(stat)`은 언제나 `[0, Cap]` 안에
있다. 즉 **"화면에 뜨고 실제 게임플레이 공식이 받는 값"의 절대 상한은 시스템이 존재하는 한
`EquipmentStatRules.Cap`(지금 40) 그 자체**다. **다음 라운드가 "스탯 X → 명중률 Y%" 공식을
설계할 때는 입력 범위를 `[0, EquipmentStatRules.Cap]`로 잡으면 되고, 그 상수를 참조하지
숫자 "40"을 베끼면 안 된다**(CLAUDE.md 확정 규칙 — 캡이 바뀌면 공식도 조용히 따라가야 한다).

이 결론은 클램프가 있는 한 항상 참이지만, 사용자가 요청한 것은 **"클램프 전에 실제로 얼마나
캡에 바짝 붙는가"**이므로 아래에서 원시(raw) 값을 정확히 재구성한다.

### 5-2. 원시 최댓값 재구성 — "실제 도달 가능한" 두 가지 정의를 구분한다

지금까지 이 시스템에는 "최댓값"이라고 부를 수 있는 서로 다른 시나리오가 3개 있었다. 사용자
요청 문구("전설장비 4종 풀세트 주스탯 + 부스탯 최대 + 세트보너스")는 **③번**을 가리키지만,
실제로 더 높은 값을 내는 것은 **②번**이라 셋을 나란히 보여준다:

| # | 시나리오 | 정의 | 근거 |
|---|---|---|---|
| ① | 이론적 스트레스 테스트(도달 불가) | 4슬롯 전부 전설, 부스탯을 "자유 배정"으로 가정하고 전부 같은 스탯에 몰아줌 | REF §7-2, `EquipmentStatRules.cs:421-423`의 양성 대조 |
| ② | **실제 카탈로그로 도달 가능한 단일 스탯 최댓값**(세트 불일치 허용) | 그 스탯의 주스탯 슬롯에 전설템 + 나머지 3슬롯은 "그 스탯을 부스탯으로 갖는" 실제 아이템 중 최고 등급(테마는 무시) | REF §7-3, `EquipmentStatRules.cs:1158-1163` 주석과 대조 완료 |
| ③ | 실제 완성 세트(전설 4종, 세트 보너스 포함) — 사용자가 지목한 조합 | 컬러 잉크 세트 4종(전부 전설) 전부 착용 | 1차안 §3-1(이 문서가 직접 재계산) |

| 스탯 | ①(도달불가) | **②(실제 도달 가능, 최댓값)** | ③(완성 세트, 세트보너스 포함) |
|---|---:|---:|---:|
| 집중력 | 41 | **35** | 31 |
| 관찰력 | — | **33** | 29 |
| 매력 | — | **32** | 28 |
| 민첩 | — | **34** | 30 |

**②가 ③보다 항상 높다** — 등급별 상승폭(MAINV/SUBV)이 **테마가 아니라 등급에만** 의존하므로
(REF §4-2), 세트를 맞추려고 테마를 통일하면 "그 스탯에 가장 큰 부스탯을 주는 아이템"을 포기해야
하는 경우가 생기고, 그 손실(②−③, 예: 집중력 35−31=4)이 세트 보너스 이득(+2)보다 크다. 즉
**"한 스탯만 극단적으로 밀어붙이는 실제 플레이"가 "이쁘게 세트를 맞추는 실제 플레이"보다
그 한 스탯에서는 항상 더 세다** — 이건 이번에 처음 발견한 사실이라 §8에 새 열린 질문으로 남긴다
(design-equipment/game-architect가 "세트를 맞추는 것이 손해"라는 이 결과를 의도했는지 확인 필요).

**따라서 캡 안전성 검증은 ②(35/33/32/34, 항상 더 높은 쪽)를 기준으로 해야 한다** — 1차안이
③(28~31)을 기준으로 삼은 것은 **더 느슨한 기준을 썼다는 뜻이므로 이번 갱신에서 바로잡는다.**

### 5-3. LevelBonus(+5, §4-3)를 더한 최종 계산

| 스탯 | ②(실제 도달 가능 최댓값) | **+ LevelBonus(5)** | 캡(40) 대비 |
|---|---:|---:|---:|
| **집중력** | 35 | **40** | **정확히 일치, 클램프 손실 0** |
| 관찰력 | 33 | 38 | 여유 2 |
| 매력 | 32 | 37 | 여유 3 |
| 민첩 | 34 | 39 | 여유 1 |

**핵심 결론: 캡40을 넘지 않는다 — 넘기는커녕 집중력 한 항목이 정확히 40에 맞아떨어진다.**
이건 우연이 아니라 §4-3의 스케줄(+5)을 **정확히 이 계산에 맞춰 역산**했기 때문이다(§5-4 참고).
③(완성 세트) 기준으로도 확인하면 집중력 31+5=36, 관찰력 29+5=34, 매력 28+5=33, 민첩 30+5=35 —
전부 여유가 더 크다(이쁜 세트를 맞추는 "보통의 완주 유저"는 캡에 훨씬 못 미친다).

### 5-4. 캡40을 넘기는가 — 세 가지 선택지 (요청대로 둘 다 계산해서 제시)

| | **Option 1(권고) — 보수적** | Option 2 — 중간 | Option 3 — 관대(캡 조정 필요) |

정보 손실이 0이다. (b) 최근(2026-09-05) 확정된 캡40을 재론하지 않아도 된다 — CLAUDE.md가

## 6. 부수 효과 갱신 — 임계 1단계(10)가 맨몸으로 열리는 시점 (캡50/+5 기준 재계산)

1차안(§5, +6 기준)을 +5로 재계산한다. BASE만으로는 어떤 스탯도 10에 못 닿는다(최댓값 8) —
LevelBonus(+5, §4-3 스케줄)를 더하면:

| 스탯 | BASE | 10 도달에 필요한 LevelBonus | 필요 레벨(§4-3 스케줄 기준) |
|---|---:|---:|---:|
| 집중력 | 8 | 2 | **Lv20** |
| 민첩 | 7 | 3 | **Lv30** |
| 관찰력 | 6 | 4 | **Lv40** |
| **매력** | 5 | 5 | **정확히 Lv50(캡)** |

**매력은 맨몸으로는 최대 레벨(50)에 도달해야만 1단계 임계를 넘는다** — 즉 "장비를 하나도 안
입고 레벨만 올려서 임계 효과를 보는" 부수 효과가 매력 하나에 한해서는 사실상 "만렙을 찍어야만"
발생하므로, 1차안보다 훨씬 좁혀졌다(1차안은 Lv25). 나머지 세 스탯도 1차안보다 필요 레벨이
전반적으로 늦춰졌다(예산이 얇아지고 넓게 퍼졌으므로 당연한 결과). **1차안의 우려("장비 없이
효과가 켜지는 것이 의도인가")는 이번 갱신으로 체감상 훨씬 완화됐다** — 그래도 매력이 "정확히
캡에서" 열린다는 사실 자체는 §8 열린 질문에 남긴다.

## 12. ★★★ XP-동전 페이싱 검산 — "같은 활동에서 나오는가"

사용자가 지목한 검산: **동전 상한(1,500/일)에 도달하는 활동**과 **XP 상한(활쏘기 72회)에
도달하는 활동**이 같은가?

**답: 아니오, 서로 다른 두 활동이다.**

- **동전 1,500 상한**은 **유휴(가만히 켜 둠)** 활동만으로, **2~3.5시간** 안에 도달한다(§10-2).
  활쏘기는 **전혀 필요 없다** — 유휴 채널과 활쏘기 채널은 서로 다른 예산(각각 1,500·1,440)을
  쓰는 **독립된 두 지갑**이다(`CurrencyRules.DailyCapCoins`가 `ArcheryCoinsToday`를 전혀 참조하지
  않는다 — `ClampArcheryCoinsToday`가 별도로 존재하는 것이 그 증거다).
- **XP 72회 상한**(활쏘기 채널)은 활쏘기라는 **능동 행동**을 요구하고, 쿨다운(600초) 때문에
  **최소 12시간(72×600초, §10-1)에 걸쳐 분산**해야 전부 채워진다 — 한 자리에서 몰아 칠 수
  없다(§3-3에서 지적한 매크로 결함이 이미 고쳐졌으므로 이 12시간 분산은 이제 **우회 불가능한
  진짜 하한**이다).

**즉 코인 상한(1,500)은 "몇 시간 켜 두면" 끝나는 낮은 문턱이고, XP 상한(72회)은 "하루 종일
간간이 활을 쏴야" 채워지는 높은 문턱이다 — 두 상한의 "난이도"가 애초에 다른 종류다.** 이건
불균형이라기보다 **의도적으로 다른 역할**로 읽을 수 있다: 유휴는 "존재만 해도 최소한을 보장",
활쏘기는 "적극적으로 참여해야 더 얹어주는" 이중 구조(REF/design 문서가 이미 "패시브가 주 경로,
능동은 가속"이라고 여러 번 명시한 것과 일치). **다만 진짜 불균형은 여기가 아니라 집중 모드다
(§12-1).**

### 12-1. ★ 진짜 불균형 — 집중 모드가 코인 경제와 레벨 경제를 갈라놓는다

§11의 P1↔P3 비교가 보여주듯, **집중 모드는 동전 상한(1,500)을 사실상 없는 것처럼 만들 수 있는
유일한 채널**이다(일일 상한 밖, `FocusWatchDirector.cs:226`) **동시에 레벨링에는 0% 기여**한다.
이건 두 가지 실제 결과를 낳는다:

1. **"동전 부자, 레벨 거지"가 가능하다.** 집중 모드를 하루 4시간 투입하면(생산성 앱으로서는
   전혀 비현실적이지 않은 사용 패턴 — 뽀모도로 25분×여러 세션) 코인만 분당 24×240분=5,760
   추가로 쌓이는데(합계 하루 7,260코인, 레전더리 가격의 0.76개분) 레벨은 P1과 똑같이 67.3일
   걸린다. **상점 가격(600~9,600)이 압박이 되는 시점 자체가 사라진다** — 이건 캡40의 "페이투윈
   방지" 설계 취지와는 다른 축의 문제이지만(현금이 아니라 시간 배분의 문제), §5-4의 스탯 캡
   설계가 전제한 "장비는 소중하게 모아야 한다"는 경제적 긴장을 이 페르소나에서만 무력화한다.
2. **레벨은 오직 (패시브 + 활쏘기)로만 통제된다.** §2·§4의 레벨 캡/소프트캡/LevelBonus 설계
   전부가 "레벨업 속도"를 조율하려는 작업이었는데, 그 속도에 영향을 주는 채널은 정확히 이
   둘뿐이다 — 집중 모드를 아무리 늘려도 레벨 설계는 흔들리지 않는다(이건 **긍정적**이다 — §2·§4의
   페이싱 계산이 집중 모드 사용 여부와 무관하게 안전하다는 뜻이기도 하다).

**이게 결함인가, 의도인가?** `FocusWatchDirector.cs:226`의 "§22-13"이 코인 쪽 설계로는 **명시적
확정 사항**이다 — design-systems가 되돌릴 결정이 아니다. 다만 "그 확정이 레벨 경제와 상호작용해
새로운 결과(동전-레벨 완전 분리)를 낳는다"는 사실은 §22-13을 정할 당시엔 **레벨이 스탯을 안
올리던 시절**(REF §3)이라 고려 대상이 아니었을 가능성이 높다 — 지금은 이 문서 §4가 레벨에도
경제적 무게(LevelBonus)를 실었으므로, **"동전은 넘치는데 레벨(=스탯)은 안 오른다"는 조합이
처음으로 의미를 갖게 됐다.** §14에 조정안 없이 열린 질문으로만 남긴다(코인 경제의 §22-13을
바꾸는 것은 design-systems 단독 판단 범위를 넘는다).

**가장 소극적인 페르소나(P1, 유휴만)조차 만렙 시점에 카탈로그의 87%를 살 수 있는 돈을 갖고
있다.** 이건 나쁜 소식이 아니다 — 요구 레벨 게이트(REF §5-1, 최고 30) 때문에 실제로는 그 시점에
**모든 아이템이 이미 해금돼 있고**, 87%는 "돈이 모자라서 못 사는 아이템이 42종 중 극소수"라는
뜻이라 상점이 "완주 시점엔 사실상 다 살 수 있는" 자연스러운 결말로 수렴한다. **P2·P3처럼 조금만
더 적극적이면 113~251%로 카탈로그를 넘어서므로, "상점 가격이 만렙 유저에게 압박으로 작동하는
구간"은 사실상 Lv50 이전(레벨업 도중 아직 코인이 부족할 때)에만 존재하고 만렙 이후엔 없다** —
이건 "만렙 = 수집 완료 + 경제적 여유"라는 흔한 엔드게임 서사와 일치하므로 **의도된 설계로
받아들여도 무방**하다고 판단한다. 별도 가격 조정은 권고하지 않는다.

## 부록 C. 3차 갱신 계산 스크립트

```python
common, rare, epic, legendary = 600, 1400, 3200, 9600
total_catalog = 14*common + 14*rare + 7*epic + 7*legendary   # 117,600

base, exp = 100.0, 1.05
def need(level): return base * (level ** exp)
cum, level = 0.0, 1
while level < 50:
    cum += need(level); level += 1
lv50_xp = cum   # 145,260.78

scenarios = {
    "P1 완전방치":  {"xp_per_day": 24*90,          "coins_per_day": 1500},
    "P2 활동형":    {"xp_per_day": 24*90+72*15,    "coins_per_day": 1500+72*20},
    "P3 집중모드중심": {"xp_per_day": 24*90,        "coins_per_day": 1500+24*120},  # 집중 2h/일=120분×24코인
}
seed = 1200
for name, s in scenarios.items():
    days = lv50_xp / s["xp_per_day"]
    coins_total = s["coins_per_day"]*days + seed
    print(name, f"{days:.1f}일", f"누적동전={coins_total:,.0f}",
          f"카탈로그대비={coins_total/total_catalog*100:.0f}%")

print("유휴 1,500 도달(분):", 1500/12)          # 125.0
print("유휴 2,500 도달(분):", 2500/12)          # 208.3
print("활쏘기 72회 최소 소요시간(시간):", 72*600/3600)   # 12.0
```

이 스크립트의 Lv50 XP 총량(145,260.78)은 §2·부록A와 동일해 재교차검증했다. §11·§13의 표는
이 스크립트 출력을 그대로 옮겼다.

## 15. ★ 4차 갱신 — "집중모드도 경험치" 확정 (열린 질문 9번 답변)

사용자가 §14 열린 질문 9번에 직접 답했다 — **집중 모드도 XP를 준다.** 동전의 완주/취소 산식
(`FocusCoinsPerMinute=24`/`FocusCancelCoinsPerMinute=20`, `CurrencyRules.cs:43,65`)과 같은
패턴으로 XP 버전을 설계한다.

### 15-1. 산식 — 코인과 같은 비대칭 구조, 같은 근거

`CurrencyRules.FocusCompletionCoins`/`FocusCancelCoins`(`CurrencyRules.cs:449-473`)의 구조를
그대로 옮긴다 — **완주는 초 단위로 연속 계산 후 마지막에 floor, 취소는 분 단위로 먼저 floor한
뒤 요율을 곱한다**:

```
FocusCompletionXp(세션 명목 길이 초) = floor(FocusXpPerMinute × 세션초 / 60)
FocusCancelXp(경과초)              = floor(경과초 / 60) × FocusCancelXpPerMinute
```

**이 비대칭을 그대로 가져오는 이유도 동일하다**(`CurrencyRules.cs:430-447` 클래스 주석 재사용):
취소를 "초 단위 연속"으로 열어 두면 사용자가 취소 타이밍을 초 단위로 재는 동기가 생긴다 —
분 격자에 묶어야 그 동기가 0이다. 완주가 초를 그대로 읽는 이유는 데모(90초)·최소(60초) 같은
격자 밖 세션 길이를 같은 식 하나로 처리하기 위해서다. **동전에서 이 비대칭이 필요했던 이유가
XP라고 다르지 않다** — 오히려 XP는 레벨링 페이싱에 직결되므로 "1분 미만 취소는 0"(하한 규칙을
따로 안 둬도 `floor(경과/60)=0`에서 저절로 나옴, 코인과 동일)이 **더** 중요하다.

### 15-2. 완주:취소 비율 — 동전과 같은 5:6을 그대로 쓴다

동전의 20:24는 기약분수로 **5:6**(취소가 완주의 83.3%)이고, `FocusSessionPayoutTests`가 이
관계를 항등식으로 고정해 뒀다(`CurrencyRules.cs:51`). **XP도 같은 5:6을 쓴다** — 근거는 코인과
동일한 안티파밍 논리(완주가 항상 더 유리해야 조기취소 스팸이 이득이 없다, `CurrencyRules.cs:60-63`
"§22-12가 전수로 확인")가 XP에도 그대로 적용되기 때문이다. 다른 비율을 쓸 근거를 찾지 못했다 —
오히려 **완주:취소 비율이 코인과 다르면** "완주하면 코인은 유리한데 XP는 아니다" 같은 조합이
생겨 사용자가 "완주해야 하는 이유"를 두 가지 다른 계산으로 따져야 한다. 같은 비율을 쓰면
**"완주가 항상 이득"이라는 메시지가 코인·XP 어느 쪽으로 봐도 하나로 통일**된다.

### 15-3. ★★ 확정 수치

| 상수 | 값 | 근거 |
|---|---:|---|
| `FocusXpPerMinute`(완주) | **6** | §15-3-a |
| `FocusCancelXpPerMinute`(취소) | **5** | 6×5/6=5, 정확히 코인과 같은 5:6 비율(§15-2)이면서 **정수로 딱 떨어지는** 유일한 완주값이 6이다(예: 9라면 취소가 7.5로 정수가 아니게 된다) |
| 일일 상한(신규, `FocusXpToday` 가칭) | **1,080 XP/일** | §15-4 |
| 상한 도달에 필요한 완주 시간 | **180분(3시간)/일** | 1,080 ÷ 6 |

**a. 왜 6인가.** 세 조건을 동시에 만족하는 값을 찾았다: ① 취소 요율이 정수(5)로 딱 떨어짐(위
표) ② 실사용 프리셋(15/25/50분, `FocusWatchDirector.cs:153`)에서 전부 깔끔한 값이 나옴 —
**15분=90XP, 25분=150XP, 50분=300XP.** ③ §15-4에서 검증하듯 일일 상한(1,080)에 도달하는
시간(3시간)이 "생산성 앱을 하루 종일 켜 두는 헤비 유저"에게 현실적인 상한이다(대안 9 —
2시간에 상한 도달 — 도 검토했으나 취소 요율이 7.5로 비정수가 되어 기각했다, §15-7 열린 질문 참고).

### 15-4. ★★★ 왜 XP는 "일일 상한 밖"이 아니라 캡을 두는가 — 코인과 다르게 간다

§22-13("집중 지급은 일일 상한 밖")은 **코인 한정 확정 사항**이다. 이걸 XP에 그대로 옮기지
않는다 — 근거:

1. **코인과 XP는 이 게임에서 하는 일이 다르다.** §12-1이 이미 밝혔듯 코인은 "얼마나 빨리
   모으는가"가 다른 시스템(레벨링 페이싱, §1~§9)에 영향을 주지 않는 **순수 자원 풀**이라
   상한 밖이어도 안전했다(§13이 "만렙 시점 87~251% 카탈로그 커버"를 "문제 아님"으로 판정한
   근거가 바로 이것). **XP는 정반대다 — 이 문서 §1~§9 전체가 XP 하나를 조율하려고 레벨 캡·
   LevelBonus·소프트캡을 계산한 것**이라, XP를 "상한 밖"으로 열면 이 문서가 만든 페이싱
   전체가 집중 모드 사용량에 따라 조용히 무너진다.
2. **실측으로 확인했다.** 집중 모드는 세션 길이만큼 실시간을 요구하므로(매크로로 초 단위를
   빨리 감을 수 없다 — §3-3의 활쏘기 결함과 **근본적으로 다른 종류**) 극단적 값 자체는 안 나오지만,
   "생산성 앱으로서 하루 여러 시간을 집중 모드로 쓰는" 것은 **전혀 비현실적이지 않다**(오히려
   이 앱의 정체성과 맞는 사용 패턴이다). 상한 없이 `FocusXpPerMinute=6`을 하루 8시간(480분) 쓰면
   2,880XP가 **추가**로 나온다 — 패시브(2,160)를 넘어서는 액수라 §2~§4가 계산한 Lv50 도달일수
   (67.3~201.8일)가 사용자의 업무 습관에 따라 수 배씩 흔들리는 값이 된다. **레벨 경제가 더 이상
   "패시브가 주 경로, 능동은 가속"(REF·이 문서 반복 확인 사실)이 아니게 될 위험이 있다.**
3. **그래서 상한을 둔다 — 크기는 활쏘기와 정확히 맞춘다.** 새 일일 상한 **1,080XP**를 도입한다.
   이 값은 임의가 아니라 **① 활쏘기 채널의 기존 상한(72회×15XP=1,080)과 정확히 같고, ②
   패시브 하루치(2,160)의 정확히 절반**이다 — 우연이 아니라 "패시브가 기준선, 활쏘기·집중모드는
   각각 최대 그 절반까지의 가속 채널"이라는 대칭 구조를 의도적으로 만든 것이다(§15-5에서 이
   대칭이 실제로 어떤 체감을 주는지 검증한다).

### 15-5. 요청사항 1 검산 — 상대적 크기감이 맞는가

| 페르소나 | 구성 | 하루 XP | Lv50까지 | 비교 |
|---|---|---:|---:|---|
| P1. 완전방치 | 패시브만 | 2,160 | 67.3일 | 기준선 |
| **P3. 집중모드(2h/일)** | 패시브+집중 120분(=상한의 2/3) | **2,880** | **50.4일** | P1보다 **25.1% 빠르다** ✅ 요청①("P3가 P1보다 확실히 빨라야") 충족 |
| P2. 활동형(활쏘기72) | 패시브+활쏘기 상한 | 3,240 | 44.8일 | |
| **P5. 집중모드 몰빵(3h/일)** | 패시브+집중 180분(=상한) | **3,240** | **44.8일** | **P2와 정확히 동일** — 집중모드를 최대로 밀어붙여도 활쏘기를 앞서지 못하고 **딱 같아진다** |
| P4. 올인(활쏘기+집중2h) | 패시브+활쏘기+집중120분 | 3,960 | 36.7일 | |
| P6. 절대최대(둘 다 상한) | 패시브+활쏘기상한+집중상한 | 4,320(=패시브의 정확히 2배) | 33.6일 | 이론적 상한 |

**결론 — 요청 사항이 전부 검증됐다.**

- **P3(현실적 집중모드 사용) > P1(방치)**: 67.3일 → 50.4일, **25.1% 단축**. "그게 원래 취지"를
  만족한다.
- **P5(집중모드를 상한까지 밀어붙여도) ≤ P2(활쏘기 상한)**: 오히려 **정확히 같다**(둘 다
  44.8일) — 이건 우연이 아니라 §15-4-3에서 두 상한을 똑같이 1,080으로 맞췄기 때문이다.
  **"방치+집중모드"가 "방치+활쏘기"를 앞지르는 일은 구조적으로 없다** — 활쏘기의 존재 의미가
  집중모드에 잠식되지 않는다(사용자가 우려한 실패 조건이 발생하지 않음을 산술로 확인).
  **오히려 둘을 "정확히 동급인 두 가지 대체 경로"로 재해석할 수 있다** — 활쏘기가 체질에 안
  맞는 사용자(적극적 클릭을 싫어함)에게 집중 모드가 정확히 같은 크기의 대안 경로가 되어,
  게임 디자인 관점에서는 **오히려 긍정적인 재발견**이다.
- **둘을 합치면(P6) 정확히 패시브의 2배(4,320)** — "두 가속 채널을 전부 최대로 밀어붙이면
  기준선의 딱 2배"라는 깔끔한 서사가 생긴다.

### 15-6. 구현 참고사항 (design 범위 밖, coder-systems·game-architect 확인 필요)

1. **새 저장 필드가 필요하다.** 코인의 `archeryCoinsToday`처럼 `focusXpToday`(가칭) 같은 일일
   누계 카운터가 새로 생겨야 한다 — **CLAUDE.md 확정 규칙**: 저장 스키마 `CurrentVersion`을
   올리는 라운드는 `vN-1` 구버전 파일을 읽었을 때 이 신규 필드가 안전한 기본값(0)으로 채워지는지
   검증하는 하위 호환 테스트 1건을 반드시 동반해야 한다. **design-systems는 숫자만 정했다 —
   이 구현·스키마 버전업·테스트는 coder-systems 몫이다.**
2. **롤오버는 기존 것과 같은 자리를 쓴다.** `CurrencyModel`의 일일 롤오버(`TodayGrantedCoins`,
   `ArcheryCoinsToday`를 0으로 되돌리는 자리, `CurrencyModel.cs:512`)에 `focusXpToday=0`도
   같이 얹으면 된다 — 날짜 판정 로직을 새로 만들 필요가 없다.
3. **어느 파일에 산식을 둘 것인가.** 코인은 `CurrencyRules`(상태 없는 순수 규칙)에 산식이
   있는데, XP는 지금 `CharacterProgressionModel`(상태 보유)에만 곡선 함수가 있고 "순수 규칙"
   전용 파일이 없다. `FocusCompletionXp`/`FocusCancelXp`/`ClampFocusXpToday`를
   `CharacterProgressionModel`에 정적 메서드로 추가할지, `CurrencyRules`처럼 새 순수 규칙
   파일(예: `ProgressionRules`)을 뽑을지는 **game-architect 판단 영역**으로 남긴다(§9의 구조적
   고려사항과 같은 종류의 질문).
4. **잠재적 이중 지급 없음 확인.** 완주/취소 XP는 코인과 똑같이 `IsSessionActive`를 재진입
   방지 관문으로 쓰는 그 자리(`FocusWatchDirector.PayCompletionCoins`/`PayCancelCoins` 옆에
   나란히 `PayCompletionXp`/`PayCancelXp` 추가하는 형태를 권고)에 붙이면 §22-13 코인이 이미
   검증해 둔 "세션 종료 경로 셋(완주/중도취소/긴급정지) 모두가 지급 함수 두 곳 중 하나를
   반드시 지난다"는 불변식을 XP도 공짜로 물려받는다 — **별도 종료 경로를 만들지 말 것.**

### 15-7. 새 열린 질문(§8 1~9번 유지, 10번 추가)

10. **`FocusXpPerMinute` 후보 6 vs 9(§15-3-a)** — 6(취소요율 정수 5, 상한까지 3시간)을
    권고했으나 9(상한까지 2시간, 취소요율 7.5→반올림 8 또는 7 필요)를 원한다면 취소 요율의
    비정수 문제를 어떻게 처리할지(반올림 방향)까지 함께 정해야 한다.

## 부록 D. 4차 갱신 계산 스크립트

```python
base, exp = 100.0, 1.05
def need(level): return base * (level ** exp)
cum, level = 0.0, 1
while level < 50:
    cum += need(level); level += 1
lv50_xp = cum   # 145,260.78

passive_per_day, archery_cap = 24*90, 72*15   # 2,160 / 1,080
focus_rate, focus_cap = 6, 1080               # 상한 = 활쏘기와 동일 = 패시브의 절반

scenarios = {
    "P1 완전방치":  passive_per_day,
    "P2 활동형(활쏘기72)": passive_per_day + archery_cap,
    "P3 집중모드(2h/120min)": passive_per_day + 120*focus_rate,
    "P5 집중모드 몰빵(3h/180min=상한)": passive_per_day + focus_cap,
    "P4 올인(활쏘기+집중2h)": passive_per_day + archery_cap + 120*focus_rate,
    "P6 절대최대(둘다 상한)": passive_per_day + archery_cap + focus_cap,
}
for name, xp in scenarios.items():
    print(name, xp, f"{lv50_xp/xp:.1f}일")

# 프리셋 완주 XP
for m in (15, 25, 50):
    print(f"{m}분 완주 = {focus_rate*m}XP")
```

P5(집중모드를 상한까지 밀어붙인 값)와 P2(활쏘기 상한)가 **정확히 같은 3,240**으로 나오는 것을
이 스크립트로 재확인했다 — §15-4-3에서 두 상한을 의도적으로 1,080으로 맞춘 결과다.
