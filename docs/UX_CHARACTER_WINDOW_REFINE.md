# 캐릭터창 고도화 — UI 표면 정련 사양 (ux-designer)

작성 2026-09-06 · 담당 `ux-designer` · 범위 **UI 표면(배치·간격·대비·상태 표현)만**

이 문서는 **정련(refine)**이지 재배치가 아니다. 사용자 지침 원문:
*"The overall layout is preserved."* → **3열 구조 · 탭 4개 · 슬롯 4자리 · 카드 격자 열 수는 한 글자도
바꾸지 않는다.** 아래 모든 변경은 (가) 색·두께·간격, (나) 이미 있는 요소의 z-순서/부모, 둘뿐이다.

## 2. 능력치 STATUS 게이지 — 지금 무엇이 잘못돼 있는가

### 2-1. 현재 구성 (`CharacterInfoWindow.Stats.cs`)

```
스탯 카드 74pt  = 11(pad) + 18(1행) + 8 + 5(게이지) + 8 + 13(3행) + 11(pad)
트랙   Flatten(TrackBackground α0.09, CardSurfaceMuted) = #2A2D32,  폭 234 × 높이 5
채움   Accent #C8A15A                                   (RadiusDot 9-슬라이스)
눈금   폭 DividerThickness(1pt) × 5,  25% / 50% / 80% 자리
        꺼짐 = PanelSurface #14171C   ·   켜짐 = Accent #C8A15A
```

### 2-2. 실측 — **세 줄이 미달이고, 그중 둘은 원리상 「보이지 않음」이다**

| 잰 것 | 값 | 하한 | 판정 |
|---|---:|---:|---|
| 트랙 vs 카드면 | **1.28 : 1** | 3.0 | 미달 |
| 채움 vs 트랙 | 5.73 : 1 | 3.0 | 통과(1.91배) |
| 채움 vs 카드면 | 7.36 : 1 | 3.0 | 통과 |
| **눈금(꺼짐) vs 트랙** | **1.30 : 1** | 3.0 | **미달** |
| **눈금(켜짐) vs 채움** | **1.00 : 1** | 3.0 | **미달 — 같은 색이다** |
| 눈금(꺼짐) vs 채움 | 7.44 : 1 | 3.0 | (그 자리에 안 온다) |

### 2-3. ★ 결함 D-1 — **임계 눈금은 어느 상태에서도 안 보인다**

이건 "대비가 낮다"가 아니라 **구조적으로 0**이다. 증명은 두 줄이다.

`EquipmentStatRules`: 임계 `{10, 20, 32}` · `Cap = 40` · `Progress01 = total/40` ·
`TierMark01(k) = 임계[k]/40` · `TierOf(total)` = 넘긴 임계 개수.
`CharacterStatReadout.IsTickLit(k, tier, reached) = k ≤ max(tier, reached)`.

```
(1) 눈금 k가 켜진다(k ≤ tier)  ⟺  total ≥ 임계[k]  ⟺  Progress01 ≥ TierMark01(k)
                                                   ⟺  그 눈금은 채움 안에 있다
(2) 채움 안의 눈금은 Accent, 채움도 Accent          →  1.00 : 1   (완전 불가시)
(3) 눈금 k가 꺼졌다                                 →  반드시 채움 밖 = 트랙 위
(4) 트랙 위 꺼진 눈금은 PanelSurface on #2A2D32     →  1.30 : 1   (사실상 불가시)
```

즉 **화면에 실제로 보이는 눈금은 「예전에 넘겼는데 지금은 장비를 빼서 못 미치는」 한 경우**
(`reached > tier`, Accent가 트랙 위에 놓여 5.73:1)**뿐이다.** 의도(H-8 *"한 번 넘긴 눈금만 황동"*)와
정확히 반대로, **넘긴 순간 사라진다.**

원가: 카드 4장 × 활성 눈금 3개 = `Image` **12개**가 화면에 아무것도 그리지 않고 있다.

### 2-4. ★ 판정 T-1 — **트랙을 밝혀 고치는 길은 없다(공집합)**

누군가 반드시 "트랙을 한 단 밝히자"고 할 것이므로 미리 닫는다. 부등식을 풀었다.

```
L(CardSurfaceMuted) = 0.00905      L(Accent) = 0.38463
트랙 vs 카드 ≥ 3.0  →  L(트랙) ≥ 3.0×(0.00905+0.05) − 0.05 = 0.12714
채움 vs 트랙 ≥ 3.0  →  L(트랙) ≤ (0.38463+0.05)/3.0 − 0.05 = 0.09488
                        0.12714 > 0.09488  →  ★ 공집합
```

**두 하한을 동시에 만족하는 트랙 색은 존재하지 않는다.** 이것은 `UiChrome.RarityTrack`이
이미 겪은 것과 **같은 부등식·같은 결론**이다(그쪽 주석: *"양쪽이 동시에 서는 색은 존재하지 않는다 …
트랙은 「보이는 구획선」이 아니라 「홈」으로 설계된 것이고, 지는 하한은 채움↔트랙 하나다"*).

⇒ **트랙 색을 더 찾지 마라.** 이 게이지에서 지는 하한은 「트랙 vs 카드면」이고 그것은
**설계상 지도록 되어 있다.** 살려야 하는 것은 채움↔트랙(5.73, 이미 통과)과 **눈금**이다.

### 3-2. 치수 — **카드 높이 74pt 불변, 세로 예산 변화 0**

| 상수 | 지금 | 확정 | 근거 |
|---|---:|---:|---|
| `StatGaugeHeight` | 5 | **8** | 아래 3-2-1 |
| `StatFootHeight` | 13 | **10** | 위 +3을 여기서 되돌려 카드 74 유지 |
| 눈금 폭 | `DividerThickness` 1 | **2** | 3-4 |
| 그 외(pad 11 · 1행 18 · 간격 8 · 칩 18) | — | **불변** | — |

```
검산   11 + 18 + 8 + 8 + 8 + 10 + 11 = 74      ← StatCardHeight 그대로
컬럼2  StatCardsHeight = 4×74 + 3×10 = 326      ← 그대로  (여유 16pt 유지)
```
★ `CharacterStatCardLayoutTests` / `CharacterStatColumnLayoutTests`가 **상수에서 다시 세는**
구조라 이 변경으로 자동으로 따라온다 — **단, 두 테스트가 5나 13을 숫자로 베껴 두었다면 그건
따로 고쳐야 한다.** coder는 착수 전에 그 두 파일에서 리터럴 `5f`/`13f`를 먼저 grep할 것.

#### 3-2-1. 왜 8인가 — **Windows 배율에서 잔차가 0인 값**

이 저장소가 `UiChrome.RarityRibbonHeight`에서 이미 세운 규칙이다(*"4의 배수만 세 배율 전부에서
정수 픽셀이 된다"*). 그 자로 지금 게이지를 재면:

```
        ×1.25    ×1.5    ×1.75          macOS ×1 / ×2
 5pt →  6.25     7.50    8.75    ← 세 배율 전부 반 픽셀   (지금 값)
 6pt →  7.50     9.00   10.50    ← 두 곳 어긋남
 8pt → 10.00    12.00   14.00    ← ★ 잔차 0            8 / 16
```
**지금 값 5pt는 Windows 세 배율에서 전부 반 픽셀에 걸려 있다.** 리본이 4pt로 간 것과 같은
결함이 여기 그대로 남아 있었고, 아무도 이 게이지를 그 자로 재지 않았다.

부수 효과 — 단계 칩 y도 함께 정수가 된다:
```
chipY 오프셋 = (StatTierChipHeight − StatFootHeight) / 2
  지금  (18−13)/2 = 2.5  →  ×1.25 3.125 / ×1.5 3.75 / ×1.75 4.375   (세 곳 전부 어긋남)
  확정  (18−10)/2 = 4.0  →  ×1.25 5    / ×1.5  6    / ×1.75 7        ★ 잔차 0
```

#### 3-2-2. 3행 10pt가 좁지 않은가 — 검산

3행에 들어가는 것은 `FontCaption`(10pt) 「초급까지 9」 하나와, 3행보다 큰 단계 칩(18pt)이다.
- `UiChrome.AddText`는 `verticalOverflow = Overflow`라 **글자가 상자에 잘리지 않는다**(설계상).
- 칩 세로 범위: `footY+4` ~ `footY−14`. 카드 바닥은 `footY−10−11 = footY−21` → **바닥 여유 7pt**.
- 칩 위: 게이지 바닥이 `footY+8` → **게이지와 칩 사이 4pt**(지금 5.5pt에서 1.5pt 좁아진다).

### 3-3. 채움 — **가로 램프** (참고 지침의 *"gradient/highlight effect for the progress portion"*)

> ★★ **2026-09-06 개정 — 내 초판(세로 3단 광택)을 철회한다.**
> `design-art`가 `docs/DESIGN_RARITY_GLOW.md` §8-2에서 **가로 램프**(시작 어둡게 → 선단 밝게)를
> 냈고, **수치로 내 안을 이긴다.** 아래 3-3-0이 그 비교이고, 3-3-1은 그 안의 **선단 색 하나를
> 반박**한다. 철회한 초판은 3-3-9에 근거째로 남긴다 — 되짚을 수 있어야 다음 판단이 싸다.

#### 3-3-0. 두 안의 실측 비교 — 내가 진다

| 축 | 내 초판(세로 3단 광택) | `design-art`(가로 램프) |
|---|---:|---:|
| 채움 **최대** 대비 vs 트랙 | 7.51 : 1 | **9.78 : 1** |
| 채움 **평균** 대비 vs 트랙 | 6.39 : 1 | **7.75 : 1** |
| 「선단이 어디인가」를 말하는가 | 아니오(세로축이라 무관) | **예 — 선단이 항상 가장 밝다** |
| 폭 변화에 불변인가 | 예 | 예(램프를 **채움 사각형에 고정**하므로 선단은 언제나 끝색) |

내가 초판에서 가로 램프를 *"밝기 경사가 길이 단서와 경쟁한다"*는 이유로 배제했는데,
**그 반론은 「램프를 채움 사각형에 고정한다」로 이미 해소돼 있었다** — 값은 여전히 길이만 말하고
색은 값에 따라 변하지 않는다. **내 배제 근거가 틀렸다.**

★ `design-art`가 **하이라이트 캡을 수치로 기각**한 것도 옳다(끝색 `L 0.691` 위에 얹을 밝은 색이
없어 후보 셋 전부 1.10~1.29 : 1). 내 초판의 A단(꼭대기 2pt)은 그 캡의 약한 변종이었다.

#### 3-3-1. ★ 그러나 **선단 색 `#FFD375`는 반박한다** — 예약색이다

`design-art` 안의 끝색은 `#FFD375` = **`UiChrome.RarityColor(Legendary)`**다.
**같은 문서, 같은 라운드에서 그 색을 「전설 포인트 글로우」로도 확정했다.** 그러면 이 창 하나에서
`#FFD375`가 **세 가지**를 말하게 된다:
```
① 전설 등급 리본 채움칸      (UiChrome._rarityRamp[3])
② 전설 포인트 글로우          (DESIGN_RARITY_GLOW 확정)
③ 스탯 게이지 선단            (같은 문서 §8-2 제안)   ← 새로 생기는 뜻
```
그리고 **셋은 동시에 보인다** — 컬럼 2의 스탯 게이지 4개와 컬럼 3의 카드 격자는 한 창 안이다.

`UiChrome` 등급 램프 절이 이 정확한 사고를 금지하고 있다:
> *"★★ **이 다섯 hex는 이 파일 밖에 존재하면 안 된다.** 등급색이 여기 말고 어디서든 다시 나타나는
> 순간 그게 드리프트의 시작이고… `RarityColorSingleSourceTests`가 프로덕션 소스를 통째로 훑어
> hex 표기와 실수 3튜플 **양쪽**으로 막는다."*

그리고 이 저장소는 **이미 한 번 당했다**: `Accent`와 `CardBorderWorn`이 같은 값이던 시절
*"「지금 착용 중인 카드」가 다른 강조 크롬과 구분되지 않았다"*(`persona-newcomer` 신고).
**같은 형태의 사고를 반복하는 제안이다.**

#### 3-3-2. 확정 — 구조는 `design-art`, 선단 색만 교체

```
끝색 = Flatten(white α0.55, Accent) = #E6D5B5     ← Accent의 순수 밝힘. 신규 hue 0
```

| 선단 후보 | vs 트랙 | ΔE(시작 `#C8A15A`) | ΔE(전설 `#FFD375`) | 판정 |
|---|---:|---:|---:|---|
| `#FFD375`(design-art) | 9.78 | 20.74 | **0.00** | ★ 예약색 |
| `Flatten(w .40, Accent)` `#DEC79C` | 8.38 | 22.09 | 28.14 | 대비 부족 |
| **`Flatten(w .55, Accent)` `#E6D5B5`** | **9.57** | **30.06** | **34.01** | **채택** |

그리고 `Image.Type.Simple`로 바꾸면 **이 저장소가 이미 실측으로 잡은 「캡이 창끝처럼 가늘어지는」
결함**이 그대로 재발한다(`UiChrome` (B) 절: *"옛: 1.97 → 2.90 → 3.33 → 3.70px"*).

```

      크기      256 × 16 텍셀

```
캡 안의 램프 왜곡은 **양 끝 4/256 = 1.6%**뿐이라 눈에 안 띈다.

#### 3-3-A. 공통 — 알파 램프 금지

★★ **어느 안이든 알파 램프 스프라이트로 만들면 안 된다.** `UiChrome.VerticalGradientFill`은 자기 문서에

그것이고, `design-art`가 등급 글로우에 못박은 제약(*"썸네일 바탕 스프라이트의 RGB에 구운 불투명
램프"*) · §4-4-0의 PREVIEW 글로우 정정과 **셋 다 같은 기법**이다.
이 앱에서 램프를 그리는 합법적인 방법은 이것 하나뿐이다.

(`UiChrome` 크롬 버튼 절 (1)). 2pt는 어느 배율에서도 최소 2px다. 8pt 막대에 2pt 홈은
막대 두께의 25%로, 「홈」으로 읽히는 정상 비율이다.

0.5·0.2pt 소수가 남고 이것은 막대 폭 234가 바뀌지 않는 한 없앨 수 없다. 홈이 반 픽셀 흐려지는
정도이고, 위 「전부 안 보임」과는 비교 대상이 아니다. **실기 캡처 항목으로 남긴다.**

테두리는 **세 번째 색을 새로 들이는** 다른 축이다. 부등식은 여전히 참이고 그것을 **우회하는**

|---|---:|---|

#### 확정 치수 — **두께 1pt · 트랙 안쪽 · 채움보다 아래**

```
GaugeTrack (234×8, RadiusDot)
├ GaugeRim   ← ★ 신규.  AddOutline(RoundedOutline(RadiusDot, 1)) · NonTextMuted
├ Fill       ← 기존(§3-3 가로 램프 스프라이트). 이 위로 그려지므로 채워진 구간에서는 림이 덮인다
└ Tick0..n
```

**왜 「채움보다 아래」인가 — 두 가지가 동시에 풀린다**
1. `NonTextMuted`는 램프의 **시작 쪽에서 1.95 : 1**(안 보임) · **선단 쪽에서 3.26 : 1**(보임)이다.
   림을 채움 **위**로 그리면 8pt 막대의 위아래 1pt씩을 회색이 덮고, 하필 **가장 밝은 선단에서
   가장 잘 보인다** — 「선단이 가장 밝다」는 §3-3의 설계를 정면으로 깎는다.
2. 원래 결함은 *"막대가 어디서 끝나는지 안 보인다"*이고 그 정보는 **빈 구간**에만 있다.
   채워진 구간은 채움 자신이 이미 **7.36 : 1**로 카드에서 분리된다 — 림이 필요 없다.
⇒ 림은 **필요한 곳(빈 구간)에만 나타나고** 진행률 100%에서는 사라진다. 그게 옳다.

**왜 1pt인가 — 2pt는 이 라운드의 목적을 되돌린다**
```
1pt →  빈 구간 내부 6pt 남음   (오늘 5pt보다 여전히 두껍다)
2pt →  빈 구간 내부 4pt 남음   ← 5→8로 올린 것이 눈에는 4로 보인다. 자기모순
```
바깥으로 두르는 안(트랙 밖 1pt 링 · 내부 8pt 유지)도 검토했으나 **카드 세로 예산이 안 된다**:
발자국이 8→10이 되면 `11+18+8+10+8+10+11 = 76 ≠ 74`이고, 맞추려면 간격을 7로 내려
(×1.25에서 8.75px) 이 라운드가 얻은 잔차 0을 잃는다. **안쪽 1pt가 유일하게 공짜다.**

**정직한 잔차**: 1pt는 ×1.25/×1.5/×1.75에서 1.25 / 1.5 / 1.75px다. 다만 이것은
**234pt 길이의 닫힌 링**이지 짧은 헤어라인이 아니고(위·아래·양 캡이 서로를 보강한다),
macOS ×2에서는 2px다. **×1에서 너무 얇으면** 2pt로 올리고 그때 `StatHeadHeight` 18 → 16으로
2pt를 되돌려 카드 74를 지킨다 — **실기 캡처 항목.**

★ 컬럼 2의 STRESS/EXP 게이지(`TrackHeight` **4**)에도 같은 결함이 있지만 **이 라운드에서 안
건드린다** — 4pt 트랙에 1pt 림을 두르면 내부가 2pt만 남는다. 별도 사안으로 넘긴다.

### 4-4. 확정 사양 — 배경 글로우를 **RenderTexture 안으로** 옮긴다

> **리더 보고 항목 (2/3) — 코드 구조 영향.** 이건 색 변경이 아니라 **소유권 이동**이다.
> 그리는 주체가 `CharacterInfoWindow`(uGUI)에서 `CharacterPortraitStage`(월드/카메라)로 넘어간다.

| 항목 | 값 |
|---|---|
| 위치 | `CharacterPortraitStage`, 미니 피규어 **뒤**(`PreviewSortingOrder = −3`보다 더 뒤, 예 −5) |
| 스프라이트 | `UiChrome.RadialGlow()`(제곱 감쇠) 그대로 — 신규 프리미티브 0개 |
| 크기 | 지름 **D = 0.95 H**(표시 179.55pt 기준 **170.6 pt**) |
| 중심 | 액자 좌표 기준 **높이 0.45 H**(가슴~허리) · 가로 중앙 |
| 색 | `UiChrome.Accent` **α = 0.20 상당** — ★ **반드시 「불투명 RGB 램프」로 구울 것**(아래 정정) |

#### ★★ 4-4-0. 자기 정정 — 초판의 *"RT 안이므로 창 알파에 영향 0"*은 **거짓이었다**

이 문서 초판은 *"글로우를 RenderTexture 안에 두면 알파는 자유롭다"*고 적었다. **틀렸다.**
`coordinator` 경유로 온 N-1(무대 시인/바닥광원 12.04% 비침) 지적을 내 사양에 대입해 보고 잡았다.

```
RT의 알파가 1로 남는지는 「그 스프라이트를 어떤 셰이더로 그리느냐」에 달렸다.
  Blend One OneMinusSrcAlpha (Sprites/Default 계열)  → dstA' = srcA + dstA(1−srcA) = 1   ✔
  Blend SrcAlpha OneMinusSrcAlpha (UI/Default 계열)  → dstA' = srcA² + dstA(1−srcA)
      srcA 0.20, dstA 1  →  0.04 + 0.80 = 0.84       ← ✘ RT가 반투명해진다
```
RT가 α0.84가 되면 `RawImage`가 그것을 그대로 캔버스에 올리므로 **§4-3에서 지적한 것과
똑같은 비침(16%)이 글로우 자리에 그대로 생긴다.** 촬영장이 쓰는 머티리얼을 내가 확정할 수 없으므로
**조건부 안전에 기대면 안 된다.**

**확정 — 셰이더와 무관하게 참인 방법만 쓴다:**
> 글로우는 **α = 1 인 불투명 사각형** 하나이고, **RGB에 라디얼 램프를 굽는다.**
> 바깥 = 바탕색 그대로, 중심 = `Flatten(Accent α0.20, 바탕색)`.
> **알파는 어디에서도 1 미만이 되지 않는다.**

즉 「배경 위에 반투명 글로우를 얹는다」가 아니라 **「배경 자체를 글로우가 섞인 색으로 굽는다」**이다.
`design-art`가 등급 글로우에 못박은 *"썸네일 바탕 스프라이트의 RGB에 구운 불투명 램프"*와
**완전히 같은 기법**이고, §3-3(게이지 가로 램프)이 쓰는 것과도 같다.
★ **`design-art`와 독립적으로 같은 결론에 도달했다는 사실 자체가 이 기법의 근거다** —
이 앱에서 램프를 그리는 합법적인 방법은 이것 하나뿐이다.

**따라서 §4-4의 구현 형태를 이렇게 고친다**(값은 그대로):
| 항목 | 확정 |
|---|---|
| 형태 | 미니 피규어 **뒤**의 전면 사각형 1장. **α = 1** |
| RGB | 라디얼 램프. 중심 `Flatten(Accent 0.20, ResolveBackdropColor())` · 가장자리 `ResolveBackdropColor()` |
| 감쇠 | `(1−t)²` — `UiChrome.RadialGlow`가 이미 쓰는 제곱 감쇠와 같은 곡선 |
| 크기 | 액자를 덮는다(램프가 D=0.95 H 안에서 0으로 떨어지므로 바깥은 순수 바탕색) |
| 카메라 | `clearFlags`/`backgroundColor`는 **그대로 둔다** — 이 사각형이 그 색으로 끝나므로 이음매가 없다 |

**왜 α 하나로 두 바탕을 다 커버하는가** — 방향이 자동으로 뒤집힌다:

| 바탕 | 합성색 | 잉크 대비(현재→글로우 중심) | 바탕↔글로우 ΔE |
|---|---|---:|---:|
| 종이 `#E9EAE6`(검은 잉크·출하 기본) | `#E2DBCA` | 17.39 → **15.28 : 1** | **9.01** |
| 목탄 `#252829`(흰 잉크) | ≈`#474137` | 14.77 → **≈10.4 : 1** | **≈15.9** |

- 두 경우 모두 ΔE가 **변별 하한 7.8을 넘는다** → 글로우가 실제로 보인다.
- 두 경우 모두 잉크 대비가 **본문 하한 4.5의 2배 이상**으로 남는다 → 캐릭터가 흐려지지 않는다.
- 종이에서는 「따뜻한 조명 웅덩이」, 목탄에서는 「브라스 헤일로」로 읽힌다. **`ResolveBackdropColor`가
  이미 하는 뒤집기와 같은 구조**라 새 분기가 필요 없다.

**동시에 처리해야 하는 것**(안 하면 결함이 남는다):
1. `StageFloorGlow` — 위 글로우가 그 역할을 인수하므로 **캔버스에서 제거**한다. 남기면
   테두리 8pt 띠에서 바탕화면 12% 비침만 남는다.
2. `StageSheen` — 안쪽이 어차피 안 보이므로 두 갈래다.
   (가) **제거**(권장) — 알파 구멍 9%가 사라진다.
   (나) 유지하려면 `Flatten(PanelSheen, 액자바탕)`으로 **미리 합성**하고 `VerticalGradientFill`
       대신 `RoundedFill`로 바꾼다(램프를 잃지만 램프는 어차피 안 보인다).
   ★ 어느 쪽이든 **`UiChrome.VerticalGradientFill`의 「호출부 0건」 주석을 사실로 되돌려야 한다.**
3. 액자 위쪽 「빛」이 필요하면 **그것도 RT 안**에서 준다(카메라가 찍으므로 알파 문제가 없다).

### 6-2. ★ 결함 D-3 — `[잠김]` 칩은 **면이 존재하지 않는다**(1.00 : 1)

`CharacterInfoWindow.Cards.cs`의 `StyleActionButton`에서
`face = !owned ? UiChrome.CardSurfaceMuted : …`인데, **잠긴 카드의 바탕 자체가
`CardSurfaceMuted`다**(같은 파일 `card.Surface.color = UiChrome.CardSurfaceMuted`).
칩과 바탕의 RGB가 완전히 같다.

★ 그 함수의 문서는 **이 1.00을 문제로 적어 두었다** — *"고치기 전 면은 1.35 / 1.26 / **1.00** : 1
이었고, 셋 다 자체 하한 3.0 미달이다. 특히 잠김은 칩과 카드 바탕이 같은 RGB였다"*. 그런데
**2026-09-02의 수정은 활성 둘만 고치고 잠김은 그대로 뒀다.** 문서만 읽으면 셋 다 고쳐진 줄 안다.
(이 저장소가 정본으로 못박은 *"「판정」과 「코드 반영」을 같은 칸에 적지 마라"*의 실례가 하나 더 나온 것이다.)

**WCAG 2.2 §1.4.11이 비활성 컴포넌트를 면제하므로 규격 위반은 아니다.**
문제는 **앱 내부 일관성**이다:

| 앱 안의 비활성 선례 | 값 | 출처 |
|---|---:|---|
| 설정창 꺼진 스위치 손잡이 | **1.70 : 1** | `SettingsControls.cs` §1.4.11 면제 근거를 명시하며 남긴 값 |
| 비활성 색 견본 `Dimmed()` | 원본에서 2.67 : 1 물러남 | `SettingsControls.DisabledFillOpacity = 0.45` |
| 카드 `[잠김]` 칩 | **1.00 : 1** | ← 혼자만 «없음» |

이 앱의 규칙은 *"면을 죽이되 없애지는 않는다"*이고 `[잠김]`만 그 규칙 밖에 있다.
1.00 : 1은 «꺼진 버튼»이 아니라 «버튼이 아니라 그냥 글자»로 읽힌다 —
**어포던스에 대한 거짓말의 반대 방향**이다.

|---|---|
| 대상 | **`[해제]`(착용 중) 칩에만.** `[착용]`·`[잠김]`에는 넣지 않는다 |

확인하고 착수할 것. 걸리면 α를 0.34(`#BFAC8A`, L 0.4053, 1.66 : 1)로 내린다.

참고 지침을 옮긴 브리프에 *"현재 착용 중 카드는 「해제」 아웃라인 버튼"*이라고 적혀 있는데,

#### 7-2-1. 어디에 — **썸네일 바탕 스프라이트의 RGB에 구운 불투명 램프**

★★ **알파 `Image` 레이어를 새로 만들지 마라.** 이 창의 판은 α<1 겹 하나로 창 알파가 무너진다
(§4-3에서 실제로 그러고 있다). `design-art`의 형태 제약과 §4-4-0의 자기 정정이 **같은 결론**이다:
> 램프는 **RGB에 굽고 α는 어디에서도 1 미만이 되지 않는다.**

```

└ Thumb(Image) 의 sprite 를 「바탕색 → 글로우 중심색」 라디얼 램프로 교체.

  감쇠 = peak·(1−t)²   (UiChrome.RadialGlow 와 같은 제곱 곡선)   R = 39pt
  신규 Image = 0개.  기존 Thumb 한 장의 스프라이트만 바뀐다.
```

#### 7-2-2. ★ 내가 잰 두 가지 제약 — `design-art` 수치를 **실제 바탕에 대입**한 결과

`design-art`의 6.07 / 11.67은 **순수 색조 vs 카드**다. 화면에 실제로 나가는 것은
**peak 세기로 섞인 색 vs 그 썸네일 바탕**이라 값이 다르다. 그것을 쟀다:

| 글로우 | 바탕 | 구워진 중심색 | 중심 vs 바탕 | 판정 |
|---|---|---|---:|---|
| 영웅 0.63 | 보유 `CardSurfaceMuted` | `#7160A9` | **3.35 : 1** | 통과 |
| 전설 0.42 | 보유 `CardSurfaceMuted` | `#776743` | **3.21 : 1** | 통과 |
| 영웅 0.63 | **착용 중** `Flatten(AccentSurface, CardSurface)` | `#7C6AAE` | **2.79 : 1** | ★ **미달** |
| 전설 0.42 | **착용 중** 같은 면 | `#89754B` | **2.90 : 1** | ★ **미달** |

**제약 ①  착용 중 카드는 브라스 wash를 걷고 글로우가 그 자리를 쓴다.**
착용 중 썸네일은 지금 `Flatten(AccentSurface, CardSurface)` 브라스 wash가 깔려 있다. 그 위에
등급 글로우를 얹으면 **한 면에 워시가 두 장**이고 대비가 2.79 / 2.90으로 **하한 미달**이다.
peak를 올려 푸는 방법(영웅 0.75 / 전설 0.50에서 3.34 / 3.49 통과)은 **상태마다 peak가 갈라져
`design-art` 정본이 두 값이 된다** — 그건 색 담당의 단일 출처를 깬다.
⇒ **착용 카드의 썸네일 바탕을 `CardSurfaceMuted`로 되돌리고 글로우만 얹는다** → 3.35 / 3.21 통과.
「착용 중」은 여전히 **세 채널**이 말한다: 테두리 `CardBorderWorn`(4.09 : 1) · 메타 낱말
「착용 중」 · 하단 `[해제]` 칩(§6-3, 여기에 2pt 하이라이트가 더해진다).
★ **워시는 그 넷 중 가장 약한 채널이고**(§ 원 코드 주석도 *"착용 중은 이미 테두리 + wash +
메타 문구 셋이 말한다"*고 적는다) **하필 글로우와 같은 자리를 다툰다.** 지우는 쪽이 옳다.
※ 이것은 **기존 상태 신호를 하나 줄이는 변경**이므로 **리더 판정 항목으로 올린다.**

**제약 ②  잠긴 카드에는 글로우를 그리지 않는다.**
잠긴 카드의 아이콘은 `TextTertiary` **α0.34 실루엣**이다. 그 뒤에 글로우를 깔면:
```
실루엣 vs 글로우 중심 =  영웅 1.20 : 1   ·   전설 1.22 : 1
(글로우가 없을 때의 실루엣 vs 잠김 썸네일 ≈ 1.77 : 1)
```
**잠긴 카드의 유일한 형태 정보가 −32% 깎여 사실상 사라진다.** 반면 얻는 것은 장식뿐이고,
「이건 전설이다」는 리본(미보유에서도 안 흐린다) + 등급 낱말이 이미 말한다.
⇒ **글로우는 보유 카드에만.** 잠금 연출 정책(*"해금 전에 소재색을 미리 보여주면 잠금 연출이
무의미해진다"*)과도 같은 방향이다.
※ `design-art`가 더 낮은 peak로 실루엣을 살릴 수 있다고 재면 뒤집어도 된다 — **다만 그때는
「실루엣 vs 글로우 ≥ 1.77」을 함께 보여야 한다**(하한이 3.0이 아니라 「지금보다 나빠지지 않음」이다).

**밝은 잉크 아이콘은 안전하다**(보유 카드 기준): `CardIconInk` `#E8E2D6` vs 글로우 중심 =
영웅 **4.11 : 1** / 전설 **4.30 : 1** — 비텍스트 하한 3.0을 넘는다.

#### 7-2-3. 리본은 손대지 않는다 (`design-art` 지시 수용 + 내 검산)

*"카드 상단 등급 띠는 손대지 마라 — 영웅을 보라로 옮기면 회색조 인접 판정이 깨진다"*는 지시를
그대로 따른다. 내 §7 G5 기각(리본 4pt에 1pt를 얹지 않는다)과 **방향이 같고 이유는 다르다** —
둘 다 유효하므로 **리본에 손대는 제안은 두 근거를 모두 반박해야 한다.**

#### 7-2-4. 동시 발광 상한 6 · 애니메이션 0 — 배치 검산

`design-art` 제약: 동시 6개 · 애니메이션 0건. 이 창의 격자는 **2열 × 3행 = 정확히 6장**이고
(`CardColumns` 2 · 펫 6종), 세로 검산 `18 + 12 + 3×208 + 2×12 = 678 ≤ 684`로 **한 화면에 6장이
전부 들어간다.** 최악의 경우 6장 전부가 영웅/전설일 수 있으므로 **상한 6은 정확히 딱 맞는다.**
⇒ 다른 카테고리(장비 4섹션 × 6 = 24장)에서는 **스크롤로 화면 밖에 나간 카드도 램프를 굽고 있다** —
스프라이트는 캐시되고 애니메이션이 0이므로 프레임 비용은 0이지만, **캐시 키가 (등급 × 바탕색)
2×3 = 6개로 닫히는지** `perf-doc`이 확인할 것(아이템마다 굽지 말 것).

## 8. 장비별 개별 능력치 표시 — 사용자 신고 대응

> 사용자 신고 2026-09-06: ***"캐릭터 창에보면 각 장비들 능력치 표시도 안되어있음 전체 능력치만 표시됨"***

### 8-0. ★ 이건 신규 설계가 아니라 **미완 항목의 회수**다

`CharacterInfoWindow.BuildSlotRow`의 문서가 **이 자리를 이미 예약해 뒀다**:

> *"인계본은 이 자리에 **「집중력 +6」 같은 스탯 기여값**을 적는데, 그 4스탯은 아직 런타임이 0줄이다
> (§1-3). 없는 값을 화면이 주장하지 않도록 지금은 **등급 낱말**을 적는다 — 실재하는 사실이고
> **같은 칸을 쓴다**. **스탯이 들어오는 라운드(§8 4단계)에 교체한다.**"*

**그 라운드는 2026-09-05에 왔다**(`CharacterInfoWindow.Stats.cs` · `EquipmentStatRules.CurrentBuild()`).
조건은 충족됐고 **교체가 안 됐다.** 사용자가 신고한 것이 정확히 그 미완이다.
(이 저장소가 정본으로 못박은 *"「판정」과 「코드 반영」을 같은 칸에 적지 마라"*의 세 번째 실례다 —
§6-2의 `[잠김]` 1.00:1과 같은 형태.)

### 8-1. 데이터는 이미 다 있다 — **새로 계산하지 않는다**

| 필요한 것 | 이미 있는 공개 API | 비고 |
|---|---|---|
| 아이템 1개의 4스탯 기여 | **`EquipmentStatRules.Contribution(in StatSlotLoadout)`** | 주+부 합산, **세트 보너스 제외** |
| 그 아이템의 등급 | `ItemCatalog.Rarity(slot, itemIndex)` | |
| 그 아이템의 부스탯 방향 | `ItemCatalog.SubStat(slot, itemIndex)` | `NoStat(-1)`이면 없음 |
| 스탯 이름 | `EquipmentStatRules.StatName(stat)` | |
| 스탯 슬롯인가 | `EquipmentStatRules.IsStatSlot(slot)` | 외형 3슬롯은 false |

★★ **화면은 `Contribution`이 돌려준 `StatVector4`만 읽는다. 주스탯/부스탯을 다시 유도하지 마라.**
근거 셋:
1. `Evaluate`가 중앙 열의 `(+N)`을 **정확히 이 함수 네 번의 합**으로 만든다
   (`Contribution(head).Plus(eyes).Plus(neck).Plus(back)`). 같은 함수를 쓰면
   **카드 4장의 숫자 합 = 중앙 열의 (+N)** 이 산술적으로 보장된다.
2. 주와 부가 **같은 스탯인 아이템**(팩이 만들 수 있다)에서 `Contribution`은 자동으로 합치는데,
   화면이 따로 유도하면 «집중력 +10 · 집중력 +4» 두 줄이 뜬다.
3. 세트 보너스가 섞이지 않는다 — `Contribution`에는 원래 안 들어 있다(리더 지시 그대로).

**표시 순서**: `StatVector4`의 0이 아닌 칸을 **값 내림차순**으로 최대 2개.
★ 이 정렬이 항상 「주 → 부」인 것이 **증명된다**: 네 등급 전부에서
`MainStatBonus > SubStatBonus`(3>1 · 6>2 · 10>4 · 15>6). 주/부를 따로 알 필요가 없다.

| 등급 | 주스탯 | 부스탯 | 아이템 1개 합 |
|---|---:|---:|---:|
| 일반 | +3 | +1 | 4 |
| 희귀 | +6 | +2 | 8 |
| 영웅 | +10 | +4 | 14 |
| 전설 | +15 | +6 | 21 |

### 8-2. ★★ 결함 D-4 — **펫·머리·이펙트 카드는 스탯이 구조적으로 0이다**

`EquipmentStatRules.MainStatOf`: 스탯 슬롯은 **HEAD / EYES / NECK / BACK 넷뿐**이고
외형 슬롯(머리·이펙트·펫)은 `NoStat`다. `ItemCatalog`도 `category == Equipment`가 아니면
`SubStat = NoStat`을 넣는다. ⇒ **외형 18종의 `Contribution`은 4칸 전부 0이다.**

**사용자가 신고할 때 보고 있던 화면에 펫 2×3 격자가 있었다.** 그러니 스탯 표시를 붙이면서
"값이 0이면 안 그린다"로 짜면 **펫 카드 6장은 여전히 아무것도 안 뜨고, 같은 신고가 다시 올라온다.**

⇒ **확정: 기여가 0인 카드에는 「없음」을 명시한다. 절대 빈칸으로 두지 않는다.**
```
IsStatSlot(slot) == false  →  고정 문구 (예: 「능력치 없음」)
IsStatSlot(slot) == true 인데 4칸 전부 0  →  같은 문구
```
★ **문구 자체는 `design-narrative` 소관이다.** 내가 요구하는 것은 *"그 자리에 문장이 반드시
들어간다"*와 *"「아직 없음」처럼 미래를 암시하지 않는다"* 두 가지다 — 외형의 스탯 0은
플레이스홀더가 아니라 **구조적 사실**이고(그 함수 주석이 그렇게 못박고 있다), 「아직」이라고 쓰면
원칙 1 위반(오지 않을 것을 약속)이다.

### 8-3. 어디에 붙일 것인가 — 대가를 재고 **둘 다** 고른다

| 후보 | 얻는 것 | 대가 | 판정 |
|---|---|---|---|
| **좌측 슬롯 행 4개** | 항상 보임. 「내 4칸이 각각 얼마인가」 | 폭 74pt 한 칸뿐 → 한 스탯만 | **채택(주스탯)** |
| **카드 격자** | 고르기 **전** 비교. 42종 전부 | 세로 여유 0 | **채택(주+부)** |
| 상세 패널(컬럼 1 하단) | 넓다 | 세 번째 자리 = 갱신 경로 3벌 | **보류(P2)** |

**둘 다 붙이는 것이 중복이 아닌 이유** — 두 순간이 다르고 **담는 내용도 다르다**:
```
카드    = 「고르기 전」.  그 아이템이 주는 전부(주 + 부).  ← 지금 사용자가 하고 있는 일
슬롯 행 = 「걸친 뒤」.    이 칸이 내 주스탯에 주는 값 하나.
중앙 열 = 「합계」.        4칸 + 세트를 합친 결과.
```
★ **부스탯을 슬롯 행에 넣지 않는 것은 공간 때문만이 아니다.** 「모자 · HEAD」 행에 `매력 +4`가
뜨면 그 행이 자기 슬롯과 무관한 스탯을 말하게 되어 오히려 읽기가 나빠진다. 부스탯은
«이 아이템이 어디에 얹히는가»의 문제이므로 **아이템을 보는 자리(카드)**가 맞다.

★ 그리고 **부스탯이 카드에 있어야 하는 결정적 이유**: 같은 슬롯·같은 등급 아이템은
주스탯이 **완전히 같다**(일반 모자는 전부 `집중력 +3`). **두 아이템을 가르는 유일한 수치가
부스탯이다.** 카드에서 부스탯을 빼면 «비교»라는 이 화면의 목적 자체가 성립하지 않는다.

### 8-4. 어법 — **미래형 동사를 절대 쓰지 마라** (원칙 1)

중앙 열이 이미 쓰는 어법: `41 (+33)` — `+` 접두 부호. 괄호는 «총합에 붙는 주석»이라는
문맥이 만든 것이므로, **독립된 항목은 괄호 없이** 쓴다. 이것이 두 어법이 아니라 같은 어법이다.
```
중앙 열(총합에 붙는 주석)   41 (+33)
개별 항목(독립)             집중력 +10
```
- **착용 중이든 아니든 같은 숫자를 쓴다.** `Contribution`은 착용 여부에 의존하지 않는다.
  모드 전환이 없으므로 화면이 상태에 따라 다른 말을 할 수 없다.
- ★★ **「걸치면 +10」 / 「장착 시 +10」처럼 쓰지 마라.** 그 문장은 **거짓일 수 있다**:
  1. **같은 카테고리 자동 해제** — 이미 일반 모자(+3)를 쓰고 있으면 전설 모자(+15)를 걸칠 때
     실제 증가는 **+12**다. (`OnActionClicked`이 *"같은 카테고리의 …를 자동 해제"*를 로그로 남긴다.)
  2. **캡 40 클램프** — `Evaluate`가 `ClampStat`으로 자른다.
  3. **세트 보너스 변동** — 테마가 바뀌면 4스탯이 동시에 ±2 움직인다.
  ⇒ 표시는 **「이 아이템의 값」**이고 **「걸치면 오를 양」이 아니다.** 명사구만 쓴다.

**진짜 델타(걸치면 실제로 얼마 오르는가)는 이 라운드에 넣지 않는다.** 그것은 교체 시뮬레이션이
필요하고(현재 로드아웃에서 그 슬롯만 바꿔 `Evaluate`를 한 번 더 돌린다) **Core 작업**이다.
넣게 되면 자리는 **상세 패널**이고, 그때는 `걸치면 집중력 +12`처럼 **동사를 써도 참**이 된다.
지금 동사를 쓰면 그때까지 계속 거짓말한다.

### 8-5. 확정 — 좌측 슬롯 행 (세로 증가 **0pt**, 신규 `Text` **0개**)

기존 `SlotValue` 칸을 **그대로 재사용한다**(`BuildSlotRow` 문서가 *"같은 칸을 쓴다"*고 예약해 둔 그 칸).

```
현재:  x = Col1ContentWidth − 12 − 74 = 179,  w = 74,  y = −16,  h = 14
       FontLabel(12) · MiddleRight · 내용 = 등급 낱말 · 색 = RarityColor(rarity)
확정:  기하 전부 동일 ·                 내용 = 주스탯 항목 · 색 = UiChrome.Accent
```

| 항목 | 값 |
|---|---|
| 내용 | `Contribution` 1순위 항목 하나. 예 `집중력 +10` |
| 미착용 | `CharacterStatReadout.NoValue`(`—`) 그대로 — 이름 줄이 이미 「비어 있음」이라고 말한다 |
| 폭 검산 | 12pt에서 `관찰력 +15` ≈ **49.3 → 59.2 pt** ≤ **74 pt** (여유 ≈ 15pt). 그래도 `Ellipsize` 필수 |
| 색 | `UiChrome.Accent` on `CardSurface` = **6.83 : 1** (하한 4.5 통과) |

**등급이 사라지지 않는다** — 두 곳이 이미 말하고 있다:
1. **행 테두리** `row.Outline.color = UiChrome.RarityBorder(rarity)` — 손대지 않는다.
2. **캡션 줄**에 낱말을 덧붙인다: `모자 · HEAD` → **`모자 · HEAD · 일반`**
   폭 검산: 캡션 칸 = `265 − 46 − 74 − 12` = **133 pt**, 10pt에서 문자열 ≈ **85.2 pt**(여유 ≈ 48pt) ✓
   구분자 ` · `는 이 창의 기존 관례다(`SlotLabel` · `_detailMeta`가 이미 쓴다).
   ※ 낱말 결합 자체는 `design-narrative` 확인 대상이지만 **새 어휘가 아니다**(`ItemCatalog.RarityName`).

### 8-6. 확정 — 카드 (세로 증가 **0pt**. 비어 있던 오른쪽을 쓴다)

카드의 두 줄은 **왼쪽만 차 있고 오른쪽이 통째로 비어 있다**(둘 다 폭 160 전체를 잡아 두고 있다):
```
상태 줄   CardMetaY −125 · h15 · w160 · FontLabel(12) · MiddleLeft   「착용 중」 ≈ 39.4pt 사용
카테고리  CardCategoryY −143 · h13 · w160 · FontCaption(10) · MiddleLeft  「모자 · HEAD」 ≈ 54.6pt 사용
```

**확정 배치 — 오른쪽에 스탯 두 줄을 오른쪽 정렬로 넣는다.**

| | 왼쪽(기존) | 오른쪽(신규) |
|---|---|---|
| 상태 줄 | 착용 중 / 보유 / LV.20 — 폭 **160 → 80** | **1순위 항목**(= 주스탯) · 폭 **72** · `FontCaption`(10) |
| 카테고리 줄 | 모자 · HEAD — 폭 **160 → 80** | **2순위 항목**(= 부스탯) · 폭 **72** · `FontCaption`(10) |

```
신규 상수   CardStatWidth = 72          (두 줄 공통 → 오른쪽 끝이 한 줄로 정렬된다)
            CardStatX     = CardPadX + CardContentWidth − CardStatWidth = 101
축소        CardMetaWidth      160 → CardContentWidth − CardStatWidth − UiChrome.Space2 = 80
            CardCategoryWidth  (지금 CardContentWidth 직접 사용) → 같은 식으로 80
```

**폭 검산**(10pt 기준 추정. 한글 ≈ 10 · 숫자/기호 ≈ 5.5 · 공백 ≈ 2.8)

| 문자열 | 추정 | 칸 | 여유 |
|---|---:|---:|---:|
| `관찰력 +15` (주 최장) | 49.3 | 72 | +22.7 |
| `관찰력 +6` (부 최장) | 43.8 | 72 | +28.2 |

### 8-10. 산술이 닫히는지 확인 (구현 뒤 반드시 볼 것)

```
카드 4장(착용 중인 것)의 스탯 X 값을 전부 더한 값  ==  중앙 열 X행의 (+N)
```
`Evaluate`가 `EquipmentBonus = Σ Contribution(4슬롯)`으로 만들므로 **정의상 참**이다.
★ 그런데 **`Total`에는 세트 보너스가 들어가고 `(+N)`에는 안 들어간다** — 세트가 완성되면
화면의 `40 (+30)`에서 `BASE 8 + 30 ≠ 40`이 된다(차이 = 세트 +2). 이건 **이 라운드가 만든 것이
아니라 이미 있던 것**이고, 개별 표시가 들어오면 **사용자가 산수를 맞춰 보기 시작하므로
드러날 확률이 크게 오른다.**
⇒ **리더 판단 항목**: 세트 완성 시 세트 몫을 어디에 보이게 할 것인가.
자리 후보는 이미 있다 — 세트 패널 2행이 `FormatSetBonus()`로 「4부위 합계 +8」을 이미 말한다.
**내 권고**: 이 라운드에서는 건드리지 않는다(개별 표시와 독립 사안이고, 문구는
`design-narrative` 소관이다). **다만 「이미 있는 미결」로 등재해 둔다.**
