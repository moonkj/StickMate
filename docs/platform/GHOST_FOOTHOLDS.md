# 유령 발판 — 조사 결과와 판정 기록

담당 `dev-platform` · 최종 갱신 **2026-09-02** · 리더 판정 반영본

> **유령 발판**: 사용자 눈에는 아무것도 없는데 캐릭터가 그 위에 서 있는 것.
> 그리고 그 쌍둥이인 **발판 전멸**: 눈에 보이는 창이 멀쩡히 있는데 발판이 전부 사라져 캐릭터가 영원히 낙하하는 것.
> 둘은 같은 원인에서 나온다 — **가려짐 솔버가 "발판이 될 자격"과 "남의 발판을 가릴 자격"을 같게 본다.**

**이 문서의 코드가 없는 주장은 전부 "실기 미확인"이다. 이 개발 머신에 Windows가 없다.**

## 0. 전제 정정 — MS 스토어 제외 (2026-09-02)

이전 라운드 비용표는 `GetWindowBand` 항목에 **"MS스토어 심사"** 리스크를 달고 있었다.
사용자가 **"MS 스토어 제외, 목표는 스팀"**으로 확정했으므로 **그 칸은 소거된다.**
`product-strategy`·`security`에 물어야 한다던 후속도 함께 없어졌다.

**그런데 ③(`GetWindowBand`) 보류 판정은 바뀌지 않는다.** 보류는 세 다리로 서 있었고,
소거된 것은 하중을 받지 않던 세 번째 다리다.

| 다리 | 채널 의존? | MS스토어 제외 후 |
|---|---|---|
| ① 실기가 없어 **잔여 유령 발판의 양을 잴 수 없다** | 무관 | **그대로** |
| ② 비문서 export **누적 개수 1 → 2** (백신·EDR 휴리스틱) | **무관 — 백신은 사용자 머신에서 돈다** | **그대로** |
| ③ 스토어 정적 심사 | 의존 | **소거** |

→ **판정 불변: 보류.** (①②만으로도 보류가 성립한다.)

## 1. ① 착지 — `WS_EX_TRANSPARENT` 무조건 배제

**`Platform/Windows/WindowsFootholdFilter.ResolveWindowAlpha`**

승격 전에는 클릭 관통 비트를 **네 번째 갈래(레이어드 + 조회 실패) 안에서만** 읽었다.
그래서 **클릭 관통인데도 발판이 되는 조합이 셋** 남아 있었다.

| # | 조합 | 승격 전 | 승격 후 |
|---|---|---:|---:|
| 1 | `TRANSPARENT` 단독(레이어드 아님) | 1.000 채택 | **0.000 탈락** |
| 2 | `LAYERED\|TRANSPARENT` + `LWA_ALPHA`=255 | 1.000 채택 | **0.000 탈락** |
| 3 | `LAYERED\|TRANSPARENT` + 컬러키만 | 1.000 채택 | **0.000 탈락** |
| 4 | `LAYERED\|TRANSPARENT` + 조회 실패 | 0.000 탈락 | 0.000 탈락 (변화 없음) |
| — | 관통 비트가 **꺼진** 5개 칸 전부 | — | **한 칸도 바뀌지 않음** |

판정 근거 한 줄: **사용자가 클릭조차 할 수 없는 창은 사용자가 쓰는 창이 아니다.**
새 OS API 0개 — `exStyle`은 이미 읽고 있던 값이다.

**정직하게 남기는 과잉 제거 위험**: 클릭 관통이면서 *눈에는 보이는* 창(클릭 관통 모드의
데스크톱 위젯 등)도 함께 빠진다. 다만 그런 창은 대부분 `UpdateLayeredWindow` 픽셀별 알파를
함께 쓰므로 **승격 전에도 이미 4번 갈래에서 빠지고 있었다**. 새로 빠지는 것은 위 세 조합뿐이다.

### 왜 `W4`(컬러키 창은 불투명)를 죽이지 않았는가
`W4`와 신설 `W12`는 모순처럼 보이지만 **갈리는 축이 컬러키가 아니라 클릭 관통 비트**다.
`W4`가 잠그는 원래 함정(`LWA_ALPHA` 비트가 없을 때 `pbAlpha`를 그대로 알파로 읽어 컬러키 창을
통째로 지우는 것)은 승격과 **무관하게 그대로 살아 있다**. 두 테스트 모두 그 사실을 주석으로
달아 두었다 — "일관성"을 이유로 지우면 함정이 조용히 되살아난다.

## 2. ② 세션 잠금 감지 — **설계와 배선 지점만**(구현은 별도 라운드)

리더 지시대로 이번 라운드에서는 **코드를 넣지 않았다.** ①과 한 커밋에 섞으면 회귀가 났을 때
어느 쪽인지 못 가른다.

### 2-1. 무엇을 고치는가
잠금 화면이 떠 있는 동안에도 앱은 계속 돌고 **`footholdPollInterval`(0.3초)마다 창을 계속 열거한다**
(`Platform/FootholdPoller.Tick`). 그 시간에 열거되는 집합은 사용자가 잠금을 풀었을 때 볼 화면과
아무 관계가 없다. **유령 발판**(잠금 UI를 딛는다)과 **발판 전멸**(잠금 UI가 다 가린다)이
동시에 소거되고, 24시간 상주 앱의 유휴 비용도 함께 내려간다.

### 2-2. Windows — 문서화된 수단 우선

| 수단 | 무엇을 잡는가 | 성격 |
|---|---|---|
| **(A) `WTSQuerySessionInformationW`** (`wtsapi32.dll`)<br>`WTSSessionInfoEx` → `WTSINFOEX_LEVEL1.SessionFlags` | 세션 **잠금/해제** | 문서화 · 읽기 전용 |
| **(B) `OpenInputDesktop(0, FALSE, DESKTOP_READOBJECTS)` 실패** | 잠금 **+ UAC 보안 데스크톱** | 문서화 · 읽기 전용 |
| (C) `WTSRegisterSessionNotification` + `WM_WTSSESSION_CHANGE` | 이벤트 | **채택 안 함** |

**(A)를 주(主), (B)를 보(補)로 쓴다.** (B)만이 UAC 보안 데스크톱을 덮는다.
**(C)를 버리는 이유**는 `WindowsViewerPresenceService`가 `DisplayAsleep`을 포기한 이유와 **같다** —
창 프로시저를 가로채야 하는데 이 앱의 창은 UniWindowController 네이티브 플러그인이 소유한다.
(A)(B)는 둘 다 **폴링 조회**라 그 벽에 부딪히지 않는다.

**구현 함정 (기록만 — 지금 고칠 코드가 없다)**
- ★ **Win7 / Server 2008 R2 플래그 반전.** 그 세대에서는 `WTS_SESSIONSTATE_LOCK`/`UNLOCK`의
  의미가 **뒤집혀 있다**. 타깃은 Win10+이므로 Win10 의미를 쓰되, **{0,1} 밖의 값이나 조회 실패는
  전부 "모름"으로 보고 잠기지 않은 것으로 취급**한다(아래 보수 규칙).
- `WTSINFOEX`는 `Level`(=1) 검사 후에만 `LEVEL1`을 읽는다. 구조체 레이아웃을 틀리면
  **에러 없이 쓰레기 플래그**가 나온다 — 이 저장소가 싫어하는 "실패한 측정과 성공한 측정이
  똑같이 생긴" 형태다.
- 반환 버퍼는 반드시 `WTSFreeMemory`.
- `OpenInputDesktop`이 성공하면 반드시 `CloseDesktop`.

**보수 규칙(비대칭 대가)**: 조회 실패·해석 불가는 전부 **"사용자가 보고 있다"**로 간다.
오판의 대가가 비대칭이기 때문이다 — 잘못 멈추면 사용자가 캐릭터가 얼어붙은 것을 본다(신고 대상),
잘못 안 멈추면 전기를 조금 더 쓴다. `IsCloaked`·`hasVirtualScreen`·`MacViewerPresenceService`의
"작은 값을 믿는다"와 **같은 원칙**이다.

### 2-3. ★ macOS 대응물 — **"불필요"가 아니다. 축이 둘로 갈린다**

리더 질문: *macOS에 잠금 중 폴링을 멈출 수단이 있는가, 아니면 `layer != 0`이 이미 충분한가.*
**둘 다 아니다.** 문제가 두 축이고 `layer != 0`은 그중 하나만 닫는다.

| 축 | macOS 현재 | Windows 현재 |
|---|---|---|
| **유령 발판**(잠금 UI를 딛는다) | **닫힘** — 잠금 화면/화면 보호기는 0이 아닌 윈도우 레벨이라 `layer != 0` 필터가 후보에서 뺀다 | **열림** — 대응 규칙 없음 (→ 대장 `미해결_...z밴드...`) |
| **유휴 비용 + 낡은/전멸한 집합** | **열림** — `CGWindowListCopyWindowInfo`를 0.3초마다 그대로 계속 부른다 | **열림** |

즉 **`layer != 0`은 ②의 대체물이 아니다.** ②가 노리는 것은 두 번째 축이고, 그 축은 macOS도 열려 있다.

**macOS 수단 검토**

| 수단 | 판정 |
|---|---|
| `CGSessionCopyCurrentDictionary()` → `kCGSessionOnConsoleKey` | **공개 API**. 다만 **빠른 사용자 전환**에서만 false가 되고 **평범한 화면 잠금에서는 true로 남는다** — 우리가 원하는 사건을 못 잡는다 |
| 같은 딕셔너리의 `CGSSessionScreenIsLocked` | **비문서 키.** ③에서 `GetWindowBand`를 물린 것과 **정확히 같은 종류의 의존**이다. 한쪽만 허용하면 판정이 일관되지 않는다 → **배제** |
| `com.apple.screenIsLocked` 분산 알림 | 널리 쓰이지만 **Apple 문서에 없다** → 위와 같은 이유로 배제 |
| ★ **`CGDisplayIsAsleep`** | **공개 API이고 이미 배선돼 있다**(`MacOS/MacViewerPresenceService`, `ViewerPresenceSnapshot.DisplayAsleep`). 잠금은 잠금 지연 뒤 대개 디스플레이 슬립으로 이어지고, 화면 보호기도 마찬가지다 |

**결론 — macOS는 새 API 0개로 같은 라운드에 함께 닫힌다.**
정책은 하나로 두고, 플랫폼은 **각자 정직하게 알 수 있는 사실만** 채운다:

```
ShouldSuspendFootholdScan(snapshot) = snapshot.DisplayAsleep || snapshot.SessionLocked
```

여기서 드러나는 **역방향 비대칭이 재미있다** — 두 플랫폼이 서로의 사각지대를 덮는다:

|  | `DisplayAsleep` | `SessionLocked` |
|---|---|---|
| macOS | **채워진다**(`CGDisplayIsAsleep`) | 문서화된 수단 없음 → 항상 false |
| Windows | **항상 false**(창 프로시저가 필요해 포기, 그 파일 문서 참고) | **채워진다**(A+B) |

### 2-4. 배선 지점 (파일과 줄 단위)

| # | 파일 | 무엇을 |
|---|---|---|
| 1 | `Platform/ViewerPresence.cs` | `ViewerPresenceSnapshot`에 `SessionLocked` 추가. **생성자를 양쪽 구현이 같은 라운드에 함께 고쳐야 한다**(그것이 플랫폼 동시 검토 규칙의 실물) |
| 2 | `Platform/Windows/WindowsViewerPresenceService.cs` | (A)+(B) 조회 추가, `SessionLocked` 채움 |
| 3 | `Platform/MacOS/MacViewerPresenceService.cs` | `SessionLocked = false`를 **명시**하고 근거를 주석으로(비문서 키를 배제한 판단) |
| 4 | **신규** `Platform/SessionVisibilityPolicy.cs` | 순수 판정 한 함수. **OS 호출 0줄** — `FullscreenSuspendPolicy` 사고(정책이 `Platform/MacOS/` 안에 있어 Windows가 못 불렀다)의 재발 방지 |
| 5 | `Platform/FootholdPoller.Tick` | 판정이 참이면 `Poll()`을 건너뛴다. **캐시는 그대로 둔다**(비우면 그 순간 발판 전멸 = 고치려던 것을 스스로 만든다) |
| 6 | `Platform/FootholdPoller` | 참→거짓 전이에서 **`PollImmediately()` 1회**. 없으면 잠금 해제 직후 최대 0.3초 동안 낡은 집합으로 판정한다 |
| 7 | `Tests/EditMode/PlatformParityAuditTests.cs` | 새 분기이므로 대장에 항목 추가(정책이 중립 위치인지 + 양쪽이 스냅샷을 채우는지) |

**★ 5·6이 `Platform/` 안이라 이 설계는 전부 `dev-platform` 범위에서 닫힌다.**
`Core/StickmanAgent.ApplySuspendDecision()`에 **세 번째 축**으로 얹는 더 강한 변형(프레임 제출까지
멈춤)도 가능하지만 그것은 `Core/`라 **리더의 파일 배정이 필요하다**. 또 `Suspend()`/`Resume()`은
캐릭터를 숨기는 경로라 부작용 검토(`debugger`)가 함께 필요하다 — 이번 권고에 넣지 않았다.

## 3. ③ `GetWindowBand` — **보류**(리더 판정 2026-09-02)

보류 사유를 **문장 그대로** 남긴다. 나중에 "왜 안 넣었지"라고 묻는 사람에게 답이 여기 있어야 한다.

> **누적 개수가 1 → 2가 된다. 백신 휴리스틱이 세는 것은 정확히 이 누적 개수.**

실측 확인(2026-09-02, `Platform/Windows/` 전수): 비문서 export 의존은 지금 **정확히 1건**이다 —
`InternalGetWindowText`(제목 조회 블로킹 제거용). 나머지 `DllImport`는 전부 문서화된
user32/kernel32/dwmapi/advapi32/shell32 함수다.

그리고 **잴 수 없는 것을 위해 의존을 늘리지 않는다**: ②가 잠금 구간과 UAC를 덮고 나면 잔여가
얼마나 남는지를 먼저 알아야 하는데, **이 머신에 Windows가 없어 그 잔여를 지금 잴 수 없다.**

**재개 조건**: ② 착지 → 실기에서 `[발판진단]` 로그로 잠금/UAC 구간의 잔여 유령 발판 확인 →
그때 대장 항목 `미해결_Windows에는_z밴드_필터가_없어_잠금화면_유령발판이_열려_있다`를 다시 연다.

## 4. 잔여 비대칭 · 미확인 목록 (파지 않고 기록만)

| 항목 | 상태 |
|---|---|
| **macOS: 레벨 0의 클릭 관통 `NSWindow`** | `CGWindowList`에는 창별 "클릭 관통" 플래그가 **없다**. 관례상 그런 창은 0이 아닌 레벨에 놓이므로 `layer != 0`이 사실상의 대응물이지만 **완전한 1:1이 아니다.** Windows의 ①에 정확히 대응하는 macOS 필터는 존재하지 않는다 — **수단이 없어서**이지 안 한 것이 아니다 |
| **macOS: 잠금 중 layer 0 창이 `kCGWindowListOptionOnScreenOnly`에 남는가** | **미확인.** 남으면 잠금 중 발판 집합이 그대로 유지되고, 빠지면 잠금 중 발판이 전멸한다 — ②의 효과 크기가 여기서 갈린다. 사용자 머신을 잠그는 실험이라 이 라운드에서 하지 않았다 |
| **⑤ Mission Control 중 앱 창 bounds 변형** | **미확인 · 이번 라운드 대상 아님.** "유령 발판"이 아니라 **"발판 순간이동"**이라 형태가 다르다(창이 사라지는 것이 아니라 좌표가 바뀐다). Mission Control 동안 `CGWindowList`가 축소 배치된 bounds를 보고하면 캐릭터가 한 프레임에 순간이동하고, 종료 시 되돌아온다 |
| **① 실기 확인** | **미확인.** Windows가 없다. 확인 수단은 `[발판진단]` 로그의 알파 탈락 사각형 목록 — 승격 후 클릭 관통 창이 그 목록에 나타나야 한다 |

### ★ 최종 `xcheck` 재실행이 트리 문제로 실패했다 — 원인과 격리
