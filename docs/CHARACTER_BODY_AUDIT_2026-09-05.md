## 2. ① 머리 — 「배율 0.35 링 포함 잉크 원반 1.184 R」

### 전제 (장비 쪽)
`r17_model.py:32` `HEAD_R_COVER = 1.0 + ONE_PT_R[0.35]/2 = 1.1842 R` — H-2(모자 착용선) 판정의 분모.
`r17_model.py:33` `HEAD_R_SHIP = M16.HEAD_OUTER_R = 1.1432 R` — N-1·외알안경·망토가 쓰는 「출하 원반」.

### 정본 실측
링 두께는 **굽기와 런타임에서 서로 다른 하한**을 받는다. 이 두 단계를 합쳐야 정답이 나온다.

```
굽기  (Editor/SceneBootstrapper.cs:744, :727-744 주석)
      baked = max(0.063 × 0.75,  2pt/35.25 = 0.0567376) = 0.0567376 유닛   ← 2pt 하한이 이긴다(의도된 예외)
      프리팹 실측 HeadOutline widthCurve = 0.056737587  (주석 :176이 같은 값을 적어 두었다)
      ⇒ 실효 계수 = 0.0567376 / 0.75 = 0.0756501     (명목 0.063이 아니다)

런타임 (Core/StickmanAgent.cs:1307-1311, MarkHeadRingAsFillOutline :1200)
      inkCore = max(baked × 배율/0.75,  MinFillOutlineScreenPoints 1pt)
              = max(0.0756501 × s,      1/PPU)
      막(InkMembrane)은 오늘 0이라 drawn = inkCore (비트 동일)
```

머리 **잉크** 바깥 반경 = `1 + inkCore / 2 / (0.22 × s)`:

| 창 높이 | PPU | 하한 교차 배율 s\* | 0.35 | 0.60 | 0.75 | 1.00 |
|---:|---:|---:|---:|---:|---:|---:|
| **846**(굽기 기준) | 35.25 | 0.3750 | **1.18421** | 1.17193 | 1.17193 | 1.17193 |
| 982(UX 실측 창) | 40.92 | 0.3231 | 1.17193 | 1.17193 | 1.17193 | 1.17193 |
| 1440 | 60.00 | 0.2203 | 1.17193 | 1.17193 | 1.17193 | 1.17193 |
| 2160 | 90.00 | 0.1469 | 1.17193 | 1.17193 | 1.17193 | 1.17193 |

⇒ **머리 잉크 원반은 사실상 항상 1.171932 R이고, 「창 높이 ≤ 906 pt」 & 「배율 < s\*」인 좁은 구석에서만 최대 1.18421 R까지 커진다.**
(906 pt = `24 / (0.0756501 × 0.35)`.)

### 일치 여부
- **1.184 R = ✅ 맞다.** 이 값은 **도달 가능한 최대 머리**이고, 모자 덮임(H-2)처럼 *가장 큰 머리를 가려야 하는* 판정에는 정확히 이 값을 써야 한다.
  장비 쪽이 스스로 *"모자 덮임 판정은 큰 쪽"*(`r17_model.py:425`)이라고 적은 것도 옳다. **여기는 고칠 것이 없다.**
- **1.1432 R = ❌ 틀렸다.** `r16_model.py:65`가 `body_w(0.063, 1.0)`으로 **명목 0.063에 1 pt 하한**을 걸었다.
  프로덕션은 **굽기에서 2 pt 하한을 먹은 값**을 쓰므로 실효 계수가 0.0756501이다. 차이는

```
1.171932 − 1.143182 = 0.028750 R  =  0.167 pt @0.75/PPU 35.25  (0.194 pt @PPU 40.92)
```

작다. **그런데 이 0.029 R이 하필 「여유가 0.03 R」인 규칙(N-1)의 분모라서 부호를 뒤집는다.**

### 조치 (숫자로)

| 대상 | 지금 | 고칠 값 | 영향 |
|---|---|---|---|
| `r16_model.W_RING_R` | `body_w(0.063, 1.0)` = 0.28636 R | **0.343864 R**(= `max(0.0756501×s, 1/PPU) / (0.22 s)` @0.75) | `HEAD_OUTER_R` 1.1432 → **1.171932** |
| `HEAD_R_COVER` | 1.1842 | **불변** | — |
| N-1 기준선 | −1.143 | **−1.17193** | §3 |

★ **왜 이 오차가 하필 여기서 나왔는지 남긴다** — `SceneBootstrapper.cs:727-744`가 *"머리 링의 하한은 굽기 시점에는 2.00 pt 그대로다(의도된 예외)"*를
길게 설명하고 있고, M6(채움 경계선 1 pt)이 바꾼 것은 **런타임 하한 하나뿐**이다. **「M6 이후 링은 1 pt」만 읽고 명목에 그 하한을 걸면 정확히 이 값이 나온다.**
같은 함정을 오늘 오전 내 문서도 v1에서 밟았다(§1 자기 결함 보고 2번).

## 3. ② 목 — 「0.175 R = 1.0 pt」

### 전제
`r17_model.py:37` `NECK_LEN = HEAD_R_SHIP + SH = 0.175 R`, 규칙 **N-1** = *"목 아이템의 착용선은 머리 잉크 원반 밑(−1.143 R) 아래이고 어깨선(−1.318 R) ±0.20 R 안. 목 길이는 0.175 R = 1.0 pt라 「목 하단」 = 어깨선이다."*

### 정본 실측

```
어깨 부착점        = (1.7646944 − 2.0546944) / 0.22 = −1.318182 R   (StickmanMetrics BaselineShoulderRatio 분자)
머리 잉크 원반 밑   = −1.171932 R                                    (§2)
드러난 목(잉크)    = 1.318182 − 1.171932 = 0.146250 R = 0.851 pt @0.75
```

장비 값 0.175 R(= 1.018 pt)과 **0.02875 R(0.167 pt) 다르다 — 실제 목이 16.4 % 짧다.**

### 일치 여부 — ❌ 틀렸다. 그러나 **N-1 규칙 자체는 옳다**

N-1은 「짧은 목 때문에 생긴 문제」가 아니라 **짧은 목의 정직한 결과**다. 0.85 pt짜리 자리에는 어떤 띠도 감을 수 없으므로
*"「목 하단」 = 어깨선"*이라는 재정의가 **유일하게 성립하는 정의**다. 그 판단은 그대로 유지한다.
**틀린 것은 규칙이 아니라 상수 하나이고, 그 상수가 여유 0.03 R 짜리 세 아이템의 부호를 뒤집는다.**

### 조치 — N-1 기준선 −1.143 → **−1.17193**, 그리고 3종의 `dy`

| 아이템 | 착용 조각 윗변(현행 설계) | 새 기준(−1.17193 − 0.03 = **−1.20193**) 대비 | 필요한 `dy` 변경 |
|---|---:|---|---|
| **나비넥타이**(날개 윗변) | −1.171 (`dy +0.30`) | ★ **여유 −0.0009 R** — 사실상 접선, 명목상은 턱 잉크 안 | `dy +0.30 → **+0.269**` (−0.031 R) |
| **펜던트** | −1.173 (`dy −0.055`) | 여유 **+0.0011 R**(의도 0.03) | `dy −0.055 → **−0.084**` |
| **반다나** | −1.173 (`dy −0.175`) | 여유 **+0.0011 R**(의도 0.03) | `dy −0.175 → **−0.204**` |
| 줄무늬타이 | −1.300 | 여유 +0.098 R | **불변** |
| 목도리 | −1.471 | 여유 +0.269 R | **불변** |
| 방울목걸이 | −1.395 | 여유 +0.193 R | **불변** |

검산: 나비넥타이 매듭 윗변 −1.681 + 0.269 = **−1.412 R**, 어깨선과 **−0.094 R** → 밴드 ±0.20 안 ✅.
펜던트·반다나는 아래로 0.029 R 내려갈 뿐이라 어깨 밴드 안에 그대로 있다 ✅.

★ **여유가 커지는 쪽(무변경)**: 외알안경 알 오른끝 +1.070 R은 y = +0.185의 머리 현 반폭이 1.128 → **1.157**로 넓어져 오히려 안전해진다.
구슬 중심 (1.204, −0.761)은 중심거리 1.4244, 잉크 안쪽 가장자리 1.2525 > 1.17193 → **깨끗이 밖** ✅.
망토 무대 부착 상단 −1.143 R은 실제 원반 밑보다 0.029 R **안쪽**이지만 뒤층(`SortBack`)이라 **가려진다 — 오히려 틈이 없어 좋다. 무변경 권고.**

### 「손대면 비용이 얼마인가」 — 목을 늘리는 안 (묻길래 재 봤다. **권고하지 않는다**)

목을 「띠를 감을 수 있는 길이」로 만들려면 최소 한 띠 높이(망토 옷깃 띠 0.44 R)가 필요하다:

⇒ **권고: 목은 건드리지 않는다.** 대신 §3의 상수 1건 + `dy` 3건으로 닫는다. **비용 = 설계 문서 숫자 4개.**

## 4. ③ 발목 −9.3395 R (망토 밑단 기준)

### 전제
`§14-10-7 (2)` — *"다리 끝점 = 루트 로컬 y 0 = 발바닥선 = **−9.3395 R**(HeadCenterY/R). 발은 없다(끝점이 곧 발목). 긴 밑단 = 발목 + 다리 획 반폭 0.285 = −9.0545 R."*

### 정본 실측

```
머리 중심 높이(발 기준) = 1.35(몸통상단) + 0.4846944(접지보정) + 0.22(머리반경) = 2.0546944 유닛
                          ↑ Core/StickConfig.cs:1873 · StickmanMetrics BaselineHeadCenterRatio 분자와 동일
발바닥선(루트 y=0) = −2.0546944 / 0.22 = **−9.339520 R**
다리 획 = 0.12 × 1.045 × s / (0.22 s) = **0.570000 R** → 반폭 **0.285 R**   (하한 미작동 구간: s ≥ 0.4525)
긴 망토 밑단 = −9.339520 + 0.285 = **−9.054520 R**
```

배율 무관(전부 s로 약분된다). `verify` BACK 하한 −9.3395도 같은 값이다.

### 일치 여부 — ✅ **정확히 맞다** (Δ < 1e−4 R). 다만 **두 가지를 문장에 붙여야 한다**

1. **−9.3395 R은 「접지한 쪽 발」이다.** `footLift = max(leftDrop, rightDrop) − SpecHipY`이므로 **낙차가 큰 다리만** y=0에 닿고 반대쪽 발끝은 그보다 위다.
   밑단 클램프(B-3)는 지면 기준이라 이 구분이 필요 없다 — **클램프에는 −9.3395가 맞다.** 다만 *"두 발이 −9.3395에 있다"*로 읽으면 틀린다.
2. **잉크는 그보다 0.285 R 더 내려간다.** 다리 끝점 −9.3395 + 둥근 캡 반폭 → **잉크 최저 −9.6245 R**. 즉 캐릭터 잉크는 접지선보다 1.66 pt 아래까지 있다.
   장비가 밑단을 −9.0545에 둔 것은 **캡 위**여서 발끝 잉크를 덮지 않는다 — 옳은 선택이다. 숫자를 그대로 승인한다.

### 조치
**없다.** ③은 통과. 위 두 문장만 §14-10-7에 각주로 붙일 것을 권고(리더 → design-equipment).

## 5. ④ 모자 2층 — 단색 잉크 원반 머리에서 「머리 뒤」가 성립하는가

> ★ 왕관 골 노출 0 px은 `persona-immersion` 실기 확인 결과로 **기지 사실**이다. 다시 재지 않았다.

### 전제

### 일치 여부 — ✅ **챙은 성립한다.** ⚠ **왕관은 다른 물건이다**

**(가) 챙 — 성립한다. 이유는 「머리 밖에서 두 반쪽이 하나로 이어지기」 때문이다.**
머리 현 바깥(|x| > 1.03~1.05 R)에서는 **먼 쪽 반과 가까운 쪽 반이 둘 다 보인다.** 자른 선을 안 그리므로 둘은 **완전한 렌즈꼴 하나**로 합쳐지고,
머리 안쪽에서만 위 반쪽이 사라진다. 그것이 정확히 「챙이 머리 뒤로 지나간다」의 그림이다.
**머리에 테두리가 없다는 사실이 오히려 유리하다** — 잉크 단색 원반이므로 챙과 머리의 경계는 색 경계 하나뿐이고,
챙의 바깥 호 윤곽이 **잉크색**(R19 C-1)이라 머리 실루엣과 **한 덩어리 잉크 윤곽**으로 이어진다. 참고 이미지 계열의 문법 그대로다.

**(나) 배율에 따른 열화 — 숫자로 남긴다.**

| 조각 | 잉크 박스 높이 | @1.00 | @0.75 | @0.35 | 그 배율의 1 pt |
|---|---:|---:|---:|---:|---:|
| 야구모자 `B2.far` | 0.274 R | 2.13 pt | 1.59 pt | **0.74 pt** | 0.1289 / 0.1719 / **0.3684 R** |
| 중절모 `B2.far` | 0.332 R | 2.58 pt | 1.93 pt | **0.90 pt** | 〃 |

⇒ **배율 0.35에서 먼 쪽 반은 자기 윤곽선(1 pt = 0.3684 R) 하나로 대체된다**(박스보다 획이 굵다).
채움 폭 0이지만 **실루엣은 유지된다** — 머리 밖으로 나오는 가로 폭이 야구모자 각 0.791 R(2.15 pt) · 중절모 각 1.011 R(2.74 pt)로 남는다.
0.35에서 「챙이 잉크 선 한 가닥이 된다」는 것은 그 배율에서 68/87 조각이 겪는 것과 같은 열화이고, **모자로 읽히는 것은 앞층(관 + 가까운 챙)이 맡는다.** 감수 가능.

**(다) 왕관 뒷벽은 성립하지 않는다 — 다만 그것은 결함이 아니라 다른 물건이다.**
머리는 **단색 잉크 원반**이라 「머리가 왕관 **안쪽**에 들어가 있다」는 깊이 정보를 **원리적으로 전달할 수 없다**(테두리도 명암도 없다).
봉우리 사이로 보이는 것은 뒷벽 색(SH `#2B220A`)이고, 그것은 「머리가 보인다」가 아니라 「왕관 안쪽 벽이 보인다」다.
노출 0 px(기지 사실)까지 합치면 **뒷벽은 시각적으로 앞층 채움과 구별되지 않는다.**
⇒ 조형 판정: **뒷벽을 남기는 것은 무해하고 오히려 안전하다**(봉우리 사이에 배경이 뚫리지 않는다). 다만 문서에서
*"봉우리 사이로 머리가 보인다"*는 **근거로 쓰지 마라** — 우리 머리에는 그걸 보여 줄 수단이 없다.

**(라) ★ 새로 생기는 레이어 동률 — 지금은 0건, 조건은 살아 있다**

`BODY_ENVELOPE_FOR_EQUIPMENT.md` §3 체크 **C-6**(동시착용에서 동률이 새로 생기는가)에 걸린다.

```
BACK 채움 −2 / 윤곽 −1        (AccessoryShapeBuilder SortBack)
HEAD 뒤층 채움 −2 / 윤곽 −1   ← R19가 새로 얹은 것. 같은 값이다
```

**전수 확인(좌표 기준, `r19_coords.txt`)**: HEAD 뒤층 조각의 y 하한은 왕관 뒷벽 **+0.05 R**(야구·중절 챙은 +0.35 이상),
BACK 조각의 y 상한은 망토 무대 부착 **−1.143 R**. **간격 ≥ 1.19 R(6.9 pt @0.75) → 실제 겹침 0건.**
⇒ **지금 고칠 것은 없다.** 되살아나는 조건 둘: (a) 머리를 덮으며 **아래로 내려오는** HEAD 아이템(후드·베일·긴 밀짚모자 뒤챙),
(b) 어깨 **위로 올라오는** BACK 아이템(후광·세운 깃). 둘 중 하나가 생기면 같은 `sortingOrder` 두 `LineRenderer`의 앞뒤는 **정의되지 않는다.**
선택지는 리더 몫이다: (ㄱ) 그때 가서 잰다(오늘 비용 0) / (ㄴ) 지금 HEAD 뒤층에 **BACK보다 뒤인 자리(채움 −4 · 윤곽 −3)**를 준다 —
높이가 겹치지 않으므로 오늘 그림은 1 px도 안 바뀌고, 미래의 동률이 원천 차단된다.

## 6. ⑤ 눈 — 조건부 「반대쪽 눈」과 r 0.1719 R

### 전제
`§14-6 #12` · `E-1` — *"한쪽 가리개(외알안경·안대)는 보는 사람 기준 오른쪽 눈에. 반대쪽 눈은 **그 아이템을 착용했을 때에만** 흰 원반
(r 1 pt = 0.1719 R, 중심 (−0.46, +0.107) R)으로 그린다. 평소엔 눈 없음."* → R20에서 **±0.56 R**로 이동.

### 정본 실측 — ★ **이 규칙은 신규가 아니다. 프로덕션에 이미 있다**

```
Interaction/AccessoryShapeBuilder.cs:1978   sink.Add(new Shape("MonocleEye", DrawnEye(rig, -1f), …));
Interaction/AccessoryShapeBuilder.cs:2030   sink.Add(new Shape("PatchEye",   DrawnEye(rig, -1f), …));
:140  DrawnEyeOffsetRatio  = 0.62      :152  DrawnEyeRadiusRatio = 0.33
:598  MonocleOffsetRatio   = DrawnEyeOffsetRatio     ← 알은 +0.62, 눈은 −0.62
:1052 <param name="sign">−1 = 진행 반대쪽(= 가려지지 않은 눈). 지금 두 소비자 모두 −1이다.</param>
```

⇒ **「외알안경/안대를 낄 때만 눈 하나가 생긴다」는 이미 출하 중인 동작이고, 알이 +x·눈이 −x인 배치도 이미 프로덕션 관례다.**
사용자 지적 [3][4](*"외눈 안경은 오른쪽에 착용 … 착용시에만 반대쪽 눈"*)는 **새 요구가 아니라, 인계본 기하로 갈아 끼우면서 잃어버린 우리 관례로 돌아오라는 것**이었다.
R17의 「반전」과 「조건부 부활」은 **복귀**다 — 방향은 옳다.

### 일치 여부

**(가) 「이상하지 않은가」 — 이상하지 않다. 다만 규칙 문장을 이렇게 써야 일관된다.**

지금 문장(*"외알안경 착용 시에만 눈을 그린다"*)은 예외처럼 읽힌다. 조형 논리로 다시 쓰면 예외가 아니다:

> **눈은 언제나 없다. 가리개가 한쪽만 덮으면, 덮이지 않은 쪽에 눈이 드러난다.**

이 문장이면 EYES 6종이 한 규칙 아래 들어온다 — 양안 안경 3종(선글라스·동그란안경·고글)은 R20의 GLASS 판이
**앞·뒤 눈 자리를 모두 덮으므로**(`§14-10-9` ②) 눈을 그리든 안 그리든 보이지 않는다. 즉 「가리개가 양쪽이면 눈은 안 보인다」가 자동으로 성립한다.
**«얘만 왜»가 사라진다.** 근거는 조형이다: 머리가 얼굴 없는 잉크 원반이므로 **「가린다」는 동사에 목적어가 필요하고, 한쪽 가리개는 그 목적어를 스스로 만들어야 한다.**

**(나) 위험 하나 — 눈이 하나면 「윙크」로 읽힌다. 그것을 막는 것은 대칭뿐이다.**
프로덕션은 `DrawnEye`와 알이 **같은 y**(`GlassesLocalY(rig)`)를 쓴다. R20 좌표는 그렇지 않다:

| | x | y |
|---|---:|---:|
| 알(`monocle.CB0`) 중심 | **+0.560 R** | **+0.185 R** |
| 드러난 눈(`monocle.ExposedEye`) 중심 | **−0.560 R** | **+0.107 R** |

x는 정확히 거울(±0.560 ✅) — **R20이 R17c의 대칭을 유지한 것은 옳다.** 그러나 **y가 0.078 R 어긋난다**(0.45 pt @0.75 · 0.60 pt @1.00 — 1 px 미만이라 눈에는 안 보인다).
인계본 아이콘이 알과 눈을 다른 높이에 그렸기 때문이고, 우리 관례(같은 y)와 다르다.
⇒ **권고: 눈 y := 알 y = +0.185 R.** 비용 상수 1개, 그림 변화 < 1 px, **얻는 것은 「두 눈 자리는 대칭이다」라는 불변식**이다(안대·미래 가리개에도 그대로 적용된다).

**(다) ★ r 0.1719 R을 「R 고정」으로 굳히면 안 된다 — 규칙이 자기 근거를 배신한다.**
0.1719 R은 **「배율 0.75에서의 1 pt」**다. 그 근거는 *"윤곽 없는 채움 원반이 1×에서 남는 최소 r = w(1 pt)"*(`r19_model.py:54`)인데,
값을 R에 고정하면 **다른 배율에서 그 근거가 깨진다**:

| 배율 | 1 pt의 R 환산 | r 고정 0.1719 R → 지름 | 판정 | pt 하한판 `r = max(0.1719 R, 1 pt)` |
|---:|---:|---:|---|---|
| 0.35 | 0.3684 R | **0.93 pt** | ★ **1 px 미만 — 회색 얼룩** | 지름 2.00 pt (머리 잉크 지름의 **31.4 %**) |
| 0.60 | 0.2149 R | 1.60 pt | 아슬아슬 | 2.00 pt (18.3 %) |
| 0.75 | 0.1719 R | 2.00 pt | ✅ 정확히 근거대로 | 2.00 pt (14.7 %) |
| 1.00 | 0.1289 R | 2.67 pt | ✅ | 2.67 pt (14.7 %) |

**「사라진다」보다 나쁜 것이 「반쯤 남는다」**이다 — 0.93 pt짜리 흰 원반은 검은 머리 위에서 **AA 회색 점**이 되어 잉크가 더러워 보인다.
같은 문제가 **구슬 `monocle.CB3`(r 0.1719 R, 같은 근거)**에도 그대로 있다.

⇒ **권고(둘 중 하나를 리더가 고른다)**
- **(A) pt 하한판** `r = max(0.1719 R, 1 pt)` — 「1 px에서 살아남는다」는 근거를 전 배율에서 지킨다. 대가: 배율 0.35에서 눈 지름이 머리 잉크 지름의 **31.4 %**(큰 만화 눈). 배율 0.35의 얼굴 폭이 애초 6.4 pt라 **실기 캡처로 확인해야 한다 — 미확인.**
- **(B) R 고정 유지** — 0.35에서 눈과 구슬이 사라지는 것을 **명시적으로 감수**한다(그 배율에서 이미 68/87이 사라진다). 대신 문서에서 *"r = 1 pt"*라는 표기를 **버리고** *"r = 0.1719 R(배율 0.75의 1 pt에서 유래, 그 아래 배율에서는 소멸)"*로 정직하게 고쳐 적는다.

**나는 (A)를 권한다** — 이유는 조형이 아니라 정직성이다. 지금 문서는 (B)의 값을 쓰면서 (A)의 근거를 적고 있다.

**(라) 비율 자체는 우리 머리와 맞는가 — 맞다.**

| 자 | 지름 / 머리 잉크 지름(2.34386 R) |
|---|---:|
| 옛 프리팹 눈동자(r 0.0818 R, `BakeEyes=false`로 죽어 있음) | 7.0 % |
| **제안 r 0.1719 R** | **14.7 %** |
| 현행 `DrawnEyeRadiusRatio` 0.33 R | 28.2 % |

현행 0.33 R은 **얼굴 폭의 1/4을 한 눈이 먹는다** — 잉크 원반 머리에서 「구멍」이 그만큼 크면 머리가 도넛으로 읽히기 시작한다.
**14.7 %는 옛 눈동자와 현행 사이의 합리적 자리**이고, 감소 방향(−48 %)은 조형적으로 옳다. **크기 비율은 승인한다.**

### 조치
1. 규칙 문장 재작성(위 (가)) — **본체 소관이라 내가 낸다**: *"눈은 언제나 없다. 가리개가 한쪽만 덮으면 덮이지 않은 쪽에 눈이 드러난다."*
2. 눈 y +0.107 → **+0.185**(알과 같은 높이). 리더 판단.
3. r 정의를 (A)/(B) 중 하나로 **못박는다**. 리더 판단.
4. `DrawnEyeOffsetRatio 0.62 → 0.56` · `DrawnEyeRadiusRatio 0.33 → 0.1719`(또는 (A)판)는 **프로덕션 상수 2개 변경**이다 — coder 배정 필요. 색도 `tone: Accent` → **잉크 대비색**(검 머리 `#FFFFFF` / 흰 머리 `#252829`)으로 바뀐다.
5. **미확인**: 초상화(`CharacterPortraitStage`, `DrawEyes = false`)에서도 조건부 눈이 같은 좌표로 나오는지 — 두 렌더러가 같은 `Shape`를 쓰므로 나올 것으로 판단하나 **실기 미확인**.

## 7. ⑥ 우클릭 부채꼴 — 실루엣을 지키는 최소 안쪽 반지름

> `docs/UX_RIGHTCLICK_FAN_MENU.md` §1-2가 **앵커 = 몸 중심**으로 확정했다. **그 결정과 충돌하지 않는다 — 오히려 독립적인 자로 재확인했다**(§7-4).

### 7-1. 본체가 앵커에서 차지하는 자리 (중립 자세 · 잉크 기준)

앵커(몸 중심) = 발바닥선 위 `TotalHeight/2` = 머리 중심 좌표로 **y = −4.16976 R**.

| 방향 | 무엇이 정하는가 | 앵커에서의 잉크 반경 E |
|---|---|---:|
| **아래 270°** | 접지발 끝 (±0.757, −9.3395) + 다리 획 반폭 0.285 | **5.5099 R** ← 최대 |
| **위 90°** | 머리 잉크 원반 꼭대기 (+1.17193) | **5.3417 R** |
| 대각 45/135° | 팔 손끝 (±2.191, −3.930) + 팔 획 반폭 0.2375 | 2.4419 R |
| 옆 0/180° | 몸통 반폭 | 0.2613 R |
| 대각 225/315° | 몸통 모서리만(다리는 45°보다 훨씬 가파르다 — 최근접 0.651 R > 획 반폭 0.285) | 0.3694 R |

★ **캐릭터는 앵커 기준으로 위아래로만 길다**(5.34 / 5.51 vs 옆 0.26). 이것이 몸 중심 앵커가 옳은 이유의 조형적 실체다.

### 7-2. 하한 공식

```
안쪽 반지름(앵커 → 부채꼴 잉크의 안쪽 가장자리)  ≥  E_max + m
E_max = 5.5099 R          (아래 방향. 위 5.3417 R)
m     = max(0.60 R, 4.0 pt)
```

**여백 m의 근거**(취향이 아니라 이 저장소의 자):
- `0.60 R` — 본체에서 **가장 굵은 획인 다리 0.57 R** 한 개분. 규칙 1-A가 *"모든 변 ≥ 1.0 W"*로 쓰는 것과 같은 논리다.
  **틈이 획 하나보다 좁으면 눈은 붙었다고 읽는다.**
- `4.0 pt` — 낱선 하한 2.0 pt의 2배. 작은 배율에서 0.60 R이 1.6 pt까지 내려가므로 절대 바닥이 필요하다.

### 7-3. 현행 값과의 대조

⇒ **잉크 안쪽 가장자리 89 pt** / 히트원 안쪽 가장자리 85 pt (`UX_RIGHTCLICK_FAN_MENU` §1-2 · §부록 표).

### 7-4. ★ 이 표가 말하는 것 두 가지

**(가) 현행 설계는 통과한다.** 사용자 창(982 pt)·굽기 기준(846 pt) 전 배율에서 여유 **+28 ~ +70 pt**다.
그리고 **머리 중심 앵커였다면 배율 1.00에서 E = 9.6245 R = 86.64 pt**로 잉크 여유가 **+2.4 pt**, 히트원은 **−1.6 pt 관통**이었다.
UX가 GrabArea로 잰 **−4.97 ~ −5.21 pt**와 **부호·방향이 같다** — 서로 다른 봉투(잉크 vs 잡기영역)로 재도 결론이 같다. **몸 중심 채택은 조형 쪽에서도 지지한다.**

**(나) ★ 결함 1건 — 이 여유는 pt 고정이 아니라 화면 높이의 함수다.**
`PointsPerWorldUnit = 창 높이 / (2 × orthographicSize 12)`(`SceneBootstrapper.cs:422`)이므로
**캐릭터의 화면상 크기는 창 높이에 비례**하는데 **부채꼴 반지름은 pt 고정**이다.

```
여백 유지 한계 :  창 높이 1589 pt (배율 1.00) / 히트원 기준 1518 pt
접촉(여백 0)  :  창 높이 1762 pt
```

⇒ **4K 100 % 스케일링(2160 pt)·4K 125 %(1728 pt)에서 배율 1.00이면 호 버튼이 캐릭터 발/머리 잉크 안에 들어간다.**
(1440 p 100 % = 1440 pt는 여유 8.4 pt로 **통과하지만 아슬아슬**하다.)
이건 조형 결함이 아니라 **좌표계 결함**이다 — 처방도 조형이 아니다(궤도를 R 비례로 만들거나, 배율·PPU에 따라 궤도를 늘리거나, 캐릭터 상한을 두는 것). **소관은 `ux-widgets`/`dev-platform`, 판단은 리더.** 나는 봉투 숫자만 낸다.

### 7-5. 펼침 전이 중에는 이미 관통한다 (사실만 적는다)

`StartRadiusFraction 0.35` · `StartScale 0.62` ⇒ 버튼이 태어나는 순간 **잉크 안쪽 가장자리 = 0.35×111 − 22×0.62 = 25.2 pt**.
같은 창(982 pt)에서 머리 잉크 꼭대기는 배율 0.75에 **36.1 pt**, 1.00에 **48.1 pt**다.
⇒ **θ₀가 위/아래면 버튼이 캐릭터 몸 안에서 태어나 0.30초 동안 빠져나온다.**
이것은 *"앵커에서 날아 나온다"*는 연출의 대가이고 **정지 상태가 아니다.**
⇒ **실루엣 규칙(§7-2)은 정지 상태에만 적용할 것**을 권고한다. 전이 중 관통의 허용 여부는 **`design-motion` 소관**이다(나는 판정하지 않았다).

## 8. 미확인으로 남기는 것

1. **실기 캡처 0장.** 이 문서 전부가 프로덕션 상수 유도 + 좌표 파일 대조다. 이 저장소 원칙상 **최종 판정은 실제 빌드 캡처로만** 한다.
   특히 ⑤-(다)(A)의 「배율 0.35에서 눈 지름 31.4 %」와 ④-(나)의 「0.35에서 챙이 선 한 가닥」은 **캡처 없이 단정할 수 없다.**
2. **중립(Idle) 자세 전용.** §7-1 봉투는 팔 벌림 40°·서 있는 다리 기준이다. 걷기·매달리기·랙돌에서는 달라진다 — `design-motion` 소관, 재지 않았다.
3. **초상화(`CharacterPortraitStage`)에서 조건부 눈·모자 2층이 같은 결과를 내는지** — 두 렌더러가 같은 `Shape.SortingOrder`를 쓴다는 것만 확인했다(오늘 오전 §3). 실기 미확인.
4. **PPU 고정 가정.** §7-3 표는 창 높이별로 냈지만, 실제 오버레이 창 높이가 어떤 값을 갖는지(멀티 모니터·DPI 변경 시)는 `dev-platform` 소관 — 미확인.
5. **§3의 `dy` 3건이 카드 표면에 영향이 없다는 것**은 장비 쪽 문서(*"카드는 인계본 그대로"*)를 믿은 것이다. 내가 카드를 재지 않았다.
6. **왕관 뒷벽 SH색이 머리 잉크와 충분히 갈리는지**(검은 잉크 `#111111` vs `#2B220A`) — 색은 `design-art` 소관. 재지 않았다.

## 10. Windows 영향 / macOS 영향

- **Windows 영향: 없음(설계 문서 1개만 추가).** 이 문서가 인용·판정한 프로덕션 파일 4개

  ★ 단 **§7-4(나)는 플랫폼별로 다르게 나타난다** — 화면 높이가 곧 캐릭터 크기이므로 **Windows 4K 100 %(2160 pt)가 가장 먼저 걸린다.**
  macOS Retina는 논리 포인트가 1080~1200 급이라 같은 물리 해상도에서도 안전 구간에 있다. **이 항목은 Windows 쪽이 더 나쁘다 — 별도 배정 필요(소관 `ux-widgets`/`dev-platform`).**
- **macOS 영향: 함께 검토함 — 없음.** 같은 근거. Retina 2×에서는 1 pt = 2 px라 ⑤-(다)의 「0.93 pt」가 1.9 px로 보여 **문제가 덜 드러난다** —
