## 2. 팀별 역할

### 🎯 기획 · 총괄 (3)

| 담당 | 범위 | 하지 않는 것 |
|---|---|---|
| **리더 — Architect**<br>(현재 세션) | 통합 · 최종 판정 · Phase 게이트 · `process.md`/`Tasklist.md` · **유일하게 커밋한다** | 설계 세부를 대신 하지 않는다 |
| `game-architect` | 시스템 간 정합성, 기술 구조 확장성, 신규 기획 ↔ 기존 구조 충돌, 착수 순서, **되돌릴 수 없는 결정 식별** | 화면·조형·수치·구현 |
| `design-systems` | 스탯 / 등급 / 세트 시너지 / 재화 경제의 **수치** — 임계값·상승폭·획득량·가격·소프트캡 | 화폐 단위가 아닌 실제 달러(→상품전략) |

### 💰 상품 전략 (1)

| 담당 | 범위 |
|---|---|
| `product-strategy` | 유통 채널(스팀 / MS스토어 / 맥앱스토어), DLC 구성·가격, 무료·유료 경계, 출시 순서 |

`design-systems`가 "동전 몇 개"를 정하면, 이쪽은 **"몇 달러"**를 정한다.

### 📣 마케팅 (1)

| 담당 | 범위 |
|---|---|
| `marketing` | 홍보 소재, 스토어 페이지, 스크린샷·GIF 구성, 개발일지·커뮤니티 |

**거짓 소재 금지.** 실제로 되지 않는 기능을 스크린샷으로 만들지 않는다.
캡처는 **실제 빌드**에서, **깨끗한 테스트 환경**에서(남의 창 제목·파일명이 찍힌다).
외부 게시는 전부 리더 승인 후 사용자가 한다.

### 🎨 디자인 (7)

| `design-character` | **캐릭터 본체** — 비율, 획 두께, 관절 곡률, 실루엣 |

**최종 판정은 실제 빌드 캡처로만**(오프라인 렌더러가 모든 점에 둥근 캡을 찍어 코너 붕괴를 가린 사고).

### ✅ 검증 (1) — 커밋 전 관문

| 담당 | 묻는 질문 |

## 3. 유기적 운영 — 라운드 사이클

```
 사용자 요구
      │
      ▼
 ① 기획·총괄  ── game-architect가 기존 구조와 충돌하는지 먼저 본다
      │             (되돌릴 수 없는 결정이면 여기서 멈추고 리더가 사용자에게 묻는다)
      ▼
 ② 설계     ── 디자인 7인 / design-systems. 서로의 산출물을 읽고 교차 검토해 올린다
      │
      ▼
 ③ 구현     ── coder / dev-platform. 리더가 파일을 갈라 준다
      │
      ▼
 ④ 테스트   ── test-engineer(기능) · qa-regression(회귀) · debugger(원인)
      │
      ▼
 ⑤ 검증     ── verify-change. 보고서의 각 주장을 독립적으로 다시 잰다
      │
      ▼
 ⑥ 판정     ── 리더. 통과하면 커밋, 아니면 해당 단계로 반려
      │
      ▼
 ⑦ 사용자 검증 ── 페르소나 3인 병렬. 의견은 리더가 받아 담당자에게 배분
```

**반려는 위로만 간다.** ⑤에서 걸리면 ③ 또는 ②로, ④에서 걸리면 ③으로.
담당자끼리 직접 되돌리지 않는다.

### 인계 계약 — 이 쌍들은 서로 직접 읽고 교차 검토한 뒤 올린다

리더에게 올릴 때 **"상대 팀 산출물의 어느 지점과 어떻게 맞물리는가"**를 반드시 적는다.

| 인계 | 왜 |
|---|---|
| `design-systems` → `ux-designer` | 수치가 화면에 뜬다. 표시 불가능한 값을 정하면 그때 알아야 한다 |
| `design-art` → `design-equipment` · `ux-designer` | 팔레트가 양쪽에 동시에 걸린다 |
| `design-equipment` ↔ `design-character` | 장비가 몸에 붙는다. **실제 사례**: 팔이 0.3297 H(인체 0.44)라 아이콘 닦기가 기하학적으로 막혔다 |
| `design-motion` → `coder` | 모션 설계가 **상태의 수평 이동 소유권**을 규정한다. 빠뜨리면 미끄러진다 |
| `design-narrative` → `design-motion` | 대사 노출 시간이 그 상태 지속보다 길면 잘린다 |
| `product-strategy` → `marketing` | 무엇을 파는지가 정해져야 어떻게 알릴지가 나온다 |
| `game-architect` → 전원 | 개별이 다 옳아도 합이 어긋날 수 있다 |
| `qa-regression` → 전원 | **누구 라운드가 무엇을 깼는지**를 그 라운드에 알린다 |
| `verify-change` → 리더 | 재현 안 되는 주장만 올린다. 판정은 리더 |

## 4. 전원 공통 규칙

### 절대 금지
- **`driver.sh stop`과 전역 단축키 `Q`** — 전역이라 **사용자가 쓰는 인스턴스까지 함께 죽는다**
- **앱 실행·빌드·Unity 배치모드를 리더 승인 없이** — `Library/` 락이 다른 라운드를 깬다
- **다른 담당자에게 직접 지시** — 전부 리더를 거친다
- **`Tasklist.md` 수정** — 리더 소유
- 디자인·기획·검증팀은 **프로덕션 `.cs` 수정 금지**

### ★ 거짓 통과 방지 (2026-09-02 하루에 9건이 나왔다)

> **실패한 측정과 성공한 측정이 똑같이 생겼다.**

| # | 실제 사고 | 규칙 |
|---|---|---|
| 1 | `-runTests`에 `-quit`을 같이 줘서 **0건 실행 + 종료코드 0** | `-quit` 금지. 콤마 구분 필터도 같은 증상 |
| 2 | **이틀 전** 결과 xml을 새 결과로 읽음 | 결과 파일은 **먼저 지우고** mtime·testcasecount 확인 |
| 3 | **하루 전** Player.log를 현재 상태로 읽음 | 드라이버 로그와 사용자 인스턴스 로그를 구분 |
| 4 | `strings`로 .NET(UTF-16) 문자열을 찾아 "0건 = 깨끗" | **모든 "없음" 판정에 양성 대조**. 하나라도 깨지면 그 파일의 0건 전부 무효 |
| 5 | 면제 목록이 비어 `foreach`가 아무것도 안 재고 초록 | 빈 목록을 기대값으로 명시 |
| 6 | 빌드해 놓고 **실행 중인 앱을 안 바꿔** 사용자가 낡은 빌드를 재신고 | 빌드 후 반드시 앱 교체 |
| 7 | `StickMate.exe` 날짜로 빌드 시점 판단(그건 Unity 런처 스텁) | 우리 코드는 `StickMate_Data/Managed/StickMate.Runtime.dll` |
| 8 | 설계 거울이 프로덕션과 **13건** 갈라진 채 서로 다른 판정 | `mirrordrift.py` / `prodverify.py`로 대조 |
| 9 | 애셋이 코드 기본값을 덮는데 애셋을 안 고쳐 스위치가 꺼진 채 출하될 뻔 | `StickConfig` 건드리면 `DefaultStickConfig.asset`도 |

**공통 처방**: 계산기·검사기를 만들면 **알려진 값으로 먼저 교정**한다
(흰/검 21.0, 동일색 1.0). **교정이 깨지면 그 뒤 숫자를 전부 폐기한다.**

### ★ 활성 빌드 타깃 사각지대 (2026-09-02 실측)
Unity 에디터의 활성 빌드 타깃 **반대편 플랫폼 파일은 컴파일되지 않는다.**
`Win32WindowService.cs`는 전체가 `#if UNITY_STANDALONE_WIN` 안이라 macOS 타깃에서는
**타입이 존재하지 않고**, 리플렉션 감사는 없는 타입을 셀 수 없다.

- 확인: `Library/Bee/artifacts/*/StickMate.Runtime.rsp`의 `UNITY_STANDALONE_*`
- 플랫폼 감사는 **타입이 아니라 소스 파일을 읽도록** 짠다
- 타깃 전환은 **전역 상태 변경** — 리더 승인 후에만

### 플랫폼 동시 검토
한쪽을 건드리면 **그 라운드 안에서** 다른 쪽도 본다. "나중에 맞추자"는 금지.
완료 보고에 **"Windows 영향 / macOS 영향"** 각각 한 줄 필수.
Windows 전용 파일은 이 머신에서 컴파일되지 않으므로 `Tools/CrossCompile/xcheck.sh win`/`osx` 필수.

### 동시 진행
**리더가 파일을 갈라 준다.** 겹친 채로 돌면 한쪽이 다른 쪽의 작업 중 파일을 커밋하거나
컴파일 불가 트리에서 검증하는 사고가 난다(2026-09-02 두 건 실제 발생).

## 5. 정직성 규칙

- **확인 못 한 것은 "미확인"으로.** 추측으로 메우지 않는다.
- **"고쳤다"고 쉽게 쓰지 않는다.** 실기 검증이 불가능하면
  "이렇게 동작할 것으로 판단한다, 실기 미확인"이 정직한 상태다.
- **자기 산출물의 거짓 통과를 발견하면 그대로 보고한다.** 이 저장소에서 가장 값진 보고들이
  전부 그것이었다 — 양성 대조가 처음에 초록이었다는 자백, 자기 게이트의 구멍을 스스로 찾은 것.
- **반증되면 반증됐다고 쓴다.** 리더의 가설도 예외가 아니다.

## ★ 거짓 통과 신형 — 「생성기와 검사기가 같이 틀린다」 (2026-09-02)

이 저장소가 아홉 번 당한 형태는 **기준과 대상이 같이 움직이는 것**이었다.
2026-09-02에 **열 번째가 나왔고 형태가 다르다.**

`localization` 라운드의 오프라인 예행 **38종이 전부 초록**이었는데 러너에서 3건이 빨갛게 났다.
원인:

> **`golden_gen.py`(생성기)와 `dryrun.py`(검사기)가 같은 잘못된 `float32` 흉내를 공유했다.**
> 둘이 **같은 함정에 같이 빠져 서로를 확인해 주지 못했다.**

구체적으로는 파이썬이 **연산마다 라운딩**했는데 Unity Mono는 **double로 계산하고 쓸 때 한 번만** 라운딩한다.
글자수 5·7·15·18·20·25에서 정확히 **1 ULP** 갈렸다.

### ★ 무엇이 이걸 구했는가 — 이 문단이 핵심이다

**기대값을 프로덕션 함수가 아니라 「디스크의 골든 비트」에서 되살린 설계.**

그래서 *"프로덕션이 틀렸나, 골든이 틀렸나"*를 **가를 수 있었다.**
같은 실패한 실행 안에서 `한국어는_구식_단일계수_식과_구조적으로_동치다`가 **Passed**였고,
그것이 **틀린 것은 골든이지 프로덕션이 아니다**를 증명했다.

> **기대값을 `ReadingSeconds()`로 만들었다면 3건 전부 초록이었고 아무도 1 ULP를 못 봤다.**

### 규칙
1. **기대값을 프로덕션 함수로 만들지 마라.** 골든 파일·상수·독립 구현 중 하나에서 와야 한다.
   그 함수가 틀어지면 기대값도 함께 틀어져 **아무것도 못 잰다.**
2. **생성기와 검사기가 코드를 공유하면 둘 다 같은 방향으로 틀린다.**
   공유해야 한다면 **바깥의 실측값으로 둘 다 교정**해라(러너가 실제로 뱉은 비트 등).
3. **오프라인 예행은 러너를 대체하지 않는다.** 예행이 전부 초록이어도 **러너를 돌려라.**

## ★ 경쟁 → 채택 → 집단 고도화 (사용자 지시 2026-09-02)

> **"DLC 팩 같은 건 디자이너별로 각각 일을 줘서 경쟁을 붙여 고도화하는 형태로 해줘"**

**큰 조형·컨셉 과제는 2단계로 돈다. 한 사람에게 통째로 주지 않는다.**

### 1단계 — 발산(경쟁)
**같은 브리프를 여러 담당에게 동시에 준다.**

- ★ **판정 기준을 브리프에 미리 공개한다.** 나중에 만든 기준으로 고르면 그건 판정이 아니라 취향이다
- **경쟁자는 축이 서로 달라야 한다.** 같은 질문에 **다른 자**를 대는 구성이라야 비교가 값을 한다

**리더가 근거로 채택안을 고른 뒤, 그 하나에 디자이너 전원이 각자의 축으로 붙는다.**

- ★ **채택 근거를 문서에 남긴다.** 왜 이겼고 왜 졌는지가 없으면 다음 경쟁이 같은 것을 반복한다

### 리더가 지키는 것
- **1단계 중에는 채택안을 암시하지 않는다.** 힌트를 주면 경쟁이 아니라 유도가 된다
- **2단계 전에 판정을 먼저 공개한다.** 순서가 뒤집히면 고도화가 아니라 사후 정당화가 된다
- ★ **1단계에서 나온 실측은 진 제안 것이라도 살린다** — 측정은 취향이 아니다

## ★ 거짓 통과 12번째 형태 — **대소문자가 프로브를 죽인다** (2026-09-02, 리더 자신이 당함)

| 도구 | 대소문자 | 결과 |

2. **"깨끗하다"를 결론으로 쓰려면 양성 대조를 붙여라** — 같은 명령이 **다른 파일에서는 실제로 M을 출력하는지**
   먼저 보여라. 빈 출력 하나로는 "변경 없음"과 "경로가 틀림"을 구분할 수 없다.
3. **파일명을 근거로 쓰는 모든 보고는 그 이름을 `ls`로 확인한 것이어야 한다.**

리더는 원인을 *"`set -uo pipefail`에 `-e`가 없어서"*라고 적었다. **`verify-change`가 재현에 실패했다** —
bash 3.2 / zsh / sh / 직접 실행 **전부 rc=1**이다. `set -u` 위반은 비대화형 셸을 **종료시킨다.**
리더가 본 `[exited with code 0]`은 **파이프 끝 명령의 rc**였을 가능성이 높다(`... | tail` → 0).
⇒ **「`set -e`가 없어서」라는 진단으로 다른 스크립트를 고치지 마라. 그 병이 아니다.**

★ **그런데 실측 중에 훨씬 나쁜 변종이 나왔다 — 이쪽이 진짜다:**
```
$ bash Tools/VerifyChange/xcheck_isolated.sh osx ""      # 2번 인자가 빈 문자열
  [osx/Assembly-CSharp-Editor] errors= sources= dll=MISSING
errors= 줄 개수: 5     ← 아래 규칙 1(「errors= 줄이 5개면 통과」)을 그대로 통과한다
```
`set -u`가 **아예 안 터진다**(빈 문자열은 unset이 아니다). 값이 전부 비었는데 **형태 검사가 통과한다.**
⇒ **규칙 1이 이 케이스에 속았다.** 형태만 세면 안 되고 **값이 채워졌는지**까지 봐야 한다.
현재 도구는 `errors=<숫자> sources=<숫자> dll=(OK|MISSING)` **정규형**으로 못박고 아니면 rc=3(측정 무효)를 낸다.
그리고 `--selftest`가 고의 `CS0103`을 섞어 **탐지 경로가 살아 있음을 매번 증명**한다.

`grep errors=`로 출력을 봤기 때문에 잡았다. **종료코드만 봤으면 "빌드해도 안전"으로 읽고,
그 빌드가 멀쩡한 산출물을 덮어썼을 것이다**(트리는 실제로 안 컴파일되고 있었다 — `CS0103` 2건).

### 규칙
1. **검증 스크립트의 성공 판정은 종료코드가 아니라 「기대한 산출물이 기대한 개수만큼 나왔는가」로 한다.**
   이 경우는 `errors=` 줄이 **어셈블리 수(5)만큼** 나왔는가다.
2. **형태만 세지 말고 「값이 채워졌는가」까지 봐라.** 빈 문자열 인자는 `set -u`를 안 터뜨리면서
   모든 필드를 비우고 **줄 수는 맞춘다**. 정규형(`errors=<숫자> …`)으로 못박아라.
3. **빌드 직전 게이트는 특히 그렇다** — 여기서 거짓 통과하면 되돌릴 수 없는 것을 덮어쓴다.

★ 같은 가족의 사고: .NET `\b`가 한글을 낱말로 셈 / zsh 글롭이 `--include`를 죽임 /
파일명 대소문자로 `git status`가 빈 출력 / 빈 문자열 인자가 형태 검사를 통과 /
**그리고 이 절 자체** — 리더가 원인을 오진한 채 정본에 적었고, 이틀을 못 갔다. **전부 "죽은 프로브의 출력이 성공한 프로브와 똑같이 생겼다."**

## ★ 절대 규칙 — 실기 테스트는 **한 번에 하나** (사용자 지시 2026-09-02)

> 사용자 신고: **"지금 맥북에 프로그램이 4개가 동시에 돌아감"**
> → **"테스트하면 기존꺼 종료시키고 다음꺼 돌리고 해야지"**

### 무슨 일이 있었나
리더가 **페르소나 3인을 동시에 파견**했고 각자 `driver.sh start`로 인스턴스를 띄웠다.
거기에 13:18부터 **6시간 방치된 고아 인스턴스** 1개가 더 있어 **총 4마리가 사용자 바탕화면을 동시에 돌아다녔다.**

★ 4개 전부 `-logFile`이 붙어 있었다 = **전부 드라이버가 띄운 것, 즉 전부 우리 것이었다.**
**상주 비침해 앱을 만들면서 우리가 사용자 화면을 가장 크게 침해했다.**

### 규칙
1. **실기 테스트는 동시에 하나만.** 리더는 실기 라운드를 **직렬로** 배정한다 —
   앞 라운드가 인스턴스를 정리했음을 확인한 뒤 다음을 띄운다.
2. **띄운 라운드가 자기 PID를 반드시 정리한다.** 끝났으면 남기지 마라.
   ★ **`driver.sh stop`(남의 PID 포함)과 전역 `Q`는 여전히 금지** — 자기 PID만 `kill -TERM`.
3. **리더는 라운드 회수 때마다 인스턴스 수를 확인한다.**
   ```bash
   pgrep -f "StickMate.app/Contents/MacOS/StickMate" | wc -l
   ```
   ★ **`ps | grep -c`로 세지 마라** — 리더가 오늘 그걸로 "3개"·"4개"를 잘못 보고했다.
   `pgrep`으로 세고 **양성 대조**(존재하지 않는 이름으로 0이 나오는지)를 붙여라.
4. **고아 감시**: 시작 시각이 1시간 이상 지난 인스턴스는 주인이 없는 것으로 보고 리더가 확인한다.
   ★ 고아는 **로그 파일을 공유하면 다른 라운드의 측정을 오염시킨다**(오늘 실측:
   `/tmp/stickmate-run/stickmate.log`가 두 프로세스가 섞여 쓴 파일이었다).
5. **세이브 파일은 모든 인스턴스가 공유한다.** 동시에 여럿 돌면 진행도가 서로 덮어쓴다 —
   이건 화면 문제가 아니라 **사용자 데이터 문제**다.

## ★ 상시 절차 — 부하 감시 (사용자 지시 2026-09-02 "부하감시도 주기적으로해")

**리더는 라운드를 회수할 때마다 `bash Tools/Ops/loadwatch.sh`를 돌린다.**

### 왜 생겼나 — 오늘 두 사고
1. **새벽 05:27부터 14시간째 8코어를 태우던 좀비 셸 8개**를 아무도 못 봤다.
   `perf-doc`이 오디오를 재면서 *"기계가 조용하지 않았다 — 총 CPU 900~990%"*라고 적었지만
   **원인을 찾지 않았고, 그래서 그 라운드의 절대값이 전부 오염됐다.**
2. **StickMate 인스턴스 4개가 동시에** 사용자 바탕화면을 돌아다녔다(사용자 신고).

### 감시가 답해야 하는 것
- 우리 인스턴스가 **몇 개인가** (순번제 규칙상 실기 테스트 중엔 **1개**)
- **1시간 넘게 산 인스턴스**가 있는가 = 고아 후보
- **CPU 상위에 우리가 아닌 것이 있으면 그것도 봐라** — 측정의 절대값이 흔들린다
- Unity 배치모드·`csc`가 도는가 = 빌드/러너 충돌 여부

### 판정 규칙
- ★ **종료코드로 판정하지 마라. 출력 줄로 판정해라.** 오늘 `xcheck_isolated.sh`가 인자 부족으로
  아무것도 안 하고 **exit 0**을 냈다(거짓 통과 13번째 형태).
- ★ **양성 대조가 내장돼 있다** — 존재하지 않는 이름이 0으로 나오는지 매번 찍는다. 0이 아니면 그 측정 전부 무효.
- ★ **부하가 높다고 자동으로 우리 탓은 아니다.** 2026-09-02 리부팅 직후 load 257은 전부 Spotlight
  재색인(`mds_stores`/`mdsync`/`mdbulkimport`)이었고 우리 프로세스는 0개였다. **원인을 찍고 나서 말해라.**
