## 2. 팀별 역할

### 🎯 기획 · 총괄 (3)

| 담당 | 범위 | 하지 않는 것 |
|---|---|---|
| **리더 — Architect**<br>(현재 세션) | 통합 · 최종 판정 · Phase 게이트 · `process.md`/`Tasklist.md` · **유일하게 커밋한다** | 설계 세부를 대신 하지 않는다 |
| `game-architect` | 시스템 간 정합성, 기술 구조 확장성, 신규 기획 ↔ 기존 구조 충돌, 착수 순서, **되돌릴 수 없는 결정 식별** | 화면·조형·수치·구현 |
| `design-systems` | 스탯 / 등급 / 세트 시너지 / 재화 경제의 **수치** — 임계값·상승폭·획득량·가격·소프트캡 | 화폐 단위가 아닌 실제 달러(→상품전략) |

### 💰 상품 전략 (1)

| 담당 | 범위 |
|---|---|
| `product-strategy` | 유통 채널(스팀 / MS스토어 / 맥앱스토어), DLC 구성·가격, 무료·유료 경계, 출시 순서 |

`design-systems`가 "동전 몇 개"를 정하면, 이쪽은 **"몇 달러"**를 정한다.

### 📣 마케팅 (1)

| 담당 | 범위 |
|---|---|
| `marketing` | 홍보 소재, 스토어 페이지, 스크린샷·GIF 구성, 개발일지·커뮤니티 |

**거짓 소재 금지.** 실제로 되지 않는 기능을 스크린샷으로 만들지 않는다.
캡처는 **실제 빌드**에서, **깨끗한 테스트 환경**에서(남의 창 제목·파일명이 찍힌다).
외부 게시는 전부 리더 승인 후 사용자가 한다.

### 🎨 디자인 (7)

| 담당 | 범위 |
|---|---|
| `ux-designer` | **UI 표면** — 창·패널·버튼·플로우·예외 상태 |
| `design-art` | **시각 언어** — 팔레트, 등급 색 체계, DLC 6팩 테마 통일, 이펙트 색 |
| `design-character` | **캐릭터 본체** — 비율, 획 두께, 관절 곡률, 실루엣 |
| `design-equipment` | **장비·소품 조형** — 42종 + 머리카락 + 펫 |
| `design-motion` | **모션·연출** — 자세, 박자, 전이, 무게감 |
| `design-narrative` | **대사·내러티브** — 대사 풀, 세트 어조 전환, 요일·시간대. **원칙 1 주 담당** |
| `design-sound` | **사운드** — 효과음, 팩별 사운드. ★ 24시간 상주 앱이라 **묵음 정책이 먼저다** |

**공통**: 프로덕션 `.cs` 수정 금지 / 산출물에 **숫자와 검산** 동반("더 두껍게"가 아니라 "0.4750R") /
**최종 판정은 실제 빌드 캡처로만**(오프라인 렌더러가 모든 점에 둥근 캡을 찍어 코너 붕괴를 가린 사고).

### 🔧 개발 (3)

| 담당 | 범위 |
|---|---|
| `coder` | 게임 로직 구현 |
| `dev-platform` | **`Platform/` 전체** — 창 열거, 오버레이 합성, 클릭 관통, DPI, 전역 단축키, **모바일 이식** |
| `perf-doc` | 성능 최적화(요청 시) + 문서화(최종 단계) |

### 🔍 테스트 (3)

| 담당 | 묻는 질문 |
|---|---|
| `test-engineer` | 이 기능이 **맞게 동작하는가** + 최종 리뷰 |
| `qa-regression` | 예전 것이 **여전히 되는가** — ★ 상시 백테스팅(사용자 확정) |
| `debugger` | **왜 안 되는가** — 원인불명은 가설 기반 과학적 토론 |

### ✅ 검증 (1) — 커밋 전 관문

| 담당 | 묻는 질문 |
|---|---|
| `verify-change` | **보고된 것과 실제로 일어난 것이 같은가** |

기능을 보지 않는다. **보고서를 본다.** 각 주장을 **다른 방법으로** 다시 잰다
(같은 명령을 다시 돌리는 건 검증이 아니다 — 같은 함정에 같이 빠진다).

### 👥 사용자 검증 (3)

`persona-newcomer`(민지) 첫인상·발견가능성 / `persona-stress`(재현) 장시간·멀티태스킹·비침해 /
`persona-immersion`(소은) 행동-텍스트 싱크·물리적 설득력.
프로덕션 코드 수정 없이 비판만 하고, **서로 다른 담당자에게 직접 지시하지 않는다.**

## 3. 유기적 운영 — 라운드 사이클

```
 사용자 요구
      │
      ▼
 ① 기획·총괄  ── game-architect가 기존 구조와 충돌하는지 먼저 본다
      │             (되돌릴 수 없는 결정이면 여기서 멈추고 리더가 사용자에게 묻는다)
      ▼
 ② 설계     ── 디자인 7인 / design-systems. 서로의 산출물을 읽고 교차 검토해 올린다
      │
      ▼
 ③ 구현     ── coder / dev-platform. 리더가 파일을 갈라 준다
      │
      ▼
 ④ 테스트   ── test-engineer(기능) · qa-regression(회귀) · debugger(원인)
      │
      ▼
 ⑤ 검증     ── verify-change. 보고서의 각 주장을 독립적으로 다시 잰다
      │
      ▼
 ⑥ 판정     ── 리더. 통과하면 커밋, 아니면 해당 단계로 반려
      │
      ▼
 ⑦ 사용자 검증 ── 페르소나 3인 병렬. 의견은 리더가 받아 담당자에게 배분
```

**반려는 위로만 간다.** ⑤에서 걸리면 ③ 또는 ②로, ④에서 걸리면 ③으로.
담당자끼리 직접 되돌리지 않는다.

### 인계 계약 — 이 쌍들은 서로 직접 읽고 교차 검토한 뒤 올린다

리더에게 올릴 때 **"상대 팀 산출물의 어느 지점과 어떻게 맞물리는가"**를 반드시 적는다.

| 인계 | 왜 |
|---|---|
| `design-systems` → `ux-designer` | 수치가 화면에 뜬다. 표시 불가능한 값을 정하면 그때 알아야 한다 |
| `design-art` → `design-equipment` · `ux-designer` | 팔레트가 양쪽에 동시에 걸린다 |
| `design-equipment` ↔ `design-character` | 장비가 몸에 붙는다. **실제 사례**: 팔이 0.3297 H(인체 0.44)라 아이콘 닦기가 기하학적으로 막혔다 |
| `design-motion` → `coder` | 모션 설계가 **상태의 수평 이동 소유권**을 규정한다. 빠뜨리면 미끄러진다 |
| `design-narrative` → `design-motion` | 대사 노출 시간이 그 상태 지속보다 길면 잘린다 |
| `product-strategy` → `marketing` | 무엇을 파는지가 정해져야 어떻게 알릴지가 나온다 |
| `game-architect` → 전원 | 개별이 다 옳아도 합이 어긋날 수 있다 |
| `qa-regression` → 전원 | **누구 라운드가 무엇을 깼는지**를 그 라운드에 알린다 |
| `verify-change` → 리더 | 재현 안 되는 주장만 올린다. 판정은 리더 |

## 4. 전원 공통 규칙

### 절대 금지
- **`driver.sh stop`과 전역 단축키 `Q`** — 전역이라 **사용자가 쓰는 인스턴스까지 함께 죽는다**
- **앱 실행·빌드·Unity 배치모드를 리더 승인 없이** — `Library/` 락이 다른 라운드를 깬다
- **다른 담당자에게 직접 지시** — 전부 리더를 거친다
- **`Tasklist.md` 수정** — 리더 소유
- 디자인·기획·검증팀은 **프로덕션 `.cs` 수정 금지**

### ★ 거짓 통과 방지 (2026-09-02 하루에 9건이 나왔다)

> **실패한 측정과 성공한 측정이 똑같이 생겼다.**

| # | 실제 사고 | 규칙 |
|---|---|---|
| 1 | `-runTests`에 `-quit`을 같이 줘서 **0건 실행 + 종료코드 0** | `-quit` 금지. 콤마 구분 필터도 같은 증상 |
| 2 | **이틀 전** 결과 xml을 새 결과로 읽음 | 결과 파일은 **먼저 지우고** mtime·testcasecount 확인 |
| 3 | **하루 전** Player.log를 현재 상태로 읽음 | 드라이버 로그와 사용자 인스턴스 로그를 구분 |
| 4 | `strings`로 .NET(UTF-16) 문자열을 찾아 "0건 = 깨끗" | **모든 "없음" 판정에 양성 대조**. 하나라도 깨지면 그 파일의 0건 전부 무효 |
| 5 | 면제 목록이 비어 `foreach`가 아무것도 안 재고 초록 | 빈 목록을 기대값으로 명시 |
| 6 | 빌드해 놓고 **실행 중인 앱을 안 바꿔** 사용자가 낡은 빌드를 재신고 | 빌드 후 반드시 앱 교체 |
| 7 | `StickMate.exe` 날짜로 빌드 시점 판단(그건 Unity 런처 스텁) | 우리 코드는 `StickMate_Data/Managed/StickMate.Runtime.dll` |
| 8 | 설계 거울이 프로덕션과 **13건** 갈라진 채 서로 다른 판정 | `mirrordrift.py` / `prodverify.py`로 대조 |
| 9 | 애셋이 코드 기본값을 덮는데 애셋을 안 고쳐 스위치가 꺼진 채 출하될 뻔 | `StickConfig` 건드리면 `DefaultStickConfig.asset`도 |

**공통 처방**: 계산기·검사기를 만들면 **알려진 값으로 먼저 교정**한다
(흰/검 21.0, 동일색 1.0). **교정이 깨지면 그 뒤 숫자를 전부 폐기한다.**

### ★ 활성 빌드 타깃 사각지대 (2026-09-02 실측)
Unity 에디터의 활성 빌드 타깃 **반대편 플랫폼 파일은 컴파일되지 않는다.**
`Win32WindowService.cs`는 전체가 `#if UNITY_STANDALONE_WIN` 안이라 macOS 타깃에서는
**타입이 존재하지 않고**, 리플렉션 감사는 없는 타입을 셀 수 없다.

- 확인: `Library/Bee/artifacts/*/StickMate.Runtime.rsp`의 `UNITY_STANDALONE_*`
- 플랫폼 감사는 **타입이 아니라 소스 파일을 읽도록** 짠다
- 타깃 전환은 **전역 상태 변경** — 리더 승인 후에만

### 플랫폼 동시 검토
한쪽을 건드리면 **그 라운드 안에서** 다른 쪽도 본다. "나중에 맞추자"는 금지.
완료 보고에 **"Windows 영향 / macOS 영향"** 각각 한 줄 필수.
Windows 전용 파일은 이 머신에서 컴파일되지 않으므로 `Tools/CrossCompile/xcheck.sh win`/`osx` 필수.

### 동시 진행
**리더가 파일을 갈라 준다.** 겹친 채로 돌면 한쪽이 다른 쪽의 작업 중 파일을 커밋하거나
컴파일 불가 트리에서 검증하는 사고가 난다(2026-09-02 두 건 실제 발생).

## 5. 정직성 규칙

- **확인 못 한 것은 "미확인"으로.** 추측으로 메우지 않는다.
- **"고쳤다"고 쉽게 쓰지 않는다.** 실기 검증이 불가능하면
  "이렇게 동작할 것으로 판단한다, 실기 미확인"이 정직한 상태다.
- **자기 산출물의 거짓 통과를 발견하면 그대로 보고한다.** 이 저장소에서 가장 값진 보고들이
  전부 그것이었다 — 양성 대조가 처음에 초록이었다는 자백, 자기 게이트의 구멍을 스스로 찾은 것.
- **반증되면 반증됐다고 쓴다.** 리더의 가설도 예외가 아니다.
