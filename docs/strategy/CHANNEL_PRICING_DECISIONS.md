## 0-0. ★ 2회차 정정 (2026-09-02 후반) — **이 배너가 아래 본문보다 우선한다**

지난 회차 이후 **사용자 확정 4건**과 **1차 출처 재확인 3건**이 들어왔다.
아래 본문에는 그 이전 전제로 쓴 문장이 남아 있다. **충돌하면 이 배너가 이긴다.**

### (가) 사용자 확정 — 되묻지 않는다

| 대상 | 구매 단위 | 지불 수단 |
|---|---|---|
| **DLC 6팩** | **팩 단위만** (개별 아이템 구매 불가) | **현금 전용** |
| **기본 42종** | 개별 | 동전 **또는** 현금 |

- **현금↔재화 다리 없음** (P-1 유지, 강화됨)
- **채널은 스팀 단독.** MS 스토어 제외 재확인, 맥 앱스토어 1차 제외 유지
- **본편 무료(F2P)** — `docs/MILESTONES.md` D-2 확정

### (나) 그래서 죽은 칸 — 본문에서 읽지 마라

| 죽은 것 | 왜 |
|---|---|
| 본편 정가 **$7.99** / 출시 주 10% 할인 | F2P 확정 → **본편 SKU가 없다** |
| **"본편 + 전 DLC 번들 $15.99"** | 본편이 무료라 묶을 것이 없다 → **SKU 폐기** |
| P-3 규칙 *"팩 가격 ≤ 본편 × 0.4"* | **분모가 0이 됐다.** 3-8절에 P-3′로 교체 |
| 7절 미확인 #3 **MS 스토어 딥링크 95%** | 채널 제외 → 잴 필요가 없다 |
| 8절 *"MS 스토어에 앱으로 등재"* | 같은 이유 |
| 위시리스트 2,000 미만 시 **$4.99로 인하** 조건부 규칙 | 본편 가격이 없어 발동 대상이 없다 |

### (다) 신규 판정 — 코드서명 (상세: 10절)

- **Windows: EV 기각 · OV(또는 Artifact Signing) 채택 · 단 1.0 차단 아님**
- **macOS: 서명 + 공증을 1.0 차단 항목으로 승격** — 이유는 Gatekeeper가 아니라 **스팀 채널 요구**

## 0. 먼저 — 사용자 조사표의 숫자 2건을 정정한다

교정 없이 시작하지 않는다. 사용자가 준 3행 표에서 **두 칸이 현재 사실과 다르다.**

| 원문 | 실제 (2026-09-02 확인) | 출처 |
|---|---|---|
| 스팀 $100 — **"첫 판매 시 환불"** | **$1,000 조정총수입(AGR) 달성 후** 다음 정산에 반환. 첫 판매가 아니다 | Steamworks `gettingstarted/appfee` |
| MS 스토어 **"무료(개인 계정)"** | 맞다. 단 이건 **최근 변경**이다 — 개인 $19는 2025-09경, 법인 $99는 2026-05-07 폐지 | Windows Developer Blog 2026-05-07 |

**정정 1이 왜 중요한가.** $1,000 AGR은 정가 $7.99 기준 **약 125~130장**(할인·환불 전 총액)이다.
"첫 판매하면 $100이 돌아온다"를 전제로 계획을 세우면 손익분기가 100배 어긋난다.
→ **$100은 회수 가정 없이 매몰비용으로 잡는다.**

### 채널별 실제 수취율 (2026-09-02)

| 채널 | 입점 비용 | 수수료 | 우리 수취 |
|---|---|---|---|
| Steam | $100 (AGR $1,000 후 반환) | 30% (첫 $1,000만까지) | **70%** |
| MS 스토어 — **앱**으로 등재 | $0 | 15% / **딥링크 유입은 5%** | 85% / **95%** |
| MS 스토어 — **게임**으로 등재 | $0 | 12% | 88% |
| 맥 앱스토어 | $99/년 | 30% / **소규모 사업자 프로그램 15%**(전년 수익 $100만 미만) | 70% / **85%** |

★ **여기서 결정 하나가 공짜로 떨어진다.** 사용자가 이미 정한 "MS 스토어 = 생산성 툴 포지셔닝"은
취향 문제가 아니라 **돈 문제로도 옳다.** 우리 유입은 사용자 조사대로 유튜브·개발일지 =
**딥링크**이고, MS 스토어의 딥링크 요율은 비게임 앱에만 적용되는 **95%**다.
게임으로 등재하면 88%로 내려간다. **7%p를 포지셔닝 하나로 번다.**
(단 "딥링크 95%"는 2019년 개발자 계약 조항이고 실제 집행 이력에 논란이 있다 — 2026-09-02 기준
Microsoft Learn 문서상 유효. **정산서로 실측 확인 전까지 85%로 보수 계상할 것.**)

## 1. 결정 1 — 맥 앱스토어: **1차 출시 제외. 위젯형 기각. Lite는 게이트 통과 시에만.**

### 1-1. 먼저 이 결정이 되돌리기 비싸지 않다는 것부터 보인다

리더가 "설계 단계에서 코어를 플랫폼별로 스위칭 가능하게 분리할지"가 여기 걸렸다고 했다.
**저장소를 읽은 결과, 그 분리는 이미 되어 있고 이미 값을 치렀다.**

| 이미 존재하는 것 | 파일 |
|---|---|
| 능력 인터페이스 12종 (`IPlatformWindowService`, `IDockMetricsService`, `IDesktopIconLayoutService` …) | `Assets/_Project/Scripts/Platform/I*.cs` |
| 아무것도 못 하는 구현 | `NullPlatformWindowService.cs` |
| 부분 실패를 흡수하는 데코레이터 | `FallbackPlatformWindowService.cs` |
| **창 열거가 원천 불가한 플랫폼용 대체 지형** | `Platform/Mobile/ScreenshotBackdropPlatformService.cs` |
| **이미 존재하는 macOS 기능 결손 2건** | 데스크톱 아이콘·작업표시줄 자동숨김 제어는 **Windows에만** 구현 (`MacWindowService.cs:59` 주석이 명시적으로 "구현하지 않는다") |

즉 **"어떤 능력이 없는 플랫폼"은 이 앱에 이미 3개(iOS/iPadOS, 그리고 macOS 자체)가 있다.**
맥 앱스토어 Lite는 새 아키텍처를 요구하지 않는다 — **네 번째 능력 프로파일**일 뿐이다.

> **권고(→ `game-architect`, 리더 경유)**: 분리 축을 **"스토어별 빌드 분기"가 아니라 "능력 플래그"**로
> 못박을 것. `#if MAC_APPSTORE` 같은 전처리 분기는 `PlatformParityAuditTests`가 감시해야 할 항목을
> 하나 더 늘리고, 이 저장소가 이미 두 번 겪은 "한쪽 플랫폼 폴더에 갇힌 정책" 사고
> (`FullscreenSuspendPolicy` / `VisibleTopEdgeSolver`)를 세 번째로 재현한다.
> **런타임 능력 조회 1곳 + 정책은 플랫폼 중립**이라는 기존 규약을 그대로 쓰면 추가 비용이 사실상 0이다.

**→ 그러므로 이 결정은 되돌리기 비싸지 않다. 지금 확정하지 않아도 구조가 썩지 않는다.**
비싼 것은 결정이 아니라 **"맥 앱스토어용으로 무엇을 잘라야 하는지 아직 모른다"**는 사실이다.

### 1-2. 샌드박스가 정확히 무엇을 막는가 — 추측 금지, 우리 코드에 대입한 표

우리 macOS 구현이 실제로 부르는 네이티브 함수를 전부 뽑아(`Platform/MacOS/*.cs` 전수) 대입했다.

| 우리 기능 | 실제 호출 | 샌드박스 판정 | 근거 |
|---|---|---|---|
| 자기 창 투명·최상위·클릭관통 | UniWindowController(NSWindow 속성) | **통과** | 자기 창 속성. 샌드박스 대상 아님 |
| **창 열거(= 헤드라인 기능 "창 = 지형")** | `CGWindowListCopyWindowInfo` | **통과 가능성 높음, 미확인** | 샌드박스는 창 목록 **읽기**를 막지 않는다는 1차 출하 증언(Crosley, MAS 통과). ★ 우리는 `kCGWindowName`(창 제목)을 **쓰지 않는다** — 읽는 키는 Layer/Bounds/OwnerPID/OwnerName/Number/Alpha/IsOnscreen뿐(`MacWindowService.cs:543-549`). 화면기록 권한 게이트는 `kCGWindowName`에만 걸린다 |
| 〃 API 수명 | 동상 | **안전** | 10.15 이후 폐기된 것은 `CGWindowListCreateImage`(15.0에서 제거). `CGWindowListCopyWindowInfo`는 **미폐기** |
| 전역 커서 좌표 | `CGEventCreate`+`CGEventGetLocation` | **미확인** | 조회 전용. 샌드박스 사례 못 찾음 |
| 전역 키 눌림 상태 | `CGEventSourceKeyState` | **미확인 (전망 양호)** | 샌드박스에서 **차단되는 것은 `CGEvent.post`**(엔타이틀먼트 없음, 조용히 실패). **읽기 계열 `CGEventTap`은 입력 모니터링 권한으로 샌드박스 통과 확인됨.** 우리 것은 tap도 post도 아닌 더 약한 조회다 |
| **Dock 실측(도크 폭·타일 수)** | `CFPreferencesCopyAppValue("com.apple.dock")` | ★ **차단** | 타 앱 preference 도메인 읽기는 `com.apple.security.temporary-exception.shared-preference.read-only` 필요. Apple 아카이브 문서가 **정당화 제출을 요구**하고, 개발자 포럼 다수 증언이 **App Review가 임시예외를 매우 부정적으로 본다**고 기록 |
| 타 앱 창 이동/조작 | **호출 없음** | 해당 없음 | 원칙 3대로 애초에 안 한다. **샌드박스에서 가장 크게 막히는 축(크로스앱 Accessibility)을 우리는 처음부터 안 쓴다** |
| 작업표시줄 자동숨김 제어 | Windows 전용 | 해당 없음 | macOS 미구현 |
| 데스크톱 아이콘 열거 | macOS 미구현 | 해당 없음 | 〃 |
| 네트워크 | **0줄** | 통과 | `OfflineFirstNetworkAuditTests`가 잠그고 있다 |

**결론: 확정적으로 막히는 것은 Dock 실측 1건뿐이고, 헤드라인 기능은 "아마 통과"다.**
이건 기획 7절이 전제한 "오버레이·창인식 제한 → 축소판 재설계 필요"와 **결론이 다르다.**
샌드박스가 죽이는 것은 창 인식이 아니라 **크로스앱 Accessibility**이고, 우리는 그걸 안 쓴다.

> ★ **그래서 "축소판 재설계"라는 전제 자체가 아직 검증되지 않았다.** 재설계 비용을 지불하기 전에
> **하루짜리 실측 스파이크**가 먼저다. 이건 조사로 끝낼 수 없고 실기로만 답이 나온다.

### 1-3. 그런데 실측 결과와 무관하게 1차 출시에서는 뺀다 — 이유가 따로 있다

**★ 맥 앱스토어는 "새 플랫폼"이 아니다. 이미 서비스하는 플랫폼의 열등한 두 번째 창구다.**

Steam은 하나의 앱 등록으로 **Windows와 macOS 빌드를 같이 배포**한다.
즉 맥 유저는 맥 앱스토어 없이도 **제약 0의 완전판**을 받는다.
맥 앱스토어가 추가하는 것은 플랫폼이 아니라 **(a) 비스팀 맥 유저 발견 경로 + (b) 기능이 깎인 SKU**다.

| | 얻는 것 | 잃는 것 |
|---|---|---|
| 맥 앱스토어 출시 | 스팀 밖 맥 유저 노출 | $99/년 · 심사 왕복 · **Dock 실측 제거** · 별도 빌드/서명/공증 파이프라인 · **같은 제품이 채널마다 다르다는 설명 부담** |

여기에 결정타가 하나 더 있다: **이 앱은 오늘 한국어 전용이다**(3-4절). 로컬라이제이션 코드 0건.
맥 앱스토어 심사·리뷰·환불 대응을 영어 없이 감당하는 것은 1차 출시에 넣을 일이 아니다.

### 1-4. 위젯형 — **기각**

macOS 위젯은 WidgetKit(SwiftUI) 위에서 돌고, **연속 실행 코드가 아니라 타임라인 항목마다
아카이브된 뷰 스냅샷**이다. Unity 런타임을 호스팅할 수 없고, 60fps 액티브 래그돌 물리를
돌릴 수 있는 갱신 예산이 존재하지 않는다.
→ 위젯형은 **이식이 아니라 다른 기술 스택의 신규 제품**이다. 6팩 DLC·42종 장비·집중모드가
전부 이월되지 않는다. **투자 대비 회수 근거 없음. 기각.**
(★ WidgetKit의 애니메이션 예산 상세는 **미확인**. 그러나 "Unity 런타임 호스팅 불가"만으로 기각에 충분하다.)

### 1-5. 판정과 게이트

> ### 결정 1
> **맥 앱스토어는 1차 출시에서 제외한다. 위젯형은 기각. Lite는 아래 게이트를 전부 통과할 때만 착수.**
>
> | 게이트 | 통과 기준 | 담당(리더가 배정) |
> |---|---|---|
> | **G1 — 샌드박스 실측 스파이크(1일)** | `com.apple.security.app-sandbox`만 켠 최소 하니스에서 `CGWindowListCopyWindowInfo`가 **창 개수와 bounds를 실제로 돌려주는가**. ★ **양성 대조 필수** — 비샌드박스 빌드에서 같은 값이 나오는지 먼저 확인하고, 두 값이 다를 때만 "막혔다"고 판정한다(이 저장소 거짓통과 규칙 4번) | `dev-platform` |
> | G2 — 영어화 | 3-4절 선결 조건 완료 | — |
> | G3 — 수요 근거 | Steam macOS 빌드 판매 비중이 전체의 **15% 이상** | `product-strategy` 재검토 |
>
> **G1이 실패하면**(창 열거가 샌드박스에서 죽으면) Lite는 "창을 딛지 못하는 스틱메이트"가 되고,
> 그건 이 제품의 헤드라인을 제거한 것이다. → 그 경우 **맥 앱스토어는 영구 제외**를 권고한다.
> 축소판을 억지로 만드는 것보다 스팀 macOS 완전판 하나가 유저에게도 우리에게도 낫다.
>
> **Lite가 실제로 나가는 경우의 상품 형태**(G1 통과 전제): 정가 **$4.99**(스팀 완전판보다 낮게),
> **DLC 없음**(StoreKit 배선 회피), 스토어 설명 **첫 문장에 "Dock 실측 미지원" 명시**.

### 2-1. 왜 스팀이 먼저인가 — "한 번만 쓸 수 있는 자원"이 스팀에만 있다

| 채널 | 출시 순간의 성질 |
|---|---|
| **스팀** | 위시리스트 + 신규출시/인기출시 노출은 **출시일 단 한 번**만 발생하는 소모 자원이다. 최고 빌드를 여기 써야 한다 |

### 2-3. 스팀 Win+Mac 동시 — 나눌 이유가 없다

### 3-7. `ECONOMY_SPEC` 교차 검토에서 나온 것 2건 (→ `design-systems`, 리더 경유)

**(a) 산술 불일치 1건.**

**(b) ★ "산 순간 입을 것이 있어야 한다"가 현재 규칙으로는 보장되지 않는다.**
`ECONOMY_SPEC` 4-5는 **선택 1종 0동전 즉시 해금**의 목적을 그렇게 적었는데, 같은 표에서
**요구 레벨은 면제하지 않는다**고도 적었다. 두 규칙을 함께 적용하면:

> Lv.1 유저가 팩을 사고 전설(요구 Lv.28)을 고른다 → **보유는 하지만 27레벨 동안 못 입는다.**
> 팩 6종 중 Lv.1에 착용 가능한 것은 일반 2종뿐이고, 그 2종은 여전히 동전 또는 유예를 거쳐야 한다.
> **= 산 순간 입을 것이 없다.** 그 상태의 유저가 하는 일은 환불이다.

**상품 요건(내 소관)**: *팩 구매 직후, **유저의 현재 레벨과 무관하게** 즉시 착용 가능한 아이템이
최소 1종 존재해야 한다.* 이건 환불률에 직결되는 구매 경험 요건이다.
**동전 수치와 규칙 형태는 `design-systems` 소관이다.** 참고용 후보 한 가지만 적어 둔다 —
"무상 1종을 **현재 레벨에서 착용 가능한 것 중에서만** 고르게 한다"(요구 레벨 면제 없이 요건 충족).

### 4-1. 경계 원칙 한 줄

> **무료 = 이 앱이 하겠다고 약속한 일 전부. 유료 = 그 일을 다른 목소리·다른 몸짓으로 하는 것.**
> 기능은 절대 유료 뒤로 가지 않는다. 24시간 상주하며 "동료"를 자처하는 앱이
> 일하는 능력에 값을 매기면 그건 동료가 아니라 구독이다.

### 4-2. ★ 슈퍼히어로 팩에는 선결 조건이 있다 — 업적 시스템이 존재하지 않는다

**실측(2026-09-02):** `grep -rli "achievement"` → **0 파일.** `grep -rl "업적"` → **0 파일.**

"슈퍼히어로 팩 = 업적 보상 전용"은 **존재하지 않는 시스템 위에 서 있는 무료·유료 경계**다.
→ 이 경계를 지키려면 업적(또는 그 역할을 하는 장기 달성 채널)이 먼저 필요하다.
**신규 인프라 0개 후보**: `ECONOMY_SPEC` 6-3이 이미 지목한 `CharacterStatsModel.TotalCompanionSeconds`
(이미 저장·표시되지만 보상이 전혀 없는 값). 판단은 기획·총괄 소관이고, 나는 **의존성만 신고**한다.

**상품전략 관점의 제약 2건**(팩이 실제로 만들어질 때 지켜야 할 것):
1. 업적 보상 팩은 **유료 팩과 같은 2/2/1/1 구조·같은 수치**여야 한다. 더 세면 유료 팩이 죽고,
   눈에 띄게 초라하면 "무료라서 대충"이 된다. 차이는 **획득 조건의 길이**여야 한다.
2. 이 팩은 **강력한 신뢰 신호**다 — "가장 멋진 팩이 무료"라고 스토어에서 말할 수 있으면,
   24시간 상주 앱이 가장 크게 의심받는 지점(과금 압박)을 첫 화면에서 해소한다. **마케팅 자산으로 쓸 것.**

### 4-3. 시즌 DLC — 형태 권고 (기획 확정 사항의 *형태*만 조정, 리더 승인 필요)

기획은 "계절 소품 = 시즌 DLC"까지 정했고 **판매 형태는 정하지 않았다.**

> **권고: 계절별 개별 판매를 하지 않는다. 연 1회 "사계절 팩" $2.99 하나로 묶는다.**
>
> 근거: 24시간 상주 앱에서 **연 4회 "새 시즌이 나왔습니다" 알림**은 정확히 기획이 피하려던
> 과금 압박 루프의 형태다(`ECONOMY_SPEC` 4-3이 일일 캡을 기각한 것과 같은 사고).
> 알림 4번을 1번으로 줄이면서 매출은 같거나 낫다($0.99×4 = $3.96 → 실구매 전환율을 감안하면 $2.99 일괄이 유리).
> 그리고 **시간대 소품 최소 버전이 무료**이므로(기획 확정) 미구매자가 계절에 소외되지 않는다.

### 4-4. 체험 경로 — 무료 채널 SKU를 만들지 않는다

"써 보고 사고 싶다"는 요구는 실재하지만, **그 답이 "MS 스토어에 무료판"이면 스팀 유료판이 죽는다**
(같은 exe가 한쪽에서 공짜인데 다른 쪽에서 $7.99일 이유를 유저에게 설명할 수 없다).
→ 체험은 **채널 기능**으로 푼다: 스팀 데모(별도 스토어 페이지) + MS 스토어 체험판 + 이미 스키마에 있는
`previewKey`(DLC 3분 체험). **SKU를 늘리지 않는다.**

> ★ **리더 확인 요청**: 사용자 조사표의 "MS 스토어 **무료**"를 나는 **입점 비용 $0**으로 읽었다
> (스팀 칸의 $100과 같은 축이므로). 만약 **제품 가격을 0원으로 하겠다는 뜻**이었다면 이 문서의
> 3절·4절이 통째로 달라진다(전 채널 F2P + DLC 가격 상향 + 팩 수 증설이 필요). **사용자 확인 필요.**

  결정 1의 G1 스파이크는 `Platform/MacOS/` 위에서만 성립하는 실측이다. 그 결과에 따라
  `IDockMetricsService`의 macOS 구현에 **"샌드박스에서는 사실 조회 실패 → 안전 기본값"** 경로가
  필요해질 수 있다. 정책이 아니라 사실 조회의 실패이므로 기존 `FallbackPlatformWindowService`
  규약 안에서 처리 가능하며, **플랫폼 중립 정책을 건드리지 않는다.**
  ★ 스파이크는 **양성 대조 필수**(비샌드박스 빌드에서 같은 호출이 값을 주는지 먼저 확인).
  그 대조 없이 "0건 = 막힘"으로 읽는 것이 이 저장소 거짓통과 4번의 재현이다.
- 이 라운드에서 만든 결정은 전부 **데이터/문서**에 산다. 실행 시점에 코드로 내려가는 것은
  `StickPackManifestSO.channels` flags 한 필드뿐이고, 그건 이미 `ARCHITECTURE.md` 5-3-2에 있다.

## 10. ★ 결정 5 — 코드서명 · 공증 (2회차 신규. 지난 회차 판정을 뒤집는다)

> **지난 회차 내 판정**: *"스팀은 서명을 요구하지 않는다. 서명은 MS 스토어 채널 항목이다."*
> **→ 절반이 틀렸다.** Windows에 대해서는 참이고, **macOS에 대해서는 거짓이다.**
> 그리고 채널이 스팀 단독으로 확정되면서 *"MS 스토어 항목"*이라는 분류 자체가 없어졌다.

### S-0. 먼저 — 무엇이 「채널 요구」이고 무엇이 「위험 완화」인가

이 둘을 섞으면 우선순위를 못 정한다. **1차 출처로 갈랐다.**

| | Windows | macOS |
|---|---|---|
| **스팀이 요구하는가** | **아니다.** Steamworks 플랫폼 문서에 Windows 코드서명 요구가 **없다** | ★ **그렇다.** *"Starting October 14th, 2019 Steam will require all new macOS Applications to be 64-bit and notarized by Apple."* |
| 따라서 서명은 | **위험 완화**(해도 되고 안 해도 출시된다) | **채널 게이트**(안 하면 출시 자격 자체가 없다) |
| 1.0 차단 항목인가 | **아니다** | ★ **그렇다 — 승격** |

★ **이 비대칭이 이번 라운드의 핵심이다.** 지난 회차의 나는 Windows를 걱정하고 macOS를 비워 뒀는데,
**막고 있는 쪽은 macOS다.**

### S-1. macOS — **1.0 차단 항목으로 승격한다** (판정)

**실측 재확인 (2026-09-02, `codesign` — `security`가 쓴 `spctl`과 다른 도구로 다시 쟀다):**

```
Builds/macOS/StickMate.app
  Identifier=com.DefaultCompany.StickMate          ← ★ 유니티 기본값 그대로
  CodeDirectory ... flags=0x2(adhoc)
  Signature=adhoc                                   ← TeamIdentifier 없음
```

애드혹 서명이므로 **공증이 물리적으로 불가능**하다(공증은 Developer ID Application 인증서를 요구).

**승격 근거는 Gatekeeper 마찰이 아니라 채널 요구다.** 스팀 파트너 문서가 신규 macOS 앱에
공증을 요구하고, **스팀은 우리의 유일한 채널**이다.

> **★ 미확인 1건 (숨기지 않는다)**: `security`가 찾은 2019년 Valve 모더레이터 답변
> *"we will allow your game to ship on Steam without notarization at this time"*이 파트너 문서와
> 어긋난다. **2026년 현재의 실제 집행 여부는 Steamworks 로그인 후에만 확인 가능**하고,
> 나는 스토어 계정을 조작하지 않는다.
> **그럼에도 판정을 바꾸지 않는 이유**: 집행이 느슨하더라도 **Apple 쪽은 느슨해지지 않는다.**
> 스팀 밖으로 나가는 모든 macOS 빌드(프레스 키 대신 보내는 zip, 개발일지 데모, 베타 테스터 배포)는
> `com.apple.quarantine`이 붙고 **애드혹은 그 자리에서 막힌다.** `marketing`이 macOS 빌드를
> 한 번이라도 손으로 배포하는 순간 필요해지는 물건이다.

**비용**

| 항목 | 값 | 출처 |
|---|---|---|
| Apple Developer Program | **$99/년** | Apple 멤버십 비교표 |
| ★ 그런데 **신규 비용이 아니다** | CLAUDE.md가 명시한 **iPad/iPhone 타깃에 어차피 필요**하다 → **선지출** | CLAUDE.md 서두 |
| 구현 비용 | 하드닝 런타임 + Developer ID 서명 + `notarytool` 제출 + `stapler` 스테이플. **중첩 Mach-O 전부 딥서명 필요** — 저장소에 `LibUniWinC.bundle`(유니버설 네이티브 플러그인)이 있다 | 저장소 실측 |
| 스팀 오버레이 제약 | 하드닝 런타임에 `com.apple.security.cs.disable-library-validation` + `com.apple.security.cs.allow-dyld-environment-variables` 필요 | Steamworks 플랫폼 문서 |
| 유저 마찰(방치 시) | 스팀 경유는 오늘 통과할 수 있으나 **그 통과는 스팀 클라이언트 동작에 기댄 우연**이고, 스팀 밖 배포는 **우클릭 → 열기**를 강요한다 | — |

### S-2. Windows — **EV 기각 / OV(또는 Artifact Signing) 채택 / 1.0 차단 아님** (판정)

**(a) EV 기각 — 1차 출처가 명시적이다.**

> *"EV certificates no longer bypass SmartScreen. … Paying a premium for EV solely to avoid
> SmartScreen warnings is no longer justified."* — Microsoft Learn, SmartScreen reputation (갱신 2026-08-17)

Microsoft의 비교표는 EV를 **$400+/년**으로 적고 *"No longer recommended specifically for
SmartScreen bypass"*로 분류한다. → **기각.**

**(b) ★ 그러나 OV도 「첫 경고를 없애 주지 않는다」 — 두 에이전트가 인용하지 않은 줄이다.**

같은 페이지의 표에서:

> **`Valid Certificate (OV/EV)` → `⚠️ Warning — app flagged as unrecognized until reputation
> accumulates; verified publisher name is displayed`**

**서명해도 첫 경고는 뜬다.** 그러므로 *"서명하면 유저가 경고를 안 본다"*는 **소재로 쓰면 거짓이다**
(→ `marketing`에 그대로 넘긴다). 서명이 실제로 사는 것은 딱 두 개다:

1. **경고 화면에 퍼블리셔 이름이 뜬다** (무서명은 "알 수 없는 게시자")
2. ★ **버전을 넘어 평판이 이어진다** — *"Unsigned files must build reputation anew with every update."*
   **상주 앱은 업데이트가 잦다.** 무서명이면 **릴리스마다 평판이 0으로 리셋**된다. 이게 진짜 값이다.

**(c) 그런데 스팀 단독 채널에서 이 값이 얼마나 큰가 — 정직하게 줄여 잡는다.**

SmartScreen의 다운로드 경고는 **Mark of the Web이 붙은 파일**에 대해 동작한다. 스팀 클라이언트는
자체 다운로더로 콘텐츠를 내려받는다. → **스팀 경유 설치에는 SmartScreen 다운로드 경고가
대체로 해당하지 않는다.** ★ **단 "스팀이 MOTW를 붙이지 않는다"는 나의 1차 출처가 없다 — 미확인.**

**남는 진짜 노출은 Smart App Control이다:**

> *"Smart App Control will block execution of unsigned files unless the file has a positive reputation.
> Smart App Control signature checks apply to **all executable files, not just those downloaded from
> the Internet**."* — 같은 페이지

**MOTW를 보지 않으므로 스팀 경유로도 비켜 갈 수 없다.** 이것이 Windows에서 서명을 사는 유일한
확실한 근거다.
★ **SAC가 켜져 있는 기기 비율은 미확인.** Microsoft는 공개하지 않는다. MS 지원 FAQ는
*"Recent Windows updates allow Smart App Control to be enabled without requiring a clean installation"*이라
모수가 넓어지는 방향임을 시사하지만, **숫자를 지어내지 않는다.**

**(d) ★★ 그래서 실제 선택지 — 여기서 리더가 받은 브리프와 갈린다**

브리프는 선택지를 *"저렴한 OV/Artifact Signing vs 없음"*으로 정리했다. **Artifact Signing은
우리가 살 수 없을 가능성이 높다.**

> *"Azure Artifact Signing is available to organizations in the USA, Canada, the European Union, and
> the United Kingdom. **Individual developers are currently limited to the USA and Canada.**
> If you are an individual developer outside those regions, see OV certificates below."*
> — Microsoft Learn, Code signing options (갱신 2026-08-29)

**우리는 한국의 개인 개발자다 → $9.99/월 경로는 닫혀 있다.**

★ **그리고 여기서 Microsoft 문서 두 개가 서로 어긋난다 — 그대로 보고한다.**

| 페이지 | 조직 대상 국가 | 개인 대상 국가 |
|---|---|---|
| Code signing options (갱신 **2026-08-29**) | USA · Canada · EU · UK | **USA · Canada** |
| Artifact Signing Quickstart (갱신 **2026-08-11**) | USA · Canada · EU · UK · 호주 · 뉴질랜드 · 일본 · **대한민국** · 싱가포르 · 스위스 · 노르웨이 · 이스라엘 | **USA · Canada** |

**개인은 두 문서가 일치(USA/Canada)한다 — 그래서 개인 자격 결론은 흔들리지 않는다.**
갈리는 것은 **조직**이고, Quickstart(더 구체적인 쪽)는 **대한민국을 포함**한다.
→ **사업자등록이 있으면 $9.99/월이 열릴 수 있다. 이건 "가격 문제"가 아니라 "법인격 문제"다.**
**미확인 — 결재 전 Azure 포털에서 확인 필요.**

| 안 | 비용 | 우리에게 가능한가 | 부대 조건 |
|---|---|---|---|
| Artifact Signing | **$9.99/월 ≈ $120/년** | ★ **개인 자격으로는 불가.** 사업자등록 시 가능성 있음(문서 충돌, 미확인) | 하드웨어 토큰 불필요, CI/CD 직결 |
| **OV 인증서** | **$150~300/년** | **가능**(전 세계) | ★ 2023-06 CA/B Forum 규정으로 **개인키를 HSM/하드웨어 토큰에 보관 필수** → 물리 토큰 국제 배송 또는 클라우드 HSM. **CI 자동서명이 번거로워진다** |
| EV | $400+/년 | 가능 | **기각**(위 (a)) |
| 무서명 | $0 | 가능 | SAC 차단 위험 + **업데이트마다 평판 리셋** |

★ **OV의 주체 문제 — 미확인 1건.** OV는 이름 그대로 *Organization* Validated이고 MS 문서도
*"The CA validates your **organization's** legal identity"*로 쓴다. **개인 개발자에게 CA가
개인(IV) 코드서명 인증서를 발급하는 경로**는 실무상 존재하지만, **DigiCert/Sectigo의 현행 개인 발급
조건과 가격은 확인하지 못했다.** 결재 전 CA에 직접 확인해야 한다.

**(e) 판정**

> **Windows 서명을 채택한다. 단 1.0 출시를 막지 않는다.**
> **데드라인은 「1.0」이 아니라 「첫 업데이트를 내기 전」이다.**
>
> 근거: 서명이 사는 것은 **버전을 넘는 평판 연속성**이고, 그 연속성은 **서명을 시작한 릴리스부터**
> 쌓인다. 1.0에 못 맞춰도 영구히 잃는 것이 없다. 반대로 **무서명으로 업데이트를 여러 번 내면
> 그 횟수만큼 평판이 리셋**되고 그건 되돌릴 수 없다. **상주 앱은 업데이트가 잦다.**
>
> 우선순위: **(1) 사업자등록 여부 확인 → 있으면 Artifact Signing($120/년, 토큰 없음)**
> **(2) 없으면 OV($150~300/년 + 토큰)** **(3) EV는 어떤 경우에도 사지 않는다.**

### S-3. ★ 비용 대비 — **"정당한 유저 한 명 잠그기 > 무단 사용 열 건"** 기준으로 재본다

`security` 정의서의 이 문장을 서명에 그대로 대입하면 방향이 **한쪽으로만** 난다.

| | 서명했는데 아무도 경고를 안 봤을 경우 | 서명 안 했는데 SAC/백신이 막았을 경우 |
|---|---|---|
| 잃는 것 | **연 $120~300** | **그 유저를 영구히 잃는다.** F2P라 매몰비용이 0이라 **되돌아오지 않는다** |
| 되돌릴 수 있는가 | 예(갱신 안 하면 끝) | **아니오** |

★ **F2P가 이 비대칭을 키운다.** 유료 앱이면 유저가 이미 돈을 냈으므로 경고를 뚫을 동기가 있다.
**무료 앱에서 경고를 만난 유저는 그냥 지운다** — 뚫을 이유가 없다. 즉 **F2P 확정이 서명의 값을 올렸다.**

★ **백신(AhnLab V3 등) 오탐은 별개 축이다.** 우리 네이티브 표면은 실측상 `EnumWindows` ·
`GetWindowTextW` · `GetAsyncKeyState` · `GetLayeredWindowAttributes` · `SHAppBarMessage` ·
`GetLastInputInfo` 등이고(저장소 grep), **종일 상주**와 결합하면 애드웨어/키로거 휴리스틱과 형태가 겹친다.
> **★ 그러나 "서명하면 백신 오탐이 준다"는 나에게 1차 출처가 없다. 직관이다.**
> 서명은 **오탐 신고(false positive submission) 창구에서 신원을 증명하는 수단**으로는 확실히 값을 하지만,
> 탐지율 자체를 낮춘다는 것은 **미확인**이다. 소재로 쓰지 마라.

### S-4. ★ 서명이 끌고 나온 **주인 없는 되돌릴 수 없는 결정 1건** (이번 라운드 신규 발견)

서명·공증을 하려면 **번들 식별자와 회사명을 먼저 정해야 한다.** 오늘 값은 유니티 기본값이다.

**실측 (2026-09-02):**
```
ProjectSettings/ProjectSettings.asset
  companyName: DefaultCompany
  applicationIdentifier: {}                 ← 비어 있음
  overrideDefaultApplicationIdentifier: 0
→ 결과 번들 ID: com.DefaultCompany.StickMate   (codesign 출력과 일치)
```

**왜 이게 상품 전략 소관인가**: 번들 ID는 **스토어 레코드의 영구 기본키**다. iOS/iPadOS(CLAUDE.md 타깃)에서는
**첫 제출 이후 변경이 불가능**하다. 즉 이건 조형이나 구현이 아니라 **상품 식별자 결정**이다.

**★ 그리고 지금 바꾸지 않으면 유저 데이터가 걸린다 — 저장소 실측:**

`CharacterSaveStore.cs:331`과 `ReservedBarRestoreLedger.cs:99`가 둘 다
`Application.persistentDataPath` 아래에 쓴다. 유니티의 이 경로는 **`companyName`/`productName`에서
파생**된다. → **출시 후에 `companyName`을 바꾸면 두 파일이 통째로 다른 경로로 이사한다.**

| 이사하는 파일 | 결과 |
|---|---|
| `stickmate_character.json` | **유저 진행도 전량 소실**(파일은 남지만 앱이 못 찾는다) |
| `ReservedBarRestoreLedger` | ★ **더 나쁘다.** 이건 CLAUDE.md 원칙 3의 **승인된 예외 1건이 성립하기 위한 안전장치**다 — *"크래시로 원복 훅이 못 돌아도 다음 실행이 디스크 흔적을 보고 먼저 복구한다(그 장치가 없으면 이 예외는 성립하지 않는다)"*. 경로가 바뀌면 **대기 중이던 원복 흔적이 영원히 안 읽히고, 유저의 작업표시줄 자동 숨김이 꺼진 채로 남는다** |

> **판정 권고: `companyName` 확정을 서명 작업의 선행으로, 그리고 「1.0 출시 전」으로 못박는다.**
> 오늘 바꾸면 비용은 **필드 2개**다. 출시 후에 바꾸면 **마이그레이션 코드 + 유저 데이터 사고**다.
> ★ 되돌릴 수 없는 결정이므로 **`game-architect`와 리더 판정 대상**이다. 나는 이름을 고르지 않는다 —
> **그 자리가 비어 있다는 사실**을 신고한다.

## 10-B. 상시 발굴 — 이번 라운드 신규 아이디어 4건

**규율**: 하나마다 **근거 / 대가 / 버리는 조건** 셋을 붙인다. 근거가 없으면 **"직관"이라고 명시**한다.
**이미 닫힌 것을 다시 올리지 않는다** — 미니 보스 레이드(제외 확정), 격파 놀이(제거), 동전 현금 판매(P-1),
개별 아이템 판매(P-6), MS 스토어, 맥 앱스토어 1차 출시는 **전부 닫혀 있고 아래에 없다.**

### 아이디어 A — **서명 사실을 스토어 페이지에 「기능」으로 적는다** (판매 전략)

무서명 상주 앱은 이 카테고리에서 *"이거 안전한가요"*를 상수로 만든다. 우리는 서명·공증을 하기로 했으니
**그 사실 자체가 팔 거리**다. 단 **"경고가 안 뜬다"고 쓰면 거짓**이다(OV도 첫 경고는 뜬다).
쓸 수 있는 참인 문장은 **"서명된 빌드 / 네트워크 통신 없음 / 관리자 권한 요구 없음"** 세 개다.

- **근거**: `MARKET_LANDSCAPE.md` 3-3(Shimeji를 죽인 것은 기능이 아니라 배포 — 백신 경고가 상수였다)
  + P6·P10 페르소나. 그리고 **저장소 실측** — `OfflineFirstNetworkAuditTests`가 네트워크 부재를 이미 잠그고 있다.
- **대가**: 서명 비용 선지출($99 + $120~300)이 **소재보다 먼저** 와야 한다. 그리고
  **과장 한 줄이면 이 소재 전체가 역효과**가 된다(카테고리 유저는 이 주제에 민감하다).
- **★ 버리는 조건**: 서명 채택이 기각되면 **즉사**. 또한 *"경고가 안 뜬다"*로 문안이 바뀌는 순간
  **거짓 소재**가 되므로 그때도 버린다.
- 소관: 문안은 **`marketing`**. 나는 **팔 수 있는 사실의 목록**만 넘긴다.

### 아이디어 B — **팩 SKU를 선물 가능으로 설계한다** (판매 전략, 구현 비용 낮음)

- **근거**: P8. Steamworks 문서상 **DLC 선물 구매 가능**, 번들 선물에도 **"세트 완성" 자동 차감**이
  적용되어 **중복 구매 사고가 구조적으로 안 난다**(9절 출처). ★ **F2P가 이걸 특별히 잘 맞게 만든다** —
  받는 사람이 이미 본편을 깔아 놓았을 확률이 높다.
- **대가**: 스팀의 **저가 지역 → 고가 지역 선물 제한**에 한국발 선물이 걸릴 수 있다.
  ★ **정확한 판정 기준 미확인**(2차 요약 의존). 그리고 이건 **스토어 설정 항목**이라
  내가 조작할 수 없다 — 사용자/리더의 결재 행위다.
- **★ 버리는 조건**: 지역 제한이 **한국 계정 발 선물을 사실상 전부 막는 형태**로 확인되면
  국내 사용자에게는 죽은 기능이 되므로, 그때는 **소재에서 빼고 설계에서만 남긴다**(영어권 유저끼리는 유효).

### 아이디어 C — **출시 주 한정 「6팩 완전판」 할인** (첫 결제 문턱을 팩 가격이 아니라 번들로 푼다)

F2P의 가장 비싼 순간은 **0원 → 첫 결제**다. 그런데 **팩 하나만 깎으면 P-4(구조가 같으면 가격도 같다)가
흔들린다.** 번들만 한시 할인하면 **낱개 가격표는 건드리지 않고** 문턱만 낮출 수 있다.

- **근거**: F2P는 **Daily/Midweek/Weekend Deal 자격이 없다**(`ROADMAP` B-3, Steamworks 확인).
  즉 **우리가 쓸 수 있는 할인 수단이 애초에 적다** — 남은 칸을 아는 것이 근거다.
  ★ **"첫 결제가 가장 비싸다"는 명제 자체는 업계 통념이고 나에게 1차 출처가 없다 — 직관.**
- **대가**: 출시 주에 팩 6개가 **전부 완성돼 있어야 한다.** 오늘 DLC 단계 C(R-5)는 0%다 →
  **1.0 출시 주에는 물리적으로 불가능**할 가능성이 높다. 그러면 이 카드는 **"DLC 출시 주"로 미뤄진다.**
- **★ 버리는 조건**: 스팀의 출시 할인 규칙이 **F2P 앱의 DLC 번들 할인을 제한**하는 것으로 확인되면 즉사.
  ★ **할인 간격·출시 할인 세부는 여전히 미확인**(7절 #4, Steamworks 로그인 필요).

### 아이디어 D — ★ **팩을 "옷장"이 아니라 "그 팩만의 어조"로 판다** (상품 고도화 — 재구매를 만드는 축)

**재구매 문제의 정직한 진단부터**: 코스메틱 6팩은 **한 번 사면 끝**이다. 우리는 확률형도 없고
소모품도 없고 시즌 패스도 없다(전부 원칙상 안 만든다). **그러면 두 번째 결제는 어디서 오는가?**

관측: 우리 팩은 이미 **대사·모션·사운드·팔레트**를 포함하기로 설계돼 있다(`ROADMAP` 3-3, 가격 근거).
즉 팩은 **아이템 묶음이 아니라 「캐릭터가 다르게 말하고 다르게 움직이는 상태」**다.
그렇다면 **팩끼리 서로 다른 것이 팩을 여러 개 사게 만드는 유일한 정당한 이유**가 된다 —
"옷이 6벌 더"가 아니라 "**오늘은 다른 애랑 일한다**".

- **근거**: 저장소 실측 — `design-narrative`가 **세트 어조 전환**을 이미 소유하고 있고
  (`docs/TEAM.md` 역할표), 팩 6종은 **테마**로 확정됐다(커밋 `eca8c58` "세트는 테마").
  즉 **이 축은 새로 만드는 것이 아니라 이미 있는 것을 가격 논거로 쓰는 것**이다.
- **대가**: 팩마다 **대사 풀이 진짜로 갈려야 한다.** 갈리지 않으면 이건 **거짓 소재**가 되고,
  ★ **원칙 1(행동-텍스트 싱크)** 때문에 대사는 상태 전이에서만 파생될 수 있다 →
  **어조 전환이 상태 기계를 건드리지 않고 가능한지**가 선결이다. 그건 내 소관이 아니다.
- **★ 버리는 조건**: `design-narrative`/`game-architect`가 **"팩별 어조 분기는 상태 기계 수정 없이
  불가능"**으로 판정하면 **가격 논거에서 즉시 뺀다.** 팔 수 없는 것을 가격 근거로 쓰면
  그게 `marketing`에 내려가 거짓 소재가 된다.
- 소관 경계: **나는 "이것이 팩의 가격 논거이자 재구매 논거"라는 것까지만 말한다.**
  어조 설계·상태 기계 판정은 각각 `design-narrative`·`game-architect`이고 **직접 지시하지 않는다.**

## 11. 보류 기록 — 다시 올리지 않는다 (리더 지시)

### E-7 「환불창 폐쇄」 — **철회됨. 그러나 실측은 참이고 보관 가치가 있다**

- **실측(참)**: 스팀 환불 정책상 DLC는 *"구매 이후 본편 플레이 2시간 미만"*일 때만 환불된다.
  **StickMate는 종일 상주하므로 유저가 아무 조작을 하지 않아도 2시간 뒤 조건이 깨진다.**
  즉 우리 제품에서 **DLC 환불창은 사실상 구매 직후 2시간뿐**이다.
- **왜 철회됐나**: 오늘의 설계에는 **해당하는 피해 시나리오가 없다.**
  사용자 확정 설계상 **DLC 아이템과 기본 42종은 겹치지 않는다** → 유저가 같은 것을 두 번 살 수 없다
  → **이중 지불이 성립하지 않는다.**
- ★ **되살아나는 조건 (이것 때문에 적어 둔다)**:
  **장래에 "DLC 아이템과 기본 42종의 겹침"을 허용하는 설계가 논의되면, 그 자리에서 이 실측을 먼저 꺼낸다.**
  겹침이 생기는 순간 *"동전으로 이미 산 것을 팩에서 또 산다"*가 가능해지고,
  그때는 **환불로 되돌릴 수 없다**(2시간이 이미 지나 있다). P-2·P-6과 함께 읽어야 한다.
- **오늘 상태**: **닫힘. 다시 제안하지 않는다.**
