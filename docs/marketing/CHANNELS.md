# 채널 설계 — 직장인에게 어떻게 도달하는가

작성: marketing / 2026-09-02
**의존**: 가격·스토어 선택·출시 순서·DLC 구성은 `product-strategy` 소관.
아래에서 **[전략팀 확정 대기]** 로 표시한 칸은 그쪽이 정해야 채워진다.

---

## 1. 출발점 — 기획 7절이 지적한 구멍

> 스팀 유저 상당수가 직장인과 겹치지만, **알고리즘은 "게임 찾는 유저" 위주 노출**이라
> 직장인 타겟 유입은 유튜브·개발일지 등 외부 채널에 더 의존해야 한다.

이건 맞다. 다만 **한 겹 더 들어가야 실행 가능한 계획이 된다.** 그대로 두면
"유튜브 하자"라는 말과 다르지 않다. 아래 세 가지를 먼저 확정한다.

---

## 2. ★ 이 제품의 채널상 특이점 3가지 (여기서 계획이 나온다)

### 2-1. **설명이 필요 없다 — 데모가 곧 제품이다**

대부분의 게임은 "재미"를 3초 안에 못 보여준다. 그래서 트레일러·리뷰·스트리머가 필요하다.
**이 앱은 반대다.** `MOMENTS.md` M5(창 도둑 2.7초), M7(창 부수기 3.4초)은
**자막도 소리도 없이** 무슨 일인지 읽힌다(C2).

**결론**: 이 제품은 **짧은 무음 영상 플랫폼에서 구조적으로 유리**하다.
길게 설명하는 콘텐츠에 예산을 쓰지 않는다. **길이가 짧을수록 이 제품에 유리하다.**

### 2-2. ★★ **개발일지 독자와 이상적 초기 고객이 같은 사람이다**

"직장인 타겟인데 개발일지는 개발자에게 닿는다 = 어긋남"이라고 보기 쉽다. **그렇지 않다.**
이 제품이 무엇을 요구하는지 보면 반대 결론이 나온다.

| 이 제품이 잘 맞는 사람의 조건 | 개발자·기술 직군이 그런가 |
|---|---|
| 하루 종일 데스크톱 앞에 있다 | **그렇다** |
| 창을 여러 개 띄운다(발판이 많다 = 놀 곳이 많다) | **그렇다. 가장 많이 띄운다** |
| 화면이 넓다(멀티 모니터) | **그렇다** |
| "권한을 요구하는가 / 포커스를 뺏는가"를 실제로 따진다 | **그렇다. 이 앱의 가장 강한 패가 여기서만 통한다** |
| 이미 스팀 계정이 있다 | **그렇다** |
| 상주 프로그램의 CPU·전력을 신경 쓴다 | **그렇다** — `FramePacing` 4단계가 여기서만 셀링포인트가 된다 |

**즉 개발일지는 "타겟이 아닌 곳에 쓰는 우회로"가 아니라 가장 정확한 교두보다.**
창을 3개만 띄우는 사무직에게는 발판이 3개뿐이지만, 개발자 화면에서는 이 앱이 가장 잘 논다.

**→ 채널 전략: 기술 직군을 1차 교두보로 삼고, 거기서 나온 소재(=사용자가 자기 화면에서 찍은
클립)를 일반 직장인 채널로 확산시킨다.** 우리가 직접 일반 직장인에게 광고하는 것보다,
**"동료 화면에서 봤다"**가 이 제품에는 훨씬 강한 경로다.

### 2-3. **트러스트가 곧 콘텐츠다 — 그리고 그 증거가 이미 코드에 있다**

`TRUTH_INVENTORY.md` 0절: 권한 0, 네트워크 API 0건, 타 창 변경 API 없음.
**중요한 건 이게 "우리 주장"이 아니라 "자동 검사 + 네거티브 컨트롤"이라는 점이다.**

기술 독자에게 이건 그 자체로 읽을 거리다:
- *"우리는 '네트워크를 안 쓴다'고 말하지 않는다. **일부러 위반 코드를 넣어 검사가 빨개지는지
  확인하는 테스트**를 함께 넣었다."*
- 이 프로젝트에는 **"0건이라 초록인 줄 알았는데 아무것도 안 재고 있었다"는 실패 기록이 9건**
  있고(TEAM.md 4절), 그 실패들이 바로 이 규율이 생긴 이유다.

**이건 지어낼 수 없는 콘텐츠다.** 그리고 경쟁 데스크톱 펫이 따라 하기 가장 어려운 부분이다.

## 3. 채널 배치

### 3-1. 1차 — 소유 채널(개발일지)

**이 프로젝트의 개발 기록은 이미 콘텐츠다.** 지어낼 필요가 없다.

| 소재 유형 | 이미 있는 실제 재료 | 왜 읽히는가 |
|---|---|---|
| **측정이 거짓말한 이야기** | *"배치모드가 9,300~13,200fps라 180프레임 예산이 실제로는 0.014초였다"* → 통과하던 테스트 8건이 아무것도 안 재고 있었음 | 테스트를 짜 본 사람 전원이 서늘해진다 |
| **자를 먼저 의심하라** | 획 두께 지표가 정점만 샘플링해 0.58W를 3.77W로 읽고 있었다 | 위와 같은 계열, 더 짧게 말할 수 있다 |
| **수치가 통과시킨 것을 눈이 잡았다** | 액세서리 4라운드 전부 초록불이었는데 실제 캡처에서 **선글라스가 화살표로, 목도리가 장화로** 보였다 | "그 이름의 물건으로 보이는가는 잰 적이 없다" — 한 줄 결론이 강하다 |
| **창이 지형이 되기까지** | 착지 판정이 ±20pt 밴드라 **2.2유닛만 떨어져도 한 프레임에 통과**해 창을 뚫고 지나갔다 → 스윕 교차로 교체. 결과 **오차 0.0pt** | 제품 헤드라인 기능의 탄생 서사 |
| **Dock 폭을 재는 데 실패한 이야기** | 정확한 폭은 화면 기록 권한으로만 얻히는데 **원칙 때문에 포기하고, 대신 틀리는 방향을 안전한 쪽(65% < 실측 70.7%)으로 골랐다** | **권한 0 서사의 가장 좋은 증거.** "안 쓴 게 아니라 못 쓰기로 했다" |
| **원칙을 실물로 증명** | 가짜 균열 위로 계산기 `7`을 실제로 눌러 통과 확인 | `MOMENTS.md` M7과 같은 소재. **글과 GIF가 한 몸** |

**형식과 박자**
- **주 1회, 실제로 일어난 일이 있을 때만.** 없는 주는 건너뛴다. 이 프로젝트에서 지어낸 문서가
  실재와 갈라진 사고가 반복됐고, 개발일지는 그 위험이 **밖으로** 나가는 통로다.
- 한 편 = **결론 1개 + 숫자 + GIF 1개.** 길게 쓰지 않는다.
- **모든 편은 "무엇이 틀렸는가"로 시작한다.** 성과 자랑은 읽히지 않고, 실패는 읽힌다.
  그리고 이 저장소의 정직성 규칙(TEAM.md 5절)과 어조가 정확히 일치한다.
- 게시처: [전략팀 확정 대기] 스팀 페이지 개발일지를 쓸 수 있는지가 스토어 결정에 달려 있다.
  **스토어와 무관하게 성립하는 자체 블로그/깃허브 릴리즈 노트를 1차 거처로 삼기를 권고한다.**

### 3-2. 2차 — 짧은 영상

2-1의 구조적 이점이 여기서 현금화된다. **긴 영상을 만들지 않는다.**

| 포맷 | 길이 | 소재 | 근거 |
|---|---|---|---|
| **루프 GIF** | 2~6초 | M5 창 도둑 / M7 창 부수기 / 쇼케이스(S7 루프 만족 시) | `MOMENTS.md` C1 |
| **쇼츠/릴스** | 8~15초 | M1 활쏘기(접근부터 정중앙까지) | 3막 구조가 코드로 보장됨 |
| **"3초 실험"** | ~10초 | M7 + 균열 위로 실제 클릭 | **전환에 가장 직접적으로 작용할 소재** |

**핵심 규율**: 첫 1초 안에 **남의 창 위에 캐릭터가 서 있는 그림**이 나와야 한다(C4).
안 그러면 "스틱맨 애니메이션"으로 스크롤된다.

### 3-3. 3차 — 커뮤니티

- **우리가 글을 쓰는 것보다 사용자가 자기 화면을 찍게 하는 것이 낫다.** 2-2 결론.
- 그래서 **공유 마찰을 낮추는 것이 마케팅 과제**가 된다.
  다만 `MOMENTS.md` 5절대로 **화면 캡처 권한을 요구하는 자동 GIF는 반대**한다 —
  OS 기본 캡처 도구로 이미 되는 일이다. 대신 **"어떻게 찍어서 올리는지"를 우리가 안내**한다.
- 게시·응대는 전부 **리더 승인 후 사용자가** 한다. 마케팅은 초안만 만든다.

### 3-4. 스토어 페이지 — [전략팀 확정 대기]

확정 전에도 정할 수 있는 것만 여기 적는다.

**태그 방향**(어느 스토어인지와 무관):
- 강조: `데스크톱 펫` / `상주형` / `방해하지 않음` / `자동 진행(관찰형)` / `오프라인`
- **피할 것**: `게임` 단독 포지셔닝. 조작이 없다(키보드 입력 자체가 설계에서 폐기됐다).
  "플레이"를 기대하고 산 사람은 환불한다. **"지켜보는 것이 코어 루프"**라고 먼저 말한다.

**스크린샷 순서 초안**(리더 승인 후 확정):
1. 창 위에 서 있는 정지컷 — 헤드라인 1장으로 제품이 설명돼야 한다
2. M7 균열 + 그 위 클릭이 통과하는 장면
3. M1 활쏘기 마지막 정중앙 프레임(`MOMENTS.md` S2)
4. [행동 명령] 창 — **"먼저 나서지 않습니다. 시키면 합니다"**의 증거
5. 캐릭터/장비 커스터마이즈
6. 설정창 — 끌 수 있다는 것을 보여준다(상주 앱의 최대 불안)

**반드시 넣을 고지 1줄**: Windows 작업표시줄 자동 숨김 예외(`TRUTH_INVENTORY.md` 0-1).

## 4. 전략팀 확정 대기 목록 (이게 정해져야 내가 채운다)

| # | 대기 항목 | 무엇이 막혀 있나 |
|---|---|---|
| 1 | **스토어 선택과 출시 순서** | 개발일지 거처, 스크린샷 규격, 태그 체계가 전부 여기 걸린다 |
| 2 | **무료/유료 경계** | 소재의 클로징 문구가 "지금 받기"인지 "구매"인지가 갈린다. **전환 설계 전체** |
| 3 | **가격** | 비교 프레이밍(커피 한 잔 등)을 쓸지 말지 |
| 4 | **DLC 6팩 구성·순서** | 팩별 소재 계획. ★ 단 `TRUTH_INVENTORY.md` 3절대로 **DLC는 구조가 아직 없다**(원칙 4 미구현) — **로드맵으로 홍보하기 전에 기술 근거가 필요하다**고 리더에게 올린다 |
| 5 | **맥 앱스토어 축소판 여부** | 축소판이 나오면 **"창 위를 걷는다"가 성립하지 않을 수 있다.** 그러면 그 채널만 **소재를 통째로 다시 만들어야 한다**. 같은 스크린샷을 쓰면 즉시 거짓 소재가 된다 |

★ 5번은 마케팅에 미치는 영향이 가장 크므로 먼저 알려주기를 리더에게 요청한다.

## 5. 플랫폼 영향

- **macOS 영향**: 없음(문서만). 소재 캡처 절차는 `CAPTURE_PROTOCOL.md` 참고.
- **Windows 영향**: 없음(문서만). 다만 **직장인 타겟의 주 채널이 MS 스토어라면 Windows
  스크린샷이 더 중요해진다.** 현재 Windows 실기는 사용자에게만 있어 소재 생산 경로가
  확보돼 있지 않다 — **별도 배정 필요(사유: 실기 부재)**.
