# A. 물리 × 남의 창

## A-1 ★★★ 「같은 높이, 세 번」 — 3분할 (동영상 1번 슬롯 / 최우선)

> **이 한 컷이 이번 라운드 최대 산출물이다.** M4·M6이 지갑을 여는 유일한 축이고,
> **캡션 한 줄 없이 물리를 증명하는 유일한 구도**다.

**논증 구조**: 스프라이트 애니메이션은 **같은 입력에 같은 그림**을 낸다.
물리는 **같은 입력에 다른 그림**을 낸다. → **같은 입력을 세 번 보여주고 결과가 다르면 끝난다.**

| 항목 | 지시 |
|---|---|
| **화면 분할** | 가로 3분할. 세 칸이 **완전히 동일한 화면**(같은 창 배치, 같은 좌표) |
| **동작** | 커서로 집어 **같은 높이·같은 지점**에서 놓는다. 3테이크 |
| **동시 재생** | 세 칸이 **같은 프레임에서 동시에 시작**. 이게 핵심 — 시차가 있으면 논증이 흐려진다 |
| **길이** | 놓는 순간 ~ 무릎앉아 착지까지. **3~4초**. 그 뒤 0.5초 정지 후 루프 |
| **프레임 안** | 창 2개(상단이 발판), Dock/작업표시줄 |
| ★ **기대 결과** | 세 칸의 **회전수·낙하 자세·착지 방향이 서로 다르다** |
| ★ **실측 근거** | `ThrowTumbleState` 회전 **220~720°/초** = **편차 3.3배**. 최대 6초, 착지 시 무릎앉기 |
| **테이크 수** | ★ **최소 8테이크 찍어 3개를 고른다.** 물리라서 원하는 그림이 언제 나올지 모른다 |
| **고르는 기준** | 셋의 **차이가 가장 크되 셋 다 「자연스러운」 것**. 하나라도 우스꽝스러우면 "버그"로 읽힌다 |

**실패 조건(찍고 나서 폐기해야 하는 경우)**
- 셋이 비슷하게 나오면 **폐기하고 다시 찍는다.** 비슷한 3분할은 논증이 아니라 **반증**이다.
- 셋 중 하나라도 미끄러짐(수평 표류)이 보이면 폐기. ★ macOS 배치모드 실측은 끝속도 **0.000000**이지만
  **Windows 실기 확인은 아직 없다**(`TRUTH_INVENTORY.md` 6절 ⑥).

★ **이 컷이 `S-1`(헤드라인 정지컷)과 다른 점**: S-1은 "전체 화면에서 무슨 일이 벌어지나",
A-2는 **"정말로 닿아 있나"**다. 둘 다 필요하다. 하나로 합치면 둘 다 약해진다.

# B. 권한 0 · 네트워크 0 — **부재를 어떻게 찍는가**

## B-0 원리 — 세 가지 방법뿐이다

| 방법 | 무엇을 찍나 | 어디에 쓰나 |
|---|---|---|
| **① 안 뜨는 것을 무편집으로** | 권한 대화상자가 **뜨지 않는 첫 실행 전체** | 스토어 · 유튜브 |
| **② 통과를 실증** | 클릭이 그대로 통과하는 장면 | 스토어 |
| **③ 제3자 계측기 화면** | 송수신 바이트 | ★ **개발일지 전용** |

---

## B-1 ★★★ 「컷이 없다」 — 첫 실행 무편집 한 테이크 (60~90초)

> **편집이 없다는 사실 자체가 주장이다.** 컷을 넣는 순간 "중간에 뭔가 눌렀겠지"가 된다.

| 항목 | 지시 |
|---|---|
| **시작** | 아무것도 안 띄운 깨끗한 바탕화면. **화면 녹화를 먼저 시작**하고 앱을 실행 |
| **끝** | 캐릭터가 창 위에 올라가 걷기 시작할 때까지 |
| ★ **핵심** | 그 사이에 **macOS 접근성/화면 기록 권한 대화상자가 한 번도 뜨지 않는다** |
| **컷** | **0개.** 배속도 걸지 않는다(배속은 편집으로 읽힌다) |
| **자막** | 화면 밖 여백에만. ★ **제품 UI 폰트를 쓰지 않는다** — UI처럼 보이면 목업이 된다 |
| **길이가 길어도 되나** | ★ 된다. **길이가 증거다.** 스토어용은 여기서 잘라 쓰되, **원본 무편집 파일을 함께 보관**한다 |

★ **Windows판도 같은 테이크를 따로 찍는다.** 다만 Windows에서는
**작업표시줄 자동 숨김 해제가 화면에 그대로 보인다** → **그 장면을 자르지 말고 그대로 두고,
고지 문구를 같은 영상 안에 넣는다.** 자르면 그게 은폐다.

## B-2 ★★★ 「클릭이 통과한다」 — `G-1`과 통합 (스크린샷 2 / GIF)

`ROADMAP.md`의 `G-1`이 이미 이 자리다. 여기서는 **B축 관점의 요구만** 덧붙인다.

- 균열(가짜)이 떠 있는 **3초 안에** 그 아래 계산기 `7` 버튼을 실제로 눌러 **숫자가 입력되는 것**까지.
- ★ **입력된 숫자가 프레임에 보여야 한다.** 클릭하는 손동작만 찍으면 논증이 아니다.
- 실측: 스윙 0.4초 + 균열 3초 후 원복. **누를 시간이 3초뿐**이므로 리허설 필요.

## B-3 「송수신 0」 — ★ 개발일지 전용, 스토어 금지

| 항목 | 지시 |
|---|---|
| **찍는 것** | macOS 활성 상태 보기 / Windows 리소스 모니터에서 **우리 프로세스의 송수신 바이트** |
| ★ **정직한 캡션** | *"N분 관측 중 송수신 0바이트"* — **관측 시간 창을 반드시 함께 적는다.** "0"은 잰 구간 안에서만 참이다 |
| ★ **스토어 금지 이유** | 제3자 UI 캡처는 **구매자가 검증할 수 없고**, 스토어 문맥에서는 오히려 방어적으로 보인다. 개발일지에서는 반대로 최고의 신뢰 소재다 |
| **선행 조건** | `security`의 **출하 빌드 아웃바운드 실측 절차**가 먼저 있어야 한다(`STORE_PAGE.md` 5절). 그 전엔 찍지 않는다 |

## B-4 「일부러 깨 보았다」 — ★ 글. 그림이 아니다

우리 감사 테스트에는 **네거티브 컨트롤**이 붙어 있다 — *"0건이라 초록"*이 아니라
**"위반 코드를 일부러 넣으면 빨개진다"**까지 검증돼 있다.

> **이건 스크린샷으로 만들 수 없고, 만들려고 하면 안 된다.** 개발일지 1편의 본문이다.
> 굳이 그림을 넣는다면 **테스트 러너가 빨간 화면**(일부러 위반을 넣은 상태) 1장 —
> ★ 단 그 화면은 **우리 제품 화면이 아니므로 스토어에 올리지 않는다.**

# E. 플랫폼 영향

- **Windows 영향: 별도 배정 필요(사유: 실기 부재).** 이 문서의 B-1·B-5는 **Windows 실기에서만**
  찍을 수 있고, 이 개발 머신에는 Windows 실행 환경이 없다. **촬영 주체가 사용자여야 한다.**
  또한 A-1의 미끄러짐 실패 조건은 Windows 실기 확인 항목 ⑥에 걸려 있다.
- **macOS 영향: 없음(문서만).** A 계열·B-1의 macOS 테이크는 이 머신에서 가능하지만
  **깨끗한 캡처 환경(별도 계정/빈 바탕화면)이 아직 없다.** 앱 실행은 리더 승인 사항이라
  이 라운드에 **실행하지 않았다.**
