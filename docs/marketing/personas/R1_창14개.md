# R1 `창14개` — 창을 늘 10개 이상 띄우고 사는 기술 직군

## 1. 한 줄 정체
에디터·터미널·브라우저·메신저·문서를 항상 띄워 둔다. 화면이 넓거나 모니터가 둘이다.
설치 전에 "이거 뭐 하는 프로그램이지"를 **직접 확인하는 습관**이 있다.

## 2. 어디서 만나는가
- **개발일지 / 기술 커뮤니티**가 1순위. `CHANNELS.md` 3-1의 실패 서사(측정이 거짓말한 이야기,
  자를 먼저 의심하라)에 반응한다.
- 스팀은 **이미 계정이 있다.** 다만 "게임 찾는 맥락"에서 이 앱을 만나지는 않는다 —
  기획 7절이 지적한 그 구멍이 이 사람에게도 그대로 적용된다.

## 3. 첫 3초에 무엇을 보는가
**자기 화면과 닮은 화면**을 본다. 창이 여러 개 겹친 데스크톱 위를 캐릭터가 걷는 그림.
`MOMENTS.md` C4(프레임 안에 남의 창)가 이 사람에게 가장 강하게 작동한다 —
창이 3개뿐인 깨끗한 데모 화면은 오히려 "내 환경에서도 될까"라는 의심을 만든다.

## 4. 마음이 움직이는 지점 — 이 사람에게만 통하는 패
| 근거 | 어디서 |
|---|---|
| **OS 권한을 하나도 요구하지 않는다** | `TRUTH_INVENTORY.md` 0절 |
| **네트워크 API 0건이고, 그걸 네거티브 컨트롤까지 붙여 검사한다** | `OfflineFirstNetworkAuditTests` |
| **Dock 폭 실측을 화면 기록 권한으로 할 수 있었는데 원칙 때문에 포기했다** | `process.md` 2026-08-28 |
| **안 보면 프레임을 낮춘다(4단계)** | `Platform/FramePacing.cs` |
| **가려진 창은 발판이 안 된다**(오클루전 컬링) | `VisibleTopEdgeSolver.cs` |

마지막 항목이 특히 중요하다. **이 사람은 "창이 겹치면 어떻게 되지?"를 반드시 생각한다.**
거기에 답이 준비돼 있다는 것 자체가 "제대로 만들었구나"의 신호다.

## 6. 어느 팀에 무엇을 요청하는가

**→ 기획·총괄 (리더 / `game-architect`)**
- `README.md`의 실재 불일치 3건 정정 배정(`TRUTH_INVENTORY.md` 4절). **공개 저장소라면 이건
  홍보물보다 먼저 새는 구멍이다.**

**→ 개발 (`perf-doc`, 리더 경유)**
- **깨끗한 환경에서의 메모리·CPU·전력 재측정 1회.** 지금 우리는 이 카테고리의 1순위 반론(A)에
  대답할 숫자가 하나도 없다. 재측정 전까지 마케팅은 성능을 일절 언급하지 않는다.

**→ 마케팅 (나)**
- 개발일지 1편을 "권한을 안 쓰기로 한 이야기"(Dock 폭 포기)로 잡는다. R1에게 가장 잘 통한다.
- **"먼저 나서지 않습니다"**를 스토어 기능 목록 상단에 올리는 문구 초안 작성.
