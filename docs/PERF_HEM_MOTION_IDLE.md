## 1. 한 장 요약

| # | 발견 | 등급 | 값 |
|---|---|---|---|
| **A** | `TickHemMotion`의 «정지 중 스킵»이 **상시 미세 피치 자세에서 영구히 막혀 있었다.** 조건에 걸린 `needsFloor`는 「각도·오프셋이 0이 아닌가」만 본다 | M | 관망 자세 −0.5°~−6.0° ⇒ `\|sinPitch\| ≥ 0.0087 > 0.0001` |

프로덕션 3파일 **+123 / −18줄**(대부분 주석·문서) · **실행되는 새 코드 약 20줄**.

## 2. 「시각 효과 0」을 **직접 다시 쟀다** — 남의 판정을 믿지 않는다

`design-equipment`가 R26d에서 *"최악 0.2305 R = 1.34 pt로 양수 — 닿지 않는다"*라고 냈다.
그 숫자를 옮겨 쓰지 않고 **다른 경로로 다시 만들었다.**

### 2-1. 무엇을 어떻게 쟀나 (M)

| 자료 | 출처 |
|---|---|
| 밑단 좌표 49점 | `AccessoryShapeBuilder.Handoff.cs`의 `Handoff_longcape_STB` / `Handoff_shortcape_STB`를 **텍스트로 파싱** |
| 좌표 → 컨테이너 변환 | `AccessoryShapeBuilder.HandoffPiece` 식 그대로: `p = (x·R, HeadCenterY + y·R)` |
| 바닥선 | `AccessoryShapeBuilder.HemFloorLine` 식 그대로: `intercept = hipY + (−hipY − s·b)/c`, `slope = −sin/c` |
| 리그 상수 | `BaselineCharacterTotalHeight 2.2746944` · `BaselineHeadVisualRadius 0.22` · `BaselineHipLocalY 0.9346944` |
| 호흡 | `StickConfig.idleBreathAmplitude = 0.012`(루트 로컬) |
| 피치 범위 | `StickmanPoseAnimator`의 관망 자세 상수 — 팔짱 −4.0° / 뒷짐 −2.5° ± L1 왕복 2.0° |
| pt 환산 | `StickConfig.ReferencePointsPerWorldUnitApprox = 846/24 = 35.25` |

★ **R26d와 달리 이산 표본이 아니라 0.1° 간격 전 구간 스윕**을 돌렸고, 호흡도 5단계로 훑었다.

### 2-2. 결과 (M)

| 항목 | 값 |
|---|---|
| 긴망토 밑단 최저 y | `HeadCenterY/R − 9.05452 = 9.33952 − 9.05452 =` **+0.2850 R**(발바닥선 위) |
| 밑단 최대 \|x\| | **1.6222 R** |
| 호흡 최저의 바닥선 상승량 | `0.012 / 0.22 =` **0.0545 R** |
| **피치 0 + 호흡 최저 여유** | **+0.2305 R** = 1.340 pt @0.75 / 1.787 pt @1.00 |
| **관망 자세 전 구간(±6.0°) 최악 여유** | **+0.2304 R** (최악점 피치 **−5.6°**, 호흡 최저) |
| 짧은망토 같은 조건 최악 여유 | **+4.1957 R** (24.40 pt @0.75) |

⇒ **R26d의 1.34 pt가 소수 셋째 자리까지 재현됐다.** 그리고 최악점이 −6.0°가 아니라 **−5.6°**임을
추가로 확인했다(R26d는 이산 표본이라 그 사이를 못 봤다 — 차이는 0.0001 R로 판정에 영향 없다).

★ **1 pt 환산의 교정**: 배율 0.75에서 `1 R = 0.22 × 0.75 × 35.25 = 5.816 pt`.
`design-equipment` 산출물과 같은 값이다 — 두 계산기가 같은 자를 쓰고 있음을 먼저 확인했다.

### 2-3. ★ 그런데 «여유가 양수다»만으로는 부족하다 — **구조적으로** 닫았다

여유가 양수면 `PressHemToFloor`가 0점을 옮긴다. 그러면 그 프레임의 버퍼는:

```
System.Array.Copy(Base → Buffer)      // 원본 복사
17점 루프                              // air01 == 0, walkAmplitude == 0 ⇒ 두 if 모두 미실행
PressHemToFloor(...)                   // 0점 이동
⇒ Buffer ≡ Base  (비트 단위로 같다)
s.Line.SetPositions(Buffer)            // = SetPositions(Base)
ApplyFillVertices(Fill, Buffer)        // = ApplyFillVertices(Fill, Base)
```

**그리고 `RestoreHemBase()`가 하는 일이 정확히 그 마지막 두 줄이다.**
⇒ 조기 반환으로 바꿔도 **첫 프레임에 같은 값을 한 번 쓰고 이후 아무것도 안 쓰는 것**이 된다.
이것이 「시각 효과 0」의 **계산이 아닌 증명**이다.

## 3. 프레임 비용 회계

### 3-1. 매 프레임 실제로 하는 일 (M — 소스에서 센 것)

흔들 선 1개(망토 뒤판 49점) 기준. 목걸이/스카프도 흔들 선을 갖는다(NECK 에셋 `swayStart ≥ 0` 4종).

| # | 작업 | 크기 |
|---|---|---|
| 1 | `Array.Copy(Base → Buffer)` | 49 × 12 B = **588 B** memcpy |
| 2 | 흔들 구간 루프 | **17회** × (`HemPressDepth` + `HemPressDamping` + 분기 2 + Vector3 읽기/쓰기) |
| 3 | `PressHemToFloor` 전수 | **49회** × (1 mul + 1 add + 1 sub + 비교) |
| 4 | `LineRenderer.SetPositions` | **588 B** 관리→네이티브 마샬 + **선 메시 더티** |
| 5 | `mesh.vertices = points` | **588 B** 관리→네이티브 마샬 + **정점 버퍼 무효화** |
| 6 | `mesh.RecalculateBounds()` | 49점 AABB 스캔(네이티브) |

**관리 측 복사 합계 = 1,764 B/프레임/선** (M).
**GC 힙 할당 = 0 B** (M — 버퍼는 전부 재구성 시점에 미리 떠 있고, `Mesh.vertices`는 **세터**라
게터와 달리 배열을 새로 따지 않는다). ★ **즉 이것은 2026-09-05 `Mesh.colors` 건과 다른 병이다.**

### 3-2. 네이티브 재굽기 추정 (E — ★ 판정 근거로 쓰지 마라)

`numCapVertices = 4` · `numCornerVertices = 4` · `loop = true` · 49점에
`PERF_EQUIPMENT_AND_FAN.md §2-4(c)`가 쓴 확장식(`2N + c·코너`)을 그대로 적용하면
**≈ 294 정점**이 매 프레임 다시 구워진다. 채움 메시는 49정점 VBO 재업로드다.
**정점당 페이로드와 Unity 내부 경로는 미확인이므로 바이트로 환산하지 않는다.**

### 3-3. 얼마나 자주 도는가 (M)

| 상태 | 개선 전 발동률 | 개선 후 |
|---|---|---|
| 평소 Idle(집중 세션 아님) | **≈50 %** (호흡 0.8 Hz의 음수 반주기) | **0 %** |
| 집중 세션 관망 자세(L0+L1) | **100 %** | **0 %** |
| 걷기 · 낙하 · 점프 · 던져짐 | 100 % (**정당하다** — 실제로 그림이 바뀐다) | **100 %, 무변경** |
| 착지 웅크림 · 기상 | 100 % (**정당하다** — 실제로 눌린다) | **100 %, 무변경** |

파생 수치(D):

| | 값 |
|---|---|
| 25분 집중 세션 1회에서 제거되는 헛 재굽기 | 60 fps × 1,500 s = **90,000 프레임** |
| 하루 유휴(평소 Idle) 기준 | 86,400 s × 60 × 0.5 = **약 259만 프레임/일** |

### 3-4. ★ 판정 — **작다. 그래서 최소로만 고쳤다**

프레임 예산 16.7 ms에 대해 이 함수는 마이크로초대다(`PERF_EQUIPMENT_AND_FAN.md §4-2`가
액세서리 `LateUpdate` 전체를 그렇게 판정했다). **「느낄 수 없는 낭비」가 맞다.**

그럼에도 닫은 이유는 셋이다:
1. **24시간 상주**가 이 앱의 전제다. 하루 259만 번의 «픽셀 0개짜리» 버퍼 재업로드는
   프레임 예산이 아니라 **유휴 전력·컴포지터** 쪽에 실리고, 그쪽은 이 앱의 핵심 지표다.
2. **비용이 8줄이다.** 리팩터링이 아니라 조건 한 겹이다.
3. **다중 인스턴스(세포 분열)에서 선형으로 늘어난다** — 지금은 작지만 커지는 방향의 항이다.

⇒ 반대로, **이 이상은 하지 않았다.** `numCornerVertices` 적응화(§`PERF_EQUIPMENT_AND_FAN` P1-2)나
`LineRenderer.alignment` 전환(P1-3)은 **실기 캡처 대조가 선행 조건**이라 이 라운드에서 손대지 않았다.

## 4. 처방 후보 3개 — 무엇을 왜 골랐나

브리프가 준 후보를 그대로 검토했다.

### (a) 「미세 피치 임계값 아래면 이전 프레임 결과 재사용」 — **기각**

- 임계값의 단위가 **각도**다. 그런데 실제로 중요한 것은 «밑단이 바닥선에 닿는가»이고,
  그것은 **망토 길이 · 몸 오프셋 · 배율**이 함께 정한다. 각도 하나로는 결정되지 않는다.
- ⇒ **DLC로 더 긴 망토가 들어오면 조용히 틀린다.** 그때 화면에서는
  «관망 자세인데 자락이 바닥을 뚫는다»로 나타나고, 원인은 성능 최적화에 있다.
- 새 마법 숫자 1개가 늘고, 그 숫자가 옳다는 것을 **증명할 방법이 없다**.

### (b) 「밑단 위치 변화량이 유의미한 픽셀을 넘을 때만 재계산」 — **채택, 단 「유의미한 픽셀」을 0으로**

브리프의 (b)를 **한 걸음 더 밀어서** 받았다. «N pt 이하의 변화는 무시»는
**실제로 그림을 N pt까지 바꾼다**(그리고 N이 또 마법 숫자다).
대신 **「한 점이라도 바닥선 아래로 갈 수 있는가」**라는 **정확한** 술어를 쓴다:

```
어떤 점 p 에 대해서도  |p.x| ≤ maxAbsX  ∧  p.y ≥ minY  이므로
    눌림 깊이 = intercept + slope·p.x − p.y  ≤  intercept + |slope|·maxAbsX − minY
우변 ≤ 0 이면 어떤 점도 눌리지 않는다.
```

- **마법 숫자 0개** — `minY`/`maxAbsX`는 그 도형 자신에서 나온다.
- **그림 변화 0** — 위 부등식이 참이면 `PressHemToFloor`가 반드시 0을 돌려준다(§2-3).
- **O(1)** — 스칼라 2개를 재구성 때 한 번 재고, 매 프레임은 부동소수 3연산이다.
- **한쪽으로만 안전하다** — 참이면 그냥 원래 경로를 돈다. 보수적으로 틀릴 수는 있어도
  **위험하게 틀릴 수는 없다.**
- **DLC 망토가 길어지면 자동으로 원래 경로로 떨어진다.** 이것이 (a)와의 결정적 차이다.

보수성의 크기도 쟀다(M): 호흡만으로 몸이 내려앉은 상태에서 이 상한은 **상체 피치 10.6°까지** 성립한다.
관망 자세 상한 **6.0°**, 그 위에 얹히는 제스처 상한 **6.5°**가 둘 다 그 안이다.

### (c) 「관망 자세 전용 저빈도 갱신(0.5초)」 — **기각**

- 렌더러가 **포즈 층의 이름을 알아야 한다.** 지금 이 렌더러는 오직 **Transform 사실**
  (torso 회전 · head 위치)만 읽는 설계이고, 그 규약이 «새 상태가 생겨도 자동으로 따라온다»를 만든다.
  자세 이름을 넣는 순간 그 규약이 깨진다.
- 0.5초가 **새 마법 숫자**다.
- **상태가 실제로 바뀌기 시작하는 순간 2 Hz 계단이 보인다** — 제스처(6.5° 숙임)나 걷기 진입이
  정확히 그 자리다. 「연출이 끊긴다」는 이 파일이 이미 두 번 고친 병이다
  (2026-08-31 «망토가 고정되어있음», 2026-09-01 착지 프레임 순간이동).
- **평소 Idle의 50 %는 전혀 못 잡는다.**

루프 안의 `damp`와 `PressHemToFloor`는 여전히 그것을 본다.

### ★ 다음 사람이 밟을 함정 하나

`BaseMinY`/`BaseMaxAbsX`는 **구워진 원본**에서 잰 값이다.
기류·보행이 걸린 프레임에는 버퍼가 원본에서 이미 밀려 있어 **이 상한이 성립하지 않는다.**
그래서 이 판정은 **`air01 == 0 ∧ walk01 ≤ 0.0001`인 프레임에서만** 쓴다.
`needsFloor` 자리에 그대로 갈아 끼우면 안 된다 — 그 순간 걷다가 웅크리는 프레임에서 자락이 뚫린다.

판정이 관망 자세에서 실제로 발동하는지를 잠그는 것이 그 테스트의 목적이다.

### 정직한 한정 1건 — 비트 단위로 같지는 않은 구간이 하나 있다

`0 < walk01 ≤ 0.0001` **이면서** `needsFloor`가 참인 프레임에서, 개선 전 코드는
진폭 `R × 0.16 × walk01` 이하의 흔들림을 실제로 적용했다. 개선 후에는 0이다.

| 배율 | 그 최대 변위 |
|---|---|
| 0.75(출하) | `0.165 × 0.16 × 1e-4 × 0.7 =` **1.85e-6 유닛 = 6.5e-5 pt** |

**1 pt의 1/15,000이다.** 그리고 이 허용오차는 **개선 전 코드가 이미 `!needsFloor` 가지에서
쓰고 있던 것과 같다**(그쪽도 `walk01 ≤ 0.0001`이면 흔들림을 버린다). **종류가 늘지 않았다.**
