## 3. 경로 B — 출하본 접붙이기 (골든 5개 무손상 · **이 라운드의 유일한 신규 좌표**)

`CostumeOfficeAssetTests`가 실제로 잠그는 것은 **정확히 다섯 값**이다(골든 상수 `:32-36`, 본문 `:85-131`):
`propShapes.Count = 10` · `minX = 0.26` · `maxX = 1.00` · `maxY = 1.02` ·
**`stage == 0`인 오버라이드의 `shapes.Length = 4`**. **`stage 1~3`은 아예 안 본다.**
아래는 그 다섯을 전부 보존한 채 R29-1·R29-2를 고친다.

### 3-1. 좌표 수정 3건 — 보조색을 **없던 자리에 만들지 않고 기존 조각에서 만든다**

`propShapes`와 `stageShapes[0]` **양쪽에 똑같이** 적용한다(둘 다 이 세 조각을 갖고 있다).

```
DeskLip   loop filled tone=1  n=4    ← 선 2점 → 채움 4각. 팩 정체 + 손이 짚는 자리
          (+0.2600,+0.5520) (+0.4000,+0.5520) (+0.4000,+0.6200) (+0.2600,+0.6200)
DeskTop   line n=2   (+0.4000,+0.6200) (+1.0000,+0.6200)     ← 근단 0.26 → 0.40
DeskLeg   line n=2   (+0.3200,+0.0000) (+0.3200,+0.5520)     ← 상단 0.62 → 0.552
```

- **왜 `DeskTop`의 근단을 물리는가**: 그대로 두면 앞턱 채움의 윗변(y=0.62, x 0.26~0.40)과
  `DeskTop`이 **같은 자리에 두 번 그린 선**이 된다(공선 겹침 0.14 H > 0.5 W_P) → **PR-4b 위반**.
  0.40으로 물리면 «앞턱이 끝나는 곳에서 상판이 시작»하는 **끝끼리 접합**(겹침 0)이라 예외에 든다.
- **왜 `DeskLeg`의 상단을 내리는가**: 0.62까지 올리면 다리가 채움 사각형을 **관통**한다. 0.552는
  앞턱 밑면이고, 다리가 앞턱을 떠받치는 그림이 된다.
- **골든 보존**: `minX`는 이제 `DeskLip`(0.26)이 잡는다 — **0.26 그대로**. `maxX` 1.00, `maxY` 1.02,
  조각 수 10/4 전부 불변. **테스트 한 줄도 안 바뀐다.**
- **채움 검산(§6의 실제 렌더 모형으로)**: 짧은 변 0.0680 H = **2.01 W_P**(하한 1.50 ✅).
  내접원 반지름 **0.0335 H ≤ 번짐 반폭 0.0373 H** → **2.2배 재묘사가 내부를 완전히 덮는다 = 진짜 색면**.
  ★ 4프롭 중 **이것 하나만** 그렇다(§6-1). 잉크 실높이 0.0680 + 0.0746 = **0.1426 H = 8.6 pt @0.75**.

## 8. 미확인 — 추측으로 안 메운 것

1. **실기 캡처 0회.** 전부 오프라인 기하 검산이다. 리더 사전 통보 없이 앱을 띄우지 않았다.
   *"오프라인 렌더러가 코너 붕괴를 가린 사고"*가 이 저장소에 있다 — **최종 판정은 빌드 캡처로만.**
2. **집중 오라가 아직 없다** → 프롭과의 겹침을 **못 쟀다**(§4).
3. **출하 오피스 키포즈 3개의 손 좌표를 FK로 재지 않았다.** `SetSegmentImmediate`의 각 규약과
   마디 계층을 확인하지 않고 각도를 좌표로 바꾸면 틀린다. PR-8은 **motion이 준 작업점**으로만 쟀다.
4. **골(valley) 모형은 `UiChrome` 캡슐에서 옮겨 온 자다**(R28 §8-2와 같음). 월드 `LineRenderer`의
   안티에일리어싱에 그대로 맞는지 **재 보지 않았다.**
4b. ★ **§6-4의 수정 2건은 하니스 실측이지만 `r28_props.py`에 «반영»하지는 않았다** — 좌표를 넣어
   재측정만 했다. 반영은 리더 배정 후. 그리고 **내가 초안에서 산술로 어림한 값이 틀렸던 이력을
   §6-4에 그대로 남겼다**(초승달 밑끝 0.8920 → 실측 0.8650).
5. **경로 A/B 중 어느 쪽이 「인계본과 동일하게 읽힘」에 가까운지는 눈 판정**이고 내 담당이 아니다.
6. **광부/사이버/대마법사 에셋 저작은 아직 아무도 안 했다** — R28 좌표는 있고 파일은 없다.

## 9. 플랫폼 영향

- **Windows 영향: 없음(함께 검토함).** 문서 1개 + 검산 스크립트/출력 3개(`design/equipment/verify/`)만
  추가. 프로덕션 `.cs`/`.asset` **0줄**, 빌드·앱 실행·Unity 락 **없음**.
- ★ **판정 축은 Windows 100%(1×)를 먼저 잡았다.** `s_min` 표는 1×/2×를 나란히 싣는다
  (출하 0.645/0.555 · 경로 B 0.625/0.535 · 설계본 0.550/0.470).
  **2×가 절벽을 없애지 않는다** — 저배율에서는 코어 간극이 이미 0 이하라 DPI가 못 구한다.
  ⇒ 저배율 절벽은 양 OS 공통이고 **Windows에서 0.09만큼 먼저 온다.**
- **macOS 영향: 없음(같은 이유).** 위 세 계기가 전부 macOS에서 더 넉넉하다.
- **모바일(iPad/iPhone) 영향: 미확인** — 스크린샷 백드롭 모드에 발판(창 상단) 개념이 없어
  접지선을 무엇으로 잡을지 모른다(R28 §8-4와 같은 항목).
