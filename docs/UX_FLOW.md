## 0. 문서 규칙
각 플로우는 다음 6항목으로 기술한다.
**목표 / 트리거 / 유저가 보는 것 / 유저가 할 수 있는 액션 / 예외 상태(빈·로딩·에러·거부) / 탈출구**

와이어프레임은 ASCII 박스 다이어그램. `[ ]`는 탭/클릭 가능 요소, `( )`는 정보성 텍스트, `▓▓▓`는 이미지/스크린샷 영역, `┈┈┈`는 점선(가이드/투명 오버레이)을 의미한다.

이 문서 전체를 관통하는 최우선 제약(재확인):
1. 말풍선 텍스트는 상태 전이가 **확정된 후에만** 생성된다. 절대 먼저 대사를 정하고 행동을 맞추지 않는다.
2. 데스크톱 클릭 관통 기본 ON — 유저 액션의 기본값은 "지켜보기"다.
3. 유저의 실제 파일/아이콘/창은 절대 건드리지 않는다 — 모든 시각 연출은 카피에도 "복사본/연출"임을 명시한다.
4. 모바일은 스크린샷 백드롭 착시이며 최초 1회 명확히 고지한다.
5. 모든 방해성 이벤트에는 즉시 해제 가능한 탈출구가 함께 존재한다.

## 1. 앱 최초 실행 흐름

### 1-A. 데스크톱(macOS/Windows) 최초 실행

**목표**: 코어 루프(창=지형 인식)에 필요한 OS 권한을 유저가 이해하고 승인하게 만들되, 거부해도 앱이 완전히 죽지 않게 한다.
**트리거**: 앱 최초 설치 후 첫 실행.

**유저가 보는 것 — 화면 1: 환영 + 사전 설명(프라이밍) 화면**
```
┌──────────────────────────────────────────┐
│                 StickMate                 │
│                                            │
│   (졸라맨이 바탕화면 창 위를 걸어다녀요)   │
│                                            │
│  이 앱은 다음 권한이 필요해요:            │
│   - 화면의 다른 창 위치 읽기(발판으로 사용)│
│     ※ 창 내용은 절대 읽거나 저장하지 않음 │
│   - 마우스 클릭을 다른 앱으로 그대로      │
│     통과시키는 권한(업무 방해 방지)       │
│                                            │
│         [ 권한 허용하러 가기 ]            │
│         [ 나중에 하기(제한 모드) ]        │
└──────────────────────────────────────────┘
```
**액션**: `[권한 허용하러 가기]` → OS 시스템 설정 화면으로 딥링크(macOS: 손쉬운 사용/화면 기록, Windows: 필요 시 UAC) 후 앱으로 복귀 시 자동 재확인. `[나중에 하기]` → 제한 모드 진입(아래 예외 상태 참고).

**유저가 보는 것 — 화면 2: 권한 확인 후 확정 화면**
```
┌──────────────────────────────────────────┐
│   권한이 확인됐어요.                       │
│   이제 졸라맨이 창 위를 돌아다녀요.        │
│                                            │
│   기본적으로 마우스 클릭은 그대로          │
│   아래 앱으로 통과됩니다(업무 방해 없음).  │
│                                            │
│              [ 시작하기 ]                 │
└──────────────────────────────────────────┘
```

**예외 상태**
- **로딩**: 권한 확인 폴링 중 스피너 + "권한 확인 중…" (최대 수 초, 타임아웃 시 수동 새로고침 버튼 노출).
- **거부**: 유저가 OS 다이얼로그에서 거부 → "권한이 없으면 창 인식 없이 화면 가장자리만 발판으로 씁니다" 안내 + `[다시 요청]` `[제한 모드로 계속]`.
- **빈 상태(제한 모드)**: 열린 창이 하나도 없거나 권한 미승인 → 화면 하단(Windows 작업표시줄/ macOS Dock 위)만 발판으로 사용하는 `NullPlatformWindowService` 폴백. 이 상태에서도 캐릭터가 화면에 서 있어야 하며 "빈 바탕화면"으로 인해 캐릭터가 사라지거나 멈춰선 안 됨.

**탈출구**: 설정에서 언제든 `[권한 다시 요청]` 재진입 가능(7절 설정창 참고). 최초 온보딩을 건너뛰어도 앱 자체 종료/제거는 일반 앱 삭제 절차와 동일(트레이 아이콘 우클릭 → 종료).

### 1-B. 모바일(iPad/iPhone) 최초 실행 — 스크린샷 백드롭 온보딩

**목표**: "이건 진짜 홈 화면이 아니라 앱 안의 사진 배경 위에서 노는 착시"라는 기대치를 최초 1회 명확히 정렬시킨다. (오해 방지가 성공 기준의 전부)
**트리거**: 앱 최초 설치 후 첫 실행.

**유저가 보는 것 — 화면 1: 개념 설명(필수, 스킵 불가)**
```
┌──────────────────────────────────────────┐
│   이 앱은 이렇게 작동해요                  │
│                                            │
│   1) 당신의 홈 화면을 "사진"으로 찍어서    │
│      앱 안에 가져와요                     │
│   2) 그 사진 위에서 졸라맨이 놀아요        │
│                                            │
│   ⚠ 이건 진짜 홈 화면이 아니에요.         │
│   앱을 나가면 원래 홈 화면으로 돌아가고,   │
│   실제 아이콘이나 앱은 전혀 건드리지       │
│   않아요. 그냥 "사진" 배경입니다.         │
│                                            │
│              [ 알겠어요, 계속 ]           │
└──────────────────────────────────────────┘
```
**액션**: `[알겠어요, 계속]`만 존재(체크박스 없이 넘어가면 오해가 재발하므로 이 화면은 강제 노출, 최소 1회 완독 스크롤 요구 가능).

**유저가 보는 것 — 화면 2: 스크린샷 확보**
```
┌──────────────────────────────────────────┐
│   배경으로 쓸 스크린샷을 골라주세요        │
│                                            │
│  ( 최근 사진첩에서 홈 화면처럼 보이는      │
│    스크린샷을 자동으로 찾았어요 )         │
│  ┌────────────────────┐                  │
│  │ ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ │  ← 자동 감지 제안 │
│  │ ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ │                  │
│  └────────────────────┘                  │
│   [ 이 사진 쓰기 ]                        │
│   [ 사진첩에서 직접 고르기 ]              │
│   [ 지금 홈 화면 캡처하는 법 안내 보기 ]  │
│   [ 나중에 하기(기본 배경 사용) ]         │
└──────────────────────────────────────────┘
```
**액션**: 자동 감지 스크린샷 채택 / 사진첩 수동 선택 / 캡처 방법 안내(홈 버튼+전원 또는 스와이프 단축키 튜토리얼) / 스킵.

**예외 상태**
- **로딩**: 사진첩 스캔 중 "최근 스크린샷 찾는 중…" 스피너, 3초 이상 시 자동 감지 생략하고 수동 선택 버튼만 남김.
- **사진 접근 거부**: "사진 접근을 허용하지 않으면 배경으로 기본 이미지를 사용해요"라는 완곡한 안내 + `[기본 배경으로 계속]` `[설정에서 권한 허용]`(iOS 설정 앱 딥링크). 앱이 멈추지 않고 번들 기본 배경(그라데이션 또는 예시 홈 화면 목업)으로 즉시 진행.
- **빈 상태**: 사진첩에 스크린샷이 전혀 없음 → 자동 감지 카드 대신 "아직 스크린샷이 없어요" + 캡처 안내 CTA만 노출.
- **저해상도/이상 비율 이미지 선택**: 발판 지정에 부적합할 정도로 작은 이미지 → "이 사진은 배경으로 쓰기엔 너무 작아요" 경고 후 다른 사진 재선택 유도(강제 차단 아님, 경고 후 진행 허용).

**탈출구**: 이 온보딩은 설정 화면의 `[배경 다시 찍기]`로 언제든 재진입 가능(7절 참고). 스킵 후에도 앱 사용 자체는 100% 가능(기본 배경 + 화면 하단 고정 발판으로 대체).

## 2. 코어 루프 UX — "지켜보기"가 기본 액션

**목표**: 클릭 관통 기본 ON 환경에서 유저의 주 행위는 관찰이다. 액션이 없어도 심심하지 않은 주변부 재미(ambient delight)를 설계한다.
**트리거**: 상시(앱 실행 중 항상 진행되는 루프).

**유저가 보는 것**
```
  창 A                    창 B
┌────────┐              ┌─────────┐
│        │   (걷기)      │         │
│        │◄── 🚶 ───────►│         │
└────────┘   창 상단 =   └─────────┘
             발판 라인
                 │
                 │ (창 사이 간격 → 낙하)
                 ▼
               🙃 (FALL 상태, 팔다리 늘어짐)
```
- 창 상단 라인을 따라 걷는 캐릭터, 창과 창 사이 간격에서 점프하거나 낙하.
- 낙하 시 IK 제어에서 Ragdoll로 전환되는 시각적 이완(관절이 툭 풀리는 느낌)이 관찰 포인트.
- 상태 변화가 있을 때만 짧은 말풍선(5절 참고)으로 코멘터리 — 상시 텍스트 노출 금지(시선 피로).

**유저가 할 수 있는 액션**
- 기본: 없음(관찰). 클릭은 하위 앱으로 관통.
- 트레이/메뉴바 아이콘: 잠깐 멈춰서 손 흔들기 등 "인사" 유발(옵션, P2).
- 대결모드로 전환 시에만 클릭 상호작용 활성(7절).

**예외 상태**
- **빈 상태**: 열린 창이 하나도 없음 → 화면 최하단(작업표시줄/Dock)을 기본 발판으로 사용, 캐릭터가 좌우로 배회. "아무것도 안 하는 상태"가 절대 정적 이미지 한 장으로 멈춰 보이면 안 됨(최소한의 idle 모션 유지).
- **로딩**: 창 목록 최초 열거 중 0.5초 이내 완료 목표. 그 이상 걸리면 캐릭터를 화면 중앙에 IDLE로 대기시켜 "멈춘 버그"처럼 보이지 않게 함.
- **에러**: 창 열거 API 실패(권한 회수 등) → 조용히 `NullPlatformWindowService`로 폴백, 에러 팝업으로 유저를 방해하지 않음(비침해 원칙). 단, 설정창 상태 표시줄에는 "제한 모드"로 표기.

**탈출구**: 해당 없음(관찰 전용 루프이므로 방해성 없음). 단, 전체화면 게임 감지 시 자동 숨김은 6절에서 다룸.

## 3. 모바일 발판 지정 UX — 아이콘 줄/Dock 탭 지정 온보딩

**목표**: 자동 그리드 인식 없이도(1차 스코프) 유저가 직접 손가락으로 정확하게 발판을 지정하게 한다. 실패 시 재시도 쉬워야 함.
**트리거**: 1-B 완료 직후(스크린샷 확정 시점) 자동 진입. 이후 설정에서 언제든 재진입 가능.

**와이어프레임 — 화면 1: 지정 안내**
```
┌──────────────────────────────────────────┐
│  아이콘 줄이나 Dock을 톡 눌러서            │
│  졸라맨이 밟고 다닐 자리를 알려주세요      │
│                                            │
│  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  │
│  ▓▓[사진 속 앱 아이콘들이 보임]▓▓▓▓▓▓▓▓  │
│  ┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈  │ ← 탭하면 여기에 초록 라인 생김
│  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  │
│  ┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈  │
│  ▓▓▓▓▓▓▓▓[Dock 영역]▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  │
│                                            │
│   지정한 발판: 0개 (최소 1개 필요)         │
│              [ 완료 ]  (비활성, 0개)      │
└──────────────────────────────────────────┘
```

**와이어프레임 — 화면 2: 탭 후 상태(발판 1개 지정됨)**
```
┌──────────────────────────────────────────┐
│  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  │
│  ▓▓[앱 아이콘 줄]▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  │
│  ══════════════════════════════════ [✕]  │ ← 지정된 발판(초록 실선) + 삭제(x)
│  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  │
│                                            │
│      🚶 (미리보기: 캐릭터가 그 줄 위를    │
│           바로 걸어보임 — 즉시 피드백)     │
│                                            │
│   지정한 발판: 1개                         │
│   [ 발판 더 추가 ]     [ 완료 ]           │
└──────────────────────────────────────────┘
```
**목표 보강**: 탭 즉시 그 자리에서 캐릭터 미리보기가 걸어다니는 시연을 보여줘 "내가 지정한 게 맞게 작동하는지"를 바로 확인시킨다(추상적 좌표 지정이 아니라 즉각적 결과 피드백).

**유저가 할 수 있는 액션**
- 아이콘 줄/Dock 위치를 탭 → 해당 y좌표에 발판 라인 생성(가로 전체 폭 기본, 추후 드래그로 좌우 범위 조절은 2차 고도화).
- 이미 지정한 라인 옆 `[✕]`로 삭제.
- `[발판 더 추가]`로 다중 층 발판 지정(계단식 이동 가능하게).
- `[완료]`로 확정 → 코어 루프 시작.

**예외 상태**
- **빈 상태(발판 0개)**: `[완료]` 비활성 + "최소 1개는 지정해야 졸라맨이 서 있을 곳이 생겨요" 인라인 안내. 강제 차단(진행 불가)하되, 우회로로 `[기본 발판 쓰기(화면 맨 아래)]` 보조 버튼 제공 — 완전히 막다른 길이 되지 않게 함.
- **오탭(엉뚱한 위치)**: 삭제가 즉시 가능해야 하며, 라인 생성에 실행취소(undo) 스낵바("발판을 삭제했어요, 되돌리기") 3초 노출.
- **화면 회전/스크린샷 교체**: 스크린샷을 바꾸면 기존 지정 좌표가 무의미해지므로, 배경 재캡처 시 발판 재지정 온보딩이 강제로 다시 뜬다(6절/7절 연계).

**탈출구**: 언제든 뒤로가기 시 "지금까지 지정한 내용을 저장할까요?" 확인 후 이탈 가능. 설정에서 재진입 시에도 동일 플로우 재사용.

## 4. 파쿠르(벽타기/매달리기/구르기) 시각 피드백

**목표**: Active Ragdoll 물리와 IK 목표 포즈 사이의 전환이 매끄럽게 "의도된 동작"으로 보이게 한다(버그처럼 안 보여야 함).

| 동작 | 트리거 | 시각 피드백 | 실패 시 처리 |
|---|---|---|---|
| 벽타기(CLIMB) | 진행 방향 창 측면이 발판 높이차보다 높음 | 양손이 창 가장자리를 짚는 IK 포즈 + 손끝 마찰 먼지 파티클, 상승 중 손가락 애니메이션 | 잡을 곳이 사라짐(창 이동/닫힘) → 즉시 FALL로 전이, 다음 프레임 말풍선도 함께 취소(5절 계약) |
| 매달리기(HANG) | 창 상단 모서리 도달 후 정지 여유 | 팔이 완전히 펴진 채 대롱대롱, 미세한 흔들림(Perlin 노이즈로 자연스러움 부여) | 일정 시간 초과 시 자동으로 위로 올라가거나(GETUP 유사) 힘 빠짐 연출로 FALL 전이 — 무한 대기 금지 |
| 구르기(ROLL) | 낙하 후 착지 순간 충격 흡수 | 착지 직전 무릎 굽힘 예비 포즈 → 착지 순간 몸통 회전 + 먼지 파티클 → WALK 복귀 | 착지면이 너무 좁아 구를 공간 없음 → 축소된 제자리 휘청임 애니메이션으로 대체(공간 인식 실패가 시각적으로 어색해 보이지 않도록) |

**유저가 보는 것(공통 원칙)**: 능동 상태(IK 제어) → 물리 위임(Ragdoll) 전환 경계가 부드러운 블렌딩(수 프레임 크로스페이드)으로 처리되어야 하며, 급격한 포즈 점프(teleport처럼 보이는 것)는 UX 결함으로 간주.

**예외 상태**
- **로딩**: 해당 없음(즉시 물리 반응이어야 함, 파쿠르에 로딩 스피너 개념 없음).
- **에러**: 잡을 곳 판정이 애매한 경계 케이스(창 높이차가 climb/jump 임계값 부근) → 판정은 Coder 상태머신 책임이나, UX 요구사항으로 "애매하면 더 안전한 쪽(낮은 난이도 동작)을 선택"하도록 권고(유저가 "왜 벽을 안 타고 그냥 점프했지" 정도는 괜찮지만 "벽을 타려다 허공에 붕 뜬 채 멈춤"은 절대 금지).

**탈출구**: 해당 없음(비침해적 관찰 콘텐츠).

## 5. 텍스트-액션 싱크 계약의 UX 표현 — `DialogueIntent` UX 요구사항

이 절은 **Coder가 구현할 `DialogueIntent` 시스템에 대한 명세**를 겸한다. UX 관점에서 "말만 하고 안 하는" 실패를 원천 차단하기 위한 타이밍/취소 규칙을 정의한다.

**목표**: 말풍선은 항상 "이미 확정된 사실"만 보고한다. 예고(미래형 약속)가 아니라 확정(현재/직후형 서술)이어야 한다.

**핵심 UX 규칙 (Coder 구현 요구사항)**
1. **생성 시점**: `DialogueIntent`는 상태 전이가 확정되어 `IStickmanState.Enter()`가 실제로 호출되는 **바로 그 프레임에만** 생성 가능. 상태 진입 조건 판정(예: "쏠 대상이 있는가", "탄약이 남았는가")은 반드시 `Enter()` 호출 이전에 완료되어 있어야 하며, `Enter()`가 불렸다는 것 자체가 "그 행동을 한다"의 확정 보증이어야 한다.
2. **말풍선 표시 = 상태 파라미터 그대로 파생**: 예) `ATTACK` 상태에 `shotsRemaining: 1` 파라미터가 있으면 말풍선 텍스트는 그 값으로부터 "한 발 더" 문자열을 생성한다. 텍스트 리소스가 상태 파라미터와 별개로 하드코딩되어 상태와 어긋날 수 있는 구조 금지 — 반드시 상태(enum+params) → 텍스트 매핑 테이블 단방향.
3. **소멸 시점 — 두 가지 경로만 허용**:
   - (a) 정상 종료: 해당 상태의 예상 지속시간(애니메이션 길이 등)이 끝나 다음 상태로 자연 전이 → 같은 프레임에 말풍선 fade-out 시작.
   - (b) 강제 취소: 상태가 완료되기 전에 상위 우선순위 상태(RAGDOLL 피격, 강제 해제 트리거 등)로 **중도 전이**될 경우, 말풍선은 **그 즉시 같은 프레임에 취소**된다(사라지는 애니메이션 없이 즉시 제거하거나 최대 1프레임 내 페이드아웃). 이 경로가 "한 발 더라고 말만 하고 안 쏨" 버그를 막는 핵심 방어선이다 — **취소된 상태에서 파생된 말풍선이 화면에 남아있는 시간이 0에 가까워야 한다.**
4. **최소 노출 시간 vs 즉시 취소의 우선순위**: 가독성을 위한 최소 노출 시간(권장 0.6~0.8초)은 "정상 진행 중" 상태에만 적용된다. RAGDOLL 등 강제 인터럽트는 최소 노출 시간 규칙을 항상 무시하고 즉시 취소를 우선한다(취소가 항상 이긴다).
5. **말풍선 큐잉 금지(원칙적으로)**: 다음 대사가 준비돼도 현재 상태의 행동이 화면에서 진행 중이면, 그 행동이 시각적으로 끝나기 전까지 다음 말풍선을 조기 노출하지 않는다. 텍스트가 행동보다 앞서가는 모든 경우를 UX 결함으로 정의.
6. **표시 위치/스타일**: 캐릭터 머리 위, 말풍선 꼬리가 캐릭터를 가리킴. 등장 150ms, 소멸 100~150ms 페이드. 화면/모니터 경계에 가까우면 꼬리 방향을 유지한 채 말풍선 박스만 안쪽으로 밀어 잘리지 않게 함(멀티모니터 예외 상태와 연계, 6절).
7. **다중 캐릭터(라이벌 스틱맨 등) 동시 발화**: 서로 다른 캐릭터의 말풍선은 독립적으로 동일 계약을 따르되, 겹침 방지를 위해 z-order와 최소 이격 거리만 조정(텍스트 내용/타이밍 로직에는 개입하지 않음).

**와이어프레임 — 정상 케이스**
```
프레임 N:     상태 전이 확정(ATTACK, shots=1) ─┐
프레임 N:     DialogueIntent 생성 "한 발 더"    │→ 같은 프레임
프레임 N+1~:  말풍선 페이드인 + 사격 애니메이션 시작(동시 진행)
프레임 M:     사격 애니메이션 종료(=행동 완료)
프레임 M:     말풍선 페이드아웃 시작
```

**와이어프레임 — 취소 케이스(버그 원천 차단 대상)**
```
프레임 N:     상태 전이 확정(ATTACK, shots=1)
프레임 N:     DialogueIntent 생성 "한 발 더"
프레임 N+2:   피격 발생 → RAGDOLL로 강제 전이(ATTACK 미완료)
프레임 N+2:   ★ 같은 프레임에 말풍선 즉시 제거 ★
              (절대 "한 발 더"가 화면에 남은 채 RAGDOLL로 널브러지면 안 됨)
```

**예외 상태**
- **에러(계약 위반 감지)**: 이는 QA/테스트 영역이지만 UX 요구사항으로 명시 — Test Engineer가 "말풍선 표시 종료 시각 ≤ 대응 애니메이션 종료 시각 + 허용오차"를 회귀 테스트로 검증해야 한다(Tasklist Phase 2 "텍스트-액션 싱크 회귀 테스트" 항목과 직결).

**탈출구**: 해당 없음(관찰 콘텐츠). 단, 이 계약이 깨지면 신뢰도 문제로 직결되므로 최우선 방어 대상.

## 6. 예외 상태 총정리

### 6-1. 최초 빈 상태
- **데스크톱**: 열린 창이 하나도 없음 → 화면 최하단을 발판으로 idle 배회(2절 참고). 절대 완전 정지 프레임으로 보이지 않을 것.
- **모바일**: 발판 미지정 또는 스크린샷 미설정 → 기본 배경 + 화면 최하단 고정 발판(3절 "기본 발판 쓰기" 경로)로 즉시 대체, 앱이 빈 화면으로 멈춰있지 않게 함.

### 6-2. 권한/접근 거부
- **데스크톱 오버레이 권한 거부**: 1-A 예외 상태 참고. 제한 모드(화면 가장자리 발판)로 조용히 폴백 + 설정에서 재요청 가능.
- **모바일 사진 접근 거부**: 1-B 예외 상태 참고. 기본 배경으로 폴백 + 설정에서 재요청 가능.
- 공통 원칙: **권한 거부가 앱을 못 쓰게 만들면 안 된다.** 항상 기능이 축소된 폴백 경험이 존재해야 하며, 재요청 경로는 설정에 상시 노출.

### 6-3. 멀티모니터(데스크톱 전용)
**목표**: 모니터 간 캐릭터 이동이 "순간이동처럼 어색"하지 않게, 그리고 모니터 배치상 물리적으로 이어지지 않는 경계(예: 다른 해상도/오프셋 모니터의 단차)를 자연스럽게 처리한다.
```
 모니터 1(1920x1080)      모니터 2(1440x900, 상단 정렬 다름)
┌────────────────────┐  ┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈
│                🚶──┼──►(경계 넘어가는 순간   │
│  ══════════════════│    바닥 높이 단차 있으면 │
└────────────────────┘    FALL/JUMP로 자동 처리)│
                       └────────────────────────┘
```
- **유저가 보는 것**: 캐릭터가 모니터 경계를 걷다가, 인접 모니터의 작업표시줄/바닥 높이가 다르면 그 단차만큼 자연스럽게 낙하하거나(내려가는 경우) 점프 판정(올라가는 경우)이 걸린다.
- **예외 — 모니터 사이 논리적 간격(비인접 배치)**: OS 가상 데스크톱 좌표계상 모니터가 물리적으로 붙어있지 않게 설정된 경우 → 그 사이는 "바닥 없음"으로 인식해 FALL 처리(순간이동 금지).
- **탈출구**: 해당 없음(비침해).

### 6-4. 전체화면 게임 감지 → 자동 숨김
**목표**: 업무/게임 방해 제로 원칙의 핵심 안전장치. 숨김/복귀가 모두 매끄러워야 하며, 숨겨진 동안 상태가 초기화되어 복귀 시 "리셋된 것처럼" 보이면 안 된다.
```
[게임 전체화면 진입 감지]
        │
        ▼
캐릭터 즉시 페이드아웃(≤200ms) + 현재 상태 "일시정지(Suspended)"로 보존
(말풍선이 떠있었다면 함께 즉시 제거 — 5절 취소 규칙과 동일 원칙 적용)
        │
   (게임 플레이 중 — 화면에 아무것도 없음, 트레이 아이콘만 "숨김 중" 표시)
        │
[전체화면 게임 종료 감지]
        ▼
보존해둔 상태에서 그대로 재개(가능하면 IDLE로 부드럽게 안착) + 페이드인
```
- **유저가 보는 것**: 게임 중에는 완전히 사라짐(트레이 아이콘 상태만 "숨김 중"으로 바뀜). 게임 종료 후 부드럽게 재등장.
- **예외**: 창모드/테두리 없는 창모드(Borderless) 게임처럼 전체화면 판정이 애매한 경우 → 오탐(false positive)으로 숨었다면 유저가 트레이 아이콘에서 즉시 `[강제로 보이기]` 토글 가능해야 함(자동 판정을 유저가 오버라이드 가능해야 함, 아래 탈출구 참고).
- **탈출구**: 트레이/메뉴바 아이콘에 상시 `[지금 보이기 / 지금 숨기기]` 수동 토글 제공 — 자동 감지가 틀렸을 때 유저가 즉시 되돌릴 수 있는 유일한 방법.

### 6-5. 방해성 이벤트(인질극/로데오 커서 등) 예외 처리 — 탈출구 설계 원칙
Tasklist Phase 3/4/5에서 구현될 인질극(닫기버튼 막기), 로데오 커서, 창 점령 등 "악동/반항" 계열 기능에 선제적으로 적용할 UX 규칙:
- 모든 이러한 이벤트는 시작과 동시에 **트레이/메뉴바에 상시 노출되는 단일 긴급 정지 버튼**(예: `[스틱메이트 진정시키기]` 또는 전역 단축키)으로 즉시 종료 가능해야 한다. 장난의 재미를 위해 앱 내부 UI로만 해제하게 설계하지 않는다(그 UI 자체가 장난에 가려질 수 있으므로 OS 레벨 트레이 아이콘이 최종 안전판).
- 모든 방해성 이벤트는 **최대 지속시간 상한**(예: 로데오 커서 10초, 인질극 15초)을 가지며 유저 개입 없이도 자동 해제된다 — "탈출구가 없어서 무한 지속"은 절대 불가.
- 인질극류(닫기 버튼을 막는 연출)는 실제 OS 창닫기 기능 자체를 막아서는 안 된다(원칙 3 "유저 자산 불변"과 직결 — 앱 자체 창의 닫기를 진짜로 가로채 프로세스를 못 죽이게 하면 안 됨). 연출은 "닫기 버튼 위치를 캐릭터가 시각적으로 가로막는 것처럼 보이는 것"까지만 허용되고, 실제로는 트레이 아이콘 종료나 강제 정지 버튼이 항상 유효해야 한다.

## 8. 핵심 행동 우선순위 (유저가 가장 쉽게 해야 할 행동)

유저가 이 앱에서 "해야 하는" 능동적 행동은 최소화하는 것이 철학(관찰형 앱)이지만, 불가피하게 존재하는 능동 행동은 다음 우선순위로 쉬워야 한다.

1. **P0 — 아무것도 안 하기(관찰)**: 설치 후 온보딩만 넘기면 그 뒤로는 클릭 한 번 없이도 앱이 재미있게 돌아가야 한다. 이게 실패하면 다른 모든 게 무의미.
2. **P0 — 최초 권한/배경 설정 완료**: 데스크톱 권한 허용, 모바일 스크린샷+발판 지정. 이게 안 되면 코어 루프 자체가 시작 안 되므로 온보딩 이탈률을 최우선으로 낮춘다(각 단계 스킵 경로 필수 제공).
3. **P1 — 방해될 때 즉시 숨기기/멈추기**: 트레이 토글, 긴급 정지 버튼. "이 앱이 나를 방해하면 1초 안에 없앨 수 있다"는 신뢰가 없으면 삭제된다.
4. **P1 — 설정창 열기/닫기**: 진입 장벽 없이 트레이 아이콘 한 번.
5. **P2 — 클릭관통 토글, 대결모드 전환**: 상호작용을 원할 때만 쓰는 선택적 행동.
6. **P2 — 모바일 배경/발판 재설정**: 자주 하지 않지만 실패하면 안 되는 행동(명확한 재진입 경로 필수).
7. **P3 — DLC/스킨 탐색·구매**: 수익화 행동, 강요하지 않고 자연스럽게 발견되게(설정 탭 안에 위치, 강제 팝업 금지).

## 9. 교차 레이어 영향 로그 (Coder 상태머신/DialogueIntent 구조에 영향)

> 아래는 이번 UX 설계에서 나온, 상태머신·이벤트버스·플랫폼 서비스 구현에 직접 영향을 주는 요구사항이다. `Tasklist.md`의 "교차 레이어 영향 로그"에도 동일 내용을 기록함.

1. **`DialogueIntent` 생성/취소는 반드시 상태머신의 `Enter()`/강제 전이 훅과 같은 프레임에 바인딩**되어야 한다. 상태 진입 가능 여부 판정(전제조건 체크)은 `Enter()` 호출 **이전**에 끝나 있어야 하며, `Enter()` 호출 자체가 "행동 확정"의 유일한 신호여야 한다. 5절 규칙 참고.
2. **상태 취소는 "최소 노출시간 규칙"을 항상 이긴다.** RAGDOLL 등 강제 인터럽트가 걸리면 진행 중이던 `DialogueIntent`는 최소 노출시간과 무관하게 같은 프레임에 즉시 철회되어야 한다. 이를 위해 상태머신은 "일반 전이"와 "강제 인터럽트 전이"를 구분하는 플래그/우선순위를 이벤트버스에 실어야 한다(현재 설계에 이 구분이 명시적으로 없다면 추가 필요).
3. **클릭 관통(ON) 상태에서도 커서 근접 반응(호버 기반 앰비언트 반응, 2절)을 원한다면**, 클릭 이벤트 자체가 아니라 전역 커서 좌표를 별도로 폴링하는 경로가 `IPlatformWindowService`(또는 별도 인터페이스)에 필요하다 — 클릭 관통 구현이 커서 위치 정보 자체까지 차단하는 방식이면 안 됨. Coder는 두 기능(클릭 통과 vs 좌표 조회)이 독립적으로 동작하는지 네이티브 플러그인 설계 시 확인 필요.
4. **전체화면 게임 감지로 숨김 처리 시, 상태머신에 "Suspended" 같은 일시정지 개념이 필요**하다 — 단순히 GameObject를 비활성화하면 재개 시 상태가 유실되어 IDLE로 리셋된 것처럼 보인다(6-4절). 숨김 직전 상태(및 진행률/파라미터)를 보존했다가 그대로 재개해야 한다.
5. **멀티모니터 간 "바닥 없는 논리적 간격"은 FALL 상태로 처리**되어야 하며(6-3절), `IPlatformWindowService` 데스크톱 구현체가 모니터별 경계 정보를 노출해 상태머신이 "여기는 어느 모니터에도 속하지 않는 좌표"를 판정할 수 있게 해야 한다.
6. **방해성 이벤트(인질극/로데오 등)는 항상 최우선순위 강제 인터럽트 채널(긴급 정지)을 가져야 한다**(6-5절). 상태머신 설계 시 "일반 상태 전이 규칙을 완전히 우회하는 글로벌 강제 종료 훅"을 Phase 3/4에서 반드시 예약해둘 것 — 나중에 끼워 넣기보다 지금 인터페이스에 자리를 만들어두는 게 안전.
7. **모바일 `ScreenshotBackdropPlatformService`는 발판 목록을 가변(추가/삭제/재지정 가능)으로 설계**해야 한다(3절, 7절 "발판 다시 지정하기"). 최초 캡처 시 고정된 배열이 아니라 런타임에 add/remove가 가능한 컬렉션이어야 하며, "발판 0개" 상태를 코어 루프 시작 전에 검증하는 `IsConfigured` 유사 가드가 필요하다(6-1절 빈 상태 대응).
8. **배경 스크린샷 교체 시 기존 발판 좌표는 자동으로 무효화**되어야 하고(3절 예외 상태), 이는 `ScreenshotBackdropPlatformService`가 배경 이미지 참조와 발판 좌표 목록을 같은 트랜잭션으로 갱신해야 함을 의미한다 — 배경만 바뀌고 발판 좌표가 옛 이미지 기준으로 남아있는 불일치 상태를 허용하면 안 됨.

## 10. 격파 미니게임 (오브젝트 소환 격파)

**목표**: 관찰형 앱 안에서 유저가 능동적으로 즐기는 짧고 명쾌한 타격감 이벤트를 제공하되, "클릭 관통 기본 ON"이라는 최우선 원칙을 이 순간에만 국소적으로 깨는 것임을 유저가 명확히 인지하게 한다. 실패해도 스트레스 없이 재도전하고 싶게 만든다.

**트리거**
- 자동(기본): 코어 루프 유휴 상태가 일정 시간 누적되면 낮은 확률로 캐릭터가 스스로 격파 시늉을 시작(예: 유휴 판정 주기마다 저확률 추첨). 완전히 관전만 해도 무방한 자발적 스펙터클로 시작한다.
- 수동: 트레이 메뉴 "격파 놀이"를 유저가 직접 선택해 즉시 발동 가능.
- 11절(라이벌 대결)과 동시에 발동하지 않도록 상호 배제(둘 다 ATTACK 계열 스펙터클이라 겹치면 화면이 혼란스러움).

**유저가 보는 것**
```
1) 캐릭터 준비 자세 → 대사 "좋아, 간다" (이미 확정된 상태에서 파생, 예고형 아님)
2) 기와/대리석/철판이 순차 소환되어 허공에 쌓임(중력 적용, 살짝 흔들림)
3) 캐릭터 주먹 주변 "기 모으기" 게이지(원형 링 또는 아우라 파티클 강도)가 1.5~2초에 걸쳐 채워짐
4) 게이지가 스위트 스팟 구간(전체의 약 70~85%)에 들어서면 색/반짝임으로 신호
```
- 스위트 스팟 폭은 최초 난이도 기준 관대하게(성공 경험 우선, 실패로 인한 짜증보다 타격감 자체가 목적).

**유저가 할 수 있는 액션**
- 이 이벤트가 활성화된 동안에만, 캐릭터/오브젝트의 화면 히트박스 영역 위 클릭이 앱에 수신된다(15절 "부분적 클릭관통 해제" 참고 — 그 외 화면은 항상 그대로 관통).
- 스위트 스팟 구간에서 클릭 → 성공: 정권지르기/내려찍기 애니메이션 확정 → 오브젝트 파괴(파편 파티클, 화면 흔들림은 캐릭터 레이어 국소 효과로 한정하고 유저의 실제 창은 절대 흔들지 않음).
- 스위트 스팟 이전/이후에 클릭 → 실패(아래 참고).

**실패 시 UX**
- 오브젝트는 부서지지 않고 그대로 유지, 캐릭터는 손을 털며 "어이쿠" 류의 짧은 코믹 리액션(확정된 실패 상태에서 파생된 대사, 원칙 1 준수).
- 게이지가 1~2초 후 자동으로 재시작(재도전), 최대 3회까지 재시도 허용.
- 3회 모두 실패하면 오브젝트가 스스로 사라지는 민망한 퇴장 애니메이션으로 이벤트 자연 종료 — 앱이 멈추거나 버그처럼 보이지 않게 항상 "정상적으로 끝나는 것"으로 처리.

**예외 상태**
- 이벤트 시작 후 5초 이상 클릭 입력이 전혀 없으면(유저가 다른 작업으로 이탈) 자동 취소하고 부분적 클릭관통 해제를 즉시 원복.
- 전체화면 게임 감지(6-4절) 발생 시 이 이벤트는 즉시 취소 — 비침해 원칙이 항상 이 미니게임보다 우선.
- 오브젝트 소환 위치는 항상 현재 보이는 화면 안전 영역(다른 창에 가려지지 않는 위치)에만 스폰되도록 보장 필요(Coder 구현 요구사항) — 가려진 곳에서 게이지가 진행되면 유저가 이벤트 존재 자체를 놓쳐 "클릭했는데 반응 없음"으로 오해할 수 있음.

**탈출구**: 트레이 긴급정지로 언제든 즉시 취소. 설정(7절 "모드" 탭에 항목 추가 권고: "격파 미니게임 자동발생")에서 자동 트리거 자체를 끌 수 있다.

## 11. 라이벌 스틱맨과의 대결

**목표**: 저확률 랜덤 이벤트로 빨간 라이벌 스틱맨이 등장해 유저 캐릭터와 짧은 난투극을 벌이는 관전형 스펙터클을 제공한다. 유저 개입 없이도 완결되는 콘텐츠로 설계해 "아무것도 안 해도 재미있다"(8절 P0 원칙)를 강화한다.

**스폰 확률/조건**
- 코어 루프 유휴 판정 주기(예: 수 분 단위)마다 저확률(3~5%) 추첨, 최소 재발생 쿨다운(예: 20분) 적용 — 너무 잦으면 스펙터클의 희소가치가 사라짐.
- 유효 발판(열린 창)이 화면에 충분히 없으면 스폰을 보류하고 다음 판정 주기로 이연(라이벌이 등장해도 뛰어다닐 창이 없으면 연출이 어색해짐).
- 10절 격파 미니게임과 동시 발동 금지(상호 배제 락).

**유저가 보는 것**
- 화면 가장자리에서 빨간 라이벌이 걸어 들어옴 → 유저 캐릭터를 발견하는 확정 모션(고개를 돌림) → 조우 확정 시 짧은 도발 대사(예: "어쭈?") → 서로 달려들어 창 상단/측면을 발판 삼아 오가며 주먹질·발차기 → 피격 시 Active Ragdoll로 전신 물리에 위임되어 창 사이로 튕겨나가는 등 물리적 반응이 관전 포인트.
- 두 캐릭터의 말풍선은 5절-7 규칙대로 각자 독립적으로 계약을 따르되 z-order/이격거리만 조정(겹침 방지).

**유저 개입 가능 여부**: 기본은 **관전 전용**. 클릭관통은 그대로 ON 유지, 부분적 클릭관통 해제를 이 이벤트에는 적용하지 않는다 — 격파 미니게임처럼 개입 요소를 추가하면 두 스펙터클 이벤트의 상호작용 규칙이 뒤섞여 혼란스러워지므로 명확히 분리한다(관전 콘텐츠와 참여 콘텐츠를 섞지 않는다는 설계 원칙).

**대결 종료 조건과 결과 연출**
- 한쪽의 체력/타점 게이지가 먼저 소진되면 승자는 짧은 승리 포즈+확정 대사, 패자는 GETUP 애니메이션으로 자연 복귀 후 화면 밖으로 걸어 나가며 퇴장(실제 파일/창은 전혀 변경하지 않음, 원칙 3).
- 최대 지속시간 상한(예: 30초) 도달 시 승부 미결이어도 무승부 처리로 강제 종료 — 무한 난투 금지(6-5절 "최대 지속시간 상한" 원칙을 관전형 이벤트에도 동일 적용, 이 이벤트는 입력을 막지 않지만 화면을 계속 어지럽히는 것도 신뢰를 깎으므로 상한을 둔다).
- 유저 캐릭터 패배 시에도 패널티 없음(스트레스 없는 톤 유지) — GETUP 후 즉시 평상시 코어 루프로 복귀.

**예외 상태**
- 대결 중 전체화면 게임 감지 → 즉시 취소(6-4절 우선).
- 대결 중 유저가 창을 닫아 발판이 사라지는 경우 → 상태머신은 이를 일반 낙하/재배치 규칙으로 처리(별도 특수 처리 불필요, 4절 파쿠르 실패 처리와 동일 철학: 더 안전한 쪽으로).

**탈출구**: 트레이 긴급정지로 즉시 종료 가능. 설정(7절 "모드" 탭)에 "라이벌 대결 이벤트 끄기" 토글 추가 권고.

## 12. 드래그&던지기 (커서로 잡고 던지기)

**목표**: 유저가 캐릭터를 직접 붙잡아 던지는 가장 적극적인 능동 상호작용. 이 기능은 클릭 관통 기본 ON 원칙을 캐릭터 몸 위에서만 예외적으로 해제해야 하는 대표 사례이며, 던지고 나서도 캐릭터가 "실종"된 것처럼 느껴지면 절대 안 된다(신뢰 원칙).

**트리거**: 유저가 캐릭터의 현재 화면 히트박스 위에서 마우스다운(클릭+홀드)을 시작.

**기술 요구사항 — 부분적 클릭관통 해제 (Coder에게 넘기는 핵심 요구사항, 상세는 15절)**
- 마우스다운이 캐릭터 히트박스 안에서 일어났는지 판정하려면, 애초에 그 좌표의 클릭 이벤트가 OS에서 앱으로 전달돼야 한다. 클릭관통이 전역 ON이면 그 좌표의 클릭조차 즉시 하위 앱으로 넘어가 감지 자체가 불가능해지는 문제가 있다.
- **유저가 체감해야 하는 규칙(불변)**: 캐릭터 몸 위에서만 클릭이 캐치되고, 그 외 모든 영역은 이 예외가 켜져 있는 동안에도 항상 그대로 관통되어야 하며, "다른 창 클릭"에는 절대 영향을 주지 않는다(원칙 2 직결). 접근 방식(지오메트리 기반 리전 vs 저수준 후킹)은 Coder 재량이나, 이 체감 규칙은 협상 불가.

**드래그 중 시각 피드백**: 마우스다운 유지 상태에서 캐릭터가 대롱대롱 매달리는 모션 — 팔이 위로 당겨진 자세로 손/옷깃이 커서 위치에 IK로 고정되고, 몸통은 커서를 스프링·댐퍼로 뒤따라오는 관성감(순간 텔레포트처럼 커서에 딱 붙지 않음)을 준다.

**놓았을 때 속도/방향 계산 방식에 대한 UX 기대치**
- 마우스업 직전 최근 약 0.12초 구간의 커서 이동 벡터를 평균 내어 던지기 속도/방향으로 환산(스무딩 없이 마지막 한 프레임 값만 쓰면 손떨림에 과민 반응).
- **과도하게 세게 던지면?** 물리적으로 자연스러운 최대 속도에 상한(clamp)을 둔다. 상한이 없으면 캐릭터가 화면 밖으로 사라져 다시 돌아오지 않는 "실종 버그"처럼 보일 위험이 있고, 이는 신뢰 문제로 직결된다(유저가 "내가 캐릭터를 없앴나" 불안해지면 안 됨). 화면 경계 도달 시 부드럽게 튕겨 돌아오거나 안쪽으로 소프트 클램프.

**창에 부딪혔을 때 이펙트**: 발판(창 상단/측면) 충돌 시 국소적인 충격 파티클(먼지/별) + 캐릭터 레이어 안에서만의 짧은 흔들림(유저의 실제 창은 절대 흔들리지 않음, 원칙 3) + 충격이 크면 즉시 RAGDOLL로 전이하고 그 확정 상태에서 파생된 "억!"류 리액션 대사(5절 계약 준수).

**예외 상태**
- 드래그 중 커서가 화면/모니터 경계를 벗어나면 마지막 유효 좌표에서 놓친 것으로 간주해 자유낙하 시작.
- 드래그 중 전체화면 게임 감지 → 즉시 드롭 + 숨김 처리(입력을 억지로 유지하지 않음, 6-4절 우선).
- 10절/11절/13절 이벤트가 이미 활성 중이면 새 드래그 시도는 무시(상태 우선순위 충돌 방지). RAGDOLL/피격류는 항상 드래그보다 우선한다는 원칙만 UX가 권고하고 세부 판정은 Coder 상태머신 책임.
- 유저가 마우스다운 상태로 오래 방치(예: 10초 이상 홀드)하면 자동으로 놓임 처리(release) — 무한 홀드로 캐릭터가 허공에 계속 매달려 있는 상태가 되지 않게 함.

**탈출구**: 마우스업으로 자연 종료. 드래그 도중에도 트레이 긴급정지로 즉시 강제 낙하 처리 가능해야 한다.

## 13. 로데오 커서

**목표**: 유저가 아무것도 안 해도(커서를 잠깐 세워두는 것만으로) 발견되는 저부담 이스터에그. 클릭이 전혀 필요 없는 유일한 커서 상호작용이라는 점이 다른 4개 기능과의 핵심 차이.

**트리거**: 마우스 커서가 화면상 좁은 반경(예: 5px) 안에서 5초 이상 정지 상태를 유지하고, 캐릭터가 그 근방(도달 가능 거리)에 있을 때 발동. 이는 9절-3에서 이미 요청한 "전역 커서 좌표 상시 폴링" 채널을 그대로 재사용 — 신규 폴링 채널을 추가로 만들 필요 없음(Coder에게 명확히: 로데오 커서는 클릭 이벤트가 아니라 좌표 폴링만으로 완결되는 유일한 케이스이므로 15절 "부분적 클릭관통 해제"가 필요 없다).

**유저가 보는 것**: 캐릭터가 커서 쪽으로 걸어와 폴짝 올라타 균형 잡는 자세(두 다리로 커서 아이콘을 감싼 모습), 살짝 까닥거리는 idle 모션.

**올라탄 상태에서 유저가 마우스를 움직였을 때의 밀당 연출**: 커서가 이동하면 캐릭터는 그 자리에 붙어 이동하되, 이동 속도에 비례해 몸이 뒤로 젖혀지는 관성 반응(버티는 각도가 커짐)을 보인다. 마우스를 일정 속도 임계값 이상으로 거칠게 휘두르면 캐릭터가 버티지 못하고 튕겨 떨어진다(낙하 → RAGDOLL → GETUP). 이 낙하는 "실패"가 아니라 그 자체로 재미있는 리액션이므로 부정적 톤 대신 "으악!"류 코믹 대사를 쓴다.

**강제 종료(탈출구) — 3중 안전망**
1. **암묵적(1차)**: 유저가 마우스를 거칠게 흔들면 자연스럽게 떨어짐 — 별도 UI 없이도 누구나 직관적으로 찾는 탈출구.
2. **타임아웃(2차)**: 최대 지속시간 상한 10초 도달 시 캐릭터가 스스로 내려옴(정상 종료 경로, 5절 (a) 재사용).
3. **트레이 긴급정지(3차)**: 항상 유효한 전역 안전판.

**예외 상태**
- 커서가 화면 경계 밖(다른 모니터)으로 이동하거나 캐릭터가 물리적으로 도달 불가능한 위치(창에 가려짐 등)에 정지해 있으면 트리거를 억제.
- 전체화면 게임 감지 시 즉시 취소(6-4절 우선).
- 10절/11절/12절/14절 등 다른 방해성·스펙터클 이벤트가 이미 활성 중이면 로데오 트리거를 억제(상호 배제 락).

## 14. 인질극/해킹 이벤트 — 긴급탈출 상세 (6-5절 연계)

이 절은 6-5절에서 정의한 "모든 방해성 이벤트는 트레이 긴급정지 + 최대 지속시간 상한을 가진다"는 원칙을, 인질극(닫기버튼 막기)/해킹 요구 이벤트에 구체적으로 적용한다.

**"닫기 버튼 위에 앉아 막기" — 방해 허용 한도**
- 이 연출은 **순수 시각적 오버레이**여야 한다. 캐릭터 스프라이트가 닫기 버튼 위치를 시각적으로 가리지만, 실제 OS 창의 클릭 수신 자체를 가로채선 절대 안 된다 — 원칙 3(유저 자산 불변)과 직결. 유저가 그 자리를 클릭하면 밑에 있는 실제 창의 닫기 버튼이 그대로 정상 작동해야 한다.
- 즉 **이 이벤트에는 15절 "부분적 클릭관통 해제"를 적용하지 않는다** — 다른 4개 기능과 정반대의 예외 취급이며, 이 점이 이 문서에서 가장 중요한 안전 규칙 중 하나다. 캐릭터는 클릭을 절대 가로채지 않고, 유저가 클릭하면 캐릭터가 "밀려나는" 코믹 저항 애니메이션(살짝 흔들리다 밀려나는 시늉)만 보여준 뒤 클릭은 그대로 밑창까지 관통해 창이 정상적으로 닫힌다.
- 허용 한도: 순수 시각적 가림 + 코믹 리액션까지만. 클릭 지연, 좌표 변조, 입력 가로채기는 전부 금지.

**사과 먹이기 상호작용 흐름**
- 트리거: 인질극/해킹 이벤트 진행 중, 캐릭터 근처에 앱 자체 UI로 작은 `[사과 주기]` 버튼이 노출(이 버튼은 앱 소유 UI 영역 안에 있으므로 클릭관통과 무관하게 항상 정상 수신 — 부분적 클릭관통 해제가 필요 없는 경로).
- 액션: 클릭 → 사과 오브젝트가 캐릭터 쪽으로 던져지는 애니메이션 → 캐릭터가 받아먹는 확정 리액션(상태 전이 확정 후 파생되는 순한 표정 대사) → 이벤트가 공격적 톤 없이 훈훈하게 즉시 정상 종료.

**드래그&셰이크 해제 — 구체적 판정 기준(Coder 구현 요구사항)**
- 입력 경로는 12절(드래그&던지기)의 마우스다운/부분적 클릭관통 해제 인프라를 그대로 재사용한다 — 이 이벤트만을 위한 별도 입력 경로를 새로 만들지 않는다.
- 판정창: 최근 0.5~0.6초(60fps 기준 약 30~36프레임).
- 방향전환 카운트: 이 판정창 내에서 커서의 수평 이동 방향이 좌→우 또는 우→좌로 전환된 횟수가 **4회 이상**이면 "흔들기 성공" 판정.
- 최소 변위 필터: 각 방향전환 구간의 이동 거리가 40px 미만이면 카운트에서 제외(손떨림·마우스 지터에 의한 오작동 방지).
- 성공 시: 캐릭터가 버티지 못하고 튕겨나가는 리액션(13절 로데오의 "거칠게 흔들면 떨어짐"과 동일 톤 재사용) 후 이벤트 즉시 종료.

**최대 지속시간 상한(자동 해제 타임아웃)**
- 인질극(닫기버튼 막기류): **15초** (6-5절 기존 예시와 동일하게 재확인).
- 해킹 요구 이벤트: **20초** (요구사항 문구를 읽고 반응할 시간을 조금 더 고려).
- 상한 도달 시 강제 인터럽트가 아니라 캐릭터가 "쳇, 알았어" 류 대사와 함께 스스로 물러나는 **정상 종료 경로**(5절 (a))로 처리한다. 이는 유저가 아무 조치도 하지 않아도 보장되는 마지노선 안전망이며, 즉시 반응하는 트레이 긴급정지와는 별개의 계층이다.

**예외 상태**
- 이벤트 도중 전체화면 게임 감지 → 모든 방해성 이벤트 중 최우선으로 즉시 취소(6-4절).
- 사과 먹이기 UI가 다른 능동 개입 이벤트(10절 격파 미니게임 등)와 동시에 뜨지 않도록 상호 배제(한 번에 하나의 "능동 개입 요구 이벤트"만 활성화).

**탈출구 — 4중 안전망**: (1) 트레이 긴급정지(즉시, 유저 주도) → (2) 드래그&셰이크(즉시, 유저 주도) → (3) 사과 먹이기(부드러운 즉시 종료, 유저 주도) → (4) 최대 지속시간 타임아웃(무조치 시 보장되는 마지노선).

## 15. 부분적 클릭관통 해제 (Partial Click-Through Override) — 공통 기술 요구사항

10절(격파 미니게임), 12절(드래그&던지기), 13절(로데오 커서 — 예외적으로 불필요), 14절(드래그&셰이크 해제)이 공통으로 요구하는 개념을 하나의 계약으로 정리한다. **이는 Phase 1에서 Coder가 지금 배선 중인 전역 클릭관통 토글과 직접 연결되는 교차 레이어 사항이다.**

**정의**: 화면 전체의 클릭관통 상태(전역 ON/OFF, Phase 1 구현)와 별개로, 캐릭터(또는 활성 미니게임 오브젝트)의 **현재 화면상 히트박스 영역에 한해서만, 한정된 시간 동안** 클릭을 앱이 수신하고, 그 외 모든 영역은 항상 기존 클릭관통 설정을 그대로 따르는 예외 메커니즘.

**기존 대결모드(7절) 토글과의 관계**: 7절에 이미 "대결모드를 켜면 클릭 관통이 이 캐릭터에 한해서만 자동으로 꺼짐(다른 창 클릭엔 영향 없음)"이라고 정의되어 있다. 즉 **대결모드는 사실 부분적 클릭관통 해제를, 유저가 수동으로 무기한 지속시키는 모드**로 재정의할 수 있다. 10/12/14절의 자동 해제는 상태머신이 이벤트 지속시간 동안만 자동으로 여는 것일 뿐, 근본 메커니즘은 동일하다. **Coder에게 권고**: 기능별로 각각 구현하지 말고 하나의 공통 진입점(예: `EnableLocalClickThroughOverride(hitboxRegion, releaseCondition)` 형태의 단일 API)으로 통합할 것 — 따로 구현하면 유지보수 리스크와 더불어 두 이벤트가 동시에 서로 다른 override를 걸려는 경쟁 상태 위험이 커진다.

**기술 제약 (Coder 관점, 반드시 지킬 것)**
1. **동적 추적**: 히트박스 영역 판정은 캐릭터의 매 프레임 갱신되는 화면 좌표 바운딩(콜라이더 투영)을 따라가야 한다 — 정적 좌표 고정 금지(캐릭터는 계속 움직인다).
2. **영역 밖 100% 관통**: 예외가 활성화된 동안에도 히트박스 밖 클릭은 100% 관통되어야 한다 — 전역 클릭관통 설정을 절대 침범하지 않음(원칙 2 직결).
3. **오인 클릭 완화**: 히트박스 안 클릭이라도 유저가 실제로는 "그 아래 다른 앱"을 클릭하려다 캐릭터와 우연히 겹친 경우를 완전히 배제할 수 없다. 완화책으로 클릭 감지 즉시(가능한 한 낮은 지연으로) 캐릭터가 반응하도록 해 유저가 "어, 쟤가 반응하네"라고 바로 인지하고 손을 뗄 수 있게 하고, 이 예외가 걸리는 동안의 반응은 항상 위험하지 않은(창을 닫거나 파일을 건드리는 등) 안전한 액션만 배치한다. **단, 14절 "닫기 버튼 막기"는 이 예외를 절대 적용하지 않는다**(항목 14에서 이미 규정, 안전 최우선 — 유일한 역예외).
4. **단일 소유자 락**: 10/12/13/14절 중 둘 이상이 동시에 부분 해제를 요청하는 상황을 막는 상태머신 레벨 상호 배제가 필요하다. 부분적 클릭관통 해제 리소스 자체를 "누가 지금 쥐고 있는가"를 아는 단일 소유자(single owner) 모델로 구현할 것을 권고.
5. **플랫폼별 구현 난이도 차이(정보 공유, UX 요구사항 아님)**: Windows는 레이어드 윈도우의 히트테스트 영역을 런타임에 리전(HRGN) 단위로 좁히는 방식이 있는 반면, macOS의 `NSWindow.ignoresMouseEvents`는 전체 온/오프만 지원해 "영역 기반 부분 무시"가 기본 API로 없다 — 캐릭터 크기의 서브 윈도우를 얹거나 `hitTest:`/`mouseDown:` 커스텀 오버라이드로 특정 좌표만 이벤트를 소비하고 나머지는 관통시키는 우회 설계가 필요할 수 있다.
6. **최소 지연**: 마우스다운 발생 시점부터 부분 해제 반영까지 지연이 있으면 "눌렀는데 반응 없음"으로 체감된다. 1프레임 이내 반영을 목표로 하고, 9절-3에서 이미 요청한 "전역 커서 좌표 상시 폴링" 채널과 결합해 "커서가 히트박스 안에 있다"는 사실은 항상 미리 알고 있다가 마우스다운 이벤트만 낮은 지연으로 후킹하는 구조를 권장한다.

**Phase 1과의 접점**: Phase 1의 "클릭 관통 기본 ON" 구현이 단순 전역 불리언 하나로 끝나지 않고, 위 확장(영역 기반 예외)을 나중에 끼워 넣을 수 있는 인터페이스 여지를 지금부터 열어두길 권고한다. 지금 당장 구현할 필요는 없으나(10/12/13/14절은 Phase 3/4 스코프), 전역 토글 API 설계 시 "나중에 영역 인자를 추가할 수 없는 구조"로 확정하지 않도록 Architect 확인을 요청한다.

## 17. 투두 말풍선 UX

**목표**: 일정 관리 앱이 아니라 "옆에서 살짝 챙겨주는 동료" 톤의 가벼운 리마인더. 할일을 강제하거나 미완료를 추궁하는 분위기(죄책감 유발)는 피하고, 8절 P0 원칙(관찰만 해도 재미있음)을 해치지 않는 선에서 능동적으로 쓰고 싶을 때만 쓰는 보조 기능으로 설계한다.

**트리거**: 설정창(7절에 "할일" 탭 추가 권고) 또는 트레이 메뉴의 `[+ 할일 추가]`에서 텍스트 입력 → 즉시 목록에 반영.

**유저가 보는 것 — 표현 방식 두 가지**
- **들고 다니는 모드(기본, 할일 1개 강조용)**: 캐릭터가 걷다가 주기적으로 종이 한 장을 꺼내 들고 확인하는 동작 → 그 순간 확정된 REMINDER 상태에서 파생된 말풍선으로 할일 텍스트 노출(5절 계약 그대로 적용, "곧 알려줄게" 식 예고형 금지). 종이는 다 보여준 뒤 다시 접어 넣고 원래 루프로 복귀.
- **포스트잇 모드(다건 노출용)**: 화면 한쪽에 작게 붙여두는 고정 카드. 유저가 위치를 드래그로 지정 가능(1회 지정 후 고정, 3절 발판 지정과 유사한 패턴).
```
┌ 포스트잇 ────────┐
│ ☐ 보고서 초안     │
│ ☐ 장보기          │
│ ☑ 세탁물 찾기 (완료, 취소선+반투명)│
│           [+2개 더보기]           │
└───────────────────┘
```

**유저가 할 수 있는 액션**
- 체크박스 클릭 → 즉시 취소선 + 반투명 처리 → 짧은 유지 후 목록에서 자동 정리(완료 항목은 별도 "완료함"에 누적, 리스트에서 사라져도 데이터는 보존).
- 항목 우클릭/스와이프로 삭제.
- `[+N개 더보기]`로 전체 목록 펼치기(포스트잇 카드 자체는 상시 3~4줄 이하로 제한해 화면을 어지럽히지 않음).

**할일이 너무 많을 때**
- 카드에는 최대 4줄만 노출, 나머지는 접힘. 활성(미완료) 할일이 임계치(예: 15개) 넘으면 새 항목 추가 시 "먼저 정리해볼까?" 같은 가벼운 톤의 안내만 뜨고 추가 자체를 막지는 않음(강제 차단은 스트레스 유발이므로 지양).
- 들고 다니는 모드의 리마인더 언급 빈도는 할일 개수와 무관하게 고정 주기(예: 무작위 유휴 판정마다 1개만 뽑아 언급) — 할일이 많다고 잔소리가 폭주하면 안 됨.

**예외 상태**
- **빈 상태**: 할일 0개 → 포스트잇 카드 자체를 숨기고, 캐릭터도 종이를 꺼내는 동작을 하지 않음(빈 리스트를 굳이 보여주지 않음).
- **완료 직후 되돌리기**: 방금 체크한 항목을 실수로 되돌리고 싶을 때를 위해 체크 취소(다시 클릭) 3초간 허용.

**탈출구**: 포스트잇 카드에는 항상 작은 `[숨기기]`가 있어 그 세션 동안 카드를 접어둘 수 있음(데이터는 유지, 설정에서 다시 켬). 기능 자체를 설정에서 완전히 끌 수 있는 토글 제공.

**Coder 참고(기술 요구사항)**: 포스트잇 카드는 클릭(체크박스)이 필요하므로, 15절 "부분적 클릭관통 해제" 인프라를 재사용하기보다 **캐릭터와 무관한 별도의 작은 항상-위 위젯 창(자체 OS 창, 클릭관통 없음)으로 구현할 것을 권고**한다. 이유: 15절의 예외는 "캐릭터의 동적 히트박스"를 전제로 한 단일 소유자 락 모델인데, 포스트잇은 고정 위치의 독립 UI라 그 락 경쟁에 끼워 넣을 이유가 없다. 별도 위젯 창으로 분리하면 10/12/14절의 단일 소유자 락과 전혀 경합하지 않는다.

## 18. 포모도로 감시자 UX

**목표**: 짧은 집중 시간 동안 "누가 보고 있다"는 가벼운 사회적 압력으로 집중을 돕는다. **오탐(false positive)이 이 기능의 가장 큰 리스크**다 — 정당하게 열심히 일하는 유저를 딴짓한다고 지적하면 신뢰를 잃고 바로 꺼버리는 기능이 된다. "예민하게 잡아내는 것"보다 "웬만하면 봐주는 것"을 기본값으로 삼는다.

**타이머 시작/종료 연출**
```
[시작] 트레이 메뉴 "집중 모드" → 시간 선택(15/25/50분)
       → 캐릭터가 안경을 쓰고 팔짱 끼는 확정 전이(FOCUS_WATCH 상태) + "좋아, 감시 시작" 대사
       → 화면 한켠에 작은 원형 타이머 링(캐릭터 발밑, 앱 소유 UI)
[종료-정상] 타이머 만료 → 확정된 COMPLETE 상태에서 파생된 축하 연출(박수/폴짝) + "수고했어!" + 휴식 제안 팝업
[종료-중도취소] 유저가 링 클릭 또는 트레이에서 "집중 모드 끄기" → 즉시 정상 종료(패널티 없는 톤, "그래 쉬자" 류)
```

**"딴짓 감지" 기준 — 신호 설계**
원칙 3(유저 자산 불변/read-only)에 따라 이 앱은 다른 창의 **내용**을 절대 읽을 수 없으므로, "무엇을 하고 있는지"는 알 수 없고 "얼마나 자주 옮겨 다니는지"만 유추 가능하다. 이 제약을 감안해 신호를 다음과 같이 조합한다.
- **1차 신호(주 판정): 전경 창(포커스) 전환 빈도.** 이미 확보된 전체화면 감지용 전경 창 폴링을 재사용(신규 채널 불필요) — 짧은 관찰 창(예: 2분) 안에서 포커스 전환이 비정상적으로 잦으면(예: 6회 이상) "산만함" 후보로 카운트.
- **2차 신호(보조, 단독 트리거 금지): 마우스 활동량.** "과다 움직임" 절대치보다 "완전한 무입력(자리비움)"과 "매우 짧은 간격의 광범위 이동(정처 없이 훑는 패턴)"의 두 극단만 약한 가중치로 반영 — 일반적인 작업 중 마우스 사용량은 개인차가 매우 커서 절대량 임계값은 오탐 확률이 높다고 판단, 단독 판정 근거로 쓰지 않는다.
- **판정 방식**: 두 신호를 즉시 반응시키지 않고 **연속 관찰 주기 누적**(예: 2분 창을 3회 연속 충족)으로만 1단계 경고를 발동 — 순간적 튐 한 번으로 지적하지 않는다.
- **유예 시간**: 타이머 시작 직후 첫 2분은 무조건 관찰만 하고 경고를 발동하지 않음(자리 세팅 시간 배려).

**경고 단계별 연출(점진적 에스컬레이션)**
1. **1단계 — 눈치주기(가장 약함)**: 캐릭터가 말없이 곁눈질하는 표정 변화만(대사 없음, 앰비언트 시각 신호). 가장 자주 발동해도 거슬리지 않아야 하는 단계.
2. **2단계 — 부드러운 리마인드**: 패턴이 더 지속되면(예: 1단계 후에도 추가 2주기 지속) 확정 상태에서 파생된 짧은 대사 1회("어? 딴 데 보고 있네?") — 예고형 금지, 이미 관찰된 사실만 언급.
3. **3단계 — 창 두드림**: 그래도 지속되면 캐릭터가 타이머 위젯을 통통 두드리는 과장된 애니메이션 + 살짝 화면 흔들림(캐릭터 레이어 국소 효과만, 원칙 3에 따라 실제 창은 흔들지 않음).
- **즉시 리셋 규칙**: 어느 단계든, 신호가 정상 범위로 돌아오면 다음 관찰 주기부터 즉시 1단계 이하로 리셋된다(과거 산만함을 누적 집계해 계속 벌주지 않음 — "지금 상태"만 본다).

**설정 가능 항목(오탐 완화용, 7절 설정창에 추가 권고)**: 감시 민감도(관대/보통/예민) 3단계 슬라이더, 감시 자체를 끄고 순수 타이머로만 쓰는 옵션.

**예외 상태**
- 전체화면 게임/영상 감지(6-4절) 중에는 감시 로직 자체를 일시정지(Suspended) — 몰입 콘텐츠 시청 중 포커스 전환이 없는 것은 정상이므로 오히려 경고가 안 나가는 게 맞고, 반대로 그 상태에서 캐릭터가 숨어있으므로 연출도 어차피 불가능.
- 관찰 신호 계산에 필요한 폴링은 기존 전경 창 감지 인프라를 재사용해 신규 상시 폴링을 추가하지 않는다(성능 부담 최소화, BUG-M3 폴링 규율 이슈 재발 방지).

**탈출구**: 타이머 링 클릭 또는 트레이 메뉴로 언제든 즉시 종료. 트레이 긴급정지도 항상 유효.

## 19. 스트레스 게이지 UX

**목표**: 캐릭터에게도 "감정"이 쌓인다는 서사적 재미를 주되, 게이지 자체가 게임화 UI처럼 화면을 침범해 관찰형 앱의 미학을 해치지 않게 한다.

**게이지가 쌓이는 트리거(제안)**
- 격파훈련 과다: 드래그&던지기(12절)·격파 미니게임(10절) 등 캐릭터에게 물리적 부담을 주는 상호작용을 짧은 시간 내 과도하게 반복(예: 5분 내 8회 이상) — "너무 험하게 다뤘다"에 해당.
- 장시간 방치: 상호작용이 전혀 없는 상태가 매우 길게(예: 반나절 이상) 지속 — "심심함/외로움" 계열 스트레스.
- 방해성 이벤트의 잦은 강제 중단: 트레이 긴급정지가 짧은 기간 내 반복 사용됨 — "하려던 걸 자꾸 못 하게 막혔다"는 좌절 누적(단, 긴급정지는 유저의 정당한 권리이므로 이 트리거는 약한 가중치로만 반영하고, 긴급정지 사용을 주저하게 만들 정도로 강하면 안 됨 — 6-5절 원칙과 충돌 방지).

**게이지 노출 방식 — 상시 노출 대신 "필요시만"**
관찰형 앱에 체력바/게이지 UI가 상시 떠 있으면 캐릭터가 아니라 "육성 게임"처럼 보여 앱의 톤이 깨진다. 노출 강도를 3단으로 분리한다.
- **상시(항상)**: 캐릭터의 표정/자세로만 은은하게 암시(수치 없음) — 정상일 땐 평소 idle, 스트레스가 쌓일수록 어깨가 처지고 표정이 흐려지는 점진적 비주얼 변화.
- **필요시(트레이)**: 트레이 아이콘에 작은 점 색상(초록/노랑/빨강 3단계)만 상시 표시 — 수치가 아니라 "지금 상태가 괜찮은지"만 곁눈질로 확인 가능.
- **원할 때(설정창)**: 설정창(7절)에 상세 게이지 바 + "요즘 왜 스트레스가 쌓였는지" 최근 트리거 요약 텍스트 노출 — 궁금할 때만 열어보는 정보.

**반항 임계값 도달 전 예고 신호**
원칙 1(대사는 확정된 상태에서만 파생, 예고형 금지)에 따라 "나 이러다 가출한다?" 같은 **미래를 약속하는 대사는 금지**한다. 대신 "지금 이미 확정된 기분 상태"만 표현한다.
- 임계값 근접(예: 80%) 시 캐릭터가 확정된 SULKY(부루퉁함) 상태로 전이 → 그 상태에서 파생된 한숨/짜증 대사("아 몰라...")와 눈에 띄게 처진 자세만 노출. 이는 "곧 가출하겠다"는 예고가 아니라 "지금 기분이 안 좋다"는 현재형 사실 보고이므로 계약 위반이 아니다.
- 트레이 점 색상이 노랑→빨강으로 전환되는 것 자체가 유저에게는 사실상의 예고 역할을 겸한다(비언어적 신호이므로 원칙 1과 무관).

**탈출구**: 게이지 자체는 방해성이 없으므로 별도 탈출구 불필요. 단, 게이지가 뒤따르는 반항 이벤트(20절/24절)는 각자의 탈출구를 따른다. 설정에서 스트레스 시스템 자체를 끌 수 있는 토글 제공(순수 관찰형만 원하는 유저 배려).

## 20. 가출 UX

**목표**: "삐져서 잠깐 사라짐"이라는 서사적 재미를 주되, 방치형 앱 특성상 **유저가 못 찾고 방치해도 앱이 영구히 깨진 것처럼 보이면 절대 안 된다.**

**"나 안 해!" 이후 흐름**
```
스트레스 임계값(2) 도달 → 확정된 RUNAWAY 상태 전이
  → "나 안 해!" 대사(확정 상태에서 파생) → 화면 가장자리로 뛰어가 퇴장하는 애니메이션
  → 캐릭터 완전히 사라짐, 트레이 아이콘 문구 "가출 중 (찾아주세요)"로 전환
```

**유저가 찾는 방법**
- 화면 안 몇 군데 정해진 "숨을 수 있는 자리"(예: 화면 네 모서리, 트레이 아이콘 근처) 중 한 곳에 실제로 숨어 있고, 유저가 그 구역들을 클릭하거나 드래그로 훑으며 찾는다.
- 힌트: 완전히 무작위 추측이 되지 않도록, 숨은 위치 근처 화면 가장자리에 아주 미세한 흔들림/작은 소리 이펙트로 은은한 단서를 준다(너무 쉬우면 재미없고 너무 어려우면 좌절 — 균형점은 실측 후 조정 권고).
```
┌───────────────────────────┐
│ ░ ← 모서리를 클릭/드래그해서 뒤져보세요       │
│                                             │
│                                    ░        │
│ ░                                          │
│                                             │
│                                     ░       │
└───────────────────────────┘
찾으면: 그 자리에 웅크린 캐릭터가 놀란 표정으로 드러남
```

**간식으로 달래기**
- 찾은 자리에 앱 소유 UI로 `[간식 주기]` 버튼 노출(14절 "사과 먹이기"와 동일 패턴 재사용 — 새 입력 경로 불필요).
- 클릭 → 간식을 건네는 애니메이션 → 캐릭터가 못 이기는 척 받아먹는 확정 리액션 → 화해 대사 → 정상 복귀 + 스트레스 게이지 상당량 감소(완전 리셋은 아님, "달래졌지 완전히 풀린 건 아님" 정도의 여운은 허용).

**못 찾고 방치하면?**
- 무한정 숨어있는 상태는 절대 허용하지 않는다. **자동 복귀 타임아웃**(예: 1~2시간, 또는 다음 앱 재실행 시점 중 먼저 도래하는 쪽)이 지나면 캐릭터가 스스로 "심심해서 왔어" 같은 멋쩍은 대사와 함께 정상 위치로 복귀한다 — 이는 유저의 어떤 조치도 없이 보장되는 마지노선이며, 14절의 "최대 지속시간 타임아웃"과 동일한 안전망 철학이다.
- 트레이 메뉴에도 언제든 `[돌아오라고 부르기]` 수동 소환 버튼을 상시 제공 — 못 찾겠으면 즉시 강제 복귀 가능(찾기 미니게임을 강제하지 않음, 8절 P0 "관찰만 해도 무방" 철학 유지).

**예외 상태**
- 가출 중에는 다른 방해성/스펙터클 이벤트(10/11/13/14절)가 동시에 발동하지 않는다(캐릭터가 화면에 없는 상태에서 다른 이벤트가 뜨는 모순 방지 — 16절 상호배제 세트에 RUNAWAY 상태 추가 권고, 25절 참고).
- 전체화면 게임 감지 시: 가출 상태는 이미 "화면에 안 보이는" 상태이므로 특별히 취소할 필요는 없으나, 숨은 위치 탐색 UI(클릭 감지 영역)는 게임 중 비활성화해 비침해 원칙을 지킨다.

**탈출구**: `[돌아오라고 부르기]`(즉시, 유저 주도) → 간식 주기(찾은 후, 유저 주도) → 자동 복귀 타임아웃(무조치 시 보장). 트레이 긴급정지 버튼은 이 상태에서는 "종료"가 아니라 "즉시 강제 복귀"로 동작(24절에서 인질극과의 차이로 재확인).

## 21. 던전 파밍 UX

**목표**: 열려 있는 창(예: 브라우저) 하나를 "탐험할 던전"으로 빌려 쓰는 연출을 제공하되, **그 창은 유저가 실제로 계속 정상 사용 중인 창일 수 있으므로 절대 그 창의 실제 조작을 방해하지 않는다.** 이 절이 원칙 2/3과 충돌하지 않는지가 이번 설계의 핵심 점검 대상이다.

**트리거**: 캐릭터가 특정 레벨(육성 시스템, 세부 수치는 Phase 5 착수 시 Architect/Coder와 별도 합의 필요)에 도달하면 트레이 메뉴에 `[탐험 보내기]`가 활성화. 유저가 이를 선택하면 현재 열린 창 목록 중 하나를 "던전"으로 지정하는 간단한 선택 UI(앱 소유 UI, 창 썸네일이 아니라 창 제목/아이콘만 나열 — 창 내용 캡처 금지, 원칙 3).

**연출 — 창 안으로 들어가는 착시**
```
1) 캐릭터가 지정된 창의 테두리로 다가감
2) 창 테두리에 반짝이는 "문(Gate)" 오버레이(캐릭터 레이어 위 순수 시각 효과)
3) 캐릭터가 점점 작아지며 문 안으로 빨려 들어가듯 사라짐
4) 사라진 자리엔 작은 진행 배지만 남음: "🗺 탐험 중... (창 우측 상단 구석)"
```

**레이어 겹침 시 원본 앱 조작 가능 여부 — 명확한 결론**
- 3번의 "문" 연출과 4번의 진행 배지는 **모두 순수 시각적 오버레이**이며, 클릭 이벤트를 절대 가로채지 않는다. 즉 던전 진행 중에도 유저는 그 창(예: 크롬)을 스크롤/클릭/타이핑하며 정상적으로 계속 사용할 수 있어야 한다.
- 이는 14절 "닫기 버튼 막기"와 동일한 **역예외 취급** 대상이다 — 15절 "부분적 클릭관통 해제"를 이 오버레이에는 절대 적용하지 않는다. 진행 배지가 창의 실제 UI(예: 브라우저 탭 닫기 버튼) 위에 시각적으로 겹치지 않도록 배치 규칙(항상 창의 콘텐츠 영역이 아닌 테두리 바깥쪽 여백에만 배치, 콘텐츠 영역과 겹칠 수밖에 없는 작은 창은 배지를 생략하고 트레이 아이콘 진행률로만 대체)을 둔다.
- 결론: 원칙 2/3과 충돌하지 않는다 — 오히려 이 기능이 "겹침 상태에서도 원본 앱 조작이 100% 가능"의 대표 사례가 되어야 하며, Coder 구현 시 이 오버레이 레이어에는 클릭 인터셉트 코드가 한 줄도 들어가지 않아야 한다.

**파밍 결과 확인 UX**
- 탐험은 그 창이 열려 있던 시간에 비례해 진행되며(정확한 산식은 Coder/Architect 합의), 완료되면 캐릭터가 문 밖으로 다시 "짠" 하고 등장.
- 앱 소유 UI로 작은 결과 팝업 노출: 획득 골드/재료 목록 → 클릭으로 닫으면 인벤토리(설정창 "보관함" 탭, 7절에 추가 권고)에 누적.

**예외 상태**
- 탐험 중 대상 창이 닫히면(창=지형이자 던전 컨테이너 소실): 즉시 탐험을 중단하고, 그때까지의 진행률에 비례한 부분 보상을 지급하며 캐릭터가 조기 퇴장 애니메이션과 함께 복귀 — "던전이 사라져서 캐릭터가 실종됨" 같은 상태가 절대 발생하지 않게 한다.
- 대상 창이 최소화되거나 다른 창에 가려짐: 탐험 자체는 계속 진행(백그라운드 진행), 완료 시점에만 재등장하면 되므로 창의 화면 가시성과 무관하게 처리 가능.

**탈출구**: 트레이 메뉴에서 `[탐험 취소]` 언제든 가능(부분 보상 지급 후 즉시 복귀). 방해성 이벤트가 아니므로(원본 창 조작에 지장 없음) 6-5절 긴급정지 대상은 아니지만, 취소 경로는 항상 열려 있어야 한다.

## 22. 세포분열/군대 UX

**목표**: 레벨맥스 도달이라는 성취를 "숫자 갱신"이 아니라 눈에 보이는 서사적 사건(분열)으로 보상하되, 다수 개체가 화면을 채울 때 유저 피로도와 성능을 동시에 관리한다.

**분열 연출**
```
레벨맥스 도달 → 확정된 MITOSIS 상태 전이
  → 캐릭터가 부르르 떨리며 형태가 두 겹으로 흐릿하게 겹쳐 보임
  → 좌우로 갈라져 나가며 두 개체로 완성(신규 개체는 레벨 초기화 또는 절반 스탯)
  → 확정된 상태에서 파생된 탄생 대사("응애" 류, 신규 개체 쪽에서 1회만)
```

**개별 구분/관리 — 우선순위 판단**
- **기본값은 전부 자동**(8절 P0 철학 유지 — 여러 마리가 늘어나는 것 자체가 관전 재미이지, RTS식 개별 지휘가 이 앱의 핵심 재미는 아니라고 판단).
- 다만 "내 캐릭터가 어느 쪽인지도 모르겠다"는 최소한의 혼란은 막아야 하므로, 각 개체 머리 위에 아주 작은 색상/번호 태그를 상시 부여하고, 태그를 클릭하면 그 개체의 이름/레벨만 보여주는 짧은 툴팁을 띄운다(정보 열람만, 개별 커맨드는 이번 스코프에서 제외 — 과설계 방지). 이름 변경은 설정창 "보관함" 탭에서 가능.
- 개별 지휘(예: "이 녀석만 재워라") 같은 세부 조작은 손맛은 있으나 이 앱의 관찰형 정체성과 맞지 않는다고 판단해 이번 Phase 5 스코프에서는 제외를 권고(향후 DLC 확장 후보로만 기록).

**개체수 상한 및 혼잡 방지**
- 화면당 최대 개체 수 상한을 둔다(제안값: 기본 6마리, 설정에서 최대 10마리까지 상향 가능하되 저사양 기기 경고 문구 동반).
- 상한 도달 후 추가 분열 조건 충족 시: 새 분열을 보류하지 않고, 기존 개체 중 하나와 "재결합(역분열)"해 강해진 하나로 합쳐지는 선택형 이벤트를 제공하거나, 초과분을 "독립"시켜 화면 밖 별도 "도감"으로 수집(컬렉션 재미로 전환) — 둘 중 하나를 Coder/Architect와 협의해 확정 권고(UX 관점에서는 도감 수집형이 더 관대하고 상실감이 적어 선호).

**군대 행진/사회생활 연출**
- 다수 개체가 있을 때 저빈도 랜덤으로 발판 위를 일렬로 행진하거나 서로 마주쳐 인사하는 앰비언트 스펙터클을 추가(입력 개입 없는 순수 관전용).
- 이 연출은 "개입 요구 이벤트"가 아니므로 10/11/13/14절의 상호배제 세트와는 별개 카테고리지만, 동시에 여러 스펙터클이 겹치면 화면이 혼잡해지므로 다른 이벤트가 활성 중이면 행진 연출은 낮은 우선순위로 자동 디바운스(뒤로 미룸)한다.

**예외 상태**
- 전체화면 게임 감지 시 모든 개체가 동시에 페이드아웃/재개(6-4절과 동일 원칙, 개체마다 Suspended 상태 개별 보존).
- 개체 수가 많을수록 각 개체의 유휴 스펙터클(격파/라이벌 등) 발동 확률은 개체당 독립이 아니라 전체 화면 기준 합산 확률로 관리해야 한다(개체가 늘수록 스펙터클이 산술급수적으로 폭증하는 것을 방지) — Coder 구현 시 유의 요청.

**탈출구**: 해당 없음(비침해 콘텐츠). 개체수 상한 설정과 도감/재결합 정책은 설정창에서 언제든 조정 가능.

## 23. PC 하드웨어 반응 UX

**목표**: 각 반응이 "정보"로서의 유용함과 "연출"로서의 재미 사이에서, 이 앱은 어디까지나 후자를 주력으로 삼고 전자는 부산물로만 취급한다 — 시스템 모니터링 앱을 대체하려 하지 않는다. 과도한 알림으로 방해가 되지 않도록 모든 반응에 공통 빈도 제한을 건다.

**공통 원칙(모든 하드웨어 반응에 적용)**
1. **지속 조건**: 순간적인 스파이크(예: CPU가 한두 프레임만 튐)에는 반응하지 않고, 일정 시간(예: 30초~1분) 이상 지속된 상태만 트리거로 인정.
2. **상태별 쿨다운**: 같은 반응이 재차 발동하려면 최소 재발생 간격(예: 5~10분)을 둔다.
3. **개별 on/off**: 설정창(7절)에 4개 반응 각각 독립 토글 제공 — 배터리 상태를 캐릭터가 알려주는 걸 유용하다 여기는 유저도, 성가시다 여기는 유저도 있으므로 개인차를 인정한다.
4. **폴링 재사용**: 신규 상시 폴링 루프를 늘리지 말고, Phase 1에서 이미 자리 잡은 발판 폴링 주기 관리 패턴(`FootholdPoller`/`StickConfig.footholdPollInterval`류)과 같은 방식으로 하드웨어 상태도 별도 설정 가능한 저빈도 폴링 주기를 두도록 Coder에게 권고(24시간 상주 앱에서 배터리/CPU 조회 자체가 부담이 되는 역설 방지).

**반응별 설계**
- **CPU 80%+**: 캐릭터가 헥헥거리며 부채질하는 연출. 정보성보다는 코믹 연출 위주 — 정확한 퍼센트 수치는 노출하지 않고 "더워하는" 은유로만 표현.
- **배터리 20% 이하**: 캐릭터가 힘없이 비틀거리거나 하품하는 연출 + 배고픈 은유의 대사("배고파..."). 실제 배터리 % 숫자는 노출하지 않는다(OS 자체 배터리 알림과 중복/충돌 방지, 이 앱은 감성적 은유만 담당). **최초 진입 시 1회만 뚜렷한 신호**를 주고, 이후로는 배터리가 회복되기 전까지 강한 재알림 없이 캐릭터의 지친 idle 자세만 조용히 유지.
- **충전 중**: 캐릭터가 밥 먹듯 기뻐하는 연출 + 에너지 차오르는 파티클. 순수 긍정 연출이라 반복 억제가 상대적으로 덜 중요하지만, 상태 진입 시 1회 전이 연출 후 지속 중에는 잔잔한 idle 변형으로 전환(충전 내내 계속 격하게 기뻐하면 오히려 산만함).
- **네트워크 끊김**: 캐릭터가 안테나를 찾듯 두리번거리는 가벼운 코믹 연출까지만. **이 앱이 실제 네트워크 장애를 대신 알려주는 신뢰할 알림 채널이 되어서는 안 된다**(스코프 아웃 명시) — 재연결 여부를 계속 감시해 알려주는 기능 등은 만들지 않는다.

**예외 상태**
- 전체화면 게임 감지 중에는 모든 하드웨어 반응 연출이 함께 숨김(6-4절 우선, 캐릭터 자체가 안 보이므로 자연히 해당).
- 여러 하드웨어 반응 조건이 동시에 충족되면(예: 배터리 부족 + CPU 과부하 동시) 한 번에 하나만 표현하고 우선순위(제안: 배터리 > CPU > 네트워크 > 충전)에 따라 순차 노출 — 캐릭터가 동시에 두 가지 다른 표정/자세를 겹쳐 보이면 안 됨.

**탈출구**: 설정창에서 개별 토글로 언제든 끌 수 있음. 방해성이 낮은 콘텐츠이므로 트레이 긴급정지 대상은 아니나, 설정 토글이 실질적 탈출구 역할을 한다.

## 24. 반항기의 두 얼굴 — 가출(20절) vs 인질극(14절) 구분 정리

이번 Phase 5 설계로 스트레스 게이지(19절)라는 공통 원인이 처음 생기면서, 기존 14절 인질극과 신규 20절 가출이 "같은 반항의 두 단계"로 묶이게 됐다. 유저가 이 둘을 혼동하지 않도록 다음을 확정한다.

**단계 구분(심각도 위계)**
- **1단계 — 인질극/해킹(14절, 기존)·로데오(13절)**: 스트레스 게이지가 중간 수준(예: 60%대)에 진입하면 이 계열 이벤트의 **발동 확률에 가중치**가 붙는 정도로만 연결한다. 즉 인질극은 "장난"의 발생 빈도가 스트레스에 따라 살짝 늘어나는 것일 뿐, 여전히 확률 기반의 가벼운 이벤트라는 기존 성격(10/11절과 동급의 스펙터클)을 유지한다.
- **2단계 — 가출(20절, 신규)**: 스트레스 게이지가 높은 임계값(예: 90%)에 도달하거나 1단계가 장시간 해소되지 않고 누적되면 발동하는 **심각한 반항**. 확률이 아니라 임계값 도달 시 확정 발동에 가깝게 설계해, "이건 진짜 삐진 거다"라는 무게감을 준다.

**시각/톤으로 명확히 분리**

| 구분 | 인질극(1단계) | 가출(2단계) |
|---|---|---|
| 캐릭터 존재 여부 | 화면에 계속 보임 | 화면에서 완전히 사라짐(부재) |
| 원본 앱 조작 | 100% 정상(클릭은 항상 관통) | 해당 없음(방해 자체가 없음) |
| 표정/톤 | 짓궂은 히죽거림, 밝은 강조색 반짝임 | 처지고 어두운 표정, 채도 낮은 팔레트 |
| 트레이 문구 | "장난치는 중 (진정시키기 가능)" | "가출 중 (찾아주세요)" |
| 트레이 긴급정지 버튼 동작 | 즉시 종료(이벤트 중단) | 즉시 강제 복귀(소환) — 라벨도 다르게 표기 권고 |

**존재/부재라는 가장 강력한 구분선**: 위 표의 항목들보다 근본적으로, "캐릭터가 보이는데 짓궂게 구는가(인질극)" vs "캐릭터가 아예 없는가(가출)"라는 구조적 차이 자체가 가장 직관적인 구분 신호이므로, 별도 설명 UI 없이도 유저가 헷갈릴 여지가 작다고 판단한다. 다만 트레이 문구와 긴급정지 버튼 라벨을 상태별로 다르게 표기하는 것은 필수로 한다(같은 버튼이 "종료"와 "소환"을 다른 상황에서 다르게 수행하면서 라벨이 안 바뀌면 혼란).

**Coder 참고**: 16절-15에서 정의한 "한 번에 하나의 스펙터클/개입 이벤트만 활성" 상호배제 세트에 신규 상태 `RUNAWAY`(가출)도 포함시켜야 한다(가출 중엔 인질극/로데오/격파미니게임 등 다른 어떤 방해성·스펙터클 이벤트도 동시 발동 금지 — 캐릭터가 없는데 다른 이벤트가 뜨는 모순 방지). 상세는 25절 참고.

## 26. 자율 배회 AI 행동 설계 (긴급 — BUG-P1-B2 Blocker 대응)

> **배경**: Debugger 2차 리포트(`docs/BUG_REPORT_PHASE1.md` BUG-P1-B2)가 Phase 1 구현의 이동 트리거가 `Input.GetAxisRaw("Horizontal")`/`GetButtonDown("Jump")`(키보드) 하나뿐임을 지적했다. 이 프로젝트 기획 원문(`CLAUDE.md`, `docs/ARCHITECTURE.md`, 본 문서 2절/8절) 어디에도 키보드 조작은 등장하지 않으며, 8절 P0 원칙("아무것도 안 해도 재미있어야 함")과 정면 충돌한다. 게다가 진짜 `WS_EX_NOACTIVATE` 오버레이가 완성되면 그 창은 키보드 포커스를 받을 수 없어 키보드 이동은 구조적으로 영구 고장난다(가설 H6). **Architect 결정: 키보드 입력 기반 이동을 완전 폐기하고 자율 배회 AI로 교체**. 아래는 Coder가 즉시 파라미터로 옮길 수 있도록 수치 위주로 정리한다.

### 26-1. 기본 배회 사이클

캐릭터는 "쉬는 페이즈(Resting)"와 "이동 페이즈(Moving)"를 번갈아 반복한다. 이 두 페이즈는 그 자체로 기존 `IdleState`/`WalkState`의 `moveInputDeadzone` 판정에 의해 자동으로 Idle/Walk 전이를 유발하므로, 상태머신 쪽 수정은 필요 없다 — `MoveInputX` 값만 이 규칙대로 채워주면 된다.

| 파라미터 | 값 | 비고 |
|---|---|---|
| Idle(Resting) 유지 시간 | 2.0 ~ 6.0초 균등분포 랜덤 | Idle 진입마다 재추첨 |
| Walk(Moving) 지속 시간 | 1.5 ~ 4.0초 균등분포 랜덤 | 시간 만료 전이라도 발판 경계 도달 시 즉시 종료(26-2 우선) |
| Walk 중 즉흥 방향전환 판정 주기 | 0.5초마다 | |
| Walk 중 즉흥 방향전환 확률 | 판정마다 8% | 경계와 무관하게 "변덕"으로 반대 방향 선택. 같은 Walk 페이즈 내 최대 1회로 제한(너무 잦으면 안절부절로 보임) |
| Idle 종료 후 다음 행동 분포 | Walk 75% / Idle 연장(제자리 유휴모션 재생) 20% / 제자리 점프 5% | 매번 가중치 랜덤 추첨 — 고정 패턴 금지 |
| 최초 진행 방향 | 좌우 50:50 랜덤 | 단, 시작 위치가 화면 경계에 붙어 있으면 안쪽 방향으로 강제(26-2 로직 재사용) |

### 26-2. 발판 경계 처리

| 파라미터 | 값 | 비고 |
|---|---|---|
| 경계 도달 판정 거리 | 진행 방향 앞쪽 **현재 서 있는 발판**의 잔여 길이 ≤ 0.3 유닛 | 전체 발판 통합 경계가 아니라 **지금 딛고 있는 그 발판 하나**의 경계를 기준으로 함(26-6 Coder 확인 필요 참고) |
| 경계 도달 시 기본 동작(90%) | 즉시 정지(`MoveInputX = 0`) → 0.3~0.8초 랜덤 대기 → 반대 방향으로 전환 후 Walk 재개 | 로봇처럼 딱 멈추지 않도록 대기시간에 지터 적용(26-3) |
| 경계 도달 시 점프 시도(10%) | 정지 대신 진행 방향 유지한 채 `JumpRequested` 펄스 발동 | **"파쿠르 전 단계 예고"** — Phase 2 파쿠르 도입 전 필드테스트 겸용 이스터에그. 착지할 발판이 없으면 `Fall`로 이어지고, BUG-P1-B1 수정(화면 하단 안전망)이 반드시 선행되어야 "허공에 뜬 채 사라짐"으로 보이지 않는다 — Coder에게 순서 의존성 명시 |
| 화면 자체의 좌우 끝(발판이 더 없음) | 90%/10% 분기와 무관하게 항상 정지+반전(점프 시도 금지) | 화면 밖으로 넘어갈 지형이 없는 경우까지 점프를 시도하면 100% 낙하이므로 이 경우만 예외적으로 점프 확률 0%로 강제 |

### 26-3. "살아있는 느낌" 디테일

애니메이션 자체는 Phase 2+ 렌더링 레이어 책임이므로, 여기서는 **트리거 조건**만 정의한다(실제 재생은 이벤트버스로 통지 후 별도 처리).

| 유휴 모션 | 트리거 조건 | 지속 시간 |
|---|---|---|
| 두리번거리기(look around) | Idle 진입 후 1.0~2.5초 랜덤 지연 뒤 발동. Idle이 그 전에 Walk로 전이되면 취소 | 0.6~1.0초 |
| 앉기/하품 | "Idle 연장"이 연속 3회 이상 선택된 경우에만 15% 확률로 발동(오래 가만히 있을수록 지친 티) | 1.5~2.5초 |

**지터(jitter) 원칙**: 위 모든 지속시간 파라미터(Idle/Walk 지속시간, 경계 정지 대기시간)에 **±15~20% 랜덤 지터**를 추가로 곱한다. 균등분포 추첨 자체가 이미 지터 역할을 하지만, Phase 5 세포분열(22절)로 여러 개체가 동시에 존재하게 되면 **개체마다 독립된 RNG 시드**를 반드시 사용해야 한다 — 모든 개체가 같은 시드/같은 타이밍으로 움직이면 그 자체로 "로봇처럼 동기화된" 느낌을 준다(22절과 연동, 지금 개체별 시드 구조를 잡아두면 Phase 5에서 재작업 불필요).

### 26-4. 커서 근접 반응과의 관계 — Phase 2로 연기 (판단 및 근거)

**결정: 이번 Phase 1 스코프에는 넣지 않는다.**

- 근거 (a): Debugger 리포트 자체가 이번 Phase 1을 "물리/전이 골격 검증" 단계로 규정하고 있다.
- 근거 (b): 커서 근접 반응은 "멈춰서 쳐다보기"라는 **시각적 표현**이 있어야 체감되는데, 그 표현(고개 돌리기 포즈 등)은 렌더링/애니메이션 레이어(Phase 2+ 스코프) 없이는 구현해도 눈에 보이지 않는 내부 상태 변화에 그친다 — 지금 넣으면 비용만 들고 체감 가치가 0.
- 근거 (c): 9절-3에서 이미 요청한 "전역 커서 좌표 상시 폴링" 채널(`ICursorPositionService`, `StickmanAgent.TryGetCursorPosition`)이 Phase 1에 이미 존재하므로, Phase 2에서 그대로 재사용 가능 — 지금 새 폴링 채널을 만들 필요가 없다.

**단, 지금(Phase 1) 훅만 열어둘 것을 권고**: `AutoWanderController` 생성자가 `StickmanAgent`(또는 `TryGetCursorPosition` 델리게이트)에 대한 참조를 미리 받아두게만 하고, 실제 반응 로직은 빈 채로 둔다. 이렇게 하면 Phase 2에서 새 클래스를 또 만들 필요 없이 로직만 채워 넣으면 된다.

**Phase 2 선반영 스펙(지금 결정, 나중에 구현)**:

| 파라미터 | 값 |
|---|---|
| 반응 트리거 반경 | 커서-캐릭터 중심 거리 ≤ 150px(OS 화면 좌표 기준) |
| 반응 조건 | 현재 Walk 페이즈 진행 중일 때만(Idle 중에는 반응 안 함 — 이미 정지해 있으므로 체감 차이 없음) |
| 반응 내용 | Walk 타이머를 **일시정지**(소멸 아님) + 0.4~0.8초간 `MoveInputX = 0` 고정 + "쳐다보기" 트리거 이벤트 발행 → 타이머 재개 |
| 로데오 커서(13절)와의 구분 | 로데오는 "커서가 5초 이상 정지"가 트리거, 이 반응은 "커서가 근접하면 즉시" 트리거 — 시간 스케일이 달라 서로 겹치지 않음. 단, Phase 2 구현 시 두 트리거가 동시에 조건을 만족하는 경우(근접 + 정지 5초) 로데오 커서가 우선하도록 명시적 우선순위 필요 |

### 26-5. 키보드 입력의 최종 처분

- **완전 제거를 확정한다.** `Input.GetAxisRaw("Horizontal")`/`Input.GetButtonDown("Jump")` 호출은 `StickmanAgent.Update()`에서 삭제하고, 그 자리를 아래 26-6 계약으로 전면 대체한다. "일부만 남기고 폴백으로 유지" 같은 절충안은 채택하지 않는다 — 어차피 진짜 오버레이 완성 시 키보드 경로는 죽으므로 절반만 남겨봐야 관리 비용만 늘어난다.
- **근거**: `CLAUDE.md`, `docs/ARCHITECTURE.md`, 본 문서(UX_FLOW.md) 전체 어디에도 키보드/화살표/WASD 조작에 대한 언급이 없다. 이 앱은 처음부터 "관찰형 데스크톱 펫"이며, 8절이 못박은 유저의 기본 액션은 P0 "아무것도 안 하기"다. 키보드 입력은 기획에 존재한 적 없는 임시 구현이었다.
- **향후 대결모드(Phase 3, 7절/15절)에서도 키보드를 부활시키지 않는다.** 대결모드는 이미 "클릭관통을 캐릭터 한정 자동 해제"(7절) + "부분적 클릭관통 해제"(15절) + 드래그&던지기(12절)의 마우스/클릭 기반 인프라로 설계되어 있다. 유저가 캐릭터와 상호작용하는 유일한 경로는 처음부터 끝까지 **마우스(클릭/드래그/커서 위치)**이며, 이는 로드맵 전체에서 재확인되는 설계 방향이다. 즉 "지금은 키보드를 빼지만 대결모드 때 다시 필요하지 않을까"라는 의문에 대한 답은 **아니다** — 명확히 남겨둔다.

### 26-6. 엔지니어링 인터페이스 제안

`Input.GetAxisRaw`/`GetButtonDown` 자리를 대체할 최소 계약. 최종 구현은 Coder 몫이며, 아래는 "이런 파라미터를 받는 이런 형태의 클래스가 필요하다" 수준의 제안이다.

```csharp
namespace StickMate.States
{
    /// <summary>
    /// Idle/Walk/Jump 상태 전이가 소비하는 "누가 MoveInputX/JumpPressed를 채우는가"의 계약.
    /// blackboard.MoveInputX/JumpPressed 필드 자체는 그대로 유지하고, 그 값을 채우는 소스만
    /// Input.GetAxisRaw 직접 호출에서 이 인터페이스 구현체로 교체한다.
    /// </summary>
    public interface IMovementIntentSource
    {
        /// <summary>-1(왼쪽)~1(오른쪽). moveInputDeadzone 이하는 기존과 동일하게 "정지"로 취급.</summary>
        float MoveInputX { get; }

        /// <summary>이번 프레임에 점프 의도가 새로 발생했는지 — Input.GetButtonDown과 동일하게
        /// "정확히 1프레임만 true" 펄스 계약을 유지해야 한다(그렇지 않으면 JumpState 전이가
        /// 매 프레임 재점프를 시도할 위험이 있음).</summary>
        bool JumpRequested { get; }
    }

    /// <summary>
    /// 자율 배회 AI 본체. FootholdPoller/GroundSensor와 같은 컨벤션을 따라 MonoBehaviour가 아닌
    /// 순수 C# 클래스로 작성 — StickmanAgent.Update()가 매 프레임 Tick(deltaTime)을 호출해
    /// 내부 타이머를 갱신하고, 그 결과를 이 인터페이스로 노출한다(유닛 테스트 가능성 확보 목적도 겸함).
    /// 26-1~26-3 규칙을 타이머 기반으로 계산해 채워 넣는 구조.
    /// </summary>
    public sealed class AutoWanderController : IMovementIntentSource
    {
        public AutoWanderController(StickmanBlackboard blackboard, StickConfig config, System.Random rng) { /* ... */ }

        public float MoveInputX { get; private set; }
        public bool JumpRequested { get; private set; }

        /// <summary>26-1~26-3의 타이머/확률 규칙을 갱신. 경계 판정을 위해 blackboard.SenseGround()
        /// (또는 26-7에서 요청한 확장판)를 내부적으로 호출한다.</summary>
        public void Tick(float deltaTime) { /* ... */ }
    }
}
```

`StickmanAgent.Update()` 교체 예시:

```csharp
// 기존
_blackboard.MoveInputX = Input.GetAxisRaw("Horizontal");
_blackboard.JumpPressed = Input.GetButtonDown("Jump");

// 교체 후
_autoWander.Tick(dt);
_blackboard.MoveInputX = _autoWander.MoveInputX;
_blackboard.JumpPressed = _autoWander.JumpRequested;
```

`IdleState`/`WalkState`/`JumpState`/`FallState`는 이미 `blackboard.MoveInputX`/`JumpPressed` 값만 소비하고 그 출처를 모르므로, 4개 상태 클래스는 **한 줄도 수정할 필요가 없다**. `JumpState.Enter()`가 `_blackboard.MoveInputX * walkSpeed`로 점프 궤적의 수평 속도를 그대로 반영하는 기존 로직도 그대로 유지된다(26-2 "경계에서 점프 시도" 시 진행 방향을 유지해야 하는 요구사항과 자연스럽게 맞아떨어짐).

### 26-7. Coder 확인 필요 사항

- **`GroundSensor.GroundInfo` 확장 필요**: 현재 `ScreenLeftWorldX`/`ScreenRightWorldX`는 "모든 발판을 통틀어 합친" 전역 경계만 제공한다(`GroundSensor.cs:30-34`). 그런데 26-2의 경계 판정은 **지금 캐릭터가 실제로 딛고 서 있는 그 발판 하나**의 좌우 경계를 기준으로 해야 한다(예: 넓은 창 위를 걷다가 그 창의 오른쪽 끝에 도달했는데, 마침 오른쪽에 다른 창이 더 있으면 전역 경계 기준으로는 "아직 안 끝남"으로 잘못 판정된다). `GroundInfo`에 `CurrentFootholdLeftWorldX`/`RightWorldX`(접지 중인 발판 하나만의 경계, `Grounded==false`면 무의미) 필드 추가를 권고한다.
- **`JumpRequested`의 펄스 계약**: `AutoWanderController.Tick()`이 점프를 결정한 바로 그 프레임에만 `true`를 유지하고, 다음 `Tick()` 시작 시 자동으로 `false`로 리셋해야 한다(`Input.GetButtonDown`과 동일한 "1프레임 에지" 의미론). 이걸 놓치면 `JumpState`가 이미 점프 중인데도 같은 의도가 계속 `true`로 남아 다음 착지 즉시 재점프를 시도하는 버그가 생길 수 있다.
- **BUG-P1-B1과의 순서 의존성**: 26-2 "경계에서 점프 시도(10%)"는 착지할 발판이 없을 경우 `Fall`로 빠지는데, 그 시점에 화면 하단 안전망(BUG-P1-B1 수정)이 아직 없으면 "점프했다가 허공으로 사라짐"처럼 보일 위험이 있다. BUG-P1-B1을 이 작업과 같은 반려 사이클에서 함께 처리할 것을 재확인 권고(Debugger 리포트의 권고 수정 순서와도 일치).

### 27-1. 윈도우 창 도둑

**목표**: 캐릭터가 창 테두리를 양손으로 붙잡고 밀거나 당기는 안간힘 연출로 코믹함을 주되, 실제 창은 1픽셀도 움직이지 않는다는 것 자체가 개그 포인트임을 명확히 한다.

**트리거**:
- 코어 루프 유휴 판정 주기마다 저확률 추첨(예: 2~4%), 최소 재발생 쿨다운(예: 15분) — 10/11절과 동일한 스펙터클 트리거 패턴 재사용.
- **대상 창 선정 기준**: 현재 열린 발판(창) 중 폭이 작은 창을 우선 선정(예: 캐릭터 신장 대비 폭 3배 이하). 큰 창(브라우저 전체화면급)을 대상으로 삼으면 "밀어도 안 움직임"이 당연해 보여 개그가 안 살고, 작은 창(계산기, 메모장, 알림 팝업류)일수록 "정말 밀리는 듯" 긴장감이 산다.
- 16절-15/24절 상호배제 세트(10/11/13/14/20절)에 편입 — 동시 발동 금지.

**유저가 보는 것**: 캐릭터가 창 테두리로 다가가 양손으로 붙잡고 부들부들 떨며 미는/당기는 애니메이션(힘줄·먼지 파티클) → 창은 그대로 → 한 번 더 세게 시도(2회차, 더 과장된 자세) → 결국 포기하고 주저앉아 헥헥거리는 코믹 리액션(확정된 실패 상태에서 파생된 대사, 원칙 1 준수) → 정상 종료.

**유저가 할 수 있는 액션**: 기본은 관전 전용(클릭관통 유지, 이 이벤트를 위한 부분적 클릭관통 해제 없음 — 11절 라이벌 대결과 같은 "관전 콘텐츠" 분류). 유저가 그 창을 실제로 조작(드래그 등)하면 아래 예외 상태로 즉시 전환.

**절대 원칙 3과의 공존(Coder/Test Engineer 필독)**: 이 기능의 연출은 100% 캐릭터 애니메이션 레이어(팔 IK, 흔들림, 파티클)와 화면 이펙트로만 구성된다. **`SetWindowPos`/`MoveWindow`류, 혹은 macOS의 창 프레임 변경 API를 호출하는 코드는 이 기능 구현 어디에도 존재해서는 안 된다.** "실패"가 아니라 애초에 "성공"이라는 결과 자체가 설계에 없다 — 성공 케이스(창이 실제로 밀림)를 만드는 순간 원칙 3 위반이므로, 2회 시도 후 포기하는 흐름 자체가 유일한 정답 경로다(1회면 성의 없어 보이고 3회 이상이면 루프가 지루함 — 2회 고정 권고).

**예외 상태**:
- 시도 도중 유저가 실제로 그 창을 옮기면(드래그) 캐릭터가 놀라며 손을 떼는 리액션으로 즉시 취소 — 캐릭터가 움직이는 실제 창을 "쫓아가려는" 시도를 하지 않는다(쫓아가면 "내가 방금 창을 움직였나?" 오해 유발 위험).
- 대상 창이 도중에 닫히면 허공을 잡던 자세에서 자연스럽게 물러나는 리액션(4절 "더 안전한 쪽 선택" 철학 재사용).
- 전체화면 게임 감지 시 즉시 취소(6-4절 우선).

**탈출구**: 트레이 긴급정지. 설정(7절 "모드" 탭)에 "창 도둑 놀이" 개별 토글 추가 권고.

**이 기능이 실제로 건드리면 안 되는 것**: 실제 창의 위치/크기(좌표를 쓰는 어떤 API 호출도 금지).

### 27-2. 바탕화면 청소부

**목표**: 아이콘을 발로 차서 정렬하는 것처럼 보이는 연출을 제공하되, 실제 아이콘 좌표/파일 위치는 절대 바뀌지 않는다. 이번 6개 기능 중 "보이는 것"과 "실제 상태"의 괴리가 가장 큰 항목이므로 구현 방식을 구체적으로 못박는다.

**트리거**: 유휴 저확률 추첨, 단 **데스크톱 아이콘이 실제로 화면에 보이는 상태일 때만**(모든 창이 최소화됐거나 바탕화면 보기 상태) 후보로 성립 — 다른 창이 덮고 있어 아이콘이 안 보이면 트리거 자체를 억제한다.

**구현 방식 제안 — "복제 스프라이트" 파이프라인**:
1. 이벤트 시작 시 현재 아이콘 영역을 1회 캡처(스크린샷 또는 아이콘 이미지+좌표 조회)해 "복제 스프라이트"를 만든다.
2. 그 캡처 이미지를 화면 최상단 오버레이 레이어에서 실제 아이콘과 정확히 같은 위치에 "얼려둔 배경"으로 한 번 덮고, 캐릭터가 발로 차는 방향에 맞춰 캡처본만 슬라이드/정렬 애니메이션으로 움직인다(실제 아이콘 좌표 조회는 오버레이가 어디를 덮을지 계산하는 **읽기 전용** 용도로만 쓰고, 그 좌표에 쓰기(재배치) API는 절대 호출하지 않는다).
3. 연출이 끝나면(정렬 완료 "짠" 포즈) 오버레이 전체(얼린 배경+움직인 복제본)를 페이드아웃하며 제거한다. 실제 아이콘은 처음부터 끝까지 그 자리 그대로였으므로, 오버레이가 걷히는 순간이 "어? 원래대로잖아" 하는 의도된 펀치라인이 된다 — 이는 버그가 아니라 이 기능의 정체(실제로는 아무것도 안 바뀌었다는 것 자체가 재미)이므로, 이 반전을 감추거나 사과하는 카피를 넣지 않는다.

**유저가 이 와중에 실제 아이콘을 더블클릭하면?(반드시 정상 동작, 원칙 2/3 직결)**: 오버레이는 처음부터 끝까지 100% 클릭관통이다(14절 "닫기 버튼 막기"/21절 "던전 파밍"과 동일한 역예외 취급 — 15절 부분적 클릭관통 해제를 이 오버레이에는 절대 적용하지 않는다). 클릭 판정은 항상 오버레이가 보여주는 시각적 위치가 아니라 **실제 아이콘의 실제 좌표** 기준이며, 더블클릭 즉시 정상적으로 앱이 실행되어야 한다. 추가로, 이벤트가 시작된 이후 그 아이콘 영역(원래 좌표+애니메이션 대상 좌표를 포함한 바운딩 박스) 안에서 마우스 활동이 감지되면(9절-3의 전역 커서 좌표 폴링을 읽기 전용으로 관찰), 오버레이는 클릭을 가로챈 게 아니라 스스로 판단해 그 즉시 전체를 제거하고 실제 아이콘을 노출한다 — 유저의 실제 조작 의도가 이 코미디 연출보다 항상 우선한다.

**유저가 할 수 있는 액션**: 관전 전용(연출 자체에 개입할 액션 없음). 단, 위처럼 실제 아이콘 클릭/더블클릭/드래그는 언제나 그대로 통과되어 정상 동작한다.

**예외 상태**:
- 더블클릭으로 새 창이 열려 데스크톱을 덮으면 오버레이를 조용히 페이드아웃하며 조기 종료(이벤트 취소는 필수는 아니나 화면이 이미 가려졌으므로 자연 종료).
- 유저가 이벤트 도중 실제로 아이콘을 드래그해 재배치하면 복제 스프라이트와 실제 좌표가 어긋나므로 재계산 없이 즉시 취소.
- 전체화면 게임 감지 시 즉시 취소.
- 27-5(블랙홀)와 상호배제(둘 다 "아이콘 대상 스펙터클" 카테고리).

**탈출구**: 트레이 긴급정지, 설정 개별 토글("바탕화면 청소부 놀이").

**이 기능이 실제로 건드리면 안 되는 것**: 실제 아이콘 좌표·파일 시스템 경로(재배치 API 호출 금지, 아이콘 좌표 조회는 읽기 전용만).

### 27-3. 화면 낙서(그라피티)

**목표**: 스프레이로 웃는 얼굴/졸라맨을 그리는 장난스러운 스펙터클을 제공하되, 다른 창을 침범하지 않고 데스크톱 배경화면 자체는 절대 바뀌지 않는다.

**트리거**: 유휴 저확률 추첨.

**캔버스 크기/위치 제약**:
- 그리기 전 현재 발판(창 사각형) 목록을 조회해, 그 사각형들과 겹치지 않는 화면상 빈 영역(바탕화면이 드러난 영역, 또는 화면 여백)만 그리기 대상으로 선정한다. **다른 창 위를 침범해서 그 위에 낙서가 겹쳐 보이면 안 된다** — 유저가 보고 있는 작업 창 위에 낙서가 그려지는 것은 침해감을 주는 연출이므로 금지.
- 겹치지 않는 빈 영역을 찾지 못하면(화면이 창들로 가득 참) 이벤트를 스킵하고 다음 유휴 판정 주기로 이연 — 억지로 창 위에 그리지 않는다.
- 캐릭터 근처 한정 반경(예: 200~300px) 안에만 그려 화면 전체를 뒤덮지 않는다.

**유저가 보는 것**: 캐릭터가 스프레이 캔을 들고 몇 번 뿌리는 확정 애니메이션 → 웃는 얼굴/졸라맨 그림 완성 → 3~5초 유지 → 옅어지며 사라지는 페이드아웃(0.5~1초, 또는 위→아래 와이프 지움 효과).

**유저가 할 수 있는 액션**: 관전 전용(클릭관통 유지, 부분적 클릭관통 해제 대상 아님 — 그림 자체가 클릭 가능한 UI가 아니므로 15절 적용 자체가 무관함).

**데스크톱 배경화면 자체를 실제로 변경하지 않음(명시)**: 그라피티는 **OS 배경화면 이미지 파일이나 배경화면 설정 API(`SystemParametersInfo`/macOS 배경 설정 API 등)를 전혀 호출하지 않으며, 화면 위에 얹는 순수 오버레이 레이어일 뿐**이다 — 21절(던전 파밍의 "문" 오버레이), 27-2(청소부의 복제 스프라이트)와 동일한 "실제 OS 상태와 완전히 분리된 렌더 레이어" 패턴의 세 번째 사례.

**예외 상태**:
- 그려지는 도중 그 빈 영역에 새 창이 열려 겹치게 되면 즉시 페이드아웃 취소.
- 멀티모니터: 캐릭터가 서 있는 모니터의 빈 영역만 대상, 모니터를 넘나들며 그리지 않음.
- 전체화면 게임 감지 시 즉시 취소.

**탈출구**: 방해성이 낮아(클릭관통 유지, 자동 소멸) 긴급정지 필요성은 낮지만 트레이 긴급정지는 항상 유효한 전역 안전판으로 남는다. 설정 개별 토글 제공.

**이 기능이 실제로 건드리면 안 되는 것**: OS 배경화면 이미지 파일·배경화면 설정(어떤 배경화면 변경 API도 호출 금지).

### 27-4. 윈도우 크래시

**목표**: 해머로 활성 창을 내리쳐 유리가 깨지는 파괴 이펙트를 잠깐 보여주되, 대상 창의 실제 내용/상태/입력 수신은 전혀 방해받지 않고 3초 뒤 오버레이만 사라진다(원본이 처음부터 안 바뀌었으므로 "복구"가 아니라 오버레이 제거).

**트리거 조건 — 기획 원문 재검토(중요)**:
- 기획 원문은 "유저가 키보드를 너무 빨리 치거나 에러 창이 뜨면"을 트리거로 제안하나, **이번 설계에서는 두 조건 다 채택하지 않는다.**
  - "에러 창이 뜨면" 감지는 다른 창의 제목/내용을 분석해 유저의 작업 상황(에러 발생)에 개입하는 것이라 원칙 3(read-only)의 취지와 충돌 소지가 있고, 하필 유저가 짜증나 있을 실제 에러 상황에 파괴 연출을 얹는 것은 "재미"가 아니라 "방해"로 받아들여질 위험이 크다.
  - "키보드를 너무 빨리 치면" 감지는 전역 키 입력 후킹이 필요한데, 이는 26-5절에서 이미 **완전 폐기하기로 확정한** 키보드 입력 경로를 이 기능 하나를 위해 되살리는 것이라 그 결정과 정면으로 모순된다.
- **대안**: 10/11/27-1과 동일한 **유휴 판정 저확률 추첨**으로 대체한다. 원문의 "화났을 때 등장"이라는 절묘한 타이밍감은 포기하지만, 원칙 3/비침해 원칙 준수가 우선이며 저빈도 랜덤이어도 "예측불가 장난"이라는 재미 요소는 동일하게 유지된다. (원문 트리거를 살리고 싶다면 "창 제목의 특정 키워드"까지만 저빈도 참고 필터로 쓰는 절충안을 Architect가 별도 논의할 수 있으나, 이번 라운드에서는 채택하지 않는다.)
- **쿨다운/빈도 제한(필수, 과도한 발동은 방해가 된다는 우려 반영)**: 파괴 연출은 시각적 충격이 크므로 다른 스펙터클보다 더 희소해야 한다 — 최소 재발생 간격 20~30분, 발동 확률 1~3%(27-1 창 도둑보다도 낮게).

**대상 창 선정**: 현재 포그라운드(활성) 창 — 전체화면 게임 감지용으로 이미 조회 중인 정보를 재사용(신규 폴링 불필요).

**크랙 이펙트가 실제 창 내용물을 가리는 정도(명시적으로 못박음)**: 금이 간 유리 텍스처가 활성 창 위에 시각적으로 겹쳐 보이는 것은 불가피하지만, **이 크랙 레이어는 예외 없이 100% 클릭관통(마우스 이벤트 완전 투과)되는 순수 시각 레이어여야 한다.** 3초 동안 활성 창의 실제 클릭/타이핑/스크롤이 조금이라도 막히면 그 자체로 원칙 2(비침해) 위반이다 — "보기엔 깨진 유리, 만지면 평범한 창"이 유일하게 허용되는 구현이다. 이는 14절/21절/27-2와 동일한 역예외 계열이며(이 문서에서 벌써 네 번째 반복), Coder는 "시각 전용 오버레이는 항상 클릭관통, 유일한 예외는 캐릭터 몸 히트박스(10/12/13/14절)뿐"이라는 단일 규칙으로 통합 구현할 것을 권고한다.

**유저가 할 수 있는 액션**: 관전 전용. 크랙이 떠 있는 3초 동안에도 대상 창은 완전히 정상 조작 가능해야 한다(위 문단이 곧 액션 명세).

**3초 후 원복 연출**: 크랙이 유리 조각처럼 파편화되어 부서져 떨어지는 페이드아웃(0.3~0.5초) → 창은 처음부터 멀쩡했으므로 "복구"라기보다 오버레이가 걷혀 원래 모습이 다시 드러나는 것.

**예외 상태**:
- 크랙이 떠 있는 도중 대상 창이 최소화/닫히면 즉시 오버레이 제거.
- 전체화면 게임 감지 시 즉시 취소.
- 16절-15/24절 상호배제 세트에 편입(다른 스펙터클과 동시 발동 금지).

**탈출구**: 트레이 긴급정지(즉시 크랙 제거), 설정 개별 토글("윈도우 크래시 놀이").

**이 기능이 실제로 건드리면 안 되는 것**: 대상 창의 실제 콘텐츠·실제 입력 수신(크랙 레이어가 클릭/키입력을 가로채는 것 금지).

### 27-5. 블랙홀 소환

**목표**: 아이콘이 빨려들어가다 튕겨나가는 코믹 물리 스펙터클. 27-2 청소부와 완전히 동일한 "실제 아이콘 위치 불변" 원칙을 재확인하고 구현 파이프라인도 그대로 재사용한다.

**발동 조건/빈도**: 27-2와 동일한 트리거 계열(유휴 저확률 추첨, 데스크톱 아이콘이 실제로 보일 때만). 청소부와 블랙홀은 같은 "아이콘 대상 스펙터클" 카테고리이므로 **서로 상호배제**한다(동시에 청소부가 아이콘을 정렬 중인데 블랙홀이 빨아들이면 두 연출이 물리적으로 모순됨).

**유저가 보는 것**: 캐릭터 손바닥에 작은 블랙홀 소환 → 근처 복제 아이콘 스프라이트들이 소용돌이치듯 빨려들어가는 궤적 → 블랙홀 소멸과 함께 아이콘들이 원래 자리로 통통 튕겨나와 복귀(만화적 탄성 물리, 원래 좌표를 살짝 오버슈트했다가 안착).

**유저가 할 수 있는 액션**: 관전 전용. 아래처럼 실제 아이콘 클릭은 언제나 정상 동작.

**27-2와 동일한 원칙 재확인 — 파이프라인 재사용**: 이 연출도 100% 복제 스프라이트 기반이다. 실제 아이콘 좌표/파일은 처음부터 끝까지 손 하나 대지 않으며, "빨려들어가는" 것도 "튕겨나가는" 것도 전부 27-2에서 정의한 복제본이다(실제 아이콘은 애초에 이동한 적이 없으므로 "복귀"라는 표현조차 사실은 오버레이 제거일 뿐). Coder는 27-2의 "캡처 → 오버레이 애니메이션 → 페이드아웃/제거" 파이프라인을 그대로 재사용하고 이 기능만을 위한 별도 캡처/스프라이트 로직을 새로 만들지 않을 것을 권고한다.

**마우스 클릭 관통 유지 여부**: 27-2와 동일하게 100% 클릭관통이며, 클릭 판정은 항상 실제 아이콘의 실제 좌표 기준이다. 블랙홀에 "빨려들어가 안 보이는" 순간에 그 실제 좌표를 더블클릭해도 정상 실행되어야 한다 — 시각적으로 없어 보이는데 클릭이 되는 게 다소 신기하게 느껴질 수 있으나, 이는 "아, 어차피 진짜로 없어진 게 아니었구나"를 확인시켜주는 오히려 신뢰를 강화하는 부작용이므로 굳이 이 틈을 메우려 애쓰지 않는다. 27-2와 동일하게, 그 영역에서 실제 마우스 활동이 감지되면 오버레이는 스스로 즉시 취소한다.

**예외 상태**:
- 유저가 연출 도중 실제 아이콘을 드래그해 재배치하면 즉시 취소(27-2와 동일).

**탈출구**: 트레이 긴급정지, 설정 개별 토글("블랙홀 소환 놀이").

### 27-6. PC 하드웨어 반응 — 신호별 폴링 주기 확정 (23절 확장)

23절 "PC 하드웨어 반응 UX"가 이미 목표/공통원칙 4가지/반응별 톤(CPU·배터리·충전·네트워크)을 정의해두었다. `docs/ARCHITECTURE.md` Phase 4 정의("OS 장난, PC 하드웨어 연동")와 `Tasklist.md` Phase 4 표의 "CPU/배터리/네트워크 반응" 행이 이 항목의 정식 소속임을 재확인한다(문서 헤더상 17~25절이 "Phase 5 선행 설계"로 표기되어 있으나, 23절 내용 자체는 Phase 4 항목의 선행 설계로 취급할 것을 권고 — 내용 수정 불필요, 소속 재확인만). 이번 라운드는 23절이 다루지 않은 **신호별 구체적 폴링 주기**만 신규로 확정한다.

| 신호 | 감지 방식 | 권장 폴링 주기 | 근거 |
|---|---|---|---|
| 배터리 잔량(20% 이하) | OS 배터리 API(퍼센트+충전여부 조회) | 60~120초 | 물리적으로 급변하지 않는 값 — 저빈도로 충분한 대표 사례. |
| 충전 중 여부 | OS 배터리 API의 충전상태 플래그 | 가능하면 OS 이벤트 구독(플러그 삽입/제거 콜백), 폴링은 이벤트 API가 없을 때만의 차선책(30초) | 이벤트 기반 API가 있는 플랫폼에서는 폴링 자체가 불필요. |
| CPU 사용률(80%+) | OS 프로세스/시스템 사용률 조회 | 5~10초 | 배터리·충전보다 변동이 빠름(짧은 스파이크가 흔함). 단, 23절 공통원칙 1의 "30초~1분 지속 조건"과 결합되므로 폴링 주기 ≠ 판정 주기 — 5~10초로 값을 갱신하되 30~60초 누적 관찰 후에만 트리거 확정. |
| 네트워크 연결 끊김 | 네트워크 인터페이스/연결성 조회 | 15~30초 | 순간적 끊김(Wi-Fi 로밍 등)에 즉각 반응하면 오탐이 잦다 — CPU보다 느슨하되 배터리보다는 촘촘하게. |

**공통 스케줄러**: 위 4개 신호는 각각 독립된 `Update()` 폴링 루프를 만들지 않고, 23절 공통원칙 4가 이미 요청한 "발판 폴링과 동일한 저빈도 폴링 관리 패턴"(`FootholdPoller`류) 아래 각기 다른 간격으로 등록되는 **하나의 공용 스케줄러**로 구현할 것을 권고한다.

**알림 피로도 방지(23절 공통원칙 1·2 재확인 + 보강)**: 지속조건(30초~1분)과 재발생 쿨다운(5~10분)에 더해, **같은 반응은 "정상 범위로 회복 확인" 없이 재알림되지 않는다** — 예: 배터리 20% 이하 반응이 한 번 나온 뒤, 배터리가 임계값 이상으로 회복했다가 다시 떨어지는 경우에만 재알림하고, 계속 20% 이하에 머물러 있는 동안은 쿨다운 경과 여부와 무관하게 재알림하지 않는다(23절 "회복 전까지 조용한 idle 자세만 유지" 원칙의 폴링 설계 차원 재확인).

**개별 on/off**: 23절 공통원칙 3에서 이미 확정(4개 반응 각각 독립 토글, 설정창 7절) — 이번 라운드 변경 없음.

**예외 상태 / 탈출구**: 23절과 동일(전체화면 게임 감지 시 전체 숨김, 동시 충족 시 배터리>CPU>네트워크>충전 우선순위 1개만 표현, 설정 개별 토글이 실질적 탈출구).

**이 기능이 실제로 건드리면 안 되는 것**: OS 설정 값 자체(배터리 절전모드 강제 전환, 네트워크 재연결 시도, 프로세스 종료 등 어떤 시스템 제어(쓰기) API도 호출하지 않음 — 4개 신호 모두 조회(read)만 수행).

## 29. 랙돌 피격/착지 연출 (Active Ragdoll 강제 전이 — Phase 2)

이 절은 4절(파쿠르)과 같은 층위의 "물리 반응형 이벤트" 연출 설계다. RAGDOLL/GETUP 전이 자체의 조건(임계값/판정 타이머)은 이미 `docs/ARCHITECTURE.md` 0절과 `RagdollState.cs`/`GetupState.cs`에 정의돼 있다(`StickConfig.ragdollForceThreshold`/`ragdollSettleSpeedThreshold`/`ragdollSettleHoldDuration`). 이 절은 그 전이가 일어나는 "순간"과 "그 이후 몇 초"를 유저가 어떻게 체감해야 하는지만 다룬다.

**목표**: 피격/투척/추락 충격으로 RAGDOLL에 강제 진입하는 순간이 "타격감 있는 만화적 한 컷"으로 읽히게 하고, 널브러진 채 누워있는 시간이 코믹함(가벼운 개그)과 무게감(진짜 맞은 느낌) 사이 어느 한쪽으로 치우치지 않게 한다. RAGDOLL~GETUP 전 구간에 유저 개입은 없다(재확인, 29-4).

### 29-1. 피격 임팩트 이펙트 — "펑!" 하는 폭발선

기획 원문의 "펑! 하는 폭발선"을 3단 콤보로 구체화한다. 전부 `RagdollState.Enter(context)` 호출과 같은 프레임에 트리거되어야 하며(5절 "확정 후에만" 원칙과 동일), 순서가 뒤바뀌면 안 된다.

| 단계 | 시작 시점 | 유저가 보는 것 | 권장 지속시간 |
|---|---|---|---|
| ① 히트스톱 | RAGDOLL Enter와 동일 프레임 | 전체(또는 캐릭터 로컬) 타임스케일이 순간적으로 0에 가깝게 떨어져 한 프레임 "정지 화면"처럼 보임 — 타격의 무게감을 만드는 값싼 트릭 | 40~80ms |
| ② 흑백 플래시 | ①과 동시 | 캐릭터 주변 국소 영역(또는 화면 전체)이 컬러→그레이스케일+약한 과다노출로 전환됐다가 컬러로 복귀 | 80~120ms (①과 겹쳐 진행, 총 체감시간을 늘리지 않음) |
| ③ 임팩트 버스트(폭발선) | ①·② 종료 직후 | 타격 지점 중심 방사형 만화 선 8~12갈래(굵은 흑선, `primaryOutlineColor` 재사용 권장) — 파티클/스프라이트 어느 구현이든 무방 | 페이드아웃 200~300ms |
| ④ 랙돌 낙하 시작 | ③ 렌더 직후 | 타임스케일 정상 복귀, 이 시점부터 전신 물리 시뮬레이션(모터 해제)이 실제로 시작 | 물리 시뮬레이션에 위임 |

**과장 정도(코믹 vs 리얼) 밸런스**: 이펙트(①~③)는 과장해도 좋다 — 액션 만화의 문법이고, 클릭관통 관찰형 앱에서 "어, 방금 뭔가 세게 맞았다"를 0.3초 안에 각인시키는 게 목적이라 절제할 이유가 없다. 반대로 ④ 이후의 실제 물리(관절이 꺾이는 각도, 튕겨나가는 궤적)는 **과장하지 않는다** — Rigidbody2D/Joint2D 시뮬레이션 값 그대로 재생하고, 관절 각도 제한(Joint2D limit)은 "부러진 것처럼 안 보이는" 해부학적 최소 안전값으로만 세팅한다. 즉 **이펙트 레이어는 만화적으로 과장, 물리 레이어는 정직하게 리얼** — 이렇게 분리하는 것이 코믹함과 무게감을 동시에 잡는 방법이다(한쪽을 과장하면 다른 쪽까지 과장하고 싶어지는 함정을 경계할 것).

### 29-2. 바닥에 누워있는 시간 — "너무 빠르면 가벼움, 너무 길면 답답함"

`ragdollSettleHoldDuration`(현재 0.5초)은 "속도가 임계값 이하로 유지되어야 하는 시간"이지 "바닥에 누워있는 총 시간"이 아니다 — 실제 낙하~기상 총 시간은 충격 크기에 따라 물리적으로 들쭉날쭉하다(가볍게 스친 경우 물리가 우연히 빨리 안정될 수 있음). 이 자체가 문제다: 약하게 맞았는데 물리가 우연히 빨리 정지하면 "타격감 없이 통통 튕기고 바로 일어나는" 가벼운 인상을 준다.

**해결 방향**: RAGDOLL 진입 후 경과한 총 시간에 최소 하한선을 두어, 물리가 그보다 먼저 안정되어도 강제로 더 누워있게 한다(`RagdollState.Tick()`의 Getup 전이 조건에 `AND 경과시간 >= 최소값`을 추가). 이 최소값은 충격 크기에 비례해 구간화한다(임계값 하나로 뭉뚱그리지 않음) — 세게 맞을수록 더 오래 누워있어야 인과가 유지된다.

| 충격 크기 (`ragdollForceThreshold` 대비 배율) | 예시 상황 | 권장 최소 누워있는 시간 | 근거 |
|---|---|---|---|
| 1.0~2.0배 (약한 피격) | 스치듯 부딪힘 | 0.6~0.9초 | 이보다 짧으면 물리가 즉시 안정돼도 "맞자마자 바로 일어남"으로 읽혀 타격감이 증발함 |
| 2.0~4.0배 (중간 피격) | 정면으로 얻어맞음 | 1.0~1.5초 | 이 프로젝트의 기본 코미디 톤에서 "아야, 잠깐 누워있다 일어남"이 가장 자연스러운 체감 구간 |
| 4.0배 초과 (강한 충격 — 던져짐/높은 곳 추락) | 창문 밖으로 던져짐, 파쿠르 실패 추락 | 1.5~2.2초 (상한 존재) | 상한이 없으면 "언제까지 누워있나" 답답함이 발생 — 상한을 넘겨서까지 늘어지게 두지 않는다 |

상한(2.2초)은 반드시 둘 것 — 이 프로젝트의 톤 자체가 "빠른 회복 개그"이지 리얼리즘 시뮬레이터가 아니므로, 실제 물리 안정과 무관하게 상한에 도달하면 잔여 물리 흔들림을 무시하고 Getup으로 강제 전이해도 무방하다(비정상이 아니라 의도된 컷).

**Coder 구현 제안**: `StickConfig`에 `ragdollMinFloorDurationLow`/`Mid`/`High`(위 3구간 값)와 `ragdollMaxFloorDuration`(상한, 예: 2.2초) 필드를 신설. `RagdollState.Enter()`가 진입 시점 충격 크기를 스냅샷해 구간을 확정하고, `Tick()`의 Getup 전이 조건을 `(속도 안정 hold 완료 AND 경과시간 >= 구간별 최소값) OR 경과시간 >= 상한`으로 변경.

### 29-3. GETUP 단계 분해 — 널브러짐 → 꿈틀 → 일어남

`GetupState`는 현재 `_getupProgress`(0~1) 하나로만 스텁돼 있다. 아래 3단계로 나누어 "생명체가 정신을 차리는 과정"처럼 읽히게 할 것을 제안한다.

```
Getup 진입(0%)
  │
  ├─ ① 정지 유지(Dead Pause)      : 완전히 미동 없음 — 유저 시선이 "어, 괜찮나?" 하고 머무는 구간
  │     권장 0.15~0.3초
  │
  ├─ ② 꿈틀거림(Stir)             : 손가락/머리 등 일부 관절만 작은 폭으로 씰룩(전신 기상 아님)
  │     권장 0.3~0.5초
  │
  └─ ③ 기상(Rise)                 : 널브러진 포즈 → 직립 목표 포즈로 IK 크로스페이드(4절 "급격한 포즈
        권장 0.4~0.6초              점프 금지" 원칙 재적용) — 이 블렌드가 끝나는 순간 Idle Enter
```

총 GETUP 소요시간 권장 0.85~1.4초(위 세 구간 합). 29-2의 "누워있는 시간"과는 별개 구간이다(29-2는 RAGDOLL 상태 자체 지속시간, 이 표는 그 다음 GETUP 상태 지속시간) — 둘을 합친 "쓰러짐~완전 복귀" 총 체감시간은 대략 1.5~3.6초 범위 안에 들어와야 한다.

**Coder 구현 제안**: `StickConfig`에 `getupStirDelay`/`getupStirDuration`/`getupRiseDuration` 3필드 신설, `GetupState`가 `_getupProgress` 단일 값 대신 이 3단계 타이머로 진행 단계를 판정(꿈틀 단계에서는 몸통 IK 미적용, 기상 단계에서만 IK 블렌드 시작).

### 29-4. 유저 개입 여지 — 없음 (재확인)

RAGDOLL 진입부터 GETUP 완료까지 전 구간은 26절 자율 배회 AI와 동일한 "지켜보기 전용" 콘텐츠다. 클릭으로 기상을 앞당기거나, 누워있는 자세를 조작하거나, 임팩트 이펙트를 스킵하는 등 어떤 형태의 유저 입력도 이 구간에 개입하지 않는다 — 이는 인질극/로데오 커서 같은 "방해성 이벤트"(6-5절)가 아니라 순수 관찰 콘텐츠이므로 긴급 정지 버튼 같은 탈출구 설계도 필요 없다(방해성이 없으니 탈출할 대상 자체가 없음). 단, GETUP 도중 새 외력이 다시 `ragdollForceThreshold`를 넘으면 RAGDOLL로 재인터럽트되는 것은 유저 "입력"이 아니라 환경 물리 이벤트이므로 이 원칙과 무관하다(`GetupState.cs` 주석에 이미 명시된 대로 — 이때 GETUP이 만든 `DialogueIntent`는 5절 계약대로 즉시 만료).

**예외 상태**: 해당 없음(로딩/에러 개념이 존재하지 않는 순수 물리 반응 구간).
**탈출구**: 해당 없음(비침해적 관찰 콘텐츠, 4절과 동일 판단).

## 30. 파쿠르 시각 피드백 보강 (Phase 2 — 4절 이어서)

4절이 CLIMB/HANG/ROLL 3동작의 기본 시각 피드백 표를 이미 확정했다. 이번 절은 Phase 2 착수 시 구체적으로 결정이 필요한 3가지 질문에 답한다.

### 30-1. "붙잡을 수 있음"을 미리 알려주는 신호 — 없음(의도적으로)

**결론: 벽 근접 예고 UI(아이콘/글로우/하이라이트 등)를 넣지 않는다.** 이유는 단순하다 — 26절에서 이미 확정했듯 이 캐릭터는 유저가 조준해서 벽을 잡는 게 아니라 `AutoWanderController`가 `parkourDetectionRadius` 이내 근접을 스스로 판정해 CLIMB에 진입하는 **완전 자율 행동**이다. "여기 잡을 수 있어요"라는 신호는 원래 유저가 그 정보를 보고 판단(잡을지 말지, 어디를 잡을지)해야 의미가 있는데, 이 앱에는 그 판단의 주체가 없다 — 신호를 넣어도 아무도 그것에 반응해 의사결정을 하지 않으니 순수 장식이 되고, 이는 기획 원문의 "담백한 액션 만화 느낌"과 정면으로 어긋난다(불필요한 게임 UI가 관찰형 캐릭터 위에 얹히는 인상).

대신 "예고"는 **UI가 아니라 캐릭터 자신의 몸짓(diegetic)**으로 처리한다: 손을 뻗어 벽을 짚는 IK가 스냅되기 2~3프레임 전부터 팔을 뻗는 예비 동작(reach anticipation)을 살짝 앞서 재생해, 손이 순간이동처럼 벽에 딱 붙는 게 아니라 "뻗다가 닿는" 것처럼 보이게 한다 — 이는 4절이 이미 요구한 "급격한 포즈 점프 금지" 원칙의 CLIMB 진입 시점 적용일 뿐, 신규 UI 요소가 아니다.

### 30-2. 벽타기 중 "지친 느낌" — 스태미나 게이지 없음, 순수 연출로만 처리

**결론: Phase 2 스코프에서 무한 매달리기를 허용해도 되는가 — 사실상 이미 허용되지 않는다.** HANG에는 이미 4절 표에 타임아웃이 명시돼 있다("일정 시간 초과 시 자동으로 위로 올라가거나 힘 빠짐 연출로 FALL 전이 — 무한 대기 금지"). 즉 "무한 매달리기 금지"는 이미 달성된 목표이므로, 이를 위해 새로 스태미나 수치를 도입할 이유가 없다.

스태미나 게이지(숫자로 관리되는 자원)를 새로 만들지 않는 이유: (1) 이 캐릭터에는 자원을 소모할 "행동 선택권"을 가진 유저가 없다(26절 자율 배회와 동일 논리 — 계기판을 볼 사람이 없음), (2) HANG 타임아웃 하나로 이미 목적을 달성하는데 별도 수치 시스템을 얹으면 관리 포인트만 늘어난다.

대신 "지친 느낌"은 4절에 이미 정의된 파라미터 하나를 재활용해 순수 연출로만 표현한다 — HANG의 "미세한 흔들림(Perlin 노이즈)" 진폭을, 타임아웃 잔여시간 비율에 반비례해 점점 키운다.

| 경과 비율(타임아웃 대비) | 손 떨림 진폭 | 유저가 받는 인상 |
|---|---|---|
| 0~70% | 기본값 그대로 | 편안하게 매달려 있음 |
| 70~90% | 기본값의 1.5~2배 | 슬슬 버거워 보임 |
| 90~100% | 기본값의 2.5~3배 + 손가락 미끄러짐 마이크로 모션 | 곧 놓칠 것 같은 긴장감 — 타임아웃 종료 시 FALL 전이가 "갑자기"가 아니라 "예견된 것"으로 읽힘 |

새 수치 시스템이 아니라 기존 노이즈 진폭 값에 곱하는 커브 하나만 추가하는 것이므로 구현 비용이 저렴하다.

### 30-3. 낙하 구르기(ROLL) 착지 — 항상 성공, 실패 조건 없음(구조적으로 보장됨)

**결론: 기획 원문("덤블링하여 부드럽게 착지")대로 ROLL에는 실패 상태가 없다 — 그리고 이는 새 규칙을 만들 필요 없이 기존 아키텍처가 이미 보장한다.** 근거: RAGDOLL 강제 전이 조건은 상태와 무관하게 "외력이 `ragdollForceThreshold`를 넘으면 즉시 전이"다(0절, 전 상태 공통). 즉 낙하 충격이 그 임계값을 넘을 만큼 강하면 애초에 ROLL을 시도할 기회 자체가 없다 — 그 낙하는 정의상 이미 RAGDOLL로 처리된다. ROLL은 오직 "임계값 미만의, 캐릭터가 감당 가능한 낙하"에서만 진입하는 상태이므로, ROLL이 실제로 실행되는 모든 경우는 이미 "성공 가능한 낙하"라는 필터를 통과한 뒤다 — ROLL 자신이 별도로 성공/실패를 판정할 필요가 없다.

4절 표가 이미 정의한 유일한 예외("착지면이 너무 좁아 구를 공간 없음 → 축소된 제자리 휘청임 애니메이션으로 대체")도 **실패가 아니라 애니메이션 변형 선택**이다 — 두 경우(정식 구르기 vs 축소된 휘청임) 모두 "성공적으로 착지해 다음 상태로 이어짐"이라는 결과는 동일하고, 차이는 순전히 시각적 스케일뿐이다. 즉 ROLL에는 애초부터 "실패"라는 결과 카테고리 자체가 존재하지 않는다 — 있는 것은 "정식 구르기"와 "약식 구르기"라는 두 가지 성공 변형뿐이다.

**경계 처리(그레이존)**: 낙하 충격이 `ragdollForceThreshold`에 아주 근접한 경우(예: 임계값의 99~101%) 판정이 프레임 단위로 오락가락(RAGDOLL이었다가 ROLL이었다가)하면 안 된다. 4절 예외 상태가 이미 세운 원칙("애매하면 더 안전한 쪽을 선택")을 그대로 재적용한다 — 임계값 근처 그레이존에서는 ROLL(더 가벼운 결과) 쪽으로 편향시킨다(예: ROLL 허용 상한을 `ragdollForceThreshold` 자체가 아니라 그보다 살짝 높은 `ragdollForceThreshold * 1.05` 정도로 잡아, "세게 떨어졌지만 구를 수는 있었다"가 "간발의 차로 나가떨어졌다"보다 더 자주 선택되게 함). 유저 입장에서 "방금 떨어진 높이가 구르기로 처리될지 랙돌로 처리될지"를 예측할 이유가 없으므로, 이 여유는 안전 방향으로만 주면 된다.

**예외 상태 / 탈출구**: 4절과 동일(로딩 개념 없음, 비침해적 관찰 콘텐츠).

## 31. `DialogueIntent` 파라미터 카피 원칙 — "한 발 더" / "오늘은 여기까지" 실전 예시 (Phase 2, 최우선)

이 절은 `docs/BUG_REPORT_PHASE0.md` BUG-M7(`DialogueIntent`의 `Func<StickmanStateId, string>` 시그니처가 상태 파라미터를 못 실어 나름)에 대한 UX 요구사항이자, 기획서 0번 항목("한 발 더"라고 말만 하고 안 쏨)을 구조적으로 재현 불가능하게 만드는 카피 설계 원칙이다. 5절이 "상태 전이가 확정된 프레임에만 생성"이라는 **타이밍** 계약을 정의했다면, 이 절은 그 위에 "파라미터 값에 따라 달라지는 텍스트"의 **분기** 계약을 추가한다.

### 31-1. 핵심 원칙

> **같은 매핑 함수, 같은 파라미터 스냅샷, 그 안에서의 조건 분기만 허용한다.** "한 발 더!"와 "오늘은 여기까지"는 서로 다른 시점에 독립적으로 트리거되는 두 개의 별개 대사가 아니다 — 정확히 같은 `Enter(Attack)` 호출 한 번이 만든 `shotsRemaining`이라는 파라미터 값 하나를, 하나의 텍스트 매핑 함수가 조건문(`if/else` 또는 `switch`)으로 갈라 만들어낸 **한 함수의 두 출력**이어야 한다.

**이 원칙이 정확히 막는 버그 패턴(금지 사례)**:
- 금지 ①: `AttackState.Enter()`가 장전 여부를 확인하기 전에 낙관적으로 "한 발 더!"를 먼저 만들고, 그 다음 별도 로직이 뒤늦게 "사실 탄약이 없었다"를 발견해 조용히 사격을 취소하는 경로 — 대사와 실제 발사 여부가 서로 다른 코드 경로에서 각자 결정된다.
- 금지 ②: "오늘은 여기까지"라는 문구가 `AttackState` 바깥의 별도 타이머나 이벤트 구독으로 "탄약이 0이 된 걸 감지하면" 사후에 끼어드는 방식(원래 텍스트를 덮어쓰거나 뒤이어 추가로 띄우는 방식) — 두 대사가 서로 다른 트리거 소스를 가지면 그 사이에 프레임 간극이나 순서 역전이 생길 여지가 구조적으로 존재한다.
- 공통점: 두 금지 사례 모두 "텍스트가 무엇을 근거로 나왔는지"를 역추적했을 때 **하나의 `Enter()` 호출, 하나의 파라미터 스냅샷으로 귀결되지 않는다** — 5절이 이미 "상태(enum+params) → 텍스트 매핑 테이블 단방향"이라 명시한 것을 파라미터가 있는 대사에도 문자 그대로 적용한 것뿐이다.

### 31-2. 상태-파라미터-텍스트 매핑 표 (Coder `IHasDialogueParams` 파이프라인용 실전 예시)

아래 표는 Coder가 BUG-M7 수정안(상태가 파라미터 구조체를 노출하고, 텍스트 매핑 함수가 이를 받는 형태로 `DialogueIntent` 시그니처를 확장하는 안)을 구현할 때, 그 파이프라인에 그대로 꽂아 검증용 픽스처로 쓸 수 있도록 실제 값 단위로 작성했다. 모든 행에서 "파라미터 스냅샷 시점"은 예외 없이 해당 상태의 `Enter(context)` 호출 시점이다.

| # | 상태(State) | 노출 파라미터 (예시 필드) | 스냅샷 시점 | 분기 조건 | 파생 텍스트 | 비고 |
|---|---|---|---|---|---|---|
| 1 | `Attack` | `shotsRemaining: int` | `Enter(Attack)` | `shotsRemaining >= 1` | **"한 발 더!"** | 기획서 0번 항목의 원 사례. 이 분기와 아래 분기는 반드시 같은 함수 안의 if/else. |
| | | | | `shotsRemaining == 0` | **"오늘은 여기까지"** | |
| 2 | `Ragdoll` | `impactMagnitude: float`(`ragdollForceThreshold` 대비 배율) | `Enter(Ragdoll)` | `impactMagnitude < 2.0` | **"윽...!"** | 29-2 충격 구간표와 동일한 3구간 재사용 — 이펙트 강도와 대사 강도가 항상 같은 파라미터에서 파생되므로 서로 어긋날 수 없음. |
| | | | | `2.0 ≤ impactMagnitude < 4.0` | **"으악!"** | |
| | | | | `impactMagnitude ≥ 4.0` | **"으아아아악?!"** | |
| 3 | `Getup` | `reimpactCount: int`(직전 GETUP 시도가 재피격으로 몇 번 취소됐는지 누적) | `Enter(Getup)` | `reimpactCount == 0` | **"으쌰..."** | 처음 일어나는 시도. |
| | | | | `reimpactCount ≥ 1` | **"…또야?"** | 일어나려다 다시 얻어맞고 재진입한 경우 — 이 카운터도 `Enter()` 시점에 한 번만 읽는 스냅샷이며, Tick 도중 증가한 값을 나중에 다시 읽지 않는다. |
| 4 | `ParkourClimb` | `climbHeightUnits: float`(오를 거리) | `Enter(ParkourClimb)` | `climbHeightUnits < 2.0` | **"가뿐하네"** | |
| | | | | `climbHeightUnits ≥ 2.0` | **"헉... 높다"** | |
| 5 | (Phase 3 선행 참고) 격파 미니게임 `Charge` | `chargeRatio: float`(0~1, 릴리즈 확정 순간 값) | 릴리즈 확정(=상태 전이 확정) 순간 | `chargeRatio ≥ 0.9` | **"필살기다!"** | Phase 3에도 동일 원칙이 그대로 적용됨을 보여주는 선행 예시 — 지금 구현 대상은 아님. |
| | | | | `chargeRatio < 0.9` | **"어... 어라?"** | |

**표를 읽는 법**: 각 번호(#) 안의 여러 행(분기)은 **하나의 텍스트 매핑 함수**를 표현한다 — 절대로 "이 조건일 때 이 함수, 저 조건일 때 저 함수"처럼 두 개의 별도 함수/이벤트로 나누어 구현하면 안 된다. 파라미터 값 하나가 함수 안으로 들어가서 텍스트 하나가 나오는, 순수 함수(pure function)에 가까운 형태를 유지하는 것이 이 원칙의 구현 목표다.

### 31-3. 일반 체크리스트 (모든 미래 대사 — 격파 미니게임/인질극 등 — 회귀 테스트 기준선)

> **하나의 텍스트를 골랐다면, 그 텍스트가 파생된 파라미터 값이 정확히 어느 한 번의 `Enter()` 호출·어느 한 번의 파라미터 스냅샷에서 나왔는지 역추적할 수 있어야 한다. 조건에 따라 달라지는 대사가 여러 개 존재한다면 그것들은 반드시 같은 매핑 함수 안의 분기여야 하며, 서로 다른 시점·다른 이벤트 소스에서 독립적으로 트리거되는 대사 쌍이 하나라도 발견되면 그 즉시 회귀 실패로 처리한다.**

Test Engineer는 Phase 2 "텍스트-액션 싱크 회귀 테스트"(Tasklist Phase 2 표) 작성 시 이 한 줄을 그대로 테스트 케이스 설계 기준으로 사용할 것 — 31-2 표의 5개 예시 각각에 대해 "파라미터를 경계값 양쪽으로 바꿔가며 `Enter()`를 호출했을 때, 정확히 대응하는 텍스트 한 종류만 나오고, 두 텍스트가 같은 프레임/연속 프레임에 동시에 나타나거나 한쪽 텍스트가 나온 뒤 다른 쪽으로 조용히 바뀌는 경우가 없는지"를 확인하는 픽스처로 그대로 재사용 가능하다.
