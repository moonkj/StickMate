## 1. 목표 / 트리거 / 유저가 보는 것 / 액션 / 예외 / 탈출구

**목표** — 이 앱에서 **창을 닫는 마우스 경로가 하나뿐**이 됐다. 그 하나가
"글자는 읽히는데 버튼으로는 안 읽히는" 상태를 끝낸다. 대비 하한 `MinNonTextContrast`(3.0:1)를
**실제로 넘긴다.**

**트리거** — 캐릭터창 / 설정창 / 팝오버 3종이 열려 있는 모든 순간(상시).

**유저가 보는 것** — 타이틀 줄 오른쪽 끝의 **밝은 키 하나**. 창에서 유일하게 "튀어나온" 물체이고,
그 위에 어두운 글자가 얹혀 있다. 창 안의 다른 어떤 칩도 이만큼 밝지 않다.

**유저가 할 수 있는 액션** — 클릭 → 즉시 닫힘 + 클릭 차단막 동시 해제(기존 동작 그대로).

**예외 상태**

| 상태 | 처리 |
|---|---|
| 창 폭이 최소치(`MinPanelWidth=320`)까지 줄었을 때 | 칩은 **오른쪽 앵커**라 항상 창 안에 남는다(기존 구조 유지). 줄어드는 것은 제목 상자다 |
| 창을 드래그하는 중 | 칩 색은 그대로. 상태 색을 바꾸면 그 자체가 깜빡임이다 |
| 전체화면 게임 감지 → 자동 숨김 | 창이 통째로 사라지므로 칩도 없다(원칙 2, 기존) |
| 앱이 비활성이라 hover가 한 프레임도 안 올 때 | **정상 동작.** hover는 장식이고, 기본 상태에서 이미 5.26:1이다 |
| 배율 1(비Retina) | 칩은 면으로 읽히므로 1px 선 소실의 영향이 없다(→ §3-3) |

**탈출구** — 이 칩이 **곧 탈출구**다. 그래서 이 문서 전체가 원칙 4에 직결된다.

## 2. 처방 A (필수) — 대비

### 2-1. 신설 상수 — 정확한 이름 = 값

**전부 `UiChrome`에 넣는다.** 값은 기존 상수에서 **파생**시킨다(숫자를 베끼지 않는다).

```csharp
// ── 목표 대비: 하한을 그대로 쓰지 않고 마진을 곱한다. 하한에 딱 맞추면 8비트 양자화·
//    감마 차이·모니터 프로파일 중 하나만 어긋나도 그 자리에서 미달이 된다.
public const float ControlFaceContrastTarget = MinNonTextContrast * 1.20f;   // = 3.60
public const float ControlInkContrastTarget  = MinTextContrast    * 1.15f;   // = 5.175

// ── 창 바탕 위에서 "누를 수 있는 것"의 면을 띄우는 흰색 α. §2-3의 두 부등식에서 유도.
public const float ControlFaceLift        = 0.50f;
public const float ControlFaceLiftHover   = 0.58f;
public const float ControlFaceLiftPressed = 0.66f;

// ── 실제 도색. Flatten이 α=1을 보장한다(창 알파의 법칙 — §3-2).
public static readonly Color ChromeButtonSurface =
    Flatten(new Color(1f, 1f, 1f, ControlFaceLift),        PanelSurface);   // #898B8E
public static readonly Color ChromeButtonSurfaceHover =
    Flatten(new Color(1f, 1f, 1f, ControlFaceLiftHover),   PanelSurface);   // #9C9EA0
public static readonly Color ChromeButtonSurfacePressed =
    Flatten(new Color(1f, 1f, 1f, ControlFaceLiftPressed), PanelSurface);   // #AFB0B2
```

**세 색을 `BrightTextBackdrops` 배열에 추가한다.** 이건 선택이 아니라 그 배열의 정의다 —
"강조색으로 가득 찬 면 = 사다리가 통하지 않는 면". 넣으면 `InkOnSurface`가 자동으로
`OnAccentSolid`를 골라 준다.

| 신설 색 | 값 | 대 `PanelSurface` | 8비트 양자화 후 | 사다리 6단 최댓값 | `BrightTextBackdrops` 적격 |
|---|---|---|---|---|---|
| `ChromeButtonSurface` | `#898B8E` rgb(0.539,0.545,0.555) | **5.26:1** | 5.26:1 | 3.10:1 | OK (전 단 < 4.5) |
| `ChromeButtonSurfaceHover` | `#9C9EA0` rgb(0.613,0.618,0.626) | **6.66:1** | 6.68:1 | 2.45:1 | OK |
| `ChromeButtonSurfacePressed` | `#AFB0B2` rgb(0.687,0.691,0.697) | **8.29:1** | 8.28:1 | 1.97:1 | OK |

> "사다리 6단 최댓값 < 4.5"는 기존 테스트
> `InkOnSurfaceTests.네거티브_컨트롤_강조색_면_위에서는_사다리_3단이_전부_무너진다`가
> `BrightTextBackdrops`의 **모든** 원소에 요구하는 조건이다. 세 색 모두 통과한다 —
> 즉 이 추가는 기존 테스트를 **깨지 않는다**(검산 완료).

### 2-3. **왜 0.50인가** — 두 부등식의 교집합에서 나온 값이다

칩을 밝히면 면 대비는 오르고 **글자 대비는 내려간다.** 둘은 반대 방향이다.
그래서 "3.0만 넘기면 된다"는 처방은 **버튼을 보이게 만들면서 그 위의 ✕를 지운다.**

`face(α) = Flatten(흰색 α, PanelSurface)` 로 두고, 두 하한을 각각 풀면:

```
면 대비 3.0:1 도달             α ≥ 0.3293   (#616367)
TextPrimary  4.5:1 유지 한계   α ≤ 0.3842   (#6E7073)     ← 밝은 잉크
TextSecondary 4.5:1 유지 한계  α ≤ 0.2055   (#44474B)
OnAccentSolid 4.5:1 도달       α ≥ 0.4312   (#797B7E)     ← 어두운 잉크
```

```
        α:  0.0        0.2055     0.3293   0.3842   0.4312              1.0
            ├───────────┼───────────┼────────┼────────┼──────────────────┤
 면 3.0:1              (미달)              ██████████████████████████████  α≥0.3293
 밝은 잉크 T1  ████████████████████████████████████                        α≤0.3842
 어두운 잉크 D                                     ███████████████████████  α≥0.4312
                                        ↑↑↑↑↑↑↑↑          ↑↑↑↑↑↑↑↑↑↑↑↑↑↑
                                       밝은 잉크 안        어두운 잉크 안
                                       (폭 0.055)          (폭 0.569 — 10.4배)
                                                              ★ 0.50 여기
```

- **밝은 잉크 안(α 0.329~0.384)은 폭이 0.055뿐이다.** 그 안에서는 hover로 조금만 밝혀도
  글자가 4.5 아래로 떨어진다 — 즉 **상태 변화를 넣을 수 없는 설계**다.
- **어두운 잉크 안(α ≥ 0.431)은 폭이 0.569로 10.4배 넓고, 밝힐수록 두 지표가 같이 오른다**
  (단조). hover/pressed를 어느 방향으로 움직여도 하한을 깰 수 없다.
- 두 제약을 동시에 푸는 최소값은 α=0.476(#848588, 4.89 / 5.19)이다.
  **0.50은 그보다 위**이고, 사람이 읽기 좋은 값이며, 두 지표 모두 목표(3.60 / 5.175)를 넘는다.

> **이것이 리더가 경고한 "실패한 측정과 성공한 측정이 똑같이 생긴" 함정의 이 라운드 판본이다.**
> α=0.34(면 3.11:1)로 고치면 `MinNonTextContrast` 검사는 **초록**이 되고, 화면에서는
> **✕가 사라진다**(TextPrimary 5.24 → hover 한 단만 올려도 4.5 붕괴). 면만 재는 검사는
> 그 붕괴를 못 본다. 그래서 §5의 테스트는 **면과 잉크를 한 쌍으로** 잰다.

### 2-4. Unity `Button`의 `ColorTint`를 **끈다** (`transition = Selectable.Transition.None`)

지금 세 표면 모두 `targetGraphic`만 지정하고 전이는 Unity 기본값(`ColorTint`)이다.
`ColorTint`의 pressed는 `targetGraphic.color`에 **0.7843을 곱한다.**

| | 면 | 대 `PanelSurface` | 글리프 대 면 | 판정 |
|---|---|---|---|---|
| 새 기본 | `#898B8E` | 5.26:1 | 5.59:1 | OK |
| 새 기본 × 0.7843 (Unity 기본 pressed) | `#6C6D6F` | 3.47:1 | **3.68:1** | **`MinTextContrast` 미달** |

지금 팔레트(어두운 칩 + 밝은 잉크)에서는 곱셈이 대비를 **올려서** 이 함정이 안 보였다.
칩을 밝히는 순간 부호가 뒤집힌다. **`Transition.None` + 명시 색**이 유일하게 안전하다.
(hover/pressed 색이 필요하면 §4-3.)

### 3-2. **"라이트/다크"가 무엇인지 — 먼저 정정한다**

리더 요구는 "다크/라이트 양쪽에서 성립"이었다. **이 앱에 라이트 테마는 없다**(실측:
`UiChrome`은 다크 글로스 팔레트 1벌뿐이고 `StickConfig`/`SettingsWindow` 어디에도 테마 전환이 없다).
그러니 그대로 두면 "라이트 검증"은 **존재하지 않는 것을 검증한 척**이 된다. 실재하는 축은 둘이다.

**(축 1) 유저의 바탕화면 — 실재하고, 지금 칩에 실제로 닿는다.**

이 저장소의 창 알파 법칙(`InfoWindowPanelOpacityTests` 클래스 문서):
`dstA' = srcA² + dstA(1−srcA)`. 불투명 본체(dstA=1) 위에 α=0.10짜리 겹을 얹으면
`dstA' = 0.01 + 0.90 = 0.91` → 그 화소에서 **데스크톱이 9% 비친다.**

| 표면 | `[✕]` 테두리 색 인자 | 창 알파 | 바탕화면 의존 |
|---|---|---|---|
| 캐릭터창 (`CharacterInfoWindow.cs:2599`) | **생 `CardBorder`(α0.10)** | **0.91** | **있다 — 1.26 ↔ 1.78** |
| 설정창 (`SettingsWindow.cs:862`) | `Flatten(CardBorder, CardSurfaceMuted)`(α1) | 1.00 | 없다 — 1.34 고정 |
| 팝오버 (`PopoverPanel.cs:602`) | **생 `CardBorder`(α0.10)** | **0.91** | **있다 — 1.37 ↔ 1.95** |

즉 **지금 `[✕]` 테두리는 어두운 바탕화면에서 더 나빠진다**(1.34 → 1.26). 유일한 탈출구가
"어두운 바탕화면을 쓰는 유저에게 더 안 보이는" 구조다. 그리고 세 표면 중 **설정창만** 이미
`Flatten`이 되어 있어 셋의 거동이 다르다 — 아무도 의도한 적 없는 3-way 분기다.
**테두리를 삭제하면 이 축이 통째로 사라진다**(면은 전부 α=1).

**(축 2) 밝은 면 위에서도 규칙이 성립하는가 — `InkOnSurface`와 같은 방식으로 값 판정.**

라이트 테마가 언젠가 생기거나, 앱 안의 밝은 면(`PortraitSurface #E9EAE6`) 위에 크롬 버튼을
놓게 되면 고정 상수 `#898B8E`는 무너진다. 그래서 **규칙 함수**를 함께 신설한다.

```csharp
/// <summary>★ "누를 수 있는 것"의 면을 고르는 단 하나의 문. InkOnSurface의 형제.
/// 두 제약을 <b>동시에</b> 만족하는 최소 혼합을 돌려준다(둘 중 하나만 풀면 §2-3의 함정에 빠진다):
///   ① 면 대 바탕      >= ControlFaceContrastTarget
///   ② InkOnSurface(면) 대 면 >= ControlInkContrastTarget
/// 반환값은 항상 alpha=1(Flatten 결과)이라 창 알파를 건드리지 않는다.</summary>
public static Color ControlFaceOnSurface(Color backdrop)
```

### 3-3. 왜 "테두리를 밝힌다"가 아니라 "면을 밝힌다"인가

`MinNonTextContrast`는 **면으로도 테두리로도** 만족시킬 수 있다(WCAG 1.4.11은 "컨트롤을 식별하는 데
필요한 시각 정보"를 요구하지 밝기의 위치를 지정하지 않는다). 그래도 면을 고른 이유:

1. **1px 선은 이 저장소가 이미 잃어 본 적 있다.** 배율 1(비Retina/Windows 100%)에서 테두리는
   물리 1픽셀이고, 커밋 `39ab690`("선 화질 조사")이 그 한계를 문서화했다.
   면은 24×24pt 덩어리라 배율에 상관없이 남는다.
2. **테두리를 밝히면 창 알파 문제가 남는다.** 밝힌 색을 `Flatten` 없이 넣으면 §3-2의 9% 비침이
   그대로다. `Flatten`을 강제해도 겹이 하나 더 있는 상태는 유지된다.
3. **"버튼처럼 보인다"의 심리적 단서는 면이다.** 테두리만 있는 것은 입력칸으로 읽힌다.

## 4. 발견가능성 판단 — **대비만으로는 부족하다**

리더 질문: *"대비만 올리면 충분한가."* **아니다.** 근거 4건, 그중 2건은 실측했다.

### 4-1. ★ `✕`(U+2715)는 **macOS 주요 UI 폰트 어디에도 없다** (실측)

`PopoverPanel.cs:604` 등이 쓰는 글자는 `U+2715 MULTIPLICATION X`다(코드포인트 확인 완료).
이 머신의 **폰트 파일 371개 cmap을 전수 파싱**했다:

| 코드포인트 | 371개 중 보유 | Arial | Helvetica | SF NS | Apple SD Gothic Neo | Apple Symbols |
|---|---|---|---|---|---|---|
| **U+2715 `✕`** (지금 쓰는 글자) | **4개** (Arial Unicode / Menlo / ZapfDingbats) | ✘ | ✘ | ✘ | ✘ | ✘ |
| U+2716 `✖` | 8개 | ✘ | ✘ | ✘ | ✔ | ✘ |
| **U+00D7 `×`** | **173개** | ✔ | ✔ | ✔ | ✔ | ✔ |

`UiChrome.AddText`는 `Resources.GetBuiltinResource<Font>("LegacyRuntime.ttf")`를 쓴다. 그 폰트의
폴백 체인이 Arial Unicode/Menlo까지 닿는지는 **Unity 런타임에서만 확인 가능 → 미확인으로 남긴다.**

그러나 **위험도는 확정적으로 낮출 수 있다**: 이 저장소는 이미 같은 이유로 심볼을 두 번 거부했다 —
톱니 U+2699(`CharacterInfoWindow.cs:2613` "없으면 두부(□)가 뜬다")와 경고 U+26A0
(`UX_FLOW.md:6998`). **`✕`만 예외로 남아 있다.** 그리고 이 앱은 한글 렌더링에서
"이름만 보고 믿지 않는다 → `RequestCharactersInTexture`로 글리프를 실측한다"는 규율을 이미 세웠다
(`DialogueBubbleRenderer.ResolveKoreanFont`).

> **대비를 아무리 올려도 글리프가 두부면 아무것도 고쳐지지 않는다.**
> 밝은 칩 위의 선명한 `□` — 그게 지금 처방 A만 적용했을 때의 최악 시나리오다.

**Windows 쪽은 이 머신에서 확인 불가 → 미확인.** Segoe UI / Malgun Gothic의 U+2715 보유 여부는
사용자 Windows 머신에서 판정해야 한다(§7).

### 4-2. 놓쳤을 때의 비용이 **무한**하다 (탈출구가 하나뿐이라서)

| 경로 | 상태 | 근거 |
|---|---|---|
| 창 밖 클릭 | **없어짐** (2026-09-02 사용자 지시) | `UiChrome.cs:382` |
| `Esc` | 없음 (클릭관통 긴급해제에 이미 묶임) | `CharacterInfoWindow.cs:33` |
| `Cmd+W` | **없음 + 남의 창을 닫는다** | `UiChrome.cs:376` |
| Dock 아이콘 / 메뉴바 | 없음 | `SettingsEscapeHatchTests.cs:37` |
| 무입력 자동 닫힘 | 캐릭터창·설정창 **없음** / 팝오버만 180초 | `UiChrome.cs:398` |

칩을 못 찾은 유저에게는 **바탕화면 위에 클릭을 먹는 사각형이 무기한 남는다.**
이건 "조금 불편"이 아니라 원칙 2(업무 방해 제로)의 정면 위반 상태이고, 시간 상한이 없다.
비용이 무한한 실패 모드에는 **중복 신호**를 넣는 것이 옳다. 대비 하나에 걸 문제가 아니다.

### 4-3. hover는 **발견 수단이 될 수 없다** (구조상)

`CharacterInfoWindow.cs:1952`가 직접 적어 둔 사실: *"hover는 있으면 좋은 것이지 필수가 아니다 —
이 앱의 uGUI 입력은 창을 클릭해야 활성화된다."* 앱이 비활성인 동안 hover가 한 프레임도 안 올 수
있고, **처음 창을 열었을 때가 정확히 그 상황**이다. 그러므로 hover는 **확인용 피드백**이지
**발견용 신호**가 아니다. 기본 상태만으로 발견 가능해야 한다.
(그래서 §2-1의 hover/pressed는 "선택"이다. 넣는다면 `Transition.None` + 폴링 경로에서 색 교체.)

### 4-4. 팝오버 칩은 **22×22pt** — 목표 크기 하한 미달

`PopoverPanel.cs:602`: `PlaceTopLeft(close.rectTransform, closeLeft, -Space3, 22f, 22f)`.
캔버스 1유닛 = OS 논리 포인트 1이다(`ScreenCoordinateConverter.ResolveCanvasScaleFactor` 문서).
WCAG 2.2 SC 2.5.8 Target Size (Minimum, AA) = **24×24**. 캐릭터창·설정창은 24로 맞고 팝오버만 22다.
**2pt 부족.** (이 저장소는 이미 1.4.3/1.4.11을 자기 하한으로 인용하고 있으므로 같은 문서의
2.5.8을 인용하는 것이 일관된다.)

### 4-5. → **처방 B (강력 권고): 글자를 쓴다**

**`[✕]` → `[닫기]` 낱말 칩. 44×24pt.**

이건 새 발명이 아니라 **이 저장소가 이미 내린 결정의 적용**이다.
`CharacterInfoWindow.cs:2610`이 [설정] 버튼에 대해 적어 둔 판정:

> *"글자를 쓰는 이유: … 톱니 글리프(U+2699)가 있다는 보장이 없고, 없으면 두부(□)가 뜬다.
> 아이콘을 선으로 그리는 방법도 있지만 24pt 칩 안의 톱니는 결국 읽히지 않는다."*

`[✕]`는 이 판정을 적용받지 않은 **마지막 하나**다. 적용하면:

- 글리프 리스크(§4-1) **소멸**. 한글은 이 앱 전체가 이미 렌더한다.
- 발견가능성: 낱말은 오독되지 않는다.
- **크기가 자동으로 해결된다** — `[설정]`이 이미 44×24다. 같은 값을 쓰면 §4-4도 같이 끝난다.
- 헤더 문법이 통일된다: `… [설정] [닫기]` — 같은 크기의 낱말 칩 둘, 밝기만 다르다.

**밝기로 서열을 준다(글자 크기가 아니라).** `[닫기]`만 `ChromeButtonSurface`(5.26:1, 어두운 글자)를
쓰고, `[설정]`은 지금 그대로 둔다. 창에서 **가장 밝은 칩이 정확히 하나**이고 그것이 탈출구다.

> **`[설정]`을 왜 같이 안 밝히는가 — 두 가지 이유, 하나는 산술이다.**
> ① `[설정]`은 낱말이 자기를 식별한다(글자 8.54:1). WCAG 1.4.11은 낱말 버튼의 테두리 대비를
>    따로 요구하지 않는다. 반면 `[✕]`는 식별 정보가 **기호와 면뿐**이라 1.4.11이 그대로 문다.
> ② **중간 밝기 칩은 이 디자인 시스템에 자리가 없다**(실측). 면이 3.0을 넘으면서 밝은 잉크를
>    유지하려면 α∈[0.329, 0.384]인데, 그 구간의 면은 `TextBackdrops`(전 사다리 4.5 요구),
>    `RaisedTextBackdrops`(Title 비활성 = `TextSecondary` ≥ 4.5 요구 → α ≤ 0.206),
>    `BrightTextBackdrops`(전 사다리 < 4.5 요구) **어느 목록에도 속하지 못한다.**
>    `TextSecondary` 상한 α=0.206 < 면 하한 α=0.329 — **교집합이 비어 있다.**
>    "중간 티어"를 만들면 세 목록의 분류 체계를 깨야 한다. 그럴 이유가 없다.

**기호를 남기고 싶다면**(리더 판단): 폰트 글리프가 아니라 **선 두 개로 그린다.**
이 앱은 모든 그림이 프로시저럴이고 `UiChrome`에 캡슐/링 프리미티브가 이미 있다. X는 톱니와 달리
24pt에서 완벽히 읽히는 도형이므로 32-1의 "심볼만 있는 원은 오독된다"가 적용되지 않는다.
선 색은 `InkOnSurface(ChromeButtonSurface, Title, true)` = `#0B1016`(5.59:1)을 그대로 쓴다.
**단, 폰트 글리프 `✕`를 그대로 두는 선택지는 없다** — §4-1이 미확인으로 남는다.

### 6-1. 문자열 `"[✕]"`를 단언하는 테스트 (수정 필요 목록)

`SettingsEscapeHatchTests.cs:189`가 `t.text.Contains("[✕]") && t.text.Contains("닫")`로
푸터 문장을 검사한다 — **`[닫기]`로 바꾸면 이 단언이 깨진다.** 나머지는 실패 메시지 안의
문자열이라 동작에 영향이 없지만, 문구가 화면과 어긋나면 로그가 거짓말을 한다:
`SurfaceCloseHintTests` / `SurfaceOutsideClickTests` / `InfoWindowExclusiveModalTests` /
`SettingsWindowReturnPathTests` / `SettingsReopenAfterSuspendTests` / `ActionCommandPopoverTests`.

### 6-2. 별건 보고 — **팝오버 180초 자동 닫힘은 이번 사용자 지시와 충돌한다**

사용자 지시 원문은 *"사용자가 닫기전에는 안꺼져야함"*이다. `PopoverPanel.DefaultIdleAutoCloseSeconds
= 180f`는 **사용자가 닫지 않았는데 꺼진다.** 캐릭터창·설정창에는 없는 동작이 팝오버에만 남아 있다.
이번 처방의 범위 밖이지만 **원칙 1(표시-실제 일치)의 잠재 위반**이므로 리더 판단을 요청한다.
(내 의견: 팝오버는 "2초짜리 심부름용"이라는 설계 의도가 있으므로 유지에 근거가 있다. 다만
**지금은 어디에도 그 사실이 안 적혀 있다** — 3분 뒤 사라지면 유저는 "버그"로 읽는다.)

### 6-3. 별건 보고 — **미확인으로 남기는 것 2건**

| # | 미확인 사항 | 판정 방법 |
|---|---|---|
| U1 | `LegacyRuntime.ttf` 폴백이 U+2715에 닿는가 (macOS) | 실제 빌드 캡처. `Text.font.HasCharacter`가 없는 레거시 `Text`이므로 `RequestCharactersInTexture` + `GetCharacterInfo('✕')`로 **글리프 폭 실측**(`ResolveKoreanFont`와 같은 방법) |
| U2 | Windows(Segoe UI / Malgun Gothic)의 U+2715 보유 | 사용자 Windows 머신 캡처 |

**처방 B(낱말 칩)를 채택하면 U1·U2가 둘 다 소멸한다.** 그게 B를 권고하는 가장 실용적인 이유다.
