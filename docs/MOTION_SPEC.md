## 1. 통합 근본원인 — "도달 불가 분기(unreachable branch)"

연출/대사의 분기 임계값이 **월드 유닛 절대값**으로 적혀 있다. 그런데
- 캐릭터 신장은 배율 슬라이더로 **1.71 ~ 3.41 유닛**을 오간다(기준 `BaselineCharacterTotalHeight = 2.2747`),
- 실제 데스크톱에서 상시로 존재하는 단차는 **Dock 하나뿐이고 1.637유닛 = 0.72 신장**이다.

그 결과 아래 5건이 전부 "한쪽 가지가 안 나오는" 상태다. **전부 같은 병이다.**

| # | 위치 | 임계값 | Dock 단차(0.72H) 대비 | 실측 결과 |
|---|---|---|---|---|
| 1 | `BattleMinigameState` 대사 | `chargeRatio ≥ 0.9` | 성공 구간 `0.70~0.85`와 **서로소** | 성공 시 "필살기다!" **0%**, 실패 시 **100%** |
| 2 | `ParkourClimbState` 대사 | `climbHeight ≥ 2.0` (0.88H) | 0.72H < 0.88H | "헉... 높다" **0/7**, 전부 "가뿐하네" |
| 3 | `LedgeHangState` 대사 | `drop ≥ 3.0` (1.32H) | 진입 자체가 0회 | "어우... 꽤 깊네" **0회** |
| 4 | `rollLandingHeightThreshold` | `2.0` (0.88H) | 0.72H < 0.88H | 무릎앉아 **1회**(초기 스폰만) |
| 5 | `LedgeHangMinDropDepth` | `2.507` (1.10H) | 0.72H < 1.10H | 매달리기 **0회** |

> ### ★★ 2026-09-01 후속 정정 (같은 담당자) — 이 표의 "0.72H"는 **배율 1.0 가정**이다
>
> 위 표의 `Dock 단차(0.72H)` 열은 `1.637유닛 ÷ BaselineCharacterTotalHeight(2.2747)`로 계산했다.
> 그런데 `BaselineCharacterTotalHeight`는 **배율 1.0에서의** 신장이고, 런타임 신장은
> `CharacterHeightWorld = 2.2747 × characterScale`이다. 즉 **같은 Dock 단차가 배율에 따라 다른 H가 된다**:
>
> | 배율 | 신장(유닛) | Dock 단차 1.637유닛 = ? H |
> |---|---|---|
> | 1.00 | 2.275 | **0.72 H** (위 표가 쓴 값) |
> | 0.75 (출하 기본 `characterScale`) | 1.706 | **0.96 H** |
> | 0.60 (실측 세션의 저장값) | 1.365 | **1.20 H** |
> | 0.35 (다이얼 하한) | 0.796 | **2.06 H** |
>
> **#1~#4의 결론은 그대로 유효하다** — 그 임계값들은 전부 **절대 월드 유닛**(2.0 / 3.0 / 비율)이라
> 배율과 무관하게 1.637유닛보다 크다. 표의 `0.88H` 같은 괄호는 배율 1.0에서의 환산 표기일 뿐이다.
> **오직 #5만 신장 파생(1.1022 H)이라 배율에 따라 판정이 뒤집힌다.** 그래서 #5의 "매달리기 0회"는
> 배율 조건부 관측이었고, **14절에서 정면으로 정정한다**(배율 0.60 실측 로그에서 매달리기 4회 발생).
> 교훈은 1-1절 규칙의 보강이다 — **H 배수로 적되, 그 H가 어느 배율의 H인지까지 적는다.**

> #5만 신장에서 파생된다(`LedgeHangDropDepth`). 나머지 4건은 전부 절대 유닛이다.
> `hopDownMinDropHeight = 0.35`도 절대값이다(0.154H) — 배율 0.35배에서는 0.44H가 되어
> "한 계단마다 뛰어내리기 결정"이 뜬다. 같은 병의 6번째 사례다.

### 1-1. 규칙 (앞으로 모든 연출/대사에 적용)

> **연출·대사의 거리 분기 임계값은 예외 없이 `CharacterHeightWorld` 배수(H)로 적는다.
> 각도는 크기와 무관하므로 절대값(도)으로 적는다.
> 비율 분기(게이지 등)는 그 비율을 판정하는 상수(스위트스팟 등)와 **같은 축 위에** 놓는다 —
> 판정 구간과 대사 구간이 서로소가 되는 순간 그 대사는 거짓말 전용이 된다.**

이 규칙은 이미 존재하는 리더 지시("거리·속도 성분은 StickmanMetrics에서 파생시켜라. 각도는 크기와
무관하니 절대값")의 **대사·임계값 판까지 확장**한 것이다.

## 2. [M1] 격파 미니게임 — 결과 축 도입 (최우선, 불변 원칙 1 정면 위반)

### 2-1. 진단 — 왜 100%인가 (수학적 증명)

```
sweetStart = 0.70, sweetEnd = 0.85          (StickConfig)
성공  ⟺  0.70 ≤ r ≤ 0.85
"필살기다!" ⟺  r ≥ 0.9
∴ 성공 ∩ "필살기다!" = ∅          ← 성공했을 때 이 대사는 절대 안 나온다
∴ "필살기다!" ⊂ 실패              ← 나왔다면 반드시 실패다
```

여기에 `TickCharging()`의 자동 릴리즈가 겹친다:

```csharp
if (ratio >= 1f) TriggerResolution(1f);   // 클릭이 한 번도 없으면 r = 1.0 확정
```

무인 관측(사용자가 클릭하지 않는 상황)에서는 **모든 판정이 r = 1.0**이다.
`1.0 ≥ 0.9`이므로 **실패 100% → "필살기다!" 100%**. 페르소나의 50/50은 표본이 아니라 항등식이다.

### 2-2. 진짜 결함은 "결과 축이 파라미터에 없다"

`ResolveOutcome()`은 `success`, `_retryCount`, `_terminal`을 **그 자리에서 전부 계산한 뒤 버린다.**
`BattleDialogueParams`에는 `ChargeRatio` 하나만 남는다. 대사 매핑 함수는 확정된 판정을 **볼 수가 없다.**

원칙 1은 "대사는 확정된 상태에서만 파생"이라고 말하는데, 이 코드는 그 상태의 **가장 중요한 확정
사실(성공/실패)을 매핑 함수에 전달하지 않는다.** 구조가 원칙을 지킬 수 없게 되어 있다.

또한 **클릭 여부를 구분할 수 없다**: `TriggerResolution(1f)`가 두 경로(클릭 릴리즈 @1.0 / 무클릭
자동 릴리즈)에서 똑같이 호출된다. "늦게 눌렀다"와 "안 눌렀다"는 유저 경험이 완전히 다른데
스냅샷이 같다.

### 2-3. 파라미터 개정 (coder 인계 사양)

```csharp
public enum BattleRelease
{
    Opening,     // 최초 진입(게이지 시작). 아직 판정 전.
    Success,     // 스위트스팟 안에서 클릭
    EarlyMiss,   // 클릭했으나 r < sweetStart
    LateMiss,    // 클릭했으나 r > sweetEnd
    NoInput,     // 클릭 없이 게이지가 만충되어 자동 릴리즈(r = 1.0)
}

public sealed class BattleDialogueParams
{
    public BattleRelease Release;         // ★ 신규 — 결과 축
    public float ChargeRatio;             // 기존
    public int   RetriesLeft;             // ★ 신규 — 확정된 남은 재도전 횟수(성공/소진이면 0)
    public bool  Terminal;                // ★ 신규 — 이번 판정으로 대결이 끝나는가
    public float ChargeDurationSeconds;   // ★ 신규 — 이번 게이지의 확정 길이(개시 대사용)
    public float SweetStart, SweetEnd;    // ★ 신규 — 스냅샷. 매핑 함수가 설정을 직접 읽지 않게 한다
}
```

**스냅샷 시점**은 예외 없이 `Enter(context)` 안이다(기존 self-transition 패턴 그대로).
`TriggerResolution(float chargeRatio, bool clicked)`로 시그니처를 넓혀 `_pendingClicked`를 함께
보류한다 — 이것 하나가 `LateMiss`와 `NoInput`을 가른다.

### 2-4. 텍스트 매핑 함수 (순수 함수 1개, 분기만. 31-1 원칙 준수)

```
resolve(p):
    mid = (p.SweetStart + p.SweetEnd) / 2          # 기본 0.775

    # ── 개시
    if p.Release == Opening:
        return p.ChargeDurationSeconds >= 1.75 ? "천천히... 모은다"
                                               : "빠르다, 집중"

    # ── 성공 (여기서만 "필살기다!"가 나온다)
    if p.Release == Success:
        return p.ChargeRatio >= mid ? "필살기다!"      # 0.775 ≤ r ≤ 0.85
                                    : "딱 맞았다!"     # 0.70 ≤ r < 0.775

    # ── 실패이면서 이번이 마지막 판정(재도전 소진)
    if p.Terminal:
        return "오늘은 여기까지"

    # ── 실패, 재도전이 정확히 한 번 남음 (Attack "한 발 더!"와 같은 모양)
    if p.RetriesLeft == 1 and p.Release != NoInput:
        return "마지막 한 번!"

    # ── 실패 사유별
    switch p.Release:
        NoInput:   return "어... 힘이 다 샜다"        # ★ 100.0%가 가리키던 자리
        EarlyMiss: return p.ChargeRatio < p.SweetStart * 0.5 ? "너무 빨랐다"
                                                             : "아, 조금 일렀나"
        LateMiss:  return "아... 늦었다"
```

**고유 대사 2개 → 10개.** 그리고 모든 문장이 확정된 파라미터의 진술이다.

| 대사 | 이 문장이 참인 조건 | 그 조건이 확정된 시점 |
|---|---|---|
| 천천히... 모은다 / 빠르다, 집중 | `_chargeDuration` 확정 | `BeginCharge()` — `DialogueIntent` 생성 **직전** |
| 필살기다! / 딱 맞았다! | `success == true` | `ResolveOutcome()` 상단 |
| 오늘은 여기까지 | `_terminal == true` (실패 소진) | `ResolveOutcome()` |
| 마지막 한 번! | `_terminal == false` ⇒ `BeginCharge()` **보장** | `TickResolving()`의 else 분기가 구조적으로 보장 |
| 어... 힘이 다 샜다 | `clicked == false` | `TickCharging()`의 `ratio >= 1f` 경로 |
| 너무 빨랐다 / 아, 조금 일렀나 / 아... 늦었다 | `clicked && r ∉ [start,end]` | `ResolveOutcome()` |

> **"마지막 한 번!"이 미래형 약속이 아닌 이유**: `_terminal == false`가 확정되면
> `TickResolving()`은 `BeginCharge()` 외의 경로가 없다. 즉 "한 번 더 한다"는 **이미 확정된 사실**이며,
> `AttackState`의 `"한 발 더!"`(shotsRemaining ≥ 1)와 구조적으로 동일하다. 5절 "미래형 약속 금지"에
> 걸리지 않는다.

### 2-5. 타임아웃(5초 무입력) 경로는 **침묵을 유지한다**

`Tick()`의 `_noInputTimer >= inputTimeout` 경로는 대사를 만들지 않는다 — 이 판정의 의미가
"**유저가 이미 다른 작업으로 이탈했다**"이기 때문이다. 이탈한 유저에게 말을 거는 것은 불변 원칙 2
(업무 방해 제로) 위반이다. `Idle`로 전이한 뒤 잡담 쿨다운이 자연히 흡수한다. **의도적 무발화다.**

### 3-3. 대사 종류 축 — `DialogueKind`

### 3-4. 발화 자격 게이트 — "컷될 대사는 애초에 만들지 않는다"

`Narrative`를 즉시 컷하면 "0.08초 번쩍이고 사라지는 글자"가 새 노이즈가 된다. 그래서 **발화 시점에
막는다.**

```
가독예산(text) = clamp(0.28 + 글자수 × 0.075, 0.62, 2.20)      [초]
필요체류(text) = FadeInSeconds + 가독예산(text)
Narrative 발화 조건: 지금 확정된 상태의 "계획 잔여 체류 시간" ≥ 필요체류(text)
```

**"계획 잔여 체류 시간"의 출처** — 지어내는 값이 아니다. 이미 존재한다.

| 상태 | 출처 | 비고 |
|---|---|---|
| `Idle` | `AutoWanderController._restDuration - _restTimer` | 진입 시 2~6초로 확정됨 |
| `Walk` | `AutoWanderController._moveDuration - _moveTimer` | 진입 시 1.5~4초로 확정됨 |
| `ParkourClimb` | `parkourClimbDuration × (1 - _climbProgress)` | Enter에서 `_climbProgress = 0` |
| `LedgeHang` | `_holdDuration` | Enter에서 확정 |
| `BattleMinigame`(개시) | `_chargeDuration` | `BeginCharge()`에서 확정 |

계획은 계획이라 **외부 사건(모서리 도달, 피격, 발판 소실)으로 깨질 수 있다.** 깨진 경우는 3-3의
즉시 컷이 받는다. 즉 **게이트가 다수(예측 가능한 종료)를, 즉시 컷이 소수(예측 불가 인터럽트)를**
담당한다. 어느 쪽도 거짓말을 남기지 않는다.

**예산 계산 예 (`FadeInSeconds`는 3-5의 신규값 0.06 적용)**

| 대사 | 글자수 | 가독예산 | 필요체류 | 현행 화면 점유 |
|---|---|---|---|---|
| "음..." | 4 | 0.62(하한) | 0.68 | 0.82 |
| "가뿐하네" | 4 | 0.62(하한) | 0.68 | 0.82 |
| "잠깐 쉬는 중" | 7 | 0.805 | 0.865 | 0.82 |
| "저쪽으로 가볼까" | 8 | 0.88 | 0.94 | 0.82 |
| "창 위는 미끄러워" | 9 | 0.955 | 1.015 | 0.82 |

> 현행 하한 0.82초는 **글자수를 전혀 보지 않는다.** "음..."과 "창 위는 미끄러워"가 같은 시간
> 떠 있다. 뒤쪽은 짧고 앞쪽은 길다 — 가독성 하한이라면서 실제로는 가독성을 보장하지 않았다.

### 3-5. 페이드 상수 개정 — 완전 불투명 구간을 늘린다

현행: `FadeIn 0.15 + 불투명 0.55 + FadeOut 0.12 = 0.82`. **읽을 수 있는 구간이 67%뿐이다.**

## 4. [M3] 착지 무게감 — 낙차 티어

### 4-1. 진단 — 두 개의 결함

```csharp
float span = deepHeights * CharacterHeightWorld;                  // 3.0 × H
float t = Mathf.Clamp01((FallHeight - threshold) / span);         // threshold = 2.0 (고정!)
```

**(a) 가산 상수 2.0만 신장에 안 걸려 있다.** 램프 상한 = `2.0 + 3.0×H`.

| 신장 | 임계값의 신장 배수 | 포화 낙차 | 포화 낙차의 신장 배수 |
|---|---|---|---|
| 1.71 (배율 0.75) | **1.17 H** | 7.13 | 4.17 H |
| 2.27 (배율 1.00) | **0.88 H** | 8.81 | 3.88 H |
| 3.41 (배율 1.50) | **0.59 H** | 12.23 | 3.59 H |

같은 "체감 높이"에서 다른 반응이 나온다. 배율 0.75에서는 둔하고 1.5에서는 예민하다.

**(b) 램프가 너무 일찍 포화한다.** 신장 3.9배면 끝인데, 실제 낙하는 신장 **10배**까지 나온다
(페르소나 실측 17.76 / 1.71 = 10.4H). 포화 이후 구간이 실사용의 **절반 이상**이다.

**페르소나 3점 검산 (신장 배수로 환산하면 원인이 즉시 보인다)**

| 낙하 | 신장 | 신장 배수 | 현행 t | 현행 지속 |
|---|---|---|---|---|
| 7.19 | 1.71 | **4.20 H** | 1.00 | 0.62 |
| 17.76 | 1.71 | **10.39 H** | 1.00 | 0.62 |
| 12.98 | 3.41 | **3.81 H** | 1.00 | 0.62 |

세 번째(3.81H)는 첫 번째(4.20H)보다 **더 가벼운 낙하**인데 절대 유닛(12.98 vs 7.19)만 보면 두 배
가까이 깊어 보인다. **절대 유닛으로 보는 순간 판단이 뒤집힌다** — 이것이 임계값을 H 배수로
적어야 하는 이유의 실증이다.

### 4-2. `차단스위치=True -> 무시`는 **옳다** — 페르소나 보고 반박

페르소나는 "랙돌 임계 8.0을 넘긴 9.88조차 무시됐다 / 아무리 높이 떨어져도 절대 안 넘어진다"를
결함으로 보고했다. **판정 자체는 반박한다.**

- 아키텍처 0절: RAGDOLL은 **외력**(피격/던져짐)에 배정된 상태다. 자기가 떨어져 땅에 닿는 것은
  외력이 아니라 **착지**다. `IsOwnLandingContact`가 "비-Dynamic 바디 + 발밑 접촉"을 착지로 보는
  판정은 정확하다.
- 그 차단막을 풀면 사용자가 명시적으로 신고한 그림("떨어질때 관절이 이상하게 꺾이면서 넘어지는데")이
  그대로 돌아온다. 그 신고 때문에 무릎앉아 착지가 생겼다.
- 무엇보다 **충격량은 무게감의 신호로 쓸 수 없다.** `FallState`가 스윕 교차로 착지를 확정하며 몸을
  발판 상단으로 스냅하고 하강 속도를 지우기 때문에, **정상 착지의 충격량은 0.00이다**(실측 로그
  3건 전부 0.00). 충격량이 0이 아닌 경우는 "논리 발판이 없는 물리 바닥 낙하"라는 예외 경로뿐이다.

**결론: `landingImpactRagdollShield`는 `true`로 유지한다. 무게감은 `LastLandingFallHeight`(낙차) 축
하나로만 표현한다.** 페르소나가 본 증상("절대 안 넘어진다")은 진짜지만, 원인은 차단막이 아니라
**낙차 축에 상위 티어가 없다는 것**이다. 아래가 그 답이다.

### 4-3. 신규 티어 표 (전부 신장 배수 H — 배율 불변)

```

```

| 티어 | 구간 | 이름 | 지속 | 최대 깊이 | 새 코드 |

| **T2** | `2.40 ≤ hH < 3.90` | 깊은 무릎앉아 | 0.48 → 0.62초 | 0.78 → 1.00 | 수식만 |
| **T3** | `3.90 ≤ hH < 6.50` | **버티는 착지(신규)** | 0.62 → 0.88초 | 1.00 고정 | 수식만 |
| **T4** | `hH ≥ 6.50` | **손짚고 엎어짐(신규)** | 0.72초 + GETUP | 1.00 | **새 곡선 필요** |

**T0.5를 넣는 이유** — 지금 Dock 단차(0.72H)는 임계값 0.88H 아래라 **완전 무반응**이다.
실측 로그에서 캐릭터는 1분에 열 번 넘게 Dock에서 내려오는데 그때마다 무릎이 **1도도 안 굽는다**.
발이 바닥에 스며드는 그림이다. `LandingCrouchState` 클래스 문서가 "한 계단 내려올 때마다 무릎을
꿇는 일은 없다"고 못 박은 것은 **옳다** — 다만 그 문서가 막으려던 것은 **무릎 꿇기 실루엣**이지
**무릎이 주는 것** 자체가 아니다. T0.5의 깊이 0.08~0.45는 무릎 꿇기가 아니라 **평범한 계단 내려딛기**다
(Dock 0.72H에서 깊이 0.334 → 앞무릎 굽힘 약 42도). 이 구분으로 그 문서의 판단과 충돌하지 않는다.

### 4-4. 수식 (연속 — 티어 경계에서 불연속 없음)

```
hH = FallHeight / H

t0 = clamp01((hH - 0.35) / 0.53)      # T0.5 램프  0.35H ~ 0.88H
t  = clamp01((hH - 0.88) / 3.02)      # 깊이 램프  0.88H ~ 3.90H
u  = clamp01((hH - 3.90) / 2.60)      # 버팀 램프  3.90H ~ 6.50H

if hH < 0.35:  상태 진입 안 함
if hH >= 6.50: T4 (4-6절 별도 곡선)

depth01      = hH < 0.88 ? lerp(0.08, 0.45, t0) : lerp(0.45, 1.00, t)
duration     = hH < 0.88 ? lerp(0.14, 0.32, t0) : lerp(0.32, 0.62, t) + u * 0.26
holdFraction = 0.24 + u * 0.16                       # 0.24 → 0.40
compressFraction = 0.18                              # 유지("툭" 받는 느낌은 언제나 짧아야 한다)
torsoPitchDeg    = lerp(6, 22, max(t0*0.35, t)) + u * 8      # 6 → 22 → 30도 (신규 축)
headLagDeg       = lerp(3, 14, max(t0*0.35, t)) + u * 6      # 3 → 14 → 20도 (신규 축)
```

## 5. [M4] 뛰어내리기 — 연출 요구사항 (원인 규명은 debugger 소관)

### 5-1. 지금 화면에서 보이는 것

> **"내려가려고 모서리로 걸어가 발을 뗐는데 그 자리에 그대로 있다."**

실측 근거(`stickmate.log`): `발 뗀 X`가 모서리보다 항상 **0.079 ~ 0.107유닛 안쪽**이고

이건 물리 이전에 **그림이 성립하지 않는다** — 판자 위에 서 있는데 떨어지고 있다.

### 5-2. 요구사항 R1 — 발끝이 모서리 밖에 있어야 한다

> 이탈 프레임에서 **앞발 발끝의 X**가 모서리보다 **바깥쪽으로 최소 `0.06 × H`** 나가 있을 것.

발끝 기준으로 다시 잡아야 한다.

### 5-3. 요구사항 R2 — 낙차 0이면 그건 뛰어내리기가 아니다. **멈칫으로 연출한다**

실제 낙차가 **예상 낙차의 50% 미만**이면 그 시도를 "뛰어내리기"로 그리지 말고
**모서리 멈칫(edge balk)** 으로 그린다. 실패를 감추지 말고 **의도된 망설임**으로 보이게 하는 것이

**참고 이미지 근거**: Alan Becker `Slime Trampoline` 컷의 노란 스틱맨 — 블록 상단 모서리에 발끝을
정확히 걸치고, **양팔을 좌우로 거의 수평까지 벌리고 상체를 뒤로 젖혀** 균형을 잡는다(10절 기록).

## 13. [M5] `idleAmbientLookElbowDegrees = 122°` — **98°로 내린다** (어깨 107°는 그대로)

### 13-0. 결론 4줄

1. **122°는 연출상 필요한 각도가 아니다. 오히려 결함이다.** 이 각도에서 **손끝이 머리 원 안쪽
   0.48 R 지점에 파묻힌다.** 머리는 불투명 원판이고 팔보다 **위에** 그려지므로(`HeadFill`
   sortingOrder **3** / `HeadOutline` **4** vs 팔 **2**) 손은 화면에 **한 픽셀도 나오지 않는다**.
   아래팔도 **58%가 머리에 먹혀** 짧은 갈고리 토막만 남는다. **실제 빌드 캡처로 확인했다**(13-3).
2. **구현 담당의 110° 안은 반증한다.** 110°에서도 손은 여전히 머리 안(실루엣 안쪽 0.56pt)이고
   아래팔은 여전히 **1.82획 길이만큼 완전히 잠긴다**. 그림은 거의 안 고쳐지고 각도만 잃는다.
   그리고 규칙 B 여유는 **1.53배가 아니라 1.325배**다(13-6에서 테스트와 같은 식으로 검산).
3. **98°는 두 축을 동시에 만족한다.** 손끝이 머리 실루엣에 **정확히 닿고**(원 유도가 원래 노렸던
   그 방향 β=52.8° 그대로), **어깨 각도를 안 바꾸므로 팔꿈치 화면 위치가 1픽셀도 안 움직이고**,
   규칙 B 여유는 **1.046 → 1.650**으로 올라 팔이 병목에서 아예 빠진다.
4. 팔을 내려도 **전체 최악 여유는 1.168에서 멈춘다** — 그 아래는 다리(무릎앉아 126°, 배율 0.35)다.
   즉 이 변경의 값어치는 "여유 1.65 확보"가 아니라 **"병목을 팔에서 다리로 넘겨 팔을 후보에서
   지운다"**이다. 리더가 인용한 "110° → 1.53"은 어느 쪽으로도 나오지 않는 숫자다(13-6).

### 13-1. 이 상수가 만드는 동작이 무엇인가 (먼저 확인한 것)

`idleAmbientLookElbowDegrees`는 **오직 한 곳**에서만 쓰인다 —
`StickmanBlackboard.BuildIdleAmbientPoseSettings()` → `StickmanPoseAnimator.ApplyIdleAmbientPose()`의
`WanderAmbientMotion.LookAround` 분기. 즉 **유휴 "주위 살피기"(손차양) 전용**이다.

발동 빈도(코드 실측, `AutoWanderController.TickResting`):

| 항목 | 값 | 출처 |
|---|---|---|
| 발동 조건 | Idle 진입 후 1.0~2.5초 뒤 **그 Idle 구간에 1회** | `wanderLookAroundDelayMin/Max` |
| 최소 간격 | **30초** | `wanderLookAroundCooldownSeconds` |
| 지속 | **0.9초** | `idleAmbientLookAroundSeconds` |
| 진행 곡선 | `env = smoothstep(sin(πp))` — 양 끝 정확히 0, 가운데 hold | `ApplyIdleAmbientPose` |
| 실제 팔꿈치 각 | `10° + 112°·env` → **122°는 `env=1`인 한 순간뿐** | `Mathf.LerpAngle(lower, 122, env)` |

`env ≥ 0.9`(팔꿈치 ≥ 110.8°) 구간은 0.9초 중 **0.465초**, `env ≥ 0.978`(팔꿈치 ≥ 119.5°)는
**0.284초**다. 즉 **30초에 한 번, 0.28초 동안** 규칙 B 여유가 1.10 아래로 내려간다.

### 13-2. 왜 122°가 됐나 — 원 유도의 결함

`StickConfig` 툴팁이 유도를 남겨 놨다:

> "107과 아래 팔꿈치 122는 임의값이 아니라 **손끝이 어깨 기준 (앞 0.20, 위 0.95)×팔길이**
> = 이마 높이에 오도록 역산한 쌍이다."

역산 자체는 맞다. 프리팹 실측으로 정방향 계산하면 손끝은 어깨 기준 `(+0.0631, +0.2654)`(로컬 유닛)
= 한 마디 길이(≈0.28)로 나누면 **(앞 0.22, 위 0.94)** — 툴팁의 (0.20, 0.95)와 사실상 같다.

**결함은 목표점의 단위가 아니라 "머리가 계산에 없다"는 것이다.** 어깨→머리 중심 거리는 **0.2175**,
머리 실루엣 반지름은 **0.19337**(외곽선 반폭 포함)인데, 손끝은 어깨에서 **0.2728**밖에 안 나가므로

### 13-6. 규칙 B 검산 — 테스트와 **같은 계산**

`LimbCurveGeometryTests.곡률_반경이_획_반두께보다_커서_안쪽에_각진_크리즈가_남지_않는다`가 쓰는 식을
그대로 재현했다(마디 규격은 프리팹 실측, 배율 표본은 `MinCharacterScale`~`MaxCharacterScale` 9등분 + 구운 배율):

```
W_world = max(구운획 × (s / 0.75), MinStrokeScreenPoints / ReferencePointsPerWorldUnitApprox)
k       = s / 0.75            W_local = W_world / k
h       = |굽힘|/2 [rad]      t0 = FilletLengthRatio × min(Lu, Ll)
sagitta 캡: t0·tan(h/2) > 1.0·W_local 이면 t = W_local / tan(h/2)   ← 병목점에서는 발동 안 함
r       = t / tan(h)          ratio = r / (W_local/2)
임계     = 1 / cos(h / 6)      (= CreaseThreshold, ArcSamplesPerHalf=4)
여유     = ratio / 임계
```

**재현 검증**: 현행 설정으로 돌리면 최악이 `LeftArm 122도 배율 0.35 → 1.0461`. 테스트가 로그에
찍는 값 **1.046**과 일치한다. 아래 숫자는 전부 같은 코드가 낸 것이다.

| 팔꿈치 | 팔 여유(배율 0.35) | **전체 최악 여유** | 그때의 병목 |
|---|---|---|---|
| 122 (현행) | 1.0461 | **1.0461** | LeftArm 122° |
| 116.55 | 1.1682 | 1.1682 | ← 여기서 병목이 다리로 넘어간다 |
| 110 (구현 담당 안) | **1.3253** | **1.1682** | LeftLeg 126° |
| **98 (제안)** | **1.6497** | **1.1682** | LeftLeg 126° |

> ★ **"110° → 1.53배"는 어느 식으로도 안 나온다.** 팔 자체의 여유는 1.3253이고, 전체 최악은
> 1.1682에서 다리에 막힌다. 리더는 이 숫자로 의사결정하면 안 된다. (1.53에 가까운 값은

**전체 안전 마진은 똑같이 1.168**이고, 둘의 차이는 오직 **그림**이다. 그래서 그림이 이기는
98°를 고른다.

리더가 3안(현상 유지)을 고를 수도 있으므로 **깨짐 지점을 전부 수치로 못 박아 둔다.**
현행 여유 1.0461은 아래 값 중 **하나만** 이 수치를 넘으면 즉시 1.0 아래로 떨어진다.

| 흔들면 깨지는 것 | 현재 | **깨짐 지점** | 여유 |
|---|---|---|---|
| `LimbCurveRenderer.FilletLengthRatio` | 0.42 | **0.4015 미만** | 이번 라운드 직전 값 **0.35로 되돌리면 즉시 위반**(여유 0.872) |
| `StickConfig.MinStrokeScreenPoints` | 2.00pt | **2.092pt 초과** | +4.6%pt만 올려도 깨진다 |

같은 표가 이렇게 바뀐다 — `FilletLengthRatio` **0.3595 미만**, `MinStrokeScreenPoints` **2.336pt 초과**
(전체 최악이 다리 1.168로 넘어가므로 다리 기준). **여유가 좁아서 위험한 게 아니라, 여유가 좁은
쪽이 하필 "그림도 틀린 쪽"이라서 지킬 이유가 없다.**

### 13-8. 액세서리(모자)와의 상호작용 — **미확인 / 교차 확인 필요**

캡처 속 캐릭터는 밀짚모자를 쓰고 있고, 머리 장식은 `sortingOrder 6`으로 **팔(2)보다 위**에 그려진다
(`Interaction/CharacterAccessoryRenderer` — 33-2-0 레이어 재배치표: 망토 2 / 머리 6).

- 이 사양은 **맨머리 기하(머리 원 0.19337)를 기준으로 확정한다.** 그것이 42종 액세서리와 무관한

- 모자 챙의 실제 외곽 반지름은 **재지 않았다(미확인).** 판단하려면 그 값이 필요하다.

## 14. [M6] "Dock에서 매달리기 0회는 정답인가" — **조건부 동의. 기전은 옳고 결론은 배율 조건부다**

### 14-0. 판정 4줄

1. **구현 담당의 기하학 증명은 옳다.** `낙차 ≥ LedgeHangDropDepth`는 튜닝 임계값이 아니라
   "매달린 발이 아래 발판을 파고들지 않는다"는 **불변식 그 자체**다. 낮추면 안 된다. **동의.**
2. **그러나 "Dock 낙차 = 0.72 H"는 배율 1.0 가정이고, 그래서 "0회"는 보편 명제가 아니다.**
   실제 배율에서 다시 재면 0.75에서 **0.96 H**, 0.60에서 **1.20 H**다. 임계는 **1.1022 H**이므로
   **배율 0.653 아래에서는 Dock 턱이 매달리기 밴드로 넘어간다.** **부분 반증.**
3. **실측이 그것을 증명한다** — 지금 떠 있는 앱(배율 **0.60**)의 로그에서 **Dock 모서리 매달리기가
   4회** 일어났다. "0회"는 배율 0.75 이상에서만 참이다.
4. 그래도 **리더의 사전 판단(올라가기와 내려오기를 분리하고, 새 자세를 만들지 않는다)은 옳다.**
   근거는 14-5 / 14-6에 적었고, **접힌 팔 매달림은 규칙 B 여유까지 계산해서 기각**한다(14-7).

### 14-1. 증명의 어느 부분이 옳은가

```
매달린 발 Y = 모서리 Y − LedgeHangDropDepth
진입 조건    = 목적지 발판 ≤ 매달린 발  ⟺  낙차 ≥ LedgeHangDropDepth
```
이 두 줄은 `StickmanBlackboard.LedgeHangMinDropDepth` 문서와 `LedgeHangState`의 불변식 그대로다.
**임계값을 낮추면 다리가 발판(창) 안으로 들어간 그림이 돌아온다** — 동의한다. 여기는 손대지 마라.

`LedgeHangDropDepth`도 실측으로 확인했다(프리팹 정방향 계산):

```
reach = 어깨y(1.3235208) + 위팔(0.285)·|cos 169°| + 아래팔(0.2775)·|cos 177°|   [매달리기 자세: 팔 180∓11°, 팔꿈치 8°]
      = 1.3235208 + 0.279764 + 0.277120 = 1.880405 (로컬)
      = 전신높이 1.7060208 의 1.10222배  →  LedgeHangDropDepth = 1.1022 H  ✓
로그 대조: 배율 0.60 → 1.880405 × 0.8 = 1.5043유닛,  로그 "손끝~발끝=1.504유닛"  ✓
```

### 14-2. 어디가 틀렸나 — H가 배율을 안 탔다

`Dock 낙차 = 0.72 H`는 `1.637 ÷ 2.2747(= BaselineCharacterTotalHeight)`인데, **분모가 배율 1.0의
신장**이다. 런타임 신장은 `CharacterHeightWorld = 2.2747 × characterScale`이다.

| 배율 | 신장 | Dock 낙차 1.637유닛 | 임계 1.1022 H | 판정 |
|---|---|---|---|---|
| 1.00 | 2.275 | 0.72 H | 2.507유닛 | 뛰어내리기 |
| **0.75 (출하 기본)** | 1.706 | **0.96 H** | 1.880유닛 | 뛰어내리기 (**"0회"가 참인 구간**) |
| **0.65** | 1.479 | **1.11 H** | 1.630유닛 | **경계** |
| **0.60 (실측 세션)** | 1.365 | **1.20 H** | 1.504유닛 | **매달리기** |
| 0.35 (하한) | 0.796 | 2.06 H | 0.878유닛 | 매달리기 |

교차점: `1.637 / (1.1022 × 2.2746944)` = **0.6529**.

### 14-3. 코드가 이미 이 숫자를 알고 있다

`StickConfig.DockHopDownCriticalScale = 0.6531f` — 이름 그대로 "Dock 낙차가 **뛰어내리기 밴드에
남아 있으려면** 필요한 최소 배율"이고, 문서가 명시적으로 이렇게 적어 놨다:

> "★★ 이 값은 **금지선이 아니라 거동 분기점**이다. **아래에서는 Dock 단차가 '매달려 내려가기'로
> 분류될 뿐이고 그 자체는 기하학적으로 안전하다.**"

내 계산 0.6529와 일치한다(차이 0.0002 = 상수 반올림). **즉 "Dock에서 매달리기는 구조적으로
불가능"이라는 서술은 이 상수의 문서와 정면으로 충돌한다.** 실제로도 그렇다:

### 14-4. 실측 — 지금 떠 있는 앱에서 4회 일어났다

`/tmp/stickmate-run/stickmate.log` (배율 **0.60**, 17분 가동):

```
[크기] 캐릭터 배율 0.60× 적용 — 구워진 배율 0.750, 루트 스케일 0.800, 전신 높이 1.365유닛
[매달리기] 진입 — 모서리핸들=-2, 손끝~발끝=1.504유닛, 매달릴시간=1.40초, 내려갈발판=핸들 -3(Y=-11.804)
[매달리기] 모서리를 붙잡았습니다 — 매달린 몸 Y=-11.671 (모서리 Y=-10.167)
[매달리기] 손을 놓습니다 — 매달린 시간 1.42초, 낙하 시작 Y=-11.671, 예상 착지 Y=-11.804
```

- `모서리핸들 = -2` = **Dock** (`[Dock계단] 윗면 y=-10.167`).
- **매달리기 진입 4회 / 벽타기 진입 4회** — 내려가기와 올라오기가 짝을 이룬다.
- **뛰어내리기(HopDown) 0회.** 이 배율에서는 Dock 턱이 통째로 매달리기 밴드다.
- 연속 캡처에서도 잡았다: 걷다가 → 두 팔을 위로 들고 → 몸이 Dock 아래로 가라앉는 4프레임.

> **그러므로 MOTION_SPEC 1절 표 #5의 "매달리기 0회"는 취소한다.** 그 관측은 배율 1.0(또는 0.75)
> 세션의 것이었고, 이 라운드의 실측 세션(0.60)에서는 정반대다. 1절에 정정 박스를 넣어 뒀다.

### 14-5. 그럼에도 리더의 분리는 옳다 — 올라가기와 내려오기는 다른 밴드다

코드가 두 경로를 완전히 분리해서 소유한다:

| 방향 | 상태 | 진입 판정 | 로그 태그 |
|---|---|---|---|
| **올라감** | `ParkourClimbState` | `되올라가기 결정 — 턱 높이 1.637유닛(상한 2.40)` | `[되올라가기]` `[벽타기]` |
| **내려옴** | `LedgeHangState` / HopDown | `TryFindDescendTarget(minDrop…)` | `[매달리기]` |

두 판정은 서로를 참조하지 않고, 로그에서도 독립적으로 발화한다(같은 세션에서 벽타기 4회 /
매달리기 4회가 서로 다른 프레임에서). 사용자 신고 문장은
**"독을 올라갈 때 손으로 짚고 다리를 올려서 올라가야지"** — **올라가는 쪽**이다.
**매달리기를 손대는 것은 그 신고에 대한 응답이 아니다.** 리더 판단에 동의한다.

### 14-6. 내려오는 그림은 어설픈가 — 판정: **자세는 정상, 박자에 결함 1건**

연속 캡처에서 본 것(배율 0.60, Dock 왼쪽 모서리):

- **자세는 맞다.** 걷다가 모서리에서 두 팔이 위로 뻗고 몸이 아래로 가라앉는다.
  `LedgeHangHandAlignmentTests`가 잠근 "손이 모서리에 붙는가"는 그림에서도 지켜진다.
- **놓은 뒤 낙하가 0.13유닛(= 0.095 H, 화면 3pt)** 이다. 이건 **결함이 아니라 설계다** —
  임계가 "발이 목적지를 지나치지 않음"이므로 임계 근처 낙차에서 낙하는 정의상 0에 수렴한다.
  매달리기의 목적은 **낙하를 없애는 것**이지 낙하를 보여 주는 게 아니다.
- **결함 1건 — 흔들림이 한 왕복을 못 채우고 끝나는 구간이 있다.**

```
매달리는 총 시간 = ledgeHangGrabDuration(0.28) + hold[0.55 ~ 1.50]
흔들림           = sin(2π × 0.9Hz × t),  ResetHangPhase()로 t=0에서 시작
왕복 수 = 0.9 × (0.28 + hold)
  hold 0.55(하한) → 0.747 왕복   ← 한 번 기울었다가 **되돌아오기 전에 손을 놓는다**
  hold 1.09(실측) → 1.233 왕복   ○
  hold 1.40(실측) → 1.512 왕복   ○
  hold 1.50(상한) → 1.602 왕복   ○
```

"대롱대롱"으로 읽히려면 **최소 한 왕복**이 필요하다. 지금은 난수 범위의 아래쪽 **약 30%**
(hold < 0.831초)가 그 조건을 못 채우고, 그 구간에서는 **기운 채로 손을 놓아** 낙하 시작 자세가
비대칭으로 튄다(진폭 5°라 크지는 않다).

> **처방(상수 1개, 코드 무변경)**: `ledgeHangHoldDurationMin` **0.55 → 0.84초**
> (검산: 0.9 × (0.28 + 0.84) = **1.008 왕복** — 하한에서 정확히 한 왕복을 채운다.
> 상한 1.5는 그대로 두면 1.602 왕복. 상태 최대 수명 `ledgeHangMaxDuration = 3`은 여유가 남는다:
> 0.28 + 1.50 = 1.78 < 3.)
> **우선순위 낮음** — 실측된 두 사례(1.09 / 1.40)는 둘 다 정상이었다. 난수 하한만 막는 예방이다.

### 14-7. 접힌 팔 매달림(tucked hang) — **기각. 규칙 B는 막지 않는다, 다른 셋이 막는다**

리더가 요구한 대로 **규칙 B 여유까지 계산했다.** 결론부터: **규칙 B는 이 안을 막지 않는다.**

배율 0.75(출하 기본)에서 Dock 턱을 매달리기 밴드로 끌어오려면
`reach ≤ 1.637`이어야 하고, 팔꿈치 굽힘 `e`에 대해

```
reach(e) = 1.3235208 + 0.285·|cos 169°| + 0.2775·|cos(169° + e)|
reach(94°) = 1.3235208 + 0.279764 + 0.033715 = 1.637   ← 필요한 굽힘은 94°
규칙 B 여유(팔꿈치 94°, 배율 0.35) = 1.771   ← 통과. 여유 있다.
```

그런데도 만들면 안 되는 이유 셋:

1. **손이 모서리에서 떨어진다(계약 위반).** 팔꿈치 8°에서 손끝의 가로 오프셋은 어깨 기준
   **+0.0689**인데, 94°에서는 **−0.2211**로 **부호가 뒤집히고 크기가 3.2배**가 된다.
   두 손 사이가 0.442유닛(신장의 26%)으로 벌어져 **모서리 X에 붙지 않는다.**
   `Tests/PlayMode/LedgeHangHandAlignmentTests`가 잠근 계약이 바로 여기다.
   즉 상수 하나짜리 변경이 아니라 **X 정렬 유도까지 다시 만드는 작업**이다.
2. **낙하가 정확히 0이 된다.** 정의상 `reach = 낙차`로 맞추는 것이므로 손을 놓는 순간
   발이 이미 바닥에 닿아 있다. 이미 이 문서 5-3절이 못 박은
   **"낙차 0이면 그건 뛰어내리기가 아니다"** 와 같은 병을 매달리기 쪽에 새로 만드는 것이다.
3. **자세의 의미가 바뀐다.** 팔꿈치 94°로 접은 매달림은 **턱걸이 정점 자세**지 대롱대롱이 아니다.
   `UX_FLOW.md` 4절이 정의한 매달리기는 "팔이 완전히 펴진 채 대롱대롱"이다.
   1.4초 동안 턱걸이 정점을 버티는 사람은 없다 — **정지 화면으로 남는 자세로 부적합**하다.

**대안이 필요하다면 매달리기가 아니라 HopDown 쪽이다.** 배율 0.75(출하 기본)에서 Dock 턱은
**HopDown 밴드에 정확히 들어가 있고**, 그 구간의 연출 요구사항은 이미 이 문서 **5절(R1~R4)** 에
적혀 있다(모서리 멈칫 / 발끝이 모서리 밖 / 결정 재발화 억제 / 무한 왕복 억제).
**새 자세를 만들 이유는 지금 없다.** 리더 판단에 동의한다.

### 14-8. 덤으로 실측된 것 (조치 대상 아님, 기록용)

- **행동-텍스트 싱크(원칙 1) 위반 사례 1건 추가 실측**:
  `[말풍선] 표시 (LedgeHang) "여기로 내려가자"` → `제거 — 노출 1.50초`인데
  같은 구간의 `[매달리기]`는 **1.10초**였다. 대사가 상태보다 **0.40초 더 살아**,
  손을 놓고 낙하해 착지가 끝난 뒤까지 "여기로 내려가자"가 떠 있었다.
  → 이 문서 **3-3/3-4절(DialogueKind + 발화 자격 게이트)** 이 이미 처방한 그 결함이다. 새 사양 불필요.
- `[말풍선] 표시 (ParkourClimb) "가뿐하네"` 노출 **0.82초** = 최소 노출 하한 그대로.
  `parkourClimbDuration = 1.05`이므로 대사가 상태보다 **0.23초 먼저 사라진다.**
  → 3-4절 게이트(필요체류 0.68초)는 통과하지만, **Narrative는 상태 끝까지 살아야 한다**는
  C3 계약과는 어긋난다. 3-3절 구현 시 이 케이스를 회귀 표본으로 쓸 것.
- 주위 살피기 **진입 램프**에서 팔이 0.2초쯤 **앞으로 수평으로 뻗은 상태**를 지난다
  (env 중간값에서 어깨≈53°/팔꿈치≈66°). 캡처 2프레임에서 확인. 98°로 바꿔도 이 구간은
  거의 동일하다(어깨 53°/팔꿈치 54°). **조치 제안 없음** — 기록만 남긴다.

### 14-9. 미확인으로 남긴 것

- **매달린 몸 전체의 그림은 확인하지 못했다.** 캡처 띠(OS y 782~962pt)가 매달린 발
  (약 968pt)보다 위에서 끝나서 하반신이 잘렸다. 전체 화면 캡처가 필요하다.
- **모자 챙의 외곽 반지름을 재지 않았다**(13-8). 그것 없이는 "모자를 쓴 채 손차양이 보이는가"를
  판정할 수 없다.
- **다른 배율에서의 실측은 없다.** 위 표의 0.75 / 1.00 행은 전부 **계산**이고, 실측 로그는
  **배율 0.60 하나뿐**이다. 리더가 판정을 굳히려면 배율 0.75에서 한 세션이 필요하다.
- **Dock 타일 크기가 다른 환경은 확인하지 않았다.** `stepUpMaxHeight` 문서의 실측대로 Dock 낙차는
  0.83~3.57유닛으로 4배 넘게 변하고, 그러면 위 교차 배율도 **0.331~1.423**으로 함께 움직인다
  (`DockHopDownCriticalScale` 문서). 즉 **"큰 Dock를 쓰는 사용자는 배율 1.0에서도 매달린다."**

## 17. [R2-M1] 매달리기 — **"놓은 뒤 보이는 낙차"의 사양** ★최우선

### 17-0. 결론 5줄

1. **몰입 담당의 실측이 옳다.** 놓은 뒤 낙차 = `총낙차 − 1.10222 H`이고, 임계가 그 값 자체이므로
   **밴드 시작점에서 정의상 0이다.** 실기(s=0.60) 실측 **0.133유닛 = 5.44pt = 0.0974 H**.
2. **그 5.44pt는 정강이 획 두께(3.08pt)의 1.77배다.** 화면에서 이건 "낙하"가 아니라 **선 두 개 두께**다.
   더 나쁜 것은 아래(17-2): 이 낙차는 **앱 자신이 "착지가 아니다"라고 판정하는 구간**이라
   무릎도 안 굽고 먼지도 안 나고 착지 연출 상태에조차 들어가지 않는다.
3. **처방 방향(임계를 올리고 HopDown이 흡수)에 동의한다.** 임계를 내리면 다리가 창을 파고든다(14-1).
4. **사양: 놓은 뒤 보이는 낙차 `G ≥ 0.50 H`.** 하드 플로어(이 아래로는 절대 내리지 말 것)는 **0.35 H**.
   → 새 임계 `LedgeHangMinDropDepth = 1.60222 H`.
5. **리더의 "경계 배율 약 0.51"은 틀렸다 — 여유 0.5 H면 0.4493이다.** 0.51은 여유 0.30 H에 해당한다.
   어느 쪽이든 **배포 0.75와 저장값 0.60은 둘 다 뛰어내리기로 정리된다**(목적 달성).

### 17-1. G는 하나의 값이다 (두 개를 재는 것이 아니다)

```
매달린 발 Y   = 모서리 Y − 1.10222 H
목적지 바닥 Y = 모서리 Y − 총낙차 D
∴ 매달린 발 밑의 공기 = D − 1.10222 H = 놓은 뒤 낙하거리 = G
```
**"매달렸을 때 발밑에 보이는 틈"과 "손 놓고 떨어지는 거리"는 같은 숫자다.** 그래서 사양이 하나다.

### 17-2. G의 하한을 정한 세 개의 독립 기준 (전부 이 저장소 안의 값)

| # | 기준 | 임계 | 근거 |
|---|---|---|---|
| C1 | **앱이 "착지했다"고 인정하는 최소 낙차** | **0.35 H** | `landingSoftAbsorbThresholdHeights`. 이 아래는 `LandingCrouchState`에 **진입조차 안 한다**(T0=무반응). 지금의 0.0974 H는 그 27.8%다 — **놓아도 아무 일도 안 일어난다** |

| C3 | **정지 프레임에서 틈이 틈으로 보임** | **≈0.11 H**(획 두께 ×2) / **≈0.22 H**(×4) | 다리 획 0.055128 H |

## 18. [R2-M2] 등반 박자 — **툴팁의 모순은 "하한이 하나뿐"이라서 생겼다**

### 18-0. 판정 4줄

1. **모순은 실재한다.** `parkourClimbDuration` 툴팁의 "가장 짧은 박자(뻗기 0.18)"는 **거짓**이다 —
   실제로 가장 짧은 것은 정착(0.12)이고 매달림(0.16)·맨틀(0.14)도 뻗기보다 짧다.
2. **그러나 0.19초 하한 자체는 폐기하지 않는다. 적용 범위가 틀렸을 뿐이다.**
   네 박자는 **같은 종류가 아니다** — 두 개는 동작(action), 하나는 정지(hold), 하나는 블렌드아웃이다.
   하나의 하한을 넷에 다 대면 반드시 모순이 난다.
3. **진짜로 하한 미달인 박자는 하나뿐이다: 맨틀 0.147초.** 그리고 그게 하필
   **사용자가 요청한 "올라섰다"의 그림**이다.
4. **1.36초 균일 확대는 기각. 1.20초 재분배를 권장한다**(18-3). 등반 대사는 재검산했고 **전부 통과**.

### 18-1. 박자 종류별 하한 (이것이 이 절의 산출물)

| 종류 | 하한 | 근거 |
|---|---|---|
| **동작(action) 박자** | **0.19초** | 24fps 2컷 홀드(4드로잉)=0.167초가 고전 하한, 여기에 여유. 기존 툴팁이 이미 약속한 값이라 유지 |
| **정지(hold) 박자** | **0.17초** | 24fps 4프레임. 이보다 짧은 정지는 "멈췄다"가 아니라 "느려졌다"로 읽힌다 |
| **블렌드아웃(settle)** | **0.12초** | 포즈 스무더 수렴. 다리 rate 44(τ=0.0227초) → 5.3τ=99.5%, 팔 rate 24.2(τ=0.0413) → 2.9τ=94.5%. 정착 구간의 팔 각도차는 62°이므로 잔차 3.4° — 무시 가능 |

**네 박자의 분류(코드로 확인한 것이지 명명이 아니다):**
- 뻗기 = **동작**. `reachW`가 0→1로 그립 IK를 켠다.
- 매달림 = **정지**. `reachW`는 이미 1이고 `pullW`는 아직 0 → **팔다리 목표가 하나도 안 바뀐다.**
  움직이는 것은 `sag`뿐(상승량 0.02→0.10 = 총 상승의 8%). **정의상 hold다.**
- 당기기 = **동작**(가장 긴, 사용자가 콕 집은 박자).
- 맨틀 = **동작**(`mantleW` 0→1, 두 다리가 턱 위 스탠스로 모인다 = "올라섰다"의 그림).
- 정착 = **블렌드아웃**(`settleW`가 전부 Idle 중립으로 되돌린다).

(0.8917−0.6583)×1.20=0.280 / (1−0.8917)×1.20=0.130. 합 1.200 ✓

### 18-4. 왜 1.36초 균일 확대를 기각하는가

오늘의 비율을 유지한 채 맨틀을 0.19초로 만들려면 `0.14 × D = 0.19` → **D = 1.357초**가 맞다.
그러면 **당기기가 0.543초가 되어 맨틀의 2.9배**가 된다. 실제 등반에서 풀업과 맨틀(누르고 일어서기)은
**비슷한 길이**이고, 맨틀 쪽이 오히려 느린 경우가 많다. 2.9:1은 **틀린 박자를 강조**한다.
1.20초 안은 그 비를 **1.43:1**로 만들면서 총 길이는 14%만 늘린다.

또 하나: 1.357초는 **오늘 값 전체를 29% 느리게** 만든다. 등반 상승 속도(Dock 67pt)는
1.05초에서 64pt/s → 1.20초에서 56pt/s → 1.357초에서 49pt/s인데, 보행이 61pt/s(s=0.60)다.
**1.20초는 아직 보행과 같은 급이고, 1.357초는 눈에 띄게 느려진다.**

### 18-7. 검증한 가설 1건 (기각 — 기록용)

**"적응형 프레임 절감이 등반 박자를 잡아먹는가?"** 실기 로그에

## 19. [R2-M3] 착지 램프 — **리더가 지목한 필드가 틀렸다** + 채택 조건

### 19-0. 판정 4줄

1. **"363pt 이상이 전부 같은 그림"은 참이다.** s=0.60에서 화면의 **62%**가 한 단계다.
2. **그러나 `landingCollapseThresholdHeights`를 올려도 아무 일도 일어나지 않는다.**
   그 필드는 버팀 램프에 **연결되어 있지 않고**, 게다가 `landingCollapseEnabled=false`라
   읽히지도 않는다. 램프의 knob은 **`landingCrouchBraceTailHeights`**다.
3. **취지는 채택.** 값은 15 H가 아니라 **포화 11.00 H**(= braceTail **7.10 H**)를 권장한다 — 근거 19-3.
4. **★ T4를 미루는 처방이 아니다. T4와 한 세트여야 한다.** 램프를 늘리면 포화점 위가
   **다시** 무차별 구간이 되고(s=0.60에서 화면의 37%), 그건 T4만이 메울 수 있다(19-4).

### 19-1. 필드가 틀렸다는 증명 (`LandingCrouchState.Enter()` 원문)

```csharp
float braceSpan = cfg.landingCrouchBraceTailHeights;                          // 2.60
float u = Mathf.Clamp01((HeightsFallen - (reaction + deepSpan)) / braceSpan);  // 포화 = 0.88+3.02+2.60 = 6.50
_duration = ... + u * (brace - deep);      // 0.62 -> 0.88
_holdFraction = Mathf.Lerp(holdBase, holdBrace, u);
_torsoPitchDegrees = ... + u * (pitchBrace - pitchDeep);
```
```csharp
private static LandingTier ResolveTier(...)
{
    float collapse = cfg.landingCollapseThresholdHeights;      // 6.50
    bool collapseEnabled = cfg != null && cfg.landingCollapseEnabled;   // 에셋 = false
    if (collapseEnabled && heightsFallen >= collapse) return LandingTier.Collapse;
    ...
}
```
`landingCollapseThresholdHeights`는 **`ResolveTier` 안에서만**, 그것도 **`collapseEnabled`가 true일 때만**
쓰인다. 6.50 → 15로 올리면 **거동 변화 0**이다. 6.50이라는 숫자가 두 곳에 같이 있는 것은
`0.88+3.02+2.60 = 6.50`이라는 **우연한 일치**이지 연결이 아니다.

### 19-2. 늘리기는 완화이지 해결이 아니다 — 몇 단계짜리인지 계산했다

버팀 램프의 살아 있는 출력은 셋뿐이고, 그 **총 분해능은 약 4단계**다:

| 출력 | 범위 | 변별 한계(JND) | 단계 수 |
|---|---|---|---|
| 지속 | 0.62 → 0.88초 | 시간 Weber 비 ≈9% | `ln(0.88/0.62)/ln(1.09)` = **4.1** |
| 상체 앞기울기 | 22 → 30° | 막대 실루엣 각도 ≈3° | **2.7** |
| hold 비율 | 0.24 → 0.40 | 지속에 종속(별도 채널 아님) | — |
| **깊이** | **1.00 고정** | — | **0** (기하학적 상한) |
| **먼지** | **3.88 H에서 이미 포화** | — | **0** (`landingDustFullHeights=3`) |

**늘려도 단계가 늘지 않는다. 단계의 위치만 옮긴다.**
braceTail 2.60 → 한 단계당 0.65 H / 7.10 → 1.78 H / 13.54 → 3.39 H.
그러므로 **"상위 62%가 한 그림"이 "전 구간이 4단계"로 바뀌는 것이지 "무거움이 계속 자란다"가 되지 않는다.**
질적으로 다른 실루엣(T4)이 **한 개** 생기는 것이 이 램프를 3배 늘리는 것보다 정보량이 크다.

### 19-3. 확정 사양

  — 즉 배포 기본값에서 "최상단 단계 없음"이 **그대로 남는다**.
- **11.00은** 가장 큰 캐릭터가 화면 꼭대기에서 떨어졌을 때 버팀을 **92.4%까지** 채우고 절대 무너지지 않는다.

### 19-4. T4 질문에 대한 답 — **영영 안 만드는 것이 아니다. 이 처방은 T4의 자리를 만드는 것이다**

## 20. [R2-M4] Fall → LandingCrouch 팔 스윙 — **확인. 단 기전 3곳을 정정한다**

육안 캡처는 못 얻었다(20-4). 대신 **포즈 스무더를 프레임 단위로 수치 적분**해 답한다 —
`SmoothTo`는 `LerpAngle(cur, tgt, 1−e^{−rate·dt})`이고 목표각은 전부 상수라 **재현이 정확하다**.

### 20-1. 정정 3건

| # | 리더 전제 | 실제 | 영향 |
|---|---|---|---|
| 1 | 스무딩 48 → **τ=0.021초** | `ApplyLimb`이 **팔에는 `baseRate × ArmSmoothingRatio(0.55)`**를 쓴다 → 팔 어깨 **26.4/s(τ=0.0379초)**, 팔꿈치 **19.8/s(τ=0.0505초)**. 다리만 48(τ=0.0208) | 팔은 **중립을 못 찍는다** — 60ms에 중립까지의 49~52%까지만 간다 |
| 2 | "팔이 위→옆→앞뒤로 두 번 꺾인다" | **앞팔은 깨끗하다**(143°→64°, 되돌림 ≤0.8°). 꺾이는 것은 **뒷팔 하나** | 결함 범위가 절반 |
| 3 | (언급 없음) | **낙차 의존적이다.** 되돌림 = 0°(hH<1.6) / 6.4°(2.0) / **19.5°(3.0)** / 33.0°(3.9) / **38.8°(≥6.5 포화)** | **자율 행동(Dock 1.20 H)에서는 발생하지 않는다** |

### 20-2. 실제로 일어나는 일 (수치 적분, s 무관 — 전부 각도)

시작 = 낙하 자세 수렴값(팔 만세 ±143°, 팔꿈치 20°). 낙하 세기는 1.14 H만 떨어져도 1.0이 되므로
(`fallPoseFullSpeedHeightsPerSecond=7`) Dock 낙차에서도 이미 만세다.

```
뒷팔 어깨각 (hH=17.44, 60fps)
  t=0     -143.0   ← 만세
  t=33ms   -91.6
  t=50ms   -89.1   ← 극점(수평 뒤). 여기서 방향이 뒤집힌다
  t=83ms   -99.3
  t=150ms -121.0
  t=250ms -127.5   → 최종 -128.0 (무릎앉아 뒷팔)
  ⇒ 앞으로 53.9° 갔다가 38.8°를 되돌린다 = 그만큼이 헛걸음이다
```
**원인은 정확히 리더가 지목한 그 줄이다.** `LandingCrouchState.Enter()`가 `CurrentCrouchAmount = 0`으로
시작하고, `ApplyLandingCrouchPose(amount=0)`은 **Idle 중립(뒷팔 −40°)**을 목표로 준다.
그런데 들어온 자세는 −143°이고 갈 곳은 −128°다 — **15°만 움직이면 되는데 103° 떨어진 목표를 향해 출발**한다.
`amount=0`의 의미가 "지금 자세"가 아니라 "Idle"인 것이 결함의 전부다.

**다리에도 같은 결함이 있다(낙차 무관, 전 구간):**
`앞엉덩이 29.0° → 19.6°(1프레임) → 26.4 → 38.0 → …` — **첫 프레임에 9.4° 반대로 내려갔다가 올라간다.**
다리는 rate 48(τ=20.8ms)이라 **한 프레임 안에 목표를 거의 찍으므로 틀린 목표 = 틀린 그림 1장**이다.
30fps에서는 이 1장이 33ms 동안 화면에 남는다.

### 20-3. 처방 — **진입 블렌드를 "압축 구간에 상대적으로" 건다** (coder 인계)

고정 시간상수(τ=0.05초 등)는 **틀린 답이다**: T0.5 착지는 압축 구간이 0.034초라 블렌드가
압축 전체를 덮어 무릎앉아가 안 나온다. 압축 구간에 비례시켜야 한다.

```
ApplyLandingCrouchPose(…, float entry01)      // 0 = 오늘과 100% 동일(네거티브 컨트롤)
   목표각 = LerpAngle( 오늘의목표(amount), 낙하자세각, entry01 )

LandingCrouchState.Tick:
   float compressSpan = landingCrouchCompressFraction * _duration;
   float u = Mathf.Clamp01(_elapsed / compressSpan);
   float entry01 = 1f - (u*u*(3f-2f*u));       // 1 - smoothstep, 압축이 끝나면 정확히 0
```
`entry01(0) = 1` 이므로 **착지 첫 프레임의 목표각이 들어온 자세와 정확히 같다** —
전이가 **구성상 C0 연속**이 된다(스무딩에 기대는 것이 아니라).

| hH | 뒷팔 현행 | 뒷팔 개정 | 앞엉덩이 첫프레임 딥 현행 | 개정 |
|---|---|---|---|---|

## 21. 곁가지 — `LightClimbHeights = 0.95 H`의 실기 분포 (배율 축 포함)

### 21-1. 툴팁 문장은 **모든 배포 배율에서 거짓이다**

> "Dock 단차(0.72H)는 이 아래라 가볍게 읽힌다."

| 16 | 영차 | 가뿐 | 가뿐 | 가뿐 | 가뿐 |
| 32 | 영차 | 영차 | 가뿐 | 가뿐 | 가뿐 |

★ **임계 0.95 H가 tilesize 48과 49 사이에 정확히 끼어 있다**(0.9455 / 0.9596).
**macOS 기본 Dock(48)과 이 개발 머신(49) 사이 1px 차이로 대사가 갈린다.**
"1.0% 차이"라는 리더의 지적은 맞고, 원인은 **분포의 최빈값 한복판에 경계를 세운 것**이다.

### 21-2. 원칙 — **경계를 분포의 최빈 구간 안에 세우지 않는다**

배포 배율 0.75에서 Dock 낙차의 분포는 **0.487 H(t16) ~ 2.092 H(t128)**이고, 실사용 최빈 구간은
tilesize 48~64 = **0.945 ~ 1.175 H**다. 따라서 경계는 **[0.90, 1.25] H 바깥**에 있어야 한다.
지금의 0.95는 그 안에 있다. (2.2 H 경계는 밖이므로 문제없다.)

### 21-3. 권고 (판단값을 몸의 기하로 교체)

```
LightClimbHeights  0.95  ->  0.4109   (= 엉덩이 높이. "손 안 쓰고 그냥 올라설 수 있는 턱")
HardClimbHeights   2.20  ->  1.1022   (= 손끝~발끝 = LedgeHangDropDepth. "서서 손이 안 닿는 턱")
```
- 두 값 모두 **프리팹에서 유도되는 실재하는 높이**라 판단값이 아니다. 배율/tilesize/OS가 바뀌어도
  의미가 그대로다(Windows 작업표시줄에서도 같은 문장이 성립한다 — 이게 진짜 플랫폼 중립이다).
- 0.4109는 최빈 구간(0.90~1.25 H) **아래**, 1.1022는… **그 안이다**(t=59 부근). **여기가 남는 문제다.**
  → 대안: `HardClimbHeights`를 **자율 등반 상한 대비 비율**로 바꾼다
  (`오를 높이 / AutoWanderController.ResolveStepUpMaxHeight() ≥ 0.85`).
  그러면 tilesize ≤65 → "영차", ≥66 → "헉"으로 갈리고 경계가 분포 최빈 구간 밖으로 나간다.
  **둘 중 어느 쪽을 택할지는 리더 판단**이다(전자는 의미가 예쁘고, 후자는 경계가 안정적이다).

### 21-4. 함께 발견한 것 — `stepUpMaxHeight`만 아직 절대 유닛이다 (★ 신규)

`stepUpMaxHeight = 2.4` **월드 유닛**이고 배율을 안 탄다. 신장 배수로 환산하면:

| 배율 | 자율 등반 상한 |
|---|---|
| 1.00 | 1.06 H |
| 0.75 | 1.41 H |
| 0.60 | 1.76 H |
| **0.35** | **3.01 H** |

**작은 캐릭터가 자기 키의 3배를 1.05초에 기어오른다.** 이건 등반 자세가 아무리 좋아도
"순간이동"으로 읽히는 조건이고, 이 필드의 툴팁이 스스로 경계한 그 실패 모드다
("높이와 무관하게 parkourClimbDuration에 올라가므로, 높은 벽까지 자동으로 오르게 두면 순간이동처럼 보인다").
→ **권고: 상한을 `max(H 배수 상한, 실측 Dock 낙차 + 0.30)`로 바꾼다.** H 배수 상한은
`1.1022 H`(= 서서 손이 닿는 높이)가 자연스럽다. **우선순위 중** — 배율 하한 쪽에서만 나타난다.
(★ 미확인: 실제로 그 배율에서 순간이동으로 보이는지 육안 확인은 못 했다.)

## 23-4. 조치안 — **임계값을 올리지 않는다. 교차 배율 3개를 이름 붙여 노출한다**

리더 지시대로 `landingReactionThresholdHeights`(0.88)는 **한 톨도 건드리지 않는다.**
`DockHopDownCriticalScale`(0.4493)이 이미 만들어 둔 패턴을 그대로 확장한다.

| 제안 상수 | 값 | 뜻 | 유도식(테스트가 매 실행 재계산) |
|---|---|---|---|
| `DockSoftAbsorbCriticalScale` | **2.0568** | 이 배율 **이하**면 Dock이 T0.5 이상 | `DockDrop / (landingSoftAbsorbThresholdHeights × Baseline)` |
| `DockKneelCriticalScale` | **0.8180** | 이 배율 **이하**면 Dock이 T1(무릎앉아 램프) | `DockDrop / (landingReactionThresholdHeights × Baseline)` |
| `DockSitDownCriticalScale` | **0.3473** | 이 배율 **이하**면 Dock에서 **실제로 앉는다**(몸하강 12 %H) | `DockDrop / (2.073 × Baseline)` |

**이 세 줄이 한눈에 말해 주는 것**(리더가 원한 "한 줄로 드러난다"):

- `DockSoftAbsorbCriticalScale 2.0568 > MaxCharacterScale 1.00`
  → **Dock은 어떤 배율에서도 무반응(T0)이 아니다.** (T0.5 이상 보장)
- `DockKneelCriticalScale 0.8180 < MaxCharacterScale 1.00`
  → **출하 기본(0.75)과 사용자 설정(0.60)은 T1 쪽이다.** 이게 "정상"임을 계약으로 못 박는다.
- `DockSitDownCriticalScale 0.3473 < MinCharacterScale 0.35`
  → **어떤 배율에서도 앉지 않는다.** 여유 **0.0027(0.8%)** — 이 줄이 벼랑을 계속 보이게 한다.

  또는 컷 대신 **0.30초까지는 남긴다**. ★ 어느 쪽이 옳은지는 원칙 1이 정한다 —
  **상태가 이미 끝났으면 남기면 안 되므로 "표시하지 않는다"가 맞다.**
- `[격파]`의 결과 축은 **이미 고쳐져 있다.** 로그가 스스로 판정한다:
  *"판정이 아니라 중단이므로 대사는 없습니다"*. R1의 M1(50/50 "필살기다!")은 **해소 확인**.

**macOS 영향: 있음.** 이 절의 모든 실측(로그 111.1분 2인스턴스, 연속 캡처 74프레임 + 전체화면 1장, Dock tilesize 49)은
macOS 빌드 기준이다. 다만 **바꾸자고 제안한 것은 전부 플랫폼 중립 위치**(`Core/`·`States/`·`Tests/`)이며
`Platform/MacOS/` 아래 파일은 **한 줄도 읽거나 건드리지 않았다.** 23-1의 기전 가설이 지목한
`Platform/DockPhysicsStep.cs`는 **플랫폼 중립 파일**(`Platform/` 직하)이다.

**Windows 영향: 별도 배정 필요(사유: 사용자 지시 "윈도우는 일단 미루고 맥만", 그리고 교차 배율이 다르다).**
- 새 `#if UNITY_STANDALONE_*` 분기 0건 → 크로스 컴파일할 대상이 없다.
- ★ **macOS 결론을 그대로 복사하면 안 된다.** 위 교차 배율 3개는 전부 **Dock 낙차 1.6375유닛**을
  대입한 값이다. 작업표시줄 기준 교차 배율은 리더가 준 **0.4883**이며(macOS는 0.8180),
  같은 식에 넣으면 작업표시줄 낙차 ≈ `0.88 × 2.2746944 × 0.4883 = 0.977유닛`이 된다.
  그 값으로 다시 계산하면 **작업표시줄의 "앉기" 교차 배율 = `0.977/(2.073×2.2746944) = 0.2072`**
  → `MinCharacterScale 0.35`보다 **한참 아래**라 **Windows에서는 어떤 배율에서도 안 앉는다**(안전).
  반대로 **T0.5 진입 교차 배율 = `0.977/(0.35×2.2746944) = 1.2270`** > 1.00 → **Windows도 전 배율에서
  최소 T0.5는 난다**(무반응 아님). ★ 단 작업표시줄 낙차 0.977유닛은 **리더가 준 0.4883에서 역산한
  값이지 내가 실측한 값이 아니다 — 미확인.**
- Windows 라운드가 열리면 23-4의 상수 3개를 **작업표시줄 낙차로도 한 벌 더** 계산해 같은 표를 만들 것.

## 23-8. 미확인으로 남긴 것 (정직하게)
