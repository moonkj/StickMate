### 2-1. 먼저: 이건 1건이 아니라 **19건이다**

두 표를 전수 대조했다(`StickmanStateId` 27개 전부, 양쪽 다 27개 등록).

### 2-2. 뿌리는 **거짓 주석**이다

```
Core/StickMateDisplayNames.cs:6
  /// ★ enum → 사람이 읽는 한글 이름의 <b>유일한 생산자</b> — docs/UX_FLOW.md 36-13 #9/#10.
```

그리고 **같은 주석 8줄 아래**가 이렇게 적혀 있다:

> *"문자열 테이블을 창 안에 두면 그 순간 「화면에 쓰는 이름」과 「코드가 아는 값」이 두 벌이 되고,
> enum에 값이 하나 늘 때 화면만 조용히 옛 이름으로 남는다"*

**그 상태가 이미 성립해 있다.** `CharacterInfoWindow.StateLabel`이 정확히 "창 안의 문자열 테이블"이다.
자기가 막겠다고 선언한 것이 자기 옆에서 이미 일어나 있는데, 주석은 "유일한 생산자"라고 말한다.

### 2-3. **정본 판정 — 어휘는 `StateLabel`, 거처는 `StickMateDisplayNames`**

「사용자에게 무엇이 보이는가」 기준으로:

1. **노출 시간이 비교가 안 된다.** `StateLabel`은 정보창이 열려 있는 **내내** 모든 상태에 대해 보인다.
   `BusyText(state)`는 *"막힌 명령 타일을 실제로 마주친"* 순간에만 보인다.
   (다만 **둘 다 실제로 보인다** — 7개 Director가 전부 `current != Idle && current != Walk`면 무조건
   `Blocked(BusyText(current))`이고, `ActionCommandPopover`는 상태 전이 즉시 + 0.25초 폴링으로 사유를
   다시 쓴다. 즉 던져서 `ThrowTumble`이 도는 동안 타일에는 **"지금 공중 회전 중이라 못 해요"**,
   정보창에는 **"지금 · 날아가는 중"**이 동시에 떠 있을 수 있다. **둘 다 "지금"으로 시작해서 더 눈에 띈다.**)
2. **어휘의 성질이 다르다.** B는 *상태 서술*이고 A는 *기능 이름*이다 — "그라피티", "창 도둑", "블랙홀",
   "할일 알림"은 개발자가 쓰는 코드명이다. A의 어휘가 그런 이유는 **같은 클래스의 `SpectacleEventKind`
   표에서 낱말을 그대로 재사용**했기 때문인데, 스펙터클은 "무슨 기능인가"라 그게 맞고
   상태는 "지금 무엇을 하고 있는가"라 맞지 않는다.
3. **문법은 양쪽 다 통과한다.** "지금 날아가는 중이라 못 해요" 정상 / "지금 · 공중 회전 중" 정상.
   → 문법으로는 못 가른다. 그래서 1·2로 가른다.
4. **UX 정본 문서가 B를 표로 갖고 있다.** `docs/UX_FLOW.md` §45-0-5가 상태 27행을 **B의 문구 그대로**
   열거한다. A의 어휘는 어떤 UX 문서에도 표로 존재하지 않는다.

> **결론: 사용자에게 보여줄 낱말은 `CharacterInfoWindow.StateLabel` 쪽이 정본이다.
> 그러나 그 낱말이 살 집은 `StickMateDisplayNames`다.**
> 27행을 Core로 옮기고 `BusyText`가 거기서 파생되게 하면, `:6`의 "유일한 생산자"가 **참이 된다.**

### ★ 통합할 때 밟을 함정 (미리 적어 둔다)

- **Focus 4상태.** A는 `FocusStart/Complete/Cancelled/Nudge`를 전부 "집중 모드"로 **일부러 뭉갰다**.
  B의 낱말을 그대로 어간으로 쓰면 *"지금 집중 모드 완료 중이라 못 해요"*가 된다.
  → **어간형과 라벨형 두 접근자**가 필요하다. 한 배열로 합치려 하면 여기서 막힌다.
- **B는 "중"을 문자열에 포함**하고 A는 틀이 붙인다. 기계적 이사는 "중 중"을 만든다.
- 이건 문구 판정(`design-narrative`) + 화면(`ux-designer`) + 코드(`coder`) 3자 사안이다.

### 2-4. 이 라운드에 한 것

**코드는 안 고쳤다**(내 권한 밖이고, 통합안이 3자 합의 사안이다).
대신 **두 파일이 서로를 모르는 상태를 끝냈다** — 양쪽 주석에 상대의 존재와 이 문서를 박았다.
`StickMateDisplayNames.cs:6`은 **"생산자 중 하나"로 낮추지 않았다** — 그렇게 쓰면 **결함이 설계처럼
보인다.** 원문을 인용하고 "거짓이다 / 틀린 것은 코드다"라고 명시한 뒤 통합 판정을 가리켰다.

## 8. 감사로 잠글 수 있는 것 (리더 승인 필요 — 아직 안 만들었다)

R1이 만든 `Tests/EditMode/CommentReferenceAuditTests.cs`는 **주석이 지목한 `*.cs` 파일 경로**를 잠근다.
이번에 나온 **6건은 전부 그 그물을 통과한다** — 파일이 아니라 **심볼**을 지목했기 때문이다.

**제안: 같은 파일에 검사 1개 추가** (새 파일 아님, `CommentReferenceAuditTests`에 편입)

> `주석이_지목한_우리_타입의_멤버가_실재한다`
> — 주석의 `Type.Member`를 뽑아, `Type`이 이 저장소의 타입일 때만 `Member`가 **코드에** 있는지 본다.

설계 규칙 3개(전부 이번에 내가 당해서 알아낸 것):
1. **심볼 사전은 주석을 제거한 소스에서만 만든다.** 안 그러면 §6-(나)처럼 주석이 자기를 증명한다.
2. **식별자 정규식은 `[A-Za-z_가-힣]`로 시작한다.** 한글 테스트 이름이 이 저장소의 절반이다.
3. **양성 대조 2개를 테스트 안에 박는다** — 실재 심볼이 찾아지고 가짜 심볼이 안 찾아지는지.
   깨지면 그 실행의 0건을 전부 폐기한다.
4. 이미 알려진 6건은 **명부에 담아 `Assert.Ignore`**로 러너에 계속 보이게 하고,
   고쳐지면 **실패**시켜 명부를 지우게 한다(R1이 쓴 래칫과 같은 방식).

**비용**: 검사 1개 + 대조 2개, 반나절. **가치**: 이번에 사람이 반나절 들여 찾은 종류가 자동으로 걸린다.
